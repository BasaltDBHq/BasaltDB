## CLI

Agents use MCP, people use pages, and the CLI only starts things. The CLI has four commands, no subcommands and six distinct flags. A person never types a `basalt` command: the agent runs `basalt init`, the MCP client runs `basalt mcp`, the service (or `basalt mcp`) runs `basalt engine`, and the engine's binary watch and `install.sh` run `basalt version`.

| Command | Who runs it | Flags |
|---|---|---|
| `basalt init` | the agent: starts setup, guard update, repair or removal, and prints one link | `--agent`, `--remote`, `--demo`, `--remove` |
| `basalt mcp` | the MCP client | `--agent` |
| `basalt engine` (hidden from help) | the service, or `basalt mcp` | `--config`, `--supervise`, `--started-by` |
| `basalt version` | the engine's binary watch and `install.sh` | none |

The six flags are `--agent`, `--remote`, `--demo`, `--config`, `--supervise` and `--started-by`. Anything else is a usage error. `--agent NAME` is needed only when the engine serves more than one agent. Exit codes: `0` ok, `1` error, `2` usage. No command has `--json`: an agent reads state through MCP.

**The surface budget.** `contract/surface.json` lists every command, flag, MCP tool, environment variable and page path. A test builds the real surface from the binary and the page tree and fails on any difference. Changing the file needs a maintainer's sign-off.

### Config discovery

Every command looks for `engine.json` at the system path (`/Library/Application Support/Basalt/engine.json` on macOS, `/etc/basalt/engine.json` on Linux), then at the user's path (`~/Library/Application Support/Basalt/engine.json` on macOS, `$XDG_CONFIG_HOME/basalt/engine.json` on Linux). When one exists, the command uses it. When both exist and the command names an agent (`basalt mcp --agent NAME`, `basalt init --agent NAME`), it uses the one that holds the agent (the config lists it; for a service engine's config the person cannot read, the socket directory has the agent's socket), and stops only when both hold it or neither does, with an error that names the agent and both paths. Without `--agent`, when both exist the command stops with an error that names both paths. `--config` exists only on `basalt engine`, which the service and `basalt mcp` start with the path they found.

### Environment variables

People set none. `BASALT_UPDATE_CHECK=0` stays: it turns off the [update notice](update-notice.md#update-notice). `BASALT_ADMIN_DATABASE_URL`, `BASALT_DATABASE_URL`, `BASALT_CACHE_DIR` and `BASALTDB_ALLOWED_HOSTS` are removed: the admin connection string is typed only on a setup page, the update notice's cache is the `basalt` folder of the user's cache directory, and the portal's allowed hosts are loopback and the listen address. The variables the binary sets for its own children stay and are listed in `contract/surface.json`.

### `basalt init`

`basalt init [--agent NAME] [--remote] [--demo | --remove]`. Run by the agent. It starts the [one setup flow](setup.md#the-one-setup-flow) and prints one link for the person; the person does the rest on the page. It reads the state (no config, a guard older than the binary, a problem `status` reports, or an installed agent) and the link opens the page for that job ([Setup jobs](setup.md#setup-jobs)). It never asks for, reads or accepts the admin connection string.

- **Persona 1** (person-operated). The link is the engine's [local setup page](setup-page.md#the-local-setup-page): the install link on a first install, and on an engine already set up the link where the person picks Update or Remove ([Which link `basalt init` prints](setup-page.md#the-local-setup-page)). On first install, `init` installs the engine as a service through the system's [administrator dialog](setup-page.md#the-administrator-dialog) before it prints the link, so the engine serves the page. On an engine already set up, `init` waits up to 90 seconds after it opened the link: when the page's Remove lands in that time it says the engine is removing itself and exits `0` at once, with no password dialog (the install's removal job removes the engine service); when the page's Update for the agent finishes, it says the agent can go on and exits `0` at once; otherwise it exits when the time is up; with `--demo` it also says on stderr that the demo needs a removal first (press Remove on the page, then run `init --demo` again), since the flag is not applied to an engine already set up. Once the removal job removed the engine, `init` (with or without `--demo`) installs again as a first install; an engine that still answers `ENGINE_REMOVED` (its job did not run) is set up again as a first install, with no removal and no dialog ([Removing the engine service](setup-page.md#the-local-setup-page)).
- **Persona 2** (`--remote`, agent-operated). The link is the [connect link](connect.md#the-connect-link) of a [connect-only setup code](setup.md#connect-only-setup-codes). `--remote` marks the engine agent-operated on first setup; afterwards the config says it, and the flag is not needed. The agent passes it because it knows whether a person sits at this machine and the engine cannot.
- **`--remove`.** Persona 1: the person asked to remove BasaltDB. On an engine that serves the agent, `init` prints and opens the agent's `REMOVE` link (no pick first) and waits as for the `CHANGE` link: the page has one box and one button ([Removing the engine service](setup-page.md#the-local-setup-page)). Where no engine service is installed it prints `basalt: BasaltDB is not set up on this computer, so there is nothing to remove.` and exits `0`, installing nothing. Where the engine serves no agent (a removal its removal job did not finish, or an engine that never had one), it removes the engine service with the fixed removal script through the [administrator dialog](setup-page.md#the-administrator-dialog), one password: no `ENGINE_REMOVED` engine is left as a dead end. With `--demo` it is a usage error; `--remote` takes no `--remove` (a bot's computer is removed on the connect page).
- **`--demo`.** Sets up the sample database (below) in the same flow.
- **Opening the link.** On persona 1, `init` opens its own link in the browser by the [Auto-open](#auto-open) rule (only a link whose origin is the engine's own local page origin) and prints it too. On persona 2 it opens nothing.
- **Output.** The person's link on its own line. On first setup, also the `basalt mcp` line the agent registers with its MCP client: that line is for the agent, not the person. Nothing else on stdout.

The rules below hold for every job, whichever page runs the SQL.

- **Plain agent roles only.** Whenever init gives a role `<prefix>_agent_<name>` that already exists `LOGIN`, a password or `<prefix>_agents` (keeping its password, a repair that sets a new one, or an `AGENT` setup code), the same SQL first refuses, with `BS008` (`LEDGER_INPUT_INVALID`) and nothing changed, a role that is not a plain agent: one that has `SUPERUSER`, `CREATEROLE`, `CREATEDB`, `REPLICATION` or `BYPASSRLS`; that is a member (directly or not, inheriting or not) of any role other than `<prefix>_agents` (an allow-list: predefined roles such as `pg_read_all_data`, `pg_monitor` or `pg_signal_backend`, `<prefix>_guard`, and any other group are all refused); that owns, or is a member of the owner of, the database or any object in it (`pg_shdepend`; the owner of a function, view or default a guarded write runs could replace it and run code as the next writer); or that holds a direct privilege on anything in `basalt_meta`, or `TRUNCATE`, `TRIGGER`, `REFERENCES` or `MAINTAIN` on an agent or guarded table. It then resets the role's own settings (`ALTER ROLE ... RESET ALL`, everywhere and `IN DATABASE` this one) before setting `statement_timeout` and `CONNECTION LIMIT 8`, since a setting such as `session_replication_role = replica` would keep the guard's triggers from firing; a setting the admin may not reset (one only a superuser may set, when the admin is not one) is refused. An `AGENT` setup code also refuses a role outside `<prefix>_agents`.

- **The agent's connection string** is built from the admin's: its scheme, hosts, ports and database, the agent's user (`<prefix>_agent_<name>`, or `<prefix>_agent_<name>.<ref>` through Supabase's pooler) and password, and only these parameters: `host`, `port`, `dbname`, `sslmode`, `sslrootcert`, `sslcrl`, `sslcertmode`, `sslnegotiation`, `sslsni`, `channel_binding`, `require_auth`, `target_session_attrs`, `connect_timeout`, `application_name`, `min_protocol_version`, `max_protocol_version` and `default_query_exec_mode`. Every other parameter is dropped, among them `user`, `password`, `passfile`, `service` and `servicefile`, and the admin's TLS client identity `sslcert`, `sslkey` and `sslpassword`. The admin connection string must be a `postgres://` or `postgresql://` URL; a keyword/value string, or a URL that does not parse, is refused before anything connects.
- **Re-running keeps the agent's password** when its role exists. A new password is set only by a repair job the person confirms on the page.

- **Replication role default.** Every install and guard update (on the setup page or by the connect service) reads the default of `session_replication_role` a new session in the database gets: `ALTER DATABASE ... SET` first, then `ALTER ROLE ALL SET`, then the server's (`postgresql.conf`, `ALTER SYSTEM`, the command line; not read when the admin's own role settings hide it). When it is not `origin` the page shows, before the SQL runs, `basalt: warning: the database default of session_replication_role is <value>, not origin. ...` with the statement that fixes it (`ALTER DATABASE <db> RESET session_replication_role;`, `ALTER ROLE ALL RESET session_replication_role;`, or `ALTER SYSTEM RESET session_replication_role; SELECT pg_reload_conf();`), and go on. A warning, not a refusal: the guard's triggers fire in any mode ([Guard triggers fire under any `session_replication_role`](basalt-meta.md#guard-triggers-fire-under-any-session_replication_role)), so only foreign keys and the person's own triggers stop in agent sessions.

**The sample database** (`--demo`, the docs quickstart). The same setup for a sample database.

- **What it creates.** The schema `basalt_demo` with `leads` (30 rows) and `lead_notes` (20 rows, two each on leads 1 to 10, `ON DELETE CASCADE` from `leads`), with row-level security off, from SQL embedded in the binary. It creates the agent `demo_bot` (`--agent` renames it) with write access to `basalt_demo.leads` and `basalt_demo.lead_notes` and nothing else; No other table can be added with `--demo`. `USAGE` on `basalt_demo` and the agent's grants are the only access it gets; no other schema gets a table, a change or a grant. Apart from `basalt_demo`, init adds only what it always adds: `basalt_meta`, the roles and the engine setup. The page asks no row-level security question: it is off on the tables it creates. When a sample table left by an earlier demo (the schema carries the comment `BasaltDB demo data`) has row-level security on, for example after a Remove that kept the schema and a provider's table editor that turned it on, the install adds the agent's policy on it (`FOR ALL`, as a real install's `ALL_ROWS` answer does) and leaves row-level security on, so the agent sees and writes every row. A `basalt_demo` without the comment gets no policy.
- **One confirmation, nothing kept before yes.** The page shows the sample-data SQL and the setup SQL (passwords redacted) and asks once for both. To plan the guard init needs the sample tables to exist, so it creates them in a transaction on the admin connection, plans, and rolls that transaction back before it prints the summary and asks: nothing is committed, and nothing is held open, while the person decides. On yes, it creates the sample data again and applies the install in one fresh transaction that commits once, so a change made meanwhile is caught by the check that every agent-writable table is guarded.
- **Safe to run again.** When `basalt_demo.leads` and `basalt_demo.lead_notes` both exist, init leaves their rows as they are (it never reseeds over a person's edits), the page says `sample schema basalt_demo already exists; its rows are left as they are`, and installs and guards as usual. When only one exists, init creates the other with its rows, its index and row-level security off, and does not touch the one that exists (no row, index or row-level security change); when the existing `leads` does not have the ids or the columns `lead_notes` needs, the statement fails with the database's error and the transaction rolls back. A re-run keeps the agent's password as init does.
- **The comment.** Init sets the schema comment `BasaltDB demo data` only when it creates the schema in that run, never on a `basalt_demo` that already exists (one from `examples/demo/seed.sql` or made by hand).
- **Output.** When it is done, the page shows `demo ready: leads 30, lead_notes 20` (the counts are read from the tables, so a re-run shows the current ones).
- **Removal.** The removal job removes `basalt_demo` before it drops `basalt_meta` and the roles, in the same transaction, only when the schema carries the comment `BasaltDB demo data`. It runs `DROP TABLE basalt_demo.lead_notes`, `DROP TABLE basalt_demo.leads` and `DROP SCHEMA basalt_demo`, never with `CASCADE`, so it cannot drop a person's view, foreign key or table that depends on or sits in the schema. When one of those statements fails (something outside depends on the tables, or the schema holds other objects), uninstall skips the demo removal, rolling back only those three statements, the page shows `demo schema basalt_demo kept: <the database's message and detail>`, and still removes everything else. A `basalt_demo` without the comment is not touched. On success the page shows `demo schema basalt_demo dropped`. The page's confirmation names the schema.

### `basalt mcp`

`basalt mcp [--agent NAME]`. Run by the MCP client. It finds the config ([Config discovery](#config-discovery)), connects to the agent's socket and serves MCP on stdio. When the engine is down it answers `status` from the config. It starts the engine itself (`basalt engine --config <the path it found> --supervise --started-by mcp`) only for a same-user config, never a service engine's ([`basalt mcp` starts a same-user engine](next-steps.md#next-steps)); a service engine is the service manager's to start.

### Auto-open

When the engine is person-operated (`operatedBy: PERSON`) and a result carries a link to the engine's own local page origin, `basalt mcp` opens it with `open` (macOS) or `xdg-open` (Linux), and still passes the result, link included, to the agent. The agent always shows the link too, so the person can open it by hand when the browser did not open (an SSH session, no screen, a blocked opener). The result's `personMessage` carries the link unchanged on both personas.

- It opens only a link that parses and whose origin (scheme, host and port) equals the engine's local page origin. It never opens any other URL from a result.
- It never opens anything on an agent-operated engine.
- There is no flag to turn it on or off.
- `basalt mcp` learns both from the engine's answer to its hello ([Version negotiation](next-steps.md#next-steps): `operatedBy` and `pagesOrigin`), not from `engine.json`, which a service engine's agent cannot read. An engine that gives neither (one older than this rule, or one that stays silent) gets nothing opened. The answers of `basalt mcp` itself, while the engine is down, open nothing.
- It reads the links only from the result's `links` lists of the call that hands the link over (the body's and its `approval`'s: a held write, `request_revert`, a plugin approval, a passkey or setup page), never from list items (`list_pending`), status problems, free text or query rows, and opens each link once per `basalt mcp` process. The result reaches the agent unchanged and never waits on the browser.

### `basalt engine`

Hidden from help. Run by the service manager, or by `basalt mcp`.

- `basalt engine [--config PATH] [--supervise] [--started-by hand|mcp|crash]`: runs the engine in the foreground, and restarts it onto a new `basalt` binary installed at the path it was started from ([Next steps](next-steps.md#next-steps), Restart onto an upgraded binary). **`--supervise`** runs the engine as a child of a small parent that restarts it when it exits with an error: after `1s`, `2s`, `4s`, `8s`, `16s`, then `30s` between restarts (the wait starts again at `1s` after a child that stayed up at least 10 seconds), and it gives up, exit `1`, after 5 exits in a row within 10 seconds each of their start, writing `crashed 5 times within 10s; last: <error>` to its output and `{ "reason", "at", "engineSha256" }` (`at` RFC 3339 UTC; `engineSha256` the lowercase hex SHA-256 of `engine.json` at the give-up) to `last-stop.json` in the state directory, removed again once an engine, supervised or run by hand, has stayed up 10 seconds. One supervisor runs per config (a `supervise.lock` flock in the socket directory): a second one prints `another basalt engine --supervise runs for this config` and exits `0`. A child that stops with status `0` ends the supervisor with `0`; a child that fails because another engine already holds the config's engine lock ends it with `0` too (an engine started by hand beside it is never crash-looped against), and SIGTERM or SIGINT to the parent stops the child and exits `0`. The child stops when its supervisor dies, so a killed supervisor never leaves an engine nobody restarts: on Linux the kernel sends the child SIGTERM (`Pdeathsig`); on macOS the child notices its parent is gone and stops. A crash restart runs the binary at the path the supervisor was started from, resolved again at each restart; when that path is gone, the supervisor writes `the basalt binary <path> is gone` to its output and to `last-stop.json` and exits `1`, instead of looping on a missing file. The upgrade restart is the child's own exec onto the new binary, so the parent never sees it as an exit. `--supervise` runs as the engine's own user. Before it takes the engine lock, a same-user engine makes its state directory, and its socket directory when every configured agent's OS user is its own, with mode `0700`: a missing one is created, one it owns with group or other permission bits (an update of a bot's computer resets folders to `0755`) is set back to `0700`, one another user owns is left as it is, and a symlink there stops it with exit `1`. A service engine's folders are its service manager's and are not changed. A socket file nothing answers on and a lock file left by a killed engine never block a start (the lock is a kernel `flock`, never read for a pid, and nothing decides by a file's age); a credential file whose mode is not `0600` is still refused, never changed. **`--started-by`** says why this engine starts: `hand` (the default), `mcp` (`basalt mcp` found the engine down) or `crash` (the supervisor restarted it); `status` reports it as `engine.startedBy`, `HAND`, `MCP` or `CRASH`; the supervisor passes its own value to its first child and `crash` to every restart; any other value is a usage error. A service engine that finds no `engine.json` waits and serves only the setup page ([The local setup page](setup-page.md#the-local-setup-page)). Started as root, the engine reads its config this way: reached from `/` without following a symlink anyone but root controls, a regular file with one link owned by root or its directory's owner and not writable by group or others; anything else stops it with exit `1` before it starts. It then reaches each agent's files the way root's `basalt init --remote` does ([`basalt init --remote`](setup.md#basalt-init---remote-the-engines-machine), step 8): the credential file must be `agents/<agent>.url` next to the config (a `store.credentialFile` anywhere else stops that agent: `... as root, basalt engine uses only that path. Fix the agent's store.credentialFile in the config`), and the config directory and `agents/` are opened once at start, from `/` without following a symlink anyone but root controls (every directory on the way owned by root or the config directory's owner, not writable by group or others); the credential file, its `.pending` and its `.lock` are then read, locked and renamed relative to `agents/`, and `engine.json` is locked, read and rewritten (when a setup is cleared) relative to the config directory, so a directory swapped for a symlink after the start redirects nothing. It reads a credential file or `.pending` that is a regular file with one link, mode `0600` or tighter, owned by root or by the owner of `agents/`, and from one the owner of `agents/` wrote it takes only what root's `basalt init --remote` takes from it (step 8: a `postgres://` or `postgresql://` URL with a password and no parameter that makes the driver read a file), else that agent stops (`... as root, basalt engine takes from it only a postgres:// or postgresql:// URL ...; fix the file`), never echoing the string; a symlinked `.lock` is refused as a lock file that cannot be used. Not as root, the engine and the setup page read an agent's `store.credentialFile` by its path with the same file rules: opened without following a symlink at the path, a regular file with one link, owned by this process's user or root, mode `0600` or tighter, checked on the descriptor it reads. A symlink there (`credential file <path> is a symbolic link; ...`, a dangling one included), a second hard link (`credential file <path>: file has more than one hard link`) or another owner (`credential file <path> is owned by uid <uid>, not this process's user or root`) is refused like a credential the engine cannot read: that agent does not start, and the setup page's `UPDATE`, `REMOVE` and `REPAIR` answer `SETUP_FAILED`, never taking a symlink for a missing file.

- Engine config (`engine.json`) also takes `stateDir` (default `/var/lib/basalt` on Linux, the systemd `StateDirectory`; `/Library/Application Support/Basalt/state` on macOS): the engine keeps each agent's last verified chain head there (`<stateDir>/<agent>.head.json`, mode `0600`, with `installId`, the guard install it was verified on, and `setAside`, its kept copy of the pins it set aside) and verifies from it on start and every hour.

- **One engine, many agents.** One engine may serve many agents. `engine.json` lists them under `agents`, each with its own name, OS user, socket (`<socketDir>/<name>.sock`) and credential (`store.credentialFile`, the connection string of its own `<prefix>_agent_<name>` role). Those credentials may point at different databases on different hosts, or at the same one. The engine opens a separate connection pool for each agent from that agent's credential; agents never share a credential or a connection. An agent's ledger, grants, connections and status are scoped to that agent and its database: the change record and its chain live in that database's `basalt_meta` (the engine pins the agent's verified chain head in `<stateDir>/<agent>.head.json`), its grants are the ones init gave its role there, and the `status` tool on its socket reports that agent and its database only. The connection limit is per agent role, not an engine-wide pool: init sets `CONNECTION LIMIT 8` on each agent role and the engine's pool for each agent opens at most 4 of them, so an agent at its limit (`TOO_MANY_CONNECTIONS`) does not take connections from another agent on the same engine. Neither MCP tool, `status` or `describe`, ever names another agent or its database. Each agent uses exactly one database. One agent across several databases, and a run, read or revert that spans databases (through `dblink`, a foreign data wrapper or otherwise), are not available.

### `basalt version`

`basalt version` prints `basalt <version>` on one line and exits `0`. It takes no flag.

### Portal check

The hosted portal must serve exactly the pages a release embeds. The release workflow's `portal-check` job runs `make portal-verify` after the release: it fetches every embedded file and page route from the portal (read-only, over HTTPS) and checks the embedded pages against `web/portal.sha256`, and fails on any file that differs, is missing, unexpected or could not be checked. A maintainer runs the same with `make portal-verify` (`go run ./scripts/portal-verify`, which also takes `--portal-url`). The engine's own daily check is unchanged and reports `PORTAL_MISMATCH` in `status` ([Next steps](next-steps.md#next-steps)).

### Removed

Everything below is removed. Where a section file not yet rewritten still names one of these as current, this list wins.

- **Commands:** `log`, `status`, `approve`, `access`, `classify`, `passkey`, `upgrade`, `uninstall`, `service`, `trust`, `crash`, `plugin`, `portal` (`portal verify` is now the release workflow's [portal check](#portal-check)), `tunnel`, and the subcommands `engine list`, `engine revoke` and `engine rotate-key`. (`log`, `status`, `access`, `crash`, `portal`, `upgrade`, `uninstall`, `engine list`, `engine revoke`, `engine rotate-key` and `service uninstall` are gone from the binary; the guard update and the removal run on the [setup page](setup-page.md#the-local-setup-page), and after a removal `basalt init` removes the engine service through the [administrator dialog](setup-page.md#the-administrator-dialog) once the person picks that on the page.) What they did goes to the agent through MCP, to the [setup flow](setup.md#setup-jobs), or to the pages: no command or page revokes an engine, and removing BasaltDB cuts one off ([Engine revocation](vault-channel.md#engine-revocation)); a saved crash report is named in the `status` result with the link to file it; plugins are prepared by the agent and approved on the plugin approval page.
- **`basalt approve` and `basalt revert`.** Removed in every mode, now that the relay is live, together with the pasted approval and revert codes on every page, `write`'s `approval` argument and `request_revert`'s `signature`. Persona 2 signs on the portal and the relay carries the signature; persona 1 signs on the engine's own pages. `basalt revert`'s last two jobs are covered without it: a whole-task revert is `request_revert` with `taskId`, widened to other agents' changes on the signing page; a revert too large to prepare in `request_revert`'s 100 seconds is split by the agent into narrower reverts (`runs`, `tables`, or one `changeId` at a time), each prepared and signed on its own. Limit, accepted: the command's 10-minute prepare is gone, so a scope that stays too large to prepare in 100 seconds even narrowed to one change and one table (a change with very large cascades, or the redo of a large revert) cannot be reverted through BasaltDB. Second limit, accepted: a task revert is started only by an agent that has its own lines in the task (`request_revert` with `taskId`); the command's empty proposal is gone, so a task in which no reachable agent changed rows cannot be reverted as a task (`NOTHING_TO_REVERT`; its message says to ask an agent that changed rows in the task).
- **`basalt init` flags:** `--setup-code`, `--write`, `--read`, `--all-tables`, `--os-user`, `--engine-user`, `--socket-dir`, `--prefix`, `--statement-timeout`, `--no-service`, `--rotate-password`, `--skip-passkey`, `--passkey-label`, `--passkey-origin`, `--add-passkey`, `--new-code`, `--forget`, `--database-url`, `--credential-file`, `--operated-by`, `--person-uid`, `--trust-root`, `--direct-addr`, `--pages-url`, `--json`, `--yes`, `--dry-run`, `--show-sql`, `--agent-rls`, `--dev-local-pages`. Tables and row-level security policies are picked on the page; the defaults those flags changed are fixed values chosen once. The page shows the SQL, so there is no `--show-sql` or `--dry-run`.
- **Saved flags.** `initArgs` in `engine.json`, the saved-flag replay on a re-run and `savedInitFlags` in results are removed: `basalt init` takes no setting to save, and `basalt init --remote` reads none back. An older `engine.json` that still has `initArgs` loads; the key is ignored and the next write leaves it out. `service install --init-arg` is accepted and refused when it holds a secret, and its value is not saved. The database's grants are the only record of an agent's tables.
- **The terminal setup.** The admin-string prompt, the row-level security checklist, the passkey registration hand-back and its pairing code, the `Install the engine as a background service?` question, `sudo basalt service install`, and the offer to run `claude mcp add` are removed. The setup page does each of them; the `basalt mcp` line stays in `init`'s output for the agent.
- **`basalt mcp` flags:** `--config`, `--socket-dir`, `--credential-file`.
- **`basalt engine` flags:** `--user`, with the engine's own privilege drop and the container example (no real user runs the engine as root in a container), and `--plugin-debug`. Both are gone from the binary.
- **The person socket.** Removed whole, with the person's commands that used it, the per-user config fallback and the root rules for the person's CLI; it is gone from the engine. The agent-context markers go with the commands they guarded. `request_plugin`'s upload goes over a second connection to the agent's own socket ([`request_plugin`](mcp-tools.md#mcp-tools)). `personUids` stays: an agent changes plugins only while it runs as a recorded person. Not yet rewritten: [Plugin approval in service mode](plugins-approval-service-mode.md#plugin-approval-in-service-mode) still describes the plugin methods (`PLUGIN_OPEN`, `PLUGIN_LIST`, `PLUGIN_DISABLE`, `PLUGIN_REMOVE`) as requests; they now run in process behind `request_plugin`, and only the two upload methods are on the wire.
- **The direct transport.** The engine's direct listener, `directAddr`, the engine address pinned in the database, `basalt tunnel`, `web/lib/direct.js`, `web/lib/pins.js` and the portal's `/engines` pages are removed. Every persona 2 signature reaches the engine through the relay.
- **CLI JSON schemas** under `api/` (`remote-init-result`, `portal-verify-result`, the plugin `--json` results). They are gone. `classify-review` stays: no command prints it any more, but it holds the PII classes and entity types the contract test checks.
- **`classify`, `passkey` and `trust`.** Their jobs are the fixes of the setup page's [Update check](setup-page.md#the-update-check) (labels, passkeys, a changed certificate) and of [Update on the connect page](connect.md#update-on-the-connect-page); the `/passkeys/check` and `/passkeys/forget` pages go with `passkey`. Every hint, step and message that named one says to run `basalt init` (`basalt init --remote` on an agent-operated engine).
- **Pasted codes.** No command, tool or page reads or shows a pasted approval or revert code.
- **Person commands in results.** Next steps never tell the person to run a command: a person's step is a link to a page ([Next steps](next-steps.md#next-steps)). The agent's own steps stay as MCP `nextSteps`.
