## Setup page

Persona 1's setup page, served by the engine on loopback, with its install, its Update check and the administrator dialog `basalt init` uses around them. The flow and the jobs are in [Setup](setup.md#setup).

### The local setup page

Persona 1. The engine serves the setup page on its loopback listener, at the same origin as its approval and revert pages, so the passkey it registers signs there.

- The admin connection string travels from the page to the engine over loopback. The engine, which runs as its own OS user, uses it once for the job's transaction and never writes it to a file, a log or the engine config. It refuses the admin string on every route but the setup page's own.
- The listener keeps the `websec` Host, Origin and header checks of the other local pages.
- **An engine with no config.** On a first install the [administrator dialog](#the-administrator-dialog) starts the service before `engine.json` exists. A service engine (started as its own OS user from the system config path) that finds no `engine.json` does not exit: it serves only `GET /healthz`, the setup page and the two setup routes below on `127.0.0.1:8787` (origin `http://localhost:8787`), and waits. When the first install writes `engine.json`, the engine loads it and serves the agent without a restart. Under `--supervise` this counts as up, so the supervisor never crash-loops on a missing config. When `127.0.0.1:8787` is taken, it exits `1` and names the port and how to find the process, as the [listener](local-pages.md#local-pages) does. Any other config error still stops it with exit `1`.
- **An engine with a config.** A person-operated engine that runs as its own OS user and serves its local pages at `http://localhost:8787` serves the same page and the same two routes there, and `doctor`, `engine` and `not-mine`, for the `UPDATE`, `REMOVE` and fix jobs of the agents in its `engine.json` and the question [Not your database](#not-your-database). It never runs an `INSTALL` (`JOB_UNAVAILABLE`), but one: after a `REMOVE` deleted its `engine.json`, an `INSTALL` runs as on an engine with no config, and once it wrote `engine.json` the engine reads it again and serves it, in the same process and with no restart of the service ([Removing the engine service](#the-local-setup-page)). An agent-operated engine, or one started as root, refuses every setup request `JOB_UNAVAILABLE` without reading it; the jobs themselves refuse root as well.
- **The link.** `basalt init` prints `http://localhost:8787/setup/#1.<b64url(json)>`, with `{ "job", "agent", "osUser" }` and `"demo": true` only for an `--demo` install: `job` `INSTALL`, `UPDATE`, `REMOVE` or `CHANGE`, `agent` the `--agent` name (default as `basalt init` picks it), `osUser` the OS user `basalt init` runs as (the agent's), `demo` is in the link only when `--demo` was given (never for `UPDATE`, `REMOVE` and `CHANGE`); the page reads a missing one as `false`. The fragment never reaches a server or a log. It is not a secret ([Holding the link is not enough](setup.md#setup-jobs)). The page shows the job, the agent and its OS user before anything is asked. The agent writes the link, so the person confirms `osUser` on the page: it is the OS user the agent runs as and the one the agent's socket admits. A `REMOVE` link asks no such confirmation: its admin connection string is the whole confirmation, and the engine checks `osUser` against `engine.json`.
- **Jobs.** `INSTALL` for an engine with no config; `UPDATE` (the [guard update](setup.md#setup-jobs)), `REMOVE` (Remove Basalt), and the fixes of [The Update check](#the-update-check), `LABELS`, `TRUST`, `REPAIR`, `PASSKEY_ADD` and `PASSKEY_REMOVE`, for an agent of an engine with a config. An `INSTALL` with `demo` sets up the sample database; one without `demo` is the [install of a real database](#the-install-of-a-real-database), with its tables, PII classes, passkey and certificate pin, and the engine refuses it with no table `NO_TABLES`. `basalt init` without `--demo` prints that `INSTALL` link.
- **Which link `basalt init` prints.** With `--remove` ([`basalt init`](cli.md#basalt-init)), on an engine that serves the agent, the agent's `REMOVE` link. On an engine with no config, the `INSTALL` link. On an engine with a config (its setup routes answer `JOB_UNAVAILABLE` to an empty request), plain `basalt init [--agent NAME]` prints and opens the `CHANGE` link, with no new flag and no `basalt mcp` line; `--demo` is ignored there. `CHANGE` is a link only: the page opens on [The Update check](#the-update-check), which offers the fixes it found and, under **Update or remove BasaltDB**, Update the guard and Remove BasaltDB; it sends the `job` of the one the person picks. Nothing runs before a pick, and a request with `job` `CHANGE` is refused `INVALID_ARGUMENT`. On an engine a `REMOVE` removed whose removal job did not remove it yet (`ENGINE_REMOVED`), `basalt init` prints `basalt: BasaltDB was removed from your database earlier. Setting up again on this computer's engine.` and the `INSTALL` link, with or without `--demo`; `basalt init --remove` removes the engine service through the administrator dialog ([`basalt init`](cli.md#basalt-init)). Before it opens the admin-string field, the page of an `UPDATE` or `REMOVE` link sends `check` for the link's job with an empty `databaseUrl` (a `CHANGE` link sends `doctor` instead, [The Update check](#the-update-check)): the engine checks the agent and its OS user before the admin string, so `CONNECTION_STRING_REFUSED` means the agent is this engine's, and any other refusal is shown instead of the field (an agent `engine.json` lacks says to run `basalt init --agent NAME`). While a check or a run is in flight the choice is locked; a pick changed after a check drops that check's answer.
- **The `UPDATE` link in next steps.** An engine that serves these jobs gives each agent's `GUARD_OUTDATED` and `GUARD_UPGRADE_AVAILABLE` steps the agent's own `UPDATE` link (`{ "job": "UPDATE", "agent", "osUser" from engine.json, "demo": false }` at its origin) as a P `OPEN_LINK`, in place of the agent's `basalt init` step ([Next steps](next-steps.md#next-steps)). An engine that does not serve them keeps the `basalt init` step. A guard below the update floor ([An older install](#the-local-setup-page)) never gets the `UPDATE` link, which cannot update it: its `GUARD_OUTDATED` steps keep the `basalt init` step, and their `personMessage` says to remove the install first, with the link to [Remove an older install](../docs/remove-old-install.md), then set up again; status gives such an agent no `NO_PASSKEY` problem.
- **Removing the engine service.** After opening the `CHANGE` link, `basalt init` polls the engine for up to 90 seconds with [the probe](#not-your-database): `ENGINE_REMOVED`, or no answer while the system config's folder is gone (the removal job already removed the engine), ends the wait at once: it prints `basalt: BasaltDB is removed from your database, and the engine is removing itself from this computer. The page shows when it is done; nothing more is needed here.` to stderr and exits `0`, with no password dialog; `GUARD_UPDATED` (the page's `UPDATE` for the link's agent ran after `basalt init` opened the link) ends the wait at once, prints `basalt: the guard is updated on the setup page. The agent <agent> can go on; it needs no restart.` to stderr and exits `0`; when the time is up it prints `basalt: this init stops waiting. Run status to see what the page changed; show the person the link above again only if they ask.` and exits `0`. A fix the page finishes for the agent after the link opened (`TRUST`, `LABELS`, `PASSKEY_ADD`, `PASSKEY_REMOVE`, `REPAIR`) also ends the wait at once, for every `basalt init` waiting for that agent: the probe is answered `CHANGED_<job>` (`CHANGED_TRUST`, …), and `basalt init` prints `basalt: the setup page finished a change for the agent <agent>: <what>. The agent can go on; it needs no restart.` with `<what>` one of `the database's certificate is checked`, `columns are labeled`, `a passkey is added`, `a passkey is removed`, `the agent's login is fixed`, and exits `0`. A fix that finished before the link opened never ends it. The engine keeps the last fix of each agent, with its time, in memory only. `GUARD_UPDATED`, `AGENT_REMOVED` and `CHANGED_<job>` come after `ENGINE_REMOVED` and `RESET_ASKED`. A `REMOVE` that deleted `engine.json` (the engine's last agent) answers `engineRemoved` `true`, and the engine then creates the [removal job](#the-administrator-dialog)'s marker, an empty file `remove-requested` in its config folder, and answers `engineRemoving` `true` (`false`, with the warning `this engine could not ask to be removed from this computer, so it stays, serving no agent: <error>`, when it could not create it). The job stops the engine and removes it from this computer; the person does nothing more. The page shows a checklist in place of the done text: `✓ Removed from the database <database>`; `Removing from this computer…` while `GET /healthz` still answers (the page asks every second, for up to 60 seconds), then `✓ Removed from this computer` once it fails, or `This computer: the engine is still running. Ask your agent to run basalt init --remove: your computer asks for your password once and removes the rest.` when the 60 seconds are up; and `Agent connection: your agent drops it the next time you talk to it.` The title is `Removing BasaltDB…` while it waits and `BasaltDB is removed` once the engine stopped, with `From the database <database> and from this computer. You can close this tab.` On macOS one small line follows, with no command: `macOS keeps BasaltDB's hidden system account, _basalt. A new setup uses it again.` ([`docs/install.md`](../docs/install.md) gives the commands for anyone who wants it gone). A `REMOVE` that leaves other agents on the engine shows `This computer: the engine stays, serving your other agents.` and `Agent connection: this agent's calls to that database now fail; your other agents go on.`, creates no marker, and answers the waiting `basalt init`'s probe for that agent `AGENT_REMOVED` (`409`), which ends its wait at once with `basalt: BasaltDB is removed from the database of the agent <agent>. The engine stays on this computer for its other agents.`; one whose marker could not be created shows `This computer: the engine stays, serving no agent (the warning below says why).` Until the job stops it, the engine answers every setup request but an `INSTALL` `ENGINE_REMOVED` (a `run` of `REMOVE` that names an agent and carries no `databaseUrl` (the one the page of a `REMOVE` link sends when it finds the engine removed) also creates the removal job's marker again, and a `check` never does; that page then shows the checklist), and the fix steps of its agents' failing calls and `status` (`CREDENTIAL_REJECTED`, `GUARD_MISSING`, `GUARD_OUTDATED`) are the steps of `REMOVED` ([Next steps](next-steps.md#next-steps)): A `STOP` that tells the agent to remove its own MCP entry. After the job, `basalt mcp` finds no engine and no config folder, and `status` answers the problem `REMOVED` with the same step.
  - **Plain `basalt init` on a removed engine** (one whose probe answers `ENGINE_REMOVED`: its removal job did not run, as on an engine installed before the job and not restarted since) never removes anything (`basalt init --remove` removes it through the administrator dialog, [`basalt init`](cli.md#basalt-init)): it prints `basalt: BasaltDB was removed from your database earlier. Setting up again on this computer's engine.` to stderr and goes on as a first install, with or without `--demo`: the `INSTALL` link and the `basalt mcp` line, no dialog. Once the job removed the engine, `basalt init` installs as on a computer that never had BasaltDB, with the administrator dialog's password once; on macOS the install takes over the `_basalt` account and group the removal kept.
  - `RESET_ASKED` runs the [reset](#not-your-database) script instead.
- **What the engine takes from the request.** `agent` must be a valid agent name and not in `engine.json`. `osUser` must be an existing OS user that is neither root nor the engine's own user, and not in the engine's group. The engine chooses the rest: the prefix `basalt`, the statement timeout `30s`, the agent's password (256 bits, generated in the engine, never in a request or an answer), the credential file `agents/<agent>.url` (mode `0600`, the engine's own user) and the agent's entry in `engine.json` (`operatedBy` `PERSON`, the local pages). For `demo`, it creates the sample schema as [`--demo`](cli.md#basalt-init) says. For `UPDATE`, `REMOVE` and the fix jobs (`LABELS`, `TRUST`, `REPAIR`, `PASSKEY_ADD`, `PASSKEY_REMOVE`): `agent` must be in `engine.json`, `osUser` must be the OS user `engine.json` gives it, `demo` must be `false`; `UPDATE` and `REMOVE` carry no `answers`, `challenge` or `passkey`, and a fix job carries only the fields [The Update check](#the-update-check) gives it (`ANSWERS_INVALID`). The admin connection string must name the database the agent's credential connects to, compared as [The setup checks](setup.md#the-setup-checks) compare a target (host, port and database, or the Supabase project ref and database), before anything connects with it: another database is `TARGET_MISMATCH`, and a string that names more than one host `CONNECTION_STRING_REFUSED`. The string takes only the parameters a connection to the server needs: `application_name`, `channel_binding`, `connect_timeout`, `default_query_exec_mode`, `max_protocol_version`, `min_protocol_version`, `require_auth`, `sslmode`, `sslnegotiation`, `sslsni` and `target_session_attrs`. Every other one, in any case, is `CONNECTION_STRING_REFUSED` before anything connects, with a fixed message that lists these and names neither the parameter nor its value: among them the file-path keys `passfile`, `service`, `servicefile`, `sslkey`, `sslcert`, `sslrootcert`, `sslcrl` and `sslcrldir`, so the engine never reads a file a pasted string names, and `host`, `hostaddr`, `port` and `dbname`, which would name another target. A private CA is trusted with the certificate step (`trustRoot`), not a root file in the string. A credential the engine cannot read is `SETUP_FAILED`.

|---|---|---|
| `GET /setup/` | | The setup page. It reads the job from the fragment |
| `POST /api/v1/setup/doctor` | `agent`, `osUser` | The [Update check](#the-update-check)'s answer. No `databaseUrl`: it reads with the agent's own credential |
| `POST /api/v1/setup/engine` | `{}` | `200 { "agents", "databases" }`: what the engine is set up with ([Not your database](#not-your-database)). It reads the engine's own files only |
| `POST /api/v1/setup/not-mine` | `{}` | `200 {}`: the person answered `No, this isn't mine`; a mark for `basalt init` that changes no file and no database |
| `POST /api/v1/setup/check` | `job`, `agent`, `osUser`, `demo`, `databaseUrl` | `200 { "database", "lines", "sql", "questions", "notes", "passkeyNeeded", "challenge", "replace" }`; `replace` only on an `INSTALL` that replaces a guard below the update floor ([An older install](#the-local-setup-page)); a `REMOVE` also answers `host`, the admin string's host and port in lowercase; an `UPDATE` or `REMOVE` answers without `challenge`, with `passkeyNeeded` `false` and no question. It connects with `databaseUrl`, reads and changes nothing in the database; an `INSTALL` check makes the engine's key file when there is none, as the engine's first start does, to show its `record_engine`. `lines` is the fixed summary, and `sql` the SQL with passwords redacted. `questions` are the row-level security questions (`kind` `ROW_LEVEL_SECURITY`, `table`, `text`, `choices` `ALL_ROWS` or `NONE`). `challenge` has the [passkey challenge](connect.md#the-passkey-challenge)'s fields, made with a key the engine holds only in memory (a restart invalidates it), over the job's fields in place of a setup fingerprint. It is not single-use, so it can be sent again until `expiresAt`. The admin connection string in the same request is what lets a run happen |
| `POST /api/v1/setup/run` | the check's fields, `confirmName` for an `INSTALL` that replaces an older install, `answers` (one per question), and, when a passkey is registered, `challenge` unchanged and `passkey` (the [passkey registration response](approvals.md#codes) and an optional `label`, at most 64 bytes; the page sends none, and the engine names a passkey with no label or a blank one `Passkey on <this computer's name>`, the name without `.local` and kept to letters, digits, `.`, `-` and `_`, or `Passkey from the setup page` when it has none; this holds for the install and for `PASSKEY_ADD`) | `200 { "agent", "lines", "warnings", "passkeys", "mcpCommand", "engineRemoved", "engineRemoving" }` (the last two: [Removing the engine service](#the-local-setup-page)). `lines` says what the install did, such as `demo ready: leads 30, lead_notes 20`. `passkeys` lists each registered passkey's credential id, label and [check code](connect.md#the-passkey-check-code). `mcpCommand` is the `basalt mcp` line the agent registers, empty after a `REMOVE` |

- **Each call stands alone.** `run` repeats every check of `check` and computes the questions itself. It refuses an answer to a question it did not compute, and a question left without one. The page holds `databaseUrl` in memory and sends it with both calls. The engine keeps nothing from `check`.
- **What `run` does.** Before it connects, it checks the challenge's expiry and the passkey as `RunSetup` does. The challenge's binding (the job, the database the server names and the admin string's host) is checked inside the transaction once the server named the database, before any change. Then, in one transaction: the guard install, the sample data for `demo`, the agent role with its password, the grants, the confirmed agent policies, `attach`, `record_engine` for this engine's signing key ([Engine records](basalt-meta-installs.md#engine-records); the key is read from `<stateDir>/channel.json`, the state directory the engine runs with, and made there when there is none; a key file that is refused records nothing and the install goes on, and the engine then reports `vault.state` `KEY_ERROR`), and `register_passkey` for a passkey given (RP ID `localhost`, origin `http://localhost:8787`). `check`'s `sql` shows the `record_engine` statement. A passkey is needed when the database has no active passkey for that origin. Without one, `run` is refused `PASSKEY_REQUIRED`. After the commit, the engine writes the credential and `engine.json` and serves the agent. If that write fails, the answer is `500 SETUP_FAILED`: the database part and the agent's credential stay, and running the setup again on the page finishes it. An install that finds the agent's role keeps it when the engine's own credential for it logs in as that role on that database: the password stays, and the engine writes `engine.json`. A kept role, and a role that gets a new password (below), first loses the grants the setup makes (`SELECT`, `INSERT`, `UPDATE` and `DELETE` on a table, `USAGE` and `SELECT` on its serial sequence) on every table not picked now whose owner the admin acts for (the admin owns it, is a member of its owner that inherits its privileges, or is a superuser: the revoke counts as the owner's), in every schema the page can list, in the same transaction as the new grants; grants the setup never makes stay. When such a grant remains on any table or sequence not picked, whoever owns it (another role made it: an owner the admin does not act for, or a role with the grant option), the run is refused `GRANTS_NOT_REVOKED`, which names the role and the tables and sequences, and nothing changed: the role that made those grants, or the owner of the table or sequence, revokes them, then the person runs the setup again. A role of that name that is a member of this guard's agents group (`<prefix>_agents`) but whose password this engine does not hold (a setup this computer's BasaltDB [forgot](#not-your-database)) gets a new password, as `REPAIR` sets one: the admin string typed on the page allows it, the install's plain-agent-role checks still apply, and `lines` says `The database already has the agent role <role> from an earlier setup whose password this computer no longer holds: this sets a new password for it, as Fix on the Update check does.` Any other role of that name stays `ROLE_EXISTS`: an install never takes over a role outside BasaltDB's agents.
- **An older install.** Alpha and beta releases may break: a database can hold a `basalt_meta` this build cannot update. There is no migration across such a release: the install removes the old one and sets up from scratch, and an update keeps the data only within one. The update floor is the lowest installed version a build updates in place, now 2: every 0.0.1 release installed only version 1, whose SQL later builds changed, and every 0.1 build installs version 8 or later, so a guard at version 1 is an install from 0.0.1. The floor is not kept by hand: it is the highest guard version marked as one no older install is updated to. A guard change that cannot be applied over an older install is marked so, which raises the floor to its version, and the changelog names it under "Breaking for alpha installs".
  - **Below the floor, the `INSTALL` replaces it.** On a guard of this engine's prefix below the floor, `check` removes it, in its transaction that it rolls back, plans the install on the database as the run will find it, and answers `replace`: `{ "guardVersion", "floor", "release", "this", "lines" }`, the old guard's version, the floor, the release `schema_version` records with that version ([Schema version 14](basalt-meta-schema-versions.md#schema-version-14-release); left out when it records none), this build's release and the first screen's words, built from those fields only: `This BasaltDB install is too old to update.`, `It was set up by BasaltDB <release> (guard version <N>).` (or `It has guard version <N>.` without a release), `BasaltDB <this> needs guard version <floor> or later.` and `Setting up removes the old install first: its agents' history and undo, their held approvals and the passkeys go with it. Your tables and rows stay.` The rest of the answer is the install's as on a database with no guard: `passkeyNeeded` `true` (the old passkeys go), every column `UNCLASSIFIED`, the agent's old role no `ROLE_EXISTS`, and `sql` the removal's statements before the install's. The page shows that screen first, then the install's normal steps, and its last button is **Remove the old install and set up**, kept disabled until the database's name is typed exactly as `check` named it. The challenge is bound to the replace. `run` carries the typed name in `confirmName` and, in one transaction, before anything else is planned: reads the guard below the floor, compares `confirmName` with `current_database()` (missing, longer than 63 bytes or different: `ANSWERS_INVALID`, `Type the database's name exactly as the page shows it to remove the old BasaltDB install and set up. Nothing changed.`), runs the removal [What run does for REMOVE](#the-local-setup-page) plans (the policies named after its roles, `basalt_meta`, its roles; never the sample schema), then the install. Any failure rolls all of it back: the old install stays as it was. `confirmName` on an `INSTALL` that replaces nothing is `ANSWERS_INVALID` (`This database has no BasaltDB install too old to update, so the setup takes no database name. Check the setup again. Nothing changed.`). Limit: the check's removal takes the locks a removal takes (the guard's triggers on the person's tables) until it rolls back, within the call's 60 seconds.
  - **What stays refused.** `check` and `run` of an `UPDATE` refuse a guard below the floor `GUARD_UNUSABLE` before anything is planned or changed, and `check` and `run` of an `INSTALL` and an `UPDATE` refuse a `basalt_meta` the build cannot read: `This database has an older BasaltDB install that this version cannot use. Remove it first, then set up again: https://github.com/BasaltDBHq/BasaltDB/blob/master/docs/remove-old-install.md says how. Nothing changed.` That is a `basalt_meta` with objects but no recorded version (`schema_version` missing or empty), with a version but no `basalt_meta.installs`, or at version 2 or later with an `installs` table without an `id` column (an install from before the versions started again at 1). An empty `basalt_meta` is not refused. [Remove an older install](../docs/remove-old-install.md) gives the removal: the page's Remove while the install still works, else the SQL.
- **`SETUP_FAILED` and its cause.** A `SETUP_FAILED` from reading the database or running the setup says what failed when the database refused a statement: `Reading the database or running the setup failed (Postgres error <SQLSTATE>, <step>); nothing changed.`, and for `42501` `The admin role lacks a privilege the setup needs (Postgres error 42501, <step>); nothing changed.`, and for `40P01` `A database maintenance task (such as autovacuum) locked a table while the setup changed it, and Postgres stopped the setup to break the deadlock (Postgres error 40P01, <step>). Run the setup again; nothing changed.`; with no SQLSTATE it is `Reading the database or running the setup failed; nothing changed.`. `<step>` is a fixed name such as `install script, statement 3` or `register the passkey`. The engine logs every refusal as `setup page: refused` with `call` and `code`; a `SETUP_FAILED` with a cause is logged at `WARN` with `step`, `sqlstate` and `cause`: the server's message, and its detail only for the guard's own `BS…` codes (another detail, hint or position can quote the statement). The cause is redacted before it is logged: no connection string, no `password=` or `PASSWORD '…'` value, no 32 or more hex characters (an agent password), and not the admin password of the request, in plain or URL-escaped form. The answer never carries the cause.
- **What `run` does for `UPDATE`.** In one transaction: the `basalt_meta` migrations the build has and the database lacks, nothing else (no password, grant, policy or passkey). `check` and `run` refuse a database with no guard (`GUARD_MISSING`), a guard as new as the binary (`GUARD_CURRENT`, `There is nothing to update.`), a guard newer than the binary (`GUARD_NEWER`, telling the person to update BasaltDB on this computer), another prefix (`PREFIX_MISMATCH`), and a database without the agent's role (`ROLE_MISSING`). The engine reads the guard on every call, so the agent is served again without a restart; `lines` says `guard updated in the database <database> from version <from> to <to>`.
- **What `run` does for `REMOVE`.** The admin connection string is the confirmation: no name is typed. The removal's page is one box and one button: no OS-user question and no Check button. 400 ms after the box last changed and is not empty (a paste is one change), the page sends `check` by itself and shows `It opens <database> on <host>.` under the box; an answer for a string that has changed since is dropped. It then shows the database and its host as `check` named them, under `This removes BasaltDB from this database, and its ledger is deleted for good. When no other agent uses this computer's engine, it removes the engine from this computer too. The admin connection string you typed is the confirmation.`, with the box's hint `Used once, on this computer, to remove BasaltDB from the database. It is never stored, and the agent never sees it.` (a setup says `to set up the database`, an update `to update the guard in the database`, a `CHANGE` link before the pick `for the job you pick`), and no passkey footnote under the button: the footnote `Your fingerprint, face or device password never leaves this device; Basalt only receives a signature.` shows only under a button that asks for a passkey (a first install's and the sample database's), never under Remove or Update the guard, and its one button reads `Remove BasaltDB from <database> on <host>`. `confirmName` on any `UPDATE` or `REMOVE` request is `ANSWERS_INVALID` (`An update or a removal is confirmed by the admin connection string, not the database name.`), as on an `INSTALL` that replaces nothing. In one transaction (shared with the connect page), the SQL `check` showed, planned again from the catalog: the `DROP POLICY` of each policy named after an agent role or the guard role, `DROP SCHEMA IF EXISTS basalt_meta CASCADE` (which also drops a view or other object of the person's that uses the ledger; `check`'s lines say so), and `DROP OWNED` and `DROP ROLE` for each agent role of the prefix, the group and the guard role; then the sample schema's `DROP TABLE` and `DROP SCHEMA` without `CASCADE` when the demo made it (marked by its comment), in a savepoint, so a view or key of the person's on it keeps the schema (a warning says so) and the rest is still removed. A role that still holds privileges in another database fails the whole run (`SETUP_FAILED`, nothing changed). After the commit the engine removes from `engine.json` the agent, every other agent whose credential connects to the same database, and every agent whose credential it cannot read (and their names from every plugin entry's `agents`), then deletes their credential files; when no agent is left it deletes `engine.json` and asks the removal job to remove the engine ([Removing the engine service](#the-local-setup-page)). The running engine keeps the agents in memory until it stops; their calls fail to log in. If the config write fails, the answer is `500 SETUP_FAILED`, and the same link run again finishes it: on a database Basalt is already gone from, `check` says so and `run` only removes the agents from this engine.
- **The admin connection string.** Only `check` and `run` read `databaseUrl`. Every other route of the listener refuses a body that holds a `databaseUrl` field (`400 INVALID_ARGUMENT`, fixed message). The engine never writes, logs or returns the string or any part of it, and never logs these routes' bodies. Each answer and each refusal message is built from fixed words and from values read from the catalog, never from the string or a driver's message, as [Answers are fixed text](connect.md#setupservice-calls) says for the connect service.
- **Checks.** The routes keep the listener's `websec` Host check (loopback names only), its Origin check (a `POST` must carry `Origin: http://localhost:8787`) and `Content-Type: application/json`, the 16 KiB body limit (256 KiB for the install of a real database, [The body limit](#the-install-of-a-real-database)) and `Cache-Control: no-store`. A wrong `Host` is `400` (the listener's check) and a wrong `Origin` `403`, both before the body is read. One setup run, of any job, runs at a time; another is `409 BUSY`. A call stops at 60 seconds and rolls back (`504 TIME_LIMIT`).
- **Errors.** JSON `{ "code", "message" }`. `code` is a reason from [Connect refusals](connect.md#connect-refusals), with the same meaning; `message` is this page's own fixed text, which names no setup code: `CONNECTION_STRING_REFUSED`, `DATABASE_UNREACHABLE`, `CERTIFICATE_NOT_VERIFIED`, `LOGIN_FAILED`, `PREFIX_MISMATCH`, `ROLE_EXISTS`, `NO_TABLES`, `TABLES_CHANGED`, `ANSWERS_INVALID`, `PASSKEY_REQUIRED`, `CHALLENGE_EXPIRED`, `CHALLENGE_INVALID`, `PASSKEY_INVALID`, `SETUP_FAILED`, `TIME_LIMIT`, `BUSY`, `REQUEST_TOO_LARGE`, `TARGET_MISMATCH` and `ROLE_MISSING`. The local codes are `INVALID_ARGUMENT` (`400`: a bad field, an agent already configured or not in `engine.json`, an OS user refused), `JOB_UNAVAILABLE` (`409`: an `INSTALL` on an engine that already has a config, which `INSTALL` never changes; an `UPDATE` or `REMOVE` on an engine with no config; any job on an agent-operated engine), `ENGINE_REMOVED` (`409`: any request but an `INSTALL` to a configured engine whose `engine.json` a `REMOVE` deleted; a `run` of `REMOVE` that names an agent and carries no `databaseUrl` (the one the page of a `REMOVE` link sends when it finds the engine removed) also creates the removal job's marker again, and a `check` never does), `RESET_ASKED` (`409`: the answer to `basalt init`'s probe, a `check` with no `job`, once after the person's [No](#not-your-database)), `GUARD_UPDATED` (`409`: the answer to the probe that names an agent and `since`, once an `UPDATE` for that agent ran after `since`), `AGENT_REMOVED` (`409`: the same probe's answer once a `REMOVE` that left the engine other agents removed that agent after `since`), `GUARD_MISSING`, `GUARD_CURRENT` and `GUARD_NEWER` (`409`, `UPDATE` only, above), and `GUARD_UNUSABLE` (`409`, `INSTALL` and `UPDATE`: [An older install](#the-local-setup-page); a guard below the update floor only on an `UPDATE`), and `GRANTS_NOT_REVOKED` (`409`, `INSTALL`: the agent role an earlier run left still has a setup grant on a table or sequence not picked now that this admin cannot revoke, because another role made it; nothing changed). The fix jobs and `doctor` answer `JOB_UNAVAILABLE` where `UPDATE` does, and add the codes of [The Update check](#the-update-check). A refusal from the database is `409`, unreachable `503`, a refused `Origin` `403`, a wrong `Host` `400`, a wrong content type `415`, a body over the limit `413`.
- **`contract/surface.json`** gains the page `/setup/` with the code that adds `web/setup/`.

### The install of a real database

For the local setup page; the connect page's own version of each part is in [Connect](connect.md#tables-on-the-connect-page). `basalt init` without `--demo` opens it. The page's steps for the tables, the column labels and the certificate reuse the connect page's screens and words. `UPDATE`, `REMOVE` and `CHANGE` are unchanged, and `demo` is unchanged: a `demo` request carries none of the fields below (`ANSWERS_INVALID`).

The job is an `INSTALL` with `demo` `false`, on the same page, the same two routes and the same rules as every setup job: the admin connection string is typed on the page and sent with `check` and `run` only, and the engine never logs or returns it. Everything the engine shows comes from the catalog or fixed words, with the exceptions named below, which are derived from data or supplied by the server: a column's `suggestedClass`, `suggestedEntityType`, `suggestedPhoneRegion` and `reason`, and a certificate's `subject`. One setup run at a time (`409 BUSY`). Each call stands alone.

**What the person decides, in this order on the page.** The database (admin connection string, then one confirm step, below, that also trusts the certificate when the provider signs its own), the tables and the access to each, the column labels (a step the person may skip), the passkey, and one confirmation that shows the SQL.

**New request fields** (`check` and `run`; each is refused `ANSWERS_INVALID` on a `demo`, an `UPDATE`, a `REMOVE` or a `CHANGE`):

| Field | Meaning |
|---|---|
| `schemas` | The schemas whose tables the page lists: 1 to 5 plain lowercase names, each at most once, none of `basalt_meta`, `pg_catalog`, `information_schema` or a name starting `pg_`. Default `["public"]`. |
| `tables` | The tables the agent gets: `[{ "table": "public.users", "access": "WRITE" }]`, `access` `WRITE` or `READ`. Absent on `check` means the listing call (below); absent or empty on `run` is `NO_TABLES`. At most 500 entries. Each `table` is a plain lowercase `schema.table` (`^[a-z_][a-z0-9_]{0,62}\.[a-z_][a-z0-9_]{0,62}$`) in one of `schemas`, each at most once; anything else, or more than 500, is `ANSWERS_INVALID`. An entry the listing in the transaction lacks is `TABLES_CHANGED`. |
| `columnClasses`, `restPublic` | The labels the person set, as [Column labels on the connect page](connect.md#column-labels-on-the-connect-page) defines them (`table`, `column`, `class`, `entityType`, `phoneRegion`, `was`), with the same rules, `ANSWERS_INVALID` and `CLASSES_CHANGED` included. The tables they name must be among `tables`. A `column` is at most 63 bytes with no control character (`ANSWERS_INVALID`). |
| `trustRoot` | The SHA-256 (64 lowercase hex digits) of the certificate authority the person trusted for this database's host, or absent. The page sends the `sha256` of the refusal as received, in lowercase, not the uppercase colon-separated form it displays. |

**The listing call.** `check` with `tables` absent reads the tables of `schemas` and answers `{ "database", "lines", "tables", "excluded", "notes", "passkeyNeeded", "questions": [], "sql": "", "host", "port", "sessionUser", "certificate" }` with no `challenge`: nothing about the install depends on a pick yet. Each entry of `tables` is `{ "table", "canWrite" }`, `canWrite` true when the connected admin role owns the table and it has a primary key ([`allTables`](setup.md#the-setup-code)); a table without one can only be `READ`. `excluded` lists the tables the admin role does not own, with the owner's role name, as `allTables` does, and they cannot be picked. The listing holds at most 500 tables, in schema and name order, and `tablesMore` is true when there are more; the person cannot pick those (a schema with more tables than that is outside this job). A table whose name is not a plain lowercase one (capitals, spaces, quotes) cannot be picked: it is listed under `excluded` with the owner `unsupported name`, never under `tables`. A listing with no pickable table at all is `NO_TABLES`. The page starts each table's access at `WRITE` when `canWrite`, else `READ`. A table the person ticks is picked; an unticked table is never granted.

**Is this your database?** The page's first screen after the listing call answers, before the tables: one action in which the person checks the database, its host, who the string signs in as and the certificate together, with the connect page's words ([The connect page](connect.md#the-connect-page)). Every `check` of an install answers its facts, none of them secret and never the string or its password: `database`, `host` and `port` (the admin string's one host, lowercase, else the connection's), `sessionUser` (`session_user`) and `certificate`, `{ "kind", "issuer" }`. `kind` is what verified the admin connection's certificate as the engine dialed it: `PUBLIC` (the system's authorities), `PROVIDER` (a built-in [trust profile](trust.md#trust-profiles); `issuer` is the provider's name, `Amazon RDS`, `Supabase`), `OWN` (a pin or an operator's profile), `NOT_VERIFIED` (`sslmode` below `verify-full`; a string with no `sslmode` for a host a built-in profile covers is checked with `verify-full`, so it is `PROVIDER`: [No `sslmode` for a provider's host](trust.md#trust-profiles)) or `NONE` (no TLS). `issuer` is the top authority's short name, read from the connection's own TLS state (common name, else first organization, else the subject; cleaned as `subject` is and cut to 128 characters), absent for `NOT_VERIFIED` and `NONE`. The page shows `✓ Verified by <issuer>` for `PUBLIC` and `PROVIDER`, the issuer for `OWN`, and for the last two a warning in place of a name (`Not checked: the connection string doesn't ask for it`, `None: the connection isn't encrypted`). **Yes, this is it** shows the tables; **No, go back** drops the string. For `NOT_VERIFIED` the certificate also carries `provider`: the provider whose built-in profile is the one for the host (`Supabase`, `Amazon RDS`; the condition of [No `sslmode` for a provider's host](trust.md#trust-profiles)), absent when none is.

**A certificate not checked.** BasaltDB keeps a given `sslmode` ([No `sslmode` for a provider's host](trust.md#trust-profiles)), so for `NOT_VERIFIED` the step warns instead: `Certificate` reads `Not checked`, and a box under the facts says `Your connection string has sslmode=<mode>: it's encrypted, but nothing checks the certificate is <provider>'s. BasaltDB has <provider>'s certificates built in, so it can check.` with **Check the certificate** (`<mode>` read from the string the page holds, `prefer` when it names none). For a host with no `provider`, the box says `… nothing checks the certificate is your database's. To check it, use sslmode=verify-full in the connection string.` and has no button. While the box shows, the main button reads **Yes, this is it, without checking**.

- **Check the certificate** replaces only the value of `sslmode` with `verify-full` in the string the page holds (text, not a parse and rebuild, so the password's encoding and every other parameter stay; a string with none gets it added) and sends the listing `check` again. The person edits nothing, and the string is never stored, as always.
- **It checks out:** the step shows again with `✓ Verified by <provider>` and **Yes, this is it**. The page holds the new string from then on, so the full check and `run` send it and the agent's credential has `sslmode=verify-full` (the agent's connection string keeps the admin string's `sslmode`).
- **It doesn't:** the `check` is refused `CERTIFICATE_NOT_VERIFIED` before any startup message, so nothing was sent. The step shows `Host`, `Certificate` `Didn't match` and `This database's certificate didn't match <provider>'s, so nothing was sent. Something between you and <provider> may be reading your traffic, such as a work network that inspects encrypted connections.`, with **Go back** (drops the string, as **No, go back** does) and **Continue without checking** (the tables, with the string as pasted: its `sslmode` kept, and the check-up and `status` keep the warning). Limit: `issuer` is text the database's server chose, except a provider's name.

**The full check.** `check` with `tables` answers as an install does today, with `lines` and `sql` for the picks, the row-level security `questions` for the picked tables (the page answers `ALL_ROWS` to each, as the connect page does, and says so), and the passkey `challenge`; `run` needs one answer per question, as today. It also answers `columns`: each ordinary column of the picked tables (`attnum > 0`, not dropped), by table and column order, at most 500 (`columnsMore` is true when there are more; those get no suggestion and are labeled only through `restPublic`), each `{ "table", "column", "dataType", "class", "entityType", "phoneRegion", "suggestedClass", "suggestedEntityType", "suggestedPhoneRegion", "reason" }`. `class` is what `basalt_meta.pii_columns` stores, `UNCLASSIFIED` for a column with no row and for every column of a database with no guard. The suggestion comes from the engine's classifier ([Suggestions](pii-classification.md#suggestions): name rules, and a sample of up to 1000 non-null values per column read with the admin connection). Each sampled value is cut to its first 256 characters before it is scored, and the whole sampling stops at 30 seconds of the call's 60. A listing of the columns or of their stored classes that fails fails the check (`SETUP_FAILED`), since `restPublic` covers columns the person must see. A column whose sample fails or runs out of time gets no suggestion (the `suggested*` fields and `reason` absent) and `check` still answers; no sampling error reaches the answer. `run` samples nothing and computes no `columns` or suggestions: the labels it writes are the ones the person sent. The sampled values stay in the engine's memory, are dropped when the column is scored, and appear in no answer, log or file. `reason` is the classifier's fixed form (`NAME:email`, `SAMPLE:EMAIL 912/1000`), names and counts only. The page shows a suggestion, and never applies one the person did not accept: a label reaches the database only through `columnClasses` or `restPublic`. **Mark them as not personal** (the choice for the columns the person did not label, as on the connect page) leaves out every unlabeled column the classifier suggests is personal (`IDENTIFIER`) or `SECRET`. The choice is the confirmation: a note under it says how many columns it marks and lists those it leaves out (`Not included, because they look personal:`); when the rest must go as `restPublic` (columns past the 500 listed, or more than 500 labels), which marks those columns too, the note says all unlabeled columns are marked and lists those that look personal, so the person accepts that by choosing it.

**What the challenge binds.** The [passkey challenge](#the-local-setup-page)'s MAC covers, in addition to the job's fields, the database and the admin string's host: the sorted `tables` with their `access`, the sorted `table:choice` row-level security answers the SQL was planned with, and `trustRoot`. `check` takes the answers in `answers` (absent means `ALL_ROWS` for every question, the page's answer) and shows the SQL for them. `check` always issues the challenge, and every `run` of this job carries it unchanged, with or without a passkey: its binding is checked inside the transaction once the database is named, before any change, so a `run` whose picks, answers or `trustRoot` differ from the `check` that made the challenge, or that carries none, is `CHALLENGE_INVALID`. `columnClasses` and `restPublic` are bound too, as one hash of the sorted entries (table, column, class, entity type, region and `was`) and the flag: `check` takes them, so the page calls `check` again with the person's labels to get the challenge it signs, and a `run` with other labels is `CHALLENGE_INVALID`. The transaction still compares each `was` with the database (`CLASSES_CHANGED`). The check's `sql` ends with a comment line saying how many columns the labels write, since a label is data in `basalt_meta.pii_columns`, not a statement.

**What `run` does.** The checks of `check`, then in one transaction, after the database is named and the challenge's binding is checked: read the tables again, refuse `TABLES_CHANGED` (nothing changed) when a picked table is gone, renamed, owned by another role now, or its `canWrite` no longer allows its `access`; install the guard; create the agent role and its grants for exactly the picked tables (`WRITE` tables as write access, `READ` tables as read access), revoking first, from a role an earlier run left, the grants the setup made on tables not picked now (`GRANTS_NOT_REVOKED` when one remains that this admin cannot revoke); apply the confirmed agent policies for the answered questions; `attach`; write the labels after the grants, as `<prefix>_guard`, as [Writing](connect.md#column-labels-on-the-connect-page) says (`CLASSES_CHANGED` refuses the whole run, nothing changed); register the passkey; and, when `trustRoot` is in force, `basalt_meta.record_trust_pin(host, port, sha256)`. Once the transaction's SQL has succeeded and before `COMMIT`, the engine writes the certificate pin (below), then the credential, then commits, then writes `engine.json`; a pin or credential write that fails rolls the transaction back, so no role is left without its credential. A commit that is known to have failed (fails before it is sent, the server answers with an error, or it turns into a rollback) leaves a pin that was approved and checked, and the engine deletes `agents/<agent>.url` before it answers `SETUP_FAILED`. A commit whose answer was lost has an unknown outcome: the role may exist, and that credential holds its only password, so the engine keeps it and answers `SETUP_FAILED` with `The database did not confirm the setup. Run it again on this page: it finishes if the setup went through, and starts over if it did not.` A run again finds the role and the kept credential (it finishes with them, as for a config write that failed after the commit), or overwrites the file when the role was never made. A rerun never takes a role it cannot log in as (`ROLE_EXISTS`). The passkey, the keep-an-own-role rule, `PASSKEY_REQUIRED`, `500 SETUP_FAILED` and the rest of [What `run` does](#the-local-setup-page) hold as they do for the demo.

**The body limit.** `columnClasses` makes a body larger than 16 KiB. The two setup routes take bodies up to 256 KiB (`413 REQUEST_TOO_LARGE` above it, with the text `The body is over 256 KiB.`); every other route keeps its limit. `columnClasses` has at most 500 entries.

**The database certificate.** The page's version of [Pinning on first use](trust.md#pinning-on-first-use), by the rules of [Pinning from the connect page](trust.md#pinning-from-the-connect-page) with the engine as the one that connects, so there is no second reading to compare.

- **The refusal.** For a host no trust profile covers whose certificate verifies against no authority this machine trusts, the admin connection fails on the certificate before any startup message, so no user name or password was sent. `check` and `run` then read the chain with the handshake alone (`SSLRequest` and a TLS handshake that does not verify the certificate; no startup message, no user name, no password) and refuse `CERTIFICATE_NOT_VERIFIED` with the body `{ "code", "message", "trustRoot": { "subject", "sha256", "expiresAt" } }`, as the connect service does ([Trusting a certificate authority on the page](connect.md#trusting-a-certificate-authority-on-the-page)): the chain's top, `subject` RFC 2253 at most 512 characters (counted in characters, not bytes), with C0 and C1 control characters and bidirectional controls removed (the removal happens before the cut), `sha256` of its DER, `expiresAt` RFC 3339 UTC. A chain from a public authority, a chain that does not verify even against its own top, or a host a profile covers gets the refusal without `trustRoot`. The `subject` is text the database server supplied, so the page shows it as text only, and the engine never logs it. It is the one value in an answer that does not come from the catalog or from fixed words.
- **The page.** The refusal is the confirm step's (above) for a certificate the provider signs itself, as on the connect page ([Trusting a certificate authority on the page](connect.md#trusting-a-certificate-authority-on-the-page)): nothing logged in yet, so `Database`, `Host` and `Signed in as` are what the admin string names, read on the page (never the password), and `Certificate` is the subject's short name, under `Check these, then continue. Your provider signs its own security certificate, so confirming also trusts it for this database only.` The fingerprint is under **Details** only, as `SHA-256: <uppercase hex pairs with colons>`. Confirming is the person's trust: **Yes, this is it** sends `check` again with `trustRoot` set and goes on to the tables, and `run` carries the same `trustRoot`. When what the engine then reached (`database`, `host`, `port`, `sessionUser`) differs from what the string named, the page shows the confirm step again with the engine's facts, and asks once more before the tables. Nothing else is sent until the person answers, only that click sends a `trustRoot`, and **No, go back** drops the admin string.
- **The login.** With `trustRoot` the engine reads the chain again and logs in only when its top has that SHA-256 and the chain verifies against it (`verify-full` against that one certificate, or the chain alone, `verify: ca`, when the server certificate does not name the host), with that certificate as the only root (the system's authorities do not count, nor a root the environment names), so the password reaches only a server that presents it. The login is made with `sslmode=verify-full`, whatever mode the string had, and the agent's credential is built the same way: the pin applies with `verify-full` only, so a credential with another mode or root could bypass it. Anything else is `TRUST_ROOT_MISMATCH`, before any login. A `trustRoot` for a host that verifies without it, or that a profile covers, is ignored (it is still bound in the challenge). An admin string that names more than one host has no pin: the refusal carries no `trustRoot`.
- **The pin.** Before the commit, once the SQL succeeded, the engine writes `pin-<host>` in the `trust.d` next to `engine.json` as [Pinning on first use](trust.md#pinning-on-first-use) says, and the agent's credential has `sslmode=verify-full` so the pin applies. A pin that stays after a failed write or commit was approved and checked. A rerun with the same `trustRoot` finds that pin in `trust.d` as its own, records it in the ledger again (the failed run's record was rolled back with it) and goes on; with no `trustRoot`, `check` finds the profile covering the host, which needs none. When a profile other than this same pin covers the host by then, the run writes nothing and is `SETUP_FAILED`.
- **New codes.** `CLASSES_CHANGED` and `TRUST_ROOT_MISMATCH` join the page's list of reasons, with the meaning [Connect refusals](connect.md#connect-refusals) gives them, and `NO_TABLES` now means that no table was listed or picked.

**Passkeys on this job.** Unchanged from the demo install: a passkey is registered in the same request as the admin string and stored in the job's transaction, and the page creates one when `passkeyNeeded`. Adding a passkey to a database that has one, removing one, and labeling an installed agent's new columns are fixes of [The Update check](#the-update-check), not part of this install.

### The Update check

Persona 1. Running `basalt init` again on an engine already set up opens the `CHANGE` link ([Which link `basalt init` prints](#the-local-setup-page)). The page checks first and shows what needs the person, then only the screens that fix it. It replaces `basalt passkey`, `basalt trust` and `basalt classify`. Persona 2's version is [Update on the connect page](connect.md#update-on-the-connect-page).

**The check.** `POST /api/v1/setup/doctor` with `{ "agent", "osUser" }`, checked as `check` checks them (an agent `engine.json` lacks, another OS user: `400 INVALID_ARGUMENT`). It takes no `databaseUrl`: a body with one is refused as on every route but `check` and `run`. The engine reads with the agent's own credential and its own state, so the answer holds only what the agent can read through its own role (its readable columns' names, the passkeys' public data in `basalt_meta.agent_passkeys`) and what the engine knows itself (its pin and the certificate the host presents). It reads metadata only (column names, passkey labels and dates, the certificate's and the guard's state): no row, no change. It is not a setup run (`BUSY` does not apply), and an agent-operated engine refuses it `JOB_UNAVAILABLE`, as every setup request. The page sends it when it opens and again after each fix. Limit: the caller is not authenticated (Host and Origin can be forged on loopback), so a program on this computer can ask for any agent of the engine and read that agent's database name, unlabeled column names and passkey labels and dates. None of it is secret and none of it lets the caller change anything; an engine serves one person's agents.

| Field | Meaning |
|---|---|
| `database` | `current_database()` as the agent reads it; absent when the engine could not log in |
| `guard` | `state` `CURRENT`, `OUTDATED` (with `from` and `to`), `NEWER` or `MISSING`, read as `status` reads it; `UNKNOWN` when the engine could not log in |
| `certificate` | `state` `OK`, `CHANGED` or `MISMATCH`. `CHANGED` is `status`'s `TRUST_ROOT_CHANGED`: the host is pinned and presents another chain top, read with the TLS handshake alone; it carries `host`, `port`, `pinned` (the pinned SHA-256), `presented` (`subject`, `sha256`, `expiresAt`, as the install's [refusal](#the-install-of-a-real-database) gives them), `pinnedSubject` (the subject of the pinned certificate, read from its PEM file in `trust.d`, as `subject` is given), `database` (the database the agent's credential names) and `sameIssuer` (true only when the presented top has the public key of a pinned certificate, the SHA-256 of its SPKI, or a pinned certificate signed it; names are never compared). `MISMATCH` is `status`'s `TRUST_PIN_MISMATCH`: the ledger records another pin for the host and port than the engine's; it carries `host`, `port`, `pinned` and `recorded`. `NOT_CHECKED` is `status`'s `CERTIFICATE_NOT_CHECKED`, a warning: the host has no pin, the agent's credential is below `verify-full` (none is `prefer`) and names no `sslrootcert`, and the agent's login used TLS; `NOT_ENCRYPTED` is `status`'s `CONNECTION_NOT_ENCRYPTED`, the same but the login used no TLS (`sslmode=disable`, or `prefer` or `allow` on a server without it) to a host that is not loopback (`localhost`, `127.0.0.0/8`, `::1` are not warned). Both carry `host`, `port`, `sslMode` and `provider` (the provider whose built-in profile covers the host, absent for none) |
| `login` | When the agent could not log in for another reason: `status`'s problem code and its fixed message (`DATABASE_UNREACHABLE`, `CREDENTIAL_REJECTED`, …). Absent otherwise |
| `labels` | `state` `OK`, `UNLABELED` or `UNKNOWN`; `count`, the columns `pii_unclassified()` returns for the agent's role with `why` `NEW` or `UNCLASSIFIED`; `columns`, the first 20 of them as `schema.table.column`, in its order |
| `passkeys` | `state` `OK` when an active passkey has this page's origin (`http://localhost:8787`), `NONE` when none has, `UNKNOWN` when not read; `items`, every active passkey of the database, at most 100, oldest first: `credentialId` (base64url), `label`, `rpId`, `origin` (the page names another origin's host), `createdAt`, and `lastUsedAt` when it was used |

While the certificate is `CHANGED`, or `login` is set, the engine reads nothing from the database: no credential is sent to a server whose certificate it does not trust. `labels` and `passkeys` are then `UNKNOWN`, and the page shows the passkeys row as `Checked once BasaltDB can connect.` After the certificate fix the page sends `doctor` again and shows the rows read.

**The page.** It shows `BasaltDB / Setup · <database>` at the top.

- **Rows.** The check is a list of rows of three kinds. A **critical** row (`✕`, a red border, its fix as a filled button in the row) is what stops BasaltDB working: `certificate` `CHANGED` or `MISMATCH`, `guard` `OUTDATED`, `passkeys` `NONE`, a `login` problem. A **warning** row (`!`, its action a plain link) does not block: `labels` `UNLABELED`, `certificate` `NOT_CHECKED` or `NOT_ENCRYPTED`. An **OK** row has `✓`. There is no page-wide **Fix these**: each critical row fixes itself, and every fix ends back on the check, so no path loops.
  - `certificate` `CHANGED`: `<database> renewed its security certificate` (`certificate.database`; `Your database` without one), `Your agents are paused until you confirm.`, **Check**. `MISMATCH`: `The certificate BasaltDB trusts doesn't match its records`, `Check it before BasaltDB connects again.`, **Check**.
  - `guard` `OUTDATED`: `BasaltDB needs an update in your database`, `A newer BasaltDB is running than the one installed in <database>.`, **Update** (the `UPDATE` job, unchanged).
  - `passkeys` `NONE`: `No passkey can approve`, `Your agents' larger writes wait until you add one.`, **Add a passkey**.
  - `login` `CREDENTIAL_REJECTED`: `Your agent can't log in`, `Its database password was changed or removed.`, **Fix** (`REPAIR`, below). Another `login` code: its message, with no action: the fix is in the agent's `status`.
  - Nothing read (`passkeys` `UNKNOWN`) and no other critical row: `BasaltDB can't check your database yet`, `The rest is checked once BasaltDB can connect.`, no action. **Done** waits with `BasaltDB has to reach your database before setup is done.`
  - `labels` `UNLABELED` (warning): `<count> columns have no label` (`1 column has no label`), the names joined by `, ` (with `…` when `count` is over 20), **Label**, which opens the `LABELS` fix. When the person chose **Leave them unlabeled for now** for these columns, the page saves that choice in the browser (per agent) and the line adds `· you chose to leave them for now`; a column they did not choose is new again. Unlabeled columns never count toward `N`.
  - `certificate` `NOT_CHECKED` (warning): `Certificate not checked`, `<agent> connects with sslmode=<mode>. Encrypted, but not proven to be <provider>.` (`… Encrypted, but nothing checks the certificate is your database's.` without `provider`), **Check it**, which opens the `TRUST` fix. It replaces the `Database certificate checked` row; the page still says `Ready`.
  - `certificate` `NOT_ENCRYPTED` (warning): `Connection not encrypted`, `<agent> connects with sslmode=<mode>. Its data and queries travel unencrypted.`, and with `provider` **Check it** (the `TRUST` fix, which sets `sslmode=verify-full` as for `require`); without `provider` no action, and the line adds `Use a connection string with sslmode=verify-full.` It also replaces the `Database certificate checked` row.
  - Rows with nothing wrong show `✓`: `Every column has a label`, `Database certificate checked`, and `Passkeys`, `<n> devices can approve` (`1 device can approve`; `n` counts the passkeys of this page's origin), **Manage**.
  - More than 3 warnings show 3, the rest under **Show N more**.
- **Something critical is open:** `<N> things need you` (`1 thing needs you`), `N` counting the critical rows, and `Fix it to finish setup.` (`The rest is checked once BasaltDB can connect.` while `passkeys` is `UNKNOWN`). The critical rows come first, then the warnings, then the OK rows. **Done** is `aria-disabled` (described by the line under it, not `disabled`) and does nothing; the line says what unlocks it and what waiting costs, for example `Add a passkey to finish. Until then, writes over 10 rows wait.`
- **Nothing critical is open:** `Ready` (the title never counts warnings), `BasaltDB is running and your agents can connect.`, the rows (warnings first), the primary **Done**, then **Update or remove BasaltDB**. **Done** opens the **All set** screen: a check, `All set`, `Close this tab and go back to your agent. It can work now.`, a `✓` line for each OK row, and, when warnings exist, `Left for later: <the warnings>. Ask your agent to run basalt init to change them.` (plain text: no code marks on any page) A page cannot close a tab it did not open, so it asks the person to.

**The admin connection string.** Every fix is a setup job on `check` and `run`, with the admin connection string, as every job is ([Holding the link is not enough](setup.md#setup-jobs)). The page asks for it at the first fix the person starts, not to show the check, keeps it in memory for the fixes that follow, and drops it when the page closes, on **Cancel** and after a refusal of the string (the person types it again). Each fix checks what `UPDATE` checks before it changes anything: the agent and its OS user, the admin string names the agent's database (`TARGET_MISMATCH`), a guard of the agent's prefix (`GUARD_MISSING`, `PREFIX_MISMATCH`) and the agent's role (`ROLE_MISSING`). Each `run` stands alone, repeats its `check`, and runs in one transaction.

**`TRUST`: the certificate.** Three cases, from the check's `certificate.state`. A host no pin covers whose agent credential checks the certificate (or names its own `sslrootcert`), or one whose pin verifies and whose ledger records the same pin, is `NOTHING_TO_FIX` (`409`, `There is nothing to fix.`).

- **`CHANGED`: a new certificate.** The install's confirm step ([Is this your database?](#the-install-of-a-real-database)) as `Is this still your database?`: `Database` and `Host` the agent's (`certificate.database`, `host`, `port`), `Signed in as` the admin string's user, `Certificate` the new certificate's short name, and `SHA-256: <new fingerprint>` under Details. The page takes `sameIssuer` as it is; it compares no names, so a provider that rotates its authority to a new key gets the new-issuer words. The same issuer: `Providers renew certificates about once a year.`, `✓ Same issuer as before`, **Yes, trust the new certificate** and **Not expecting this? Stop here**. Otherwise: `The certificate now comes from someone new. Check with your provider first. Your agents stay paused.`, the certificate marked, `Before: <pinnedSubject's short name>`, the weaker **Trust it anyway** and **Stop here**. Either stop drops the admin string and trusts nothing. The issuer is text the server chose: it changes the words only, and only the click sends `trustRoot`. After the run the done screen says `Security certificate trusted` and `Your agents reconnect.`. A host whose certificate still matches its pin has no `CHANGED` row and no confirm step.
  - `check` without `trustRoot` reads the chain with the handshake alone and refuses `CERTIFICATE_NOT_VERIFIED` with `trustRoot` (`subject`, `sha256`, `expiresAt`) and `pinned` (the SHA-256 now pinned). **Yes, trust the new certificate** (or **Trust it anyway**) sends `check` again with `trustRoot`, which logs in as the install's [login](#the-install-of-a-real-database) does, with that certificate as the only root (`TRUST_ROOT_MISMATCH` otherwise). It answers `lines` `This replaces the certificate BasaltDB trusts for <host>.` and `sql` `SELECT basalt_meta.record_trust_pin(<host>, <port>, <sha256 of trustRoot>);`.
  - `run`, with the same `trustRoot`: in one transaction `basalt_meta.record_trust_pin(host, port, sha256)`; once that succeeded and before `COMMIT`, the engine replaces its pin as a pin is written ([Pinning on first use](trust.md#pinning-on-first-use)): the new PEM file, then the profile, then the old PEM file removed, under the config lock; then it commits. A pin replaced before a commit that fails stays: the person approved it and the login checked it.
- **`MISMATCH`: the ledger names another certificate.** The engine's pin still verifies, so nothing is pinned: the fix only records the engine's pin in the ledger.
  - `check` takes no `trustRoot` (one given is `ANSWERS_INVALID`), logs in under the engine's pin, and answers `pinned` (the engine's SHA-256), `recorded` (the SHA-256 of the ledger's latest `TRUST_PIN_RECORDED` for the host and port), `lines` `This records the certificate BasaltDB trusts for <host> in the ledger.` and `sql` `SELECT basalt_meta.record_trust_pin(<host>, <port>, <pinned>);`. The page shows both fingerprints, as uppercase hex pairs with colons: `BasaltDB trusts <pinned>` and `Your database's ledger names <recorded>`, with `If you replaced the certificate yourself, record the one BasaltDB trusts.` and **Record it**.
  - `run`, also without `trustRoot`, carries `pinned`, the engine's SHA-256 the check answered, logs in under the pin again and calls `record_trust_pin` with the engine's pin in one transaction; it writes no file. A `pinned` that is not the engine's pin when the run logs in, or a pin that changes before its commit, is `TRUST_ROOT_MISMATCH`, nothing recorded. `pinned` on a `check`, with `trustRoot`, or on any other job is `ANSWERS_INVALID`.
- **`NOT_CHECKED` or `NOT_ENCRYPTED`: turn the check on.** No pin, and the agent's credential is below `verify-full` (encrypted or not), with no `sslrootcert`. Nothing is pinned or recorded: `trustRoot` or `pinned` is `ANSWERS_INVALID`.
  - `check` logs in with the admin string and makes the checks every fix makes, then dials the agent's own credential with only `sslmode=verify-full` (and no `sslrootcert`) and checks it logs in as the agent's role. A certificate that does not verify is `CERTIFICATE_NOT_VERIFIED` (`This database's certificate didn't match <provider>'s, so nothing was sent. …`; the host without `provider`): the driver sends the startup message only after the certificate verified. It answers `lines` `This turns on the certificate check for <agent>: its connection to <host> changes from sslmode=<mode> to sslmode=verify-full. Nothing changes in the database.` and `sql` a comment saying nothing runs in the database. The page shows it with **Check it**.
  - `run` repeats the check, then writes the agent's credential with `sslmode=verify-full`, the rest as it was, and has the engine serve its config again (as for a connect-only agent's setup that changed), so the agent's connections check the certificate from then on with no restart by hand. Nothing changes in the database. The done screen says `Certificate checked` and `<agent> now checks the database's certificate. BasaltDB reconnects it.`; the page asks `doctor` again, a few times while the engine is not answering yet.
- In `CHANGED` and `MISMATCH`, the engine reads `trust.d` for each new connection, so the agent is served again with no restart; `TRUST_ROOT_CHANGED` and `TRUST_PIN_MISMATCH` clear at the next `status`.

**`LABELS`: unlabeled columns.** The install's labels screen ([The full check](#the-install-of-a-real-database)), with the same leave and mark choice, showing only the columns without a label.

- `check` answers `lines`, `sql` and `columns`: each column the agent's role may read (`pii_readable_columns()` with the agent role's privileges, as `pii_unclassified()` filters) whose class is `UNCLASSIFIED` (no row, or a row of that class), in its order, at most 500 (`columnsMore` past that), each with the install's fields and suggestion, sampled with the admin connection under the install's limits.
- `run` takes `columnClasses` and `restPublic` as the install does, with its rules, `was` and `CLASSES_CHANGED`; an entry for a column `check` does not list is `ANSWERS_INVALID`. **Mark them as not personal** marks every listed column but those the classifier suggests are personal or secret, as on the install; `restPublic` marks every column the agent's role may read that has no class in the transaction. It writes as the install writes, deletes the rows of columns that no longer exist (a confirmed class survives a revoked grant, owner decision OR-1), and sets `pii_catalog`, so the engine reloads its classes. **Leave them unlabeled for now** with nothing labeled sends no `run`.
- Labels apply to every agent on the database; the screen says so, as on the install.

**`REPAIR`: an agent that can't log in.** For `login` `CREDENTIAL_REJECTED` (the database refuses the agent's credential, or the credential file is gone). `check` answers `lines` (`This sets a new password for <role>. Only this computer's BasaltDB knows it.`) and `sql` (the `ALTER ROLE` with the password redacted); a role that logs in with the engine's credential is `NOTHING_TO_FIX`. `run` applies the plain-agent-role checks and the settings reset of [`basalt init`](cli.md#basalt-init) to the agent's role, then sets a new password the engine makes (256 bits, never in a request or an answer), in one transaction; it writes the credential file before `COMMIT` and handles a failed or unknown commit as the install does ([What `run` does](#the-install-of-a-real-database)). When the credential file is gone, the engine has no target of its own: `check` and `run` take the database the admin string names, with every check above (this engine's guard and prefix, the agent's role, the plain-agent-role checks), and `run` writes a new credential made from the admin string as the install makes it (`sslmode=verify-full` on a pinned host); a known failure deletes it again. It changes no grant, policy, label or passkey.

**`PASSKEY_REMOVE`: a lost device.** The passkey list (**Manage**): `Passkeys`, `These devices can approve your agents' writes and undos. Remove one you lost.`, then each passkey of `doctor`'s `items`: its `label` and `Added <day month> · used <today | N days ago | N weeks ago | never>`, with **Remove**; one of another origin reads `Added <day month> on <the origin's host> · used …` (`Added 3 Nov on portal.basaltvault.app`): it signs on that site's pages, not this computer's. Under them **Add a passkey on this device** and the note `Removing asks for the database's admin connection string, so it works even if the lost device was your only passkey. If you remove the last one, the page asks you to add one before your agents' writes and undos can be approved again.`

- `check` with `credentialId` (base64url of an active passkey; any other is `ANSWERS_INVALID`, `This passkey is not active any more. Nothing changed.`) answers `lines` (`This removes the passkey <label>, added <date>. It can no longer approve writes or sign undos.`, and when no other active passkey has this page's origin, `It is the last passkey for this computer: until you add one, your agents' held writes and undos wait.`) and `sql` (`SELECT basalt_meta.revoke_passkey('\x…'::bytea, true);`). The page asks once, **Remove passkey**.
- `run` calls `basalt_meta.revoke_passkey(credential_id, true)`. It always forces: the admin connection string is what allows it, as it allows removing BasaltDB, so the last passkey can go. The function stays admin only and appends `PASSKEY_REVOKED` with `forced`. A revoked passkey is refused by `_verify_assertion` from then on ([Passkey management](passkey-management.md#passkey-management)). It answers `remaining`, the active passkeys of this page's origin.
- After a removal of a passkey whose `rpId` is `localhost`, the page tells the browser it is gone (`PublicKeyCredential.signalUnknownCredential`, feature-detected; a browser without it is a no-op). With `remaining` `0` it goes to the add screen: `Add a passkey so your agents' writes and undos can be approved again.`

**`PASSKEY_ADD`: a passkey on this device.** `check` answers `lines` and the install's `challenge`, bound to the job, the agent, the database and the admin string's host. `run` carries the `challenge` unchanged and `passkey` (the registration response and an optional `label`), checked as the install checks them, and registers it in one transaction (`register_passkey`, RP ID `localhost`, origin `http://localhost:8787`). It answers `passkeys` with each one's [check code](connect.md#the-passkey-check-code), which the page shows as the install's done screen does. A database may hold any number of passkeys up to the list's 100.

**Codes.** `NOTHING_TO_FIX` (`409`) joins the page's local codes ([Errors](#the-local-setup-page)).


### Not your database

Persona 1. A program running as the person's OS user can forge `Host` and `Origin` on loopback ([Holding the link is not enough](setup.md#setup-jobs)), so it can finish the first install itself, under an agent name and OS user it picks, with an admin string for a Postgres it controls and a passkey of its own. The engine then serves that database and refuses every later install (`JOB_UNAVAILABLE`). The person has no admin string or passkey for that database, and their link may name another agent, so no setup job can undo it. A reset can, and it is authorised only by the person's password in the [administrator dialog](#the-administrator-dialog): no setup route resets anything.

- **The question.** A `CHANGE` link opens with `engine`, before `doctor`: the install's confirm step ([Is this your database?](#the-install-of-a-real-database)), `Is this your database?`, `Check these, then continue.`, with `Database` and `Host` (`host:port`) for each of its `databases`. **Yes, this is it** sends `doctor` and shows the check, or its refusal, as before. **No, this isn't mine** sends `not-mine` and shows `Your computer asks for your password next` and `You answered that this database isn't yours. To reset BasaltDB on this computer, type your computer's administrator password in the system dialog that opens. It deletes BasaltDB's setup on this computer and touches no database. If no dialog opens, ask your agent to run basalt init again.` When `engine` is refused, or names no database, the page sends `doctor` as before.
- **`engine`** takes `{}`, names no agent (the setup may have been made under a name the person's link does not carry) and never connects to a database. It reads `engine.json` and, from each agent's credential file, the database, host and port it names (never the password), and answers `agents` and `databases` (`{ "database", "host", "port" }`, each once). **`not-mine`** takes `{}` and keeps, in the engine's memory only, the time of the person's No. Both refuse a body with any field (`INVALID_ARGUMENT`, a `databaseUrl` as on every route but `check` and `run`), and `JOB_UNAVAILABLE` on an engine with no config, an agent-operated one or one run as root.
- **The probe.** Before it opens a link, `basalt init` sends a `check` with an empty body. The `basalt init` that opened the `CHANGE` link polls with a `check` whose body is `{ "agent", "since" }` only: the link's agent, and the time (RFC 3339, from this computer's clock) taken just before it printed the link. On an engine with a config, `since` on any other request is refused `INVALID_ARGUMENT`; an engine with no config ignores it. Within 5 minutes of a No, either probe is answered `RESET_ASKED` once, and the mark is gone. `basalt init` then runs the reset script through the administrator dialog. A `RESET_ASKED` an init finds when it starts, before it opened a link, is taken as an engine set up: it opens the `CHANGE` link and resets nothing. The engine keeps, in its memory only, when each agent's last `UPDATE` run finished; a probe whose agent's `UPDATE` finished after its `since` is answered `GUARD_UPDATED`, every time, so every init waiting for that agent ends, and an `UPDATE` that finished before an init opened its link, or a refused one, never ends it. `ENGINE_REMOVED` and `RESET_ASKED` come first. Limit: a probe with a `since` of its choosing learns only whether an agent's guard was updated since then (nothing secret).
- **The reset script.** Fixed, built from constants, as the removal script is: it refuses unless the engine's OS user is the system account the install made, its config folder passes the walk from `/`, and `engine.json` exists. As root it stops and removes the plugin services (by name prefix), deletes `engine.json`, the credential files `agents/*.url` (and `*.url.pending`) and the certificate pins `trust.d/pin-*.json` and `trust.d/pin-*.pem`, and restarts the engine service (`systemctl restart`, `launchctl kickstart -k`). It connects to no database. Operator trust profiles, the state folder and the plugin files stay. The engine starts with no config and serves the setup page of [an engine with no config](#the-local-setup-page); `basalt init` waits for it and prints and opens the `INSTALL` link. A dialog the person closes resets nothing and `basalt init` exits `1`; with no dialog (an SSH session, a headless machine) it says so, resets nothing and exits `1`, as for an install.
- **What stays.** Every database keeps what it has: the guard, the ledger, the agent roles and the passkeys. An install under an agent name whose role an earlier, reset setup left behind sets a new password for that role and revokes the grants the setup made on tables not picked now; it is refused `GRANTS_NOT_REVOKED` when such a grant remains that this admin cannot revoke ([What `run` does](#the-local-setup-page)).
- **Limit.** `engine` and `not-mine` need no proof, so a program on this computer can read the database names and hosts of the engine's agents (none of it secret), and can leave a No: a `basalt init` polling within 5 minutes then shows the administrator dialog, which resets nothing unless the person types their password. On macOS the dialog names the reset and says to cancel unless the person just answered No ([What the dialog says](#the-administrator-dialog)); on Linux its text is polkit's generic one.

### The administrator dialog

Persona 1. On first install `basalt init` installs the engine as a service under its own OS user, with a removal job that removes that service when the setup page's removal asks for it. The agent cannot type a password, so `init` asks through the system's own administrator dialog (`osascript` "with administrator privileges" on macOS, `pkexec` on Linux), which only the person can answer.

- **A fixed command.** The dialog runs a script `init` builds from constants and the running binary only (its resolved path and its SHA-256): copy that binary to the service's own path (below), create the engine's OS user and the system directories, write the service unit that runs `<service binary> engine --config <the system config path> --supervise`, and start it, then write and load the removal job (below). The install takes over an existing engine user in the system range whose group is missing by making the group again with the user's group id, when no other group holds that id; it refuses a user outside the range. A folder the install makes and cannot give to the engine's user is removed again, and an existing root-owned folder of the engine's (the config folder, `run`, `state`) is given to that user only when it holds nothing but folders. While it waits for the setup page, `basalt init` stops waiting when the service manager starts the engine again during the wait after an exit with an error, and names the engine's log. Limit: an engine installed with `service install --user` makes the script stop before it removes anything. The source is the running binary's own path with every link resolved. No value from the agent reaches it: not `--agent`, not the environment, not the working directory.
- **The removal job.** The install writes, root's and mode `0644`, the job's script next to the service's copy of `basalt` (`/usr/local/libexec/basalt-remove` on macOS, `/usr/libexec/basalt-remove` on Linux) and its units, and loads them: on macOS the LaunchDaemon `system/dev.basaltdb.remove` (`/Library/LaunchDaemons/dev.basaltdb.remove.plist`), whose `WatchPaths` is the marker; on Linux `basalt-remove.path` (`PathExists=` the marker, enabled with `paths.target`) and the oneshot `basalt-remove.service` it starts. Both run `/bin/sh <script>`, a fixed argv as root. The marker is `remove-requested` in the engine's config folder (`/Library/Application Support/Basalt` on macOS, `/etc/basalt` on Linux), which only root and the engine's account can write, and whose own parent (`/Library/Application Support`, `/etc`) and every folder above are root's, so the engine's account can replace the marker but never a folder above it; the engine creates it after the setup page's `REMOVE` deleted `engine.json` ([Removing the engine service](#the-local-setup-page)). The restart script (below) writes and loads the job again, so an engine installed before it gets it. The script reads no input and never the marker's content. It first removes the marker, on every path and whatever it is (`rm -rf`, which never follows a symlink), so a `PathExists` unit never fires again on it: with no marker it exits `0`; a marker that is not a plain file owned by the engine's account (a symlink, a folder, root's, or any marker when the engine's account or the marker's owner cannot be read: the check fails closed) is refused (`basalt: <marker> is not a plain file of <user>, so nothing was removed`, exit `1`) and nothing is removed. Then it waits 2 seconds, so the engine finishes answering the page's removal, and runs the removal: it refuses while `engine.json` exists, then stops and removes the engine and plugin units (by name prefix), the job's own units and script, the service's copy of `basalt` (when its folder passes the walk; otherwise it says it left the copy and goes on) and the system directories (after the same walk from `/`). On Linux it deletes the OS users the install made: it kills each user's processes (`pkill -KILL -U`, up to 10 tries a second apart) and deletes the user with `userdel` only once none is left, so no process stays on a uid a new account can get; an account that can log in is kept ([Service units](plugins-runtime.md#service-units)). It deletes a user's group only once the user is gone; a user it cannot delete (a process that would not end) keeps its group and the script names it with `userdel <user>`, and a group left without its user fails the script, after everything else is removed. macOS keeps the OS users and their groups (`_basalt` and `_basalt-plugin-*`): a root job cannot delete a user there without Full Disk Access, and a new install takes them over again. After stopping the units it kills every process those users still run (`pkill -KILL -U`), so none outlives the removal into a reinstall that takes the account over; the script says so, and [`docs/install.md`](../docs/install.md) gives `sudo sysadminctl -deleteUser _basalt`, then `sudo dseditgroup -o delete _basalt`, for anyone who wants them gone. On macOS the job's output goes to `/var/log/basalt-remove.log` (root's, outside every folder the engine's account owns), which a removal that finished deletes and one that stopped keeps; its last command unloads the job itself (`launchctl bootout`, which ends it); on Linux it stops the `.path` unit, deletes both units and reloads systemd, which does not stop the running `.service`. The install and restart scripts first wait, up to 60 seconds, for a removal job still running (`systemctl is-active basalt-remove.service`, or `launchctl print` saying `state = running`), then refuse, so a reinstall never races the job's last steps; on macOS they load the job only when it is not loaded yet. Limits: anyone with the engine's own account can create the marker; that removes BasaltDB from this computer, which that account can already make useless by stopping the engine. That account can also create the marker over and over until systemd's start limit stops the `.path` unit (it then watches no more until a restart of the unit or a reinstall); `basalt init --remove` on an engine that serves no agent (a removal the job did not finish) removes the service with the fixed removal script through the administrator dialog, one password. A removal re-asked in the job's 2-second grace can race an `INSTALL` started on the removed engine in that time and cancel that setup; that is a denial of service only, and the person runs the setup again.
- **The binary root runs.** The service runs only its own copy of `basalt`: `/usr/local/libexec/basalt` on macOS, `/usr/libexec/basalt` on Linux. The running `basalt` may sit in a folder the person's account owns (a Homebrew prefix, a release archive unpacked in a home folder), so `init` never asks root to run it in place, and never asks the person or the agent to copy it with `sudo`: the agent has no terminal to type a password in. Before it asks, `init` reads the running binary and passes its SHA-256 and size to the script. As root, the script checks before anything is created that the copy's folder, when it exists, passes the walk below and that the copy's path is no symlink; a folder on the way that is not root's alone (an older Homebrew layout gives `/usr/local` to the person's account) stops it, naming the folder and its owner and saying the service can be installed once that folder belongs to root and only root can write it (the dialog does not take a folder from its owner, so this message does not say to run `basalt init` again). Then it makes the missing folders root's (`0755`), checks that the source is a plain file and no symlink right before reading it, copies at most the size `init` read into a new root-only file in the copy's folder, compares its SHA-256 with the one `init` read and removes it on a difference (`<source> changed after basalt init read it, so it was not copied to <copy>; run basalt init again`), makes it `root:root` `0755` and renames it over the copy, so an older copy is replaced whole and the service never runs a half-written file. It then checks the copy as the unit will run it: the file and every directory above it root-owned and not writable by group or others. Run from the copy itself, the script copies nothing and checks it the same way. The script reaches every directory it writes in from `/` without following a symlink anyone but root controls, and refuses a directory on the way owned by anyone but root or the engine's user, or writable by group or others. A failed copy or check stops the script, says what failed and says to run `basalt init` again; no message, next step or error names a `sudo` command. When neither dialog exists (an SSH session, a headless machine), `init` says so and stops. It never falls back to running the engine as the person's user.

**The restart.** On an engine service already installed, `basalt init` reads the engine's build from the `basalt-build` header of `GET /healthz` ([Local pages](local-pages.md#local-pages)) before it goes on. When it differs from the build of the `basalt` running, or the engine sends none (one older than this rule), the person upgraded `basalt` (`brew upgrade`, a new release) and the service still runs its older copy. `init` updates the service only when the running `basalt` is newer than the engine's build by semantic version precedence (an engine that sends no build is older); it never moves the service to an older build: when the engine's build is newer, `init` exits `1` with no dialog, naming both builds and saying to update this `basalt` to the engine's build or later first (`brew upgrade basaltdbhq/tap/basaltdb`, or the release page), then run `basalt init` again; a build whose order cannot be told is refused the same way. Otherwise `init` updates the service through the same dialog, with a fixed prompt that names the RESTART: the script copies the running `basalt` over the service's copy, checked as the install checks it (its SHA-256, the folder walk, no symlink, a rename into place), then restarts the service (`launchctl kickstart -k system/dev.basaltdb.engine` on macOS, `systemctl restart basalt-engine.service` on Linux). Run from the service's copy itself, the script is the restart command alone. One password covers the copy and the restart. After the restart `init` waits for `GET /healthz` to answer (up to 15 seconds) and reads the build again: an engine that never answers stops `init` with exit `1` and names the engine's log; one that still runs a different build (its unit names another binary than the copy, as an install older than the copy did) stops it and says that removing BasaltDB on the setup page (which deletes the ledger for good) and running `basalt init` again installs the service onto the copy; that is the person's choice, so it is said as a question to ask them. With no dialog, or a closed or failed one, `init` exits `1`, says the engine runs a different build and says to run `basalt init` again (in a desktop session, with no dialog); it names no root command and opens no link. An engine that does not answer, and a first install, restart nothing here.

**The reset.** After the person answered [No, this isn't mine](#not-your-database), `basalt init` runs the fixed reset script through the same dialog.

**A setup from before the last breaking release.** `engine.json` records the breaking epoch it was written in, `"breaking"`, which every write of it sets; the binary's is `BreakingEpoch`, 1 now, and a breaking release bumps it. A config without the field is read by its shape: 0 for the shape of the releases before the first breaking one (an agent with its own `credentialFile` and no `store`, or a top-level `directAddr`), else 1. The install and restart scripts read, as root and after their checks, the epoch of the `engine.json` at the system path, by the same keys (a value they cannot read resets nothing). Below the binary's, they stop and remove the engine's and the plugins' units, move the config folder to the first free `<folder>.old`, `<folder>.old.2`, … (never deleting, overwriting or nesting one), print `basalt: this computer's BasaltDB was set up by a release before the last breaking one: its engine service is removed and its config folder moved to <folder>.old. Delete that folder once the new setup works.`, and install the service as a first install does, in the same dialog: the restart script installs it instead of restarting it. The engine then waits for a first install, and `basalt init` prints and opens the `INSTALL` link and the `basalt mcp --agent NAME` line the agent registers again. A config in the person's own config folder, which no root script may name, is read by `basalt init` itself once the dialog is done, and moved aside the same way when it is below the epoch, with the line `basalt: <path> was written by a BasaltDB release before the last breaking one: its folder is moved to <folder>.old, and this computer is set up again. Delete that folder once the new setup works.` `basalt init --remote` does the same for its config (the person's own folder, or the system path as root) before anything else. Limit: a 0.0.1 engine that serves no local pages answers no build, so `basalt init` restarts nothing and the reset waits for the hand steps of [Remove an older install](../docs/remove-old-install.md).

**What the dialog says.** On macOS the dialog shows a fixed prompt per action, a constant passed as an argument of the AppleScript (`with prompt`), never text from the agent. Its first sentence names the action: `BasaltDB wants to install its engine on this Mac. It copies basalt into a system folder, creates the engine's own system account and folders and starts the engine. Cancel unless you just asked to set up BasaltDB.`, `BasaltDB wants to restart its engine on this Mac. The engine runs another build than the basalt you just ran, so it copies that basalt into a system folder and restarts the engine onto it. Cancel unless you just installed or upgraded BasaltDB.`, `BasaltDB wants to remove its engine from this Mac. It stops the engine and deletes its folders and system accounts. Cancel unless you just chose to remove BasaltDB.` and `BasaltDB wants to reset its engine on this Mac. It deletes the engine's config and credentials. Cancel unless you just answered 'No, this isn't mine' on the setup page.` Limit: on Linux, `pkexec` shows polkit's generic text and takes no prompt, since a message of its own needs a polkit action file installed as root; the setup page and `basalt init`'s line on the terminal say which action it asks for.

**Limit of persona 1.** An agent running as the person's OS user can serve a lookalike `localhost` page that asks for the admin string, or replace a `basalt` binary in a folder that user can write to before `init` reads it, and the person's password then copies that binary for root to run. That is not new (a terminal prompt, or a `sudo install` the person types, has the same exposure) and is not built around. What the copy closes: a binary changed or swapped (a symlink to a root-only file included) between `init`'s read and the copy is never installed, since its SHA-256 differs, and once copied, nothing but root can change what the service runs. Signing stays safe: Postgres checks the exact origin, port included.
