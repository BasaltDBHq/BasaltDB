# BasaltDB contracts

Normative contract for the surfaces BasaltDB exposes: **MCP tools** served by the engine (through the per-agent shim), the **`basalt` CLI** (four commands that only start things: [CLI](contract/cli.md#cli)), the **pages** people use to set up, approve, revert and manage passkeys, and the **`basalt_meta` schema** the guard installs in the person's Postgres. Agents use MCP, people use pages. This file and the section files it lists fix the wire rules. There is no REST API, no OpenAPI/AsyncAPI and no event stream: the only events BasaltDB emits are the plugin [notifier messages](contract/plugins-runtime.md#notifier-messages), as CloudEvents. The HTTP surface is the engine's loopback [local pages](contract/local-pages.md#local-pages) (persona 1, the person's laptop): the pages plus a same-origin relay for them, not an API for other clients. On persona 2 (an engine a bot runs) the same pages run on the portal and reach the engine through the end-to-end encrypted [Vault channel](contract/vault-channel.md#vault-channel) over the relay, the one carrier for a signed approval. The [connect service](contract/connect.md#connect) is the second hosted piece, used only at setup, with its own ConnectRPC API ([`connect.proto`](api/connect/proto/basalt/connect/v1/connect.proto)). The direct transport is removed ([Removed](contract/cli.md#removed)).

**Removed surface.** [Removed](contract/cli.md#removed) lists every command, flag and transport that is gone. It wins over any section file that still names one of them as current: those passages describe the build being taken apart, and are rewritten as each part is removed.

## Sections

The contract is split by section under [`contract/`](contract/). This file holds the rules every change needs ([Process](#process-contract-first) and [Wire format](#wire-format)) and the map below. Read this file, then only the sections your change touches: the whole contract is too large to load for one task.

A reference in the code such as `(CONTRACT.md, Link secrets)` names a heading. Find the heading in the map to get its file. The map lists the `##` and `###` headings; for a smaller heading or a named item such as `Pasted codes`, search for it under `contract/`. ## Process: contract first

- A new MCP tool, a change to a tool's input or output schema, a new error code or a new `basalt_meta` table or function lands in a **contract-only PR** first: tool schemas under `api/mcp/`, the contract's index or section file if a convention changes, and the contract test that checks the served tool list against the schemas. No behaviour change in the same PR unless CI needs it.
- Every tool in `api/mcp/` declares a status, `IMPLEMENTED` or `PLANNED`. A contract test fails if a served tool is missing from the schemas, or an `IMPLEMENTED` tool is not served.
- One file per tool, `api/mcp/tools/<name>.json`: `name`, `status`, `milestone`, `description`, `inputSchema` (JSON Schema, `additionalProperties: false`), `outputSchema`, and `errors` (codes from the [Error codes](contract/error-codes.md#error-codes) table). The engine embeds these files and lists each tool's `inputSchema` as written, so the schema has one source. The contract test (`api/mcp/contract_test.go`) checks camelCase property names, SCREAMING_SNAKE_CASE enum values, closed input schemas, and that every declared error code is in the Error codes table.
- **Planned parts of a served tool.** A change to an `IMPLEMENTED` tool lands in its contract before the engine serves it. An input property whose `description` starts with `Planned (` is in the contract but not served: the engine leaves it out of the tool's listed `inputSchema` and refuses it as an unknown argument (`INVALID_ARGUMENT`) until the change that serves it removes the marker (`mcpcontract.Load` serves, `mcpcontract.LoadAll` is the contract as written). Likewise a [next-steps](contract/next-steps.md#next-steps) entry with `"planned": true` is contracted but not returned yet; its row in the next-steps tables starts its Steps with `Planned (`, and when it lands it replaces the served entry of the same key, if there is one. Output properties and enum values marked `Planned` in their description are not returned yet. A planned input property may not appear in its schema's `required`, `dependentRequired` or `oneOf`/`anyOf`/`allOf` (loading the contracts fails), so leaving it out never changes what the served schema accepts otherwise. **Version-scoped payload schemas are outside this convention**: a schema under `api/mcp/revert/` whose description names a `basalt_meta` version (`revert-select.schema.json`, "From basalt_meta version 20") describes that version's format only, as a whole. The version such a description names is a step from before the first release ([Step numbers from before the first release](contract/basalt-meta.md#step-numbers-from-before-the-first-release)): every guard has all of those steps, so no guard emits the older format the description names.
- Breaking changes are allowed until M4 (nothing has shipped). Record each one in the PR description.

## Wire format

- JSON keys we define (MCP arguments and results, the change record, page requests and answers, config) are **camelCase**. Exception: column names and values from the person's tables pass through exactly as Postgres returns them, except a `timestamptz` value, which follows the Timestamps rule below.
- **Enum values are SCREAMING_SNAKE_CASE** everywhere (Go consts, JSON, `validate` `oneof`, `basalt_meta` values, docs). Go identifiers stay PascalCase (`StatusApplied = "APPLIED"`).
- **IDs:** UUIDv7 for every id BasaltDB generates (`changeId`, run, task, approval), canonical text on the wire, `uuid` in Postgres. Row versions are an opaque string the store writes (`"xmin:<n>"` in Postgres).
- **Texts about the person's data** (what a person signs, change records, the plugin feed, tool errors) are store-neutral: a shared part, a `shape` and a store part, with agents named `agent:<name>` ([What every store writes](contract/stores.md#what-every-store-writes)). Only the texts a person signs and their lines are written by the [text rules](contract/stores.md#text-rules), which fix their bytes; change records, the feed and tool errors share the model but not that byte layout.
- **Timestamps:** RFC 3339 UTC with `Z` (`2026-11-10T06:02:11Z`), fractional seconds kept when present (`2026-11-10T06:02:11.513958Z`). This holds for the values of the person's tables too: a `timestamptz` column is reformatted to it wherever the engine returns row values to an agent or a page (`query`, `run_history`, the lines of `preview_revert` and `revert_plan`, the revert page), whatever `TimeZone` the session or the writing session had. In `query` the column's type decides (Postgres prints it in `DateStyle` ISO, which the engine sets; see below). Inside stored row values (the ledger, revert lines) there is no type, so any string at any depth in the exact shape of a `timestamptz` in JSON (`2026-11-10T08:02:11+02:00`: date, `T`, time with an optional fraction of 1 to 6 digits, numeric offset `+HH:MM`, with `:SS` when the zone has seconds) is reformatted, a text column holding such a string and the elements of a `timestamptz[]` column included. In `query` an array, json, jsonb or text column is returned as Postgres prints it, so the same array shows as Z strings in `run_history` and in Postgres form in `query`. A `timestamp` without time zone, a `date`, `infinity` and any value RFC 3339 cannot write (BC, year over 9999) are not touched. What the guard stores and the person signs (held and revert lines, `rowsHash`, the ledger's row values) is not reformatted: it keeps Postgres's JSON form, so the signing pages show `2026-11-10T06:02:11+00:00`. It does not depend on the session either: every transaction in which the engine writes, reads for an agent, previews, holds or reverts first sets `TimeZone` to `UTC`, `DateStyle` to `ISO, MDY`, `IntervalStyle` to `postgres`, `extra_float_digits` to `1`, `lc_monetary` to `C` and `bytea_output` to `hex` for that transaction only (`set_config(name, value, true)`), whatever the client, the role or the database set. The agent's own SQL runs in it too: a `timestamptz` literal without an offset is read as UTC, `now()::date` or a `::text` cast prints in UTC, a `money` value prints and is read in the C locale's form (`$1,234.50`), and a `bytea` value prints in hex (`\x00ff`). The guard's row trigger sets the same six values for itself ([Row images in fixed settings](contract/basalt-meta.md#row-images-in-fixed-settings)), so a write that skips the engine (the agent's credential used directly, as in psql) stores the same row images as one through it, and its own SQL keeps its session's settings. The revert's own read of the row now and its restore set them too, so a person calling the revert functions by hand from any session finds no false conflict. For every write, a stored `timestamptz` reads `+00:00`, an `interval` `01:30:00` and a `float8` its shortest exact form (`0.30000000000000004`) and a `bytea` `\x00ff`, the lines and `rowsHash` are the same from any client, and a revert's conflict check (the row now against the row the agent left, compared as JSON) finds no false conflict when the write and the revert ran in different sessions. A row value stored before this by a session in another zone (`+07:00`) no longer matches the row now: its line is skipped `CHANGED_AFTER`, never written (lane decision, 14 Nov 2026; owner decision on the returned values, 13 Nov 2026).
- **Events are CloudEvents.** Anything BasaltDB emits as an event, to a plugin or outside the engine, is a [CloudEvents](https://github.com/cloudevents/spec) 1.0 event in its JSON form: the JSON event format, media type `application/cloudevents+json`, and several events in one message as a JSON batch, `application/cloudevents-batch+json` (spec version 1.0.2, `cloudevents/spec.md` and `cloudevents/formats/json-format.md`). Today that is the two notifier messages, `feed/1` and `deliver/1` ([Notifier messages](contract/plugins-runtime.md#notifier-messages)). It does not cover what Basalt stores (ledger rows and every other table in Postgres) or what it answers (tool results, CLI output, error bodies, approval and revert requests and responses): those are records and answers to calls, not events. The envelope's attributes are the standard's, with its names (`specversion`, `datacontenttype`: lowercase letters and digits only), so the camelCase rule above does not apply to them; every key and value inside `data` follows the rules above (camelCase keys, SCREAMING_SNAKE_CASE enum values, UUIDs, RFC 3339 UTC timestamps). Basalt sets no extension attribute. An event travels in its JSON form on every transport, ConnectRPC included, so a plugin that forwards it to a message broker passes it on unchanged.
- Named Go types for anything (de)serialized; DTOs separate from domain structs.
