> Part of **Plugins**. The section starts in [plugins.md](plugins.md).

### Consent

There is no `basalt plugin` command (Simplify for beta, SB-2: agents use MCP, people use pages). A person adds, changes or removes a plugin by asking their agent, which calls [`request_plugin`](mcp-tools.md#mcp-tools), and approves an install or change once with a passkey on the [plugin approval page](#the-plugin-approval-page). The page shows the hooks, the entity types, the egress hosts, `LOCAL` or `REMOTE` with the host, the signer and the agents, in plain words, with the warning of its level; an agent's text in the chat is never the consent.

- **Where.** On an engine that runs as a service, is `operatedBy: PERSON` and serves its local pages, and on an agent-operated engine that runs as the agent's own OS user, through the portal ([Plugin approval through the portal](#plugin-approval-through-the-portal)). Every entry the agent prepares is an [engine-kept entry](plugins-approval-service-mode.md#plugin-approval-in-service-mode) and requires approval. On an agent-operated engine that runs as a service under its own OS user plugin changes stay refused (`PLUGIN_REFUSED` `AGENT_OPERATED`); on a person-operated engine that runs as the person's own OS user (same-user mode) the tool is refused (`SAME_USER_MODE`). On those engines `engine.json`'s `plugins` is edited by hand, and the engine applies it as this section and the next say (an entry with `"approval": "REQUIRED"` still waits for a signed approval, which only an approval opened for it can carry).
- **Narrowing needs no approval.** Removing a plugin, and a change that only removes agents from an entry that is on, apply at once: they only narrow.
- **Health** is in the agent's `status` (`plugins`, and the problems of [Problems and errors](plugins-ledger.md#problems-and-errors)), not in a command.

### Plugin approval

A person approves a plugin install or change once, with a passkey, on the page a link opens, and that one approval installs and enables it. It is a signed kind like a held write or a revert: Postgres builds the binding text, verifies the passkey signature and writes the record ([schema version 5](basalt-meta-schema-versions.md#schema-version-5-plugin-approvals)), so neither the agent nor the engine can forge it. Schemas: [`api/plugin/approval/`](../api/plugin/approval/). Shared vectors, which the contract test (`TestPluginApprovalVectors`) checks and the guard, engine and page tests run: [`vectors.json`](../api/plugin/approval/vectors.json), one binding per page level, a change binding, a settings mismatch and a binding of another kind, each text as Postgres returned it.

**What an approval protects.** A local plugin approved this way runs as the engine's OS user, with the engine's access ([Plugin approval in service mode](plugins-approval-service-mode.md#plugin-approval-in-service-mode), What the person gives up). What the approval gives:

1. An honest engine never runs a plugin for an agent without a matching approval in that agent's ledger ([Plugin approvals at engine start](#plugin-approvals-at-engine-start)).
2. The ledger shows exactly what a person approved and with which passkey, and nobody but a passkey holder can create that record.
3. An agent tricked by text (prompt injection) cannot install anything: it can only produce a link, and the person sees the truth on the page.

On an agent-operated engine the bot and the engine share one OS user, so there the approval is consent, not containment ([The honest limit](#plugin-approval-through-the-portal)).

**Who needs one.**

- **Every engine-kept entry**, and every entry with `"approval": "REQUIRED"` ([Config](plugins.md#config)); on an agent-operated engine every entry, whatever `engine.json` says.
- **Never:** removing an entry, and a change that only removes agents from an entry that is on (the same manifest bytes, the same settings, no agent added). They only narrow.

**The flow.** The agent calls `request_plugin` with `source` (or `name`, for the installed copy):

1. **Check.** Before anything is written, the engine stages and checks the copy as [Signing and the trust store](plugins.md#signing-and-the-trust-store) says (manifest rules, file hashes, the path rule) and works out its [signer state](#signer-states). It does not refuse an unknown or missing signature. It refuses, writing nothing, for a bad manifest (`BAD_MANIFEST`), a path (`UNSAFE_PATH`), an unknown agent (`UNKNOWN_AGENT`), an agent outside the caller's reach (`AGENT_NOT_ALLOWED`) and a `.sig` that names a built-in key and does not verify (`NOT_TRUSTED`); and also when the database does not answer within 15 seconds (`DATABASE_UNREACHABLE`), or its guard is older than [schema version 5](basalt-meta-schema-versions.md#schema-version-5-plugin-approvals) (`GUARD_OUTDATED`).
2. **Write.** It moves the copy into place and writes the entry, enabled, requiring approval. Nothing runs yet: the engine withholds the entry until a matching approval exists. Writing first means no process has to commit anything after the signature.
3. **Open.** One approval, in the caller's database, with the caller's own credential (`open_plugin_approval`), naming every listed agent. An open that fails now (the database reached its 8 pending approvals meanwhile, `TOO_MANY_PENDING`, or stopped answering, `DATABASE_UNREACHABLE`) leaves the entry written and withheld: the call answers `PLUGIN_REFUSED` with that reason, and the `name` form opens the missing approval later. Reasons after the write: `BS007` detail `TOO_MANY_PENDING` is `TOO_MANY_PENDING`, detail `UNKNOWN_AGENT` is `UNKNOWN_AGENT`, an older guard is `GUARD_OUTDATED`, and anything else (no answer, a refused connection, `BS008` or another guard error) is `DATABASE_UNREACHABLE`, its message carrying Postgres's detail.
4. **Hand over.** The result carries the short link to the plugin approval page on the engine's local pages, with a `personMessage` and next steps ([Plugin approval links](#plugin-approval-links)); `basalt mcp` opens it in the browser. On an agent-operated engine: the portal short link, which the agent shows in the chat ([Plugin approval through the portal](#plugin-approval-through-the-portal)).
5. **Sign.** The person reads the page and signs with a passkey registered on that database. The page relays the signature to the engine over its own origin (on the portal: inside its Vault session), and `submit_plugin_approval` verifies it and appends `PLUGIN_APPROVED` to the ledger of every agent the approval lists. The agent never relays or holds a plugin signature.
6. **Start.** No restart and no command: the running engine sees the signed approval within a few seconds, checks it as at start, records the entry and starts it ([Plugin changes while the engine runs](#plugin-changes-while-the-engine-runs)). The agent's waiting call returns `RUNNING` once it serves the entry `READY` on that approval.

Narrowing needs no new approval: the engine checks that the approval names the agent, not that the lists are equal, so the agents that stay still match and an agent removed from the entry is simply no longer served.

#### Signer states

- **`KNOWN`**: the manifest's `.sig` names a publisher key built into the engine, passes its schema and verifies. The key's id is recorded (`signerKeyId`).
- **`UNKNOWN`**: everything else: no `.sig`, a `.sig` that does not pass its schema and names no built-in key, or one that names a key the engine does not have built in. A signature file carries a key id and no public key, so a signature by an unknown key cannot be checked at all, and its key id could be made up. No key id is recorded or shown for it, and it is treated exactly as unsigned.
- **A `.sig` that names a built-in key and does not pass its schema or does not verify is refused**, whatever the approval says: at `add` and `enable` (`PLUGIN_REFUSED` `NOT_TRUSTED`) and at every start (`PLUGIN_NOT_TRUSTED`). That is damage or tampering.
- **The trust store does not make a publisher known** in the approval flow: in same-user mode an agent can write it. It keeps its role for an entry that does not require approval, which a person adds to `engine.json` by hand.
- **No publisher key is built in yet**, so until one ships every plugin is `UNKNOWN`, and the page's level 1 cannot occur.
- **Verification** of an entry that requires approval, at `add`, `enable` and every start: steps 1, 2, 4 and 5 of [Verification](plugins.md#signing-and-the-trust-store) as for any entry; step 3 becomes "a `.sig` that names a built-in key passes its schema and verifies", and the signer state is worked out as above.
- **The approval takes the place of the trust record.** An entry that does not require approval is served to an agent only when that agent's ledger records the key that signed it ([A record that cannot be written](plugins-ledger.md#in-the-ledger)). For an entry that requires approval, the signed approval takes that place: the engine serves it without a `PLUGIN_TRUST_ADDED` of any key, and a `PLUGIN_TRUST_REMOVED` never withholds it or writes its `PLUGIN_DISABLED`. The key it rests on is built in or there is none, and the approval records the signer state the person saw.

#### How long an approval lasts

- **Pending.** A pending approval expires 24 hours after it is opened (`expiresAt`). The entry then stays in the config, withheld, and `status` says the approval expired and names the two ways out: open a new approval (`request_plugin` with `name`, or with `source` again) or remove the entry (`request_plugin` with `name` and `remove: true`).
- **Cancelled.** Opening a new approval for the same `(name, instance)` in a database cancels the earlier pending one there.
- **At most 8 pending** plugin approvals per database, so an agent cannot flood the person or the disk. Opening a ninth is refused (`TOO_MANY_PENDING`); expired and cancelled ones do not count.
- **Signed.** A signed approval does not expire and is not single use. It stays the entry's approval for an agent until a newer approval for the same `(name, instance)` that names that agent is opened in its database, or the entry is turned off or removed for that agent. A newer approval decides from the moment it is opened: until it is signed, the entry is withheld. So removing an entry and adding it again always needs a new signature, even when both happen between two engine starts, because adding opens a new approval, and because `PLUGIN_OPEN` writes the ends owed (below) before it writes the entry, refusing `PLUGIN_REFUSED` `DATABASE_UNREACHABLE` and writing nothing when one cannot be written ([Plugin approval in service mode](plugins-approval-service-mode.md#plugin-approval-in-service-mode)). An agent running as the engine's OS user that flips `enabled` in `engine.json` itself between two starts is not seen: the stated limit of same-user mode, as for dropping the `approval` key. "Newest" is by `opened_at`, ties broken by `approval_id`.
- **Turning off ends it.** A `PLUGIN_DISABLED` of `(name, instance)` in an agent's ledger, written after that agent's `PLUGIN_APPROVED`, ends the approval for that agent: `record_plugin_event` marks it ended when it writes the row, so the end outlives the ledger's one-year retention. The engine writes `PLUGIN_DISABLED` when the entry was disabled or removed, when the agent was removed from it, and when it withholds for an approval reason an entry the agent's ledger records as served ([Plugin approvals at engine start](#plugin-approvals-at-engine-start)). Turning it on again, also for the exact same copy, agents and settings, always needs a new signature: anything that turns something on goes through the person. Such records only narrow, so it does not matter that an agent role can write them. An end may follow a signed approval that was never served: disabling or removing an engine-kept entry ends its signed approvals at once ([Plugin approval in service mode](plugins-approval-service-mode.md#plugin-approval-in-service-mode)).

### What a plugin approval binds

The binding text is the text `open_plugin_approval` builds from the detail the caller passes and Postgres validates, as for held writes ([What an approval binds](approvals.md#what-an-approval-binds-decision-m2-1)): it follows the [text rules](stores.md#text-rules) at every depth (Postgres's `jsonb` text does), and clients parse the text and never rebuild it. **Challenge** = `sha256(utf8(binding text))`, in `clientDataJSON.challenge` as base64url without padding. Every list is sorted by its text `COLLATE "C"`, with no repeats. Schema: [`binding.schema.json`](../api/plugin/approval/binding.schema.json). For example (a level 3 vector):

```json
{"kind": "PLUGIN", "name": "local-ner", "hooks": ["wire.detect"], "roles": ["VALUE"], "store": {"kind": "POSTGRES", "name": "app"}, "agents": ["agent:product_b"], "egress": [], "signer": "UNKNOWN", "version": "0.3.1", "endpoint": {"kind": "LOCAL"}, "instance": "client_x", "expiresAt": "2026-11-20T10:00:00.500000Z", "isolation": {"files": "NONE", "network": "NOT_ENFORCED"}, "approvalId": "…", "requestedBy": "agent:product_b", "manifestSha256": "…", "settingsSha256": "…"}
```

| Key | Value | The engine matches it at start |
|---|---|---|
| `kind` | `PLUGIN` | no |
| `approvalId` | the approval's id | no |
| `store` | `{kind, name}`: the store's kind and the name it gives what the agents are bound to (`current_database()` in Postgres), for display | no |
| `expiresAt` | Exactly `YYYY-MM-DDTHH:MM:SS.ffffffZ` ([Text rules](stores.md#text-rules)), 24 hours after the approval was opened | no |
| `requestedBy` | the agent that opened it, `agent:<name>` (from the role that is `session_user`): which agent asked | no |
| `agents` | the agents of this store the entry will serve, each `agent:<name>` whose role is a member of `<prefix>_agents`; at least one | the agent is in it |
| `name`, `instance`, `version`, `manifestSha256` | of the installed copy | yes |
| `settingsSha256` | lowercase hex `sha256` of the settings text (below) | yes |
| `hooks`, `roles` | the manifest's hooks, and its `wire.detect` roles, present exactly when `hooks` holds `wire.detect` | yes |
| `endpoint` | `{"kind": "LOCAL"}`, or `{"host": "<host:port>", "kind": "REMOTE"}` | yes |
| `egress` | the manifest's `network.egress` | yes |
| `isolation` | `LOCAL` only: `{files, network}` with the values the plugin events use ([In the ledger](plugins-ledger.md#in-the-ledger)); in same-user mode `files: NONE`, `network: NOT_ENFORCED` | yes |
| `signer`, `signerKeyId` | `KNOWN` with the built-in key's id, or `UNKNOWN` with no `signerKeyId` | yes |
| `change` | what differs from the approved entry (below) | no |

- **The detail.** `open_plugin_approval(p_detail jsonb, p_settings jsonb)` takes the keys `agents` to `signerKeyId` of the table, without `settingsSha256`; Postgres adds `kind`, `approvalId`, `store`, `expiresAt`, `requestedBy`, `settingsSha256` and `change`. It validates the detail with the rules of `_check_plugin_detail` ([schema version 3](basalt-meta-schema-versions.md#schema-version-3-plugin-events)) and the binding schema: shapes and patterns, a semantic `version`, `roles` exactly with `wire.detect`, `isolation` exactly with `LOCAL`, `signerKeyId` exactly with `KNOWN`, lists sorted with no repeats. It checks every agent in `agents` names a role that is a member of `<prefix>_agents` (`BS007` `NOT_ALLOWED` detail `UNKNOWN_AGENT` otherwise). A detail of an honest command always fits: a manifest whose detail could break these bounds is refused at `add` (`BAD_MANIFEST`), as for the plugin events.
- **The caller is not trusted** to tell the truth about the copy. The engine recomputes every field the table marks from the installed copy and its own config at each start, and serves only on an exact match ([Plugin approvals at engine start](#plugin-approvals-at-engine-start)). A caller that lies in the detail gets a signature for something the engine will not run. The fields marked "no" describe the request and are never matched.
- **Agents are named, not their roles.** `agents`, `requestedBy`, `change.agentsAdded` and `change.agentsRemoved` hold `agent:<name>` ([Agent names](stores.md#agent-names)), as a revert binding does, never the store's login. The guard maps each to its role (`<prefix>_agent_<name>`) from its record of the install's agents; the engine matches an agent by its own name. The page shows the part after `agent:`, as the approval and revert pages do.
- **The settings text** is the `jsonb` text Postgres returns for the object of the entry's keys other than `name`, `instance`, `manifestSha256`, `enabled`, `agents` and `approval` (today `config`, `auth`, `timeoutMs` and `minConfidence`), each only when the entry sets it: `config` and `auth` as `engine.json` holds them, and the numbers `timeoutMs` and `minConfidence` by value, in their shortest decimal form (`0.60` and `0.6` are the same setting and both are written `0.6`, as the engine writes its entries). No default is filled in, so writing `"timeoutMs": 300` where it was absent is a change. It is `{}` when the entry sets none ([`binding.schema.json`](../api/plugin/approval/binding.schema.json), `$defs/settings`). A plugin's settings can decide where data goes, so a change to them needs a new approval. Go and JavaScript never build it: `open_plugin_approval` takes the object as `p_settings`, computes `settingsSha256` itself, and stores and returns the text; the engine, at start, sends the object it reads from `engine.json` to the agent's database as `jsonb` and reads its text back (`SELECT $1::jsonb::text`) before it hashes it. So both sides get the same bytes: inside `config`, `0.60` stays `0.60` and `1e3` reads `1000` (a vector holds such a case), and a number written another way there is a change. The settings never hold a secret: [Config](plugins.md#config) refuses one in `config`, and `auth.credentialFile` is a path, never the file's contents.
- **`change`** is built by Postgres from its own records, never from the caller. It is present exactly when the database holds an earlier signed approval for the same `(name, instance)`, and then compares with the newest such one. Each key appears only when that thing differs: `fromVersion`, `fromManifestSha256`, `fromSigner`, `fromEndpoint` and `fromIsolation` hold the earlier value (`fromIsolation` is `null` when the earlier entry was `REMOTE`); `hooksAdded`, `hooksRemoved`, `rolesAdded`, `rolesRemoved`, `egressAdded`, `egressRemoved`, `agentsAdded` and `agentsRemoved` are sorted lists, never empty; `settingsChanged` is `true`. `{}` means nothing differs: the same entry turned on again. A change of built-in key with `signer` staying `KNOWN` has no key of its own yet; it is added with the first built-in key. A first approval of an entry that a person installed at a terminal has no `change`.

**In the ledger.** Neither detail names an agent, so no agent's ledger names another agent; the list is in the binding and the approval table ([`events.schema.json`](../api/plugin/events.schema.json), `approvalPendingDetail` and `approvedDetail`):

| Kind | Written by, to | Detail |
|---|---|---|
| `PLUGIN_APPROVAL_PENDING` | `open_plugin_approval`, to the ledger of the agent that opened it | the binding's keys without `kind`, `store`, `requestedBy`, `agents` and `change` |
| `PLUGIN_APPROVED` | `submit_plugin_approval`, to the ledger of every agent the approval lists | the same without `expiresAt`, plus `credentialId` (the passkey that signed, base64url) and `bindingSha256` (lowercase hex of the challenge) |
| `PLUGIN_APPROVAL_WITHDRAWN` | `withdraw_plugin_approval` ([schema version 15](basalt-meta-schema-versions.md#schema-version-15-withdraw)), to the ledger of the agent that opened it | `approvalId`, `name`, `instance` and the `reason` the agent gave ([Withdrawn requests](approvals.md#withdrawn-requests)) |

`record_plugin_event` refuses both kinds, so no agent role can write a `PLUGIN_APPROVED` row, and the engine's check reads the approval, never an event an agent role could have written.

### The plugin approval page

`<base>/plugins/<approvalId>` ([Page links](page-links.md#page-links)): on the portal for an agent-operated engine, on the engine's local pages otherwise. One page, three levels (owner decision, from a mockup).

- **Input.** The binding text and the settings text, and nothing else: from a long link's format 2 fragment (`texts` are exactly `[binding, settings]`, then optionally `credentialIds`; [Format 2](approvals.md#format-2-the-compact-request)), from a hash link's request file or text blocks ([The request file and pasted blocks](showing-links.md#the-request-file-and-pasted-blocks)), or, for a short link, from `GET /api/v1/plugins/{approvalId}` ([`request.schema.json`](../api/plugin/approval/request.schema.json)): on the engine's own origin, or on the portal inside a Vault session ([Plugin approval through the portal](#plugin-approval-through-the-portal)). The level and every sentence are derived on the page from the binding text.
- **Checks before anything is shown.** The binding's `approvalId` is the id in the page's path; `kind` is `PLUGIN` (otherwise the page says the link is not a plugin approval and shows no approve button); the binding passes [`binding.schema.json`](../api/plugin/approval/binding.schema.json); and the lowercase hex `sha256` of the settings text is `settingsSha256`. When the settings do not match, the page says the settings in the link do not match what would be approved and to ask the agent for a new link, and shows no approve button.
- **The level**, from `signer`, `endpoint` and `isolation`:
  1. **Known publisher**: `signer` `KNOWN`. Calm.
  2. **Unknown publisher, fenced in**: `signer` `UNKNOWN`, and `endpoint` `REMOTE` or `isolation.files` `OS_USER`. One warning. (`open_plugin_approval` refuses `isolation.files` `OS_USER`: the engine runs every entry that requires approval itself, in either mode, and derives `NONE` for it, so such an approval would never match. A local plugin under its own OS user is a config entry added with `sudo`, which never requires approval. The page still derives the level from `isolation` as it is given.)
  3. **Unknown publisher, local, not fenced in**: `signer` `UNKNOWN`, `endpoint` `LOCAL` and `isolation.files` `NONE`: every local plugin in same-user mode. The strong warning, and the tick.
- **The tick** (level 3 only): a checkbox labelled "I know who made this plugin and I trust them with my data." The approve button works only once it is ticked. Levels 1 and 2 have no tick.
- **The sentences.** The page shows these fixed sentences word for word, filling in only the `<…>` parts from the binding: `<name>` and `<version>` as they are; hosts as `host:port`, joined by ", "; agents by the part after `agent:`, joined by ", "; the publisher as `Basalt` (`KNOWN`) or `unknown` (`UNKNOWN`); a place as `the computer Basalt runs on` (`LOCAL`) or the host (`REMOTE`). The page cannot tell whose computer runs Basalt (an agent's own machine, or the person's laptop), so the words fit both. In this order:
  1. **What changes**, first, for a binding with `change`. With `change` `{}`: "You approved <name> before, and it was turned off. Turning it on again needs your approval." Otherwise "This changes <name>, which you approved before." and then, for each key present, in this order:
     - `fromVersion`: "Version <fromVersion> becomes <version>."; without it, `fromManifestSha256`: "Its files change, but its version stays <version>."
     - `fromSigner`: "Its publisher was <fromPublisher>; now it is <publisher>."
     - `fromEndpoint`: "It moves from <fromWhere> to <where>."
     - `fromIsolation`: "How it is kept apart from Basalt changes."
     - `hooksAdded`: "It gets new access to: <hookLabels>.", and `hooksRemoved`: "It no longer gets: <hookLabels>.", each hook by its label below, joined by "; ".
     - `rolesAdded`, one line per role: `NAME_CUE` "It now also looks for names in the text.", `VALUE` "It now also looks for private values in the text."; `rolesRemoved`: "It no longer looks for names in the text." and "It no longer looks for private values in the text."
     - `egressAdded`: "It now also connects to <hosts>."; `egressRemoved`: "It no longer connects to <hosts>."
     - `agentsAdded`: "It will now also be used for <agents>."; `agentsRemoved`: "It will no longer be used for <agents>."
     - `settingsChanged`: "Its settings change."
  2. **The level's line.** Level 1: "Published by Basalt." Level 2: "Nobody vouches for this plugin. Add it only if you trust where it came from." Level 3, in red: "Nobody vouches for this plugin. It runs a stranger's program on the computer Basalt runs on, with the same access as Basalt itself, so it could read your database password and the key Basalt uses to hide private values."
  3. **The tick**, at level 3.
  4. **Where it runs.** `REMOTE`: "It runs at <host>. Everything it sees is sent there." and "Basalt cannot check what runs there or where it sends things next." `LOCAL` with `files` `OS_USER`: "It runs on the computer Basalt runs on, as its own user, so it cannot read Basalt's files." `LOCAL` with `files` `NONE` at level 1, the plain line a known publisher still gets: "It runs on the computer Basalt runs on, with the same access as Basalt itself." (At level 3 the warning says it.)
  5. **A declared limit that is not enforced**, for `LOCAL` with `network` other than `ENFORCED`: with an empty `egress`, "It says it needs no network. That is not enforced on the computer Basalt runs on."; otherwise "It says it connects only to <hosts>. That is not enforced on the computer Basalt runs on."
  6. **What it sees**, one line per hook in the binding's order, from the consent texts of [Consent](#consent) and [Hooks](plugins.md#hooks):
     - `wire.detect` (label "the text your agents send to the AI provider"): "It reads the text your agents send to the AI provider, before Basalt hides private values in it." With `NAME_CUE` among its `roles`, then: "It also sees values from your database that appear in that text."
     - `feed.observe` (label "what your agents do in the database"): "It is told what your agents do in the database, such as which tables they change and how many rows, never the values."
     - `approval.deliver` (label "your approval links"): "It delivers your approval links. Anyone who can read where it delivers them can see the rows of writes waiting for your approval. Some links carry the whole request, so they can also see what the agent asked to run and why."
     - `classify.suggest` (label "the names of your tables and columns"): "It reads the names and types of your tables and columns, never their values, and suggests which ones hold private data."
  7. "Used for: <agents>." (the binding's `agents`), then "Asked by <agent>." (`requestedBy`), then "Plugin fingerprint: <fingerprint>", the first 16 hex digits of `manifestSha256` in four groups of four (`a1a1 a1a1 a1a1 a1a1`).

  Beside them the page shows the plugin's name and version, the database, and the settings text. `TestPluginApprovalVectors` builds each vector's sentences from these rules and checks every sentence above is written here word for word.
- **Signing.** The approve button asks for the passkey with the binding's challenge, `allowCredentials` from `credentialIds` when present, and `userVerification: "required"`. The result is the signed response ([`response.schema.json`](../api/plugin/approval/response.schema.json)): `{ "approvalId", "credentialId", "authenticatorData", "clientDataJson", "signature" }`, as an approval response. On a short link the page posts it to the relay and shows "Approved. The plugin starts within a few seconds."; if the relay fails, it shows the error and tells the person to open the link again or ask the agent for a new one; it never shows a code to paste. On a long or hash link, which has no engine and which nothing issues any more, the approve button stays off ([Plugin approval links](#plugin-approval-links)): it relays nothing and tells the person to ask the agent for a new link.

### Plugin approvals at engine start

Same-user mode. At each start, for each enabled entry that requires approval and each agent it lists, after [verification](#signer-states), the engine reads `agent_plugin_approvals` with that agent's credential (within the 15 seconds of [A record that cannot be written](plugins-ledger.md#in-the-ledger)) and takes the newest approval for `(name, instance)` that names the agent's role. Such an entry is served to no agent until this check passes for that agent: an agent whose approvals were never read is not served.

| What the engine finds | Served to that agent | `status` problem for that agent |
|---|---|---|
| The agent's guard is older than [schema version 5](basalt-meta-schema-versions.md#schema-version-5-plugin-approvals) | no | `PLUGIN_UNAVAILABLE`, reason: the guard is older than schema version 5 (update the guard with the setup page's `UPDATE`; on an agent-operated engine an `UPGRADE` setup code; the running engine checks again on its own) |
| The approvals cannot be read (no answer within 15 seconds, or the guard refused) | no | `PLUGIN_UNAVAILABLE`, with the reason |
| No approval names the agent | no | `PLUGIN_AWAITING_APPROVAL`: none was opened |
| The newest is pending | no | `PLUGIN_AWAITING_APPROVAL`, with its expiry |
| The newest was cancelled (a newer approval for the entry does not name this agent) | no | `PLUGIN_AWAITING_APPROVAL` |
| The newest expired unsigned | no | `PLUGIN_APPROVAL_EXPIRED` |
| The newest is signed and a matched field differs, ended or not | no | `PLUGIN_APPROVAL_MISMATCH`, naming the fields that differ, never a value |
| The newest is signed, every matched field is equal, and it has ended for this agent (turned off or removed since, or withheld for a mismatch) | no | `PLUGIN_AWAITING_APPROVAL`: turning it on again needs a new approval |
| The newest is signed and every matched field is equal | yes, if the usual checks pass (a local plugin may run on this engine, the record is written) | none from the approval |

- **Matched fields** are those [What a plugin approval binds](#what-a-plugin-approval-binds) marks: `name`, `instance`, `version`, `manifestSha256`, `settingsSha256` (recomputed through the agent's database), `hooks`, `roles`, `endpoint`, `egress`, `isolation` (as the entry would run on this engine), `signer` and `signerKeyId`, each equal to what the engine derives from the installed copy and `engine.json`; and the agent in `agents`.
- **The newest is per agent.** Only an approval that names the agent decides for that agent. An approval another agent of the database opens for the same `(name, instance)` that does not name this agent never withholds the entry from it or changes what it is served, pending or signed, and its `PLUGIN_DISABLED` ends nothing for this agent. Opening one does cancel a pending approval of the entry that names this agent: until a new one is signed the entry stays withheld from it, never served.
- **Withheld** is as in [A record that cannot be written](plugins-ledger.md#in-the-ledger): the entry refuses any call naming that agent, and an entry left with no agent is not started. Other agents and every other tool are served as before, and so is the agent itself: a withheld entry blocks none of its calls.
- **Not active is not failing.** An entry withheld with `PLUGIN_AWAITING_APPROVAL` or `PLUGIN_APPROVAL_EXPIRED` (none opened, pending, cancelled, expired unsigned, or turned off since it was signed) is simply not active for that agent: nothing was promised yet, so it never makes a data-path hook fail closed ([Failure](plugins-runtime.md#failure)), and the agent can still carry the approval link to its person. An entry withheld with `PLUGIN_APPROVAL_MISMATCH`, approved and no longer matching, counts as a failing entry of its hook, as [Failure](plugins-runtime.md#failure) says for that hook; for `wire.detect` that is settled with the `detector/1` contract. No data-path hook is called yet, so today no withheld entry blocks anything; a withheld `feed.observe` entry gets no event of that agent.
- **The record.** An entry withheld with `PLUGIN_UNAVAILABLE` keeps its record as it is, as any entry that is not started does, so a passing failure ends nothing. An entry withheld with `PLUGIN_AWAITING_APPROVAL`, `PLUGIN_APPROVAL_EXPIRED` or `PLUGIN_APPROVAL_MISMATCH` keeps it too, except when the agent's ledger records it as served: then the engine writes `PLUGIN_DISABLED` with the detail last recorded, as for a removed signing key, so the ledger never shows it served after it stopped matching. That ends any approval of it for that agent ([How long an approval lasts](#how-long-an-approval-lasts)), so an entry withheld for a mismatch keeps showing `PLUGIN_APPROVAL_MISMATCH` while it differs, and `PLUGIN_AWAITING_APPROVAL` once changed back: changing it back needs a new approval too. An entry served this way is recorded with `signer` in its `PLUGIN_ENABLED` or `PLUGIN_CHANGED` detail ([In the ledger](plugins-ledger.md#in-the-ledger)); its `PLUGIN_ENABLED` is written only after its approval matched.

### Plugin changes while the engine runs

Same-user mode only; in service mode the engine reads `plugins` at start only, as before. The engine applies plugin changes while it runs, so after a person signs nobody restarts it.

- **What it watches.** `engine.json`, read every second (a change made by any writer is seen); and, while an entry that requires approval is configured, each agent's ledger and plugin approvals, read with that agent's own credential over the connections the engine already holds: every 2 seconds while such an entry waits for a signature for one of its agents (`PLUGIN_AWAITING_APPROVAL`), every 15 seconds otherwise. With no entry that requires approval, no database is read until `engine.json` changes.
- **One check, as at start.** Each time, the engine derives what each agent should be served by the checks of [Plugin approvals at engine start](#plugin-approvals-at-engine-start), [Signer states](#signer-states) and [In the ledger](plugins-ledger.md#in-the-ledger), with the same code: verification of a new or changed entry's installed copy, the approval match, the record. It writes `PLUGIN_ENABLED` or `PLUGIN_CHANGED` before an entry starts serving an agent, and `PLUGIN_DISABLED` after it stopped.
- **Starts without a restart.** An entry that requires approval starts once a matching approval is signed for an agent, within a few seconds of the signature, for each agent whose approval matches; an agent added to a served entry is served once its own approval matches.
- **Stops without a restart.** Any entry, whether or not it requires approval, stops for an agent within a few seconds of `engine.json` turning it off (the next read, plus the stop), removing it or removing that agent, before any database is read. An entry that requires approval also stops for an agent when the check finds its approval no longer matches (a newer approval naming the agent, pending or signed and not matching; the approval ended; a matched field changed): `status` shows the same problem as at start. Stopping is as at engine stop: drain, `shutdown`, close, within 5 seconds. One process serves all of an entry's agents, so when the agents it serves change, the engine stops it and starts it again for the agents it now serves.
- **A changed entry.** A change to an entry that requires approval (a new copy, new settings, other agents) stops the running plugin as soon as the engine sees it, before any database is read. It runs again once a matching approval is signed: for a new copy, the approval `add` opened for it. Until then it is withheld as at start.
- **What still needs a restart.** Adding an entry that does not require approval, turning one on, or changing its copy or settings (a hand edit of `engine.json`, [Consent](#consent)): while the engine runs such an entry only narrows, and the change takes effect at the next start. Every key of `engine.json` outside `plugins` (agents, `mode`, `operatedBy`), also take effect at the next start. So does any change to the trust store: while the engine runs, an entry that does not require approval keeps the verification and trust store of the start.
- **A file the engine cannot read.** When `engine.json` changes and does not parse, fails validation or cannot be read, the engine applies nothing: every plugin keeps running or stopped as it was, no database is read for plugins and no record is written (so a newer approval or an ended one is not acted on either until the file can be read), and `status` shows every agent `PLUGIN_CONFIG_INVALID` (`WARNING`), naming no entry; the engine's log says what is wrong. Once the file can be read again, its state applies. Changes are level-triggered: two writes between two reads end in the state of the last.
- **A database that does not answer.** When an agent's database does not answer (no connection, or no answer within 5 seconds), nothing is decided for that agent and what runs for it stays as it is: a served entry keeps being served (its approval was verified, and no revocation can be written to a database that does not answer), an entry not served stays withheld, and a change to the entry or its config still stops it. Any answer decides as at start: a guard that refuses, is missing or is too old, or an agent served status only, withholds. An agent whose check failed either way is checked again after 2 seconds, doubling up to 60 seconds, until its check passes, also when no entry requires approval (a `PLUGIN_DISABLED` it still owes is written then); the other agents are checked as usual. A `PLUGIN_DISABLED` that could not be written is tried again 2 seconds later.
- **Shutdown.** The watch stops with the engine; the plugins stop within 5 seconds, as at any engine stop.

### Plugin approval links

What `request_plugin` hands over when it opens an approval ([MCP tools](mcp-tools.md#mcp-tools)).

- **The link.** `approvalUrl` is the short link `<base>/plugins/<approvalId>#s=<secret>` on the engine's local pages, issued in process for the caller, which keeps its secret in `<agent>.links.json` ([Link secrets](local-pages.md#link-secrets)). There is no long or hash link for a plugin approval and no request file: a person-operated engine without local pages refuses the tool (`NO_LOCAL_PAGES`). On an agent-operated engine the link is the portal short link over the [Vault channel](vault-channel.md#vault-channel), and an engine that cannot hand one over refuses `NO_PORTAL_LINK` ([Plugin approval through the portal](#plugin-approval-through-the-portal)). The link is never handed to an `approval.deliver` plugin.
- **`personMessage`**: "<agent> asks you to approve the plugin <name> <version>." (with a `change`: "<agent> asks you to approve a change to the plugin <name> <version>."), then the page's level line, then "Approve it with your passkey:" (level 3: "Approve it with your passkey only if you know who made it:"), then the link as a paragraph of its own, then "Expires <YYYY-MM-DD HH:MM> UTC. The plugin starts within seconds of your approval." The rules of [Links in `personMessage`](showing-links.md#links-in-personmessage) apply. When the database has no registered passkey, `personMessage` says so first and the steps start with those of `APPROVAL_REQUIRED` `NO_PASSKEY`.
- **`nextSteps`**: P `OPEN_LINK`; A `CALL_TOOL` (`request_plugin` with `approvalId`: the wait, in the same turn after showing `personMessage`).
- **The warning in the chat is a courtesy.** `personMessage` carries the page's level line, so an honest agent relays it. No warning lives only there: the agent's text is not trusted, and a tricked agent would leave it out. The page is what protects the person.

### Plugin approval through the portal

Persona 2 plugin approval (owner decision of 22 Nov 2026). On an engine a bot operates, a plugin is approved the way a held write is. `request_plugin` opens the approval and the agent hands the person a portal short link. The portal page reads the plugin's details from the engine over the [Vault channel](vault-channel.md#vault-channel), and the person signs with a passkey. Postgres verifies the signature, and the engine serves the plugin only on a verified approval.

**What is reused, unchanged.** The signed data and its checks: the binding and settings texts ([What a plugin approval binds](#what-a-plugin-approval-binds)), `open_plugin_approval` and `submit_plugin_approval`, the signed response, the checks at start and while the engine runs, the expiry, the 8 pending approvals. No guard change. The tool's arguments, results, states and next steps ([MCP tools](mcp-tools.md#mcp-tools)). The page's checks, levels, tick, sentences and signing ([The plugin approval page](#the-plugin-approval-page)). The channel's link secret, handshake, frames, limits, close codes and Vault messages, as for an approval or a revert. The upload and the engine-kept entries of [Plugin approval in service mode](plugins-approval-service-mode.md#plugin-approval-in-service-mode).

**What is new.**

1. Engine-kept entries on an agent-operated engine, and `request_plugin` served there (below).
2. A plugin approval's portal short link, registered at the Vault like a held write's.
3. Two routes a Vault session dispatches: `GET /api/v1/plugins/{approvalId}` and `POST /api/v1/plugins/{approvalId}/approve` ([Frames](vault-channel.md#frames)).
4. One refusal reason, `PLUGIN_REFUSED` `NO_PORTAL_LINK`.
5. One sentence on the portal page, the only one the page does not derive from the binding.

**Where.** An engine whose `operatedBy` is `AGENT` and that runs as the agent's own OS user: the bot's computer, where `basalt mcp` starts the engine ([Who operates the engine](setup.md#who-operates-the-engine)). An agent-operated engine that runs as a service under its own OS user stays refused `AGENT_OPERATED`: no beta install runs that way. A person-operated engine is unchanged (persona 1: the local pages, [Plugin approval links](#plugin-approval-links)), and so is the `SAME_USER_MODE` refusal of a person-operated engine that runs as the person's own OS user.

**On such an engine.**

- **Engine-kept entries.** The engine keeps them as a service engine does ([Plugin approval in service mode](plugins-approval-service-mode.md#plugin-approval-in-service-mode), Engine-kept entries): `<stateDir>/plugins.json`, the installed copies under `<stateDir>/plugins/`, at most 16 entries, 4 open uploads and 1 GiB, and every entry requires approval, as every entry already does on an agent-operated engine. It runs a local entry as its own child, as same-user mode runs any local plugin ([Transports](plugins-runtime.md#transports)), and applies changes while it runs ([Plugin changes while the engine runs](#plugin-changes-while-the-engine-runs)). A change `request_plugin` makes to its engine-kept entries applies also while `engine.json` cannot be read: only the config entries wait for the file, as that section says. A local entry is bound and recorded with `isolation` `{"files": "NONE", "network": "NOT_ENFORCED"}`, so a plugin by an unknown publisher gets the level 3 page.
- **Who may call.** Every agent of the engine: they run as the engine's OS user, the one user the agent's socket admits. The scope is the rule of [Agents](mcp-tools.md#mcp-tools): the caller is listed, and every listed agent uses the caller's database. `personUids` and the OS-user scope (SM-4) do not apply. An engine that runs as root opens no local plugin (`ENGINE_IS_ROOT`).
- **The upload** is the service engine's: `basalt mcp` reads the folder and uploads it over a second connection to the agent's socket ([The upload](plugins-approval-service-mode.md#plugin-approval-in-service-mode)). It uploads when the engine's hello answer says `operatedBy` `AGENT`, as it does for `PERSON` with a local page origin. The engine could read the path on this computer, but it does not: both personas use one code path.

**The link.** `approvalUrl` is the portal short link `https://portal.basaltvault.app/plugins/<approvalId>#s=<secret>`, issued for the caller and kept in `<agent>.links.json` with its `linkToken` and `psk` ([Link secrets in a session](vault-channel.md#link-secrets-in-a-session)). Before handing it over, the engine registers it at the Vault (`REGISTER_LINK`, waiting up to 5 seconds for `OK`), as for a held write's portal link. A plugin approval has no long or hash link to fall back to, and nothing takes a pasted plugin code, so:

- **Before anything is written**, the install, change and `name` forms are refused `PLUGIN_REFUSED` `NO_PORTAL_LINK` when the engine cannot hand over a portal link: `vault` is `OFF`, the key file is refused (`KEY_ERROR`), the engine has no `READY` socket to the Vault, or the caller's database revoked this engine ([Engine revocation](vault-channel.md#engine-revocation)). The message names which, and the upload is dropped as for every refusal. The upload methods refuse `NO_PORTAL_LINK` in the same cases, before anything is written, so a call that would be refused uploads nothing.
- **After the approval was opened**, a registration that fails (an `ERROR`, or no `OK` within 5 seconds) leaves the entry written and withheld, as an open refused after the write does ([Plugin approval](#plugin-approval), step 3). The call answers `PLUGIN_REFUSED` `NO_PORTAL_LINK` and issues no link. The `name` form opens a new approval later, which cancels the one nobody can reach.
- **Removal and the wait** need no link, and are never refused for one.

With `devLocalPages` (development only, [Page origins](page-links.md#page-origins)) the link is the local short link and the page reads from the engine on its own origin, as on persona 1.

**`personMessage` and next steps** are those of [Plugin approval links](#plugin-approval-links), with the portal link. `basalt mcp` opens nothing on an agent-operated engine ([Auto-open](cli.md#auto-open)): the agent shows the link to the person in the chat.

**The page on the portal.** At `https://portal.basaltvault.app/plugins/<approvalId>#s=<secret>` the page derives `linkToken` and `psk` from the fragment and opens a session through the Vault, as the approval and revert pages do. In the session it reads `GET /api/v1/plugins/{approvalId}`: the binding and settings texts, which carry the name, version, signer, manifest hash and agents, and `credentialIds` ([`request.schema.json`](../api/plugin/approval/request.schema.json)). After the passkey signs, it posts the response to `POST /api/v1/plugins/{approvalId}/approve`. Everything else is [The plugin approval page](#the-plugin-approval-page). In addition:

- It shows the engine's fingerprint next to the agent, as every portal page with a session does ([Engine keys](vault-channel.md#engine-keys)), in a line that names it the engine's, apart from the "Plugin fingerprint" line, which is the manifest's.
- At every level, between items 4 (Where it runs) and 5 (A declared limit) of the sentences, it shows: "Basalt runs on the agent's own computer, as the same user as the agent. Your approval decides whether Basalt runs this plugin. It cannot stop the agent from reading what Basalt can." The page shows it because it runs on the portal, and only an agent-operated engine hands over a portal plugin link. It does not depend on the binding: an agent on that computer holds the database credential, so it can open an approval whose detail it chose itself (a `KNOWN` signer, a `REMOTE` endpoint) and get a calmer level. An honest engine never runs such an approval, because it matches every field against the installed copy ([What a plugin approval binds](#what-a-plugin-approval-binds)), but the page cannot know the engine is honest.
- The relay answers `{ "approvalId", "status": "APPROVED", "approvedAt" }`, with no receipt, as on loopback ([Local pages](local-pages.md#local-pages)). There is no receipt kind for a plugin approval. The page shows "Approved. The plugin starts within a few seconds.", and the agent's wait returns `RUNNING` once the engine serves the plugin.
- A session that cannot be opened is shown as for an approval ([Close codes](vault-channel.md#close-codes)): link gone, engine offline, broken, or try later.

**The honest limit (owner decision, 22 Nov 2026).** On the bot's computer the bot and the engine run as one OS user, so there the approval is consent, not containment.

- The bot can read everything the engine can: every agent's credential on that engine, `pii.key` and the engine's key file. It can change the engine's files, `plugins.json` and `engine.json` included. It can run any program itself without asking anyone. A plugin the person approves runs with the engine's access: it can read what BasaltDB can.
- What the approval still gives: an honest engine runs a plugin only on an approval a person signed with a passkey and Postgres verified; the ledger records what was approved and with which passkey, and nobody but a passkey holder can create that record; an agent that uses only Basalt's tools, tricked by text or not, can only produce a link.
- What it does not give: any protection from a bot that is hostile, or that runs commands of its own on that computer. Such a bot needs no plugin to reach what the engine can.
- For beta there is no isolated path: a plugin under its own OS user is not built, and is added when a user asks for it.
