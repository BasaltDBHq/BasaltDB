> Part of **Plugins**. The section starts in [plugins.md](plugins.md).

### Plugin approval in service mode

`basalt init` at a terminal installs the engine as a background service by default, so a person's own laptop usually runs in service mode. There a person adds a plugin as in same-user mode: they tell their agent to add it, approve once with a passkey on the [plugin approval page](plugins-approval.md#the-plugin-approval-page), and it runs. No step needs `sudo` and nothing runs as root. The engine runs such a plugin itself, as its own OS user, without the isolation a plugin added with `sudo` gets, and the page says so. Everything in [Plugin approval](plugins-approval.md#plugin-approval) and the sections after it applies, except where this section says otherwise.

**What the person gives up.** Service mode exists so that agents cannot read the engine's files. A local plugin approved this way runs as the engine's OS user, so it can read what the engine can: every agent's database credential on that engine and the masking key (`pii.key`). It can also change what the engine can change: the engine's config directory and state directory, and the sockets in its socket directory. With an agent's credential it can write plugin events to that agent's ledger and open plugin approvals for that agent's database, so for an engine running such a plugin [the plugin events](plugins-ledger.md#in-the-ledger) are only as trustworthy as the plugin. That is the same as a local plugin in same-user mode. A person who wants a local plugin fenced in adds it to `engine.json` as root, as a config entry, which runs it under its own OS user and unit ([Isolation and trust](plugins-runtime.md#isolation-and-trust)). A remote plugin runs no process on the machine, so it gives up none of this. What no plugin and no agent can do is sign: an entry is served only with an approval a person signed with a passkey, which Postgres verifies.

**Two kinds of entry.**

- **Config entries**: `engine.json`'s `plugins`, added to `engine.json` by hand as root, each local one under its own unit and OS user (`files: OS_USER`). Unchanged by this section, and they never require approval.
- **Engine-kept entries**: added without `sudo`, by the agent with [`request_plugin`](mcp-tools.md#mcp-tools). The engine keeps them under its own state directory. **Every engine-kept entry requires approval**, whatever the file says, so this section's rules hold for it on a person-operated engine and on an agent-operated one alike.

The agent's `status` shows both kinds of entry served to it, with their health (`plugins`).

**Asking.** A refusal is `request_plugin`'s `PLUGIN_REFUSED` error with the engine's reason and message, and the steps A `STOP`, A `ASK_PERSON`.

- **The agent asks, through the engine.** [`request_plugin`](mcp-tools.md#mcp-tools) is how an entry is added, changed or removed: `basalt mcp` uploads the plugin's files over a second connection to the agent's own socket as the agent's OS user, and the engine runs `PLUGIN_OPEN` and `PLUGIN_REMOVE` in process for that user, with the credentials it holds. An install or change always opens an approval (unless the change only narrows, below), and a removal acts on engine-kept entries only. There is no `basalt plugin` command.
- **Config entries** are edited in `engine.json` by hand, as root, and read at the engine's start.
- **Who may call.** On a person-operated engine, an agent whose OS user is a uid in `personUids` (the person's), through `request_plugin` (on an agent-operated engine: [Plugin approval through the portal](plugins-approval.md#plugin-approval-through-the-portal)). An agent's own OS user, when it is not the person's, is refused `AGENT_NOT_ALLOWED` before anything is read or written, its upload included; root and the engine's user are never admitted.
  - **Scope (SM-4).** The plugin methods are scoped to the agents whose `osUser` is the caller's uid: `PLUGIN_OPEN`'s `agents`, and every agent of the entry it changes before and after, must be among them; `PLUGIN_DISABLE` and `PLUGIN_REMOVE` act only on an entry whose `agents` are all among them; `PLUGIN_LIST` lists only entries that name one of them, and shows only those agents. Otherwise the request is refused with `AGENT_NOT_ALLOWED` before anything is read or written. On the default laptop install (`basalt init` without `--os-user`) the person's uid is the `osUser` of every agent, so nothing is narrowed. The upload methods are not scoped.
  - An agent that runs under the person's own uid (a coding agent on a laptop) reaches these methods: that is how "tell the agent to add a plugin" works. It is safe for the reason it is in same-user mode: such an agent can open an approval, which nothing serves until a person signs it with a passkey, and narrow (disable, remove, or remove agents from an enabled entry). It can never turn on what a person turned off.
- **Only the engine opens plugin approvals for engine-kept entries.** It does so only on a `PLUGIN_OPEN` that `request_plugin` runs, and only for the agents that request names explicitly: there is no default to every agent. It opens them in the guard with the listed agents' own credentials, which it holds. On a person-operated engine with no engine-kept local plugin running, nothing else can: an agent's OS user cannot read its credential, and the SQL tools refuse `open_plugin_approval`, `submit_plugin_approval` and every other `basalt_meta` function (`STATEMENT_REFUSED`, `FUNCTION_NOT_ALLOWED`). Where something else holds a credential (an agent on an agent-operated engine, or a local plugin running as the engine's user), it can also open approvals for that credential's database, as in same-user mode: an opened approval only cancels a pending one or withholds an entry, and serves nothing until a person signs it.
- **Operated by an agent.** An agent-operated engine that runs as the agent's own OS user keeps engine-kept entries, admits every agent of the engine without `personUids`, and hands over a portal link ([Plugin approval through the portal](plugins-approval.md#plugin-approval-through-the-portal)); one that runs as a service under its own OS user refuses `request_plugin` (`PLUGIN_REFUSED` `AGENT_OPERATED`).

**Engine-kept entries.**

- **The entries file** is `<stateDir>/plugins.json`, owned by the engine's OS user, mode `0600`.
  - It holds a JSON array of entries in the shape of `engine.json`'s `plugins` ([`engine-entries.schema.json`](../api/plugin/engine-entries.schema.json)), each with `instance` and `"approval": "REQUIRED"`, and none with `auth`. At most 16 entries.
  - Only the engine writes it, holding an exclusive lock (`flock`) on `<stateDir>/plugins.json.lock` (the engine's, mode `0600`), as a new file renamed into place. A missing file means no engine-kept entries.
  - A file that fails the path rule (below) or its schema, is over 1 MiB, or holds a `(name, instance)` twice is not used (an entry naming an agent the engine no longer has does not make it unusable: that agent is served nothing) and never overwritten. The engine then serves no engine-kept entry, logs the cause, and every agent's `status` shows `PLUGIN_UNAVAILABLE` naming the file and the way out: move it aside (`sudo mv <file> <file>.bad`), then restart the engine, which starts with no engine-kept entries. `PLUGIN_LIST` lists the config entries with `problem` set. Every other `PLUGIN_*` method that would read or write the file is refused `PLUGIN_REFUSED` `UNSAFE_PATH`, its `message` naming the file and the rule it fails.
- **Installed copies** are under `<stateDir>/plugins/<name>/<instance>/<manifest-sha256>/`. They are staged, checked and renamed into place as [Installed copies](plugins.md#signing-and-the-trust-store) says, from an upload (below) instead of a source directory.
  - Modes as a same-user install gives them: directories `0755`, the manifest, its `.sig` and other files `0644`, the manifest's `command` and every path `PLUGIN_OPEN` names in `executables` `0755`.
  - The [path rule](plugins.md#signing-and-the-trust-store) holds for them and for the entries file, with the engine's OS user as the required owner from `<stateDir>` down (root or that user above it, as for any path).
  - **Space.** The installed copies of all engine-kept entries and the open uploads together take at most 1 GiB (1,073,741,824 bytes). A `PLUGIN_UPLOAD_PART` that would pass it, or a `PLUGIN_OPEN` that would add a seventeenth entry, is refused `PLUGIN_REFUSED` `TOO_LARGE` before anything is written.
  - **Old copies.** When a change to an entry is written, the engine stops the plugin running from the old copy and removes that copy at once: the entry is withheld until the new approval is signed anyway. `PLUGIN_REMOVE` removes the entry's copies. A copy no entry names (left by a crash) is removed at the engine's next start.
- **The engine never writes** `engine.json`'s `plugins`, `<base>` (`/opt/basalt` or `/Library/Basalt`, root's: the config entries' copies and the trust store), or a service unit. `engine.json` belongs to the engine's user in service mode. The engine writes it only as before (to clear a finished setup), never for plugins.
- **One `(name, instance)`, one kind.**
  - A `(name, instance)` that `engine.json` holds, as the engine reads it from disk when it handles the request or as it held it at the engine's start (an entry removed with `sudo` since counts until the engine restarts, since the running engine still has it), cannot be added as an engine-kept entry (`PLUGIN_REFUSED` `NAME_TAKEN`).
  - A hand-edited config entry with a `(name, instance)` the engine keeps is the clash below.
  - If both still hold one (an `engine.json` edited by hand, or an add that raced the engine), the config's entry is served and the engine-kept one is not, with `PLUGIN_UNAVAILABLE` naming the clash.
- **Fields.** `agents` and `settings` are as in [Config](plugins.md#config): each agent is one of the engine's agents, and `config`, `timeoutMs` and `minConfidence` follow the same rules.
- **No `auth`.** `auth` is refused for an engine-kept entry: the engine would send the contents of the file it names to the plugin's host. In service mode the engine's own files, an agent's credential file among them, are files the engine's user owns with mode `0600`, so a request could name one. A remote plugin that needs a token is added with `sudo`.

**Running.**

- **Local.** Once an engine-kept local entry's approval matches ([Plugin approvals at engine start](plugins-approval.md#plugin-approvals-at-engine-start)), the engine runs it itself, as its own child, exactly as a same-user engine does ([Transports](plugins-runtime.md#transports)):
  - its own process group, with its installed copy as the working directory and no environment but `BASALT_PLUGIN_SOCKET`;
  - a socket directory new for each start, under the OS temporary directory (on Linux the engine unit's private `/tmp`), with the same checks; every local transport works, `jsonrpc-stdio` included, as in same-user mode;
  - crash records in `<stateDir>/plugin-runs/`, and restarts after a failure from the copy the entry names, verified again;
  - stderr discarded (shown on the terminal only with `--plugin-debug` in the foreground, which a service engine is not);
  - `shutdown` and a kill of its process group when it stops.

  **This replaces the rule that an engine in service mode never starts a local plugin itself, for approved engine-kept entries only** ([Isolation and trust](plugins-runtime.md#isolation-and-trust)). Config entries keep their own units, and the engine still never starts, signals or kills a config entry's process.
- **Remote.** An engine-kept remote entry is dialled, as any remote entry.
- **Never as root.** An engine running as root starts no local plugin, engine-kept ones included (`PLUGIN_UNAVAILABLE`). It also refuses to open one: `PLUGIN_OPEN` of a local plugin is refused `PLUGIN_REFUSED` `ENGINE_IS_ROOT` before anything is written. When an agent's OS user is in the engine's group, the engine starts no local plugin either, as [Service units](plugins-runtime.md#service-units) says.
- **On Linux** the plugin runs inside the engine's unit, under the same sandbox (`ProtectSystem=strict`, `PrivateTmp`, `NoNewPrivileges` and the rest; the `systemd` CI job shows that a program the engine's user writes into the state directory starts and is reached on a Unix socket under those settings). As a child of the engine it is in the engine's cgroup, so it shares the engine's `MemoryHigh` and `MemoryMax`: a plugin that uses too much memory throttles the engine, or gets it stopped. It stops when the engine stops.
- **On macOS** the engine's launch daemon has no sandbox: the plugin runs as the engine's user with the engine's umask.
- **When it starts.** The engine checks the approval at each start, as for every entry that requires approval, and while it runs as [Plugin changes while the engine runs](plugins-approval.md#plugin-changes-while-the-engine-runs) says, for its engine-kept entries only: it reads `<stateDir>/plugins.json` (and `engine.json`, for a clash) every second, and a `PLUGIN_OPEN`, `PLUGIN_DISABLE` or `PLUGIN_REMOVE` is applied to what runs before the method answers. So the engine starts the entry within seconds of the signature, stops it when it is turned off, and no step in service mode names an engine restart for an engine-kept entry. Config entries are read at start only, as before: the watch neither checks, records nor changes them.

**Isolation, the binding and the page.** An engine-kept local entry is bound and recorded with `isolation` `{"files": "NONE", "network": "NOT_ENFORCED"}`, on Linux and macOS: the plugin has the engine's files and network. A remote one has no `isolation`, as always. So the [page](plugins-approval.md#the-plugin-approval-page) is unchanged:

- An unknown publisher is level 3, with the warning that it runs with the same access as Basalt itself, and the tick.
- A known publisher is level 1, with the plain line "It runs on the computer Basalt runs on, with the same access as Basalt itself."
- The ledger records `files: NONE`, `network: NOT_ENFORCED` for it ([In the ledger](plugins-ledger.md#in-the-ledger)), next to config entries recorded `files: OS_USER`.

**The upload.** `basalt mcp` sends the plugin's files to the engine over a second connection to the agent's own socket ([`request_plugin`](mcp-tools.md#mcp-tools), The upload connection). The engine never reads the agent's directories.

1. `PLUGIN_UPLOAD_BEGIN` returns a new `uploadId`, its `expiresAt` (15 minutes later; parts do not extend it), `maxPartBytes` (65,536) and `maxUploadBytes` (268,435,456).
2. `PLUGIN_UPLOAD_PART` adds bytes to one file of the upload, and returns the bytes now held for that `path`.
   - `path` follows the manifest's path rules (relative, no segment starting with `.`, at most 255 characters). The manifest is `basalt-plugin.json` and its signature `basalt-plugin.json.sig`. The engine does not read the manifest before `PLUGIN_OPEN`, so whether the manifest lists a path is checked there (`BAD_MANIFEST`); parts may arrive in any order of paths.
   - `offset` must equal the bytes already held for that path: the parts of one path arrive in order.
   - `data` is 1 to 65,536 bytes, base64url without padding, decoded strictly as everywhere in this file. An empty file is sent as one part with no bytes (`""`) at offset 0; no other part may be empty.
   - Refused with `INVALID_ARGUMENT`, the upload kept: an `offset` other than the bytes held (a part sent twice included), `data` that does not decode, and a `path` that is a directory of another path held (`a` beside `a/b`). `NOT_FOUND`: an `uploadId` that is unknown, expired, used, dropped or another uid's.
3. **Limits** are the manifest's own: the manifest at most 1 MiB and its `.sig` at most 4 KiB. On top of that: at most 1,024 paths, and at most 256 MiB (268,435,456 bytes) in all, the cap on the whole transfer; and the engine's 1 GiB for copies and uploads together (above). A part over a limit is refused `PLUGIN_REFUSED` `TOO_LARGE`, and the upload is dropped.
4. **An upload belongs to the peer uid that began it.**
   - At most 4 uploads are open on the engine at a time, shared by every admitted uid (as the 1 GiB is), so one caller can hold the others off until its uploads expire; a fifth `PLUGIN_UPLOAD_BEGIN` is refused `PLUGIN_REFUSED` `TOO_MANY_UPLOADS`.
   - Uploads are kept in `<stateDir>/plugin-uploads/<uploadId>/` (mode `0700`) and removed when `PLUGIN_OPEN` uses them (whatever its result once it took the upload: a request refused `AGENT_NOT_ALLOWED` for its scope is refused before the upload is read, and leaves it until it expires), when they expire (checked at each `PLUGIN_UPLOAD_BEGIN` and `PLUGIN_UPLOAD_PART`), and at the engine's start. `PLUGIN_OPEN` checks the expiry when it takes the upload; from then the upload is its own until it answers.
5. The upload is checked only by `PLUGIN_OPEN`, as a staged copy. Until then it is bytes the engine does not read.

**The methods.** The schemas are in [`person.schema.json`](../api/plugin/approval/person.schema.json), with valid and invalid examples in `api/plugin/testdata/` (`*-person-*`, `*-engine-entries-*`). The engine applies the methods that change entries one at a time. None of the `PLUGIN_*` methods is refused by the guard check as a whole: each agent's database is checked where a step needs it (`PLUGIN_OPEN` step 3), and `PLUGIN_LIST`, `PLUGIN_DISABLE` and `PLUGIN_REMOVE` answer while a guard is outdated or a database is down. A method that reaches databases works on them in parallel, each within 15 seconds; the client waits up to 60 seconds for the response.

- **`PLUGIN_OPEN`** `{ "uploadId"?, "name", "instance", "agents", "settings"?, "executables"? }`. With `uploadId` it adds the uploaded copy as a new engine-kept entry, or changes an existing one to it (the manifest's `name` must be `name`). Without it, it opens a new approval for the entry's installed copy (`enable`): an entry that does not exist is `NOT_FOUND`, a config entry's `(name, instance)` `PLUGIN_REFUSED` `CONFIG_ENTRY`.
  - **`agents`** is the entry's full new list: 1 to 256 names, no repeats, always given. `add` sends `--agents`. `enable` sends the entry's current `agents`, or `--agents` when given.
  - **`settings`** `{ "config"?, "timeoutMs"?, "minConfidence"? }` replaces the entry's settings. Absent, it keeps them (none for a new entry). The commands send none today.
  - **`executables`**: paths of the upload to install with mode `0755` besides the manifest's `command`, each one the manifest lists. `add` sends every listed file that has an execute bit in the source directory, as a same-user install keeps it. Given without `uploadId` it is `INVALID_ARGUMENT`: an installed copy keeps its modes.
  - **Steps:** [The flow](plugins-approval.md#plugin-approval), with the engine in the command's place.
    1. Refusals before anything is written: `ENGINE_IS_ROOT`, `NAME_TAKEN` for a config entry's `(name, instance)`, `AGENT_NOT_ALLOWED` for the scope, `TOO_LARGE` for a seventeenth entry.
    2. Check the copy. Manifest rules: `BAD_MANIFEST`, also when the manifest's `name` is not `name`, the upload holds a file the manifest does not list or lacks one it lists, or `executables` names a path it does not list. File hashes, the path rule (`UNSAFE_PATH`), the signer state, and a `.sig` that names a built-in key and does not verify (`NOT_TRUSTED`). The trust store does not make a publisher known here, as in [Signer states](plugins-approval.md#signer-states).
    3. Check every listed agent: it is one of the engine's agents (`UNKNOWN_AGENT`), its database answers within 15 seconds (`DATABASE_UNREACHABLE`), and its guard is at [schema version 5](basalt-meta-schema-versions.md#schema-version-5-plugin-approvals) or later (`GUARD_OUTDATED`). **Ends owed first.** When the entry is disabled or does not exist, the engine writes `PLUGIN_DISABLED` for every agent, of the old list and the new, whose newest approval of `(name, instance)` is signed and not ended (an end a `PLUGIN_DISABLE` or `PLUGIN_REMOVE` could not write), with the detail that approval binds (the entry and its copy may be gone), and for every agent whose ledger records the entry as served, with the detail last recorded. When the entry is enabled, it writes the same for every agent the change adds or removes, so an agent added back never returns on an approval it had before, and an agent removed loses its approval. One it cannot write refuses the request, `DATABASE_UNREACHABLE`, before anything is written. So an entry turned off never comes back on its old approval, even when the new approval cannot be opened afterwards.
    4. Write the copy (removing the entry's old one, above; with the same manifest bytes the copy stays as it is), and the entry with `"approval": "REQUIRED"`: enabled, except for a narrowing, which keeps `enabled` as it was.
    5. Open one approval per database: with the credential of that database's first agent in `agents` order (`requestedBy`), naming every listed agent of that database.
  - **A narrowing** is a change to an **enabled** entry with the same manifest bytes and the same settings that only removes agents. It writes the entry and opens nothing: `narrowed` is `true` and `approvals` is empty. It first ends the approval of every agent it removes (step 3). A change to a disabled entry is never a narrowing: it opens an approval and enables the entry, so turning an entry on again always needs a new signature.
  - **Result.** `approvals` has one item per database, in the order of each database's first agent: `database` `{ host, name }`, `agents`, then either `approvalId`, `expiresAt`, `bindingText` and `settingsText` (the texts as `open_plugin_approval` returned them), or `refused` `{ reason, message }` with the reasons after the write of [The flow](plugins-approval.md#plugin-approval) step 3.
  - **The tool** builds from the result what [Plugin approval links](plugins-approval.md#plugin-approval-links) says: the short link through the engine's local pages, `personMessage` and `nextSteps`.
  - **A running entry** that a `PLUGIN_OPEN` changes is stopped when the change is written (step 4), and agents removed from it are no longer served from then on; the rest wait for the new approval.
- **`PLUGIN_LIST`** `{}`: every entry, config and engine-kept, in name and instance order, with `source`, `enabled`, `agents`, the installed copy's `version`, `signer` (and `signerKeyId` when `KNOWN`), `endpoint`, `isolation` (`LOCAL` only, as the entry runs on this engine), `health`, and `approval` as `basalt plugin list --json` gives it. `health` is what the running engine knows of the entry, config or engine-kept, and names no agent: `READY`, `UNAVAILABLE` or `NOT_STARTED`, as [`basalt plugin list`](plugins-approval.md#consent) shows it. A config entry is `required: false` with `NOT_REQUIRED` for each agent; an engine-kept entry is always `required: true`.
- **`PLUGIN_APPROVE`** `{ "approvalId", "assertion" }`, the decoded `basalt-plugin.1.` code: a relay. The engine asks each database, in parallel, through its agents in name order until one of them is the agent that opened the approval (the agent whose `agent_plugin_approvals` row for that id carries `binding_text`, which only the opener's does), and calls `submit_plugin_approval` with that agent's credential: Postgres verifies the signature.
  - Result: `{ "approvalId", "status": "APPROVED", "approvedAt" }`.
  - `NOT_FOUND` when no database answered with the approval and every one answered; `REFUSED` with `DATABASE_UNREACHABLE` in its `message` when none had it and one did not answer; `REFUSED` with Postgres's detail (`APPROVAL_INVALID`, `APPROVAL_EXPIRED`) as the page relay answers it.
- **`PLUGIN_DISABLE`** and **`PLUGIN_REMOVE`** `{ "name", "instance" }`, engine-kept entries only.
  - `PLUGIN_DISABLE` sets `enabled` to `false`. `PLUGIN_REMOVE` deletes the entry and its installed copies.
  - Both stop the plugin and **end every listed agent's signed approval** of the entry when the engine handles the request: the engine writes `PLUGIN_DISABLED` to the ledger of every listed agent whose ledger records the entry as served (with the detail last recorded) or whose newest approval of it is signed and not ended (with the detail that approval binds, so the end needs no copy), so the approval [ends](plugins-approval.md#how-long-an-approval-lasts) at once, served yet or not. A record that cannot be written then is logged, tried again at each later start while the entry is kept disabled, and written before any `PLUGIN_OPEN` turns the entry on again (step 3), so the entry stays off until a new approval is signed.
  - A config entry is refused `PLUGIN_REFUSED` `CONFIG_ENTRY`: it is edited in `engine.json` by hand. An unknown one is `NOT_FOUND`.
  - Disabling an entry that is already disabled returns the same result and writes nothing new.
- **Errors.** `INVALID_ARGUMENT`, `NOT_FOUND` and `INTERNAL`, plus `PLUGIN_REFUSED`: `{ "error": { "code": "PLUGIN_REFUSED", "reason", "message" } }`. Reasons:
  - from [Consent](plugins-approval.md#consent) and [The flow](plugins-approval.md#plugin-approval): `BAD_MANIFEST`, `NOT_TRUSTED`, `UNKNOWN_AGENT`, `UNSAFE_PATH`, `GUARD_OUTDATED`, `DATABASE_UNREACHABLE`;
  - new here: `NAME_TAKEN`, `CONFIG_ENTRY`, `TOO_LARGE`, `TOO_MANY_UPLOADS` and `ENGINE_IS_ROOT`.

  The command prints a refusal as the same-user [`PLUGIN_REFUSED`](plugins-ledger.md#problems-and-errors) error body with that reason. `reason` appears only with `PLUGIN_REFUSED`. `INTERNAL` keeps its generic `message`.
