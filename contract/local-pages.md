## Local pages

M4.1. The engine serves the approval and revert pages itself, so a held write reaches the person as a short link that works out of the box, and the page relays the signature without a pasted code. The signed data does not change: the page fetches the same request the long link carries, checks it the same way (binding, `rowsHash` or `sampleHash`), and the person signs the same binding; Postgres verifies the signature as before. The long-fragment links stay supported (hosted page, phone).

- **Listener.** `pagesAddr` in `engine.json`: a loopback `host:port`. Default: when the pages base URL is local (`http://localhost:<port>`, the default `http://localhost:8787`), `127.0.0.1:<port>`; for the portal, `off`. `"off"` disables it. A non-loopback address is refused when the config is loaded: this listener has no TLS or plaintext opt-in. If the port cannot be bound when the engine starts (another process holds it), the engine refuses to start, naming the address and how to find the process (`lsof -nP -iTCP:<port> -sTCP:LISTEN`); it never falls back to the long link silently. To run without the pages, set `pagesAddr` to `"off"`. The listener applies the `websec` Host check (loopback names only), Origin check and security headers.
- **Origin.** The page origin is the pages base URL (scheme, host, port), so the passkey's RP ID and origin are the ones it was registered with. Short links: `<base>/approvals/<approvalId>#s=<secret>` and `<base>/reverts/<revertId>#s=<secret>` (see [Link secrets](#link-secrets)).
- **Assets.** The files under `web/` are embedded in the binary (`go:embed`); to try an edit to a page, rebuild the binary and restart the engine.

**Display-only fields.** The engine's `GET` answers for the pages (and the request in the scope route's answer) may carry fields that are never signed and never in a long link; the Go parsers and the pages refuse them in a link, even empty or `null`. They change how the page shows the rows, never which rows or values:

- `columns` (approvals and reverts): each table the lines name, spelled as the lines spell it, to its column names in table order, read by the agent's engine from `pg_attribute` (by `attnum`) as the agent role sees the catalog. Rows arrive as `jsonb`, which reorders their keys; the page orders each table's columns by this list, shows any column the rows carry that it does not list after them in the rows' order, and never hides one. A long link has no engine, so its page keeps the rows' order. Optional: an engine that cannot read the catalog leaves it out.

- **Which agent.** The engine looks the id up with each configured agent's credential (the ledger views show a role only its own approvals and reverts) and acts with the one that finds it. When none does: `404`. The secret is checked before the lookup, so a missing or wrong secret is answered the same as an unknown id.
- **Errors.** JSON `{ "code", "message" }` with a code from [Error codes](error-codes.md#error-codes): `NOT_FOUND` 404; `APPROVAL_EXPIRED` or `REVERT_EXPIRED` 410; `APPROVAL_INVALID` or `REVERT_INVALID` 409 (already used, already signed, or refused by Postgres, with its detail); `INVALID_ARGUMENT` 400 (a bad id or body, or ids that differ); 415 for a body that is not `application/json`; 413 over 16 KiB; 403 for a missing or foreign `Origin`. Planned ([Next steps](next-steps.md#next-steps)): the body also carries `personMessage` and the `PERSON` steps of the code's entry, which the page shows; a link without its secret or replaced is `NOT_FOUND` reason `LINK`. Revert scope (RS-2): a link revoked by a reset is `NOT_FOUND` reason `LINK_RESET`; `POST …/scope` follows the [check order](revert.md#rescope-widen-and-reject): a descriptor that fails on its shape alone (the schema, `store`, over 20 runs or tables) is `400 INVALID_ARGUMENT`; then anything that is not provably the agent's own work, and anything at all after a widen, without a valid proof or token is `409 REVERT_INVALID` with one fixed message, whatever the reason (a run or table of another agent, or unknown, included); only after that is a run, table or agent outside the scope `400 INVALID_ARGUMENT`; a rescope over 100 seconds is `504 QUERY_TIMEOUT` reason `TIME_LIMIT`; `POST …/scope` on a signed, rejected or expired revert answers as `apply` does (409 or 410), and so does `POST …/reject`. `GET` of a widened revert whose lines the engine no longer holds (it restarted since the widen) is `409 REVERT_INVALID` whose body also carries `rescopeNonce`, and the page asks the person to widen again with it. Postgres wins over the engine's memory: when the engine holds a scope token for the link but the revert is no longer widened with the binding it holds (the agent role reset it in Postgres directly), the engine drops what it held, revokes the link as a reset does, and answers `404 NOT_FOUND` reason `LINK_RESET`. A widen whose `newSecret` is the link's current secret is `400 INVALID_ARGUMENT`. `POST …/reveal` (HR-1): every proof, key, nonce or ticket failure is `409 APPROVAL_INVALID` or `409 REVERT_INVALID` with `reason` `REVEAL_REFUSED` and one fixed message; hidden rows that changed since the hold or the prepare are `409` with `reason` `ROWS_CHANGED`; an expired item is `410`, a used, signed or rejected one `409` as on `apply`; a guard older than [version 30](basalt-meta-revert.md#version-30-reveal-hidden-approval-rows) (approvals) or [29](basalt-meta-revert.md#version-29-reveal-hidden-revert-rows) (reverts) is `503 UNAVAILABLE` reason `GUARD_OUTDATED`. The engine serializes the reads, rescopes and resets of one revert, so it never serves an older rescope than Postgres stored. The plugin routes answer as the approval routes do, with the plugin page's own `personMessage` and `PERSON` steps (never a held write's): `NOT_FOUND` 404 (also an approval only another agent opened, or that names the agent without its having opened it, and any id asked of an agent whose guard is older than [schema version 5](basalt-meta-schema-versions.md#schema-version-5-plugin-approvals), which cannot hold one), `APPROVAL_EXPIRED` 410, `APPROVAL_INVALID` 409 (cancelled, already signed, or refused by Postgres, with its detail), and the same 400, 403, 413 and 415.
- **CSRF.** A `POST` must carry an `Origin` equal to the page origin and `Content-Type: application/json`. The listener sends no CORS headers, so another site's page can neither read a preview nor make a JSON post. The relay only carries a signature: Postgres refuses anything the person's passkey did not sign.
- **Who can read a preview.** Only a holder of the short link (its secret), or of the long link, which carries the preview itself. The id alone is not enough: ids appear in tool results, logs and the CLI.
- **The page.** It shows the same review as the long link. After the passkey signs, it posts the response and shows "Approved. The agent will continue." (approval) or the revert result. If the relay fails, it shows the error and the code to paste into `basalt approve` or `basalt revert --apply`.

### Link secrets

Owner decisions, Decided Nov 12: short links carry a per-link secret.

- **The secret.** 16 random bytes (128 bits), base64url without padding (22 characters), in the fragment: `<base>/approvals/<approvalId>#s=<secret>`. The fragment is never sent in an HTTP request, so the secret stays out of server and proxy logs and `Referer`; the page reads it from `location.hash` and sends it to the same-origin API in the `basalt-link-secret` header. A custom header also makes any cross-origin request need a CORS preflight, which this listener never grants.
- **Storage.** The engine keeps only `sha256(secret)` per held item, with the item's expiry (an approval after 24 hours, a revert after its hour, a plugin approval at its `expiresAt`), per agent in `<stateDir>/<agent>.links.json`: mode `0600`, owned by the engine's OS user, written atomically on every change and pruned of expired items. Short links survive an engine restart. It compares in constant time. A file it cannot read is logged and replaced: those links stop working and are issued again as below.
- **One live link per item.** Issuing a link for an item revokes its earlier one. Links are issued by: `write` when it holds a write (`approvalUrl`); `revert_plan` while the plan is `PENDING` and not widened; `request_revert` when it prepares a revert, and in its wait form only with `reissueLink: true`; `list_pending` only when called with `reissueLink: true` (then every item it returns gets a new link and the old one stops working; the agent hands the person the new one); the CLI through `POST …/links`, for `basalt revert` (a freshly prepared revert has no link yet) and for `basalt approve --show`/`--open` whenever the engine serves the pages (`--reissue` is accepted and means the same), which revokes the link the agent handed over; the agent still applies the write by its approval id. Without `reissueLink`, `list_pending` touches no link: `approvalUrl` is the long link and `personMessage` points back to the link already given (on an engine that serves no pages, the link the budget chooses, which over the budget is the hash link with `requestFile`: [The request file and pasted blocks](showing-links.md#the-request-file-and-pasted-blocks)). A waiting `write` that times out issues none and returns the hold's own answer, with the link it issued.
- **Issuing for the CLI.** `POST /api/v1/approvals/{approvalId}/links` (and `/reverts/{revertId}/links`) with `{ "proof": "<hex>" }`, where `proof` = lowercase hex of `sha256(utf8("basalt-link.1\n" + binding text))`. Only a holder of the binding text can issue: a role that can read the item in `basalt_meta` (the CLI with the agent credential) or a holder of the long link, both of whom can already see the whole preview. The proof is not derivable from a signed response (whose challenge is `sha256(binding text)`). No `Origin` or a page-origin `Origin`, `Content-Type: application/json`; a wrong proof is answered as an unknown id.
- **Refusals.** A missing or wrong secret, or a link revoked by a newer one, gets `404 NOT_FOUND` with the same body as an unknown id, on both the request and the relay. The page then says the link is incomplete or replaced and how to get a new one (`list_pending`, `basalt approve --open`).
- **A widened revert** (RS-2 and RS-5, [Rescope, widen and reject](revert.md#rescope-widen-and-reject)). A proven widen rotates the revert's link to the page's `newSecret` and revokes the old one, as reissuing does: the link the agent handed over then reads `404 NOT_FOUND` (the same body as an unknown id) on `GET`, every relay route and a new Vault session. The engine stores the rotated link like any other (`sha256`, `linkToken`, `psk`, expiry). No route issues a link to a widened revert for the agent: `reissueLink: true` (`request_revert` and `list_pending`; planned for `revert_plan`) resets the revert to the agent's proposal through `reset_revert` and issues a link for that, and `POST /api/v1/reverts/{revertId}/links` on a widened revert is refused as an unknown id (its proof hashes a binding text the agent role can no longer read). The engine keeps the `sha256` of a link revoked by a reset until the revert expires and answers it `404 NOT_FOUND` reason `LINK_RESET` instead of `LINK`, so the page can say what happened (it keeps the hash in `<agent>.links.json` with the live links). A rejected revert's link is revoked: the page holding it then reads `404 NOT_FOUND`, and in a Vault session the engine sends the reject's answer first, then the session ends with `LINK_REFUSED`. Over the Vault a reset revokes the person's relay link like any reissue: its open sessions end with `LINK_REFUSED`.
- **Not affected.** The long-fragment links (`#2.<request>`, or `#1.` before it; the hosted form) carry the preview themselves and need no secret. The passkey pages, `/passkeys/register#1.<request>`, `/passkeys/check#1.<request>` and `/passkeys/forget#1.<request>`, are static: their whole request travels in the fragment, so the link is already the bearer of everything the page shows, and the engine has no data or relay endpoint for them to gate. They carry no `#s=` secret. A passkey page that ever reads from or posts to the engine gets a short link with a secret and gates its routes as above. The one exception is not the engine: the registration page of the pages `basalt init` serves itself posts the passkey back to init, with the `handBack` secret its request carries ([CLI](cli.md#cli), `basalt init`).
- **Over the Vault (M3.5).** On the portal the same short link opens an end-to-end encrypted session through the Vault: the engine also keeps the link's `linkToken` and `psk`, derived from the secret, and the secret travels only inside the session ([Vault channel](vault-channel.md#vault-channel)).

### Handing a held action to the person

Every result that names a held action gives the agent what to show the person, so the person needs nothing else: `APPROVAL_REQUIRED` (`write`) and `list_pending` items carry `headline`, `approvalUrl`, `approveCommand` and `personMessage` (above). `revert_plan` for a plan not yet signed (`status` `PENDING`) and not widened carries `revertUrl` (the short link when the pages are served, else the long link, or the hash link when that is over the link budget) and `personMessage`; so does `request_revert` when it prepares a revert, or reissues its link. Wherever `approvalUrl` or `revertUrl` is a hash link, `requestFile` is beside it ([The request file and pasted blocks](showing-links.md#the-request-file-and-pasted-blocks)). An agent that lost a link calls `list_pending` again (for a revert, `request_revert` with `revertId` and `reissueLink: true`).
