## Update notice

People and agents are told when a newer release is out. On by default.

- **The check.** At most once every 24 hours, `basalt` asks `https://api.github.com/repos/BasaltDBHq/BasaltDB/releases` (public, no credentials, 2 seconds, at most 1 MiB). The request carries no data beyond the HTTP request itself (the IP address and a `User-Agent` of `basalt/<version>`): nothing about the person, the machine, the database or an agent. The answer (tag, pre-release flag and security flag of each release, draft releases left out) is cached in `update-check.json` (`0600`) in the `basalt` folder of the user's cache directory. A failed request keeps the old answer and is tried again after an hour. The refresh runs beside the command; a command waits for it at most one second and never fails because of it.
- **Which release counts.** The newest release with a higher version than the running build. A pre-release (a tag with a pre-release suffix such as `-alpha.2`, or a release GitHub flags as pre-release) is offered only when the running build is a pre-release; a tag whose suffix is not made of `[0-9A-Za-z-]` identifiers is not a version and is ignored. A build with no release number (`0.0.0-dev`) gets no notice and makes no request, in the CLI and in the engine. A release is a **security release** when a line of its release notes starts with `Security:` (any case); the notice is a security notice when any newer release that the person may be offered (by the rules above) is one.
- **Off switch.** The environment variable `BASALT_UPDATE_CHECK` set to `off`, `0`, `false` or `no`, or `"updateCheck": "OFF"` in `engine.json` (`ON` or absent leaves it on; the CLI reads the config it would read by default). Off means no request and no notice. In service mode `engine.json` is `0600` and the CLI cannot read it, so the engine reports its setting in the `PAGES` answer (`updateCheck`, `ON` or `OFF`) and the CLI follows it; a config that exists but cannot be read or loaded, with no engine answer within a second, means no request. No config file at all means the check is on.
- **Terminal.** Every `basalt` command except `engine`, `mcp` and help prints one line on stderr after its own output when a notice applies: `basalt <current> is out of date; <latest> is available. <how>` (a security notice reads `is out of date (SECURITY UPDATE)`). `<how>` is `Run: brew upgrade basaltdbhq/tap/basaltdb` when the binary, after symlinks are resolved, sits in a Homebrew Cellar, Caskroom or prefix (`/opt/homebrew`, `/home/linuxbrew/.linuxbrew`), else `Get it at <release page>`. (The setup page's `UPDATE` updates the guard in Postgres, not the binary.) The line is yellow, red for a security notice, only when stderr is a terminal and `NO_COLOR` is not set. The `status` tool carries `update` instead, in this shape (`{ "current", "latest", "security", "url", "message" }`, absent when there is no notice or the check is off): the notice from this binary's own cache, else the engine's `update`; it reads the cache only. The exit code is never changed.
- **Agents.** The engine runs the same check (at start, then when the cache is a day old; cache `update-check.json` in `stateDir`) unless it is off or the build has no release number. When a newer release exists: `status` and `describe` (form `OVERVIEW`) carry `update`: `{ "current", "latest", "security", "url", "message" }`, with `message` starting `WARNING:` (or `SECURITY UPDATE:` for a security notice) and saying what to tell the person and how they upgrade (the brew command when the engine's binary sits in a Homebrew prefix; both ways when it is the engine service's own copy (`/usr/local/libexec/basalt`, `/usr/libexec/basalt`), which does not say how `basalt` was installed: `They upgrade the way they installed it: brew upgrade basaltdbhq/tap/basaltdb if it came from Homebrew, otherwise the new release at <url>`; else the release page; then the agent runs `basalt init` so the engine runs the new binary: with the engine service, init's one administrator dialog copies the new `basalt` over the service's copy and restarts it ([The administrator dialog](setup-page.md#the-administrator-dialog), The restart); the message names no root command); and the first successful tool result of each MCP connection carries the same `message` as one more text item after the result (once per connection, never on an error result). The `initialize` instructions carry: *"When a result carries a WARNING: or SECURITY UPDATE: notice or an update field, tell the person that a newer BasaltDB release is out and give them the upgrade command it names; never upgrade BasaltDB yourself unless the person says yes."* `basalt mcp` while the engine is down adds nothing.
