## Approvals

M2. This section fixes the bytes. JSON Schemas for every payload are in [`api/mcp/approval/`](../api/mcp/approval/).

- An approval or revert (and a [plugin approval](plugins-approval.md#plugin-approval)) counts only with a valid P-256 passkey signature (WebAuthn ES256), verified inside Postgres. Pages and relays (the engine, the CLI, the agent's chat) carry signed data and are not trusted.
- **Pages.** Static files under `web/`. Hosted (not live yet) on the portal `https://portal.basaltvault.app` with passkey RP ID `basaltvault.app` (fixed for good: registered passkeys depend on it) and origin `https://portal.basaltvault.app`. The origins a page may run on are a closed list ([Page origins](page-links.md#page-origins)). Until hosting exists the default everywhere is the engine's local pages, `http://localhost:8787` with RP ID `localhost` (owner decisions, Decided Nov 12). Both have the same paths ([Page links](page-links.md#page-links)). The clientDataJSON origin check stays strict: a passkey signs only on the origin it was registered on. The pages have no backend, load no third-party code, and send nothing over the network: input comes in the URL fragment, output is a code the person copies. From M4.1 the engine also serves them on loopback with a same-origin relay ([Local pages](local-pages.md#local-pages)); that listener follows the listener rules in [AGENTS.md](../AGENTS.md) and the `websec` hardening; custom HTTP headers use the lowercase **`basalt-`** prefix.
- **Expiry.** 24 hours after the hold. No answer means blocked.
- **Engine.** On `BS002` the engine checks the write is repeatable (`NOT_REPEATABLE` otherwise), previews it, holds it, and answers `APPROVAL_REQUIRED` with the link. The engine config (`engine.json`) may set `pagesUrl` (the pages base URL, default `http://localhost:8787`; the older key `approvalPage` is still read, its origin only) and `pagesAddr` (see [Local pages](local-pages.md#local-pages)). A config with a `notify` key, which configured the parked Telegram notifier, is refused, as every unknown key is, with a message that names it.
- **Waiting write (M4.1).** `write` takes `waitForApproval` (integer seconds, 0 to 110). When the write is held, or the call names an `approvalId` whose approval is not signed yet, the engine keeps the call open up to that long, checking about once a second. As soon as the approval is signed (by the page's relay, `basalt approve` or the `approval` argument) it applies the held write exactly as a repeat with `approvalId` would, and returns `APPLIED` in the same call. On timeout it returns `APPROVAL_REQUIRED` with the same `approval` body, and nothing is applied; its message tells the agent not to wait again but to end its turn, telling the person the write waits for their approval (link, expiry) and that it applies the write when they say they approved (a later `write` with `approvalId` applies at once). One wait per turn: a review can take longer than any wait, and MCP cannot start a client turn when the person approves. Default: **0 on a new write**, so the agent gets the link at once and can hand it over; **90 when `approvalId` is given**. The intended loop: the agent shows `personMessage`, then, in the same turn, repeats the write once with `approvalId` (also after a `list_pending` that handed over a link), and the call returns `APPLIED` once the person signs, with no "I approved it" from the person. Bound: Claude Code moves an MCP call still running after 2 minutes to a background task (`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS`, default 120000), and its hard tool timeout (`MCP_TOOL_TIMEOUT`) is about 28 hours, so 110 seconds keeps a wait in the foreground. A client with a 60 second request timeout should pass a smaller value.

### What an approval binds (decision M2-1)

Bound: the statement, its parameters, and for every affected row, cascades included: table, operation, cascade flag, primary key, full old row, and the new values of the columns the statement assigns (`UPDATE … SET` targets; the `INSERT` column list, or every column when it is omitted). Not bound: defaults, identity and sequence values, and values set by the app's triggers. A write that would be held and contains a value that changes between transactions is refused with `STATEMENT_REFUSED` reason `NOT_REPEATABLE`. Postgres reads the strings `now`, `today`, `tomorrow` and `yesterday` as the time the write runs, so they count as such values when they are a literal or a parameter (see [Error codes](error-codes.md#error-codes)).

**Preview line.** One per affected row: the `jsonb` text Postgres returns for

```json
{"op": "UPDATE", "key": {"id": 7}, "old": {"id": 7, "status": "open"}, "set": {"status": "merged"}, "table": "public.leads", "cascaded": false}
```

`key` and `old` are `null` for an `INSERT`; `set` is `null` for a `DELETE` and for cascaded rows. A row of a table the agent role cannot `SELECT` is redacted to `{"op", "table", "rowHash", "cascaded", "redacted": true}` with `rowHash` = lowercase hex of `sha256(jsonb_build_array(key, old, set)::text)`. Lines are ordered by their text `COLLATE "C"` (byte order). Clients hash and parse the text as given and never re-serialise it. Planned: on the approval page the engine serves, the person can reveal a redacted line's values with their passkey ([Rows hidden from the agent](#rows-hidden-from-the-agent)).

**Binding text.** The `jsonb` text Postgres returns for

```json
{"kind": "APPROVE", "rows": 15, "agent": "bot", "runId": "…", "intent": "…", "params": ["merged"], "taskId": "…", "database": "app", "rowsHash": "<hex>", "expiresAt": "2026-11-12T06:02:11.123456Z", "statement": "…", "approvalId": "…", "assignedColumns": ["status"]}
```

`rowsHash` = lowercase hex of `sha256(utf8(lines joined by "\n"))`. `expiresAt` is RFC 3339 UTC with microseconds. Keys appear in `jsonb` order (shorter first, then bytewise); clients parse the text and never rebuild it. `kind` is `APPROVE` (M3 adds `REVERT`; a plugin approval's binding has `kind` `PLUGIN` and keys of its own, [What a plugin approval binds](plugins-approval.md#what-a-plugin-approval-binds)). **Challenge** = `sha256(utf8(binding text))`, in `clientDataJSON.challenge` as base64url without padding.

### Codes

All base64url is RFC 4648 §5 without padding. Byte fields inside JSON are base64url strings.

| Approval request, format 1 (read only) | URL `<base>/approvals/<approvalId>#1.<b64url(deflate-raw(json))>` | `{ "approvalId", "binding", "lines", "credentialIds" }`: `binding` the binding text, `lines` the preview lines in order, `credentialIds` the registered passkeys (may be empty). The pages still read it; the engine no longer writes it. The engine's local pages serve this JSON at `GET /api/v1/approvals/{approvalId}`, with (planned) `revealNonce` ([Rows hidden from the agent](#rows-hidden-from-the-agent)), which a long link never carries |
| Approval response | Text `basalt-approval.1.<b64url(json)>` | `{ "approvalId", "credentialId", "authenticatorData", "clientDataJson", "signature" }` from `navigator.credentials.get` (`signature` DER) |
| Passkey registration request | URL `<base>/passkeys/register#1.<b64url(json)>` | `{ "challenge", "userId", "userName", "displayName" }`: 32 and 16 random bytes; names are labels for the passkey picker. `handBack` (optional): the hand-back secret, only in links of the pages `basalt init` serves itself ([CLI](cli.md#cli)); the page then posts the passkey to init and shows the pairing code instead of the long code |
| Passkey registration response | Text `basalt-passkey.1.<b64url(json)>` | `{ "credentialId", "clientDataJson", "authenticatorData", "publicKey", "publicKeyAlgorithm" }`: `publicKey` the SubjectPublicKeyInfo DER from `getPublicKey()`, algorithm `-7` (ES256) only; `prfSupported` optional boolean: the page asked for the WebAuthn `prf` extension and the authenticator reported it enabled (absent means not, or unknown). Registration never fails because `prf` is missing, and no `prf` output is ever read, logged or sent. Nothing acts on the flag until the vault channel's Phase 1b |
| Pairing code | Text `XXXX-XXXX`, shown on the registration page after a hand-back, typed into `basalt init` ([CLI](cli.md#cli)) | 8 characters of Crockford base32 (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`, 40 bits): the first 5 bytes of `sha256("basalt-pairing.1\n" ‖ challenge ‖ credentialId ‖ x ‖ y)`, where `challenge` is the registration request's and `x`, `y` the 32-byte P-256 coordinates of the registered key, shown as two groups of four. Read as typed: surrounding space trimmed, any case, `-` and spaces dropped, `O` read as `0` and `I`, `L` as `1`; anything that is then not 8 Crockford characters is not a pairing code. Shared vectors, which Go and the page both run: [`pairing-code.json`](../api/mcp/passkey/pairing-code.json) |

### Format 2: the compact request

Owner decisions VC-7 and VC-29; the layout details are VC-31. The engine writes approval and revert links in format 2; the pages read format 2 and format 1. Schema: [`compact-request.schema.json`](../api/mcp/links/compact-request.schema.json). Shared vectors, which the contract test, the Go codec and the pages all run: [`compact-request.json`](../api/mcp/links/compact-request.json).

`#2.<b64url(deflate-raw(json))>`, where the JSON is `[shapes, texts]` or `[shapes, texts, credentialIds]`:

- **`texts`**: the binding text first, then the lines in order: the preview lines of an approval, or the revert lines (a large plan's sample) of a revert. At least 2 texts, at most 51 for an approval and 1001 for a revert. There is no separate id: it is the binding's `approvalId` or `revertId`. A plugin approval's link carries exactly 2, the binding text and then the settings text, and its page checks `settingsSha256` where the others check `rowsHash` ([The plugin approval page](plugins-approval.md#the-plugin-approval-page)).
- **`credentialIds`** (optional, M4.1): the database's active passkey credential ids (`basalt_meta.agent_passkeys`, at most 100), base64url without padding, each 1 to 1023 bytes and listed once. The engine and `basalt approve`/`basalt revert` write them whenever the database has any. They are not signed: the page passes them, as it passes an engine answer's `credentialIds`, as `allowCredentials` on every approval, revert, widen and reveal prompt, so the browser offers only this database's passkeys (every local database's pages share RP ID `localhost`, so without them the picker offers the person's passkeys for every database). A list naming a passkey the database does not hold only makes the prompt find none; Postgres checks the signature either way. When the prompt offered some and ends without a signature, the page says the device may hold none of this database's passkeys.
- **A text** is a JSON string, the text as it is, or `[shape, value, ...]`: the index of a shape in `shapes` and one value per slot of that shape.
- **`shapes`**: the key layouts the texts share, each listed once and used by at least one text, never more than there are texts. A shape is 1 to 64 entries in text order. An entry is `"key"`, which takes one slot, or `["key", ["column", ...]]` for a key whose value is an object (`key`, `old`, `set`, `now`), which takes one slot per column (at most 1600), in text order.
- **A value** is a string, `true`, `false`, `null`, an integer of magnitude at most 2^53 − 1 that is not `-0`, an array of values (nested at most 32 deep), or `{"raw": "<text>"}`: the value's `jsonb` text as it is, for anything else (other numbers, nested objects). Numbers are read as JavaScript's `JSON.parse` reads them, so `1.0` is the integer 1.

**Rebuild.** A text `[shape, value, ...]` is `{`, then its entries joined by `, `, then `}`. An entry is `"key": value`, or for an object entry `"key": {`, then `"column": value` for each column joined by `, `, then `}`. An array is `[`, its values joined by `, `, then `]`; an integer is written in decimal; `{"raw": text}` is `text`. Keys, columns and strings are quoted as Postgres's `escape_json` quotes them: `\"`, `\\`, `\b`, `\f`, `\n`, `\r`, `\t`, any other character below U+0020 as `\u00xx` (lowercase hex), everything else as it is. That is `jsonb`'s own text layout, so the texts rebuild to the binding text and the lines byte for byte. The engine checks each text rebuilds exactly and sends any text that does not as a string.

**Limits.** The page first repairs the fragment ([The pages repair what they can](showing-links.md#the-pages-repair-what-they-can): line breaks, spaces and the other characters a client adds are dropped), then decodes it. It refuses the repaired fragment unless: its payload is at most 1 MiB of base64url characters and nothing else (a decoder given an unrepaired fragment, as the Go codec is, refuses a line break rather than skipping it); it inflates to at most 1 MiB of UTF-8, with nothing after the end of the deflate stream (the page finds that end itself, without relying on the browser's decompressor); that is one JSON value the schema allows, with nothing after it; and the rebuilt texts total at most 1 MiB. Then it checks the rebuilt request exactly as a format 1 request: the binding's id against the id in the page's path, which the approval and revert pages require (a page whose path has no id refuses to run: a format 2 request has no id of its own), the kind, the number of lines, and `rowsHash` (or `sampleHash`). A wrong rebuild fails closed: the lines no longer hash to the binding's `rowsHash`, and a binding text that differs from the one Postgres built has a different challenge, which Postgres refuses.

A page first repairs the fragment and, when it still does not decode, offers to read the link from the pasted message ([Showing links](showing-links.md#showing-links), planned M3.5). A page whose fragment does not decode as base64url, deflate-raw or JSON says the link looks cut short and to open it with `basalt approve --open` (or `basalt revert ... --open`), which builds the full link itself. The approval page checks `sha256(lines joined by "\n")` equals the binding's `rowsHash` and refuses to ask for a signature otherwise. Registration asks for `userVerification: "required"`, `residentKey: "required"`, `attestation: "none"`, ES256 only. `basalt init` verifies the registration in Go: type `webauthn.create`, challenge, origin, `rpIdHash`, the UP, UV and AT flags, the attested credential id equals `credentialId`, and a P-256 key.

### Checks in Postgres

`submit_approval` accepts an assertion only if: `type` is `webauthn.get`; the challenge is the approval's binding; `origin` and `rpIdHash` match the passkey's stored RP ID and origin; UP and UV are set; the signature counter increased (0 is accepted while the stored count is 0); the ES256 signature over `authenticatorData ‖ sha256(clientDataJSON)` is valid; the approval is not expired and not yet approved. Applying with `basalt.approval_id` commits only if the approval is approved, unused, unexpired, of this agent and run, and the statement, parameters, row count and `rowsHash` recomputed at commit match. Failures are `BS005`.

### Rows hidden from the agent

Owner decisions HR-1 to HR-4. Applies to approvals and to reverts ([Revert](revert.md#revert) links here). A redacted line (`"redacted": true`: a table the agent role cannot `SELECT`, cascaded rows above all, and revert lines redacted for row-level security) keeps its values from the agent. The person can see them before signing, on the page the engine serves (loopback or a [Vault channel](vault-channel.md#vault-channel) session), after a fresh passkey proof Postgres verifies. Nothing new is stored, no view or tool result an agent role reads changes, and the engine holds the values for one request.

- **When.** The engine's `GET /api/v1/approvals/{approvalId}` and `GET /api/v1/reverts/{revertId}` carry `revealNonce`, the item's single-use nonce (16 bytes, base64url), read with `reveal_nonce` ([Reveal objects](basalt-meta-revert.md#reveal-objects)). The page shows a "Show values with passkey" button above the hidden rows (after a reveal, "Hide values" hides them again on the page only, without a prompt) when it has `revealNonce` and at least one redacted line; it never prompts on its own (HR-4). A long link carries no nonce, so its page shows the values hidden and says to open the short link to see them. The CLI cannot reveal.
- **Reveal key.** For each reveal the page makes `revealSecret`, 16 random bytes (`crypto.getRandomValues`), and sends it only to the engine, with the proof (over loopback, or inside the end-to-end encrypted session), never shown. The engine derives `revealKey = HKDF-SHA-256(ikm = the 16 decoded bytes of revealSecret, salt = empty, info = "basalt-reveal-key.1", length = 32)` and passes Postgres only that key, never the secret; Postgres refuses unless `sha256(revealKey)` is the hash the proof signed. So a reveal proof alone, pasted or leaked, is worthless to the agent role, as a widen proof is without its `newSecret`. The engine never logs or stores the secret or the key.
- **Challenge.** `sha256(utf8("basalt-reveal.1\n" + kind + "\n" + id + "\n" + revealNonce + "\n" + hex(sha256(revealKey)) + "\n" + rowsHash))`, in `clientDataJSON.challenge` as base64url without padding. `kind` is `APPROVE` or `REVERT`, `id` the `approvalId` or `revertId` in canonical lowercase form, `revealNonce` as the request carries it, hex lowercase, `rowsHash` the binding's (a large plan's too, never its `sampleHash`). The prefix keeps a reveal proof from verifying as an approval or revert signature (their challenges hash a JSON binding) or a widen proof (`basalt-rescope.1`), and `rowsHash` makes it worthless after a rescope. Postgres checks it with `_verify_assertion`, as `submit_approval` does. The page never shows a reveal proof as a code to paste.
- **Request.** `POST /api/v1/approvals/{approvalId}/reveal` or `POST /api/v1/reverts/{revertId}/reveal` ([Local pages](local-pages.md#local-pages)), body [`reveal-request.schema.json`](../api/mcp/approval/reveal-request.schema.json): `{ "proof": { "credentialId", "authenticatorData", "clientDataJson", "signature" }, "revealSecret" }`, the proof an assertion as in an approval response without `approvalId`.
- **Revert.** One call, `reveal_revert_rows(revertId, proof, revealKey)`: checks the proof and key, replaces the nonce, appends `ROWS_REVEALED`, rebuilds each redacted line the request carries (every line, or a large plan's sample) from the ledger and the live row, and returns the answer, or that the rows changed. Both outcomes commit, so a proof that passed is used up either way.
- **Approval.** The values exist only while a preview transaction is open, and a `PREVIEW` transaction cannot commit, so two transactions: `open_reveal(approvalId, proof, revealKey)` checks the proof and key, replaces the nonce, appends `ROWS_REVEALED` and returns a fresh 128-bit ticket good for 2 minutes (Postgres keeps only its `sha256`); then the engine re-runs the held statement with its parameters in a `PREVIEW` transaction, as at the hold, records it with `finish_change` as an apply does, calls `reveal_approval_rows(approvalId, ticket)` there and rolls back. The agent role has no ticket: it exists only in the engine's memory and as a bind parameter. The re-run fires the app's triggers again and locks the rows briefly, as the hold's preview did (M3-7).
- **Answer.** [`reveal-response.schema.json`](../api/mcp/approval/reveal-response.schema.json): `{ "rows": [{ "line", "row", "secretColumns"? }] }`, one entry per redacted line, in line order. `line` is the 0-based index of the line in the request's `lines`. `row` is the exact text of `jsonb_build_array(key, old, set)` (approval) or `jsonb_build_array(key, now, set)` (revert), the text that line's `rowHash` hashes. For a row without `secretColumns` the page checks `sha256(utf8(row))` equals the line's `rowHash` before it shows any value; a row that fails is an error, never values. So for those rows neither the engine nor the Vault can show the person values other than the ones bound into what they sign. The engine answers with `Cache-Control: no-store`, keeps nothing after the response, writes nothing to `stateDir` and logs no value; the ticket and the reveal key never reach the MCP channel or the engine's log. A Postgres server that logs bound parameters (`log_statement = 'all'`, or `log_min_duration_statement` with parameters) records the ticket and the reveal key in the server log; only the database admin can turn that on, and either is worthless after its request (the ticket after 2 minutes, the key without a fresh proof).
- **`SECRET` columns** ([PII classification](pii-classification.md#pii-classification), HR-3). Never returned: Postgres sets every `SECRET` column to `null` wherever it appears in `row` and names it in `secretColumns`. Such a row cannot be checked on the page: `rowHash` hashes the whole row text, so no per-column hash lets the page rebuild it, and an engine or Vault could add `secretColumns` to any row and change its other values. The page therefore accepts the row only when every value of the named columns is `null`, shows those columns as "secret · not shown", and says under the table "Row <key> has a secret column, so this page can't check it against what you sign.", never that it is checked. `IDENTIFIER` and `FREE_TEXT` values are shown as they are: the page is the person's, and only the wire to the model is tokenized.
- **Refusals.** Every proof, key, nonce or ticket failure (no proof, a proof over another item, nonce, key or `rowsHash`, an approval or revert signature, a widen proof, a replay, an expired or wrong ticket, `reveal_approval_rows` outside `PREVIEW` or for another statement or parameters) is `APPROVAL_INVALID` or `REVERT_INVALID` with reason `REVEAL_REFUSED` (the Postgres detail) and one fixed message, and changes nothing. Hidden rows that changed since the hold or the prepare are reason `ROWS_CHANGED` and return nothing: an approval then can no longer apply (it would fail with `APPROVAL_INVALID` at commit), so the page tells the person to ask the agent to try the write again, and for a revert to prepare it again.
- **Single use.** A proof that passes consumes the nonce and Postgres sets a new one, whatever the outcome (synced passkeys report a signature counter of 0, so the counter cannot stop a replay). A refused proof changes nothing.
- **Ledger.** `ROWS_REVEALED` (detail `kind`, `id`, `credentialId`, `rows`, and `rowsChanged: true` on a revert whose rows changed: hashes and counts, no value), appended when the proof passes. It records the person's request: for an approval at `open_reveal`, before the re-run.
- **Limits** (as for a widen). Over the Vault on `RELAY`, whoever holds the link secret and gets the Vault to route the session to their own engine can read what the page reads (VC-42). In same-user mode an agent running as the person's OS user can read the person's screen. What the reveal guarantees is that the agent's database role learns nothing new. Out of scope: lines of a large plan beyond its sample, approval lines of rows RLS filters on a table the agent can `SELECT` (they are not redacted today), and the CLI.
