## Vault channel

**Target.** The direct transport is removed ([Removed](cli.md#removed)): the relay (`RELAY`) is the only transport.

Planned (M3.5, Vault channel Phase 1a; owner decisions VC-1 to VC-42). An engine with no inbound port reaches the person's browser through the hosted Vault (`relay.basaltvault.app`, VC-20). The engine dials out, the portal page dials in, and the two run an end-to-end encrypted session keyed by the short link's secret, inside which the page speaks the same pages API the engine serves on loopback. The Vault pairs sockets and forwards opaque bytes.

**The Vault is untrusted.** Neither the engine nor the page depends on it being honest. A Vault that drops, delays, duplicates, reorders, replays, truncates, reflects or alters any message can make a session fail, never make either side accept something. It never holds a key that opens a session (VC-4). The Vault service is closed source (VC-13, VC-18): this section is the whole protocol it must speak, and its internals (hosting, storage, its own rate numbers) are not part of the contract. Schemas, the close-code registry and the vector format: [`api/mcp/vault/`](../api/mcp/vault/).

**Scope (VC-1, VC-17).** Link sessions only, for the approval and revert pages, and the plugin approval page of an agent-operated engine ([Plugin approval through the portal](plugins-approval.md#plugin-approval-through-the-portal)). Pairing, box keys in use, envelopes, device codes, the pending list, notifications and accounts are after M4 (their contract is VC2-1's). The direct transport is [removed](cli.md#removed): `RELAY` is the only prologue transport, and an engine or page refuses any other. Revocation of an engine in `basalt_meta` is in [Engine revocation](#engine-revocation).

**The exception (VC-1).** "No hosted service before M4" has one narrow exception: this rendezvous. It stores no plaintext, no credentials and no ledger, has no accounts, and when it is down a persona 2 page cannot be signed: the relay is the only carrier of a persona 2 signature ([Signing](approvals.md#signing)); the person signs once it is back. Planned: the [connect service](connect.md#connect) is a second one, used only at setup: when the person opens the connect link, and while the engine of a connect-only code polls it for the database's address, for up to the code's life plus the 30-minute hold (40 minutes after the code was made, [The reach check](connect.md#the-reach-check)). It writes nothing anywhere and has no accounts; unlike this rendezvous, it holds the admin connection string in memory for one setup, and the address of a connect-only setup in memory for up to 30 minutes, until the engine collects it (planned: also from `CheckSetup`, so the engine can test that it reaches it before the person approves) ([What the connect service sees](connect.md#what-the-connect-service-sees)). Every setup code needs it: the connect page is the only place a code runs.

### Primitives and encodings

- **Algorithms (VC-5).** P-256 (ECDH and ECDSA), SHA-256, HMAC-SHA-256, HKDF-SHA-256 (RFC 5869) and AES-256-GCM: all in WebCrypto and in Go's standard library (`crypto/ecdh`, `crypto/ecdsa`, `crypto/hkdf`, `crypto/hmac`, `crypto/cipher`). No third-party crypto in the engine or the pages, and no primitive of our own: the handshake is a Noise pattern and every other step is a signature, an HKDF or an AEAD call.
- **Public keys.** In a handshake message: the 65-byte uncompressed SEC1 point (`0x04 ‖ X ‖ Y`). As an identity: the 91-byte DER SubjectPublicKeyInfo (`id-ecPublicKey`, `prime256v1`, uncompressed point), base64url without padding (122 characters). Any other encoding (a compressed point, explicit curve parameters, trailing bytes) and any point not on the curve is refused.
- **ECDH output** is the 32-byte x-coordinate (WebCrypto `deriveBits` with 256 bits; Go `ecdh.PrivateKey.ECDH`).
- **Signatures** are ECDSA P-256 with SHA-256, encoded as 64 bytes `r ‖ s` (IEEE P1363, WebCrypto's form; Go converts from ASN.1), base64url without padding (86 characters). A verifier refuses any other length. A high-S signature (`s` above half the group order) is **accepted**: verifiers use plain ECDSA verification (WebCrypto `verify`, Go `ecdsa.Verify`), which accepts both `s` and `n − s`, and nothing uses a signature's bytes as an identifier, so the second form gains nothing.
- **Bytes** in JSON are base64url without padding unless a field says otherwise; in test vectors, lowercase hex.
- **Signing contexts.** The engine's signing key signs only these, each input starting with its context line, so no signature made for one can be used as another (VC-37). A new context is a contract change.

| Context line | Signed by | Over |
|---|---|---|
| `basalt-vault-engine.1\n` | Engine signing key | The Vault's challenge and the engine's Vault host ([engine socket](#the-engines-socket-to-the-vault)) |
| `basalt-vault-session-sig.1\n` | Engine signing key | The handshake hash `h` after `e, ee` ([Handshake](#handshake)) |
| `basalt-receipt.1\n` | Engine signing key | A receipt's payload bytes ([Receipts](#receipts)) |
| `basalt-engine-box-key.1\n` | Engine signing key | The engine id and the box key's public key |
| `basalt-engine-rotate.1\n` | The previous signing key | Reserved for a later key rotation's statement over the new keys (`rotatedFrom` in the [key file](../api/mcp/vault/channel-key-file.schema.json)); nothing signs it today |
| `basalt-connect-collect.1\n` | Engine signing key | The audience `connect.basaltvault.app`, the `setupId`, the setup fingerprint and the time of a request for a connect-only setup's address ([The address hand-off](connect.md#the-address-hand-off)) |
| `basalt-connect-reach.1\n` | Engine signing key | The same four lines as `basalt-connect-collect.1`, then the address the engine probed (host, port, database, Supabase ref) and its result and reason: a report of whether it can reach a connect-only setup's database ([The reach check](connect.md#the-reach-check)) |
| `basalt-connect-removed.1\n` | Engine signing key | The same four lines as `basalt-connect-collect.1`, then the result and reason of the engine removing itself from the bot's machine after a removal on the connect page ([The removal hand-off](connect.md#the-removal-hand-off)) |

### Engine keys

- **Two keys (VC-5).** A **signing key** (ECDSA P-256) and a **box key** (ECDH P-256, used from Phase 1b; made now so the key file keeps its shape). Neither does the other's job. The box key's public key is signed by the signing key (`basalt-engine-box-key.1\n` + `engineId` + `\n` + the box key's SPKI as its base64url text, as `channel.json` holds it).
- **Engine id** = base64url of the first 16 bytes of `sha256(signing key SPKI DER)`: 22 characters. It is self-certifying (anyone holding the key can check it; nobody can claim another engine's id) and a key fingerprint, not a UUIDv7. **Shown to people** as its first 16 characters in four groups of four, separated by spaces (`AbCd EfGh IjKl MnOp`), next to the agent name: in `status` and on every portal page with a session, so the person can compare.
- **When made (VC-36).** On the engine's first start, whatever `vault` says: receipts need the signing key on every path, the local pages and the CLI included. A missing file is created. An engine that waits for its config makes it earlier, at the first install `check` on the setup page, so the install records it ([The local setup page](setup-page.md#the-local-setup-page)).
- **Storage.** `<stateDir>/channel.json` ([`channel-key-file.schema.json`](../api/mcp/vault/channel-key-file.schema.json)): mode `0600`, owned by the engine's OS user (as `<agent>.links.json` and the credential file), written atomically (a temporary file in the same directory, `fsync`, rename). Private keys are PKCS#8 DER. No key material goes anywhere else: not to logs, `engine.json`, `status`, the ledger or the Vault. No OS keychain (as M51-1).
- **Refused, never replaced (VC-36).** A key file that is not a regular file with one link (a symlink, or a second hard link to it, is refused), grants group or other access, is owned by another user, cannot be read, fails its schema, whose `engineId` is not its signing key's or whose `boxKeySig` does not verify is left as it is. The engine then serves MCP and the local pages as usual, does not connect to the Vault, hands over long links instead of portal short links (and refuses a plugin approval, `NO_PORTAL_LINK`), signs no receipt (the result says why), and `status` reports `vault.state` `KEY_ERROR`. The fix is to correct the file's owner and mode. (The links file is replaced instead, because a new link costs nothing; new keys change the engine id the person may have compared.)
- **Who can read it.** Whoever can read the agent's credential file: in same-user mode (`GUARD_ONLY`) and with `operatedBy` `AGENT`, the agent. A leaked key lets its holder pose as the engine to the Vault and sign receipts in its name. It reads no session without that session's link secret and approves nothing: only the person's passkey signs, and Postgres verifies it.
- **Recorded by the setup.** The setup records the signing key in the person's database ([Engine records](basalt-meta-installs.md#engine-records)). No command or page revokes it ([Engine revocation](#engine-revocation)).

### Engine revocation

No command or page revokes an engine: `basalt engine revoke` is removed, and the portal has no revoke action ([Removed](cli.md#removed)). A person who wants an engine cut off removes BasaltDB from the database ([Remove Basalt](setup.md#setup-jobs)), which drops every `basalt_*` role, so the engine can no longer log in. `revoke_engine` stays in the guard ([Engine records](basalt-meta-installs.md#engine-records)), so a row can still be revoked by hand in SQL; the engine only reports it.

- **Per database.** `engines` has no agent column, so a revoked row applies to every agent of that database.
- **What the engine does.** For every agent of a database whose row for its key is revoked, the engine reports `engineRecord.state` `REVOKED` and the problem `ENGINE_REVOKED` in `status`. It does not act on it: it still hands over relay short links, and the links it handed over keep working until they expire.
- **No new key.** A revoked key is never recorded again. With rotate-key removed, a revoked engine is set up again from the start.

### Link secrets in a session

The short link is unchanged ([Link secrets](local-pages.md#link-secrets)): `https://portal.basaltvault.app/approvals/<approvalId>#s=<secret>` and `…/reverts/<revertId>#s=<secret>`, and `…/plugins/<approvalId>#s=<secret>`. The page tells the transport by its own origin: same-origin `fetch` on the engine's local pages, the Vault on the portal (VC-25: the portal never calls `localhost`). With `s` the 16 bytes the 22-character secret decodes to (VC-9):

- `linkToken` = HKDF-SHA-256(ikm `s`, salt empty, info `basalt-vault-link.1`, 16 bytes), base64url: 22 characters. The Vault's routing key for the link.
- `psk` = HKDF-SHA-256(ikm `s`, salt empty, info `basalt-vault-psk.1`, 32 bytes): the session's pre-shared key.

Neither reveals `s` and neither gives the other. The engine keeps `linkToken` and `psk` per item in `<agent>.links.json` next to `sha256(secret)`, with the same expiry, the same one-live-link rule, and constant-time comparison. The page derives both from `location.hash` and never sends `s` or `psk` to the Vault: the socket path carries `linkToken` only, and the secret itself travels only inside the encrypted session, as `basalt-link-secret`.

### Handshake

`Noise_NNpsk0_P256_AESGCM_SHA256`, from the Noise Protocol Framework (revision 34), with an engine signature in the second payload (VC-32; design 6.1). The page is the initiator, the engine the responder.

- **Functions.** `DH`: P-256. Noise's `DHLEN` is the length of both a public key and a DH output; here they differ: an `e` token writes, reads and hashes the 65-byte uncompressed point, and `DH` returns the 32-byte x-coordinate (both meet Noise's minimum of 32). `HASH`: SHA-256. `HKDF`: Noise's (HMAC-SHA-256; the same as RFC 5869 with empty info, and implemented with HMAC so a zero-length input key works in WebCrypto). Cipher: AES-256-GCM with Noise's nonce, 4 zero bytes followed by the 64-bit big-endian counter. The protocol name is 31 bytes, so `h` starts as the name padded with zero bytes to 32, and `ck` = `h`. Because the pattern has a `psk` token (Noise section 9.2), every `e` token is followed by `MixKey(e.public_key)` as well as `MixHash(e.public_key)`, on both sides and for both ephemeral keys. A Noise message, which here is everything after a message's 2-byte header (and, in message 1, the 16-byte `linkToken`), is at most 65 535 bytes.
- **Prologue** = UTF-8 of `basalt-vault-prologue.1\n` + transport (`RELAY`, the only one) + `\n` + `linkToken` as its 22-character base64url text (not the raw bytes), with nothing after it. Each side builds it from what it knows itself (the page from its link; the engine from the token it looked up), so a session moved to another link fails, and so does a message 1 made for any other transport.
- **Message 1, page to engine** (`psk, e`): exactly 99 bytes, `0x01` (version) ‖ `0x01` (type `HELLO`) ‖ `linkToken` (16 raw bytes) ‖ `e` (65 bytes) ‖ `EncryptAndHash` of the empty payload (the 16-byte tag). The payload is always zero bytes: `EncryptAndHash` of it is the tag alone, and the fixed length refuses anything else. `linkToken` travels here as its 16 raw bytes. With `psk0`, that tag is under a key derived from `psk`: the page proves it holds the link before the engine does any public-key work.
- **The engine on message 1**, in order: the handshake rate for the token (every token counts, held or not, so the answer says nothing of whether the engine holds it; over it, `RATE_LIMITED`); the version byte (`UNSUPPORTED_VERSION`), then the type and the exact length (`PROTOCOL`); look `linkToken` up (it must equal `SESSION_OPEN`'s; a token that is not live still runs the tag check under an all-zero `psk` and is refused after it); the other [limits](#limits); check the tag (the `e` token hashes and mixes the 65 bytes as they are, so this needs no point arithmetic); only then check `e` is a valid point. A token it does not hold, a link expired or revoked, a different `SESSION_OPEN` token, a failing tag and an invalid point all close with `LINK_REFUSED`, alike, as a wrong secret answers today, so a probe cannot tell a live token from a dead one by the answer.
- **Message 2, engine to page** (`e, ee`): `0x01` ‖ `0x02` (type `WELCOME`) ‖ `e` (65 bytes) ‖ `EncryptAndHash` of the payload, at most 1 024 bytes in all. The payload is UTF-8 JSON, [`handshake-payload.schema.json`](../api/mcp/vault/handshake-payload.schema.json): `{ "engineKey": <SPKI, base64url>, "sig": <base64url> }`, where `sig` signs `basalt-vault-session-sig.1\n` followed by the 32 raw bytes of `h` after the `e` and `ee` tokens (before the payload is hashed in).
- **The page on message 2.** Check the version byte (`UNSUPPORTED_VERSION`), the type (`PROTOCOL`) and the size (`TOO_LARGE`), then that `e` is a valid point, decrypt, parse the closed schema, verify `sig` over the same `h` with `engineKey`, and compute the engine id from `engineKey`. Any failure closes with `HANDSHAKE_FAILED` and shows nothing from the engine.
- **Engine identity is not pinned (VC-42).** The link carries no engine id and the page keeps nothing between sessions, so the page accepts whatever key a holder of the link's `psk` signs with. The engine's identity is trust on first use, checked only by the person comparing the fingerprint the page shows with the one `status` or the agent's earlier messages gave. Only someone who holds the link secret (the engine itself, or whoever saw the link) and gets the Vault to route the token to their own engine (a malicious Vault, or the registration race in [The engine's socket to the Vault](#the-engines-socket-to-the-vault)) can present another key. What that gains them: a fake fingerprint on the page, fake receipts in the page, and denial of service (taking the person's signature and not relaying it). Not a forged approval: the page builds the binding from the rows it shows and checks `rowsHash`, and Postgres accepts a signature only over a real pending item's binding, so the most such an engine can obtain is the person's signature over the real item they were shown, which approves only that item. A plugin approval's page shows only what the binding text it signs says (and checks the settings text against `settingsSha256`), and `submit_plugin_approval` accepts a signature only over the binding text Postgres stored for that approval, so the same holds. Reading the preview is no gain: the link already lets its holder read it.
- **Split.** `Split()` gives `k1` (page to engine) and `k2` (engine to page), each with its own counter from 0. Both sides erase the ephemeral private keys and `ck`. The final `h` may be logged as the session id; keys never are.

What this gives against the Vault and anyone on the path:

- **Confidentiality and integrity.** Every key depends on `psk` (from the link secret, which the Vault never sees) and on the ephemeral-ephemeral DH. The Vault cannot read or change a session or pretend to be either side.
- **Authentication by the link.** Only holders of `s` (the engine that issued the link, and whoever holds the link) can make message 1's tag or a message 2 the page accepts. The signature binds the session to the engine's identity key, for the fingerprint on the page and receipts; nothing but the person's comparison checks that key (above).
- **Transcript binding.** `h` covers the prologue (version, transport, `linkToken`), both ephemeral keys and both payloads; the signature covers `h`; `Split` derives from the whole chain.
- **Forward secrecy.** A later leak of the link secret, the links file or the engine's key does not open a recorded session.
- **Replay.** A replayed message 1 meets a fresh engine ephemeral key and leads nowhere: the replayer lacks the page's ephemeral private key, so it can neither read message 2 nor send a frame. A replayed message 2 fails against the page's fresh key. Within a session, implicit counters refuse replays ([Frames](#frames)); across sessions, Postgres refuses a used approval or revert ([Replay and expiry](#replay-and-expiry)).

### Frames

After the handshake, every binary WebSocket message either way is one frame: `0x01` (version) ‖ `0x03` (type `FRAME`) ‖ AES-256-GCM ciphertext, made with Noise's `EncryptWithAd` under the direction's key and counter, with the two header bytes as associated data (VC-33). The nonce is the receiver's own count, never sent, so a frame dropped, repeated, reordered, reflected to its sender or taken from another session does not decrypt: the receiver closes with `FRAME_INVALID` and drops the session. There is no rekey; the limits end a session long before a counter could wrap. A text message, or a binary message with another header, closes with `PROTOCOL` (an unknown version with `UNSUPPORTED_VERSION`). A receiver checks a frame in this order: its size ([limits](#limits)), the version byte, the type, then decrypts and unpads.

**Padding (VC-34; design 6.2).** The plaintext is `len` (4 bytes, big-endian) ‖ content (`len` bytes) ‖ zero bytes up to `max(1024, the next power of two ≥ 4 + len)` bytes, at most 32 768 (content at most 32 764 bytes per frame, so every Noise message stays under Noise's 65 535-byte limit). A receiver refuses (`FRAME_INVALID`) a plaintext of any other size for its `len`, or with a non-zero padding byte. Sizes on the wire are then 1 024, 2 048, … 32 768 bytes plus 18: one frame leaks a bucket, not a row count. What a whole session still leaks is in [What the Vault sees](#what-the-vault-sees).

**Content** is UTF-8 JSON, one of [`frame-message.schema.json`](../api/mcp/vault/frame-message.schema.json):

- `REQUEST`, page to engine: `{ "type", "id", "method", "path", "headers", "body", "more" }`.
- `RESPONSE`, engine to page: `{ "type", "id", "status", "headers", "body", "more" }`.
- `CONTINUE`, either way: `{ "type", "id", "body", "more" }`, the next piece of a body.

`body` is text (the pages API speaks JSON). A body too large for one frame continues in `CONTINUE` frames, appended in order up to the one with `more: false`. A message is acted on only once that frame arrives, so a truncated message is never used: the page times out and shows nothing. `id` is 1 for a session's first request and one more for each next one; a response and its continuations carry the request's `id`. One request is in flight at a time: a `REQUEST` before the previous response ended closes with `PROTOCOL`.

**Requests.**

- **Routes.** Only these are dispatched; any other method or path is answered `404 NOT_FOUND` with the same body as an unknown id:
  - `GET /api/v1/approvals/{approvalId}` and `POST /api/v1/approvals/{approvalId}/approve`;
  - `GET /api/v1/reverts/{revertId}` and `POST /api/v1/reverts/{revertId}/apply`;
  - `POST /api/v1/reverts/{revertId}/scope` and `POST /api/v1/reverts/{revertId}/reject` (revert scope, RS-2, [Local pages](local-pages.md#local-pages); a reject revokes the revert's link, so its session ends with `LINK_REFUSED` once the answer went out);
  - HR-1, [Rows hidden from the agent](approvals.md#rows-hidden-from-the-agent): `POST /api/v1/approvals/{approvalId}/reveal` and `POST /api/v1/reverts/{revertId}/reveal`;
  - [Plugin approval through the portal](plugins-approval.md#plugin-approval-through-the-portal): `GET /api/v1/plugins/{approvalId}` and `POST /api/v1/plugins/{approvalId}/approve`, for a plugin approval's link only;
  - reserved, each when its own contract lands: after M4 (VC-27) `GET /api/v1/setups/{setupId}` and `POST /api/v1/setups/{setupId}/done`.

  Never the `…/links` issuing routes, `/healthz`, the pages or their scripts.
- **One item per session.** The path's id must be the item of the session's link, and `basalt-link-secret` must be that link's secret (its `sha256` and its `linkToken` both match). Otherwise `404 NOT_FOUND`. Revert scope: when a widen in the session rotates the revert's link, the session stays open under its keys and the revert keeps its id, so one item per session holds; its later requests must carry the new secret (`newSecret`, whose `sha256` the engine now holds for the item), and the old one is answered `404 NOT_FOUND`. The engine moves the session to the new `linkToken`, ends every other session of the old one with `LINK_REFUSED`, and registers the new one, so a session opened with the new secret works and one opened with the old secret is refused by the engine at message 1 (`LINK_REFUSED`). It does not send `UNREGISTER_LINK` for the old token, which would close the rotating session's page socket; the Vault drops the old token at its `expiresAt`.
- **Headers**, lowercase. A request carries `basalt-link-secret` and `origin` (`https://portal.basaltvault.app`), and on `POST` `content-type: application/json`. A response carries `content-type`. Any other header in a request is answered `400 INVALID_ARGUMENT`.
- **Dispatch.** The engine hands the request to the same handlers as on loopback, with the same checks, statuses and JSON bodies ([Local pages](local-pages.md#local-pages)): `NOT_FOUND` 404, `APPROVAL_EXPIRED` or `REVERT_EXPIRED` 410, `APPROVAL_INVALID` or `REVERT_INVALID` 409, `INVALID_ARGUMENT` 400, 413 over 16 KiB, 415, 403 for a wrong `origin`, and `QUERY_TIMEOUT` reason `TIME_LIMIT` 504 for a rescope over 100 seconds. The `approve` and `apply` responses also carry `receipt`, or `noReceipt` ([Receipts](#receipts)). The plugin `approve` response carries neither, as on loopback: there is no receipt kind for a plugin approval.

### Receipts

A statement signed by the engine of what a relayed signature did (VC-22, mitigation 5; built in VC1-17; VC-38). Token: `basalt-receipt.1.<payload>.<sig>`.

- `payload`: base64url of UTF-8 JSON, [`receipt.schema.json`](../api/mcp/vault/receipt.schema.json): `format` (1), `kind` (`APPROVAL` or `REVERT`), `itemId`, `status` (`APPROVED`; `APPLIED` or `APPLYING`), `headline`, `rowsHash` (the signed binding's, from the store's record, so the receipt names exactly the rows the passkey signed), `agent`, `engineId`, `at`, and `changeId` when there is one.
- `sig`: over `basalt-receipt.1\n` followed by the payload's decoded bytes. Signing exact bytes means no one needs canonical JSON.
- **Checking one needs an expected engine key from outside the receipt.** The engine the person already knows: the engine id or fingerprint the `status` tool reports, or an earlier message of the same agent. The verifier checks the signature against that key, then parses the payload, then checks that `engineId` is that key's id and that the payload passes the closed schema; a receipt signed by any other key is refused. A receipt checked only against a key that came with it (the session's own `engineKey`, or a key the Vault or the agent hands over with it) proves only that whoever holds that key signed it, not which engine that is.
- **In the page, a receipt proves nothing beyond the session's own key.** The page can verify it only against the session's `engineKey`, which is not pinned ([Handshake](#handshake)), and the page's code is what a compromised portal would change. So the page shows it with the fingerprint and asks the person to compare; the check that counts is the one in the chat, against the engine the person knows (VC1-17).
- `headline` is built from the store's record of the item, never from what the page sent, so a page that made the person sign another item than the one shown is caught when the receipt names the real one.
- **Where (VC1-17).** In the relay responses, on loopback and in a session: `POST …/approve` answers `{ "approvalId", "status": "APPROVED", "receipt" }` and `POST …/apply` the applied revert's result plus `receipt` ([Local pages](local-pages.md#local-pages)). In the tool results that report a signed item the page relayed: `write` when it applies a held write (`approvalId`), and `request_revert` with `revertId` when it answers `APPLIED` or `APPLYING`. Each tool result with a receipt also carries the receipt line first in its `personMessage`, which the agent shows as it is. A receipt is made for each answer, so a later wait on the same item returns a new receipt naming the same item.
- **Built from Postgres, after the signature.** The engine signs a receipt only once Postgres accepted the signature, and builds the payload from its own read of the item after that, with the credential of the agent that holds it: `itemId`, `headline` (an approval's from its preview lines, as `APPROVAL_REQUIRED`'s `approval.headline`; a revert's from its binding and totals, as `list_pending`'s), `rowsHash` (from the binding text Postgres holds), `agent` (the agent, `agent:<name>`, [Agent names](stores.md#agent-names)), `status` and `changeId` (a revert's own change record, once set; an approval receipt has none). An approval's receipt says `APPROVED`, also once the write is applied; a revert's says `APPLIED` or `APPLYING` as Postgres shows it. `at` is when the engine made the receipt (UTC, whole seconds). Nothing the page, a code or the agent sent goes into a receipt except through Postgres, and only the engine's signing key signs one ([Engine keys](#engine-keys)); the agent cannot make one.
- **The receipt line.** One sentence built from the same payload, at most 300 characters: `Approved: <headline> (approval <itemId>), receipt from engine <fingerprint>.` for an approval, `Signed: <headline> (revert <itemId>), receipt from engine <fingerprint>.` for a revert. `<fingerprint>` is the engine id's fingerprint as `status` shows it (its first 16 characters in four groups of four, [Engine keys](#engine-keys)), for the person to compare character by character. The headline's final full stop is dropped first; then, when the line would pass 300 characters, only the headline is shortened, ending in `...` (the id and fingerprint are never cut). The rest of the `personMessage` follows it and the whole stays within the [Links in `personMessage`](showing-links.md#links-in-personmessage) rules.
- **No receipt.** The signature is applied whether or not a receipt can be made; the answer then carries `noReceipt` with the reason instead of `receipt` (never both), and the receipt line says why. `KEY_ERROR`: the engine key file is refused ([Engine keys](#engine-keys)); the line is `No receipt: the engine's key file is refused (Basalt's status reports KEY_ERROR), so nothing confirms what was signed.` `WIDENED` (provisional, an open owner question): a revert whose scope was widened on the signing page; the agent role cannot read its binding (RS-5), so the engine cannot name its rows from Postgres. The line gives the totals the agent may see and asks the person to speak up: `No receipt: the revert's scope was changed on the signing page (<rows> rows restored). If you did not change it, tell the agent at once.` (`<rows> rows to restore in batches` while `APPLYING`). Both forms of a relay response (`approve`, `apply`) carry `noReceipt` the same way.

### The engine's socket to the Vault

`wss://relay.basaltvault.app/v1/engines/<engineId>`, compiled into the binary (as the page origins are, CO-8). `vaultUrl` in `engine.json` overrides it for development and tests only, and only with a `ws://` URL on a loopback address (`127.0.0.1`, `[::1]` or `localhost`); anything else is refused when the config is loaded. The engine connects only when `vault` is `ON` and `pagesUrl` is the portal: a passkey with RP ID `localhost` cannot sign on the portal.

1. **Open**, with the header `basalt-engine-key: <signing key SPKI, base64url>`. The Vault refuses (`AUTH_FAILED`) a key that is not a valid P-256 SPKI or does not hash to the path's `engineId`.
2. **Challenge.** The Vault sends `CHALLENGE` with 32 random bytes: fresh per socket, single use, valid for `CHALLENGE_TTL` ([Limits](#limits)).
3. **Auth.** The engine answers `AUTH` with `version` 1 and `sig` over `basalt-vault-engine.1\n` + challenge (as sent, base64url) + `\n` + host, where host is the engine's own Vault host (`relay.basaltvault.app`, or the override's `host:port`), never one the Vault names. A bad or late answer: `AUTH_FAILED`.
4. **Ready.** The Vault sends `READY`. One live socket per engine id: a newer authenticated socket replaces the older, which is closed with `REPLACED`. After every `READY` the engine registers every live link again (registering is idempotent for the same engine), so a Vault that lost its state recovers.

Control messages are text messages, JSON per [`control-message.schema.json`](../api/mcp/vault/control-message.schema.json), at most `MAX_CONTROL` ([Limits](#limits)). Session bytes are binary `ROUTE` messages: `0x01` ‖ `0x10` (type `ROUTE`) ‖ `sid` (16 bytes) ‖ the page's message exactly as received, or the engine's message for the page.

| Message | Direction | Fields | Meaning |
|---|---|---|---|
| `REGISTER_LINK` | engine to Vault | `ref`, `linkToken`, `expiresAt` | Route page sockets for this token to me until `expiresAt` (at most `MAX_EXPIRY_AHEAD` ahead, [Limits](#limits)) |
| `UNREGISTER_LINK` | engine to Vault | `ref`, `linkToken` | Stop routing it, and close its page sockets with `LINK_UNKNOWN`. Only the engine the token is bound to can: another engine gets `LINK_CONFLICT` and the binding stays. A token that is not registered (or expired) answers `OK` |
| `OK` | Vault to engine | `ref` | Request `ref` succeeded |
| `ERROR` | Vault to engine | `ref` (when it answers one), `code` | `LINK_CONFLICT` (another engine registered the token), `LINK_LIMIT` (too many live links), `INVALID_EXPIRY`, `UNKNOWN_SESSION`, `RATE_LIMITED`, `PROTOCOL` |
| `SESSION_OPEN` | Vault to engine | `sid`, `linkToken` | A page connected for the token; its message 1 follows as a `ROUTE` |
| `SESSION_CLOSE` | either way | `sid`, `code` | The session ended (1000, or a [close code](#close-codes)); the Vault closes the page's socket with the same code |

`ref` is a positive integer the engine picks, unique among its requests waiting for an answer; `sid` is 16 random bytes the Vault picks per page socket (base64url in JSON). **No control message is trusted:** a forged `SESSION_OPEN` costs one refused handshake; a forged `OK` gives a link the page cannot reach (the person asks for the link again, which falls back if the Vault keeps failing); a forged `SESSION_CLOSE` or `ERROR` ends a session or a registration. None can open a session, read one or make the engine act on a request.

- **Reconnecting (VC-2).** Exponential backoff from 1 to 60 seconds with full jitter, reset after `READY`. A WebSocket ping every 30 seconds; no pong for 90 seconds closes and redials.
- **Registering a link (VC-15, design 6.5).** Before handing over a portal short link, the engine sends `REGISTER_LINK` and waits up to 5 seconds for `OK`. With no socket, an `ERROR` or no answer, it hands over the long link under the [link budget](showing-links.md#the-link-budget) rules instead, and the short link is not issued. A plugin approval has no long link: `request_plugin` is refused `PLUGIN_REFUSED` `NO_PORTAL_LINK` instead ([Plugin approval through the portal](plugins-approval.md#plugin-approval-through-the-portal)). `status` shows the socket's state.
- **A token belongs to one engine (VC-42).** The Vault binds each registered token to the engine id that registered it on an authenticated socket, and refuses (`LINK_CONFLICT`) a registration of a live token by any other engine id until the token's `expiresAt` or its `UNREGISTER_LINK`. It must keep that binding durably for the token's whole lifetime, across its own restarts and failovers. **Known limit:** if the Vault loses the binding anyway, an engine that also holds the link secret (someone who saw the link) could register the token first while the real engine reconnects. The impact is that of an unpinned `RELAY` identity ([Handshake](#handshake)): a fake fingerprint, fake receipts in the page, or denial of service, never a forged approval. Mitigations: the engine registers every live link at once after each `READY`; on `LINK_CONFLICT` for a link it holds, it revokes that link and logs it, so the item's next link (`list_pending` with `reissueLink: true`) has a new secret whose token nobody else knows; and the person compares the fingerprint.
- **Unregistering.** Reissuing a link unregisters the old token first, without waiting for its answer: an `ERROR` `LINK_CONFLICT` there (a rival engine holds the old token) does not stop the reissue, which registers the new token as usual, so a rival that took the old token cannot block it; a link that expires or is revoked is unregistered then, and its open sessions are closed with `LINK_REFUSED`. The Vault also drops a token at its `expiresAt` by itself.

### The page's socket

`wss://relay.basaltvault.app/v1/links/<linkToken>`, opened by a portal page (the Vault refuses another `Origin` with `PROTOCOL`; a check against other sites' pages, not a security boundary). The Vault closes with `LINK_UNKNOWN` when no engine registered the token or it expired, and with `ENGINE_OFFLINE` when its engine has no socket. Otherwise it sends `SESSION_OPEN` to the engine and forwards every binary message both ways unchanged and in order, as `ROUTE` messages on the engine's side. A text message from the page closes with `PROTOCOL`. When one side ends, the Vault closes the other with the same code. When the engine's socket ends (it dropped, or a newer one `REPLACED` it), the Vault closes that socket's page sockets with `ENGINE_OFFLINE`: sessions do not move to the engine's next socket. `SESSION_CLOSE` carries 1000 or a registry code only: a page that leaves with another code (a browser's 1001) or without a close frame is reported as 1000, and an engine's `SESSION_CLOSE` with any code but 1000 or one whose "Sent by" names the engine (so never `AUTH_FAILED`, `REPLACED`, `LINK_UNKNOWN`, `ENGINE_OFFLINE` or `HANDSHAKE_FAILED`) is malformed: the Vault closes the engine's socket with `PROTOCOL`.

The page sends nothing but handshake message 1 and frames; it keeps no state between sessions (no storage in Phase 1a) and never holds a key past its session.

### Close codes

WebSocket close codes, with the name as the close reason. Registry: [`close-codes.json`](../api/mcp/vault/close-codes.json), checked against this table by the contract test. A code that comes from the Vault only decides what the page shows; nothing else trusts it (VC-39). What the page shows: link gone (the link expired, was replaced or is incomplete, and how to get a new one, as the loopback `NOT_FOUND` reason `LINK`), engine offline (ask the agent to check `status`, or use the long link), broken (nothing was accepted; open the link again), or try later.

| Code | Name | Sent by | When | The page shows |
|---|---|---|---|---|
| 4000 | `PROTOCOL` | page, engine, Vault | A message out of place or malformed (text for binary, unknown type, content that fails its schema, a second request in flight, a foreign `Origin`) | broken |
| 4001 | `UNSUPPORTED_VERSION` | page, engine, Vault | A version byte or `AUTH` version other than 1 | broken |
| 4002 | `AUTH_FAILED` | Vault | Engine socket: a bad `basalt-engine-key`, or a bad or late `AUTH` | (engine only) |
| 4003 | `REPLACED` | Vault | Engine socket: a newer authenticated socket for the same id | (engine only) |
| 4004 | `LINK_UNKNOWN` | Vault | No engine registered the token, it expired, or it was unregistered | link gone |
| 4005 | `ENGINE_OFFLINE` | Vault | The token's engine has no socket | engine offline |
| 4006 | `LINK_REFUSED` | engine | Message 1 for a link the engine does not hold, expired, revoked, with another token than `SESSION_OPEN`'s, a failing tag, or an invalid ephemeral key, all alike; also open sessions of a link revoked or expired | link gone |
| 4007 | `HANDSHAKE_FAILED` | page | An invalid engine ephemeral key; message 2 that does not decrypt, fails its schema or its signature | broken |
| 4008 | `FRAME_INVALID` | page, engine | A frame that does not decrypt with the next counter, or with non-canonical padding | broken |
| 4009 | `TOO_LARGE` | page, engine, Vault | A message over its [limit](#limits), or a response body over 16 MiB | broken |
| 4010 | `RATE_LIMITED` | engine, Vault | Too many handshakes for a link, requests in a session, or connections at the Vault | try later |
| 4011 | `SESSION_LIMIT` | engine, Vault | Too many open sessions for the link or the engine | try later |
| 4012 | `TIMEOUT` | page, engine, Vault | The handshake took over 10 seconds, the session was idle 5 minutes, or it reached 30 minutes or its link's expiry | try later |
| 4013 | `ENGINE_REVOKED` | engine | Not sent: the engine does not act on a revocation ([Engine revocation](#engine-revocation)). Kept so a page that gets it shows the engine offline | engine offline |
| 4014 | `ENGINE_SHUTDOWN` | engine | The engine is stopping | engine offline |

A page that ends a session normally closes with 1000. A refusal inside a session that leaves it usable (`404`, `409`, `410`, `413`) is an HTTP status in a `RESPONSE`, not a close.

### Limits

Enforced by the engine and the page (VC-35). The Vault must carry messages up to these sizes, and may apply lower rates of its own (private numbers), never lower sizes. Rate checks come before any public-key operation. The limits the Vault applies too are named here and valued in [`limits.json`](../api/mcp/vault/limits.json) ([`limits.schema.json`](../api/mcp/vault/limits.schema.json)), which the engine's tests check its constants against.

| Limit | Value | Over it |
|---|---|---|
| Handshake message 1 | exactly 99 bytes | `PROTOCOL` |
| Handshake message 2 | at most 1 024 bytes | `TOO_LARGE` |
| Frame | at most `MAX_FRAME` (32 768 bytes of padded plaintext, 2 of header, 16 of tag) | `TOO_LARGE` |
| `ROUTE` message on the engine's socket | at most `MAX_ROUTE` (a frame plus 18 bytes) | `TOO_LARGE` |
| Control message | at most `MAX_CONTROL` | `TOO_LARGE` |
| Request body | at most 16 KiB, as on loopback | `413` |
| Response body | at most 16 MiB | `TOO_LARGE` (page) |
| Handshake time | 10 seconds from `SESSION_OPEN` (engine) or from opening the socket (page) | `TIMEOUT` |
| Idle session | 5 minutes without a frame | `TIMEOUT` |
| Session lifetime | 30 minutes, and never past the link's expiry | `TIMEOUT` |
| Requests per session | 64 | `RATE_LIMITED` |
| Open sessions per link | `MAX_SESSIONS_PER_LINK` | `SESSION_LIMIT` |
| Open sessions per engine | `MAX_SESSIONS_PER_ENGINE` | `SESSION_LIMIT` |
| Handshakes per link | `MAX_HANDSHAKES_PER_LINK` per `HANDSHAKE_WINDOW` | `RATE_LIMITED` |
| Live links the Vault accepts per engine | at least `MIN_LINKS_PER_ENGINE` | `ERROR` `LINK_LIMIT`; the engine hands over the long link (a plugin approval: `NO_PORTAL_LINK`) |

### Replay and expiry

- Session keys are fresh per session; counters refuse replays within one ([Handshake](#handshake), [Frames](#frames)).
- An approval is single-use in Postgres, a revert is applied once, and both expire (24 hours; one hour for an unsigned revert). A replayed signature is refused by Postgres (`APPROVAL_INVALID`, `REVERT_INVALID`) whatever carried it (design 6.3).
- A reissued link revokes the old one at the engine (its `psk` deleted, its token unregistered, its sessions closed with `LINK_REFUSED`). An expired link goes the same way, and the Vault drops its token at `expiresAt` on its own.
- A restarted engine keeps its links (the links file) but no session; it registers its links again after `READY`.

### What the Vault sees

**Sees (metadata only, VC-4):** engine ids and their public keys; when each engine is connected and from which IP address; link tokens, when they are registered, used and unregistered, and their expiry; page IP addresses and user agents; how many sessions and frames, their padded sizes and timing; close codes. Padding hides one frame's exact size, not these: how many frames a message took (a large response, such as a big revert, shows as many full frames), which way each went, and the rhythm of a session. From them the Vault can usually tell that a page read an item and then posted a signature (a small request answered after Postgres's time): **that an approval, revert or plugin approval was probably signed, and when**, though not which item, rows or result. **Never sees:** link secrets, `psk`s or session keys; item ids, rows, statements, headlines, signatures, receipts, results; any database credential; any private key. (The portal's static host sees the page path, `/approvals/<id>`, `/reverts/<id>` or `/plugins/<id>`, whose id the contract already treats as not secret.)

**What the Vault must do** (tested against the Go fake Vault, VC1-4, and attacked by a hostile one, VC1-12): forward session bytes unchanged and in order; keep one engine's sessions apart from each other and from other engines'; route a token only to the engine that registered it first, and refuse another engine's registration (`LINK_CONFLICT`); drop tokens at their expiry; accept the sizes above; send fresh single-use challenges; never log session bytes. Retention (VC-24): connection metadata at most 7 days. Nothing in the engine or the page relies on any of these: each is about service and privacy, not about what gets accepted.

### Configuration and status

- **`vault`** in `engine.json`: `ON` or `OFF` (VC-19): `ON` on an agent-operated engine (`basalt init --remote`) and when installed through a Vault-driven setup, `OFF` otherwise; `basalt init` has no `--vault` flag. An `ON` value with a local pages origin is refused when the config is loaded, for the passkey reason above. `vaultUrl`: the development override above.
- **`status`** gains `vault` ([`status.json`](../api/mcp/tools/status.json)): `state` (`OFF`, `CONNECTING`, `CONNECTED`, `UNREACHABLE` after 30 seconds without `READY`, `KEY_ERROR`), `engineId` and `fingerprint` whenever the key file loads. No state is a problem: approvals work in all of them, through long links when the Vault is not there. The exception is a plugin approval on an agent-operated engine, which needs the Vault: in any state but `CONNECTED`, `request_plugin` refuses to open one (`NO_PORTAL_LINK`).
- **Links** follow the [link budget](showing-links.md#the-link-budget)'s order: the portal short link when the Vault registered it, else the long link.
- **`status.engineRecord`** ([`status.json`](../api/mcp/tools/status.json)): `state` `RECORDED` (the agent's database records this engine's key, not revoked), `NOT_RECORDED`, `REVOKED` or `UNKNOWN` (the guard is older than version 33, the key file is refused, or the database cannot be read); `recordedAt` and `revokedAt`. The `status` tool reports it on an engine that is running, as a service or in the foreground (the report of an engine that is down, or whose key file the CLI's user cannot read, has none). The problem `ENGINE_REVOKED` (`REVOKED`) is in [Next steps](next-steps.md#next-steps-per-code).
- **`status.ledger`** ([`status.json`](../api/mcp/tools/status.json)): `bytes`, the size of every relation in `basalt_meta` (tables, indexes and TOAST, from `pg_class` and `pg_total_relation_size`, which need no privilege on the schema); `valuesKeptDays` (30) and `recordsKeptDays` (365), the fixed retention `prune()` applies. Absent when the guard cannot be read (the engine is down, the database cannot be reached, or `basalt_meta` is missing), never `0`. A failed size read leaves it out and adds no problem.

### Test vectors

Shared files under `api/mcp/vault/testdata/` (VC1-2: `link-derivation.json`, `engine-id.json`, `padding.json`, `handshake.json`, `frame.json`, `signature.json`, `receipt.json`), each one kind, in the format of [`vectors.schema.json`](../api/mcp/vault/vectors.schema.json): `LINK_DERIVATION`, `ENGINE_ID`, `PADDING`, `HANDSHAKE`, `FRAME`, `SIGNATURE` (every context above) and `RECEIPT`. Each case says what a receiver must do (`ACCEPT`, `REFUSE`, or a close code), so the refusals are pinned too: a tampered tag, a wrong `psk`, an invalid point, a compressed key, a reflected, replayed, reordered or spliced frame, non-zero padding, a signature from another context. Go tests and `node --test` read the same files; a mismatch fails `make ci`. Private keys are fixed 32-byte scalars so the bytes are reproducible (WebCrypto imports one as PKCS#8 without the optional public key and computes it); ECDSA signatures are randomized, so a vector pins one valid signature and a writer under test uses it instead of signing.

The Vault service's own vectors and tests live with it, privately.
