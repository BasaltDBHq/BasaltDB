# Changelog

All notable changes to BasaltDB are recorded in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- An agent on a computer the person cannot reach can now ask for a plugin with `request_plugin`. The person approves it with their passkey on the portal page the agent links to, which reaches the engine through the BasaltDB Vault, and the engine runs the plugin only once the database has verified the signature. On that computer the agent and BasaltDB run as one user, so the approval is consent, not containment: a plugin you approve can read what BasaltDB can, and the page says so. Without a connection to the Vault, `request_plugin` refuses (`NO_PORTAL_LINK`) and writes nothing.

### Changed

- The plugin approval page names the plugin's fingerprint "Plugin fingerprint", apart from the engine's fingerprint a portal page shows.

- The README, `llms.txt` and `docs/` describe the simplified product: the agent runs `basalt init`, the person finishes on the setup page, and no guide asks a person to type a `basalt` command or paste an admin connection string into a terminal. `docs/bot-setup.md` asks the person for nothing but the page they open. The same-user limit of the local setup is written down in the install guide and the README.
- The MCP initialize instructions tell an agent on a computer the person cannot reach to run `basalt init --remote`.
- `basalt --help` and the error for an agent missing from the config tell an agent to run `basalt init` on the person's own computer and `basalt init --remote` on one the person cannot reach, and to show the person the link it prints, instead of a setup code.

### Added

- `pkg/setup` `CheckRemove` and `RunRemove`: remove BasaltDB from a database with only an admin connection, for the connect page's Remove BasaltDB tab. They list the bots that lose their access by name, show the SQL, and run it in one transaction once the typed name equals the database's name.

### Removed

- `docs/setup-from-laptop.md` and `docs/crash-reports.md`, with the commands and flags they described.
- `basalt service uninstall`, with its flags. Removing BasaltDB on the setup page now also removes the engine service: the page's last step asks you to tell your agent to finish, and the agent's next `basalt init` asks for your password once in the system's administrator dialog, which stops the engine and plugin services and removes their units, the system directories (config, state, sockets, logs, the plugin base) and the engine's and plugins' OS users. The service stays while the engine still serves an agent of another database.
- `basalt engine revoke` and its `--yes` flag, and the engine's handling of a revoked key on the relay. To cut an engine off, remove BasaltDB from the database on the setup page: that drops every `basalt_*` role, so the engine can no longer log in. A key revoked by hand in SQL still shows as `REVOKED` in `status`, and the engine no longer ends its relay links for it.
- `basalt upgrade` and `basalt uninstall`, with their flags. The guard update and the removal of BasaltDB run on the engine's local setup page: the page shows the SQL, you type the admin connection string there, and it runs in one transaction. A removal also drops the agents of that database from the engine's config and deletes their credentials.
- `basalt log`, `basalt status`, `basalt access`, `basalt crash` (`list`, `show`, `report`) and `basalt portal verify`, with their flags and the `portal-verify-result` JSON schema. The agent's `status` tool reports what `basalt status` did, names the newest crash report with its GitHub link, and lists what the agent can read and write. `basalt revert` stays until the relay carries every revert. The portal check runs in the release workflow (`make portal-verify` runs it by hand). A panic in a command now prints where its report was saved.
- The person socket (`person.sock`). On a service engine, `basalt approve`, `basalt revert`, `basalt passkey` and `basalt upgrade` run by a person who is not root now say to run them with `sudo`, and the update notice no longer asks the engine whether its update check is on. `request_plugin` uploads the plugin's files over a second connection to the agent's own socket; `--person-uid` and `personUids` now only say which OS users may change plugins.
- `basalt plugin` (`add`, `enable`, `disable`, `remove`, `list`, `check`, `approve`) and the JSON schemas of its `--json` results. Ask your agent to add or remove a plugin: it calls the new `request_plugin` tool and you approve the plugin on the plugin approval page. The plugin's health is in the agent's `status`. A plugin in `engine.json` is changed by editing that file.
- `basalt engine --user` and the engine's own privilege drop, and `basalt engine list` (with `--admin`, `--agent` and `--json`). In a container, start `basalt engine` as the OS user that should own the engine's files.
- `basalt plugin keygen`, `sign` and `trust`. They are for plugin authors, not people running Basalt. Make a key and sign a plugin with `basalt-plugin keygen` and `basalt-plugin sign` from the plugin SDK (`github.com/basaltdbhq/basalt-plugin-go`); the engine verifies the same signatures. To trust a publisher's key, put its public file in the engine's `plugin-trust` folder as `<keyId>.pem` and restart the engine.
- The direct transport: `basalt tunnel`, the engine's direct listener (`directAddr` in `engine.json`), `--direct-addr` on `basalt init` and `basalt init --remote`, `--engine-url` on `basalt init --setup-code`, and the portal's engine pin pages (`/engines`, `/engines/add`) with their per-person `connect-src` cookie. Portal pages reach the engine through the Vault relay only; until its page side ships, a portal short link says to use the long link. An `engine.json` that still has `directAddr` is refused at load, as any unknown key is: delete the key.
- The engine address recorded with an engine's key. The guard's schema moves to version 8 (non-breaking): `record_engine` takes the key alone and `basalt_meta.engines` drops its `url` column. `status.engineRecord` and `basalt engine list` (`--json` too) no longer show an address, `status` no longer reports `DIRECT_NOT_SERVED`, and `basalt init --setup-code` no longer asks to revoke another engine at the same address. `basalt engine revoke` and `basalt engine rotate-key` stay.
### Changed

- Every next step, warning and person message now hands the person a link, never a `basalt` command. Setup jobs (a guard update, a passkey, a table to grant, row-level security, a database certificate, a new password, a reinstall, an expired setup link) are an `AGENT` `RUN_COMMAND` of `basalt init --agent NAME` (with `--remote` on an agent-operated engine), which prints the link the person opens; the agent runs it on a person-operated engine too. A held write's link stands alone: the `approveCommand` field of `APPROVAL_REQUIRED` and `list_pending`, the `command` of `preview_revert` and the "Or run" line of the approval message are gone. A revert too large to prepare in one call asks for a narrower one (`runs` or `tables`), and an expired one is requested again with `request_revert`. Steps no longer carry `--config` or the flags `basalt init` saved. The MCP instructions name only `basalt init`.
- `basalt init` without `--remote` refuses when stdin is not a terminal, as it already did under an agent marker, before it reads `BASALT_ADMIN_DATABASE_URL` or stdin. A person types the admin connection string at its prompt; piping it in no longer works. Plain `init` no longer reads `BASALT_ADMIN_DATABASE_URL`: when it is set, init refuses, does not use it, and says to remove it and change that password.

### Fixed

- A Vault session that a duplicated or otherwise refused frame ends now always closes with `FRAME_INVALID`. When the engine was answering the page's request at that moment, it could close with `PROTOCOL` instead and send the Vault a second `SESSION_CLOSE`.
- The warning for a binary in a temporary folder now also fires on macOS, where the default temp folder is a link (`/var/folders/...` to `/private/var/...`) and the binary path was never matched against it.

### Breaking for alpha installs

- `basalt init --remote` takes `--agent` and no other flag: `--write`, `--read`, `--all-tables`, `--prefix`, `--statement-timeout`, `--operated-by`, `--vault`, `--database-url`, `--new-code`, `--forget`, `--trust-root` and `--json` are gone, with the `remote-init-result` JSON schema. A new engine is agent-operated with the Vault on, and the first run prints the connect link of a connect-only code: the person gives the agent nothing about the database, and the connect page asks for its connection string and tables. Without `--agent` it sets up the config's one agent. The recoveries need no flag: a pending setup that expired, that the person refused, or whose address the engine refused (the engine now records that as `addressInvalid` in `engine.json`) is forgotten on the next run, which makes a fresh code, and a credential the database refuses gets a code with a new password. An `AGENT` code with a new password now runs as an `INSTALL` when its role is missing, so a role someone dropped is created again instead of refused `ROLE_MISSING`. After a connect-only setup, the next run saves the tables the person ticked as the agent's tables, so later codes never ask for every table in `public`. `init --remote` never pins a certificate: it prints the person's `basalt trust pin` command. Its output is text only.
- `basalt init` on your own computer (without `--remote`) only starts setup. It takes `--agent` and `--demo` and no other flag. If the engine service is not installed yet, it installs it through the system's administrator dialog: one password, in the dialog, and nothing in the terminal. It then waits for the engine's setup page, prints the setup link and opens it in the browser, and prints the `basalt mcp` line the agent registers. It never asks for or reads the admin connection string, and there is no `sudo` step: the person finishes on the setup page. If a setup page install committed but could not write `engine.json`, running the page again finishes it with the agent the engine already holds.
- A first install of the engine service on a person-operated engine asks for your password through the system's administrator dialog (`osascript` "with administrator privileges" on macOS, `pkexec` on Linux) before `sudo`. The dialog runs a fixed script built only from constants and the resolved path of the running binary: it creates the engine's OS user and system folders and installs and starts the unit. Before it creates anything, the script checks every folder it writes in and the binary again as root, and refuses a symlink root does not own, a folder owned by anyone but root or the engine's user, a folder writable by group or others, an existing engine account that is not a system account with no login shell, and an engine group that exists without its user. With no dialog (an SSH session, a machine without a desktop) `basalt init` stops before it reaches the database and never runs the engine as your user instead. A first install takes only the default engine user. The `sudo` step that writes the agent's config and credential stays for now, so a first install asks for the password twice.
- The engine service's unit (systemd and launchd) now runs `basalt engine --config <system path> --supervise`.
- Every command finds `engine.json` by itself: at the system path, else in the person's own config directory (`~/Library/Application Support/basalt/engine.json` on macOS, `$XDG_CONFIG_HOME/basalt/engine.json` on Linux). When both exist the command stops with an error that names both. `--config` is now a flag of `basalt engine` only, `--credential-file`, `--socket-dir` and `--socket` are gone, and `--agent` is needed only when the engine serves more than one agent. `basalt mcp` reads the socket directory from the config, so the MCP line is `basalt mcp --agent NAME` wherever the config is, and the commands the engine prints no longer carry `--config`.
- A `basalt init` or `basalt init --remote` without a terminal, against a database whose certificate verifies against no authority this machine trusts and no trust profile, now stops with a usage error that names `--trust-root` and the fingerprint the server presents: pass `--trust-root <SHA-256>` after checking it with your provider, or name the CA with `sslrootcert`. Under an agent marker `init --remote` goes on and prints the person's `basalt trust pin` command instead.
- Breaking for installs of an alpha release: an agent's `credentialFile` in `engine.json` moves inside `store`. The old key is not read, and every command that loads `engine.json` stops with the edit for the agent. Replace `"credentialFile": "<path>"` with `"store": {"kind": "POSTGRES", "credentialFile": "<path>"}` by hand, then run `basalt upgrade --agent NAME` for the guard schema below.
- The guard's schema moves to version 2, a breaking upgrade: run `basalt upgrade --agent NAME` once after updating the binary. Until then the engine serves only `status`, with the upgrade steps.

### Added

- Removing BasaltDB on the local setup page is confirmed by typing the database's name, in place of a tick box. The engine checks the typed name against the database inside the removal's transaction and refuses it, with nothing changed, when they differ.
- `basalt init` without `--demo` sets up your own database on the local setup page. You type the admin connection string, tick the tables the agent gets (each read and change, or read only; a table without a primary key is read only), label the columns that hold personal data (the page suggests labels and applies only the ones you accept, or you skip the step), trust a database certificate no public authority signs for that host only when asked, create a passkey, and read the SQL before it runs. The run sends exactly what the last check showed: change a table, a label or the certificate and the page checks again.
- `basalt init` on a computer whose engine is already set up prints and opens the setup page, where you pick Update the guard or Remove BasaltDB. When the guard is behind, the agent's `status` and its next steps give you the update link directly.
- The local setup page runs two more jobs on an engine that is already set up: `UPDATE` adds the guard's missing migrations and nothing else, and `REMOVE` drops BasaltDB from the agent's database. Both check that the admin connection string is for the agent's own database before connecting, and neither registers a passkey.
- The local setup page (`/setup/` on `http://localhost:8787`). An engine with no config serves it. The person confirms the agent's OS user and types the admin connection string, which is used once and never written or logged. The person reads what the install does and the SQL, creates a passkey when the database has none for this computer, and runs the install. `POST /api/v1/setup/check` reads and changes nothing. `POST /api/v1/setup/run` runs the guard, the sample data, the agent role and the passkey in one transaction, then the engine writes the agent's credential and its own `engine.json` and starts serving the agent. Every other route of the engine's pages refuses a body that holds a `databaseUrl`.
- A service engine started before its `engine.json` exists (a first install through the administrator dialog) no longer exits and crash-loops. It serves only `/healthz` and the setup page on `127.0.0.1:8787` and waits. Once `engine.json` appears, it loads it and serves its agents in the same process. If the port is taken, it exits `1` and names the port.
- The `request_plugin` MCP tool: the agent prepares a plugin install or change, you approve it with your passkey on the plugin approval page (which opens in your browser), and the agent's next call waits until the plugin runs. It also removes a plugin. It works on an engine you operate that runs as a service and serves its local pages; on an engine an agent operates, plugin changes stay refused.
- The `status` tool now also shows the newest saved crash report (its file and a link to file it on GitHub), the tables the agent can read and write, and the health of each plugin served to it.
- The portal's approval and revert pages, opened from a short link, show the engine's receipt for a relayed signature next to the engine fingerprint, with the ask to compare it with the one in the chat (the page never calls it verified), or say why there is none. When the engine does not take a signature relayed through the Vault, the page says to open the link again instead of showing a code to paste.
- A portal short link (`https://portal.basaltvault.app/approvals/<id>#s=<secret>` and `/reverts/<id>`) now opens an end-to-end encrypted session to the engine through the BasaltDB Vault (`wss://relay.basaltvault.app`), run in the page with WebCrypto. The page shows the engine's fingerprint (four groups of four, as `basalt status` prints it) to compare before signing, says when it is connecting, when the link is gone, when the engine is not connected to the Vault, and when the Vault cannot be reached (ask the agent for the long link). The portal's CSP gains `connect-src wss://relay.basaltvault.app` and nothing else; the engine's own local pages are unchanged. `basalt portal verify` and the engine's portal check expect the new policy, so a binary from before this change reports `PORTAL_MISMATCH` against the redeployed portal, and this one does until the portal is redeployed.
- On a person-operated engine, `basalt mcp` opens a link to the engine's own local pages in the browser when a result carries one (a held write's approval page, a revert to sign), and still passes the result, link included, to the agent. It opens no other URL, nothing on an agent-operated engine, and each link once. There is no flag. The engine's hello answer now carries `operatedBy` and `pagesOrigin` for it.
- Pins refuse public authorities. No pin (`basalt init`, `init --remote`, `basalt trust pin`, the connect page) is made for a chain whose top is, or that chains to, an authority in the system's trust store. With the name such a chain verifies already; without it, a `"verify": "ca"` pin would accept every certificate that authority issues as the host. An operator `"verify": "ca"` profile with such a root is refused when `trust.d` is read.
- Pinning from the connect page, for a connect-only code: when the connect service refuses a database's certificate (`CERTIFICATE_NOT_VERIFIED`) for a host no profile covers, it hands the page the chain top it read with the TLS handshake alone, and the page asks `Trust it for this host only?`, showing its subject, SHA-256 and expiry. `connect.proto` gains `Refusal.trustRoot`, `trustRoot` on `CheckSetupRequest`, `RunSetupRequest` and `CollectAddressResponse`, the refusal `TRUST_ROOT_MISMATCH` and the reach reason `TRUST_ROOT_MISMATCH`. The engine reads the chain itself from its own network and pins the certificate authority (`pin-<host>` in `trust.d`, on the person's yes, before the credential) only when its chain top has the SHA-256 the person approved. Otherwise `status` reports `TRUST_ROOT_MISMATCH`, nothing is pinned and the engine does not log in.
- Pin on first use: for a database no profile covers whose certificate verifies against no authority this machine trusts (Cloud SQL, DigitalOcean, Aiven, self-signed), `basalt init`, `basalt init --remote` and the new `basalt trust pin --host H [--port P]` show the certificate authority it presents (subject, SHA-256, expiry), read with nothing but the TLS handshake, and pin it for that host only on yes (default no). The pin is a `pin-<host>` profile in `trust.d`; the agent's connection then verifies with `sslmode=verify-full`. A certificate that does not name the host (connections by IP) is pinned with `"verify": "ca"`, the chain checked against the pin alone, only after the full check failed on the name alone. An agent never pins.
- `basalt init` records the pin in the ledger (`TRUST_PIN_RECORDED`, guard schema version 6, non-breaking: run `basalt upgrade` for it). `status` warns `TRUST_PIN_MISMATCH` when the ledger records another pin, and refuses a pinned host that presents another root with `TRUST_ROOT_CHANGED`, naming both fingerprints and `basalt trust pin` to accept it; the CLI's connections say the same. `status.trust` gains `verify`.
- Trust profiles: which root certificates verify a database's certificate, as data. Supabase's and Amazon RDS's roots are now built-in profiles (a JSON file per provider with its PEM files, each pinned by SHA-256), and operators add their own in `trust.d` next to `engine.json`, for a provider whose CA is per instance (Google Cloud SQL, DigitalOcean, Aiven) or a self-signed database. A profile's roots are added to the system's authorities only for its hosts and only with `sslmode=verify-full`, the host name always checked; `sslrootcert` still wins. `trust.d` files are read with the rules `engine.json` and the credential file have (owner, mode, no symlink, one link), and a file that breaks one, or whose roots file does not match its SHA-256, is refused and named; a refused file named after a built-in keeps that built-in off. The engine reads them again for each new connection, so a new profile applies with no restart and no upgrade.
- `basalt trust list`, `basalt trust add --name N --match SUFFIX --ca FILE`, `basalt trust remove --name N` and `basalt trust disable --name N` manage those profiles. `add` refuses a certificate that is not a CA and a match that is a public suffix on its own, by Go's public suffix list plus a short list of shared cloud and database zones such as `amazonaws.com` and `rds.amazonaws.com` (`com`, `co.uk`, `github.io`, `cloudfront.net`, `s3.amazonaws.com`); `add` and `remove` refuse to run under an agent marker.
- `status` (the tool and `basalt status`) reports `trust`: the profile, `sslrootcert` or system authorities that verify the agent's database, with the roots' fingerprints and expiry. New problems: `TRUST_ROOT_EXPIRING` (a root in use expires within 90 days), `TRUST_PROFILE_REFUSED` (a `trust.d` file was not loaded) and `CERTIFICATE_NOT_VERIFIED` (the database's certificate does not verify; it names the host and the `basalt trust add` command, in place of `DATABASE_UNREACHABLE`). The CLI's own connections that fail on the certificate say the same.
- `make check-provider-roots` reads each built-in profile's `source` and is on the release checklist.
- The engine and the CLI now connect to Amazon RDS and Aurora databases with full TLS verification (host name checked). They carry AWS's global RDS bundle and trust it, next to the system's authorities, only for hosts under `rds.amazonaws.com` and `rds.amazonaws.com.cn` with `sslmode=verify-full`, as they already do for Supabase's roots on Supabase hosts. Each provider's roots verify only its own hosts: a Supabase root never verifies an RDS host, nor the reverse. A connection string that names its own `sslrootcert` keeps it. The bundle has no roots for the China or GovCloud regions, so hosts there still need their own `sslrootcert`. `make check-provider-roots` compares each carried roots file with the one its provider publishes.
- `basalt init` and `basalt init --setup-code` ask about row-level security with a checklist at a terminal: the agent's hidden tables grouped by schema, every table checked by default (Enter lets the agent see all rows), arrows to move, `→`/`←` to open and close a schema, Space to toggle a table, `a` to toggle a schema. `--agent-rls` now also takes a list (`--agent-rls=us.*,global.user_router`: `schema.table` or `schema.*`, comma-separated); a name that matches no hidden table is a usage error before anything is written. Without a terminal and without `--yes`, init prints the same grouped list on stderr and reads one line from stdin: `all`, `none` or a list; an empty line or end of input is `all` (before, piped input got no policy). `--yes` and `--dry-run` answer `all` for `ask` (before, `none`) and print one line naming the tables that get the policy; pass `--agent-rls=none` or a list to opt out.
- `basalt init` and `basalt init --remote` print the `basalt mcp` command (and `mcpCommand`, and the `claude mcp add` offer) with the absolute path of the running binary instead of `basalt`, so an agent app whose `PATH` lacks the binary can still start it. A binary under the temp directory or a Go build cache gets a warning to move it somewhere that survives.

- `basalt init --remote` now prints the `basalt mcp` command the agent should register, and `--json` returns it as `mcpCommand` (an argv array). The command carries `--socket-dir` whenever the socket directory is not the one `basalt mcp` uses when no `--socket-dir` is given (`basalt mcp` never reads the socket directory from the config), and `--config` whenever `basalt mcp` would not find the config by default, the same as the line `basalt init` already prints. A non-root init without `--config` therefore includes `--socket-dir` pointing at the per-user run directory. `docs/bot-setup.md` uses that printed command instead of a hand-written one.
- New guide section "Bot computers with no service manager" in `docs/bot-setup.md`: one folder that survives a reboot or update, the binary in it, the `basalt mcp` line with `--socket-dir` and `--config`, what the first Basalt call after a restart does, and the limit that nothing runs until the bot's next session.
- A same-user engine now recovers after an update of a bot's computer: it recreates its state and socket folders when they are gone, sets them back to `0700` when an update reset them to `0755` (never a folder another user owns, never a service engine's), and starts over a leftover lock file or socket. A credential file that is not `0600` is still refused. `status` reports why the engine started in `engine.startedBy` (`HAND`, `MCP`, `CRASH`), and, when the engine does not answer because its supervisor gave up, `engine.lastStop` with the new problem `ENGINE_GAVE_UP`.
- The `basalt mcp` line that `basalt init` prints and offers to `claude mcp add` now carries `--config <path>` when the engine config is not where `basalt mcp` looks by itself (for example a config under `/workspace`), so the shim can read it and start the engine. A config in the default place leaves the line unchanged.
- `basalt mcp` starts a same-user engine it finds down, so a bot's computer that lost its engine (a reboot, an update) needs no step: the next tool call starts `basalt engine --supervise` in the background, waits up to 15 seconds for it, and answers normally. Two `basalt mcp` processes at once start one engine. A service-mode config, a config another user owns, or root keeps today's `ENGINE_UNREACHABLE` answer. When the engine cannot be started the answer names the reason and the engine log (`engine.log` in the state directory), and `status` shows the new problem `ENGINE_START_FAILED`.
- After `basalt engine --supervise` gives up, `basalt mcp` does not launch another supervisor for 1 minute, counted from the `at` time in `last-stop.json` (never the file's mtime). Calls in that hold-off answer at once with the problem `ENGINE_GAVE_UP`, the reason, and when the next try happens. Editing `engine.json` ends the hold-off early: the supervisor records a SHA-256 of that file in `last-stop.json` (`engineSha256`).
- `basalt engine --supervise` runs the engine under a small parent that restarts it after a crash (waiting 1s, 2s, 4s, up to 30s) and gives up after five crashes in a row within 10 seconds each, recording why in `last-stop.json` in the state directory. One supervisor runs per config, and one started beside an engine that already runs exits at once. `--started-by hand|mcp|crash` says why an engine started.
- `basalt init --remote` without `--database-url` on an agent-operated engine with the Vault on makes a connect-only setup code: it names no database and carries the engine's key, and only the connect link runs it. The person pastes the database's connection string on the connect page only; the bot never needs an address or table names. The agent's password waits in `agents/<agent>.secret` (`0600`, owned as the credential file) and `engine.json` records `awaitingAddress`. While the code waits, a re-run prints it again and a change of tables or `--new-code` is refused; after it expires, after the person refuses the database, or with `--forget`, the next run makes a recovery code. `--database-url` still works on every path and replaces a waiting connect-only code. `basalt init --setup-code` refuses a connect-only code with `CONNECT_ONLY` and says to open the link.
- The engine collects a connect-only setup's address itself: it asks the connect service for it with a request signed by its engine key, checks it (a plain host name, port and database name; global unicast addresses only; a verified certificate always), and probes it with a login bound to fail. It never sends the agent's real password before the person confirms the database: `status` names the database (`setup.state` `CONFIRM_DATABASE`), the agent asks the person in the chat, and the new `confirm_database` tool records the answer. On yes the engine writes the agent's credential, removes `.secret` and serves the agent after a restart of its own; on no it forgets the address and the password and the agent makes a new code. Until then every other tool answers `UNAVAILABLE` with `SETUP_PENDING` or `DATABASE_NOT_CONFIRMED`. New `status` problems: `CONFIRM_DATABASE`, `DATABASE_REFUSED`, `DATABASE_UNREACHABLE_FROM_BOT`, `ADDRESS_INVALID`, `SETUP_NOT_FOUND`, `CLOCK_SKEW`. `basalt status` while the engine is down reports the pending setup from `engine.json` without collecting.
- The connect page can check, before the person approves, that the bot can reach the database they pasted. The engine probes that address with a login bound to fail and reports to the connect service whether it reached it, and why not (a private address, no route, a certificate that does not verify, or no answer in time). It shows nothing of that address in `status`, writes nothing, and asks the person about a database only after the setup ran; the probe after the setup reuses the earlier one for the same address and IP within 5 minutes.
- A waiting connect-only setup now collects every 15 seconds for the first 2 hours after its code was made, then every 5 minutes until the code expires, and at once on `status`. The engine also refuses a collected address that the `--database-url` rules would read as another database, such as a Supabase project's own host without its project ref.
- A setup with `--all-tables` whose tables changed after the person approved the list now stops with `TABLES_CHANGED` and says to check the setup again, in place of a generic setup failure. Nothing changes in the database.
- The public setup package (`pkg/setup`) runs what the connect page needs:
  - the tables the person left ticked, granting exactly those (read only for a table without a primary key);
  - each column's current label;

It reads `engine.json` every second and, while a plugin waits for approval, each agent's approvals every 2 seconds (every 15 seconds otherwise), and starts the plugin within a few seconds of your signature. Seven new person socket methods upload a plugin's files in parts, open a change, list, relay a signature, disable and remove. The engine stages and checks the copy itself under its state directory, keeps the entry in `<stateDir>/plugins.json` with `"approval": "REQUIRED"`, and opens one plugin approval per database with the listed agents' own credentials. Nothing is written outside the state directory. ### Security

- Row-level security answers cover only the agent's own tables. When an agent had no `--read` tables or no `--write` tables (or a setup code listed none of one kind), `basalt init`, `basalt init --setup-code` and the connect page also offered every RLS table the agent's role could already read through another grant, such as one to `PUBLIC`. `--yes`, Enter on the checklist or an empty piped line then let the agent see all rows of those tables, and a read table could get a write policy. Now only tables in the agent's lists get the agent policy, read tables get a read-only one, and naming another table in `--agent-rls` is a usage error. On a database where that happened, drop the agent's policy on each table it was not given: `DROP POLICY <agent role> ON <table>`.
- Portal setup links expire after 10 minutes and are refused on open when already used or replaced by a newer code, so a link found hours later cannot still walk the setup.
- The release `SHA256SUMS` is signed with keyless cosign, and the signature is attached to the release as `SHA256SUMS.sigstore.json`. `SHA256SUMS` now also lists the portal checksum, so one signature covers every file. See [docs/install.md](docs/install.md) to check it with `cosign verify-blob`.

- A connection to the vault that BasaltDB ends itself, for example after the link is rotated, ended, or a session times out, now closes with its reason (such as `LINK_REFUSED` or `TIMEOUT`) instead of an abnormal closure without a code. The session always ended; only the reason could be lost.
- A data race in the vault session's idle timeout, seen only with very short idle timeouts (the default is 5 minutes).

### Changed

- Release binaries are built with Go 1.26.11, the toolchain set in `go.mod`, instead of Go 1.26.0.

## [0.0.1-alpha.1] - 2026-11-15

### Fixed

- The release publishes the Homebrew formula. The 0.0.1-alpha release has the binaries but no formula, so `brew install` starts with this version.

## [0.0.1-alpha] - 2026-11-15

The first public alpha, for macOS and Linux (amd64 and arm64). Expect bugs and breaking changes between alpha releases.

### Added

- The engine and its MCP server: an agent reads and writes your Postgres through BasaltDB, with a scoped role and no database URL of its own.
- The guard, installed in your own Postgres by `basalt init`: it records every agent write with the old values, refuses schema changes and writes of more than 50 rows, and holds writes of 11 to 50 rows and every DELETE for your passkey approval.
- Undo for a run, a single change or a task, signed with your passkey. Rows changed after the agent are left as they are and listed.
- The CLI: `init`, `status`, `log`, `revert`, `upgrade`, `uninstall`, `service` and `classify`.
- Setup for an agent on another machine, with a setup code (`basalt init --remote`).

### Changed

- The guard's schema is kept as SQL files under one version, 1 (`internal/guard/schema/`).

### Known limits

- Windows is not built yet.
- See the [limits page](https://docs.basaltvault.app/limits/) for what BasaltDB does not catch.
