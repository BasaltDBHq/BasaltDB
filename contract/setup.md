## Setup

The agent starts setup, the person finishes it on a page and signs with a passkey. One flow does every setup job: install, guard update, repair, passkeys, tables, column PII classes, a database certificate and removal. The person never types a `basalt` command. The admin connection string is typed only on a setup page and never reaches the agent: not in the chat, a file, the environment, a log or an MCP result.

The CLI side is [`basalt init`](cli.md#basalt-init). The sections from [Agents and the admin credential](#agents-and-the-admin-credential) on describe the persona 2 path (an engine run by a bot on a machine the person cannot reach) and the parts the two personas share. Where they still name a removed command or flag, [Removed](cli.md#removed) wins.

### The one setup flow

1. The agent runs `basalt init` (with `--agent` when the engine serves more than one agent, `--remote` on first setup of an agent-operated engine, `--demo` for the sample database). It prints one link.
2. On persona 1, `basalt init` opens its own link in the browser, by the same rule as [Auto-open](cli.md#auto-open): only a link whose origin is the engine's own local page origin. It always prints the link too, and the agent shows it on both personas, so the person can open it by hand when the browser did not open.
3. The page shows what it will do and the SQL, and asks once. The person types the admin connection string on the page, picks the tables, and registers a passkey when the database has none for the page's origin.
4. The SQL runs in one transaction. The page says when it is done; the agent calls `status` to see it.

| | Persona 1 (the person's laptop) | Persona 2 (a bot's machine) |
|---|---|---|
| Page | the engine's local setup page ([Local pages](local-pages.md#local-pages)) | the portal's [connect page](connect.md#the-connect-page) |
| The admin string goes to | the engine, over loopback, used once, never stored | the connect service, in one request's memory, never stored |
| The SQL runs in | the engine | the connect service |
| The passkey belongs to | `localhost` | `basaltvault.app` |

There is no second way to set up: no terminal prompt for the admin string, no admin string in an environment variable, no setup code a person runs on their own computer ([Removed: the laptop setup command](#removed-the-laptop-setup-command)).

### Setup jobs

The same flow does each job. The page names the job, shows the SQL, and asks once.

| Job | How it starts |
|---|---|
| First install | The person asks the agent to connect a database; the agent runs `basalt init`. |
| Guard update | The engine sees the guard is older than the binary. `status` tells the agent to run `basalt init`, which makes an update link. The update applies only the `basalt_meta` migrations the build has and the database lacks: it rotates no password, changes no grant or policy and registers no passkey. |
| Repair | `status` names the problem and tells the agent to run `basalt init` (for example a missing credential file: the page sets a new password and the engine writes the credential). |
| Fix what is wrong: unlabeled columns, a changed database certificate, a lost passkey, a passkey to add | The person asks the agent, or a `status` problem tells it to; the agent runs `basalt init`. The page checks first and shows only the screens that fix what it found ([The Update check](setup-page.md#the-update-check)). |
| Change an agent's tables | Planned, not part of the Update check yet: the agent runs `basalt init` and the person picks the tables on the page. |
| A database certificate no public authority signs | On first install the page shows the certificate and the person pins it for that host. When a pinned host presents another certificate later (`TRUST_ROOT_CHANGED`), the Update check shows the new one and the person pins it there ([Trust profiles](trust.md#trust-profiles); on persona 2 [Pinning from the connect page](trust.md#pinning-from-the-connect-page)). |
| A setup the person did not make | A program on this computer can finish a first install itself, with a database it controls. When the person runs `basalt init` (or asks the agent to), the page first asks `Is this your database?`; after **No**, `basalt init` resets BasaltDB on this computer through the administrator dialog, which changes no database ([Not your database](setup-page.md#not-your-database)). |
| Remove Basalt | The person asks the agent. The page shows the `DROP` statements. It drops the guard's policies, the demo schema when `--demo` made it (without `CASCADE`, as [`--demo`](cli.md#basalt-init) says), `basalt_meta` and the roles. It registers and asks for no passkey: the admin connection string typed on the page is what allows it, as it allows dropping the schema by hand. On persona 1, after the `DROP` commits, `basalt init` removes the engine service through the [administrator dialog](setup-page.md#the-administrator-dialog), with its own fixed command. |

**Persona 2.** The guard update runs from an `UPGRADE` code on the connect page; the removal needs only the admin connection string ([Removal on the connect page](connect.md#removal-on-the-connect-page)). Nothing removes the bot's engine: its role is gone. The fixes run on the connect page after the bot runs `basalt init --remote` again ([Update on the connect page](connect.md#update-on-the-connect-page)).

There is no command for any of these jobs: `basalt passkey`, `basalt trust` and `basalt classify` are removed ([Removed](cli.md#removed)), and every message that named one says to run `basalt init` (`basalt init --remote` on an agent-operated engine).

**Holding the link is not enough.** The agent holds the setup link, and a program running as the person's user can forge `Host` and `Origin` on loopback. So:

- Every job needs the admin connection string typed on the page. No setup route acts on a database, stores or keeps anything without it. The routes that take no string only read, or keep a mark: the Update check's `doctor` reads with the agent's own credential ([The Update check](setup-page.md#the-update-check)); `engine` reads the engine's own files, and `not-mine` keeps, in memory, the person's answer that the database is not theirs ([Not your database](setup-page.md#not-your-database)). That answer resets nothing: the reset needs the person's password in the system's administrator dialog, which `basalt init` opens.
- A passkey the job registers arrives in the same request as the admin connection string, and is stored in the job's transaction. The engine keeps no passkey, certificate pin or answer from an earlier request.
- There is no hand-back of a passkey before the admin string and no pairing code.

### Agents and the admin credential

**Target.** The agent runs `basalt init`; it never takes the admin connection string, so nothing in `init` needs to be refused under an agent. The agent-context markers and the refusals below go with the commands they guarded ([Removed](cli.md#removed)). What stays is the goal: the admin connection string never reaches the agent.

Most people tell their agent "connect to database X" rather than run `basalt init` themselves. Setup must work from that sentence, and the admin connection string must never reach the agent: not in the chat, a file, the environment, a log or an MCP result. The agent-led path is `basalt init`, which needs no admin credential: on the person's own computer it opens the [local setup page](setup-page.md#the-local-setup-page), where the admin connection string is typed, and on a computer the person cannot reach `basalt init --remote` makes a [connect link](connect.md#the-connect-link), and the string goes from the person's browser to the hosted connect service for one setup, never to the agent's machine. It is the same for each further database: a new agent name, the same engine.

- **Agent context.** `basalt` runs under an agent when one of these environment variables is set to a non-blank value: `BASALT_AGENT_CONTEXT` (Basalt's own marker, which a person can set in a bot's environment), `CLAUDECODE`, `CODEX_SANDBOX`, `CODEX_SANDBOX_NETWORK_DISABLED`, `GEMINI_CLI`, `CURSOR_AGENT`, `OPENCODE` (set by coding agents in the shell they run commands in). The first one set, in that order, is the one named in messages.
- **Refused under an agent.** Every command that still takes the admin connection string (`classify` and the `passkey` and `engine` subcommands that connect as the admin) refuses under an agent with exit `1` before it reads one: `BASALT_ADMIN_DATABASE_URL` is not read and there is no prompt. They refuse where they would ask. The message names the marker and never echoes a connection string: `<command> needs the database admin connection string, and it is running under an agent (<marker> is set), so basalt does not read one. An agent never asks for, accepts or types the admin connection string or password.`, then to give the person the command to run in a terminal of their own, which no agent reads, and to run `basalt init` (`basalt init --remote` on a computer the person cannot reach) for setup. Plain `basalt init` is not refused: it reads no admin string. These commands go with the CLI cut ([Removed](cli.md#removed)).
- **An admin credential in the agent's environment.** When `BASALT_ADMIN_DATABASE_URL` is set under an agent, the refusal adds `BASALT_ADMIN_DATABASE_URL is set where an agent can read it; basalt did not use it. Remove it from this environment and ask the person to change that database password now.` `basalt init --remote` never uses it either; when it is set, init warns on stderr (`basalt: warning: BASALT_ADMIN_DATABASE_URL is set here; basalt init --remote never uses it. If an agent can read this environment, remove it and ask the person to change that database password now.`) and goes on.
- **A credential in a tool call.** Every MCP tool, before it does anything else (before the engine checks the guard, reaches Postgres or writes the ledger), looks at its arguments: every string, nested ones and object keys included, and the raw request when it is not valid JSON. Each string is checked as given and normalised: JSON escapes left in it (`\u0026` for `&`, as Go's default encoder writes a JSON-text parameter) and percent-encoding are decoded until nothing changes, invisible format characters (a zero-width space) are dropped, and it is lower-cased. One that then holds a URL of the `postgres://` family (`postgres`, `postgresql`, `jdbc:postgresql`, `postgresql+<driver>` such as `postgresql+psycopg2`) with a password, in its user part (`postgres://user:secret@host/db`, the password with a quote, a slash or a space) or as a `password` parameter (`?sslmode=require&password=…`), or a libpq key and value string with a `password` key in one whitespace-separated run with a `host`, `hostaddr`, `user` or `dbname` key (`host=h user=u password=…`, as `dblink` takes it), is refused with `INVALID_ARGUMENT` reason `ADMIN_CREDENTIAL`. A connection string without a password is not refused, nor is text that only names a password: SQL such as `SET password = $1 WHERE user = $2` is not one run. The call changes nothing and is not recorded: no run, no change record, no refusal row, no log line carries the value or any part of it, and neither does the error, whose message is fixed. The next steps tell the agent to ask the person to change that database password now and to call again without the string; the person's message says the same. This is a mistake guard, like the markers above. The engine-down tools of `basalt mcp` (the engine does not answer) refuse the same way. A password in another spelling is not detected: split over several arguments or joined in SQL (`'postgres://u:' || 'pw@h'`), a `PGPASSWORD=` setting, another encoding (base64, HTML entities), or a password with both a space and a slash. The boundary stays `basalt init --remote`.
- **What an agent reads.** Text written for agents never asks the agent to take the admin connection string, and never tells it to give `--database-url`. It may name plain `basalt init [--agent <name>]` for a person's own computer and `basalt init --remote [--agent <name>]` for one the person cannot reach, and says the person finishes on the link it prints: the MCP `initialize` instructions ([What the agent is told](showing-links.md#what-the-agent-is-told)), tool descriptions, next steps and the engine's own messages, `basalt --help` (which ends with `Agents: never ask for or accept the database admin connection string or password.` and `To set up, run basalt init on the person's own computer, or basalt init --remote on one the person cannot reach, and show the person the link it prints.`), the error for an agent missing from the config (`agent "<name>" is not in <config>; set it up with basalt init --agent <name> on the person's own computer, or basalt init --remote --agent <name> on one the person cannot reach, and show the person the link it prints`), and the agent setup guide. A test reads these surfaces and fails on a command that takes the admin string outside a setup page. A `RUN_COMMAND` step addressed to the `PERSON` on a person-operated engine is the person's command, run in their own terminal, and is not covered by this rule.
- **The honest limit.** The markers stop mistakes, not a determined agent: an agent that shares the person's OS user and terminal can unset them, or read what is typed there, and `sudo` drops them by default (`env_reset`), so a bot with passwordless `sudo` is not detected under it. The boundary is the admin connection string typed only on a setup page: the local setup page on the person's own computer for persona 1 (where an agent sharing the person's OS user can still serve a lookalike page, [Limit of persona 1](setup-page.md#the-administrator-dialog)), the connect page for `basalt init --remote`. Beyond that, the engine and the agent run as OS users who cannot read the person's files.

### Who operates the engine

**Target.** `--remote` on the first setup of an agent marks the engine agent-operated (`"operatedBy": "AGENT"`); afterwards the config says it. Without it the engine is person-operated. `--operated-by`, `--passkey-origin` and `--dev-local-pages` are removed: the operator fixes the page origin (the engine's local pages for `PERSON`, the portal for `AGENT`).

- `engine.json` holds the operator as the top-level `"operatedBy": "PERSON"` or `"AGENT"` (absent means `PERSON`). One engine per machine, one operator. It decides who runs machine steps ([Next steps](next-steps.md#next-steps)). `basalt init --remote` sets `AGENT` on the first setup of an agent; there is no flag to set it or to switch it back. `AGENT` uses the portal's pages and turns the Vault on. `basalt init --help` shows only the agent-led setup ([Agents and the admin credential](#agents-and-the-admin-credential)).
- With `AGENT`, `pagesUrl` is the portal `https://portal.basaltvault.app` (CO-6, CO-8): the loopback pages would belong to the bot's machine, so a local `pagesUrl` is refused, except for development with the `devLocalPages` config key ([Page origins](page-links.md#page-origins)).
- **In the ledger (CO-15).** Every `HEARTBEAT` row's detail carries `operatedBy` next to `engineVersion` (and `chainBrokenAt` when the chain is broken), so the ledger shows the periods when enforcement was guard-only. A change shows at the next heartbeat.

### `basalt init --remote` (the engine's machine)

`basalt init --remote [--agent NAME]` takes no other flag ([CLI](cli.md#cli)); the steps below are what it does. **Target:** every code is run on the connect page ([Removed: the laptop setup command](#removed-the-laptop-setup-command)), so the output is the connect link, or where to paste the code, and never a command. With no credential for the agent it makes a [connect-only setup code](#connect-only-setup-codes); for an agent with a credential, a code for the credential's database, which the person runs on the connect page. The tables are the agent's saved ones, else every table in `public` ([Connect-only setup codes](#connect-only-setup-codes)), and the role prefix and statement timeout are fixed values. Without `--agent` it sets up the config's one agent, or `demo_bot` on a new engine; with more than one agent `--agent` is required (exit `2`). A new engine is agent-operated with the Vault on; afterwards the config says who operates it, and a person-operated engine is refused for a connect-only code (`this engine is person-operated ...`). A pending setup that expired, that the person refused, or whose address the engine refused is forgotten on the next run, which makes a fresh code with no flag: every recovery step says to run `basalt init --remote` again.

Before its probes (step 2), for a host no profile covers whose certificate verifies against no authority this machine trusts, `init --remote` pins nothing: the agent runs it, and the person trusts the certificate on the connect page ([Pinning from the connect page](trust.md#pinning-from-the-connect-page)); the setup goes on.

0. **A release version.** The code carries the build's version, which must be `major.minor.patch` with an optional pre-release (a leading `v` is dropped). A build that reports anything else (a source build without tags reports `dev`) is refused before anything is written, with exit `1` and `this build of basalt has no release version (it reports "dev"), so it cannot make a setup code; install a release build`.
1. **No admin credential.** The database is the one the agent's credential file (or its `.pending`) names; with neither, the code is connect-only. When init cannot make one, it refuses (exit `1`, nothing written) and names what the connect page needs: an agent-operated engine with the Vault on and the portal's pages, and init run as the engine's OS user. `BASALT_ADMIN_DATABASE_URL` is ignored and there is no prompt.
2. **The agent's password stays here.** Init generates it (256 bits, as `basalt init` does), writes the agent's connection string (user `<prefix>_agent_<name>`, or `<prefix>_agent_<name>.<ref>` through Supabase's pooler) to the `0600` credential file, and puts only its SCRAM-SHA-256 verifier in the code. Because the verifier is sensitive ([The setup code](#the-setup-code)), the connection string it writes keeps the strongest protection init can confirm, on by default, in this order: `sslmode=verify-full` with channel binding (`channel_binding=require`, SCRAM-SHA-256-PLUS, bound to the server's TLS certificate); `sslmode=verify-full` alone, for a server whose certificate verifies but that offers no channel binding (PgBouncer, Supabase's pooler); `sslmode=verify-ca` (when the connection string had it) or `sslmode=require`, with channel binding; else the connection string as built. A `verify-ca` or `verify-full` the connection string already had is never weakened. Only a verified certificate stops an active attacker who holds the verifier: with `sslmode=require` they can pose as the server with their own certificate and recover the `ClientKey` from the agent's proof, so channel binding there only stops a plaintext downgrade and a relayed session. Init tries each first with a login bound to fail (the new password is not set yet). With channel binding only a refused password (`28P01`) counts, which proves TLS and channel binding work; `verify-full` alone counts on any refusal of the login (SQLSTATE class `28`, or Supabase's pooler answering `Tenant or user not found` for a role it does not know yet), since the client sends its login only after a TLS handshake whose certificate verified for the host name. On Supabase's pooler (`*.pooler.supabase.com`) that is the pooler's own certificate, the one the agent's connection checks. When none counts (no TLS, a Unix socket, `sslmode=disable`, a certificate that does not verify and no channel binding, or the database is not reachable), it keeps the connection string as built, since a credential that cannot log in is worse; a probe that reaches no address of the server (every address failed to connect or timed out) ends the probing. Init prints one line saying what it applied, for example `basalt: connection protected: database identity verified (channel binding not available through the Supabase pooler)`, or `basalt: connection not protected further: ...` with the reason, the `sslmode` kept and, when no certificate verified, a hint to trust its CA on the connect page; a certificate signed by a CA the system does not trust verifies once the person trusts it there (a pin); Supabase's and Amazon RDS's need none ([Trust profiles](trust.md#trust-profiles)). Each run leaves up to three failed logins in the server's log (some hosts ban an address after many); running init again probes again, as when the server's certificate changes. A new password for an agent with a credential file goes to `<credentialFile>.pending` (`0600`) instead: the old one keeps working until the person runs the code, and the engine swaps the files when it sees the setup recorded (below). For a connect-only code there is no address to build a connection string from, so the password goes to `agents/<agent>.secret` instead and nothing is probed ([Connect-only setup codes](#connect-only-setup-codes)).
3. **The kind of code.** A connect-only code is `INSTALL`, or a recovery `AGENT` code ([Connect-only setup codes](#connect-only-setup-codes)). Otherwise, when the agent's role cannot log in with its credential: `INSTALL` with the password the credential holds while an `INSTALL` setup is pending, else `AGENT` with a new password and verifier (the database refuses the credential, `CREDENTIAL_REJECTED`). A login that fails on the certificate of a pinned host that presents another chain top (`TRUST_ROOT_CHANGED`, read with the TLS handshake alone) is not a refused credential: init makes a code that changes no grant, password or policy, carrying `engine`, and adds `"certificateChanged": true` to the pending `setup`: an `AGENT` code with no change and no verifier for an agent whose tables its saved flags name, and an `UPGRADE` code with `guard.from` 0 for one saved with every table in `public` (its tables are not known until its role logs in, and an `AGENT` code with `allTables` would grant every table in `public` now, more than the person may have ticked) ([Pinning from the connect page](trust.md#pinning-from-the-connect-page)). When the role logs in while the connect-only setup the person confirmed is not recorded in that database (`SETUP_NOT_FOUND`: it ran in another database of the same server): `AGENT` with a new password and verifier. Otherwise `AGENT` when the tables or the statement timeout change; else `UPGRADE` when the installed guard (read with the agent credential, which every guard version allows) is older than this build's; else an `AGENT` code with no change and no verifier (it re-applies the grants, and the connect page registers a portal passkey when none is active). A code of any kind also applies the migrations the database lacks up to `guard.to`.
4. **One pending code per agent.** While an unexpired code is pending and nothing changed, init prints the same code again (`reused: true`: same `setupId`, same expiry). A code is valid for 10 minutes, so this reuse applies only within those 10 minutes. An expired code is never reprinted: the next `basalt init --remote` makes a fresh one. A change makes a new one with a new `setupId` and expiry; the old one is then refused by the person's computer once the new one has run (`SUPERSEDED`). An expired code is replaced by a new one. A pending connect-only code is not replaced before it expires ([Changes while waiting](#connect-only-setup-codes)). After it expires it is replaced, even inside the 30-minute grace in which a run the person already confirmed may still finish: that run is abandoned (its password is gone with the old `.secret`, and the engine collects only the new code), and the person sets up again from the new link.
5. **Config.** Init writes `engine.json` as `basalt init` does (`initArgs`, [CLI](cli.md#cli)), plus `operatedBy`, `pagesUrl` and, per agent, the pending setup: `"setup": { "setupId", "kind", "guardVersion", "expiresAt", "code", "fingerprint" }` (`guardVersion` is the code's `guard.to`; `code` is the setup code, kept so `status` and a re-run hand out the same one). A code made for a changed certificate (step 3) adds `"certificateChanged": true`. A connect-only code adds `"awaitingAddress": true` to `setup`, replaced by `"refused": true` when the person says no ([Connect-only setup codes](#connect-only-setup-codes)). Nothing secret goes in `engine.json`. `setupId` is a UUIDv7 of the clock now, and `expiresAt` is its time plus 10 minutes, truncated to the second.
6. **Output.** Exit `0`: the setup is pending, not failed. Text: the code in a block of its own, its [fingerprint](#the-setup-code), and what the person does with it: on an engine whose `operatedBy` is `AGENT`, whose `vault` is `ON` and whose `pagesUrl` is the portal (not with `devLocalPages`), the [connect link](connect.md#the-connect-link) `https://portal.basaltvault.app/connect#<code>`, on a line of its own, when the whole link fits `linkBudget`, else where to paste the code (`portal.basaltvault.app/connect`), which is also what an engine that is person-operated, has the Vault off or uses `devLocalPages` gets: no link is made for it, and the code is never handed to a laptop command. There is no network call either way. It also prints the `basalt mcp` command the agent registers in its client: `<binary> mcp --agent NAME`, where `<binary>` is the absolute path of the running `basalt` with links resolved (the agent app may not have it on its `PATH`; a path under the temp directory or a Go build cache is kept, with a warning line to put the binary in a folder that survives). `basalt mcp` takes no other flag: it finds the config by [Config discovery](cli.md#config-discovery). There is no `--json`. A code longer than 1500 characters is refused (exit `1`), saying to name fewer tables. A connect-only code's output is in [Connect-only setup codes](#connect-only-setup-codes): the link and no laptop command.
7. Init does not install or start the engine: on an agent-operated machine the agent does it with the printed `mcpCommand` (an `AGENT` `RUN_COMMAND`).
8. **As root** (`sudo basalt init --remote`). The config's directory may belong to the engine's OS user, so root trusts nothing that user could redirect, and refuses (exit `1`, nothing written) before reading or writing any credential: a config that is not a regular file with one link, is reached through a symlink anyone but root controls (root-owned links on the way, such as macOS's `/etc`, are followed), is owned by anyone but root or its directory's owner, or is writable by group or others (`... is writable by group or others (mode 0666), so another user could change what root trusts in it; remove that access (sudo chmod go-w ...)`); a config whose agent names a `store.credentialFile` other than `agents/<agent>.url` next to the config, the only path `basalt init` and `basalt service install` write (`the config names the credential file X, not Y where basalt init puts it; as root, basalt init --remote uses only that path. Fix the agent's store.credentialFile in the config`). A `store.credentialFile` that differs only in spelling (`agents/sub/../bot.url`) is accepted, and root then uses the path it computed, never the config's string, and writes that path back to the config as an absolute path (also with a relative `--config`). The `agents/` directory is opened once from `/` without following a symlink anyone but root controls, every directory on the way owned by root or the config directory's owner (when the config directory does not exist yet, the owner of the nearest directory above it that does) and not writable by group or others (made `0700` when missing), and the credential file, its `.pending`, its `.lock` and the agent's `.secret` are then read, written and renamed relative to that directory: an `agents/` swapped for a symlink is refused (`... is not a real directory (a symlink is refused)`), on the first run as on later ones. The config directory is opened the same way, once, and `engine.json` is locked (its `.lock`), read (the checks above again) and written relative to it, so a config directory swapped for a symlink between the hardened read and the write (by a user who owns a directory above it) redirects nothing; a symlinked `.lock` there or in `agents/` is refused as a lock file that cannot be used. The `engine.json` root writes there is handed to the config directory's owner when that owner is not root (set on the new file's descriptor before it is renamed into place), as the files in `agents/` are, and a directory root makes on the way (`agents/`, or the config directory itself) is handed to the trusted owner when its parent belongs to that owner. So on a service engine's machine (`basalt service install` made the config directory, owned by the engine's OS user) `engine.json`, a new `agents/` and every file in it are the engine user's, and the service reads them. Root also records the user who ran sudo (`SUDO_UID`, never `0`) as the person, added to the config's `personUids` (an agent changes plugins only while it runs as a recorded person: [`request_plugin`](mcp-tools.md#mcp-tools)); without `SUDO_UID` it records none. With `SUDO_UID` set, a config directory owned by a user other than root and the one who ran sudo is an engine user's, so root writes the config with `"mode": "SERVICE"` and, once `engine.json` is written, says so on stderr (`basalt: <dir> belongs to uid N, not root or you (uid P): this config is a service one (mode SERVICE). ...`); a config directory the user who ran sudo owns stays theirs, in same-user mode. Every file root makes there (the credential file, its `.pending`, its `.lock` and the agent's `.secret`) is handed to the owner of `agents/`, read from the opened directory, when that owner is not root (the engine's user in service mode, as for the [lock files](#on-the-engine)): the owner is set on the new file's descriptor before it is renamed into place, so the engine reads its credential and promotes a `.pending` one. Root reads only credential files owned by root or that owner, and from one that owner wrote it takes only a string starting exactly `postgres://` or `postgresql://`, with a non-empty password, no `#`, `;`, space or control character, and no parameter but `application_name`, `channel_binding`, `connect_timeout`, `default_query_exec_mode`, `max_protocol_version`, `min_protocol_version`, `require_auth`, `sslmode`, `sslnegotiation`, `sslsni` and `target_session_attrs`, checked with the Postgres driver's own parser as well, whose host, port, database and password must match the URL's (exit `1` otherwise, never echoing the string). Every other parameter is refused, among them those that make the driver read a file for root (`passfile`, `service`, `servicefile`, `sslkey`, `sslcert`, `sslpassword`, `sslrootcert`, `sslcrl`), as is a URL without a password, which falls back to root's `~/.pgpass`: that owner could otherwise have root read a root-only file, or send a password from root's `~/.pgpass` to a server of their choosing. Such a credential is still usable by `basalt init --remote` run as that user.

### Connect-only setup codes

The chat path, where the person gives the bot nothing about the database: no address, no table names. The full connection string is typed only on the [connect page](connect.md#the-connect-page), and the admin password never reaches the bot's machine, not even the engine: the bot controls that machine, so anything the engine receives there, the bot can read.

- **When init makes one.** `basalt init --remote` makes a connect-only code when all of these hold: the agent has no credential file (a `.secret` left by an earlier connect-only code does not count), the engine's `operatedBy` is `AGENT`, its `vault` is `ON`, its `pagesUrl` is the portal (not with `devLocalPages`), and init can load or make the engine's key ([`engine`](#the-setup-code)). The code has no `target` and carries `engine`. Its kind is `INSTALL`, or `AGENT` with a verifier when it is a recovery code (below). Otherwise init refuses, as in step 1. When the engine's key cannot be loaded or made (`KEY_ERROR`, or init runs as another OS user than the engine's), init refuses with exit `1`, nothing written: `A setup code for the connect page needs the engine's key, and basalt cannot read or make it as this user (<reason>). Run basalt init --remote as the engine's OS user (the owner of the engine's state directory).`
- **The tables.** With no tables in the agent's saved flags, the code carries `agent.allTables` `{ "schemas": ["public"] }`, and the agent gets write access to every table in `public` that exists when the setup runs ([The setup code](#the-setup-code)); the page lists the concrete tables before the person approves. Tables made after the setup are not covered; the bot makes a new code to add them.
- **The agent's password without an address.** Init generates the password as in step 2 and writes it to `agents/<agent>.secret` (`0600`, next to where the credential file goes, with the same ownership and root rules as the credential file in step 8). The code carries only its verifier, as always. `engine.json` records the pending setup as in step 5 with `"awaitingAddress": true`; nothing secret goes in `engine.json`. Loading the engine config accepts an agent with `awaitingAddress` and no credential file, and the engine serves it as below. `basalt service install --agent --keep-credential` accepts one too: it places the agent with no credential file and keeps its pending setup in the config. The role is `<prefix>_agent_<name>` whatever the address; through Supabase's pooler the agent logs in as `<role>.<ref>`, and the engine learns `<ref>` when it collects the address.
- **Changes while waiting.** While `awaitingAddress` is set and the code has not expired, a re-run prints the same code (`reused: true`), unless `.secret` is gone (then the code's password is lost and the run makes a recovery code, below). So `.secret` is never overwritten before its code expires. After it expires the next run makes a recovery code and a new `.secret`, even inside the 30-minute grace; a run the person confirmed before expiry and that finishes after this is abandoned, and the person sets up again from the new link (`SUPERSEDED` stops the old code once the new one has run).
- **Recovery codes.** When the pending connect-only code expired before the address arrived, the engine cannot tell whether its setup ran. The next run makes a new connect-only code of kind `AGENT` with a verifier (a new password in `.secret`). The connect service runs such a code as a password rotation when the role exists, with the laptop command's warning for that kind (`Run it only if <name> itself gave you this code.`), and as an `INSTALL` when it does not ([Connect](connect.md#setupservice-calls)). The same holds after the person refused the database (`confirm_database` `NO`, which leaves `"refused": true` in the pending `setup`) and after the engine refused the address the connect service handed over (`addressInvalid`, below): init forgets the pending setup and makes a recovery code when it is connect-only and either expired, `refused` or `addressInvalid`, or its `.secret` is gone. A recovery code is safe either way: if the old code ran, it rotates that role's password; if it runs first, the old code is refused `ROLE_EXISTS` or `SUPERSEDED`.
- **A refused address.** When the engine refuses the address the connect service handed over (the problem `ADDRESS_INVALID`, [The engine and a connect-only code](#the-engine-and-a-connect-only-code)), it adds `"addressInvalid": true` to the pending `setup` in `engine.json`, once. The next `basalt init --remote` deletes `.secret` and makes a recovery code as above. The engine never logged in with that password, so nothing in a database depends on it.
- **Output.** Exit `0`. Text: the [connect link](connect.md#the-connect-link) and the code's fingerprint, and no laptop command. It also prints the `basalt mcp` command, as in step 6. The message says the page asks for the database's connection string, that the bot never needs it, and to check the fingerprint. The page waits until the engine has collected the address and says so, so the person does not have to tell the bot. When the link does not fit `linkBudget`, the text says to paste the code at `portal.basaltvault.app/connect` and `connectUrl` and `links` are left out.

### The setup code

`basalt-setup.1.<payload>.<check>`, one line, shown in a code block (so chat apps do not read `_` as emphasis).

- `payload`: base64url without padding of deflate-raw of the JSON in [`setup-code.schema.json`](../api/mcp/setup/setup-code.schema.json): `format` (1), `setupId` (UUIDv7), `kind`, `prefix`, `target` (absent in a connect-only code), `guard` (`from`, `to`), `build`, `agent` (`name`, `write`, `read`, `allTables`, `verifier`, `statementTimeoutMs`, in that order; absent for `UPGRADE`), `expiresAt`, from M4.1 `engine` (`publicKey`; below), and `trustPin` (below). Never the agent's password, never anything of the admin; the one sensitive field is `agent.verifier` (below). Encoders write compact JSON in the schema's key order, deflated at level 9; decoders accept any raw deflate stream and any key order.
- `check`: base64url without padding of the first 4 bytes of sha256 over the bytes before the last `.` (`basalt-setup.1.<payload>`), 6 characters.
- **Decoding**, in order: drop every whitespace character (a wrapped copy still works); not `basalt-setup.` → `NOT_A_SETUP_CODE` (`This is not a Basalt setup code.`); `basalt-setup.1` with nothing after it → `INVALID`; a version other than `1.` → `UNSUPPORTED_FORMAT`; a check that does not match → `DAMAGED` (`This setup code is damaged; copy it again.`); a payload that is not base64url, inflates past 64 KiB, is not JSON, holds a key twice in one object (at any depth; a decoder that kept the first or the last would read different codes) or fails the schema → `INVALID`; `format` other than 1 → `UNSUPPORTED_FORMAT` (`This setup code is newer than basalt on this computer: update it from the release page.`). The golden fixtures [`setup-code.fixtures.json`](../api/mcp/setup/setup-code.fixtures.json) pin each case, and pin the verifier for a password and salt; the contract test checks them.
- **Rules the schema cannot state:** `guard.from` ≤ `guard.to` (`<` for `UPGRADE`); at least one table in `write` or `read`, unless `agent.allTables`; no table in both; a code without `target` carries `engine`, and an `AGENT` code without `target` carries `agent.verifier`; the role `<prefix>_agent_<name>` at most 63 bytes; `expiresAt` no later than the `setupId`'s UUIDv7 time (its first 48 bits, milliseconds since the epoch) plus 10 minutes. Failing one is `INVALID`. These do not depend on the clock; the clock checks are the person's computer's and Postgres's (below).
- **Fingerprint.** `sha256(utf8("basalt-setup-fingerprint.2\n" + payload))`, where `payload` is the decoded payload written back as the compact JSON an encoder writes (the schema's key order, absent keys left out, no HTML escaping), so it covers every field of the code (agent name, tables or `allTables`, verifier, kind, statement timeout, target, guard, build, expiry, engine key) whatever key order or deflate stream the code-maker used; its first 10 bytes (80 bits, too many to grind a matching substitute within the 10 minutes) in lowercase hex as five groups of four (`3f9a 21c0 7d44 e1b2 90ac`). `basalt init --remote` prints it, `status` returns it while the setup is pending, the agent's `personMessage` names it, and the connect page shows it before asking. It lets the person check that the code they run is the one their own agent made, not one another chat member posted, or reposted with anything changed. It is a matching aid: it proves nothing about who made the code.
- **`verifier`**: `SCRAM-SHA-256$4096:<salt>$<StoredKey>:<ServerKey>` (RFC 5802 and RFC 7677, standard base64): salt 16 random bytes, 4096 iterations, `SaltedPassword` = PBKDF2-HMAC-SHA-256 of the password, `StoredKey` = sha256(HMAC(`SaltedPassword`, `Client Key`)), `ServerKey` = HMAC(`SaltedPassword`, `Server Key`). Postgres stores a verifier given as `PASSWORD` as is, whatever `password_encryption` says. **The verifier is sensitive.** It is not the password, but whoever holds it and sees one SCRAM exchange of the role (a connection without TLS, or TLS the client does not verify) can derive the `ClientKey` and log in as the agent; with the `ServerKey` they can also pose as the server to the agent. So the code goes only from the agent to the person (and, planned, from the person's browser to the [connect service](connect.md#what-the-connect-service-sees) when they use the connect link), and the agent's connection string is hardened ([`basalt init --remote`](#basalt-init---remote-the-engines-machine), step 2).
- **Kinds (CO-14).** `INSTALL`: the guard, a **new** agent role with its password from the verifier, its grants, a portal passkey; a role that already exists is refused (the code-maker would otherwise set the password of a role that is not theirs). `AGENT`: an existing agent's tables (a role that does not exist is refused, except with `verifier`: then the code runs as an `INSTALL`, creating the role with that password, so a new password for a role someone dropped still works), replaced by `write` and `read` as given (grants on tables no longer listed are revoked); with `verifier` its password is rotated, without it kept. `UPGRADE`: migrations only; password, grants and policies unchanged. A code without `target` must be `INSTALL`, or `AGENT` with a verifier (a [recovery code](#connect-only-setup-codes)), and carry `engine`; anything else is `INVALID`. `UPGRADE` codes and other `AGENT` codes keep `target`, since their engine already has an address. The format stays 1: a laptop older than this refuses a connect-only code as `INVALID`.
- **`allTables`**: `{ "schemas": ["public"] }` in place of `write` and `read` (a code with both is `INVALID`). The agent gets write access, with the same grants and policies as a `write` table, to every ordinary and partitioned table in those schemas that the admin role owns when the setup runs; `public` is the only schema allowed, so Supabase's `auth` and `storage` are never included. A table without a primary key is given read access only, as a `read` table, since the guard keys an agent's writes by it, and the summary says so (`<table> has no primary key, so <agent> can read it but not change its rows.`). Partitions are not listed (the agent reaches their rows through the partitioned table), and neither is a table whose name is not a plain lowercase identifier, the only names a setup code's tables may have. A table owned by another role is left out, and the page and the laptop command list it as `not included: owned by <role>`. No table at all is refused (`NO_TABLES`, nothing changed). The setup reads the list again inside its transaction; a list that changed since it was shown is refused, nothing changed (today `SETUP_FAILED`; planned: `TABLES_CHANGED`). On the wire the row-level security questions stay one per table, as for named tables; the connect page asks them once for all the tables (all rows or none), with a per-table override, and sends one answer per table, and the laptop command's `--agent-rls` answers all of them. Planned: the connect page asks no row-level security question and answers `ALL_ROWS` for every table it includes, and for an `INSTALL` code the person may untick tables there ([Tables on the connect page](connect.md#tables-on-the-connect-page)). Tables made later are not covered.
- **`trustPin`**: in an `AGENT` or `UPGRADE` code with `target` only (the schema gives an `INSTALL` code none), the SHA-256 (DER, 64 lowercase hex digits) of the certificate the bot's engine has pinned for the target's host (its `pin-<host>` profile in `trust.d`), absent when it has none. `basalt init --remote` adds it to every `AGENT` and `UPGRADE` code whenever that pin exists. It is a hint for the connect page's trust step ([Trusting a certificate authority on the page](connect.md#trusting-a-certificate-authority-on-the-page)): it adds no trust, and the engine still checks its own reading ([Pinning from the connect page](trust.md#pinning-from-the-connect-page)). It is in the payload, so the setup fingerprint covers it. A `trustPin` in a code without `target`, or in an `INSTALL` code, is `INVALID`. The format stays 1.
- **`target`**: the database the bot's engine connects to (`host`, `port`, `database`, and `supabaseRef` when the connection string names a Supabase project: a pooler user `postgres.<ref>` or a host `db.<ref>.supabase.co`). Absent in a connect-only code, whose database is the one the person pastes on the connect page; that code gives up the mechanical wrong-database check (`TARGET_MISMATCH`), and the person's own checks replace it: the page names the database before they approve, and the engine serves nothing until they confirm it in the chat ([On the engine](#on-the-engine)).
- **Valid for 10 minutes, single use (CO-13).** `expiresAt` is 10 minutes after `basalt init --remote` made the code. There is no flag that makes it last longer. Because the code-maker writes `expiresAt` and `setupId`, neither is trusted as given: the person's computer (its clock) and the connect service refuse an expired code on open and when the person confirms it, a `setupId` whose time is more than the **clock skew of 5 minutes** ahead of now, and an `expiresAt` more than 10 minutes plus 5 minutes ahead of now (`EXPIRY_TOO_FAR`). Expiry itself is checked without skew: a code is expired from `expiresAt` on. Once the person has confirmed a still-live code (on the connect page, "Yes, same code", after the page's clock checks), the run itself may finish after those 10 minutes, within a **grace of 30 minutes** (the length of the address hold): `record_setup` refuses `EXPIRED` only once the database's clock is more than 30 minutes past `expiresAt`. Past the grace an unused code is refused in Postgres whatever the client checked, so expiry holds even with an old or modified client. Single use is enforced in Postgres (`basalt_meta.setups`): the person's computer records `setupId` in the install's transaction. A code is also refused when the agent's latest recorded setup is newer (UUIDv7 ids are time-ordered), so an older unused code cannot reset the password to an old verifier. Planned: single use is enforced inside the database the code runs in, so a connect-only code, which names no database, can run once in every database it is pointed at. The connect service refuses a second database while it holds the first one's address (`RUN_ELSEWHERE`, [The address hand-off](connect.md#the-address-hand-off)), and the person's confirmation is what stops the engine using a database they did not choose.
- **`engine`** (M4.1, CO-18): `{ "publicKey" }`, the engine's signing key as its SPKI in base64url (122 characters, [Engine keys](vault-channel.md#engine-keys)), optional in a code with `target` (required in a connect-only code, whose engine signs its request for the address with it). `basalt init --remote` adds it whenever the engine's key file loads; when the file is missing it creates it first, as the engine does on its first start (owned by the engine's OS user, mode `0600`), and when the file is refused (`KEY_ERROR`), or this OS user cannot read or create it (init run as another user than the engine's), it leaves `engine` out and says why on stderr, naming the user to run it as. As root (`sudo basalt init --remote`, a service engine's machine) it reads or creates the key file relative to the state directory opened from `/` without following a symlink anyone but root controls. The state directory comes from `engine.json`, which the config directory's owner may write, so it is trusted no further than the config directory: every directory on the way must be owned by root or the config directory's owner and not writable by group or others, the state directory itself must be owned by the config directory's owner, and init never makes it (the service manager makes the default one when the service starts; when it is missing init says to start the service once, or, for a state directory elsewhere (a config given with `--config` keeps its state next to it), to make it for the config directory's owner with `sudo install -d -m 0700 -o <uid> <dir>`). The file must be a regular file with one link owned by that owner, mode `0600` or narrower, and pass the engine's own checks; a new one is written whole for that owner (given to it before it appears under its name), and one the engine made meanwhile is kept. It is in the payload, so the setup fingerprint covers it. A rule the schema cannot state: a `publicKey` that is not a P-256 SPKI with an uncompressed point on the curve is `INVALID`. The format stays 1: a laptop older than this refuses a code with `engine` as `INVALID` (its schema is closed), and the person updates `basalt`.

### The setup checks

Every runner of a setup code (today the connect service, [`RunSetup`](connect.md#setupservice-calls)) runs these steps, in this order. They were the laptop command's, which is removed; a message below that names the laptop command or a laptop flag is rewritten for the connect page with the code.

1. **Decode and validate** as above. A code without `target` is accepted (the connect service decodes with a flag that allows it). Then, by the runner's clock, exit `1` with nothing changed, in this order: `EXPIRED`, now at or past `expiresAt` (`This setup code expired on <time UTC>. Ask <agent> for a new one.`); `SETUP_ID_IN_FUTURE`, the `setupId`'s time more than 5 minutes ahead of now, and `EXPIRY_TOO_FAR`, `expiresAt` more than 10 minutes and 5 minutes ahead of now (both `This setup code claims a time in the future. Check this computer's clock, or ask <agent> for a new code.`); `BINARY_TOO_OLD`, `guard.to` newer than this binary's guard (`Update basalt on this computer to at least <build>.`); `GUARD_TOO_OLD`, `guard.to` older than 1, the first version with `record_setup`, which a valid code never is (`This setup code is for guard version <to>, but setup codes need guard version 1 or later. Ask <agent> for a new code made with an up-to-date basalt.`).
2. **The admin connection string**, typed on the page, never written anywhere.
3. **Target (CO-17).** The admin connection string must name the same database as `target`: with `supabaseRef`, the same project ref (from the pooler user or the direct host) and database name, so the pooler and the direct host of one project match; otherwise the same host, port and database. A mismatch is refused, never asked about (exit `1`, nothing changed): `This setup code is for database <database> of <Supabase project <ref> | <host>:<port>> (the agent connects there). Your admin connection string points at <...>. Either run this command with the admin connection string of <...>, or ask <agent> for a new code for the database you meant (basalt init --remote --new-code --database-url <that database, without password>).`
4. **The database's state**, read with the admin connection string, refused in this order (exit `1`, nothing changed): `PREFIX_MISMATCH`, `basalt_meta` is installed with another prefix (its owner role is not `<prefix>_guard`: `This setup code is for prefix <prefix>, but this database's Basalt uses <installed>.`); `USED` and `SUPERSEDED` (read from `basalt_meta.setups`, and enforced again by `record_setup`: `This setup code was already used on <time UTC>. Ask <agent> for a new one.`, or `A newer setup for <agent> already ran on <time UTC>. Ask <agent> for a new code.`); `ROLE_EXISTS`, an `INSTALL` code whose role already exists (`<role> already exists. This code would replace its password: ask <agent> for a new code.`), also enforced in Postgres, since the `INSTALL` SQL creates the role with a plain `CREATE ROLE`, never `IF NOT EXISTS`; `ROLE_MISSING`, an `AGENT` code without a verifier whose role does not exist (one with a verifier runs as an `INSTALL`). The fixtures' `laptop` cases pin this order. Then an `UPGRADE` code whose `guard.to` is at or below the installed guard's version has nothing to do: exit `0`, nothing changed and nothing recorded (`basalt: the guard is already at version <installed> and this code upgrades it to version <to>: nothing to upgrade; nothing changed`).
5. **Show, then ask.** First the summary, whose lines are fixed so the person reads the same words every time: by kind, `This creates the agent <name> (role <role>). Its password comes from the code: only whoever made this code can log in as <role>.` (`INSTALL`), `This replaces the password of the existing agent <name> (role <role>): only whoever made this code can then log in as <role>. Run it only if <name> itself gave you this code.` (`AGENT` with a verifier), `This changes the tables of the existing agent <name> (role <role>); its password stays.` (`AGENT` without), or `This upgrades Basalt's guard from version <from> to <to>; no agent changes.`; then `Prefix <prefix>, statement timeout <n> ms, at most 8 connections.` (for `AGENT`, with `(now <m> ms)` after the timeout when the role's current `statement_timeout` differs, and `(<m> ms set for this database only, which takes precedence)` when the role has a different `statement_timeout` for the connected database (`ALTER ROLE ... IN DATABASE`), both joined by `; ` when both apply; `UPGRADE`: `Prefix <prefix>.`); then `Setup fingerprint: <fingerprint>. Check that <name> shows the same fingerprint.` (`your agent` for `UPGRADE`). Then in words what the agent gets (`<agent> will be able to read … and change rows in …, up to 10 rows at a time without asking you, 11 to 50 with your passkey, never more. It cannot change your tables' structure.`; with `allTables`, the tables are the ones in those schemas the admin role owns now, listed by name, then each table left out as `not included: owned by <role>`), tables outside `public` flagged (for Supabase, `auth` and `storage` more strongly); then the row-level security question, as `basalt init` asks it (`--agent-rls`: the checklist at a terminal, one line from piped input, or the flag's list form, see [the `basalt init` command](cli.md#cli); with `--yes` or `--dry-run` and `--agent-rls=ask`, every table is answered yes and one line on stderr names them and says how to opt out); the wire stays one answer per table; then the SQL (the role's password shown as the verifier); then `Run this? [y/N]` unless `--yes`. **All or nothing (CO-16):** every requested table or none; to change the list the bot makes a new code. `--dry-run` prints and runs nothing.
6. **One transaction:** the missing migrations, the role (`CREATE ROLE ... PASSWORD '<verifier>'` for `INSTALL`, `ALTER ROLE ... PASSWORD '<verifier>'` for `AGENT` with a verifier), the grants, the confirmed agent policies, `attach`, and `basalt_meta.record_setup`. Any failure leaves the database as it was.

### Removed: the laptop setup command

`basalt init --setup-code`, which ran a setup code on the person's own computer with the admin connection string, is removed from the binary (its checks stay, in [The setup checks](#the-setup-checks)), with its flags (`--engine-url` included) and the laptop half of the setup code. Persona 2 has one setup path, the [connect page](connect.md#the-connect-page): every code `basalt init --remote` makes is run there, and `--database-url`, which made a code for the laptop command, is removed. The [setup code](#the-setup-code) format stays, for the connect page. Not yet: an agent with a credential still gets a code with `target` (the guard update and a new password need the kinds [Persona 2, planned](#the-one-setup-flow) names).

### On the engine

- **Serving while an `INSTALL` setup is pending.** An agent whose `engine.json` has a pending `INSTALL` `setup` is served degraded: `status` works, and every other tool answers `UNAVAILABLE` reason `SETUP_PENDING` (`SETUP_EXPIRED` after `expiresAt`) with the [steps](next-steps.md#next-steps-per-code), the pending `code` filled in. A pending `AGENT` or `UPGRADE` setup does not change serving; `status` reports `SETUP_CHANGE_PENDING` (except a connect-only recovery code, whose agent has no credential yet: it is served degraded as a pending `INSTALL`, [The engine and a connect-only code](#the-engine-and-a-connect-only-code)). An expired `AGENT` or `UPGRADE` setup is dropped from `engine.json`, and the problem that called for it comes back with its steps; one marked `certificateChanged` is kept, as a connect-only one is, for the collect window (the code's life plus the 30-minute hold), so its engine can still collect the certificate ([A changed certificate on persona 2](trust.md#pinning-from-the-connect-page)).
- **Finishing.** On `status`, on every call while degraded, and at each heartbeat, the engine logs in with the agent's credential (not for a connect-only code before the person confirmed its database, [The engine and a connect-only code](#the-engine-and-a-connect-only-code)) (the `.pending` one first, when there is one) and looks for the pending `setupId` in `basalt_meta.agent_setups`. Found: it moves a `.pending` credential over the credential file, clears `setup` from `engine.json`, and serves normally; `setup.state` is `DONE`. Logging in proves the role exists with the bot's password: only the bot knows it, and the verifier came from the bot. Guard version, grants and passkeys are then `status`'s usual checks (`GUARD_OUTDATED`, `PERMISSION_DENIED` on use, `NO_PASSKEY`). Details: the engine moves the `.pending` credential and writes `engine.json` (atomically, only when the agent's pending `setupId` is still the one found, never through a symlink, under `<config>.lock`, the config-wide lock every read-modify-write of `engine.json` by `basalt init` takes too) while it holds `<credentialFile>.lock`, the lock `basalt init --remote` takes; it moves `.pending` only when that path still names the file that logged in (a regular file with one link, owned by the engine's user, mode `0600`), and only when it names the same host, port, database and user as the engine's credential (a code for another database is moved over by the next `basalt init --remote`, and the engine uses it once restarted); the engine's connections then log in with the new password, with no restart. A held lock or a failed move leaves the setup pending in memory and the next call or heartbeat tries again; a config the engine cannot write is logged, and the agent is served all the same, since the database, not the file, says the setup ran.
- **Lock files.** `<config>.lock` and `<credentialFile>.lock` belong to the engine's OS user, mode `0600`, so the engine can always take them. Writers that run as root take them too and never leave one the engine cannot open: `basalt service install --agent` holds `<config>.lock` from reading `engine.json` until the new file is in place, and a lock file that a root process creates, or finds owned by root, is handed to the owner of its directory when that owner is not root (in service mode the engine's user owns the config and credential directories). A lock file the engine cannot open (permissions, owner, not a regular file) is not retried in silence: the engine logs it and `status` reports the problem `LOCK_FILE_UNUSABLE` (`WARNING`, its `personMessage` naming the file) for as long as the next try fails; a `.pending` credential is not promoted meanwhile. Its fix is a root command on the engine's machine, so it is a `PERSON` step on an agent-operated engine too.
- **The shim** reads `operatedBy` and `setup` from the engine config when the engine is down; when it cannot read the file it assumes `PERSON` and no pending setup.
- **Fingerprint in messages.** While a setup is pending, `status` returns `setup.fingerprint`, and every `personMessage` that hands the person the setup code names the fingerprint and asks them to check that the connect page shows the same.

### The engine and a connect-only code

How the engine of a [connect-only code](#connect-only-setup-codes) gets its database's address, checks it, and starts only after the person confirmed it. The connect service's side is [The address hand-off](connect.md#the-address-hand-off).

- **Serving while waiting.** While the code is pending, the agent is served degraded as for a pending `INSTALL`: `status` works, and every other tool answers `UNAVAILABLE` reason `SETUP_PENDING` (`SETUP_EXPIRED` after the collect window: the code's life plus the 30-minute hold), with the steps of [Next steps for a connect-only code](next-steps.md#next-steps-for-a-connect-only-code). `setup.connectOnly` is `true`. Until the address arrives, `status` reports `SETUP_NOT_RUN` with the message `Waiting for the setup on the connect page. If you already approved it there, open the same link again and approve once more: your bot will connect.` (the engine cannot tell a setup not run yet from an address the service lost). Once the code has expired, that report still waits through the collect window, but it does not reprint the code or the connect link, and the message is `Waiting for a setup already started on the connect page. The setup link has expired, so it cannot be opened again. If you already approved it there, your bot will connect.` After the collect window it becomes `SETUP_EXPIRED`.
- **Collecting.** The engine asks the connect service for the address (`CollectAddress`, signed with its engine key) every 15 seconds while it waits for an address or is `DATABASE_UNREACHABLE_FROM_BOT`, for the code's life plus the connect service's 30-minute hold (40 minutes after the code was made), and at once on `status` ([The reach check](connect.md#the-reach-check)). For an address in phase `PREVIEW` (the person has not approved yet; any phase but `SET_UP` counts as one) it only checks it, probes it and reports whether it reached it (`ReportReach`), shows nothing of it in `status` or the next steps, and keeps collecting: the same address collected again is reported again from its probe, without a new one; an address it reached is not probed again while it stays the same, and one it did not reach is probed again 5 minutes after its probe (such a probe got no SCRAM exchange, so it leaves no failed login on the server). On `RATE_LIMITED` it waits `retryAfterSeconds`; on `HANDOFF_UNKNOWN` it keeps waiting; on `CLOCK_SKEW` `status` reports the problem `CLOCK_SKEW` (the engine's clock is more than 5 minutes off; fix it) and the engine keeps trying. A collected address that the engine has not yet used is kept in memory only; collecting again returns the same address, so an engine that stopped in between collects again. Once a probe of a `SET_UP` address passed (below), the engine stops collecting, so the database it asks the person about cannot change under the question; it collects again only after a restart, which asks again. It drops a collected address as soon as `engine.json` no longer records that pending setup (after a new code; it reads the config on every call and heartbeat). The shim's `status` while the engine is down collects once, as the engine would, only in same-user mode and never as root, where the CLI runs as the engine's user and reads its key; it never reads `.secret` and never confirms. It shares the engine's probe cache (`connect-probe.json` in the state directory, `0600`: a hash of the address, never the address, the IP, the time, the result and the `RATE_LIMITED` wait), so a reached `PREVIEW` address is probed once whichever process collects it; it never probes a `SET_UP` address, which waits for the engine (`ENGINE_UNREACHABLE` comes first) unless a passed `PREVIEW` probe of it may be reused, and then shows `CONFIRM_DATABASE` for the engine to ask. In service mode the shim's `status`, and the shim in every mode, report the pending setup from `engine.json` without collecting, and `ENGINE_UNREACHABLE` says the engine must be running.
- **An engine started as root.** An engine started as root never collects: root trusts nothing the agent's OS user could redirect, and a YES writes that user's credential. It serves the waiting agent degraded, `status` reporting the problem `ENGINE_AS_ROOT` (restart the engine as the engine's user, the owner of its state directory), touches none of that agent's files, and serves its other agents as usual.
- **Checking the address itself.** The engine trusts the service's address no further than its shape. It accepts only a host name of letters, digits, `.` and `-` (at most 253 characters), a port from 1 to 65535, a database name of `[A-Za-z0-9_.-]` up to 63 characters, and a Supabase ref of 20 lowercase letters and digits, given only with a host that names that project (`db.<ref>.supabase.co`) or Supabase's pooler (`*.pooler.supabase.com`, where the agent logs in as `<role>.<ref>`), since the ref is what the person is asked about; anything else is the problem `ADDRESS_INVALID` and nothing of it is shown, since whoever ran the setup chose it and it would land in the agent's context. It then checks the connection string it would log in with: the host, port and database come from the URL itself (a `host`, `hostaddr`, `port` or `dbname` parameter is refused), and the database that string names, read as init reads it, must be the address itself, so a Supabase project's own host (`db.<ref>.supabase.co`) comes with its ref. It resolves the host once, uses only global unicast addresses with the same refused ranges as [Where the runner connects](connect.md#where-the-runner-connects) (a refused address is also `ADDRESS_INVALID`), and connects to that address with the host name kept for TLS. It ignores any TLS mode from the service and requires `sslmode=verify-full`.
- **The probe, with a wrong password.** A server that holds the agent's verifier recovers its `ClientKey` from one real login ([The setup code](#the-setup-code), `verifier`), and the database the engine was handed may be someone else's. So after collecting, the engine only probes, as init does in step 2: logins bound to fail, with a random password, that prove the server is reachable and its certificate verifies for the host name (against the system's authorities, and the roots of the trust profile that matches the host: [Trust profiles](trust.md#trust-profiles)), and whether channel binding works. It never sends the agent's real SCRAM proof before the person confirmed the database. The probe of a `SET_UP` address reuses a passed `PREVIEW` probe only for the same address and the same resolved IP address within 5 minutes, so one flow leaves at most two probes' failed logins in the server's log. When no address of the server answers, `status` reports `DATABASE_UNREACHABLE_FROM_BOT`, naming the database, with the fix in its message: for Supabase, paste the pooler connection string on the page; otherwise allow the bot's machine in the database's firewall. The setup already ran, so the person runs the same link again with a string the bot can reach ([The address hand-off](connect.md#the-address-hand-off), running again), or opens the firewall; the engine keeps collecting, and probes again when the address changes, on every `status` and at the heartbeat.
- **Confirming the database.** After a probe that passed, `setup.state` is `CONFIRM_DATABASE` and `setup.database` names the database. `status` reports the problem `CONFIRM_DATABASE`: the agent asks the person `The setup points me at <Supabase project <ref>, database <db> | <host>:<port>, database <db>>. Is that your database?` and calls [`confirm_database`](mcp-tools.md#mcp-tools) with their answer and the database it named; a `setupId` or database other than the one waiting is refused, so an answer never confirms a database the person was not asked about. Every other tool answers `UNAVAILABLE` reason `DATABASE_NOT_CONFIRMED` until then. `confirm_database` called in any other state answers `INVALID_ARGUMENT`. The steps are A `ASK_PERSON`, A `END_TURN`, then A `CALL_TOOL` of `confirm_database` once the person answered: the engine fills in `setupId` and `database`, never `answer`, which the agent sets from the person's words. The engine never logs in to, or serves, a database the person did not confirm.
  - **Yes.** The engine writes the credential file as init does in step 2 (the role, or `<role>.<ref>` through Supabase's pooler, the address, `sslmode=verify-full`, and `channel_binding=require` when the probe showed it works), under the same locks and ownership rules, removes `.secret`, clears `awaitingAddress`, logs in, and looks for its `setupId` as in [On the engine](#on-the-engine). Found: `DONE`. Not found: the problem `SETUP_NOT_FOUND`, naming the database, and the tools answer `UNAVAILABLE` reason `SETUP_PENDING`. A first login that fails is the usual `status` problem for it (`CREDENTIAL_REJECTED`, `DATABASE_UNREACHABLE`), as for any agent with a credential file.
  - **No.** The engine deletes `.secret` and the collected address, having never logged in there, and replaces `awaitingAddress` with `"refused": true` in the pending `setup` of `engine.json`. While `refused` is set, the engine, and the shim when the engine is down, report `setup.state` `REFUSED` and the problem `DATABASE_REFUSED`, never collect, and never try to log in; the tools answer `UNAVAILABLE` reason `SETUP_PENDING`. The next `basalt init --remote` sees `refused` and makes a [recovery code](#connect-only-setup-codes).

### Controls

What stops a setup code being used against the person (design section 10):

- **Another agent's role.** `INSTALL` never touches an existing role (`ROLE_EXISTS`, and `CREATE ROLE` in Postgres), except, on the local setup page, a role of this guard's agents group that a reset setup left ([What `run` does](setup-page.md#the-local-setup-page)); a code that sets an existing role's password says so in the summary, naming the agent and role.
- **Old or forged-time codes.** Expiry is refused on open and when confirming the code, by the person's clock and by the connect service (no skew: a code is expired from `expiresAt` on). A `setupId` in the future and an `expiresAt` more than 10 minutes plus 5 minutes of clock skew ahead are refused by the person's clock, the connect service and the database; single use and order are enforced by `record_setup`.
- **A substitute code** posted in the chat by someone else, with their own verifier: the fingerprint shown on the person's computer must match the one their agent reports (`status`, `personMessage`).
- **Wrong database**: target mismatch is refused (CO-17). Planned: not for a connect-only code, which has no target; there the page names the pasted database before approval, the connect service refuses a second database while it holds the first (`RUN_ELSEWHERE`), and the engine logs in only after the person confirmed the database it collected ([On the engine](#on-the-engine)). **Wrong prefix**: refused (`PREFIX_MISMATCH`).
- **The admin credential** is used only on the person's computer (CO-9); the SQL comes from the person's own `basalt` binary, never from the code. Planned: with the [connect link](connect.md#connect) the person chooses instead to hand it, for one setup, to the hosted connect service, whose SQL comes from the same public setup package at the engine version it pins, plus the grants of the tables the person left ticked and the column labels they set ([Tables on the connect page](connect.md#tables-on-the-connect-page), [Column labels on the connect page](connect.md#column-labels-on-the-connect-page)); [What the connect service sees](connect.md#what-the-connect-service-sees) says what that trusts.
- **Someone else has the link** of a connect-only code (planned): whoever runs it first, with any database they own, sends the bot there. The engine sends no real login there before the person confirms, so they learn nothing that logs in as the agent elsewhere, and the person, who did not paste that database, says no. The confirmation stops a leaked log or a forwarded link, not someone in the same chat: a member of a group chat with the bot sees the link and can also answer yes. In a group chat the setup is only as safe as its members. Planned: before anyone approves, the bot also probes, without logging in, the address of any database pasted on the page, and that server sees the bot's outbound address; someone else with the link can cause that, and can make the person's reach check read "couldn't check" ([The reach check](connect.md#the-reach-check)).
- **An agent running `basalt`** with the admin credential: refused under an agent marker ([Agents and the admin credential](#agents-and-the-admin-credential)), within the limit stated there.
