### Transports

The contract is the messages, defined once; a **transport** is an adapter that carries them. The engine and the hooks do not know which transport is in use, and adding a transport is an adapter compiled into the engine, with no change to the hooks or existing plugins. v1 has two:

- **JSON-RPC 2.0**, newline-delimited JSON, one message per line: `jsonrpc-stdio` (the plugin reads requests on stdin and answers on stdout) and `jsonrpc-unix` (the plugin accepts connections on a Unix socket it is handed at start; the engine connects as the client). A local socket plugin, `jsonrpc-unix` or local `connectrpc`, is handed its socket as the one environment variable it starts with, `BASALT_PLUGIN_SOCKET`, the socket's absolute path; the engine connects once the socket appears. In same-user mode the socket's directory is new for each start: made by the engine's user under the OS temporary directory, mode `0700`, holding only the socket, never a directory the plugin's files live in, and removed when the plugin stops. The temporary directory and every directory above it must be owned by root or the engine's user and writable by no one else, as for the [path rule](plugins.md#signing-and-the-trust-store), with one exception: a directory root owns with the sticky bit set, such as a stock `/tmp`, may be writable by group or others, since no other user can rename or remove an entry of the engine's there. A world-writable directory that root does not own, or that has no sticky bit, is refused, symlinks on the way are followed only when root owns them, and then no socket plugin starts and the error says to set `TMPDIR` to a directory only that user can write. The socket directory's name ends in 64 random bits; it is made in the temporary directory opened without following a link, and anything already at that name (a directory, a file or a symlink) fails the start and is left as it is. The directory made is then opened without following a link and must be the engine user's, mode `0700` exactly, with no ACL entry that allows access (one the temporary directory passes on to new directories, on macOS) and empty, or it is removed and the start fails. **After a crash.** A same-user engine records each local plugin process it starts (its pid, the process's start time, its socket directory, and the engine's own pid and start time) in `<stateDir>/plugin-runs/` until the plugin stops, and refuses to start a plugin it cannot record. At its next start, holding its lock and before it starts any plugin, it reads those records, leaving alone a record whose engine still runs: it kills the process group of a recorded plugin that still runs, only when that pid's start time is the one recorded (so a pid the OS has given to another process is never touched), removes a recorded socket directory that holds nothing but its socket, and drops the record; a record it cannot read is dropped without acting on it. A plugin whose own process has exited while something it started runs on is not found this way. A health check records nothing. A socket path longer than the OS takes (103 bytes on macOS, 107 on Linux) is refused before the plugin starts, naming the limit. In same-user mode every local plugin starts in its own process group, with its installed copy as its working directory and no environment but that variable (a `jsonrpc-stdio` plugin gets none). A plugin must not write there: a file it adds or changes in its copy fails the next verification, and the entry is not started again; stopping it kills the whole group, so nothing it started outlives it. In service mode the plugin's unit starts it, sets the same variable, and the socket's directory stays between starts ([Service units](#service-units)): a plugin removes a socket left at that path by its last run before it listens (the Go SDK does) and must not change the socket's mode (on Linux the unit refuses `chmod`, and the directory already keeps others out), and every local plugin listens there, a `jsonrpc-stdio` one included, since no service manager holds its standard input for the engine (the Go SDK switches to `jsonrpc-unix` on its own when the variable is set and no transport is forced). A plugin that only speaks on stdio is not reached in service mode and stays `PLUGIN_UNAVAILABLE`. Methods are the message names (`initialize`, `health`, `shutdown`) and each hook's methods.
- **ConnectRPC** (`connectrpc`), over HTTP: Connect, gRPC and gRPC-Web, so a plain gRPC server works. Local (over a Unix socket) or remote. The service is `basalt.plugin.v1.PluginService` in `plugin.proto`, where each message has the same fields as its JSON schema, in snake_case.

**Remote endpoints.** TLS is always required: an `http://` URL is refused. The engine verifies the server's certificate against the URL's host, and refuses a certificate valid for any other host. The URL's host and port must be in the manifest's `egress`. Redirects are not followed, and proxy environment variables are not used: the engine connects to that host and port only. A refused endpoint is never started, and the error names the entry and the endpoint's host. The engine connects once to check the certificate before its first call, and calls with the gRPC protocol (binary protobuf over HTTP/2), which ConnectRPC and plain gRPC servers both accept.

**Local ConnectRPC.** A local `connectrpc` plugin serves on a Unix socket it is handed at start, as for `jsonrpc-unix`. The engine calls it with the same gRPC protocol over HTTP/2 without TLS (prior knowledge), so a plain gRPC server works. There is no TLS, credential file or egress check: the socket's ownership and mode are the protection. The engine connects to that socket path only (never TCP, no proxy, no redirects, no `Authorization` header) and, each time it opens a connection, refuses a path that is not itself a socket (a symbolic link to one included). Messages, size limits and failure classes are the same as for a remote endpoint.

### Protocol

Every plugin answers three messages, whatever its hooks ([`api/plugin/protocol/`](../api/plugin/protocol/)):

- **`initialize`**, the first call on every connection. The engine sends `{protocols, hooks, config, limits}`: the protocol versions it speaks, the hooks it will call (the manifest's), the entry's `config` (`{}` when none) and `limits` (`maxMessageBytes` 4,194,304, `maxInFlight` 4, the entry's `timeoutMs`). The plugin answers `{protocol, name, version, hooks, model?}`: one offered protocol, and its name, version and hooks exactly as in the installed manifest. Any difference refuses the plugin.
- **`health`**, every 30 seconds while the plugin runs: `{status: READY | NOT_READY}`. A plugin that answers `NOT_READY` takes no hook call (`UNAVAILABLE`) until a later `health` answers `READY`; it is not restarted.
- **`shutdown`**, when the engine stops or the entry is disabled. The engine first stops sending the entry new calls and lets the ones in flight finish, then sends `shutdown` and lets a local plugin exit on its own. It kills a local plugin's process group once the plugin has exited, when `shutdown` fails or is not answered within the entry's `timeoutMs`, and at the latest 5 seconds after it began stopping the entry. In service mode the engine runs no plugin process: it closes its connection instead, and the service manager starts the plugin again to wait for the next one. The engine stops all its plugins at once, so it stops within 5 seconds whatever they do.

Limits: a message in either direction is at most 4 MiB, checked before it is decoded. At most 4 hook calls are open per entry (`maxInFlight` counts hook calls only); a fifth waits for a free one until its own deadline, then fails `TIMEOUT`. `health` and `shutdown` are outside that cap: each has one slot of its own, so the engine may send one of each while four hook calls are open, and a plugin must answer them then (the Go SDK does). A busy plugin is never restarted, or killed before its `shutdown`, only because its hook calls fill the cap. Each call's deadline is the entry's `timeoutMs`. Unknown fields in a message are ignored; a breaking change is a new `basalt-plugin/<major>`.

### Notifier messages

Served: the Go SDK ([`basalt-plugin-go`](https://github.com/BasaltDBHq/basalt-plugin-go), a module of its own that holds a copy of these messages) serves both hooks, and the engine calls `feed.observe` and `approval.deliver` while it serves agents, as this section says. This section fixes their bytes, so the engine, the Go SDK and every notifier plugin build on the same messages. Schemas: [`protocol/feed.schema.json`](../api/plugin/protocol/feed.schema.json) and [`protocol/deliver.schema.json`](../api/plugin/protocol/deliver.schema.json); samples: `api/plugin/testdata/valid-feed-*.json` and `valid-deliver-*.json`, with invalid ones beside them; the ConnectRPC mapping in [`plugin.proto`](../api/plugin/proto/basalt/plugin/v1/plugin.proto). The contract test checks every sample, that the batch is one agent's in ascending `seq` with `id` and `source` built as below, that no sample carries a value, a statement, an intent, a refusal message or a passkey, and that every type name and fixed sentence of the schemas is written here.

Both messages carry CloudEvents ([Wire format](../CONTRACT.md#wire-format)). The two kinds share the envelope and differ in what a plugin may do with them, and their `type` names tell them apart. A **feed event** is durable: it can be replayed from the cursor and holds no values, so it is safe to store or forward. A **notice** is one-shot: it is not replayed, it expires, and its link lets a reader see the request.

#### The envelope

Every event is one CloudEvents 1.0 event in its JSON form, with these attributes and no other:

| Attribute | Feed event | Notice |
|---|---|---|
| `specversion` | `1.0` | `1.0` |
| `id` | `<installId>:<seq>` (`0193a0f2-5b7e-7c41-9d2a-6e1f00c0ffee:4211`); for the skipped marker `<installId>:skipped:<afterSeq>:<seq>` | A UUIDv7 the engine makes once, when it makes the notice, and keeps on every try of it |
| `source` | `urn:uuid:<installId>` | `urn:uuid:<installId>` |
| `type` | One per ledger kind, below | One per notice kind, below |
| `time` | The ledger row's `at`; absent on the skipped marker | When the engine made the notice: the moment the agent's answer was built |
| `subject` | The agent, `agent:<name>` ([Agent names](stores.md#agent-names)), as `data.agent` | The agent, `agent:<name>`, as `data.agent` |
| `datacontenttype` | `application/json` | `application/json` |
| `data` | The event's fields, below, as a JSON object | The notice's fields, below, as a JSON object |

- **The install id** is `basalt_meta.install_id()` of the agent's database ([Schema version 2](basalt-meta-schema-versions.md#schema-version-2-install-ids)), read with the agent's credential: one per guard install, shared by every agent of that database. Sequence numbers are the database's one chain, shared by its agents, so one agent's events skip the `seq` of other agents' rows, and a new install begins them again. An agent whose guard reports no install id gets no feed events and no notices; each notice for it counts as dropped.
- **`source` and `id`.** CloudEvents lets a consumer treat two events with the same `source` and `id` as one. A feed event's pair is built from the install id and `seq` only, so a redelivery after a crash, a restart or a failed call has exactly the same pair, through a broker as well. `source` names the database's guard install, not the engine: an engine's id changes when the engine is set up again and does not exist while its key file is unusable, and a `source` that changes would break that dedup. Two entries that receive the same row receive the same event, with the same `id`. Known limit: a database copied with `basalt_meta` in it (a template, a restored dump) keeps the install id, so two copies that go on writing can emit different events with the same `source` and `id`; give each copy that goes on serving agents its own guard install.
- **Types** are reverse-DNS names under `dev.basaltdb.`, the prefix the engine already uses for itself (its launchd labels). Nothing the open-source engine emits is named after the Vault: the Vault's domain is reserved for events the Vault may one day emit itself (the portal's URLs inside a notice's link are page addresses, not names). Each type names what happened, not the hook that carries it, so it still reads right on a broker or a webhook; the one feed-only event is the skipped marker. The notices' names (`requested`, `replaced`) are not names any feed event uses, so a consumer never mistakes a notice, which carries a link, for a feed event, which never does. One type per kind (owner decision, Nov 19):

| `type` | What happened | Message |
|---|---|---|
| `dev.basaltdb.write.applied` | A write was applied | `feed/1` |
| `dev.basaltdb.write.refused` | A write was refused | `feed/1` |
| `dev.basaltdb.write.held` | A write was held for the person's approval | `feed/1` |
| `dev.basaltdb.approval.signed` | The person signed a held write | `feed/1` |
| `dev.basaltdb.revert.prepared` | A revert was prepared for the person to sign | `feed/1` |
| `dev.basaltdb.revert.signed` | The person signed a large revert's plan, which the agent then applies in batches | `feed/1` |
| `dev.basaltdb.revert.applied` | A revert was applied | `feed/1` |
| `dev.basaltdb.revert.rejected` | The person rejected a revert | `feed/1` |
| `dev.basaltdb.feed.skipped` | The skipped-ahead marker | `feed/1` |
| `dev.basaltdb.approval.requested` | The engine held a write: an approval was requested | `deliver/1` |
| `dev.basaltdb.revert.requested` | The engine prepared a revert: a revert was requested | `deliver/1` |
| `dev.basaltdb.link.replaced` | The agent asked for a new link for a held write or a revert: a link was replaced | `deliver/1` |

- **Versions.** These names and fields are those of `feed/1` and `deliver/1`. A later minor version may add a field to `data`, which a plugin ignores as it ignores any unknown field ([Protocol](#protocol)); a breaking change is a new contract (`feed/2`) with new type names. One exception, before the first release (clean state): `feed/1` is amended in place to the store-neutral form below (`agent:<name>`, `resource`, `store`), `deliver/1` likewise names the agent `agent:<name>`, and the Go SDK ships its copy of the messages in the same change. The schemas list today's fields and close `data`, so a sample with a field this contract does not name fails.

#### `feed.observe` (`feed/1`)

- **The call.** JSON-RPC method `feed.observe`, params `{ "agent", "events" }`: `agent` is the agent, `agent:<name>` with `<name>` its name in `engine.json` ([Agent names](stores.md#agent-names)), and `events` is a CloudEvents JSON batch (`application/cloudevents-batch+json`) of 1 to 100 of that agent's events in ascending `seq`. ConnectRPC: `basalt.plugin.v1.PluginService/FeedObserve`, where `events` is the batch's exact JSON bytes.
- **The answer.** `{ "lastSeq" }`: the `seq` of the last event the plugin handled, which must be the `data.seq` of one event of the batch. A plugin that handled only the first events answers the last of those, and the engine sends the rest again next. Any other answer (a `seq` not in the batch, none, an error) is a failed call (`BAD_RESPONSE`, or the class of the failure) and moves nothing.
- **At least once, in order.** The engine moves the cursor only on an answer, so a plugin may get an event again after a crash, a restart or a failed call; it dedups by `source` and `id`. At most one `feed.observe` call is open per entry and agent, so one agent's events arrive in chain order; calls for different agents of one entry may overlap, within the entry's 4 call slots, of which the engine keeps one for notices: at most 3 `feed.observe` calls of one entry are open at once.
- **Through the agent's own access.** The engine reads `agent_ledger` with the agent's credential, after the cursor, only the kinds below, while the entry is served to that agent.

**Which ledger rows are events.** What an agent did to data, and what happened to its approvals and reverts: one event per action, never one per row. Each event's `data` holds `installId`, `seq` and `agent` (`agent:<name>`, as in the params), and the fields below, each present only when the ledger row itself holds it at that `seq`. Nothing comes from a change's current status, which can differ between two deliveries of the same `seq`.

| Ledger kind | `type` | `data` besides `installId`, `seq`, `agent` |
|---|---|---|
| `CHANGE` whose detail `status` is `APPLIED` | `dev.basaltdb.write.applied` | `changeId`; `runId` and `taskId` when it ran in a run and task; `op` (`INSERT`, `UPDATE`, `DELETE`) and `store` (`{kind, verb}`); `resource`, the request's own resource, when it changed a row; `rows` (rows written, cascades included) and `cascadedRows` |
| `REFUSED` whose `op` is not `READ` | `dev.basaltdb.write.refused` | `changeId`; `runId`, `taskId` when present; `op` (`INSERT`, `UPDATE`, `DELETE`, `OTHER`) and `store` (`{kind, verb}`, `verb` only when the request parsed); `reasonCode`, the refusal's error code, when it is one of [Error codes](error-codes.md#error-codes) |
| `APPROVAL_PENDING` | `dev.basaltdb.write.held` | `changeId` (the held change), `approvalId`, `runId`; `taskId` when present; `op` (the request's own resource's) and `store` (`{kind, verb}`), `rows` (the rows it changes, cascades included), `expiresAt` |
| `APPROVED` | `dev.basaltdb.approval.signed` | `changeId` (the held change), `approvalId` |
| `REVERT_PENDING` | `dev.basaltdb.revert.prepared` | `revertId` |
| `REVERT_SIGNED` | `dev.basaltdb.revert.signed` | `changeId` (the revert's own change), `revertId` |
| `REVERTED` | `dev.basaltdb.revert.applied` | `changeId` (the revert's own change), `revertId` |
| `REVERT_REJECTED` | `dev.basaltdb.revert.rejected` | `revertId` |

- **Not events.** Reads (the `READ` ledger kind, and a `REFUSED` whose `op` is `READ`: one per query, too many to be a notice), the rows of a write (`ROW_CHANGE`: its `CHANGE` is the event), a `CHANGE` whose status is `PREVIEW` (the person's reveal re-runs a held write as a preview), the steps inside one revert (`REVERT_BATCH`, `REVERT_RESCOPED`, `REVERT_RESET`: its prepared, signed, applied or rejected event is the one), and everything about the engine itself: `RUN_STARTED`, `PRUNED`, `HEARTBEAT`, `DEAD_MAN`, `UNCOVERED_TABLES`, `AGENT_POLICY_ADDED`, `AGENT_SETUP`, `ENGINE_RECORDED`, `ENGINE_REVOKED`, `PIN_SET_ASIDE`, `TRUST_PIN_RECORDED`, `PASSKEY_REVOKED`, `ROWS_REVEALED`, every `PLUGIN_*` kind (plugin events and plugin approvals). A held write or a revert that expires writes no ledger row (its expiry is a status the guard reads, not an entry), so expiry is not an event: a plugin that needs it compares `expiresAt` with the clock. A kind added to the ledger later is not an event until this table names it.
- **`resource` is the store's text.** An agent may name what it creates (in Postgres, an agent with `CREATE` names its tables), so a plugin that shows `resource` treats it as untrusted plain text, never as markup or a link (the notice's headline does this for it). The engine replaces a control character in it with U+FFFD.
- **Left out of every event**, though some rows hold them: `intent`, `statement`, `params`, a refusal's `reason`, `rowsHash`, row keys and images, a passkey's `credentialId`, the role that relayed a signature (`relayedBy`, which can name another agent), a revert's selections (`select`, `oldSelect`, `droppedSelect`), `binding`, the skipped lines of a revert, and a rejection's `note`. `chainVerified` has no source in a ledger row and is not sent; `reasonCode` is the `code` a `REFUSED` row holds. `APPROVAL_PENDING` holds no resource, so `write.held` names none.
- **A revert's events carry its ids only.** `agent_ledger` shows an agent a revert row with only `revertId` once the person widens that revert ([Revert scope objects](basalt-meta-revert.md#revert-scope-objects)), and a revert can be widened after its row was written, so any other field could read differently at a redelivery of the same `seq`. Its row counts reach the person in the notice.
- **The skipped-ahead marker.** The ledger keeps rows one year. When retention deleted rows after the cursor before they were delivered (a plugin down that long), the next call starts with one `dev.basaltdb.feed.skipped` event, with no `time`, whose `data` holds `installId`, `agent`, `afterSeq` (the cursor) and `seq`: the `seq` just before the agent's oldest row after the cursor that remains, or the chain head when none remains. The agent's events with `afterSeq < seq ≤ data.seq` may have been deleted; how many, if any, is not known. The plugin acknowledges it like any event, which moves the cursor to its `seq`. The engine tells with the agent's own access: `check_head(<cursor seq>, …)` answers true exactly when retention deleted that `seq` (it lies before the chain's anchor), whatever hash it is given, and agent roles may call it; other agents' rows are no gap.

#### The cursor

- **One per entry and agent**, keyed by the plugin's `(name, instance)`, the agent and its database's install id, in `<stateDir>/plugin-cursors/<name>/<instance>/<agent>.json` (`{ "installId", "seq" }`, mode `0600`, owned by the engine's OS user, written atomically after each answer that moves it). It survives a plugin crash and an engine restart: the events wait in the ledger, never in memory. Two entries share no cursor ([Per-agent scope](plugins.md#per-agent-scope)).
- **It starts at the ledger's head** in each of these cases, and the first event sent is the first after it:
  - the entry begins to be served to that agent after not being served: the agent's ledger holds a `PLUGIN_ENABLED` of the entry after the cursor (a first approval, an approval signed again after it ended, an agent added back, an entry turned on again), or a `PLUGIN_CHANGED` after the cursor that adds an egress host or moves the endpoint. The cursor starts at that record's `seq`, the head when the engine began serving it, so a plugin is never handed events from a time it was not approved for that agent. A `PLUGIN_ENABLED` written again because retention deleted the earlier record does the same;
  - the cursor's install id is not the database's now: the guard was installed afresh and sequence numbers began again. It starts at the `PLUGIN_ENABLED` the engine wrote in the new ledger;
  - there is no cursor yet, or its file cannot be read (it is replaced): the chain head (`chain_head()`) when the engine first reads for that agent.
- **It moves only on an answer**, to the answer's `lastSeq`.

#### `approval.deliver` (`deliver/1`)

- **The call.** JSON-RPC method `approval.deliver`, params `{ "agent", "event" }`: the agent, `agent:<name>` as in `feed/1` ([Agent names](stores.md#agent-names)), and one notice, a CloudEvent in its JSON form. ConnectRPC: `basalt.plugin.v1.PluginService/ApprovalDeliver`, where `event` is the event's exact JSON bytes.
- **The answer** is `{}`. The notice gives the plugin no power over the action: approving and signing still need the person's passkey, checked in the store, and the signed code returns as without plugins (the page's relay, or pasted to the agent).
- **When a notice is sent**: three moments, each for a listed agent, each with the link of that answer:

| Moment | `kind` | Its link |
|---|---|---|
| `write` holds a write | `APPROVAL_REQUESTED` | `approval.approvalUrl` of the `APPROVAL_REQUIRED` answer the engine built for that held write |
| `request_revert` prepares a revert | `REVERT_REQUESTED` | `revertUrl` of that answer |
| The agent asks for a new link and the engine issues one: `list_pending` with `reissueLink: true` (one notice per item it issued a link for), or `request_revert` with `revertId` and `reissueLink: true` | `LINK_REPLACED` | The new `approvalUrl` or `revertUrl` |

- **A held write is noticed when it is held.** The notice is made once the engine has held the write and built its `APPROVAL_REQUIRED` answer, with that answer's link. A new `write` with `waitForApproval` that is held keeps its call open ([Approvals](approvals.md#approvals)): its notice is made at the hold too, while the call still waits, so the person hears of it at once and not up to 110 seconds later. The agent has no link yet at that moment. When the wait runs out, the call answers `APPROVAL_REQUIRED` with the same link, byte for byte; when the person signs first (through the notice's link), the call answers `APPLIED` and the agent never gets a link. Either way the held write is noticed once: the call's answer sends no second notice. Every other notice is made when the answer that carries its link is returned to the agent, never before. A `list_pending` that fails sends no notice for any of its items.
- **Only a link that was issued is a replaced link.** An engine that hands over long links (no pages served, no portal short link) issues nothing on `reissueLink`: the same link is restated, the earlier one still works, and no notice is sent.
- **Which entries get it.** Each `approval.deliver` entry the engine serves to that agent at that moment. An entry not served to the agent then (withheld, turned off, not started, or another agent's) gets nothing, and nothing is counted as dropped for it.

- **Nothing else sends one.** Not a wait or a list that issues no link, a refusal that restates one, or a widen on the signing page. Not `revert_plan`. Known limit, accepted: reading a large revert's plan with `revert_plan` issues a fresh short link each time, which replaces the one a notice delivered; that page then says the link was replaced, and the person asks the agent.
- **A request too large for any link** (`REQUEST_TOO_LARGE`): a held write, and a revert `request_revert` prepared and then answered with that error, are noticed with no link.
- **With no passkey registered** (`NO_PASSKEY`) the notice is sent as usual, with the answer's link: the agent's answer tells the person to register a passkey first, and the notice does not repeat it.
- **The engine never issues a link for a notice.** Issuing a short link revokes the item's earlier one ([Link secrets](local-pages.md#link-secrets)), which would kill the agent's link. The notice reuses the link of the answer, at the moment the answer is built; for a held write whose call waits, that is the answer built at the hold, which the call returns unchanged if the wait runs out.

**What a notice's `data` holds:**

| Field | Value |
|---|---|
| `kind` | `APPROVAL_REQUESTED` (a held write), `REVERT_REQUESTED` (a prepared revert) or `LINK_REPLACED` (a replaced link: the earlier link no longer works) |
| `agent` | The agent, `agent:<name>` with `<name>` its name in `engine.json` |
| `approvalId` or `revertId` | The held write's approval id, or the revert's id: exactly one |
| `headline` | The item in one line (below) |
| `expiresAt` | When the item expires: RFC 3339 UTC |
| `link` | Present only when the agent's answer handed over a link that stands alone (below) |
| `linkOpens` | With `link` only: `ANYWHERE` or `ENGINE_COMPUTER` (below) |
| `instruction` | What the person does: one of six fixed sentences (below) |

- **The headline** is built by the engine from the operation, the target and the row count, never a value, a statement or the intent. The engine builds it with the same text as the item's `headline` in the agent's `APPROVAL_REQUIRED` answer and `list_pending` item (held write) or the revert's headline in `list_pending` (revert), then applies the rule for "Text from the agent or the database" of [Links in `personMessage`](showing-links.md#links-in-personmessage) to the whole of it: one line, no control or format character (bidirectional controls and zero-width characters included), lookalike slashes and dots folded, no scheme separator, a dot between two labels of a host name as a middle dot (`public.leads` shows as `public·leads`). So a table an agent named like a link never reads as one beside the notice's real link. A headline over 1,000 characters is then cut to 999 and ends with `…`. A plugin shows it as plain text; it does not parse it.
  - A held write: for each table and operation of the statement's own rows, in the order of its preview lines, `<verb> <n> row` or `<verb> <n> rows` and ` in <table>`, with the verb `insert`, `update` or `delete`, joined by `, ` and the first letter capitalized; then, when rows change by cascade, ` + <m> cascaded row` or ` cascaded rows` and ` (<entries>)`, each entry `<table> <k>`, followed by ` inserted`, ` updated` or ` deleted` when its operation is not the statement's first, most rows first, then by table and operation, joined by `, ` (with no rows of its own: the cascade part alone, capitalized). ` [values hidden]` follows a group whose rows the agent cannot read. A held write always has rows of its own (the guard holds none without). For example, after the rule above, `Update 27 rows in public·leads`, or `Delete 1 row in public·customers + 30 cascaded rows (public·invoices 28, public·payments 2 [values hidden])`.
  - A revert: `Revert of <scope> <scopeId>`, then, when it has filters, `, only ` and its filters joined by ` and ` (`<n> of its runs`, `table <table>`, or `tables <table> and <k> more`, the table already in that message form and cut to 32 characters, ending with `...` when longer), then `: <n> rows to restore, <m> left as they are (changed after the agent).`, the scope as `change`, `run` or `task`. For example `Revert of run 0193a1b2-7c4d-7e8f-9a0b-1c2d3e4f5a6b: 27 rows to restore, 0 left as they are (changed after the agent).`
  - A replaced link: the item's headline as above.
- **The link** is exactly the link in the agent's own answer for that item, byte for byte: the short link (`#s=`) when the engine handed one over, else the long link (`#2.`) within the link budget ([The link budget](showing-links.md#the-link-budget)). When the answer has no link that stands alone, the notice has no `link`, and its `instruction` says to ask the agent: a hash link (`#h=`), whose request travels beside it as a file or text blocks; a request too large for any link this engine has (`REQUEST_TOO_LARGE`), whose answer gives only the page's address.
- **The link is the one stated exception** to "never a value, a statement or an intent". A short link carries only a secret that opens the page. A long link carries the whole request in it: the statement, its parameters, the intent and the affected rows, values included. The approval does not know in advance which kind of link an item will get, so the consent text and the plugin approval page say it for every `approval.deliver` plugin, always. Every other field of a notice stays free of them. **A plugin that forwards notices to a message broker puts that link into the broker's log**, readable by whoever can read that log, for as long as it keeps it.
- **Where the link opens**, from its origin ([Page origins](page-links.md#page-origins)): `ANYWHERE` for `https://portal.basaltvault.app`, and `ENGINE_COMPUTER` for `http://localhost:<port>`: the engine's local pages, which open only on the computer Basalt runs on, so a channel's plugin can word it.
- **The instruction**, chosen by the item and the link, word for word:

| Item | `ANYWHERE` | `ENGINE_COMPUTER` | No link |
|---|---|---|---|
| Held write | "Open the link to review the held write and approve it with your passkey." | "Open the link on the computer Basalt runs on to review the held write and approve it with your passkey." | "Ask the agent for the link to review the held write and approve it with your passkey." |
| Revert | "Open the link to review the revert and sign it with your passkey." | "Open the link on the computer Basalt runs on to review the revert and sign it with your passkey." | "Ask the agent for the link to review the revert and sign it with your passkey." |

- **What never reaches a notifier**, restating [What a plugin never receives](plugins.md#what-a-plugin-never-receives) for these hooks: outside the notice's link, row values and keys, statements, intents and refusal messages; in any form, the name or data of an agent the entry does not list, and anything about plugins or passkeys.

#### Limits and numbers

- **Nothing blocks.** No agent call, write, approval or revert waits on a notifier, in any failure mode, and no setting changes that. A plugin that is down, slow or crashing costs the agent nothing: its answer carried the link all along.
- **Feed.** At most 100 events per call. The engine reads each served agent's ledger for each `feed.observe` entry every 5 seconds while the entry is ready, and sends what it finds. After a failed call (an error, the entry's `timeoutMs`, a bad answer, the entry not ready) it waits 5 seconds before the next, doubling up to 60 seconds, and back to 5 seconds after an answer; the cursor does not move meanwhile.
- **Notices.** Best effort and never stored: held in memory only, so an engine that stops drops the notices still waiting. Each is tried at most 4 times, at once and 5, 20 and 60 seconds after it was made, each try within the entry's `timeoutMs`; a try when the entry is not ready to take it (not running, `NOT_READY`, or no longer served to that agent since the notice was made) fails. After the fourth failed try it is dropped. A notice is never sent at or after its `expiresAt`: then it is dropped. At most 100 notices wait per entry; a notice made while 100 wait is dropped. Notices for one entry are not promised in order.
- **Notices and the feed.** Notices wait apart from feed batches: a full feed queue never drops a notice, a waiting notice is sent before a waiting batch, and one of the entry's 4 call slots takes only notices, so feed calls that hang never hold up a notice.
- **Dropped notices** are counted per agent and entry and shown in `status` (`PLUGIN_NOTICES_DROPPED`, [Problems and errors](plugins-ledger.md#problems-and-errors)) as a number and the entry, never what they were about, while a notice was dropped in the last 24 hours. The count is kept in memory, so it starts again when the engine starts. A dropped notice is not an error for the agent, and it is logged with the entry, the agent and a fixed reason only.

#### The notifier samples

For each notifier hook there is one fixed sample, which the SDK's tests send (`basalt plugin check`, which sent it to an installed plugin, is gone; health is in `status`): for `feed.observe` the batch of [`valid-feed-request-check-sample.json`](../api/plugin/testdata/valid-feed-request-check-sample.json) (a `write.applied` and a `write.held`), whose answer must be `lastSeq` `2`; for `approval.deliver` the notice of [`valid-deliver-request-check-sample.json`](../api/plugin/testdata/valid-deliver-request-check-sample.json), with no link. They are sent byte for byte as written there, compacted as every message is (no insignificant whitespace), except that `agent`, `subject` and `data.agent` name the entry's first agent in `agents`, and in the notice `time` is the moment `check` sends it and `expiresAt` one hour later, so a plugin that drops expired notices still handles it (for an entry that serves no agent, `check` says so and calls neither hook). They hold no store data: the install id `00000000-0000-0000-0000-000000000000`, which no install has, so a plugin can tell a sample from a real event (and should not keep it for dedup), and the table `basalt_check.sample`.

### Failure

A failed call has one of the failure classes `TIMEOUT`, `EXITED`, `BAD_RESPONSE`, `OVER_LIMIT` or `UNAVAILABLE` (a hook's contract may add its own). A plugin that fails (a failed `health`, a process that exited, a failed start or `initialize`) is marked `UNAVAILABLE` and restarted with a backoff from 1 to 60 seconds, doubling, back to 1 second once it has passed a `health`. Before each start the engine verifies the installed copy again ([Signing and the trust store](plugins.md#signing-and-the-trust-store)). One entry failing or stopping never affects another, and a plugin failure never stops the engine from serving agents.

- **Data-path hooks fail closed.** While a `wire.detect` entry listed for an agent is failing or not running, every request of that agent to the AI provider is refused (`DETECTOR_FAILED`, naming the entry and the class), until the plugin is back or the person disables it. `status` shows `PLUGIN_UNAVAILABLE`. An entry that requires approval and is withheld because it waits for its approval, its approval expired unsigned or it was turned off is not active, so it never fails anything closed; one withheld because it no longer matches its approval counts as failing ([Plugin approvals at engine start](plugins-approval.md#plugin-approvals-at-engine-start)).
- `feed.observe` and `approval.deliver` never block anything; `classify.suggest` lets classify go on and says so.
- **Stderr.** A plugin may see PII, so the engine never logs its stderr and never reads it. In service mode the service manager keeps it, apart from the engine's log: on Linux in the journal under the plugin's unit, on macOS in a log file of the plugin's own ([Service units](#service-units)). In same-user mode it is discarded.

### Isolation and trust

- **Service mode.** Each local entry runs as its own OS user, under its own service unit, started by the service manager. It cannot read the engine's files, `pii.key`, the vault or credential files, and the agents' OS users cannot connect to its socket. With an empty `egress` it also runs without network, recorded `network: ENFORCED`. With a non-empty `egress` it runs with network access: the allowlist is declared, shown at install and recorded `network: DECLARED`, not enforced per host. On an OS where network isolation is not available yet it is recorded `NOT_ENFORCED`, and `status` warns. The engine never starts a local plugin itself in service mode, so none ever runs with the engine's privileges: it connects to the entry's unit only when that unit is installed as it expects, and otherwise the entry is not started (`PLUGIN_UNAVAILABLE`). A health check refuses a local entry in service mode. The units, users and sockets are set out in [Service units](#service-units).
- **Never as root.** An engine running as root, in any mode, never starts a local plugin (`PLUGIN_UNAVAILABLE`).
- **Same-user mode is no security boundary.** In the foreground engine (development, CI) a plugin runs as a child process of the engine's user and can read whatever the engine can; an agent that runs as that same user can bypass the `request_plugin` refusals by writing `engine.json` and the trust store itself, adding a plugin and trusting its own key. The ledger shows it happened (`PLUGIN_TRUST_ADDED`, `PLUGIN_ENABLED`, `isolation.files: NONE`), but that agent can write plugin events to its own ledger too ([What an agent role can write](plugins-ledger.md#in-the-ledger)), so this record is only as trustworthy as the agent. The engine warns at start whenever a plugin runs this way. With [Plugin approval](plugins-approval.md#plugin-approval), in same-user mode: on an agent-operated engine every entry requires a plugin approval, which only a passkey holder can create, so an honest engine serves nothing an agent added that way.
- **Agents' OS users stay out of the engine's group.** The setup page's job refuses an agent OS user (the `osUser` of its link, and `basalt service install --os-user` until that command goes) that is the engine's own OS user, is in the engine's group, or is named as a plugin's user (`basalt-plugin-…`, `_basalt-plugin-…`), the group named as the engine's user: that group reaches every plugin socket and the engine's config directory. Before the first install the group does not exist and no one is in it; a user or group that cannot be looked up refuses.
- **Remote plugins are trusted by declaration and record.** A signature proves who published a remote plugin's manifest, endpoint and egress, not what runs on that host. A remote plugin's own onward calls cannot be enforced; the declaration the person approved and the ledger's `endpoint: REMOTE` are the control, and the plugin approval page says so.

### Service units

In service mode the service manager runs each local entry, never the engine. A remote entry gets no unit and no OS user. Every name below is made from the entry's `(name, instance)`, so two entries, two instances of one plugin included, share no unit, OS user, group, socket, directory or process.

**Not yet rewritten.** The `basalt plugin` commands this section names (`add`, `enable`, `check`) are removed: an agent prepares a plugin with `request_plugin` and the person approves it on the plugin approval page, and `basalt plugin check` is gone with its health in `status`. `basalt service install` still writes an entry's unit until that command goes. The path where a plugin runs as its own OS user from a hand-written `engine.json` entry has no installer now; whether it stays is an owner decision still open. Where a sentence below names a removed command, [Removed](cli.md#removed) wins.

| | Linux (systemd) | macOS (launchd) |
|---|---|---|
| Unit | `/etc/systemd/system/basalt-plugin-<name>-<instance>.service` | `/Library/LaunchDaemons/dev.basaltdb.plugin-<name>-<instance>.plist` |
| OS user and its own group | `basalt-plugin-<name>-<instance>` | `_basalt-plugin-<name>-<instance>` |
| Socket directory | `/opt/basalt/run/<user>/` | `/Library/Basalt/run/<user>/` |
| Network | none with an empty `egress` (`PrivateNetwork=yes`, `ENFORCED`); else `DECLARED` | `NOT_ENFORCED` |
| Stderr | the journal, under the plugin's unit (the unit sets no `StandardError=`, so systemd's default applies; the journal's own size limits apply, and who can read it is the journal's rule: root and the groups the distribution lets read the system journal, such as `adm` and `systemd-journal`) | `/Library/Logs/Basalt/plugins/<user>.log`, the plugin's user's, mode `0600`, rotated by newsyslog at about 1 MiB ([below](#service-units)) |

- **The OS user.** Made by the install when missing (`useradd --system --user-group`, no home, no login shell; on macOS a hidden system account with a free id from 300 to 499 and a group of the same name and id), and named `BasaltDB plugin <name> <instance>`. A user name longer than 32 characters is shortened: the prefix, the start of `<name>-<instance>`, `-0` and the first 12 hex digits of the SHA-256 of `<name>/<instance>`, 32 characters in all. An unshortened name ends in its instance, which starts with a letter, so a shortened one never equals one. A plugin install refuses an entry whose user, on Linux or macOS, would equal another entry's, before anything is written. The unit's name is never shortened, so it always records the entry. Basalt treats OS users with these prefixes as its own, and `basalt init` refuses them as an agent's `--os-user`.
- **What the unit runs.** The command and `args` of the installed copy's manifest, from `<root>/<name>/<instance>/<manifest-sha256>/`, with the copy as the working directory. A manifest value that holds a control character or a line break, or an argument that is a lone `;`, is refused, never written into a unit; on Linux every argument is quoted with `%` and `$` doubled, so the unit reads back exactly the manifest's arguments.
- **Isolation on Linux.** `User=` and `Group=` are the plugin's, with `NoNewPrivileges`, `ProtectSystem=strict` (so the copy is read-only to it), `ProtectHome`, `PrivateTmp`, `PrivateDevices`, kernel and cgroup protection, `RestrictSUIDSGID`, `ProtectProc=invisible` with `ProcSubset=pid`, no capabilities, no new namespaces, private IPC, no `chmod` calls (so it cannot open its socket directory or socket to others by their mode; an ACL it sets instead is refused when the engine connects), `MemoryMax` from the manifest's `resources.memoryMB` (1 GiB without it), only its socket directory writable, and `InaccessiblePaths` for the config directory, the engine's state directory, the engine's socket directory and every agent's credential file outside the config directory (a missing one is skipped). Unit files are readable by every user, so a credential file inside the config directory is hidden with it and never named; one an agent keeps elsewhere is named in the unit by its path. A remote entry's `auth.credentialFile` is not listed: the engine uses it only when it is the engine's user's alone. With an empty `egress` only Unix sockets can be opened (`RestrictAddressFamilies=AF_UNIX`). The unit is bound to the engine's (`BindsTo`, `After`, `PartOf`, and enabled as wanted by it): it starts after the engine, starting the engine starts it, and it stops and restarts with the engine. `Restart=always`, so after `shutdown` the plugin is started again and waits for the engine. On macOS file modes and ACLs are the boundary: the plugin's user owns none of the engine's files and is not in the engine's group.
- **Stderr on macOS.** The plist's `StandardErrorPath` is `/Library/Logs/Basalt/plugins/<user>.log`; stdout is not kept. `/Library/Logs/Basalt` and its `plugins/` are root's, mode `0755`, so neither the engine's user nor a plugin's user can put a file or a link in them (the engine's own `engine.log` there is the engine's user's, mode `0600`, made by `service install` before the engine's daemon loads). An earlier install gave `/Library/Logs/Basalt` to the engine's user: `service install`, and a plugin install or enable in service mode, move that directory aside as a whole to `/Library/Logs/Basalt.old-<UTC time>` (renamed without following a link, nothing in it re-owned or read; a link or a file at the path is refused, and a directory anyone else owns is left for the usual ownership check), make the new root-owned one and the engine's log, print `moved the old /Library/Logs/Basalt, which <user> owned, to <path>`, and go on. The engine writes its log there again from its next start: `service install` restarts it itself; after `plugin add` or `enable` it keeps writing into the moved directory until the restart those commands name. The install makes the plugin's log before its daemon loads: created exclusively without following a link, owned by the plugin's user and group, mode `0600`. An existing log keeps its content and gets that owner and mode, with any flag its owner set (such as `uchg`, which would block root and newsyslog) cleared first, as on the old directory before it is moved; a path that is not a plain file (a link, a file of another user's with a second name, a directory) refuses the step. Only the plugin's user and root can read the log: not the engine's user, not the agents. It is capped by a newsyslog rule, `/etc/newsyslog.d/basalt-plugin-<name>-<instance>.conf` (root's, `0644`): owner `<user>:<user>`, mode `600`, one moved copy, size 1024 KiB, any time, flags `N` (no process is signaled) and `B` (no turnover line is written into the new log). macOS runs newsyslog once an hour. When the log is past 1 MiB, newsyslog moves it to `<user>.log.0`, dropping the copy moved before, and makes a new empty log with the same owner and mode. The size is checked on newsyslog's schedule, not at each write, so a log can grow past 1 MiB in between. launchd opens the log when it starts the plugin, so a plugin that keeps running goes on writing to the moved copy until it starts again (after a crash, an enable, `basalt service install` or a reboot): the cap of about two files of 1 MiB holds from one start to the next, not within one long run. `disable` keeps the log and the rule; `remove` and `service uninstall` delete the rule, the log and its moved copy by the entry's names, and `service uninstall` then removes `plugins/` when it is empty. Neither the engine nor `status` reads or names the log.
- **The socket.** The unit sets `BASALT_PLUGIN_SOCKET` to `<socket directory>/p.sock` and the plugin listens there, as in same-user mode ([Transports](#transports)). In service mode every local plugin must listen on that socket, a `jsonrpc-stdio` one included: no service manager holds a plugin's stdin, so a plugin that only reads stdin never starts there. A plugin install cannot tell such a plugin from one built with the Go SDK (which listens on the socket when the variable is set); when nothing listens on the socket, `status` shows `PLUGIN_UNAVAILABLE` saying the plugin must listen on the socket `BASALT_PLUGIN_SOCKET` names, and a health check in service mode says the same. The socket directory is made by root at install: owned by the plugin's user, group the engine's group, mode `2750`; its parent `run/` and `<base>` are root's, mode `0755`. Every directory the install makes or takes over is left with no ACL (on Linux no access or default ACL, on macOS no extended ACL), so one a directory above passes on to new directories does not open it, and `sudo basalt service install` removes an ACL found on it later. The unit's umask is `0007`, so the socket the plugin makes belongs to the engine's group, which may connect, and others, agents included, cannot reach the directory. The directory stays between starts.
- **How the engine connects.** At start, for each local entry that verified, the engine renders the unit it would install for that entry and its verified copy (with this engine's OS user and config) and compares it, byte for byte, with the installed unit file. It connects only when they are equal, on Linux no drop-in and no unit file of the same name that systemd reads first (`system.control`, `transient`, `generator.early`) changes it, and the unit's OS user exists, is neither root nor the engine's own user and is not in the engine's group. Drop-ins are resolved as systemd resolves them: every `*.conf` in a drop-in directory that applies to the unit (`<unit>.d`, a dash-prefix one such as `basalt-plugin-.service.d`, or `service.d`), in any directory systemd loads units from, a file replacing or masking (as a link to `/dev/null`, or empty) only a file of the same name in a drop-in directory of the same name in a lower-priority directory. Where systemd would also let one drop-in directory name override another (a longer dash prefix over a shorter, a name-specific one over `service.d`), both files are checked, which may refuse a unit systemd would leave alone but never passes one it changes. A drop-in that sets only how long systemd waits to start or stop the unit and what it does when that runs out (`TimeoutSec`, `TimeoutStartSec`, `TimeoutStopSec`, `TimeoutAbortSec`, `TimeoutStartFailureMode`, `TimeoutStopFailureMode`, such as Fedora's stock `service.d/10-timeout-abort.conf`) passes; any other setting, a continued line or a link elsewhere refuses, and `status` says to remove or mask it. A file or directory that cannot be read refuses. The check reads the files, not what systemd has loaded. A plugin's OS user in the engine's group is named in `status`, with the command that takes it out (`sudo gpasswd -d <user> <group>`, on macOS `sudo dseditgroup -o edit -d <user> -t user <group>`). Otherwise the entry is not started, and `status` shows `PLUGIN_UNAVAILABLE` naming `sudo basalt service install`, which writes every unit again: after a new copy, a new agent whose credential file is outside the config directory, or an upgrade that changed the unit. Every connection, the first and each one after (a `connect` transport's own new connections included), is checked before a byte is sent: the unit, its drop-ins and its OS user are checked again as at start, so a unit changed while the engine runs is refused at the next connection (what the unit runs and as whom changes only when its process starts again, which drops the engine's connection; `systemctl set-property` changes resource limits of a running unit, which the engine does not see until then; `status` then shows `PLUGIN_UNAVAILABLE` with the cause); the socket directory is a directory, not a link, owned by the unit's OS user, in the engine's group, with no permission for others, by its mode or by an ACL entry that allows any access (a macOS extended ACL entry; on Linux a POSIX ACL entry for a named user or group, which fits under the group bits), so a plugin that opened its directory to other users is not connected to (an ACL refusal names the directory and says it `has an ACL entry that opens it to others`, or `has an ACL that cannot be read` with the cause); the path is itself a socket, not a link, with no such ACL entry; and the process listening on it runs as the unit's OS user, so a socket another process put at the path, a hard link to one included, is refused. The engine never starts, signals or kills the plugin's process. When an agent's OS user is in the engine's group, the engine starts no local plugin, and each listed agent's `status` shows `PLUGIN_NOT_TRUSTED`.
- **Who writes them.** `basalt service install` makes `<base>` and `<base>/run` (on macOS also `/Library/Logs/Basalt/plugins`) and every local entry's user, socket directory and unit (on macOS also its log and newsyslog rule) whose installed copy verifies: on Linux it starts the engine first; on macOS these plugin steps come before the engine's daemon is loaded; an entry that fails is named and left as it is. Writing an entry's unit (`service install`, `plugin add`, `enable`) stops before any step when the entry's OS user already exists and is in the engine's group, naming the user and the command that takes it out. A plugin install writes the entry's unit (stopped while the entry is disabled), `enable` writes it again and starts it, `disable` stops it and keeps it, and `remove` stops it and deletes its unit, socket directory and OS user, and on macOS its log, the log's moved copy and its newsyslog rule. A plist in `/Library/LaunchDaemons` loads at boot unless it is disabled, so a disabled entry's daemon is also `launchctl disable`d. If the unit step fails after `engine.json` was written, the command says so and names `sudo basalt service install`, which writes every unit again. `basalt service uninstall` is removed. After the setup page's Remove deleted `engine.json`, the [administrator dialog](setup-page.md#the-administrator-dialog)'s removal script stops and deletes every entry's unit, found by its fixed prefix (`basalt-plugin-*.service` on Linux, `dev.basaltdb.plugin-*.plist` on macOS) since the entries were in the deleted `engine.json`, every newsyslog rule `basalt-plugin-*.conf` on macOS, every OS user and group named with the plugin prefix (`basalt-plugin-`, `_basalt-plugin-`) whose login shell refuses a login (one that can log in is named and kept), and `<base>` whole, with installed copies, trusted keys, sockets and, on macOS, `/Library/Logs/Basalt` with the plugins' logs.
- **A base the path rule refuses.** `/opt` is root's and writable by root alone on stock Linux distributions, so `<base>` is the same on all of them. When a directory above `<base>` can still be written by someone other than root, `<base>` is refused as any other path is: on Linux `basalt service install` stops at that step with the cause (the engine is already running) and makes no plugin's user or unit; on macOS, where the plugin steps come before the engine's daemon, it names the cause and skips making `<base>`; a plugin install is refused (`PLUGIN_REFUSED` `UNSAFE_PATH`), naming the directory and who can write it. The rule is not relaxed.
