## Error codes

Tool errors return an MCP tool result with `isError: true` and a JSON body `{ "code": "<CODE>", "message": "…", "reason": "…", "sqlState": "…" }`. `reason` is set for `STATEMENT_REFUSED` and `QUERY_TIMEOUT`; `sqlState` is set when Postgres raised the error. Codes are stable once `IMPLEMENTED`.

Every tool error body also carries `docsUrl`, the link to the code's section on the public docs: `https://docs.basaltvault.app/reference/errors/#<anchor>`, where the anchor is the code in lowercase with underscores as hyphens (`APPROVAL_REQUIRED` is `#approval-required`). The server adds it when it writes the error, from the code alone, including the errors `basalt mcp` answers itself while the engine is down. The docs site's errors page has one anchor for every code in this table (and `UNKNOWN_TOKEN`, planned); the contract test checks each code's anchor against the page's anchors, kept in [`api/mcp/errors/docs-anchors.json`](../api/mcp/errors/docs-anchors.json). Warnings and `status` problems are not error codes and carry no `docsUrl`. Neither are the pinning refusals of the setup pages ([Pinning on first use](trust.md#pinning-on-first-use)): `TRUST_ROOT_CHANGED`, a pinned host that presents another certificate authority, naming both fingerprints, is a `status` problem, as are `TRUST_PIN_MISMATCH`, `CERTIFICATE_NOT_VERIFIED`, `TRUST_ROOT_EXPIRING` and `TRUST_PROFILE_REFUSED` ([Next steps](next-steps.md#next-steps)). The ledger kind `TRUST_PIN_RECORDED` is in [Schema version 6](basalt-meta-schema-versions.md#schema-version-6-trust-pins).

Planned (actionable errors, owner decisions AE-1 to AE-14; not emitted yet): the body also carries `nextSteps` (required, at least one step), `personMessage` (when the person must know or act), `errorId` (on `UNAVAILABLE` and `INTERNAL`), and `reason` for every code with more than one case. Schema: [`api/mcp/errors/tool-error.schema.json`](../api/mcp/errors/tool-error.schema.json); rules in [Next steps](next-steps.md#next-steps).

From M2, an `APPROVAL_REQUIRED` body also carries `approval: { "approvalId", "expiresAt", "rows", "headline", "approvalUrl", "personMessage" }` (see [Approvals](approvals.md#approvals) and [Handing a held action to the person](local-pages.md#handing-a-held-action-to-the-person)):

- `headline`: the held write in one line, cascade stated (`Delete 1 row in public.leads + 2 cascaded rows (public.lead_notes 2)`). The page shows the same line.
- `approvalUrl`: the **short link** `<base>/approvals/<approvalId>` when the engine serves the [local pages](local-pages.md#local-pages); otherwise the long link `<base>/approvals/<approvalId>#1.<request>` (below, [Page links](page-links.md#page-links)), or, when that is over the link budget, the hash link `<base>/approvals/<approvalId>#h=<h>` with `requestFile` beside it ([The request file and pasted blocks](showing-links.md#the-request-file-and-pasted-blocks)). Clients that render links may show it.
- `requestFile`: only with a hash link: the request as a file and as numbered text blocks for the agent to send the person ([The request file and pasted blocks](showing-links.md#the-request-file-and-pasted-blocks)).
- `personMessage`: the message the agent shows the person verbatim: what is held, the headline, the link and the expiry, with the link on its own line ([Showing links](showing-links.md#showing-links), which has an example). Planned (M3.5): `approval.links` and the body's `links` carry the link with a label, as there.

`headline` and `personMessage` are new (M4.1); `approvalUrl` changes from always-long to short-when-served (M4.1, a breaking change). `list_pending` items carry the same four fields, so an agent that lost the link gets it again there.

| Code | When |
|---|---|
| `INTENT_REQUIRED` | A write without an intent (guard SQLSTATE `BS001`) |
| `STALE_READ` | An `UPDATE` or `DELETE` of a row whose version changed since the run last read or wrote it (`BS004`). A row the run never read is a blind write, not refused |
| `STATEMENT_REFUSED` | DDL, multiple statements, data-changing `WITH`, `COPY`, or a function outside the allowlist (engine policy, or `BS007` from the guard) |
| `ROW_LIMIT_EXCEEDED` | More than 50 rows in one action, cascades included (`BS003`) |
| `QUERY_TIMEOUT` | A `SELECT` hit the row or time limit (time limit: SQLSTATE `57014`), or the result went over the 16 MiB budget (size limit: the reads of the whole call), or one row of a `query` or `RETURNING` is over the budget alone (reason `ROW_TOO_LARGE`), or a revert's request is too large for any link the engine has (`request_revert` reason `REQUEST_TOO_LARGE`); also `request_revert` when preparing the revert hit its 100-second limit (reason `TIME_LIMIT`; the message says the revert is too large to prepare in one call and the agent asks whether a narrower revert will do) |
| `APPROVAL_REQUIRED` | The action is held; the result carries the approval id and expiry (`BS002`), or reason `REQUEST_TOO_LARGE` when no link the engine has can carry the request ([Large values](mcp-tools.md#large-values)) |
| `APPROVAL_EXPIRED` | The approval was not given within 24 hours (`BS005`) |
| `APPROVAL_INVALID` | The approval does not exist, is used, belongs to another agent, or no longer matches the rows (`BS005`). HR-1: also a reveal Postgres refused (reason `REVEAL_REFUSED`, one reason for every proof, key, nonce or ticket failure) or whose hidden rows changed (reason `ROWS_CHANGED`), on the pages API only ([Rows hidden from the agent](approvals.md#rows-hidden-from-the-agent)) |
| `REVERT_INVALID` | M3. The revert authorisation does not exist, is already applied, carries a bad signature, or its rows changed since the preview (`BS005`). For a batch of a large plan: the plan is not this agent's, not signed or already finished, or a line is not in the plan, repeated, or already applied. Revert scope: also a revert the person rejected (`REJECTED`), a rescope or reset after the signature, a binding whose `select` is not the revert's stored scope, and a widen Postgres refused (detail `WIDEN_REFUSED`, one detail for every proof or token failure). HR-1: a reveal refused (reason `REVEAL_REFUSED`) or whose hidden rows changed (reason `ROWS_CHANGED`), on the pages API only ([Rows hidden from the agent](approvals.md#rows-hidden-from-the-agent)) |
| `REVERT_EXPIRED` | M3. The revert was not signed within 1 hour of `prepare_revert`, or a signed large plan was not finished within 24 hours of the signature (`BS005`) |
| `NOTHING_TO_REVERT` | M3. Every row in the scope would be skipped, or the scope wrote no rows (`BS009`). Served (AE-8): also `preview_revert` and `request_revert`, in place of `NOT_FOUND`, with reason `READS_ONLY` (the scope wrote no row a revert could restore: only reads, or rows it both inserted and deleted), `ALL_CHANGED_BY_PEOPLE` (every row would be skipped, not all as `ALREADY_REVERTED`) or `ALREADY_REVERTED` (every row was last written by a revert of the scope; the next steps name that revert's `changeId` and when it ran) |
| `PERMISSION_DENIED` | The agent's role lacks the privilege; the database refused (`42501`) |
| `NOT_FOUND` | The run named in the arguments does not exist for this agent; for `preview_revert` and `request_revert`, also a change or run that is not this agent's (before any preview or prepare) and a task the agent never ran in (reason `TASK`, RS-6); also an approval or revert that is not this agent's, and a page link without its secret or replaced (reasons in [Next steps per code](next-steps.md#next-steps-per-code)). For `describe` (M4), a resource that does not exist and one the agent cannot read: the same answer for both, so the agent cannot probe for names. Unknown ids and other agents' ids only: an own scope with nothing to undo is `NOTHING_TO_REVERT`. Planned (revert scope, RS-2): a revert link the agent reset is `NOT_FOUND` reason `LINK_RESET` (pages only) |
| `SQL_ERROR` | Any other error Postgres raised for the agent's statement (syntax, unknown column, constraint); `sqlState` says which |
| `INVALID_ARGUMENT` | Arguments fail schema validation, or an unknown argument was passed. Served (revert scope, RS-1): a revert scope filter outside the agent's own work or naming a table the store cannot use (reason `SCOPE_FILTER`) or with more than 20 entries (reason `SCOPE_FILTER_CAP`). Served (admin credential): a string in the arguments, a key included, holds a `postgres://` or `postgresql://` URL with a password (reason `ADMIN_CREDENTIAL`, [Agents and the admin credential](setup.md#agents-and-the-admin-credential)) |
| `UNAVAILABLE` | The database or the guard cannot be reached; planned (chat-only operator): also the agent's [setup from the laptop](setup.md#setup) has not run yet (reasons `SETUP_PENDING`, `SETUP_EXPIRED`); also, for a connect-only code, the engine collected the database's address and the person has not confirmed that database yet (reason `DATABASE_NOT_CONFIRMED`, [The engine and a connect-only code](setup.md#the-engine-and-a-connect-only-code)) |
| `INTERNAL` | A defect in the engine or the guard (`BS006`, `BS008`) |
| `PLUGIN_REFUSED` | `request_plugin` refused a plugin change and changed nothing, except an approval that cannot be opened after its entry was written: that leaves the entry written and withheld ([Plugin approval](plugins-approval.md#plugin-approval)). Reasons: `AGENT_OPERATED` (the engine is `operatedBy: AGENT`: only one that runs as a service under its own OS user: plugin changes stay refused there), `SAME_USER_MODE` (the engine runs as the person's own OS user and keeps no plugin entries of its own), `NO_LOCAL_PAGES` (a person-operated engine serves no local pages, so the person could sign nowhere), `NO_PORTAL_LINK` (an agent-operated engine cannot hand over a portal link, so the person could sign nowhere; [Plugin approval through the portal](plugins-approval.md#plugin-approval-through-the-portal)), `AGENT_NOT_ALLOWED` (an agent outside the caller's reach: the caller not among `agents`, an agent on another database, or one of another OS user; also when the person socket refuses the agent's OS user), `TOO_MANY_PENDING` (the database already holds 8 pending plugin approvals), `GUARD_OUTDATED` (the guard is older than [schema version 5](basalt-meta-schema-versions.md#schema-version-5-plugin-approvals)), `DATABASE_UNREACHABLE` (the database does not answer), `BAD_MANIFEST` (the manifest breaks a rule of [Manifest](plugins.md#manifest); the message names the rule), `NOT_TRUSTED` (a `.sig` that names a built-in key does not verify, or a file's hash failed), `UNKNOWN_AGENT` (an agent in `agents` is not one of the engine's agents), `UNSAFE_PATH` (the [path rule](plugins.md#signing-and-the-trust-store) refused a path; the message names it), and those of [Plugin approval in service mode](plugins-approval-service-mode.md#plugin-approval-in-service-mode): `NAME_TAKEN`, `CONFIG_ENTRY`, `TOO_LARGE`, `TOO_MANY_UPLOADS`, `ENGINE_IS_ROOT` |

`STATEMENT_REFUSED` reasons: `PARSE_ERROR`, `MULTIPLE_STATEMENTS`, `WRONG_TOOL` (a write sent to `query` or a read sent to `write`), `DDL_NOT_ALLOWED`, `STATEMENT_NOT_ALLOWED` (`SET`, `DO`, `COPY`, `EXPLAIN`, transaction control and other utility statements), `SELECT_INTO`, `LOCKING_READ`, `MERGE_NOT_ALLOWED`, `DATA_MODIFYING_WITH`, `FUNCTION_NOT_ALLOWED`, `HOLD_TOO_LARGE` (a write that would be held has preview lines over what a hold keeps, [Large values](mcp-tools.md#large-values) rule 7), and from M2 `NOT_REPEATABLE` (a write that would be held contains a value that changes between transactions: a function such as `now()` or `random()`, `DEFAULT`, or a string that is a date/time word, `now`, `today`, `tomorrow` or `yesterday` in any case, alone or with a time of day, a day name or a zone (`tomorrow 10:00`, `today 09:00 Europe/Berlin`; a zone is an offset, one of Postgres's default zone abbreviations or an `Area/City` name), as a literal anywhere in the statement or as a parameter; pass a fixed value, a timestamp, as a parameter. A string that holds such a word among other words (`call back tomorrow`) is plain text and is not refused, but a string that is only a time word cannot be held, whatever the column's type: the check reads the statement, not the column). `QUERY_TIMEOUT` reasons: `TIME_LIMIT`, `ROW_LIMIT`, `SIZE_LIMIT`: the result costs more than 16 MiB (16 777 216 bytes) as the engine counts it, summed over its rows: each value's bytes in text form, what JSON adds to escape them, a fixed cost per value (NULLs included) and each column's name per row. A single row over 16 MiB on the wire is refused before it is read. The engine stops reading at either point, so one large value, or many small or NULL ones, cannot grow its memory without bound. **One budget per call.** Every read the engine makes on the agent's connection for one tool call is charged against the same 16 MiB, with the same accounting: the agent's own statement in `query` and a write's `RETURNING`, the held write's preview, and the reads behind `run_history`, `list_pending`, `preview_revert`, `revert_plan`, `request_revert` and `describe`. Reads the person's CLI makes are not budgeted. The ledger tools never fail on one large item: they replace large values with a marker ([Large values](mcp-tools.md#large-values)), so their pages always fit at `limit` 1 and a smaller `limit` always ends a `SIZE_LIMIT`. The reads of `list_runs`, `run_start`, `apply_revert_batch` and `status` are charged too but are bounded far below the budget (short fields only), so those tools do not declare `QUERY_TIMEOUT`; `run_history`, `list_pending` and `revert_plan` declare it. Reason `REQUEST_TOO_LARGE` (`request_revert`; and `APPROVAL_REQUIRED` `REQUEST_TOO_LARGE` for a held write): the request is over what a page can decode and the engine has no short link that can carry it ([Large values](mcp-tools.md#large-values)). Reason `ROW_TOO_LARGE` (`query` and a write's `RETURNING`): one row alone costs more than the budget. `query` never shortens a value, so it refuses the row: the message names the row's size and its largest columns with their sizes (when the row was over 16 MiB on the wire and could not be read at all, the row's size and the result's columns, largest unknown), and the agent selects fewer columns, a size (`length(col)`, `octet_length(col)`) or a slice (`substr(col, 1, 100000)`). The agent never holds a shortened value it could write back. `SIZE_LIMIT` stays the reason when no single row is over the budget but the rows together are. Planned (AE-5): `STATEMENT_REFUSED` gains `NO_PRIMARY_KEY` and `NOT_ALLOWED` (the guard's `BS007`, which carries no reason today), and the other codes with more than one case get reasons; [Next steps per code](next-steps.md#next-steps-per-code) lists them all.

New codes and reasons go through the contract-first process. Each one needs its entry in [Next steps per code](next-steps.md#next-steps-per-code) and [`api/mcp/errors/next-steps.json`](../api/mcp/errors/next-steps.json).
