## Next steps

Planned (owner decisions AE-1 to AE-14). Every error body and every result the agent must act on tells it what to do next and what to tell the person. No bare error strings to agents.

- **`nextSteps`**: an ordered array of steps, first step first ([`next-step.schema.json`](../api/mcp/errors/next-step.schema.json)). Each step has `actor` (`AGENT` or `PERSON`), `action`, and `text` (one plain sentence, at most 200 characters), plus what the action needs: `tool` and `arguments` (filled in by the engine: complete for `CALL_TOOL`, except `confirm_database`, planned, whose `answer` the agent sets from the person's words and the engine never fills in; where `repeatCall: true` merges them over the arguments of the call that returned the step and `null` removes one; the ids it knows for `REVISE_CALL`), `command`, `url`, `maxRows`, `waitSeconds`.
- **Actions.** `AGENT`: `CALL_TOOL` (call `tool` with `arguments`), `REVISE_CALL` (change the statement or arguments as `text` says, then call `tool`), `RETRY_SMALLER_BATCHES` (split into writes of at most `maxRows` rows, same intent and run), `ASK_PERSON`, `END_TURN` (end the turn; the person acts next), `STOP` (do not retry, do not work around). `PERSON`: `OPEN_LINK` (`url`, optionally `command` that opens the same page), `RUN_COMMAND` (`command`), `TELL_AGENT`. No step is conditional: each result carries its own steps. `AGENT` `SEND_REQUEST` (send the person the request file, or its text blocks, of the `requestFile` beside the link; [The request file and pasted blocks](showing-links.md#the-request-file-and-pasted-blocks)) is not in the catalog's sequences: the engine puts it right before the first step of an entry exactly when the result, or the `list_pending` item, carries `requestFile`, and the catalog checks run on the steps without it. Chat-only operator (CO-1): `AGENT` also `RUN_COMMAND` (`command`), only when the engine's `operatedBy` is `AGENT`.
- **Who runs machine steps** (chat-only operator). A machine step runs a command on the engine's machine: start or restart the engine, install or upgrade `basalt`, `basalt init --remote`. When `operatedBy` is `PERSON` it is a `PERSON` step, as above; when it is `AGENT` it is an `AGENT` `RUN_COMMAND`, with `command` as complete as a person's and `text` written to the agent. A step that needs the admin connection string is always a `PERSON` step, whatever `operatedBy` says: on an agent-operated engine it runs on the person's own computer (`text` says so) and is never addressed to the agent (CO-9). The catalog writes this two ways: a machine step whose entry reads the same in both modes has actor `OPERATOR`, a catalog-only value the engine resolves to `AGENT` or `PERSON` from `operatedBy` (the shim, when it cannot read the config, resolves it to `PERSON`); an entry whose steps differ on an agent-operated engine has a variant in `agentOperated` ([Next steps on an agent-operated engine](#next-steps-on-an-agent-operated-engine)) that replaces its steps there. On the wire the actor is always `AGENT` or `PERSON`.
- **Setup code steps.** An `AGENT` `RUN_COMMAND` of `basalt init --remote ... --json` makes a [setup code](setup-from-laptop.md#the-setup-code). Its output carries its own `personMessage` and `nextSteps` (the person runs `basalt init --setup-code <code>` on their own computer, then tells the agent; [`remote-init-result.schema.json`](../api/mcp/setup/remote-init-result.schema.json)): the agent shows them to the person and follows them in place of the rest of the entry's steps. An agent runs a machine step at most once for one problem; when `status` reports the same problem right after, it asks the person instead (`ASK_PERSON`), never loops. On an engine that hands the [connect link](connect.md#the-connect-link), those steps start with a `PERSON` `OPEN_LINK` of that link, before the `RUN_COMMAND` of the laptop command ([Next steps with the connect link](#next-steps-with-the-connect-link)). A [connect-only code](setup-from-laptop.md#connect-only-setup-codes)'s steps are P `OPEN_LINK`, A `END_TURN`, A `CALL_TOOL` (`status`), with no laptop command ([Next steps for a connect-only code](#next-steps-for-a-connect-only-code)).
- **`personMessage`**: plain text, at most 500 characters not counting its URL lines, that the agent shows the person verbatim. Set whenever the person must know or act. Each URL in it stands on a line of its own, and `links` lists them with labels ([Showing links](showing-links.md#showing-links); until M3.5 the engine writes one line). The agent also shows each `PERSON` step's `command` and `url` unchanged.
- **Commands** are complete and copy-pasteable: every `basalt` command names `--agent <name>` and its ids, and `--config <absolute path>` unless the config is the default the CLI finds by itself (`/etc/basalt/engine.json` on Linux, `/Library/Application Support/Basalt/engine.json` on macOS). No placeholders. Never a secret (connection string, password, token); a command that needs the admin connection string asks for it itself. A short link's `#s=` secret appears only in `url` and `personMessage`. "Run `basalt init` again" steps use the flags init saved in `engine.json` ([CLI](cli.md#cli)), plus the one change the step is for.
- **Steps never suggest getting around a limit**: no split below the hold threshold to avoid an approval, no other path around a refusal, no retry loop on a refusal. Over 50 rows the agent stops and asks; only on the person's explicit yes does it split into held batches of up to 50 rows, each needing the person's approval.
- **Results.** `preview_revert`, `request_revert`, `revert_plan`, `apply_revert_batch` and each `list_pending` item carry `nextSteps` and `personMessage` when there is something to do. `query` and `write` carry `warnings: [{ code, message, table, personMessage, nextSteps }]` ([`warning.schema.json`](../api/mcp/errors/warning.schema.json)), absent when empty, with `RLS_HIDES_ROWS` (row-level security hides every row of a table in the statement from the agent role and the statement returned or changed 0 rows); `run_start` carries `GUARD_UPGRADE_AVAILABLE`.
- **`status`.** The MCP tool `status` (below) reports what is ready and lists `problems`, each with `code`, `severity` (`ERROR` or `WARNING`), `personMessage` and `nextSteps`. The agent calls it at the start of a session, after the person says they fixed something, and after a failure that looks like setup. When `operatedBy` is `PERSON` the agent never starts, stops, restarts or upgrades anything itself.
- **Pages.** The local pages' JSON errors carry `personMessage` and the entry's `PERSON` steps.
- **Startup failures.** `basalt mcp` that cannot reach the engine first tries to start it (the next paragraph), and when that does not apply or fails it serves `status` and the tool list from its embedded contracts and answers every other call `UNAVAILABLE` reason `ENGINE_UNREACHABLE` (it holds no credential and reaches no database). An engine whose guard misses a **breaking** migration serves the agent degraded: `status` works, every other tool answers `UNAVAILABLE` reason `GUARD_OUTDATED` with the `basalt upgrade` steps; it checks again on each call and serves normally once upgraded, with no restart. Missing only **non-breaking** migrations: served normally, with `GUARD_UPGRADE_AVAILABLE` (see [`basalt_meta`](basalt-meta.md#basalt_meta)). A connection to an agent's socket from any OS user but that agent's `osUser` runs nothing: the engine writes one JSON-RPC error line with a `null` id and code `-32001`, whose message names the agent and says only its `osUser` may use the socket and how to change it, reads and drops what the peer sent for up to 2 seconds (at most 8 such connections per agent at a time; past that, and once the engine stops, it closes right after the line), and closes. An accept that fails for lack of file descriptors or memory is retried with a backoff (5 ms doubling to 1 s); any other accept error ends that agent's socket. `basalt mcp` does not pass that line on: it answers each request it had sent on that connection, or tried to send after the engine had already refused and closed it, with a JSON-RPC error (`-32000`) carrying the message, and exits with it when that connection is its last one (a later connection the engine admits decides instead).
- **`basalt mcp` starts a same-user engine.** When a message finds the agent's socket not answering and no engine was serving this session a moment ago (or the wait for one that went away ended, 15 seconds), `basalt mcp` starts the engine itself, once, when its config is for same-user mode (not a service-mode config), is a file owned by the OS user `basalt mcp` runs as, and that user is not root. Any other config keeps the answer above unchanged. It makes the socket and state directories `0700` if they are missing, takes an exclusive lock on `start.lock` in the socket directory (a `basalt mcp` that finds it held waits for the socket instead), checks again under the lock that no engine holds the engine lock, and runs `basalt engine --supervise --config <path> --started-by mcp` from its own binary (the symlink resolved when `basalt mcp` started; a binary that is gone is a failure naming its path) in a new session, with no stdin and its output appended to `engine.log` in the state directory (`0600`, a symlink there refused). It waits for the agent's socket to answer, up to 15 seconds (`DefaultStartWait`) in all, holding `start.lock` meanwhile (a `basalt mcp` that finds the lock held waits for the socket the same way); on any failure or timeout it answers as above, and the answer names why (an engine that holds its lock but never serves this agent's socket is one: the first message waits the 15 seconds, later ones look once until that engine is gone) and the log's path: every other tool's message ends with `basalt mcp could not start the engine: <reason>. Its log is <state dir>/engine.log.`, and `status` adds the problem `ENGINE_START_FAILED` with that sentence as its message, before `ENGINE_UNREACHABLE`. The next message tries again; nothing is remembered but the sentence and whether a running engine failed to serve this socket. No secret is written to the log by this path or to the sentence. Two `basalt mcp` processes that find the engine down at once start exactly one engine.
- **Engine restarts (upgrades).** `basalt mcp` is the thin, long-lived side: it holds no state and no credential, so it needs no restart when `basalt` is upgraded; only the engine restarts. When an engine that was serving this `basalt mcp` goes away, the next message waits up to 15 seconds for the engine's socket to answer again before it is answered as in the paragraph above; after one wait that fails, later messages do not wait until the engine has answered once more. A request the engine had already taken and drops unanswered is sent once more to the engine that comes back only when it is a call of a read-only tool (`query`, `describe`, `list_pending`, `list_runs`, `run_history`, `status`). Every other request (`write`, `run_start`, the revert tools, `initialize`) is answered as dropped (`UNAVAILABLE` `ENGINE_UNREACHABLE`, "may or may not have run") and never sent twice, so no write, approval or revert runs twice or is lost silently across a restart. A retried `query` is recorded as a second read. A request the engine answers with JSON-RPC error `-32003` (below: it did not run it because it is restarting) is different: nothing ran, so `basalt mcp` sends it once more, whatever the tool, to the engine that comes back, after the same wait, and sends nothing more on that connection; a second `-32003` for the same request, or no engine within the wait, is answered as usual (the `-32003` error is passed to the client as it is; with no engine, `ENGINE_UNREACHABLE` as for a request the engine never received).
- **Restart onto an upgraded binary.** `basalt engine`, with or without a service manager and with or without `--user`, restarts itself when a new `basalt` binary is installed where it was started from, so an upgrade needs no restart by hand:
  - **What it watches.** The path it was started from: `argv[0]`, looked up on `PATH` when it has no slash, so a package manager's symlink that now points at a new version is followed; when that path leads to another file than the running binary (`argv[0]` can be anything), the running binary's own path. It looks every 5 seconds. A different file there (another device and inode, size, modification time or mode: a rename over it, a copy over it and a new symlink target all count) is used once it was the same on two looks in a row, so a file still being copied is never run. A path the engine cannot read at start turns the restart off, with a warning in the log.
  - **Checks on the new binary.** When the engine runs as root, or the binary it runs (its own executable, whatever path started it) passed the root-only check of `basalt service install` ([CLI](cli.md#cli)), the new one must pass that check too, again right before it is run: a restart never runs a binary less protected than the first. In that case a watched path that fails the check itself (a link in a directory others can change) is not used: the engine watches its own executable's path instead. Then `<path> version`, run with `BASALT_UPDATE_CHECK=off` for at most 10 seconds, must exit `0` and print `basalt <version>`. A binary that fails a check is logged once (`a new basalt binary is installed but the engine does not restart onto it`, with the reason) and skipped until it changes again.
  - **Between calls.** The engine logs `a new basalt binary is installed` with its version, then waits up to 2 minutes for a moment when nothing runs: no agent call on any of its sockets, no person socket request and no page-session request through the Vault or the direct listener (a call waits at most 110 seconds for a person, so only requests that keep overlapping hold it off). From that moment it admits none of them. When no such moment comes, it admits none after the 2 minutes and lets those still running finish for up to 2 more minutes; past that it cancels them: their transactions roll back, and `basalt mcp` answers them as dropped (above), so a cancelled write, approval or revert is never sent again. A person socket request it does not admit is answered `REFUSED` (`the basalt engine is restarting onto the upgraded basalt binary and did not run this request; nothing was run: run the command again in a few seconds`), and a page-session request `503` `UNAVAILABLE` with the same meaning; neither runs anything. A stop (`SIGTERM`, `SIGINT`) during the wait or the drain is a stop: the engine exits as on any stop and does not run the new binary.
  - **Stopping.** It closes every agent socket at once, so a `basalt mcp` that dials waits for the new engine. Each open connection is read for 250 milliseconds more, counted from when the engine stopped admitting calls or from the connection's last answer, whichever is later: every request read then is answered with JSON-RPC error `-32003` and nothing is run for it (message: the engine is restarting onto the upgraded binary and did not run this call; nothing was run; call again in a few seconds). The hello and notifications are not refused. Then it closes the connection, the pages, the person socket and the Vault connection as on a stop, and releases its lock.
  - **Running the new binary.** It replaces itself with the new binary at that path (`execve`), with the same arguments and environment: the same process id, OS user, groups, umask and, on Linux, `no_new_privs`, which a process cannot undo. A service manager sees no restart. `--user NAME` finds the process already running as `NAME` and still runs its binary check and its verification (`basalt engine: already running as NAME ...`), so the privilege drop and the owner of every file it makes are the same after the restart. The new engine reads the config again and serves; a `basalt mcp` waiting for it sends its next message there, with no client restart. When the new binary cannot be run (`execve` fails), this binary serves on with a new start of the engine, and restarts only when the binary changes again. A new binary that runs but then stops (a config it refuses) leaves no engine running: a service manager starts it again, and without one the person does.
- **Version negotiation.** The shim and the engine agree on an integer protocol version for the link between them. It is raised only when a change would make an older shim or an older engine misbehave; this build speaks version 1, serves every shim from version 0 and works with every engine from version 0, so nothing is refused today. A peer from before the negotiation is version 0. On every connection the shim's first line is the request `basalt/hello` (id `basalt-hello`) with params `{ "protocol", "build" }`; the engine answers `{ "protocol", "build", "minShimProtocol" }`, and the shim passes neither to the client. The shim holds the client's first request until the answer arrives (one round trip per connection; an engine that stays silent for 3 seconds is treated as if it had answered), so no request reaches an engine the shim refuses. A shim that sends no hello counts as version 0, and an engine that answers the hello with method not found (`-32601`) is version 0.
  - **Shim too old for the engine.** When the shim's version is below the engine's `minShimProtocol`, the engine runs no request of that connection: it answers the hello and every request after it with a JSON-RPC error, code `-32002`, whose message names both builds and the step: reconnect the MCP server so the client starts the upgraded `basalt mcp` (in Claude Code run `/mcp` and reconnect `basalt`, or restart the agent client), then call again; nothing was run for the call. The shim passes the error on as it is, and does not judge the engine's version from it. A shim that never says hello gets the same errors.
  - **Engine too old for the shim.** When the engine's version is below the oldest the shim works with, the shim closes the connection without sending the client's request and answers every request with a JSON-RPC error (`-32000`) saying the engine was not restarted after the upgrade and asking the person to restart the engine (or its service), then call again; nothing was run for the call. It checks again each time it connects, so the next call after the restart works with no client restart.
- **The catalog.** [`api/mcp/errors/next-steps.json`](../api/mcp/errors/next-steps.json) fixes, per code and reason (and per tool where a tool differs), per result case, per warning and per `status` problem, the `(actor, action)` sequence the engine returns and whether `personMessage` is set. The tables below are the same list, and the variants for an agent-operated engine, for the connect link and for a connect-only code are listed in their own tables ([agent-operated](#next-steps-on-an-agent-operated-engine), [connect link](#next-steps-with-the-connect-link), [connect-only](#next-steps-for-a-connect-only-code)). The contract test checks both agree and that every code in [Error codes](error-codes.md#error-codes), every warning and every `status` problem has an entry; the engine's test checks every returned `nextSteps` against it. Entries marked `planned` (rows whose Steps start with `Planned (`) are left out of the engine's catalog until they land ([Planned parts of a served tool](../CONTRACT.md#process-contract-first)).
