# Changelog

All notable changes to BasaltDB are recorded in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Breaking for alpha installs

- Breaking for installs of an alpha release: an agent's `credentialFile` in `engine.json` moves inside `store`. The old key is not read, and every command that loads `engine.json` stops with the edit for the agent. Replace `"credentialFile": "<path>"` with `"store": {"kind": "POSTGRES", "credentialFile": "<path>"}` by hand, then run `basalt upgrade --agent NAME` for the guard schema below.
- The guard's schema moves to version 2, a breaking upgrade: run `basalt upgrade --agent NAME` once after updating the binary. Until then the engine serves only `status`, with the upgrade steps.

### Added

- The portal has a home page and a not-found page. Opening `https://portal.basaltvault.app/` or a mistyped link now shows a short page that says what the portal is and links to the docs, instead of the browser's bare 404. Both pages are static and run no script. `basalt portal verify` checks them too: the home page at `/`, and the not-found page at an unknown path, which must answer 404 with that page.
- A daily check for a newer release. After a command, `basalt` prints one line on stderr when a newer release is out, in red when that release has a security fix. It asks the public release list once a day and sends nothing but the request itself. Turn it off with `BASALT_UPDATE_CHECK=off` or `"updateCheck": "OFF"` in `engine.json`. `basalt status --json` carries an `update` field instead of the line, and when the engine runs as a service, `basalt` follows the engine's setting.
- Agents hear about a newer release too: the `status` and `describe` tools carry an `update` message, and the first tool result of each MCP connection repeats it once. The agent is told to pass it on and never to upgrade BasaltDB unless the person says yes.
- `basalt mcp` and the engine agree on a protocol version when they connect. If the two builds do not fit, the agent gets a clear error that says to reconnect the MCP server or restart the engine, instead of a failure that depends on what changed.
- The engine restarts itself onto an upgraded binary installed at the path it was started from, with or without a service manager such as systemd or launchd. It waits for running calls to finish first, then admits nothing new. A request it turns away with error `-32003` was not run, and `basalt mcp` sends it once more to the restarted engine.
- When `basalt` panics, it saves a scrubbed crash report on your machine (version, OS, command, stack; no SQL, table or column names, row values, connection strings, host names, home paths or environment values) and prints one line pointing to `basalt crash show <id>` and `basalt crash report <id>`. `basalt crash list` and `show` let you read exactly what was saved; `report` opens a pre-filled GitHub issue that you review and submit yourself. Nothing is sent by basalt. A tool call in the engine that panics now ends with an `INTERNAL` error instead of stopping the engine.
- `basalt status` without `--agent` lists the engine's agents when there are several: each agent with the name and host of its database, in text and `--json`. `basalt status --agent NAME` also shows the agent's database and host. No user, port, password or connection string is shown. Under an agent (Claude Code, Codex and the others) it does not list other agents; it asks for `--agent NAME` and says the person can run `basalt status` in their own terminal.
- The MCP `describe` overview names the agent's own database by name and host.
- `basalt plugin list | add | enable | disable | trust | remove`, and a `plugins` list in `engine.json`. `add <dir> --agents a,b [--instance NAME]` verifies the plugin's signature and files, installs its own copy, and adds the entry disabled; `enable` turns it on. Both show the hooks, entity types, egress hosts, whether it runs on this machine or on another host, the signer and the agents, with plain-words warnings, and write nothing until you say yes. Under an agent (Claude Code, Codex and the others), or on an engine an agent operates, `add`, `enable`, adding an agent or a new manifest, and `trust` are refused with `PLUGIN_REFUSED` and change nothing; `disable`, `remove` and removing agents still work. Every entry names the agents it serves, and each must be one of the engine's.
- `basalt plugin check <name>` starts an entry from its verified copy, runs `initialize` and `health`, prints the timing and stops it; it needs no database and sends no data. `basalt plugin keygen --out DIR` makes a signing key pair (the private key file is mode 0600 and never printed, and no file is overwritten), and `basalt plugin sign <dir> --key FILE` checks a plugin's manifest and files and signs it, so you can build and trust your own plugin.
- The engine starts and supervises every enabled plugin. At start it verifies each entry's installed copy (again before every restart), starts it, checks its health every 30 seconds, restarts one that fails with a backoff from 1 to 60 seconds, and stops them all within 5 seconds when it stops. A plugin that fails never stops the engine or another plugin. Each local plugin runs in its own process group, in its installed copy, with no environment but its socket path, and its socket lives in a new private directory removed when it stops. An engine run as root does not start local plugins. With no plugins enabled nothing changes.
- `status` shows `PLUGIN_UNAVAILABLE` (an enabled plugin for the agent is not ready) and `PLUGIN_NOT_TRUSTED` (the engine refused to start it: its signature, files or permissions failed), each with `basalt plugin check <name>` and `basalt plugin disable <name>` for you to run.
- In service mode each local plugin gets its own service unit, OS user and socket directory: `basalt-plugin-<name>-<instance>` (on macOS the user is `_basalt-plugin-<name>-<instance>`, shortened past 32 characters). `basalt service install` writes them for every local entry, `basalt plugin add`, `enable`, `disable` and `remove` write, start, stop and delete one, and `basalt service uninstall` removes them all. On Linux the unit runs the plugin read-only, without the config directory, the engine's state and socket directories or any agent's credential file, cannot change file modes, starts and stops with the engine, and has no network when the manifest's `egress` is empty. An engine run as a service connects to the unit's socket, only when the installed unit is the one it expects and only to a process running as the plugin's own user, and never starts the plugin itself; otherwise the plugin shows `PLUGIN_UNAVAILABLE` with `sudo basalt service install` as the fix. When an agent's OS user is in the engine's group, no local plugin starts and `status` shows `PLUGIN_NOT_TRUSTED`.
- A plugin built with the Go SDK replaces a socket a crash left at its socket path, so a service unit can restart it.
- An engine that was killed no longer leaves its plugins running: in same-user mode it records each local plugin process it starts, and its next start stops any still running and removes their socket directories. Socket plugins need a temporary directory that no one else can change: a directory root owns with the sticky bit set, such as a stock `/tmp`, is accepted, so socket plugins start with `TMPDIR` unset; any other directory others can write is refused, and the error says to set `TMPDIR` to a private directory. Each socket directory gets a random name and is refused if anything is already there.
- A plugin's `health` check and `shutdown` never wait behind its hook calls: the cap of four calls in flight counts hook calls only, and each lifecycle call has a slot of its own, so a busy plugin is not restarted as unhealthy. A plugin must answer `health` and `shutdown` while four hook calls run; the Go SDK does, even when its hook handlers run past their deadline: a hook call that gets no free slot in time is answered deadline exceeded.
- `basalt service install` makes `/opt/basalt` (Linux, the same on every distribution) or `/Library/Basalt` (macOS), owned by root, for plugins; `uninstall` removes it when it is empty.
- `basalt plugin add`, `trust`, `enable` and `check` refuse a path the path rule does not accept with their own reason, `PLUGIN_REFUSED` `UNSAFE_PATH`: the message names the path and what is wrong with it (who besides its owner can write it, that it is a symlink, or its owner) and says what to do, instead of suggesting to trust the publisher's key, which cannot fix it.
- In service mode the engine checks each local plugin's service unit again before every connection, not only at start: a unit changed since, a systemd drop-in that changes more than its timeouts or a unit file systemd reads first, a plugin OS user in the engine's group, or a socket directory opened to others is refused, and `status` says why. Installing a unit for a plugin OS user that is in the engine's group is refused, naming the command that takes it out. When nothing listens on a plugin's socket, `status` and `basalt plugin check` say that a service-mode plugin must listen on `BASALT_PLUGIN_SOCKET`.
- `basalt init` refuses an `--os-user` that is the engine's own OS user, is in the engine's group, or is named like a plugin's OS user.
- `basalt engine --plugin-debug` shows local plugins' stderr on the engine's terminal in same-user mode. Without it a same-user plugin's stderr is discarded, since it may hold data; the engine never logs it. In service mode a plugin's stderr goes to its own log file on macOS and to the journal on Linux (below).
- On macOS a service-mode plugin's stderr goes to its own log, `/Library/Logs/Basalt/plugins/<user>.log`, which only the plugin's OS user and root can read. A newsyslog rule moves it aside at about 1 MiB and keeps one older copy. newsyslog checks the size once an hour, and a plugin that keeps running writes to the moved copy until it starts again. `basalt plugin remove` and `service uninstall` delete the log and its rule. On Linux a plugin's stderr stays in the journal under its unit. After upgrading, run `sudo basalt service install` so each plugin's launch daemon names its log; until then the engine refuses the old daemon and shows `PLUGIN_UNAVAILABLE`. `/Library/Logs/Basalt` is now owned by root (the engine's `engine.log` in it is still the engine's user's). If an earlier install made it, `service install` moves the old directory to `/Library/Logs/Basalt.old-<time>` itself and says so; there is nothing to do by hand.
- Each agent's ledger records its plugins. At start, before any plugin runs, the engine compares what it serves with what the agent's own ledger says and writes only what changed: `PLUGIN_ENABLED`, `PLUGIN_CHANGED`, `PLUGIN_DISABLED` (also for an agent removed from an entry) and `PLUGIN_TRUST_ADDED` for each key you trusted. A restart with no change writes nothing, and a change made with `basalt plugin` is recorded at the next engine start. Each record names the plugin, version, manifest hash, signer, hooks, egress, whether it runs here or on another host, and its isolation; never its config, a path or another agent. If the engine cannot write the record to an agent's ledger, or the record of the trusted key that signed the plugin, it does not serve that plugin to that agent and `status` shows `PLUGIN_UNAVAILABLE`. `basalt log` prints a `Plugins:` line with each plugin the ledger records as on. This needs guard schema version 3, a non-breaking upgrade: run `basalt upgrade --agent NAME`, then restart the engine, before its plugins serve that agent.
- The ledger records `PLUGIN_TRUST_REMOVED` when it lists a plugin key as trusted that the trust store does not hold: a key you removed, or an event an agent wrote itself. The engine writes it at its next start, and writes `PLUGIN_TRUST_ADDED` again for a held key the ledger says was removed. A plugin is served to an agent only when that agent's ledger records the key that signed it. This needs guard schema version 4, a non-breaking upgrade: run `basalt upgrade --agent NAME`, then restart the engine; until then such a key stays recorded as trusted and the engine logs it.
- Guard schema version 5, a non-breaking upgrade (`basalt upgrade --agent NAME`), adds plugin approvals signed with a passkey. The database builds what the person approves, checks the passkey signature itself, and only then writes `PLUGIN_APPROVED` to the ledger of each agent the approval names; no agent can write that record. A pending approval expires after 24 hours, a new one for the same plugin entry cancels the earlier one, and a database holds at most 8 pending. A plugin event may now record whether the plugin's signer is known.
- In same-user mode an agent can prepare a plugin for you to approve. When an agent runs `basalt plugin add` or `enable`, on an engine an agent operates, or with `--approve-with-passkey`, the command installs the copy, writes the entry with `"approval": "REQUIRED"`, opens one plugin approval per database and prints a link to the plugin approval page (`--json` for agents). The page says who vouches for the plugin and warns plainly about an unknown local one. You approve with your passkey there; the engine's local pages relay the signature, or you give the agent the code the page shows and it runs `basalt plugin approve <code>`. `basalt plugin list` shows each agent's approval state. Turning a plugin off and on again, or adding an agent back, always needs a new signature: `disable` and `remove` end the old approval, and `add` and `enable` end it before they write anything. An unsigned plugin can be added this way. `basalt plugin trust` stays refused for agents, a person at a terminal without the flag gets the consent screen as before, and service mode is unchanged.
- A plugin entry in `engine.json` can carry `"approval": "REQUIRED"`, and on an engine an agent operates every entry requires approval, key or not (same-user mode only; in service mode nothing changes and the key is refused). The engine then serves the entry to an agent only when that agent's database holds a signed plugin approval naming the agent that matches the installed copy and its settings exactly; the plugin may be unsigned. Otherwise the entry is withheld from that agent, and `status` shows `PLUGIN_AWAITING_APPROVAL`, `PLUGIN_APPROVAL_EXPIRED` or `PLUGIN_APPROVAL_MISMATCH` (naming the fields that differ) with the steps to take; on a guard older than schema version 5 it shows `PLUGIN_UNAVAILABLE` with the upgrade. A withheld entry blocks none of the agent's calls. Turning an approved entry off, or changing it, ends its approval: turning it on again needs a new signature.
- In same-user mode the engine no longer needs a restart after you approve a plugin. It reads `engine.json` every second and, while a plugin waits for approval, each agent's approvals every 2 seconds (every 15 seconds otherwise), and starts the plugin within a few seconds of your signature. Turning a plugin off, removing it or removing an agent from it stops it within about a second, for any plugin, and a plugin whose approval no longer matches stops too. `basalt plugin add`, `enable`, `approve`, `disable` and `remove` no longer print a restart command there. Adding or changing a plugin that does not require approval, at a terminal, still takes effect at the next start. If `engine.json` changes into something the engine cannot read, nothing that runs changes and `status` shows `PLUGIN_CONFIG_INVALID` until it is fixed. When an agent's database does not answer, what runs for it stays as it is and the engine asks again after 2 seconds, doubling up to a minute. Service mode is unchanged.
- A service-mode engine keeps plugin entries of its own, added without `sudo` over its person socket. Seven new person socket methods upload a plugin's files in parts, open a change, list, relay a signature, disable and remove. The engine stages and checks the copy itself under its state directory, keeps the entry in `<stateDir>/plugins.json` with `"approval": "REQUIRED"`, and opens one plugin approval per database with the listed agents' own credentials. Nothing is written outside the state directory. An upload is capped at 64 KiB per part, 256 MiB and 1,024 files, the copies and open uploads together at 1 GiB, at most 4 uploads may be open and 16 entries kept, and an unfinished upload is dropped after 15 minutes. Disabling or removing such an entry ends its signed approval at once, so turning it on again needs a new signature. An entry whose name and instance `engine.json` holds cannot be added this way, and `auth` is refused for these entries.
- In service mode a plugin can be added without `sudo`. On a laptop where `basalt init` installed the engine as a background service, `basalt plugin add`, `enable`, `disable`, `remove`, `list` and `approve` run without `sudo` talk to the engine over its person socket, so an agent can add a plugin and hand over the approval link, and the wait on `enable --approval-id` works there too. Once a person signs the approval with a passkey, the engine starts the plugin within seconds as its own child, running as the engine's OS user without the isolation a plugin added with `sudo` gets (the page says so), and stops it when it is turned off. No restart is needed. An engine running as root, or one whose agent runs as a user in the engine's group, starts no such plugin. Plugins added with `sudo` keep running under their own unit and OS user as before, and `sudo basalt plugin add`, `enable`, `disable` and `remove` refuse a name the engine keeps itself.
- `basalt plugin enable <name> --approval-id <id> --json` waits, up to 90 seconds by default (`--wait`, at most 110), until the plugin runs on that signed approval, and says `RUNNING`, so an agent can tell you "done" in the same turn. `add` and `enable` still hand the link over at once, with this wait as the agent's next step; `--wait` on them waits before printing.

### Changed

- Upgrading no longer needs your agent's MCP client restarted: `basalt mcp` waits up to 15 seconds for a restarted engine and sends a read the engine dropped once more. Writes, approvals and reverts are never sent twice.
- When `basalt` runs under an agent (Claude Code, Codex, Gemini CLI, Cursor's agent, OpenCode, or `BASALT_AGENT_CONTEXT` set), every command that needs the database admin connection string refuses before reading it, and tells the agent to make a setup code with `basalt init --remote` or to give the person the command. An admin connection string in `BASALT_ADMIN_DATABASE_URL` there is not used, and `basalt` says to change that password.
- `basalt init --help` shows only the setup-code path when an agent reads it, `basalt --help` ends with the rule for agents, and the MCP instructions tell the agent never to ask for or accept the admin password.
- Every MCP tool refuses a call whose arguments hold a `postgres://` or `postgresql://` URL with a password (`INVALID_ARGUMENT`, reason `ADMIN_CREDENTIAL`), before it reaches Postgres. The value is never recorded or logged, and the next steps tell the agent to ask the person to change that password.
- When `claude` is on your `PATH`, `basalt init` offers `claude mcp add --scope local ...` and says the server is registered for this project directory only. `docs/mcp-clients.md` shows the per-project setup for `.mcp.json`, Codex and OpenCode.
- Release binaries embed `golang.org/x/crypto` v0.59.0, so binary scanners no longer flag GO-2026-5932. BasaltDB never called the package involved.

### Fixed

- A call that `basalt mcp` sends just as the engine stops for a restart goes to the restarted engine. It no longer fails with "the call may or may not have run" when the old engine never received it.
- `basalt log` keeps its other health output when the plugin entries cannot be read, and prints one `Plugins: could not be read (...)` line instead of failing. The `Plugins:` line and the health answer list at most 20 entries and say how many more there are.
- `basalt log` and the engine no longer report "ledger chain broken" on a new, untouched ledger after the database was recreated the same way, for example after removing the Postgres container and running the quickstart again. The guard now identifies each install by a random id instead of the schema's oid, which repeats in a cluster made the same way. An old pin is reported as a reinstall with its notice instead.

### Security

- The release `SHA256SUMS` is signed with keyless cosign, and the signature is attached to the release as `SHA256SUMS.sigstore.json`. `SHA256SUMS` now also lists the portal checksum, so one signature covers every file. See [docs/install.md](docs/install.md) to check it with `cosign verify-blob`.

## [0.0.1-alpha.2] - 2026-11-15

### Fixed

- A connection to the vault that BasaltDB ends itself, for example after the link is rotated, ended, or a session times out, now closes with its reason (such as `LINK_REFUSED` or `TIMEOUT`) instead of an abnormal closure without a code. The session always ended; only the reason could be lost.
- A data race in the vault session's idle timeout, seen only with very short idle timeouts (the default is 5 minutes).

### Changed

- Release binaries are built with Go 1.26.11, the toolchain set in `go.mod`, instead of Go 1.26.0.

## [0.0.1-alpha.1] - 2026-11-15

### Fixed

- The release publishes the Homebrew formula. The 0.0.1-alpha release has the binaries but no formula, so `brew install` starts with this version.

## [0.0.1-alpha] - 2026-11-15

The first public alpha, for macOS and Linux (amd64 and arm64). Expect bugs and breaking changes between alpha releases.

### Added

- The engine and its MCP server: an agent reads and writes your Postgres through BasaltDB, with a scoped role and no database URL of its own.
- The guard, installed in your own Postgres by `basalt init`: it records every agent write with the old values, refuses schema changes and writes of more than 50 rows, and holds writes of 11 to 50 rows and every DELETE for your passkey approval.
- Undo for a run, a single change or a task, signed with your passkey. Rows changed after the agent are left as they are and listed.
- The CLI: `init`, `status`, `log`, `revert`, `upgrade`, `uninstall`, `service` and `classify`.
- Setup for an agent on another machine, with a setup code (`basalt init --remote`).

### Changed

- The guard's schema is kept as SQL files under one version, 1 (`internal/guard/schema/`).

### Known limits

- Windows is not built yet.
- See the [limits page](https://docs.basaltvault.app/limits/) for what BasaltDB does not catch.
