## Database certificates

How the engine and the connect service decide to trust a database's TLS certificate: trust profiles, and the pins a person makes on first use or from the connect page. Moved whole from [Setup](setup.md#setup).

### Trust profiles

`basalt trust` is removed. A certificate no public authority signs is pinned on the setup page (persona 1) or the connect page (persona 2). The `trust.d` profile files stay, as data the engine reads, so an operator can still place a profile file by hand.

A trust profile says which root certificates verify a database's certificate beyond the system's authorities, and for which hosts. The engine and the CLI apply them on every connection they open with `sslmode=verify-full`: the agent's credential, the hand-off probe ([The engine and a connect-only code](setup.md#the-engine-and-a-connect-only-code)), init's probes (step 2 of [`basalt init --remote`](setup.md#basalt-init---remote-the-engines-machine)) and the CLI's own connections. A matching profile's roots are **added** to the system's authorities, never in their place, and only for its hosts; each profile has its own pool, so one profile's roots never verify another profile's hosts. The host name is always checked. `verify-ca`, `require` and weaker modes are unchanged.

**The profile.** One JSON file per provider or host, its PEM files beside it:

```json
{ "name": "supabase",
  "match": ["supabase.co", "supabase.com"],
  "roots": [ {"file": "supabase-2021.pem", "sha256": "700723581420dd1ac98fd7e9ac529f0ef210eadcaf87fc868a3ad7d114c2f3b7"},
             {"file": "supabase-2025.pem", "sha256": "5865d2b26f6128e5795a13ae58b6543599bdb82d808f7f62e3c9a8d7e8527970"} ],
  "source": ["https://supabase-downloads.s3-ap-southeast-1.amazonaws.com/prod/ssl/prod-ca-2021.crt",
             "https://raw.githubusercontent.com/supabase/cli/develop/apps/cli/src/command-internal/supabase-ca-templates/prod-ca-2025.ts"] }
```

- `name`: lowercase letters, digits and dashes, up to 63; the file is `<name>.json`, so two files never hold one name.
- `match`: host suffixes, compared in lowercase without a trailing dot, on a label boundary: `x.supabase.co` matches `supabase.co`; `evilsupabase.co`, `supabase.co.example.com` and the bare `supabase.co` do not. An entry starting with `=` is one exact host, a name or an address (`=db.example.com`, `=203.0.113.7`). No wildcards. At most 32 entries.
- `roots`: up to 16 files next to the profile, each one or more PEM certificates, each a CA (`basicConstraints CA:true`), up to 1 MiB. A profile whose every `match` entry is an exact host (a pin) may hold a certificate that is not a CA: the server's own, when it sends no other ([Pinning on first use](#pinning-on-first-use)). `sha256` is the SHA-256 of the file's bytes, in hex of any case, with or without colons. A mismatch, a certificate that is not a CA, or anything in the file but PEM certificates refuses the whole profile: a swapped file never loads.
- `source` (optional): where the provider publishes each roots file, one URL (`https`) per file in the order of `roots`, for `make check-provider-roots`.
- `disabled: true` (an operator profile only, with nothing else but `name`): turns off the built-in profile of the same name.
- `verify` (optional): `full`, the default (the chain against the system's authorities and the profile's roots, and the host name), or `ca`, accepted only on a profile whose every `match` entry is an exact host: the chain must end at one of the profile's own roots (not the system's) and the host name is not checked, for a server whose certificate does not name the host ([Pinning on first use](#pinning-on-first-use)).

Unknown keys are refused.

**Where profiles live.**

1. **Built-in**, embedded in the binary: `supabase` (`supabase.co`, `supabase.com`: Supabase's databases `db.<ref>.supabase.co` and its pooler `*.pooler.supabase.com`, `*.pooler.supabase.co`; its two self-signed roots, both named Supabase Root 2021 CA with different keys, the 2021 one valid 2021-04-28 to 2031-04-26, fingerprint `80:70:25:AD:50:D4:ED:21:9D:2C:9C:7D:29:9C:00:4F:82:4E:B0:0C:F7:F6:5A:FE:F6:07:D0:7B:72:E6:CA:FA`, the 2025 one valid 2025-09-03 to 2035-09-01, fingerprint `5F:9B:77:95:1A:7A:A1:30:3F:9B:58:EE:A9:BF:A8:9E:35:8C:FD:C1:5F:97:86:FF:10:D4:93:0A:72:2C:9A:E2`; a chain under either verifies) and `aws-rds` (`rds.amazonaws.com`, `rds.amazonaws.com.cn`: Amazon RDS and Aurora; AWS's global bundle, `https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem`, one root per region and key type, 114 on 21 November 2026, file SHA-256 `90a6f1a7978a1b1b096dca6c57511ca48d3b8cf052f8e704baf358f34ea2f21b`; it holds no root for the China or GovCloud regions, which AWS publishes separately: hosts there are matched and get this bundle, which cannot verify them, so they need an operator profile or the person's own `sslrootcert`). The engine has no provider-specific code: a new provider is a new profile, files only. Each file is carried byte for byte as its provider publishes it.
2. **Operator**, in `trust.d`, the directory next to the engine's config (`engine.json`), written by the pins of the setup pages ([Pinning on first use](#pinning-on-first-use)) or by hand. Read with the rules the engine applies to `engine.json` and the credential file: `trust.d` and every directory above it owned by root or the config directory's owner (the engine's OS user) and not writable by group or others, reached without following a symlink anyone but root controls; each file a regular file with one link, owned by root or that owner, not writable by group or others, opened without following a link and read through the descriptor that was checked. Only `*.json` files that are not hidden are profiles; the roots files they name are read the same way. At most 64 profiles load. A file that breaks a rule, or a profile that does not load, is **refused**: `status` names it (`TRUST_PROFILE_REFUSED`) and the engine's log says why. It never brings roots back: a refused `<name>.json` named after a built-in keeps that built-in off (the file may have meant to disable or narrow it) until it is fixed or removed; any other refused file changes nothing. A `trust.d` that breaks a rule is refused whole. No `trust.d` is no operator profile. An operator profile with a built-in's name replaces that built-in (or turns it off with `disabled`). An operator suffix entry may not be a public suffix on its own (a single label such as `com`, a country's second level such as `co.uk`, a zone a provider hands out to many parties such as `github.io` or `s3.amazonaws.com`; Go's public suffix list, ICANN and private entries, plus a short list of shared cloud and database zones it treats as ordinary domains: `amazonaws.com`, `amazonaws.com.cn`, `azure.com`, `cloudapp.azure.com`, `windows.net`, `rds.amazonaws.com`, `rds.amazonaws.com.cn`, `database.windows.net`, `postgres.database.azure.com`): such a profile would be a global root by another name. Profiles are read again for each new connection (a single connection when it is opened, a pool for each connection it adds), so a profile added to `trust.d` applies from the next connection, with no upgrade and no restart. Built on linux and darwin; elsewhere only the built-in profiles apply.

**Precedence**, per host, first match wins:

1. The connection names its own roots: `sslrootcert` (or `PGSSLROOTCERT`, a service file, `~/.postgresql/root.crt`, `sslrootcert=system`). It keeps exactly those.
2. A profile with an exact-host entry for the host (`=host`), the operator's before a built-in.
3. The operator's suffix profiles, longest matching suffix first.
4. The built-in suffix profiles, longest matching suffix first.
5. The system's authorities alone.

Ties go to the profile name that sorts first. In a connection string with several hosts, each host is matched on its own.

**Status.** The `status` tool and `basalt status` report `trust` for the agent's database (the first host of its connection string): `host`, `applies` (`PROFILE`, `SSLROOTCERT`, `SYSTEM`, or `NOT_VERIFIED` when `sslmode` is below `verify-full`), and for a profile its `profile` name, `origin` (`BUILT_IN`, `OPERATOR`), `verify` (`CA` for a pin with `verify: ca`, else absent), `rootCount` and up to 8 `roots` (`subject`, `sha256`, `notAfter`), those that expire first. When a root of that profile expires within 90 days or has expired, `status` warns `TRUST_ROOT_EXPIRING`, naming the profile, the root and the date. A refused `trust.d` file is `TRUST_PROFILE_REFUSED`, one per file. A database whose certificate does not verify is `CERTIFICATE_NOT_VERIFIED`, naming the host and the fix that can work ([Next steps](next-steps.md#next-steps)): a profile file for it, or `sslrootcert`; when the connection names its own roots, that root file, since no profile applies then; when its `sslmode` is below `verify-full`, `sslrootcert`, since profiles apply only with `verify-full`. The CLI's own connections that fail on the certificate say the same in their error. Without `--config`, every command reads the `trust.d` of the config it would use (the per-user config `basalt init` left when nothing is installed system-wide, else the system default).

**Refresh.** Providers add roots (AWS adds one when it opens a region), so `make check-provider-roots` reads each built-in profile's `source`, downloads each file (for a source that serves code, such as Supabase's 2025 root in `prod-ca-2025.ts` on the `develop` branch of `supabase/cli`, the PEM inside it) and compares its SHA-256 with the carried file's. It needs the network and is not part of CI; it is on the release checklist. When it fails, check that the change is only new roots from the provider, replace the file, and update both pins (the profile's `sha256` and the test's).

Other managed providers: Neon and Azure Database for PostgreSQL use certificates the system's authorities verify; Google Cloud SQL, DigitalOcean, Aiven, Heroku and Railway use a CA per instance, cluster or project, or a self-signed certificate, which a pin from the setup page, an operator profile placed by hand (with `=host` or the provider's domain for that instance) or the person's own `sslrootcert` names.

### Pinning on first use

For a host no profile covers whose certificate verifies against no authority this machine trusts (Google Cloud SQL, DigitalOcean, Aiven, a self-signed database), the person can pin the certificate authority it presents, for that host only, the way SSH's `known_hosts` does. Pins are made only on a setup page: the local setup page's install ([The database certificate](setup-page.md#the-install-of-a-real-database)) and its `TRUST` fix ([The Update check](setup-page.md#the-update-check)), and the connect page ([Pinning from the connect page](#pinning-from-the-connect-page)). Never by the engine on its own, never from an MCP call or a command: an agent cannot create trust. The pins the engine writes without the local page are for a certificate authority the person trusted on the connect page that the engine's own reading of the chain matched.

- **What is sent first.** Before anything else reaches the server (before the admin login, before init's probes), the reader connects, sends Postgres's `SSLRequest`, completes a TLS handshake that does not verify the certificate, only to read the chain, and closes the connection. No startup message, no user name, no password. A server that offers no TLS, or a chain that cannot be read, gets no question. A connection string that names its own roots (`sslrootcert`) or uses no TLS gets no question either: no pin would apply to it.
- **What is shown.** The host and the chain's top certificate (the root when the server sends it, else the highest one it sends): its subject, its SHA-256 fingerprint (of the DER, uppercase hex pairs with colons) and its expiry, and the advice to check the fingerprint against the provider's console. When the chain verifies against the system's authorities, or a profile covers the host, there is nothing to pin. A chain that does not verify even against its own top (expired, not for a server, incomplete) cannot be pinned: name its CA with `sslrootcert`.
- **The question.** `Trust it for this host only?`, default no, on the page.
- **What yes writes.** An exact-host operator profile in `trust.d`: name `pin-<host>` (the host's letters and digits, the rest as dashes, up to 63), match `=<host>`, the top certificate in `pin-<host>-<first 16 hex of its SHA-256>.pem`. It is the one profile for that host (precedence 2 above). The page's admin login uses `sslmode=verify-full` against the accepted certificate alone, so the admin password reaches only a server that presents it, and the agent's connection string gets `sslmode=verify-full`, so the pin applies.
- **Name-only failures.** A server certificate that does not name the host (Cloud SQL's default, for a connection by IP address) fails `verify-full` even with the right root. Only when the chain verifies against the top but not for the host name does the page say so (`... for <host> only, with the host name not checked?`), and the pin then carries `"verify": "ca"`: the chain must end at the pinned certificate, the name is not checked.
- **Public authorities.** A chain whose top is, or that chains to, an authority in the system's trust store is never pinned, with or without the name. With the name it verifies and needs no pin. Without it, it failed on the name, the fix is the host name its certificate names, and a `"verify": "ca"` pin would accept every certificate that authority issues, for any name, as the host. The page says so and pins nothing. An operator profile with `"verify": "ca"` whose root is in, or chains to, the system's store is refused when `trust.d` is read (`TRUST_PROFILE_REFUSED`). Public means the Mozilla root store the binary carries, checked the same way on every system, plus whatever the system's own store holds (an administrator's roots included). A system store that cannot be read leaves the Mozilla roots to decide.
- **Audit.** Whoever holds the admin connection records the pin in the ledger with `basalt_meta.record_trust_pin(host, port, sha256)` (admin only; [Schema version 6](basalt-meta-schema-versions.md#schema-version-6-trust-pins)), appending `TRUST_PIN_RECORDED`, in the job's transaction: the local page's install and `TRUST` fix, and the connect service's `RunSetup` when it logged in against a `trustRoot`. The engine never reads trust from the database (it must trust the connection before it reads anything); `status` reads the record afterwards and warns `TRUST_PIN_MISMATCH` when the ledger's latest pin for the database's host and port names another certificate than the engine's. No record is no problem. The `TRUST` fix records the engine's pin, which clears it.
- **On change.** A pinned host presenting another chain top is refused: `status` reports `TRUST_ROOT_CHANGED` (`ERROR`, for a `pin-<host>` profile only), naming both fingerprints (the engine reads the chain it presents with the TLS handshake alone, only for a pinned host whose certificate did not verify), and its step is to run `basalt init` (`basalt init --remote` on an agent-operated engine). The Update check shows the new certificate, and the `TRUST` fix replaces the pin on the person's yes: the new PEM file, then the profile, then the old PEM file removed, under the config lock. On persona 2 the connect page asks, and the engine replaces the pin only after its own reading matches ([Pinning from the connect page](#pinning-from-the-connect-page)). Never automatic.

### Pinning from the connect page

For a [connect-only code](setup.md#connect-only-setup-codes) the person has no terminal, so the connect page asks them to trust the certificate authority ([Trusting a certificate authority on the page](connect.md#trusting-a-certificate-authority-on-the-page)), and the engine pins it only when its own reading of the chain shows the same one. What the connect service hands over adds no trust by itself.

- **What the engine is handed.** With the address, `CollectAddress` returns `trustRoot`: the SHA-256 of the chain top the person trusted on the page, or empty. Empty is everything [The engine and a connect-only code](setup.md#the-engine-and-a-connect-only-code) says, unchanged.
- **What the engine checks.** For a host a trust profile covers, `trustRoot` is ignored and the profile decides. Otherwise, after its checks of the address and before any login, the engine reads the chain from the address it resolved, as [Pinning on first use](#pinning-on-first-use) does (`SSLRequest` and a TLS handshake that does not verify the certificate, nothing else), from its own network. A chain that verifies against the system's authorities needs no pin. A chain from a public authority that fails on the name is never pinned ([Public authorities](#pinning-on-first-use)): the probe is `TLS_NOT_VERIFIED`. Otherwise the chain's top must have the SHA-256 `trustRoot` names, and the chain must verify against that top (for the host name, or without it, `verify: ca`, when the server certificate does not name the host). Anything else, a malformed `trustRoot` included, is `TRUST_ROOT_MISMATCH`: nothing is pinned and no login is tried. On `SET_UP`, `status` then reports the problem `TRUST_ROOT_MISMATCH`, naming the database ([Next steps for a connect-only code](next-steps.md#next-steps-for-a-connect-only-code)), and the engine keeps collecting, so the person can open the same link again. On `PREVIEW` it reports `UNREACHABLE` with the reason `TRUST_ROOT_MISMATCH` ([The reach check](connect.md#the-reach-check)).
- **The probe.** The probe verifies the certificate against that top, held in memory as a pin, and nothing is written. A passed `PREVIEW` probe stands in for the `SET_UP` one only under the same `trustRoot` and when the chain read again for `SET_UP` gives the same pin (or, for both, none).
- **Yes.** Before it writes the credential, the engine writes the pin to the `trust.d` next to `engine.json`, as [Pinning on first use](#pinning-on-first-use) says (`pin-<host>`, match `=<host>`, `"verify": "ca"` for a name-only certificate). When a profile covers the host by then, it writes nothing, and the yes fails with nothing else written unless that profile is this same pin; the person then answers no, and the next `basalt init --remote` makes a recovery code. A pin written before a credential write that fails stays: it was approved and checked. The credential has `sslmode=verify-full`, so the pin applies. **No** pins nothing. The engine has no admin connection: the connect service recorded the certificate the person trusted in `RunSetup`'s transaction ([Audit](#pinning-on-first-use)).
- **A changed certificate on persona 2.** For an agent with a credential whose pinned host presents another chain top, `basalt init --remote` makes a code with no change, carrying `engine` (an `AGENT` code with no change, or an `UPGRADE` code from guard version 0 for an agent saved with every table in `public`: [step 3](setup.md#basalt-init---remote-the-engines-machine)), and marks the pending setup `certificateChanged` ([step 3](setup.md#basalt-init---remote-the-engines-machine)). The connect service accepts `trustRoot` for a code with a target that carries `engine`, logs in against it as for a connect-only code, records the pin with `record_trust_pin` in `RunSetup`'s transaction, and keeps a `SET_UP` hold of the code's target with that `trustRoot` ([The address hand-off](connect.md#the-address-hand-off)). While its pending setup is `certificateChanged`, the engine collects for its `setupId` as it does for a connect-only code. It takes the hold only when its address is the credential's own (host, port, database, Supabase ref; anything else pins nothing), reads the chain itself and checks it as **What the engine checks** says, then replaces its pin as the `TRUST` fix does ([The Update check](setup-page.md#the-update-check)) and logs in. It asks no `confirm_database` question: the database is the one its credential already names. `TRUST_ROOT_MISMATCH` pins nothing and keeps the setup pending. The setup then finishes as any pending setup does ([On the engine](setup.md#on-the-engine)). Limit: on persona 2 the engine's own reading is the only check against the hold, so Vault together with an attacker on the path between the bot's machine and the database can hand over a hold and present a chain that match, and so replace an established pin; neither one alone can.
- **The bot's pin on the page.** The service keeps no pin, so the code carries the engine's: `basalt init --remote` adds `trustPin` to its `AGENT` and `UPGRADE` codes, the SHA-256 of its `pin-<host>` certificate ([The setup code](setup.md#the-setup-code)). For a pinned host that is unchanged, the page says `This matches the certificate <bot> trusts.` and goes on with one click; for one that changed, it shows the new certificate with the pinned one as `Was:` and asks ([The bot's pin](connect.md#trusting-a-certificate-authority-on-the-page)). The hint changes only the words: the engine's pin changes only through a `certificateChanged` setup and its own reading. A person who trusts another certificate there than the engine's pin sees `TRUST_PIN_MISMATCH` in the bot's `status`.
