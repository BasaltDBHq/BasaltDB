### Engine records

M4.1 (owner decisions VC-21, CO-18, VC-27). The person's database records the engine's public identity key. Since [schema version 8](basalt-meta-schema-versions.md#schema-version-8-engine-address-removed) no address is recorded with it: the direct transport is [removed](cli.md#removed). Written only by the admin: by the setup flow in its install transaction. No command or page calls `revoke_engine`; it stays for an admin in SQL, and the engine only reports a revoked row ([Engine revocation](vault-channel.md#engine-revocation)).

| Object | Purpose |
|---|---|
| `engines` | One row per engine key the person recorded: `engine_id text` primary key (the [engine id](vault-channel.md#engine-keys), 22 characters, computed in Postgres from the key, never taken as given), `public_key bytea` (the signing key's 91-byte SPKI DER), `recorded_at`, `recorded_by` (`session_user`), `updated_at`, `revoked_at`, `revoked_by`. Rows are never deleted: a revoked engine stays for the record. No agent role may write it |
| `agent_engines` | What an agent role may `SELECT`: `engine_id`, `public_key`, `recorded_at`, `revoked_at` of every row (engines are not per agent; a key is not a secret). The engine reads its own row through it |
| `record_engine(public_key bytea) returns text` | Admin only, not granted to agents. Returns the engine id. Refuses with `BS008` (`LEDGER_INPUT_INVALID`), nothing written: a key that is not a 91-byte P-256 SPKI with an uncompressed point (the DER prefix of `id-ecPublicKey` and `prime256v1`, then `0x04`), or whose point is not on the curve (`_p256_on_curve`), detail `ENGINE_KEY`; a key whose engine id is revoked, detail `ENGINE_REVOKED`. A new key is inserted with an `ENGINE_RECORDED` ledger row; a key already recorded changes nothing |
| `revoke_engine(engine_id text) returns int` | Admin only, not granted to agents. Marks the engine revoked (`revoked_at` `clock_timestamp()`, `revoked_by` `session_user`) and returns how many engines remain not revoked. Refuses an unknown or already revoked id (`BS008`, detail `ENGINE_UNKNOWN`, alike). Appends an `ENGINE_REVOKED` ledger row. Revoking the last engine is allowed: approvals keep working through long links |

Every function `SECURITY DEFINER`, owned by `<prefix>_guard`, no `EXECUTE` for `<prefix>_agents` or `PUBLIC`; `agent_engines` granted `SELECT` to `<prefix>_agents`. Clock: `clock_timestamp()`, as the person's other acts ([Hardening](basalt-meta.md#hardening)).

Ledger kinds `ENGINE_RECORDED` and `ENGINE_REVOKED`: `agent` the admin role, detail `engineId`, `by` (`session_user`), and for `ENGINE_REVOKED` `remaining`. Rows written before schema version 8 also carry `url` (and `previousUrl`), as they were written.

### Reinstalls on the record

M4 (owner decision of 14 Nov 2026 on reinstalls). Each engine pins the last chain head it verified (`<stateDir>/<agent>.head.json`). When the guard is uninstalled and installed again, that pin names a ledger that no longer exists. Checking the new ledger against it gives a false tamper alarm. Setting the pin aside quietly would hide a real attack: an admin-level attacker can dump `basalt_meta`, rewrite history with a consistent chain, and drop and restore the schema. So a reinstall sets the old pin aside, never silently. The witness that held the pin records the set-aside in the new ledger, and every engine shows it until an admin acknowledges it (acknowledgement by an admin passkey: Access and audit, later). Each engine is a witness; the Vault keeps heads too (later).

**The install.** From [schema version 2](basalt-meta-schema-versions.md#schema-version-2-install-ids), which this section describes, a guard install is identified by a random id the install writes (`installs.install`, a `gen_random_uuid()`), which agent roles read with `install_id()`. A new install (after the setup page's `REMOVE`, or `DROP SCHEMA basalt_meta`) gets a new id; an upgrade and running the install again keep it. A copy of `basalt_meta` (`pg_dump` and `pg_restore`, a template database, a physical backup or replica) keeps it too, so a pin is checked against a copy exactly as against the original. Before this, the install was the oid of the `basalt_meta` schema, which repeats: two clusters made the same way (a Postgres container removed and started again from the same image, then `basalt init`) give the schema the same oid, so the pin of the old ledger was checked against the new one and reported a broken chain. A pin carries the install it was verified on: the pin file adds `installId`. A pin without one (saved before install ids) is taken as a pin of another install, so it is moved or reported (below), never checked as the current install's.

| Object | Purpose |
|---|---|
| `installs` | This install's one row (`id boolean` primary key, always true), written by the install transaction itself. Running the install again keeps the row (`ON CONFLICT DO NOTHING`, `install` and `installed_at` unchanged); when the row is missing (deleted, or `basalt_meta` recreated outside the install), the next `basalt init` writes a new one, a new install. Columns: `install uuid` (random, `gen_random_uuid()`), `installed_at` (`clock_timestamp()`), `installed_by` (`session_user`), `vault_user text` (the Vault user the install ran for, from the transaction setting `basalt.vault_user` that the Vault's install path sets; null otherwise, and always null until the Vault installs, Access and audit). No agent role may read or write it |
| `install_id() returns uuid` | Granted to `<prefix>_agents`. `STABLE`. This install's id from `installs`, null when the row is missing. The engine pins with it; a null id fails its check with "basalt_meta has no install record; ask the agent to run basalt init again and use the setup page", so nothing is checked or set aside until an admin installs again |
| `record_pin_set_aside(p_seq bigint, p_hash bytea, p_install uuid) returns boolean` | Granted to `<prefix>_agents`. An engine calls it when its pin (`p_seq`, `p_hash`) was verified on another install (`p_install`). Refuses with `BS008` (`LEDGER_INPUT_INVALID`), nothing written: `p_seq` below 0, `p_hash` not 32 bytes or `p_install` null (detail `PIN_SHAPE`), `installs` without a row (detail `NO_INSTALL`, no install to set the pin aside on), `p_install` equal to the current install (detail `PIN_SAME_INSTALL`, a pin of this install is checked, never set aside). Appends a `PIN_SET_ASIDE` ledger row and returns true. A second call with the same `session_user`, `p_install`, `p_seq` and `p_hash` appends nothing and returns false |
| `pin_on_chain(p_seq bigint, p_hash bytea) returns boolean` | Granted to `<prefix>_agents`. True only when `p_seq` is after `chain_anchor`'s seq and the ledger row at `p_seq` exists, holds `p_hash` and recomputes to it, or `p_seq` equals the anchor's seq and the anchor's hash is `p_hash`. False for a pin before the anchor, which `verify_chain_from` and `check_head` accept as verifying from the anchor. Agents cannot read `chain_anchor` or other agents' ledger rows, so this is how a witness tells "my pinned entry is still here" from "the anchor moved past it". Reads only; returns no row data |
| `agent_reinstalls` | What an agent role may `SELECT`: every `PIN_SET_ASIDE` row of every agent (a reinstall concerns the whole database, so every engine shows it): `at`, `agent`, `pinned_seq`, `pinned_hash`, `pinned_install`, `install`, `installed_at`, `installed_by`, `vault_user`. No secrets: chain heads, role names and the Vault user's name, which the notice shows and the agent relays |

Every function `SECURITY DEFINER`, owned by `<prefix>_guard`; `install_id`, `record_pin_set_aside` and `pin_on_chain` are granted `EXECUTE` to `<prefix>_agents` only. `agent_reinstalls` is granted `SELECT` to `<prefix>_agents`. Clock: `clock_timestamp()`.

Ledger kind `PIN_SET_ASIDE`: `agent` the caller (`session_user`), detail `pinnedSeq`, `pinnedHash` (lowercase hex), `pinnedInstall`, `install` (install ids, as text), `installedAt`, `installedBy` and `vaultUser` (when set), copied from `installs` so the row stands on its own. `agent_reinstalls` shows it as it is (`pinned_install` and `install` as `uuid`).

**Who sets a pin aside.**

- **The engine** (upkeep, on start and every hour), with a pin of another install:
  1. It first checks the pin against the current chain. This step counts only when `pin_on_chain(seq, hash)` is true (through its anchor branch only when the anchor is the genesis, seq 0: a legitimate pin is at most an hour old and retention deletes rows only after a year, so a pin at a later anchor means the history before it was cut), `verify_chain_from` from the pin is intact, and the full `verify_chain()` is intact (so rows before the pin cannot have been re-chained either). Then this is the same ledger under a new install id: the `installs` row was deleted and `basalt init` wrote a new one, or the pin was saved before install ids. The engine moves the pin to the new install and records nothing in the ledger. It logs a warning naming both installs, the only trace that the install changed (`CHECK_HEALTH` returns `pinMoved`). A pin before the anchor fails `pin_on_chain` and goes to step 2. A restore or copy of `basalt_meta` keeps the install id, so it never comes here: its pins are checked as usual, and a copy whose history was rewritten reports a broken chain.
  2. Otherwise it reports the pin with `record_pin_set_aside` and then sets it aside. The full check covers the new chain, and every new pin carries the new install. A new install over a rewritten copy of the old ledger fails step 1, so it gets the notice.
  3. A call that returns false (this report is already recorded, for example when the pin file write failed after an earlier call) counts as recorded. When the call fails (the database is down, for example), the engine keeps the pin and reports the chain broken at it (`chainBrokenAt` at the pinned seq), without checking from it. It never sets aside a pin it did not record.
  4. It also keeps each set-aside it recorded in its own pin file (`setAside`: `pinnedSeq`, `pinnedHash`, `pinnedInstallId`, `installId`, `at`). It shows the notice from that copy as well as from the ledger, so deleting the rows or changing the view in the database does not hide what this witness saw.
- **`basalt log`** is removed; the engine is the one witness.

**The notice.** The engine, on every engine, reads `agent_reinstalls` and its own kept copy. It shows one notice per reinstall (one `install` with rows), newest first, at most 3, followed by "and N earlier reinstalls" when there are more:

```
This database's ledger was reinstalled on <installedAt> by <installedBy> (via Vault: <vaultUser>). Previous ledger ended at entry <n> (hash <h>), as reported with the credential of <agent>. If nobody on your team reinstalled Basalt, treat this as tampering.
```

- `(via Vault: <vaultUser>)` appears only when `vault_user` is set. `<installedAt>` is RFC 3339 UTC.
- When no ledger row records the install (the reader's kept copy has a report whose `PIN_SET_ASIDE` rows are gone), the first sentence reads "This database's ledger was recreated or restored outside basalt init (no install record), first reported <at>."
- Each witness keeps its own `<n>` and `<h>`. The notice uses the report of the reader's own credential when there is one, otherwise the earliest report. It is followed by one line per other agent credential that reported this reinstall, at most 5, each with that agent's earliest report and a count of its further ones: "Also reported with the credential of <agent>: entry <n> (hash <h>)[, and N more reports]." Then "and N more agents" when there are more. One agent's many reports therefore take one line and cannot crowd out real witnesses.
- No report replaces another, so an agent role that reports a false pin cannot overwrite a real witness's entry and hash.
- `<n>` is the last entry that witness verified, not necessarily the last the old ledger held.

The notice stays until an admin acknowledges it with an admin passkey, recorded in the ledger (Access and audit, a follow-up). Until then nothing clears it. The `status` tool carries it as the problem `LEDGER_REINSTALLED` ([Configuration and status](vault-channel.md#configuration-and-status)). Its `personMessage` is the notice of the newest reinstall: the first notice line only, then "Older reports stay in the ledger's install records." `vaultUser` is cut to 64 characters, so the message stays under 500 characters. `basalt status` prints that problem with the other problems. `basalt log` prints every notice in full on stderr before the change records, with the other warnings.

**Only an admin reinstalls** (Access and audit, AA-2). Both the removal and the install need the admin connection string, typed on the [setup page](setup-page.md#the-local-setup-page). Dropping `basalt_meta` needs its owner, and the install creates roles. An agent role owns nothing in `basalt_meta` and can do neither.

**Limits.**

- An agent role can call `record_pin_set_aside` with a pin it never held. That raises a false notice of its own, which names the agent's credential, and it changes no other witness's report. It can also append any number of such rows: a ledger write like any other agent write, with no rate limit.
- `installs` is only as trustworthy as the admin. Someone with the admin connection can write a row that names another user or Vault user, or change the install id. A changed id sends every witness's pin to the steps above (moved when the ledger is unchanged, otherwise reported with the notice); a deleted row stops every check until `basalt init` writes a new one. Neither is silent.
- A restore, or a new install over a copy, that keeps every entry up to the pin and rewrites only later ones passes the check (or moves the pin) with no notice, exactly as a rewrite in place would. Entries after the last pin are unprotected either way.
- An admin can move `chain_anchor` in place on an unchanged install; a pin older than the anchor then verifies from it. That gap is not covered here (a follow-up).
- The install identity is a random id (`gen_random_uuid()`, 122 random bits), so two installs share one only by copying `basalt_meta`. A copy is the same ledger: a faithful one verifies, a rewritten one reports a broken chain. A pin checked on a copy that lost entries since the pin (a restored backup older than the pin) or went its own way (a copy that took writes while the original kept going) also reports a broken chain: that ledger is not the one the witness saw. Getting such a copy onto the reinstall path takes a new install id, as above.
- That admin can also delete `PIN_SET_ASIDE` rows. Doing so changes the chain after the witness pinned it, so the witness's next check of the same install reports a broken chain, and its own kept copy keeps the notice.
- The witnesses rely on the guard's own code. `verify_chain_from` and `agent_reinstalls` run in the database, and an admin who can replace `basalt_meta` can also redefine them. The engine's kept copy covers a hidden view. Only a witness outside the database that recomputes the hashes itself covers a rewritten verifier (the Vault, later).
