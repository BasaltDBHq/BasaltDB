### Direct transport

M4.1 (owner decisions VC-16, VC-21, VC-25, VC-27, CO-18, OR-5, OR-6). For an agent-operated engine whose person does not use the hosted Vault: the person runs their own tunnel (Cloudflare Tunnel, Tailscale Funnel, a reverse proxy with TLS) to a loopback listener of the engine, and the portal page connects to it straight, at an address the person recorded with the admin credential and pinned on their device by hand. The session is the one above, byte for byte, with transport `DIRECT` in the [prologue](vault-channel.md#handshake): a tunnel that ends TLS sees only ciphertext, as the Vault does. Nothing here changes the `RELAY` transport or the engine's local pages.

**The engine address.** An origin `https://<host>[:<port>]`, the address the tunnel publishes. Who checks it (`basalt init --setup-code --engine-url`, `record_engine` in Postgres, the portal's pin page) applies the same grammar, refusing (never repairing) anything else:

- scheme `https` only; no user part, query or fragment, and no path but an empty one or `/` (the written form drops it);
- host: ASCII only, lowercase, at least two labels separated by `.`, each 1 to 63 characters of `a-z`, `0-9` and `-`, not starting or ending with `-`; at most 253 characters; no trailing `.`, no `%`, no `[`; an internationalized name is given in its `xn--` form (a Unicode name is refused, not converted, so no two checkers can map it differently);
- the last label starts with a letter, so no IP literal and nothing a browser's URL parser reads as a number (`2130706433`, `0x7f.1`, `127.1`);
- not `localhost` or a name under it, nor a name under `.local`, `.internal` or `.home.arpa` (the portal never calls a local engine or the person's local network, VC-25), and not `basaltvault.app` or a name under it;
- port: none (meaning 443), or decimal 1 to 65535 with no leading zero, other than `443`.

The pattern, shared by [`status.json`](../api/mcp/tools/status.json) and the tests: `^https://([a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?\.)+[a-z]([a-z0-9-]{0,61}[a-z0-9])?(:[1-9][0-9]{0,4})?$` (no lookahead, so Go, Postgres and JavaScript compile it alike), plus what a pattern cannot state: the host's 253 characters, the name exclusions, the port's range and `443`. Two limits no checker here can see: a browser may still refuse an `xn--` label that is not valid punycode (the pin page then cannot pin it, which fails safe), and a public name may resolve to a loopback or private address (`127.0.0.1.nip.io`); only the person records an address, so that is theirs to avoid. The written form, everywhere it is stored or compared, is the origin with no trailing `/`. A link never carries an engine address (a bot could change it).

**Where it is pinned.** Twice, by the person, and the bot can change neither:

- **In the person's database**, with the engine's identity key, by `basalt init --setup-code <code> --engine-url <address>` on the person's computer ([Version 33](basalt-meta-installs.md#version-33-engine-keys-and-the-pinned-address)). The setup code carries the key (`engine.publicKey`, [The setup code](setup-from-laptop.md#the-setup-code)); the address is given on the person's computer, never in the code. This record is what the engine reads to know its address and whether it is revoked.
- **On each device**, once, on the portal's pin page (OR-6, below). This pin is what the page trusts: it holds the address and the engine key, and the page compares every session's `engineKey` with it.

**The listener: `directAddr`.** A second listener of the engine, separate from the local pages, for the tunnel to forward to. `directAddr` in `engine.json`: a loopback `host:port` (`127.0.0.1` or `::1`), or `off`, the default. It is refused when the config is loaded unless `pagesUrl` is the portal (a local `pagesUrl` has the local pages instead, and a `localhost` passkey cannot sign on the portal), when it is not a loopback IP address with a port (the listener has no TLS: the tunnel ends TLS; the [listener rules](../AGENTS.md#listeners-and-local-sockets) hold), and when it is the same address as `pagesAddr`. Set with `basalt init --direct-addr <host:port|off>` (agent mode and `--remote`; saved in `initArgs`, so a re-run keeps it). An address it cannot bind stops the engine from starting, as for `pagesAddr`. It serves only these routes; any other method or path is `404` with an empty body, and it serves no page, script or `/api/v1/` route outside a session:

| Method and path | What |
|---|---|
| `GET /v1/engine` | The probe. `200` JSON, [`direct-engine.schema.json`](../api/mcp/vault/direct-engine.schema.json): `{ "engineKey", "engineId" }`, the signing key's SPKI (base64url) and its id, with `Cache-Control: no-store`. With an `Origin` of `https://portal.basaltvault.app` it adds `Access-Control-Allow-Origin` with that origin and `Vary: Origin`; with no `Origin` (the CLI's check, `basalt tunnel`) it answers without CORS; any other `Origin` is `403`. It is public: the key is not a secret, and nothing trusts this answer alone (the page's pin compares it by hand, every session checks the key again) |
| `GET /v1/session` | A WebSocket upgrade for one link session. `Origin` must be exactly `https://portal.basaltvault.app` (`403` otherwise, also when absent); no subprotocol, no extension (no `permessage-deflate`, which would leak sizes). A request that is not an upgrade is `400` |

- **Host.** Both routes take the request's `Host` only when it is an address recorded for this engine's key in the database of at least one agent the engine serves, revoked or not (so a revoked engine's honest `ENGINE_REVOKED` reaches the page) (read as below), compared as host and port: `:443` is dropped from the `Host` first, so `engine.example.com` and `engine.example.com:443` are the same address, and any other port must match the recorded one. Anything else, a loopback name included, is `400` before the route runs: these routes are reached only through the tunnel. The engine checks against the addresses it last read; a `Host` not among them makes it read the records again first (at most once every 10 seconds), so an address the person just recorded works without a restart. The engine never trusts `X-Forwarded-For`, `Forwarded`, `X-Real-IP` or `X-Forwarded-Host`.
- **The probe is not a session.** `GET /healthz` stays on the local pages listener only and keeps its loopback-only `Host` check; the direct listener has no `/healthz`. (The design's `/healthz` with CORS is replaced by `/v1/engine`, because the pin page needs the key.)
- **Headers.** The `websec` security headers on every answer. No cookies are read or set.

**The socket.** After the upgrade, binary WebSocket messages exactly as on the [page's socket](vault-channel.md#the-pages-socket) to the Vault: the page sends handshake message 1, then frames; the engine sends message 2, then frames. There is no `ROUTE` wrapping and no control message. A text message closes with `PROTOCOL`; a message over its [limit](vault-channel.md#limits) with `TOO_LARGE`. The engine's handshake time (10 seconds) runs from the upgrade.

- **The engine on message 1** does what it does on `RELAY`, in the same order, with transport `DIRECT` in the prologue and no `SESSION_OPEN` to compare `linkToken` with. Then, once the tag and the point are good, it reads its record in the link's agent's database (with that agent's credential, through `agent_engines`, at most 5 seconds): the key revoked closes with `ENGINE_REVOKED`; no record, or the session's `Host` not the address recorded there, closes with `LINK_REFUSED`, alike; a read that fails or takes longer closes with `TIMEOUT`. Only then message 2. So a link of an agent whose database never recorded this address does not open over it, even when another agent's database did.
- **Limits.** The [limits](vault-channel.md#limits) hold as on `RELAY`, and sessions on both transports count together towards the per-link and per-engine numbers. Rate checks the Vault makes on `RELAY` the engine makes here, before any public-key operation: at most 16 sockets at a time that have not finished the handshake (one more is answered `503` before the upgrade), and at most 600 upgrades per minute in all (`503` over it). Message 1 must arrive within 3 seconds of the upgrade (`TIMEOUT`); the request line and headers within 5 seconds, at most 8 KiB of them (`431` over it); at most 64 connections open on the listener before an upgrade or a probe's answer. The per-link handshake limit is counted before the tag ([Handshake](vault-channel.md#handshake)), so whoever sees a `linkToken` (the tunnel, another pinned engine the page tries) can spend that link's budget for 10 minutes and tell a live token by `RATE_LIMITED`: a denial of service and one bit of metadata, never a session. The engine cannot tell clients apart behind a tunnel, so these numbers are for the whole listener.
- **Close codes.** The engine sends the codes of the [registry](vault-channel.md#close-codes) that name it. The Vault's codes (`LINK_UNKNOWN`, `ENGINE_OFFLINE`, `AUTH_FAILED`, `REPLACED`) never occur on `DIRECT`: a link the engine does not hold is `LINK_REFUSED`, and an engine that does not answer is a failed connection.

**Which transport, and which link.** An engine hands over a portal short link for an item when the Vault registered it ([Configuration and status](vault-channel.md#configuration-and-status)) or when the item's agent is **direct-ready**: `directAddr` is not `off`, and the agent's database records this engine's key, not revoked, with an address. Otherwise the long link, as before. The link is the same in both cases (`https://portal.basaltvault.app/approvals/<approvalId>#s=<secret>`), with no engine address and no transport hint. On the portal, the page (VCT-4):

1. Tries `DIRECT` first, over each engine this device pinned, the one that last opened a session first, one at a time: `GET <address>/v1/engine` (`credentials: "omit"`, `cache: "no-store"`, 5 seconds), and only when its `engineKey` equals the pin, `wss://<host>/v1/session`. An engine that closes with `LINK_REFUSED` does not hold this link, and one that closes with `ENGINE_REVOKED` may be revoked: either way the page tries the next pin. At most 8 pins per device.
2. Then `RELAY`: planned, not built. The portal has no relay transport yet, so the page skips this step.
3. When neither opens a session, the page says the link could not reach the engine, and how to go on: add this engine on this device (the pin page), ask the agent for the link again, or the long link (`basalt approve`, `list_pending`).

`linkToken` is a routing value, not a secret ([Link secrets in a session](vault-channel.md#link-secrets-in-a-session)), so trying it on another engine of the same person gives that engine no session: it cannot answer message 1 without the link's `psk`. It does learn that the person is opening a link, and the token, with which it can spend the link's handshake budget (above).

**Pinned key on `DIRECT` (VC-42).** On `DIRECT` the page compares the engine id computed from message 2's `engineKey` with the pinned one before it shows anything from the engine; a different key closes with `HANDSHAKE_FAILED`, and the page says this address now answers with a different engine and to check with the person's own computer (`basalt engine list --admin`) before pinning again. So on `DIRECT`, unlike `RELAY`, the engine's identity is checked by the page, and receipts in the page are checked against the pinned key ([Receipts](vault-channel.md#receipts)). A revoked engine's honest answer is `ENGINE_REVOKED`. A close code travels outside the session and anyone on the path can forge one (VC-39), so the page changes no stored state on it: it shows that the engine may be revoked, says to check with `basalt engine list --admin` on the person's own computer, and offers to remove the pin, which it does only when the person confirms.

**The pin page** (VCT-4, OR-6). `https://portal.basaltvault.app/engines/add`: the person types the address; the page checks it by the rules above, fetches `/v1/engine`, refuses an `engineId` that is not the hash of `engineKey`, and shows the address and the [fingerprint](vault-channel.md#engine-keys). The person compares the fingerprint with the one `basalt init --setup-code` printed on their own computer (or `basalt engine list --admin`), then confirms. The page keeps `{ "address", "engineKey", "engineId", "addedAt", "lastUsedAt" }` per pin in the portal origin's `localStorage` (and, under the provisional CSP below, the addresses alone in a cookie); `https://portal.basaltvault.app/engines` lists the pins and removes one. Nothing about a pin goes to the Vault, the engine or a link. A pin is per device and per browser profile: each device pins by hand, once (OR-6).

**CSP (OR-5, TP-1).** A portal page that may run `DIRECT` (`/approvals/<id>`, `/reverts/<id>`) is served with `connect-src 'self'` plus, for each pinned address, that origin (`https://<host>[:<port>]`) and its WebSocket origin (`wss://<host>[:<port>]`), and nothing broader (never `https:` or `wss:`); the relay transport adds `wss://relay.basaltvault.app` to the base when it lands (VC1-9). Decided by the owner on Nov 14, 2026 (TP-1):

- **The cookie.** After a pin is added or removed, and on every portal page that finds it stale, the page writes the pinned addresses to a first-party cookie `__Host-basalt-engines` on `portal.basaltvault.app`: the addresses in their written form, separated by `|` (a cookie value holds no comma, semicolon or space, and no address holds a `|`), the one that last opened a session first, at most 8; `Secure; Path=/; SameSite=Lax` (not `Strict`: a link clicked in a web chat is a cross-site navigation, and the edge must see the cookie on it; the cookie carries no authority), no `Domain` (the `__Host-` prefix makes the browser refuse it otherwise, so no other `*.basaltvault.app` host can set it), `Max-Age` 400 days, and `Max-Age=0` when no pin is left. Only the page sets it; nothing else on the portal reads or writes cookies. A page whose served policy (its `<meta>` `connect-src`, which the edge rewrites with the header) does not list every pin, or whose cookie does not, rewrites the cookie and reloads once per tab, so its policy lists them.
- **The edge function.** A Cloudflare Pages Functions middleware in front of the portal (`functions/_middleware.js`, logic in `web/edge/portal.js`, run only for `/approvals/*`, `/reverts/*` and `/engines/add` by `_routes.json`) reads the cookie (its name matched exactly, trimming only spaces and tabs; two cookies of that name in one request, which only another host can plant, count as none) and adds an origin only when it is an address in its written form by the [grammar](#direct-transport) (the same cases as `internal/engineaddr`, `internal/engineaddr/testdata/addresses.json`); anything else is dropped, and with nothing left the strict default of `_headers` is served unchanged. It adds the same sources to the `connect-src` of the page's own `<meta>` policy (a browser enforces both), sets the other security headers of `_headers` itself, and never answers a conditional request with `304`.
- **Per person, never shared.** Every answer of the function carries `Cache-Control: no-store` and `Vary: Cookie`, is built for its request alone, and leaves the static asset it starts from unchanged, so one person's policy is never served to another (`web/edge/portal.test.mjs`).
- **The pin page.** `/engines/add?address=<address>` (the address URL-encoded, in its written form, given once) is served with `connect-src 'self' <address>` (the `https` origin only, for the probe) and nothing from the cookie; `/engines/add` without it, and `/engines`, keep the default.
- **Defence in depth.** The CSP limits where a page that is already ours can connect. It is not what makes signing safe: that rests on subresource integrity on every script (VC1-18), the engine record pinned in Postgres ([Version 33](basalt-meta-installs.md#version-33-engine-keys-and-the-pinned-address)) with the pinned key checked in every handshake, and the person's passkey, verified in Postgres.

With the cookie, the portal's host sees every pinned address of the device: metadata, like the Vault's. The pages of the engine's own listeners keep the `internal/websec` policy, and `basalt portal verify` compares the portal's header with a cookieless request's (the default). When the person has a Vault account, the allow list will come from the server-side record instead of the cookie (follow-up with the Relay and Vault milestone).

**Revocation by the person.** `basalt engine revoke` on the person's computer, with the admin connection string ([CLI](cli.md#cli)), calls `revoke_engine` ([Version 33](basalt-meta-installs.md#version-33-engine-keys-and-the-pinned-address)). Revocation is per database: `engines` has no agent column, so it applies to every agent of that database. On `DIRECT` the engine reads its record per agent database at every session (after message 1's tag and point checks), before answering each request of an open session and every minute for the agents with one open, so an open session is closed at its next request, and within a minute of a revoke while the reads succeed. When a database revokes its key, the engine, for every agent in that database, on `DIRECT` today: stops handing over direct portal short links (long links still work: the person's passkey signs and Postgres checks, whatever carries it) and closes the agent's open direct sessions and refuses new ones for the agent's links with `ENGINE_REVOKED`. On either transport it reports `engineRecord.state` `REVOKED` and the problem `ENGINE_REVOKED` in `status`. A failed read on `DIRECT` refuses a new session, as above, and a failed re-read during an open session keeps it open (only a revoke ends it). A revoked key is never recorded again: after `basalt engine rotate-key` the new key is recorded with a new setup code. A revoked engine on a compromised server can ignore all this; it still cannot sign anything a person did not, and the record tells the person not to open its links.

**Planned, with the relay transport (not built in M4.1).** The relay half of revocation is not built. With the Vault connected, a revoked key does not stop the engine handing over a relay short link, and the engine does not revoke the agent's live short links, unregister their tokens at the Vault or close relay sessions with `ENGINE_REVOKED`. It does not read its record at start, at every heartbeat or at a relay session, and it does not leave the Vault when every database it serves has revoked the key. When the relay work lands, a revoked database will do all of that for its agents, and on `RELAY` a failed read will keep the last state the engine read. Until then a person who revokes the engine should treat any relay short link it handed over as live.

**What the tunnel sees.** The tunnel provider sees what the Vault sees ([What the Vault sees](vault-channel.md#what-the-vault-sees)), minus link registrations: the engine's address, page IP addresses and user agents, `/v1/engine` probes, the number, sizes and timing of frames. It never sees a link secret, an item id, a row or a signature. A wrong or hijacked address can deny service, not read or forge: the page checks the pinned key in the handshake. The listener's routes face the internet through the tunnel, gated by 128-bit link secrets, by the [limits](vault-channel.md#limits) and by the `Host` and `Origin` rules above.

### Test vectors

Shared files under `api/mcp/vault/testdata/` (VC1-2: `link-derivation.json`, `engine-id.json`, `padding.json`, `handshake.json`, `frame.json`, `signature.json`, `receipt.json`), each one kind, in the format of [`vectors.schema.json`](../api/mcp/vault/vectors.schema.json): `LINK_DERIVATION`, `ENGINE_ID`, `PADDING`, `HANDSHAKE`, `FRAME`, `SIGNATURE` (every context above) and `RECEIPT`. Each case says what a receiver must do (`ACCEPT`, `REFUSE`, or a close code), so the refusals are pinned too: a tampered tag, a wrong `psk`, an invalid point, a compressed key, a reflected, replayed, reordered or spliced frame, non-zero padding, a signature from another context. Go tests and `node --test` read the same files; a mismatch fails `make ci`. Private keys are fixed 32-byte scalars so the bytes are reproducible (WebCrypto imports one as PKCS#8 without the optional public key and computes it); ECDSA signatures are randomized, so a vector pins one valid signature and a writer under test uses it instead of signing.

The Vault service's own vectors and tests live with it, privately.
