# BasaltDB contracts

Normative contract for the surfaces BasaltDB exposes: **MCP tools** served by the engine (through the per-agent shim), the **`basalt` CLI**, the **approval and revert pages**, and the **`basalt_meta` schema** the guard installs in the person's Postgres. This file and the section files it lists fix the wire rules. There is no REST API, no OpenAPI/AsyncAPI and no event stream: the only events BasaltDB emits are the plugin [notifier messages](contract/plugins-runtime.md#notifier-messages), as CloudEvents. The HTTP surfaces are the engine's loopback [local pages](contract/local-pages.md#local-pages) and, from M4.1, its [direct listener](contract/vault-direct-transport.md#direct-transport) behind the person's own tunnel, which serves only a probe and the encrypted link session. The local pages are the pages plus a same-origin relay for them, not an API for other clients. From M3.5 the same pages API also runs inside the end-to-end encrypted [Vault channel](contract/vault-channel.md#vault-channel), the one hosted piece before M4 (owner decision VC-1).

## Process: contract first

- A new MCP tool, a change to a tool's input or output schema, a new error code or a new `basalt_meta` table or function lands in a **contract-only PR** first: tool schemas under `api/mcp/`, the contract's index or section file if a convention changes, and the contract test that checks the served tool list against the schemas. No behaviour change in the same PR unless CI needs it.
- Every tool in `api/mcp/` declares a status, `IMPLEMENTED` or `PLANNED`. A contract test fails if a served tool is missing from the schemas, or an `IMPLEMENTED` tool is not served.
- One file per tool, `api/mcp/tools/<name>.json`: `name`, `status`, `milestone`, `description`, `inputSchema` (JSON Schema, `additionalProperties: false`), `outputSchema`, and `errors` (codes from the [Error codes](contract/error-codes.md#error-codes) table). The engine embeds these files and lists each tool's `inputSchema` as written, so the schema has one source. The contract test (`api/mcp/contract_test.go`) checks camelCase property names, SCREAMING_SNAKE_CASE enum values, closed input schemas, and that every declared error code is in the Error codes table.
- **Planned parts of a served tool.** A change to an `IMPLEMENTED` tool lands in its contract before the engine serves it. An input property whose `description` starts with `Planned (` is in the contract but not served: the engine leaves it out of the tool's listed `inputSchema` and refuses it as an unknown argument (`INVALID_ARGUMENT`) until the change that serves it removes the marker (`mcpcontract.Load` serves, `mcpcontract.LoadAll` is the contract as written). Likewise a [next-steps](contract/next-steps.md#next-steps) entry with `"planned": true` is contracted but not returned yet; its row in the next-steps tables starts its Steps with `Planned (`, and when it lands it replaces the served entry of the same key, if there is one. Output properties and enum values marked `Planned` in their description are not returned yet. A planned input property may not appear in its schema's `required`, `dependentRequired` or `oneOf`/`anyOf`/`allOf` (loading the contracts fails), so leaving it out never changes what the served schema accepts otherwise. **Version-scoped payload schemas are outside this convention**: a schema under `api/mcp/revert/` whose description names a `basalt_meta` version (`revert-binding.schema.json`, "the shape from basalt_meta version 20") describes that version's format only, as a whole, and the guards before it emit the older format its description names.
- Breaking changes are allowed until M4 (nothing has shipped). Record each one in the PR description.

## Wire format

- JSON keys we define (MCP arguments and results, the change record, CLI `--json` output, config) are **camelCase**. Exception: column names and values from the person's tables pass through exactly as Postgres returns them, except a `timestamptz` value, which follows the Timestamps rule below.
- **Enum values are SCREAMING_SNAKE_CASE** everywhere (Go consts, JSON, `validate` `oneof`, `basalt_meta` values, docs). Go identifiers stay PascalCase (`StatusApplied = "APPLIED"`).
- **IDs:** UUIDv7 for every id BasaltDB generates (`changeId`, run, task, approval), canonical text on the wire, `uuid` in Postgres. Row versions are `"xmin:<n>"`.
- **Timestamps:** RFC 3339 UTC with `Z` (`2026-11-10T06:02:11Z`), fractional seconds kept when present (`2026-11-10T06:02:11.513958Z`). This holds for the values of the person's tables too: a `timestamptz` column is reformatted to it wherever the engine returns row values to an agent or the person's CLI (`query`, `run_history`, `basalt log`, the lines of `preview_revert` and `revert_plan` and of `basalt revert`), whatever `TimeZone` the session or the writing session had. In `query` the column's type decides (Postgres prints it in `DateStyle` ISO, which the engine sets; see below). Inside stored row values (the ledger, revert lines) there is no type, so any string at any depth in the exact shape of a `timestamptz` in JSON (`2026-11-10T08:02:11+02:00`: date, `T`, time with an optional fraction of 1 to 6 digits, numeric offset `+HH:MM`, with `:SS` when the zone has seconds) is reformatted, a text column holding such a string and the elements of a `timestamptz[]` column included. In `query` an array, json, jsonb or text column is returned as Postgres prints it, so the same array shows as Z strings in `run_history` and in Postgres form in `query`. A `timestamp` without time zone, a `date`, `infinity` and any value RFC 3339 cannot write (BC, year over 9999) are not touched. What the guard stores and the person signs (held and revert lines, `rowsHash`, the ledger's row values) is not reformatted: it keeps Postgres's JSON form, so the signing pages show `2026-11-10T06:02:11+00:00`. It does not depend on the session either: every transaction in which the engine writes, reads for an agent, previews, holds or reverts, and those of `basalt revert` (on a direct connection or through the person socket), first sets `TimeZone` to `UTC`, `DateStyle` to `ISO, MDY`, `IntervalStyle` to `postgres`, `extra_float_digits` to `1`, `lc_monetary` to `C` and `bytea_output` to `hex` for that transaction only (`set_config(name, value, true)`), whatever the client, the role or the database set. The agent's own SQL runs in it too: a `timestamptz` literal without an offset is read as UTC, `now()::date` or a `::text` cast prints in UTC, a `money` value prints and is read in the C locale's form (`$1,234.50`), and a `bytea` value prints in hex (`\x00ff`). The guard's row trigger sets the same six values for itself ([version 34](contract/basalt-meta-versions-29-on.md#version-34-the-row-trigger-stores-row-images-in-fixed-settings), [version 35](contract/basalt-meta-versions-29-on.md#version-35-bytea_output-and-the-revert-functions)), so a write that skips the engine (the agent's credential used directly, as in psql) stores the same row images as one through it, and its own SQL keeps its session's settings. The revert's own read of the row now and its restore set them too, so a person calling the revert functions by hand from any session finds no false conflict. For every write, a stored `timestamptz` reads `+00:00`, an `interval` `01:30:00` and a `float8` its shortest exact form (`0.30000000000000004`) and a `bytea` `\x00ff`, the lines and `rowsHash` are the same from any client, and a revert's conflict check (the row now against the row the agent left, compared as JSON) finds no false conflict when the write and the revert ran in different sessions. A row value stored before this by a session in another zone (`+07:00`) no longer matches the row now: its line is skipped `CHANGED_AFTER`, never written (lane decision, 14 Nov 2026; owner decision on the returned values, 13 Nov 2026).
- **Events are CloudEvents.** Anything BasaltDB emits as an event, to a plugin or outside the engine, is a [CloudEvents](https://github.com/cloudevents/spec) 1.0 event in its JSON form: the JSON event format, media type `application/cloudevents+json`, and several events in one message as a JSON batch, `application/cloudevents-batch+json` (spec version 1.0.2, `cloudevents/spec.md` and `cloudevents/formats/json-format.md`). Today that is the two notifier messages, `feed/1` and `deliver/1` ([Notifier messages](contract/plugins-runtime.md#notifier-messages)). It does not cover what Basalt stores (ledger rows and every other table in Postgres) or what it answers (tool results, CLI output, error bodies, approval and revert requests and responses): those are records and answers to calls, not events. The envelope's attributes are the standard's, with its names (`specversion`, `datacontenttype`: lowercase letters and digits only), so the camelCase rule above does not apply to them; every key and value inside `data` follows the rules above (camelCase keys, SCREAMING_SNAKE_CASE enum values, UUIDs, RFC 3339 UTC timestamps). Basalt sets no extension attribute. An event travels in its JSON form on every transport, ConnectRPC included, so a plugin that forwards it to a message broker passes it on unchanged.
- Named Go types for anything (de)serialized; DTOs separate from domain structs.
