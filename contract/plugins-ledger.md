### In the ledger

Plugin events go through `record_plugin_event` into the ledger of each agent a change affects ([`events.schema.json`](../api/plugin/events.schema.json)):

| Kind | Written to |
|---|---|
| `PLUGIN_ENABLED` | Each agent the entry starts serving, once (a restart writes nothing new) |
| `PLUGIN_DISABLED` | Each agent the entry stops serving, including an agent removed from its `agents` |
| `PLUGIN_CHANGED` | Each listed agent, when the version, manifest, hooks, egress, endpoint, isolation or reported model changes |
| `PLUGIN_TRUST_ADDED` | Every agent: a key added to the trust store applies to the whole engine |
| `PLUGIN_TRUST_REMOVED` | Every agent whose ledger records as trusted a key the trust store does not hold ([schema version 4](basalt-meta-schema-versions.md#schema-version-4-plugin-trust-removed)) |
| `PLUGIN_APPROVAL_PENDING` | The agent that opened a plugin approval, written by `open_plugin_approval`, never by `record_plugin_event` ([What a plugin approval binds](plugins-approval.md#what-a-plugin-approval-binds)) |
| `PLUGIN_APPROVED` | Every agent a signed plugin approval lists, written by `submit_plugin_approval`, never by `record_plugin_event` |

- **Detail keys**: `name`, `instance`, `version`, `manifestSha256`, `signerKeyId`, `signer` ([schema version 5](basalt-meta-schema-versions.md#schema-version-5-plugin-approvals): `KNOWN` or `UNKNOWN`, written only for an entry that requires approval; with `UNKNOWN` there is no `signerKeyId`, and without `signer` `signerKeyId` is required, as before), `hooks`, `roles` (`wire.detect` only), `egress`, `endpoint` (`{kind: LOCAL | REMOTE, host}`, `host` for `REMOTE` only), `isolation` (`{files: OS_USER | NONE, network: ENFORCED | DECLARED | NOT_ENFORCED}`, `LOCAL` only) and `model` (`{name, version}`, when the plugin reports one; each matches `^[A-Za-z0-9._+-]{1,64}$`, so it is only a short identifier, never free text). `PLUGIN_TRUST_ADDED` and `PLUGIN_TRUST_REMOVED` carry `signerKeyId` only. The guard refuses any other key, and a detail over 4 KiB.
- The detail never holds a config value, text a plugin saw, or the name of any agent: no agent's ledger names another agent.
- **When they are written.** The `basalt plugin` commands have no database access and write no ledger row. The engine writes the events at each start, and in same-user mode at each check while it runs ([Plugin changes while the engine runs](plugins-approval.md#plugin-changes-while-the-engine-runs)), before it starts any plugin and after it stopped one, on each agent's own credential, from what it serves now and what that agent's own ledger records: the latest event of each `(name, instance)` and the trust keys it records as added. A restart with no change writes nothing, and a change made while the engine was stopped is recorded at the next start. For each agent, trust keys first, then each entry:
  - `PLUGIN_TRUST_ADDED` for each key added to the trust store that the agent's ledger does not record as trusted (no event for it, or a later `PLUGIN_TRUST_REMOVED`);
  - `PLUGIN_TRUST_REMOVED` for each key the agent's ledger records as trusted (its latest trust event is `PLUGIN_TRUST_ADDED`) that the trust store does not hold: a key the person removed, or an event the agent wrote itself. A key built into the engine is held by every trust store and needs no event. When the trust store cannot be read, no trust event is written;
  - `PLUGIN_ENABLED` for an entry the agent is served that its ledger records as disabled, or not at all;
  - `PLUGIN_CHANGED` for an entry the agent is served whose detail differs from the latest recorded (a new version, manifest, signer, hooks, egress, endpoint or isolation);
  - `PLUGIN_DISABLED`, with the detail last recorded, for an entry its ledger records as served that the agent is no longer served: the entry was disabled or removed, or the agent was removed from its `agents`.

  An enabled entry listed for the agent that the engine does not start (it failed verification, or a local plugin may not run on this engine) keeps its record as it is, so a passing failure writes nothing; `status` shows why. The exception is an entry whose recorded signing key the agent's ledger no longer records as trusted (the key was removed from the trust store, so a `PLUGIN_TRUST_REMOVED` was written) and that is not built into the engine: it gets `PLUGIN_DISABLED`, with the detail last recorded, so the ledger never shows it served after its key's removal. So does an entry that requires approval and is withheld with `PLUGIN_AWAITING_APPROVAL`, `PLUGIN_APPROVAL_EXPIRED` or `PLUGIN_APPROVAL_MISMATCH` while the agent's ledger records it as served ([Plugin approvals at engine start](plugins-approval.md#plugin-approvals-at-engine-start)); the trust-key exception does not apply to such an entry, whose approval takes the place of the trust record ([Signer states](plugins-approval.md#signer-states)).
- **Isolation as it runs.** A `LOCAL` entry records the isolation it runs with on this engine: in same-user mode `files: NONE`, `network: NOT_ENFORCED`; in service mode, where a local entry is served only through its own unit and OS user, `files: OS_USER` with the network its unit gets ([Service units](plugins-runtime.md#service-units)): `ENFORCED` for an empty `egress` on Linux, `DECLARED` for a non-empty one, `NOT_ENFORCED` on macOS. A `REMOTE` entry records its `host` and no isolation. Only an entry the engine serves is recorded as enabled: one it refuses (no matching unit or OS user, a failed verification) keeps its record as it is.
- **A record that cannot be written.** The record is part of consent. When the engine cannot write an entry's `PLUGIN_ENABLED` or `PLUGIN_CHANGED` to an agent's ledger, or the `PLUGIN_TRUST_ADDED` of the key that signed it (a key added to the trust store; a key built into the engine has no record), it does not serve that entry to that agent until a later start writes it, so the ledger never shows an entry served without the key that made it trusted: the entry refuses any call naming that agent, an entry left with no agent is not started, and that agent's `status` shows `PLUGIN_UNAVAILABLE` with the reason and what to do: the guard is older than [schema version 3](basalt-meta-schema-versions.md#schema-version-3-plugin-events) (run `basalt upgrade` for the agent, then restart the engine: unlike other upgrades, plugins need the restart), the database has no guard, the agent is served `status` only (an outdated guard or a pending setup; no plugin record is written for it then), the guard refused the record, the database did not answer within 15 seconds, the trust store could not be read and the ledger does not record the key yet, or the trust store no longer holds the key that signed it (trust it again, or disable the plugin, then restart the engine). For a key it could not record it writes no `PLUGIN_ENABLED` or `PLUGIN_CHANGED` of the entries that key signed. Other agents and every other tool are served as before. A `PLUGIN_DISABLED` or `PLUGIN_TRUST_REMOVED` that cannot be written (the latter on a guard older than [schema version 4](basalt-meta-schema-versions.md#schema-version-4-plugin-trust-removed)), or a `PLUGIN_TRUST_ADDED` of a key that signed no entry the agent is served, is logged and tried again at the next start, and withholds nothing.
- **What an agent role can write.** `record_plugin_event` is granted to every agent role, since the engine writes with the agent's own credential, so an agent that holds its credential (same-user mode) can call it too. It writes only to the caller's own ledger, chained like every row, and only details the guard accepts: no free text, no other agent's name, no config value. A false event (a `PLUGIN_DISABLED` for a plugin still served, an `OS_USER` that is not true) stays in the ledger under the agent's role, and the engine's next start writes what is true over it whenever the latest record of an entry differs from what it serves. A false event that is exactly what the engine will serve is not written again either: the latest record already matches, so the ledger keeps the earlier time. Trust events are corrected the same way: a false `PLUGIN_TRUST_ADDED` (a key the trust store does not hold) gets a `PLUGIN_TRUST_REMOVED` at the next start, and a false `PLUGIN_TRUST_REMOVED` of a held key gets a `PLUGIN_TRUST_ADDED`. **What the events prove.** The engine obeys the trust store and `engine.json` on disk, never the ledger, so a false event changes nothing it serves. But in same-user mode, and whenever an agent operates the engine (`operatedBy: AGENT`), the agent holds its credential and can write any plugin event the guard accepts, between two starts or before the engine's first: there the plugin events in a ledger are only as trustworthy as the agent. They show what the engine served at each start, the agent's own events between starts, and nothing about who wrote which. In service mode with the person operating the engine, the agent cannot write them: its OS user cannot read the credential file, and the SQL tools refuse a call to any function outside their fixed allowlist of built-ins (`basalt_meta.record_plugin_event` included) with [`STATEMENT_REFUSED`](error-codes.md#error-codes), reason `FUNCTION_NOT_ALLOWED`.
- **Retention.** Plugin events are ledger metadata, deleted after one year with the other rows; an entry still served then is recorded `PLUGIN_ENABLED` again at the next start.
- **`basalt log`** prints on stderr, after the PII line, `Plugins: <name>/<instance> <version> (signer <keyId>, LOCAL, files <files>, network <network>); <name>/<instance> <version> (signer <keyId>, REMOTE <host:port>)`, one part per entry the agent's ledger records as served, in name and instance order, at most 20, then `; and N more` when there are more; `Plugins: none` when it records only disabled ones, and no line when it has no plugin event. When the entries cannot be read it prints `Plugins: could not be read (<error>)` and the rest of the health output is unaffected.
- A feed cursor starts again at the agent's chain head when the entry begins to be served to that agent after not being served (a `PLUGIN_ENABLED`: enabled again, a first approval or one signed again after it ended, an agent added to its `agents`), when a `PLUGIN_CHANGED` adds an egress host or moves the endpoint, and on a new install id: history is never sent to a newly approved destination ([The cursor](plugins-runtime.md#the-cursor)).

### Problems and errors

- `status` problems ([Next steps per code](next-steps.md#next-steps-per-code)): `PLUGIN_UNAVAILABLE` (an enabled entry listed for the agent is not ready) and `PLUGIN_NOT_TRUSTED` (the engine refused to start an entry listed for the agent: its signature, a file's hash or a path's permissions failed, or, in service mode, an agent's OS user is in the engine's group, which would let it reach plugin sockets). The message names the entry and the failed check, and a file only when it is the manifest or its signature: a local plugin runs in its installed copy, so other names there may be its own.
- [Plugin approvals at engine start](plugins-approval.md#plugin-approvals-at-engine-start): `PLUGIN_AWAITING_APPROVAL` (an entry that requires approval has no signed approval for the agent: none opened, one pending or cancelled, or turned off since it was signed), `PLUGIN_APPROVAL_EXPIRED` (its newest approval expired unsigned) and `PLUGIN_APPROVAL_MISMATCH` (its newest signed approval does not match the installed copy or config). Each names the entry, and the mismatch names the fields that differ, never a value.
- [Plugin changes while the engine runs](plugins-approval.md#plugin-changes-while-the-engine-runs): `PLUGIN_CONFIG_INVALID` (`WARNING`, every agent, naming no entry: `engine.json` changed and its plugins cannot be read, so no plugin change is applied).
- [Notifier messages](plugins-runtime.md#notifier-messages): `PLUGIN_NOTICES_DROPPED` (`WARNING`: an `approval.deliver` entry served to the agent dropped notices in the last 24 hours, counted from the engine's start; it names the entry and the count, never what a notice was about, and goes away 24 hours after the last drop).
- The error `PLUGIN_REFUSED`, reasons `AGENT_OPERATED`, `BAD_MANIFEST`, `NOT_TRUSTED`, `UNKNOWN_AGENT` and `UNSAFE_PATH` ([Error codes](error-codes.md#error-codes)), from the `basalt plugin` commands only; also `TOO_MANY_PENDING`, `GUARD_OUTDATED` and `DATABASE_UNREACHABLE` ([Plugin approval](plugins-approval.md#plugin-approval)).
