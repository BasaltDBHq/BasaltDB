# Changelog

All notable changes to BasaltDB are recorded in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.1.0-alpha] - 2026-11-24

The first release of the 0.1 line, for macOS and Linux (amd64 and arm64). Setup moves from the terminal to a page: the agent runs `basalt init` and the person finishes on the page it links. The CLI only starts things. Expect bugs and breaking changes between alpha releases, and read "Breaking for alpha installs" before you upgrade.

### Added

- The local setup page (`/setup/` on `http://localhost:8787`). On your own computer `basalt init` installs the engine service through the system's administrator dialog, one password and nothing typed in the terminal, then prints and opens the setup link. On the page you type the admin connection string, which is used once and never written or logged, pick the tables the agent gets (read and change, or read only; a table without a primary key is read only), label the columns that hold personal data, create a passkey, read the SQL and run the install in one transaction. A service engine with no `engine.json` yet serves only this page and waits.
- The check-up. `basalt init` on a computer already set up opens the page on a check-up. Problems that stop BasaltDB working (a guard update, a new database certificate, a certificate that does not match the ledger, no passkey, an agent that cannot log in) each have their own fix button, which asks for the admin connection string or your passkey. Columns without a label are a warning that never blocks, and leaving them unlabeled is remembered. With nothing critical open the page says "Ready", and **Done** ends on an "All set" screen that says to go back to your agent. The passkey list removes a lost device's passkey and adds one on this device.
- Passkeys work without Touch ID: the prompts accept a fingerprint, face, the computer's password or PIN, a phone or a security key.
- Remove BasaltDB on the setup page. It shows what goes (the ledger, the guard, the agents by name; your tables stay) with the SQL, and runs once you type the database's name. On your own computer, a removal within 90 seconds of the page opening goes on to remove the engine service through the administrator dialog. After that, `basalt init` removes nothing by itself: it opens a page that asks whether to set BasaltDB up again on the same engine or remove it from this computer too, and only that Remove asks for your password. `basalt init --demo` on a removed engine sets the demo up again. On macOS the password dialog's first line names what it does ("BasaltDB wants to remove its engine from this Mac."). The service stays while the engine still serves an agent of another database.
- The connect page (`https://portal.basaltvault.app/connect`), for an agent on a computer you cannot reach. `basalt init --remote` makes a connect-only setup code and prints its link. The code names no database, so you give the agent nothing about it. The page checks that the code matches the one in the chat, takes the passkey step, and asks for the admin connection string, which it sends to the hosted connect service for that one setup and keeps nowhere. It checks that the bot can reach the database, shows it by name with its tables, and lets you untick tables and label personal data.
- The engine collects a connect-only setup's address itself and logs in with the agent's real password only after you confirm the database in the chat, through the new `confirm_database` tool.
- The connect page runs the update for a bot that is already set up (the guard, labels, passkeys, a changed certificate), and has a Remove BasaltDB tab that needs only the admin connection string: no bot and no setup code.
- Both setup pages ask one question after you paste the admin connection string: "Is this your database?", with the database, its host, the user the string signs in as and how its certificate was verified.
- Trust profiles: which root certificates verify a database's certificate, as data. The engine now connects to Supabase and Amazon RDS with full TLS verification (`sslmode=verify-full`, host name checked) from built-in profiles of their roots, and each provider's roots verify only its own hosts. An operator can place a profile file in `trust.d` next to `engine.json`. `status` reports which trust verifies the agent's database and warns `TRUST_ROOT_EXPIRING`, `TRUST_PROFILE_REFUSED` and `CERTIFICATE_NOT_VERIFIED`.
- A connection string that is encrypted but doesn't check the certificate (`sslmode=require`, `prefer` or `verify-ca`) gets a warning in three places. BasaltDB keeps the `sslmode` you gave it and changes it only on your click. "Is this your database?" warns and, for Supabase and Amazon RDS, offers **Check the certificate**, which switches only `sslmode` to `verify-full` and checks again; if the certificate isn't the provider's, nothing is sent and you go back or continue without checking. The check-up shows a **Certificate not checked** row whose **Check it** rewrites the agent's saved connection to `verify-full` after a check that passes. `status` warns `CERTIFICATE_NOT_CHECKED`. A connection with no encryption at all (`sslmode=disable`, or `prefer` on a server without TLS) gets the same treatment: `status` warns `CONNECTION_NOT_ENCRYPTED`, and the check-up shows **Connection not encrypted**. On Supabase and Amazon RDS hosts, **Check it** switches the connection to `verify-full`.
- Pinning on first use. For a database whose certificate no authority on the machine signs (Cloud SQL, DigitalOcean, Aiven, self-signed), confirming "Is this your database?" pins its certificate authority for that host only. From the connect page the engine pins only when its own reading of the chain matches what you trusted. A chain from a public authority is never pinned. The pin is recorded in the ledger, and a pinned host that presents another certificate is refused with `TRUST_ROOT_CHANGED` until you accept it on the Update check.
- `basalt engine --supervise` restarts a crashed engine with a backoff and gives up after five fast crashes in a row, recording why. `basalt mcp` starts a same-user engine it finds down, so a bot's computer that lost its engine after a reboot or an update needs no step. `--started-by` says why an engine started, and `status` reports it.
- The engine restarts itself onto an upgraded binary installed at the path it was started from, with or without a service manager, once running calls finish. `basalt mcp` waits for the restarted engine and sends a dropped read once more; writes, approvals and reverts are never sent twice. `basalt mcp` and the engine agree on a protocol version when they connect.
- A daily check for a newer release. `basalt` prints one line on stderr when one is out, and the agent's `status` and `describe` carry an `update` message for it to pass on. It sends nothing but the request. Turn it off with `BASALT_UPDATE_CHECK=off` or `"updateCheck": "OFF"` in `engine.json`.
- On an engine you operate, `basalt mcp` opens a link to the engine's own local pages in the browser when a result carries one, such as a held write's approval page or a revert to sign. It opens no other URL, and nothing on an engine an agent operates.
- When `basalt` panics it saves a scrubbed crash report on the machine, and `status` names the newest one with a link to file it on GitHub yourself. Nothing is sent. A tool call that panics ends with `INTERNAL` instead of stopping the engine.
- The `status` tool lists the tables the agent can read and write and names each passkey with a check code. `describe` names the agent's database and host.
- The CLI's help and the MCP instructions say that one engine serves many agents, each on one database, and that another database needs another agent.
- The portal has a home page and a not-found page.
- A database whose BasaltDB install is too old to update is replaced on the setup page. The page says so first, from what it found ("It was set up by BasaltDB <release> (guard version N)", or "It has guard version N" when no release is recorded, and the guard version this release needs), then runs the normal install steps. The last button, **Remove the old install and set up**, asks for the database's name and removes the old install and installs in one transaction: if the setup fails, the old install stays as it was. Your tables and rows stay; the old install's agent history and undo, held approvals and passkeys go. An update is still refused there.
- Guard version 14 records, in `basalt_meta.schema_version`, the BasaltDB release that wrote each version (`release`), so a later release can name the one that set a database up. Non-breaking: an engine serves agents on a guard without it.
- Guard version 15 records a held write, revert or plugin approval its agent withdrew, with the agent's reason, and never takes a signature for it: the approval, revert and plugin pages say "The agent withdrew this request: <reason>. Nothing changed." and offer nothing to sign, on the engine's own pages and on the portal alike, and a write sent with a withdrawn approval writes nothing. A held write the agent withdrew reads `APPROVAL_WITHDRAWN` in `run_history`, and `status` reports a plugin entry whose approval the agent withdrew as `PLUGIN_APPROVAL_WITHDRAWN`. Breaking: an engine of this release needs guard version 15, and `basalt init` updates a guard at version 14 in place.
- A `withdraw` MCP tool: the agent takes back its own held write, revert or plugin approval that still waits for the person, with the reason it heard (for example when the person says to cancel it). The link stays and its page shows the request withdrawn with that reason and nothing to sign. Withdrawing a revert or a plugin approval is a safety step, since signing either takes effect on its own. Another agent's request is `NOT_FOUND`, and one that no longer waits keeps its state. `list_pending` no longer lists a withdrawn request, and the `request_revert`, `revert_plan` and `request_plugin` wait forms answer `WITHDRAWN` at once instead of still waiting.
- `engine.json` records the breaking epoch it was written in (`"breaking": 1`). `basalt init` (and `basalt init --remote`) on a computer whose config is from before the last breaking release moves the config folder aside to `<folder>.old` (never deleting it), removes the old engine service in the administrator dialog it already shows, says so in one line and sets the computer up as a first install, printing the `basalt mcp --agent NAME` line to register again.
- `http://localhost:8787/` shows that BasaltDB is running instead of an empty 404: how many agents and databases (the kind only: Supabase, Amazon RDS or Postgres), whether the engine, the guard and the passkeys are fine, and a button per database that opens its check-up. It has no login, so it never shows an agent's name, a database's host or name, a table or any record of what an agent did.

### Changed

- Every next step, warning and person message hands the person a link, never a `basalt` command. A setup job is an agent step that runs `basalt init` (`basalt init --remote` on an agent-operated engine), which prints the link.
- Approvals and reverts are signed only on a page with a passkey: the engine's own pages on your computer, or the portal on a bot's computer, whose signature the hosted relay carries to the engine. Nothing is pasted. A whole-task revert is `request_revert` with `taskId`, widened on the signing page, and a revert too large to prepare in one call is split with `runs` or `tables`.
- A portal short link (`/approvals/*`, `/reverts/*`) opens an end-to-end encrypted session to the engine through the BasaltDB Vault relay (`wss://relay.basaltvault.app`). The page shows the engine's fingerprint to compare before you sign, and the engine's receipt for the signature.
- `basalt init --remote` prints the `basalt mcp` line with the absolute path of the running binary, so an agent app whose `PATH` lacks it can still start it. A binary in a temporary folder gets a warning to move it.
- The README, `llms.txt` and `docs/` describe the simplified product. No guide asks a person to type a `basalt` command or to paste an admin connection string into a terminal.
- Release builds are reproducible: the same tagged commit built with the Go toolchain set in `go.mod` gives byte-identical archives, packages and `SHA256SUMS`. [docs/RELEASING.md](docs/RELEASING.md) explains how to check a release.
- Release binaries embed `golang.org/x/crypto` v0.59.0, so binary scanners no longer flag GO-2026-5932. BasaltDB never called the package involved.
- The setup page and the engine refuse more spellings of an admin connection string in a tool call: JSON text with `\u0026` for `&`, a percent-encoded `password` name or scheme, a password with a space, `postgresql+psycopg2://` and a libpq key and value string. The connection string pasted on the local setup page takes only the parameters the engine needs and refuses file-path keys such as `sslrootcert`, so the engine no longer reads files a pasted string names. Error and status messages no longer advise adding `sslrootcert`.
- A database whose host a built-in trust profile knows (Supabase, Amazon RDS) is checked with `sslmode=verify-full` when the admin connection string names no `sslmode`, which Supabase's own copy of the string does not. The confirm step shows "Verified by Supabase" (or Amazon RDS) and the agent's connection string checks the certificate too. An `sslmode` in the string is kept as given. An RDS host in the China or GovCloud regions, whose roots BasaltDB does not carry, needs `sslmode=require` in the string.
- `status` counts only the passkeys registered on the origin the agent's links open, and it is not `ready` until one can sign there. The tools keep working meanwhile.
- A repair keeps the role's grants. `basalt init --remote` no longer saves the agent's tables, prefix or timeout in `engine.json`, and the database's grants are the only record. A role that was dropped, or that holds no table, asks the person to tick tables on the connect page, which shows the ticks from the connect service's answer.
- `preview_revert` says its timeout is the agent's statement timeout, not the 100 seconds of `request_revert`.
- A tool call that panics now answers `INTERNAL` with an `errorId`, like every other `INTERNAL` and `UNAVAILABLE` error, and the engine logs the panic under that id (the tool and the crash report's id, never the panic's value), whether or not the crash report could be saved.
- `describe` names what the agent may do with Basalt's ops: a resource's `actions`, and `access` in the overview's and search's lists, say `READ` where they said `SELECT` (the grant that allows a read); `INSERT`, `UPDATE` and `DELETE` do not change. An agent or tool that looks for `SELECT` there needs `READ`.
- A write sent with an `approvalId` that is not the held write is refused with `APPROVAL_INVALID` `DIFFERENT_WRITE` and the message "the request must be exactly the held write's" (was "sql and params must be exactly those of the held write"); its next step's text and `list_pending`'s step after it name the held request instead of its sql and params. The step's call arguments do not change. `list_pending`'s `request.kind` is now read from the held write (still `SQL` on Postgres).
- Change records, tool errors and the plugin feed name things in words that fit any store. `run_history`'s records carry `resource` and `shape` in place of `target`, `store: {kind, verb}` (the store's own command, such as `SELECT` for a read), and `request: {kind, statement, params}` in place of `statement` and `params`; a read's `op` is `READ` (was `SELECT`), and each row change carries `resource` and `shape` in place of `table`. Tool errors answer `STORE_ERROR` (was `SQL_ERROR`) and carry `storeCode` (was `sqlState`) whenever the store raised the error. `list_runs` gives `resources` and `resourcesTruncated` (were `tables` and `tablesTruncated`); `list_pending` gives a held write's `request` and `assignedFields` (were `statement`, `params` and `assignedColumns`). The plugin messages `feed/1` and `deliver/1` name the agent `agent:<name>` in the params, `subject` and `data.agent`, and the feed's write events carry `resource` (was `table`) and `store`. A plugin built with the Go SDK needs the SDK release that reads them.
- The engine and the approval, revert and plugin approval pages read what a person signs in the store-neutral form of guard version 10: `store`, `request`, `resource`, `shape` and `agent:<name>`, and the conflict `TARGET_GONE` (was `ROW_GONE`). The engine checks that every text it relays follows the text rules and refuses one that does not. A page refuses to offer signing for data it cannot draw (`shape` `OBJECT` or unknown) or a `request.kind` it has no view for, and names the store from `store.kind`. Links in the old `#1.` form are no longer read; ask the agent for a new link (`list_pending` or `request_revert` with `reissueLink`). Plugin approvals name agents `agent:<name>`. The guard's `hold_action` takes the request's own command, so an upsert's ledger rows carry `verb` `INSERT`.
- The guard gets schema version 10 (breaking): what a person signs names things in words that fit any store. An approval's binding carries `store`, `request` (the statement and its parameters), `assignedFields` and the agent as `agent:<name>`; its lines, and a revert's lines, carry `shape`, `store` and `resource` in place of `table` (a revert line's SQLSTATE is `store.code`, and the conflict `ROW_GONE` is `TARGET_GONE`); a revert's binding carries `store`, `resources` in its select and every agent as `agent:<name>`; a plugin approval's binding carries `store` and its agents as `agent:<name>`. The ledger records a read as `READ` and the store's word for each operation as `verb` (none on a revert, or on a refused DDL statement). Texts in the earlier form are not read, and the ledger's chain does not verify rows written before the upgrade: reinstall `basalt_meta` on a dev or demo database (remove BasaltDB on the setup page, then run `basalt init`).
- Two more agent-facing names fit any store: the `RLS_HIDES_ROWS` warning's `table` is `resource` (for Postgres still `schema.table`), and a `largeValues` entry's `column` is `field`. The receipt, `query` and `describe` descriptions, and the person's pages, say the store and resources where they said Postgres and tables.
- `describe`'s overview names what it counts in words that fit any store: `counts.schemas` is now `counts.namespaces`, `counts.tables` is `counts.resources`, the large overview's `schemas` list is `namespaces`, each item `{ namespace, resources }` (was `{ schema, tables }`), and `otherSchemas` is `otherNamespaces`, `{ namespaces, resources }` (was `{ schemas, tables }`). The resource and search forms do not change. An agent or tool that reads these keys needs the new names.
- `describe`'s resource form names its foreign keys and size in words that fit any store: each item of `foreignKeys` carries `fields` (was `columns`) and the other `resource` (was `table`, for Postgres still a `schema.table` name), and `stats.resourceBytes` replaces `stats.tableBytes`. An agent or tool that reads these keys needs the new names.
- A badly formed name in the `resources` filter (was `tables`) of `preview_revert` or `request_revert` now gets the database's own refusal: `INVALID_ARGUMENT` reason `SCOPE_FILTER`, message "the revert filter is not valid, nothing was prepared: " and the store's text, which names the first bad entry ("`leads` is not a schema.table name"), where it was `INVALID_ARGUMENT` with no reason and the tool's own message. The tool schemas no longer carry a name pattern for the filter. A name with a semicolon, such as `public.leads;drop`, is no longer refused up front: it reads "`public.leads;drop` has no change of yours in this scope", like any table the agent did not write.
- The guard gets schema version 9 (non-breaking): a revert scope's table entry that is not one `schema.table` name is refused with its own detail, `NAME`, and a hint that names the entry.
- The revert tools name things in words that fit any store. `preview_revert` and `request_revert` take `resources` in place of `tables` (for Postgres still `schema.table` names); the lines of `preview_revert`, and the items of `revert_plan` and their `plan`, carry `resource` in place of `table`; and the lines and items of `preview_revert`, `revert_plan` and `apply_revert_batch` carry `storeCode` in place of `sqlState` (for Postgres still the SQLSTATE). Messages and next steps that name the filter say `resources`, the next steps of a refused filter point to the resources the agent wrote, and the `select` that `preview_revert` describes is the descriptor as the store normalized it. The signed revert line, the binding the person signs, the person's page and the tool error's `sqlState` are unchanged.
- The guard gets schema version 11 (breaking): the refusals the engine tells apart carry a code as their detail and the sentence as their hint. A signed revert's `REVERT_INVALID` is `ALREADY_APPLIED`, `ALREADY_SIGNED`, `PASSKEY_REVOKED` or `ROWS_CHANGED`, and `NOTHING_TO_REVERT` for a scope that changed no rows is `READS_ONLY`, so the engine no longer matches the guard's words. A revert scope refused for a bad `agents`, `runs` or `resources` entry now names the first such entry, for example "the revert scope was refused: x is not a run id". The engine needs this version: run `basalt init` again and update the guard on the page it opens.
- The engine's warning "pii: a column the agent read is not classified" logs the column as `field` (the store's ref for it, for Postgres `<table oid>/<attnum>`) in place of `tableOid` and `attnum`. A log filter or alert that reads those two fields needs the new one.
- The engine's warning "plugin feed paused" gives a database refusal's class as `STORE_CODE <code>` (was `SQLSTATE <code>`); for Postgres the code is still the SQLSTATE. A log filter or alert that matches the old class needs the new one.
- `describe`'s search names what matched in words that fit any store: `matched` is `resource`, `namespace` or `field <name>` (was `table`, `schema` or `column <name>`); `comment` does not change. The approval and revert pages' request, served by the engine, carries `fields` (was `columns`), each resource to its field names in the store's order, for display only. `describe`'s messages and next steps, a revert's person message ("only resource <name>", was "only table <name>") and the plugin feed's revert headline, and the descriptions of `describe`, `preview_revert`, `run_history`, `run_start`, `status` and `write` say resource, namespace and field where they said table, schema and column. An agent or tool that reads `matched` needs the new values.
- `engine.json` must hold only its one JSON object. A file with anything after the closing brace, such as a second object, a `//` comment or stray characters, was accepted before. The engine now refuses to start with `config <path>: data after the JSON value`. To fix it, remove everything after the closing `}`.
- Go API: `pkg/trustprofile` takes a host and its `*tls.Config` (`TrustTLS`, `ExplainTLS`) in place of `Trust` and `Explain`, which took a `*pgconn.Config`, so the package no longer links the Postgres driver. Call `TrustTLS` once for each host of a connection.
- A setup code run against the wrong database (`TARGET_MISMATCH`) now tells the person to paste the admin connection string of the code's database on the page, or to ask the agent for a new code. It no longer says to run a command. The refusals that told the person to fix or update "this computer" now say what to do on the connect page: `UNSUPPORTED_FORMAT` says to try again later and `BINARY_TOO_OLD` to try again shortly, since the connect service runs the code; `SETUP_ID_IN_FUTURE` and `EXPIRY_TOO_FAR` say to check the clock of the agent's machine; and a code the database's clock refuses says to check the database's clock, no longer "this computer's".

### Removed

- The commands `basalt log`, `status`, `access`, `approve`, `revert`, `passkey`, `classify`, `upgrade`, `uninstall`, `tunnel`, `portal verify`, `service uninstall`, `engine list` and `engine revoke`, with their flags. What they did is in the agent's MCP tools and on the pages. The portal check runs in the release workflow.
- Every `basalt init` flag but `--agent`, `--remote` and `--demo`: `--write`, `--read`, `--prefix`, `--statement-timeout`, `--os-user`, `--engine-user`, `--socket-dir`, `--credential-file`, `--config`, `--no-service`, `--rotate-password`, `--skip-passkey`, `--passkey-label`, `--passkey-origin`, `--add-passkey`, `--agent-rls`, `--operated-by`, `--person-uid`, `--vault`, `--database-url`, `--new-code`, `--direct-addr`, `--dev-local-pages`, `--json`, `--yes` and `--dry-run`. Tables, labels and passkeys are set on the page.
- `basalt init --setup-code`, with `--engine-url` and the laptop half of the setup code, and the terminal setup: the admin connection string prompt and the passkey hand-back with its pairing code.
- `basalt mcp --config`, `--socket-dir` and `--socket`, and `basalt engine --user` with the engine's own privilege drop.
- `write`'s `approval` argument and `request_revert`'s `signature`, with the pasted approval and revert codes on every page.
- The direct transport: the engine's direct listener (`directAddr` in `engine.json`), the engine address recorded with its key, and the portal's engine pin pages (`/engines`, `/engines/add`). Portal pages reach the engine through the relay only.
- The person socket, and the `/passkeys/check` and `/passkeys/forget` pages.
- The `remote-init-result` and `portal-verify-result` JSON schemas, and `docs/setup-from-laptop.md`.
- The `DIRECT_NOT_SERVED` problem from `status`, and the last mentions of the direct transport in the tool schemas.
- The environment variables `BASALT_DATABASE_URL`, `BASALT_ADMIN_DATABASE_URL`, `BASALT_CACHE_DIR` and `BASALTDB_ALLOWED_HOSTS`. The engine reads its connection from `engine.json` only, and the update notice keeps its cache in the user cache folder.
- The passkey registration request no longer takes `handBack` (`api/mcp/approval/registration-request.schema.json`), and the registration page no longer shows a pairing code; the shared pairing-code vectors are gone. Both went with the terminal setup's hand-back to `basalt init`; the page shows the code to paste, as before.
- The plugin person schema (`api/plugin/approval/person.schema.json`) no longer lists `PLUGIN_APPROVE` or its params and result: a plugin approval is signed on its page, which relays the signature.
- The Go setup package (`pkg/setup`) gains the replace of an install too old to update: a caller sets `Request.Replace` to offer it, `Check` then returns `Checked.Replace` (the old guard version, its recorded release, the floor, this release and the first screen's words) and checks the rest as after the old install's removal, and `Run` removes it and installs in one transaction once `RunInput.ConfirmName` is the database's name. A caller that does not set `Request.Replace` gets `GUARD_UNUSABLE` as before.
- The Go setup package (`pkg/setup`) drops `Request.ConnectPage` and the `CONNECT_ONLY` refusal (`CodeConnectOnly`), left from the removed laptop setup command. Every request is run the way the connect page runs it: a code without a target is accepted, `Check` always returns the column labels (and, for a code with a target, the passkeys), and `Run` refuses a code with ticks and no `Included` with `NO_TABLES`. The laptop's passkey step goes too: `RunInput.AskPasskey`, `RunInput.AddPasskey` and the `PASSKEY_NOT_REGISTERED` refusal (`CodePasskeyNotRegistered`). A run needs `RunInput.Passkey` whenever the database has no active portal passkey. The contract no longer promises OSC 8 terminal hyperlinks, which the CLI never printed.

### Fixed

- `basalt init --demo` on an engine that is already set up says that the flag was ignored. It opens the page that updates or removes BasaltDB, as before, and now prints that a fresh demo needs a removal first: press Remove on the page, then run `basalt init --demo` again. Plain `basalt init` prints nothing new.
- A write held for approval that uses `now()`, `current_timestamp` or one of the other time functions is no longer refused. The engine has Postgres evaluate the time once, when it holds the write, and holds the statement with that value, so the approval page, the preview and the applied rows all show the same time. The agent sends its own statement again with the approval id and it applies. Before, the agent had to retry with a literal timestamp. `random()`, `gen_random_uuid()` and other values that change on every run are still refused, and the message names the function.
- A held `INSERT` without a column list on a table with a `now()` column default can be applied. The approval binds every column of such an `INSERT`, so the default's time changed between the hold and the apply, and the approved write always failed. The engine now fixes that default's time too. A column left to an identity or to a default such as `nextval()`, `gen_random_uuid()` or any function the database marks volatile (an extension's or your own) is refused when the write is held, and the message names the column, instead of being held as a write that could never apply.
- On the approval and undo pages, short values in the row tables (names, numbers, timestamps) stay on one line instead of breaking mid-value. Only long text wraps, and a wide table scrolls sideways inside its card.
- Row-level security no longer hides itself from the agent. A table whose rows row-level security hides from the agent now gives the `RLS_HIDES_ROWS` warning on every read and write that touches it, not only on an empty result: a `count(*)` returns one row holding 0, and the agent used to take that for an empty table. A write that row-level security refuses (`new row violates row-level security policy`, in its insert, update and delete forms) is `PERMISSION_DENIED` with guidance that names row-level security and sends the person to `basalt init`, where they answer the row-level security question, instead of the generic "denied access" message.
- `list_runs` shows all of an agent's history. Besides runs it now lists the reverts the person signed (`kind` `REVERT`) and the reads the agent made outside any run, grouped per UTC hour (`kind` `LOOSE_READS`), in one time order with the same paging, and `run_history` takes `from` and `to` instead of `runId` to list the reads of one hour. Each item now carries a `kind` (`RUN` for a run). The `cursor` of `list_runs` is a new shape: a cursor from an older engine is `INVALID_ARGUMENT`; call again without it.
- A release now counts as newer than its release candidates. The update notice offers `0.1.0-alpha` to someone running `0.1.0-alpha-rc.3`, and `basalt init` from the release no longer refuses an engine service that runs the candidate as "newer than this basalt".
- `basalt init` installs the engine service from a Homebrew `basalt`, or one unpacked in a folder of your own, with no manual step. The one password dialog now copies `basalt` into a folder only root can change (`/usr/local/libexec/basalt` on macOS, `/usr/libexec/basalt` on Linux), checked against what `init` read, and the service runs that copy. Before, `init` refused a binary in a folder your account owns and handed the agent two `sudo` commands, which an agent session cannot run. After `brew upgrade`, `basalt init` copies the new `basalt` over the service's copy and restarts the engine in the same single dialog. Removing BasaltDB deletes the copy. No message tells you or the agent to run `sudo`.
- A Vault session that a duplicated or otherwise refused frame ends now always closes with `FRAME_INVALID`. It could close with `PROTOCOL` instead and send the Vault a second `SESSION_CLOSE`.
- The engine no longer reports "ledger chain broken" on a new ledger after the database was recreated the same way, for example after running the quickstart again on a fresh Postgres container. The guard now identifies each install by a random id instead of the schema's oid.
- A program on your computer could finish the first setup with a database it controls and leave you unable to set up your own. Running `basalt init` again now asks "Is this your database?" first. After "No, this isn't mine", `basalt init` asks for your password in the system's administrator dialog and resets BasaltDB on this computer: it deletes the engine's config, credentials and certificate pins, restarts the engine and opens the first-install page. No database is touched. On macOS the dialog says what it asks for.
- The engine opens its agents' sockets before it reads the database, so a slow database no longer makes the engine look down to the bot. The first guard read runs beside the serving and gives up after 15 seconds.
- `basalt init` on a computer with the engine service installed moves the service to the `basalt` you ran, through the administrator dialog, when that build is newer than the engine's, for example after `brew upgrade`. Before, the old engine kept answering and the fix was not in effect. An older `basalt` never replaces a newer engine: `init` stops and says which one is newer.
- `basalt mcp --agent NAME` and `basalt init --agent NAME` use the engine config that holds the agent when two exist, a service engine's and your own. Before, the MCP server never connected. They stop only when both hold the agent or neither does, and name the agent and both paths.
- A setup that Postgres stops to break a deadlock (`40P01`, most often autovacuum on a table the setup changes) says that a database maintenance task locked a table and that running the setup again is safe. Before, it showed the raw Postgres error.
- Supabase pooler hosts under `.pooler.supabase.co` are recognised as the pooler, like `.pooler.supabase.com`.
- Setup refuses a database with an older or partial BasaltDB install (`GUARD_UNUSABLE`) at the check, before you sign anything, and links [docs/remove-old-install.md](docs/remove-old-install.md). Before, the check passed and the install failed with `SETUP_FAILED`.
- The passkey label defaults to "Passkey on <hostname>" when the setup page sends none, so the install and Add a passkey no longer fail.
- A failed setup run logs its step, its SQLSTATE and the database's reason, with passwords removed.
- Remove on macOS keeps the engine user and its group together, and says so when macOS refuses to delete the user.
- Reinstall repairs a missing engine group and gives root-owned leftover engine folders back to the engine user, so `basalt init` no longer fails with `chown: _basalt: illegal group name` or leaves the engine crash-looping.
- `basalt init` stops and names the log when the engine service keeps crashing, instead of waiting out the 30 seconds.
- `apply_revert_batch` errors for a revert that is not signed yet point at the revert page instead of the removed `basalt revert`.
- The engine's systemd unit now escapes `%` and `$` in the binary and config paths, so a path containing them starts the engine instead of being expanded by systemd.
- Commands the CLI prints now quote an argument that starts with `=`, so a zsh user can paste them: zsh expands `=cmd` to a path.
- A tool call that panics names its saved crash report even when older reports could not be deleted; it said no report could be saved. A `basalt` command that panics now names its saved report in that case too.
- A read and a refused action are recorded with qualified resource names, as a write is: the agent's `leads` is `public.leads` in `run_history` and the ledger, resolved with the agent's own `search_path`. A read recorded the name as the agent wrote it, and a refused action recorded no resource at all. The guard gets schema version 12 (breaking): run `basalt init` again and update the guard on the page it opens.
- The next step of `APPROVAL_INVALID` `DIFFERENT_WRITE` now repeats the held write's large integer params exactly. They were rounded through a float, so sending the step as it was refused the write again.
- A tool call that panics and could not save a crash report now answers `INTERNAL` with a `personMessage` that says so, as every `INTERNAL` error does; it had none.
- A list cursor the engine did not return now gets `INVALID_ARGUMENT` reason `STALE_CURSOR` from every paged tool. A cursor whose id was not a valid id reached the database from `run_history` and `list_pending` and came back as `STORE_ERROR`, with steps to fix a statement the agent never wrote; `list_runs` already refused it.
- The engine's key files (`channel.json`, `pii.key`) and a remote plugin entry's `auth.credentialFile` are refused when the file has a second hard link, as an agent's credential file already was: another link is another path to the same secret. Every key and credential file is now read with the same checks, and must belong to the user the engine runs as; an agent's credential file may also belong to root. A kept plugin approval, a trusted plugin key and `last-stop.json` now survive a crash right after they are written.
- A refused action with a very long statement, intent, reason or parameters is now in the ledger. The guard used to refuse to record it, so the refusal was only in the engine's log; now it keeps the text cut to its limit (2000 bytes for an intent or reason, 64 KiB for a statement) and ending in `...`, and parameters over 64 KiB as `{"cut": true, "bytes": <size>}`. This is guard schema version 13 (breaking): it also refuses a revert or an approval the agent does not have, or one that does not exist, with the code `NO_SUCH_REVERT` or `NO_SUCH_APPROVAL`, which the engine reads in place of the words "no such revert" and "no such approval". The engine needs this version: run `basalt init` again and update the guard on the page it opens.
- The setup page creates the passkey on the first try for an agent with a long name; before, it refused every passkey it made with "This passkey was made for another setup page". A long agent or database name in the name your password manager shows for the passkey is shortened to fit and ends with "…".
- `basalt init` on an engine already set up ends as soon as the guard update on the page it opened is done: it prints `the guard is updated on the setup page. The agent NAME can go on` and exits `0`. Before, it kept the agent waiting, with no output, for the full 90 seconds it waits for a Remove. A Remove and "No, this isn't mine" work as before.
- The help of `basalt` and `basalt init` now says to connect another database with `basalt init --agent NAME`, and with `basalt init --remote --agent NAME` only on a bot's machine. It named only the `--remote` command.
- `basalt init --demo` on sample tables an earlier demo left behind, with row-level security turned on (for example in Supabase's table editor), now gives the agent its policy on them. Before, the agent saw no lead and its writes were refused, while the page said `demo ready: leads 30, lead_notes 20`. A `basalt_demo` schema that BasaltDB did not make still gets no policy.
- An install from the local setup page records the engine's key in the database, as a setup code's install does, so `status` reports `engineRecord.state` `RECORDED`. It reported `NOT_RECORDED`.
- A statement with no placeholders sent with parameters is `INVALID_ARGUMENT` `the statement uses no parameters but N were given`, instead of `uses 0 parameters ($1..$0)`.

### Security

- The agent's credential file is read without following a symlink at its path, and a file with a second hard link or owned by another user than the engine's or root is refused. Before, a symlink was followed and only the mode of the file it pointed to was checked. A credential file that is a symlink must be replaced by the file itself.
- An engine started as root on a config outside the service folder reads `engine.json` through the same checked read at every change, not by following a symlink.
- Finishing an install that was interrupted now revokes the agent's grants on tables you did not pick the second time. Before, the agent kept read access to them. On a database where that happened, check the agent role's grants and revoke the ones you did not pick.
- Row-level security covers only the agent's own tables. A setup with no read or no write tables also offered every RLS table the agent's role could already read through another grant, such as one to `PUBLIC`, and a read table could get a write policy. Now only the agent's tables get the agent policy, and read tables get a read-only one. On a database where that happened, drop the agent's policy on each table it was not given: `DROP POLICY <agent role> ON <table>`.
- Setup codes and their links expire 10 minutes after they are made (they lasted 24 hours), and a link is refused on open once used or replaced by a newer code. A link found hours later can no longer walk the setup.
- Every MCP tool refuses a call whose arguments hold a `postgres://` or `postgresql://` URL with a password (`INVALID_ARGUMENT`, reason `ADMIN_CREDENTIAL`), before it reaches Postgres. The value is never recorded or logged.
- The release `SHA256SUMS` is signed with keyless cosign, and the signature is attached as `SHA256SUMS.sigstore.json`. `SHA256SUMS` also lists the portal checksum, so one signature covers every file. See [docs/install.md](docs/install.md) to check it with `cosign verify-blob`.

### Breaking for alpha installs

- From 0.0.1: run `brew upgrade basaltdb` (or install the new release), then ask your agent to run `basalt init`. On the computer, init moves the 0.0.1 config folder aside to `<folder>.old` and removes the old engine service in the administrator dialog, then sets the computer up again and prints the new `basalt mcp --agent NAME` line to register. On the page that opens, the setup replaces the database's 0.0.1 install: it removes it and installs in one transaction, once you type the database's name. The 0.0.1 install's agent history, held approvals and passkeys go; your tables and rows stay. [docs/remove-old-install.md](docs/remove-old-install.md) keeps the SQL for an install too broken for the page.
- `basalt init` on your own computer only starts setup. It installs the engine service through the administrator dialog when needed, prints and opens the setup link, and prints the `basalt mcp` line the agent registers. It never asks for or reads the admin connection string. With no dialog, such as in an SSH session, it stops and never runs the engine as your user instead.
- `basalt init --remote` takes `--agent` and no other flag, and its output is text only. A new engine is agent-operated with the Vault on, and the first run prints the connect link of a connect-only code. An expired or refused setup is forgotten on the next run, which makes a fresh code.
- An agent's `credentialFile` in `engine.json` moves inside `store`. An `engine.json` with an agent's own `credentialFile`, or with `directAddr`, is from before this release: every command refuses it and says to run `basalt init`, which moves it aside and sets the computer up again.
- Every command finds `engine.json` by itself: at the system path, else in your own config directory, and it stops with an error when both exist, unless you name an agent that only one holds. `--config` is a flag of `basalt engine` only, so the MCP line is `basalt mcp --agent NAME`; update the line your MCP client runs. The engine service's unit runs `basalt engine --config <system path> --supervise`.
- A database set up by 0.0.1 is not updated in place. Its guard is at version 1, below the lowest version this release updates, so an update refuses it with `GUARD_UNUSABLE` and changes nothing, and the engine serves only `status` on it and gives no update link. The setup page's install replaces it (above); the connect service does once it offers the replace (`pkg/setup`'s `Request.Replace`).
- An updated guard refuses a setup code made by an older `basalt`, which carries a 24-hour expiry, with `EXPIRY_TOO_FAR`. Ask the agent for a new link.

### Known limits

- A pin trusts the provider's certificate authority, so where a provider shares one across customers, another customer on the network path could pose as your database.
- A revert that is too large to prepare even when narrowed to one change and one table cannot be reverted through BasaltDB.
- A reboot between Remove on the setup page and its last step leaves the engine service installed until you remove it by hand, as [docs/install.md](docs/install.md) shows.
- Resetting a setup you did not make needs your OS password. A program running as your user can still start a first setup before you do, and you undo it with "No, this isn't mine".
- On Linux, the administrator dialog shows the system's generic text instead of naming what it asks for.

## [0.0.1-alpha] - 2026-11-15

The first public alpha, for macOS and Linux (amd64 and arm64). Expect bugs and breaking changes between alpha releases.

### Added

- The engine and its MCP server: an agent reads and writes your Postgres through BasaltDB, with a scoped role and no database URL of its own.
- The guard, installed in your own Postgres by `basalt init`: it records every agent write with the old values, refuses schema changes and writes of more than 50 rows, and holds writes of 11 to 50 rows and every DELETE for your passkey approval.
- Undo for a run, a single change or a task, signed with your passkey. Rows changed after the agent are left as they are and listed.
- The CLI: `init`, `status`, `log`, `revert`, `upgrade`, `uninstall`, `service` and `classify`.
- Setup for an agent on another machine, with a setup code (`basalt init --remote`).

### Changed

- The guard's schema is kept as SQL files under one version, 1 (`internal/guard/schema/`).

### Known limits

- Windows is not built yet.
- See the [limits page](https://docs.basaltvault.app/limits/) for what BasaltDB does not catch.
