## Setup

The agent starts setup, the person finishes it on a page and signs with a passkey. One flow does every setup job: install, guard update, repair, passkeys, tables, column PII classes, a database certificate and removal. The person never types a `basalt` command. The admin connection string is typed only on a setup page and never reaches the agent: not in the chat, a file, the environment, a log or an MCP result.

The CLI side is [`basalt init`](cli.md#basalt-init). The sections from [Agents and the admin credential](#agents-and-the-admin-credential) on describe the persona 2 path (an engine run by a bot on a machine the person cannot reach) and the parts the two personas share. Where they still name a removed command or flag, [Removed](cli.md#removed) wins.

### The one setup flow

1. The agent runs `basalt init` (with `--agent` when the engine serves more than one agent, `--remote` on first setup of an agent-operated engine, `--demo` for the sample database). It prints one link.
2. On persona 1, `basalt init` opens its own link in the browser, by the same rule as [Auto-open](cli.md#auto-open): only a link whose origin is the engine's own local page origin. It always prints the link too, and the agent shows it on both personas, so the person can open it by hand when the browser did not open.
3. The page shows what it will do and the SQL, and asks once. The person types the admin connection string on the page, picks the tables, and registers a passkey when the database has none for the page's origin.
4. The SQL runs in one transaction. The page says when it is done; the agent calls `status` to see it.

| | Persona 1 (the person's laptop) | Persona 2 (a bot's machine) |
|---|---|---|
| Page | the engine's local setup page ([Local pages](local-pages.md#local-pages)) | the portal's [connect page](connect.md#the-connect-page) |
| The admin string goes to | the engine, over loopback, used once, never stored | the connect service, in one request's memory, never stored |
| The SQL runs in | the engine | the connect service |
| The passkey belongs to | `localhost` | `basaltvault.app` |

There is no second way to set up: no terminal prompt for the admin string, no admin string in an environment variable, no setup code a person runs on their own computer ([Removed: the laptop setup command](#removed-the-laptop-setup-command)).

### Setup jobs

The same flow does each job. The page names the job, shows the SQL, and asks once.

| Job | How it starts |
|---|---|
| First install | The person asks the agent to connect a database; the agent runs `basalt init`. |
| Guard update | The engine sees the guard is older than the binary. `status` tells the agent to run `basalt init`, which makes an update link. The update applies only the `basalt_meta` migrations the build has and the database lacks: it rotates no password, changes no grant or policy and registers no passkey. |
| Repair | `status` names the problem and tells the agent to run `basalt init` (for example a missing credential file: the page sets a new password and the engine writes the credential). |
| Add a passkey, change tables, change column PII classes | The person asks the agent; the agent runs `basalt init`; the person picks the change on the page. |
| A database certificate no public authority signs | The page shows the certificate and the person pins it for that host ([Trust profiles](trust.md#trust-profiles); on persona 2 [Pinning from the connect page](trust.md#pinning-from-the-connect-page)). |
| Remove Basalt | The person asks the agent. The page shows the `DROP` statements and the service removal. It drops the guard's policies, the demo schema when `--demo` made it (without `CASCADE`, as [`--demo`](cli.md#basalt-init) says), `basalt_meta` and the roles. It registers and asks for no passkey: the admin connection string typed on the page is what allows it, as it allows dropping the schema by hand. On persona 1, after the `DROP` commits, `basalt init` removes the engine service through the [administrator dialog](#the-administrator-dialog), with its own fixed command. |

**Persona 2, planned.** The guard update and the removal on the connect page need setup-code kinds the [setup code](#the-setup-code) rules do not have yet (an `UPGRADE` code without `target`, and a removal kind). Both are planned, with the task that builds the setup flow. That task also says who removes the engine on the bot's machine.

**Holding the link is not enough.** The agent holds the setup link, and a program running as the person's user can forge `Host` and `Origin` on loopback. So:

- Every job needs the admin connection string typed on the page. No setup route acts, stores or keeps anything without it.
- A passkey the job registers arrives in the same request as the admin connection string, and is stored in the job's transaction. The engine keeps no passkey, certificate pin or answer from an earlier request.
- There is no hand-back of a passkey before the admin string and no pairing code.

### The local setup page

Persona 1. The engine serves the setup page on its loopback listener, at the same origin as its approval and revert pages, so the passkey it registers signs there.

- The admin connection string travels from the page to the engine over loopback. The engine, which runs as its own OS user, uses it once for the job's transaction and never writes it to a file, a log or the engine config. It refuses the admin string on every route but the setup page's own.
- The listener keeps the `websec` Host, Origin and header checks of the other local pages.
- **An engine with no config.** On a first install the [administrator dialog](#the-administrator-dialog) starts the service before `engine.json` exists. A service engine (started as its own OS user from the system config path) that finds no `engine.json` does not exit: it serves only `GET /healthz`, the setup page and the two setup routes below on `127.0.0.1:8787` (origin `http://localhost:8787`), and waits. When the first install writes `engine.json`, the engine loads it and serves the agent without a restart. Under `--supervise` this counts as up, so the supervisor never crash-loops on a missing config. When `127.0.0.1:8787` is taken, it exits `1` and names the port and how to find the process, as the [listener](local-pages.md#local-pages) does. Any other config error still stops it with exit `1`.
- **An engine with a config.** A person-operated engine that runs as its own OS user and serves its local pages at `http://localhost:8787` serves the same page and the same two routes there, for the `UPDATE` and `REMOVE` jobs of the agents in its `engine.json`. It never runs an `INSTALL` (`JOB_UNAVAILABLE`): it loads `engine.json` only when it starts. An agent-operated engine, or one started as root, refuses every setup request `JOB_UNAVAILABLE` without reading it.
- **The link.** `basalt init` prints `http://localhost:8787/setup/#1.<b64url(json)>`, with `{ "job", "agent", "osUser", "demo" }`: `job` `INSTALL`, `UPDATE` or `REMOVE`, `agent` the `--agent` name (default as `basalt init` picks it), `osUser` the OS user `basalt init` runs as (the agent's), `demo` whether `--demo` was given (always `false` for `UPDATE` and `REMOVE`). The fragment never reaches a server or a log. It is not a secret ([Holding the link is not enough](#setup-jobs)). The page shows the job, the agent and its OS user before anything is asked. The agent writes the link, so the person confirms `osUser` on the page: it is the OS user the agent runs as and the one the agent's socket admits.
- **Jobs.** `INSTALL` for an engine with no config; `UPDATE` (the [guard update](#setup-jobs)) and `REMOVE` (Remove Basalt) for an agent of an engine with a config. The other [setup jobs](#setup-jobs) add their `job` values with the tasks that build them. Until the table picker lands, the page offers only the sample database: an `INSTALL` without `demo` is refused `NO_TABLES` (`Picking tables on this page is not available yet; set up the sample database with basalt init --demo.`).
- **Which link `basalt init` prints.** Not built yet: how `basalt init` on an engine with a config prints the `UPDATE` link (when `status` says the agent's guard is older than the binary, [Next steps](next-steps.md#next-steps)) and the `REMOVE` link, and when it then removes the engine service through the [administrator dialog](#the-administrator-dialog), is decided with the `basalt init` task. The page runs both jobs from a link of the shape above.
- **What the engine takes from the request.** `agent` must be a valid agent name and not in `engine.json`. `osUser` must be an existing OS user that is neither root nor the engine's own user, and not in the engine's group. The engine chooses the rest: the prefix `basalt`, the statement timeout `30s`, the agent's password (256 bits, generated in the engine, never in a request or an answer), the credential file `agents/<agent>.url` (mode `0600`, the engine's own user) and the agent's entry in `engine.json` (`operatedBy` `PERSON`, the local pages). For `demo`, it creates the sample schema as [`--demo`](cli.md#basalt-init) says. For `UPDATE` and `REMOVE`: `agent` must be in `engine.json`, `osUser` must be the OS user `engine.json` gives it, `demo` must be `false`, and the request carries no `answers`, `challenge` or `passkey` (`ANSWERS_INVALID`). The admin connection string must name the database the agent's credential connects to, compared as [The setup checks](#the-setup-checks) compare a target (host, port and database, or the Supabase project ref and database), before anything connects with it: another database is `TARGET_MISMATCH`, and a string that names more than one host `CONNECTION_STRING_REFUSED`. A credential the engine cannot read is `SETUP_FAILED`.

| Method and path | Body | Answer |
|---|---|---|
| `GET /setup/` | | The setup page. It reads the job from the fragment |
| `POST /api/v1/setup/check` | `job`, `agent`, `osUser`, `demo`, `databaseUrl` | `200 { "database", "lines", "sql", "questions", "notes", "passkeyNeeded", "challenge" }`; an `UPDATE` or `REMOVE` answers without `challenge`, with `passkeyNeeded` `false` and no question. It connects with `databaseUrl`, reads and changes nothing. `lines` is the fixed summary, and `sql` the SQL with passwords redacted. `questions` are the row-level security questions (`kind` `ROW_LEVEL_SECURITY`, `table`, `text`, `choices` `ALL_ROWS` or `NONE`). `challenge` has the [passkey challenge](connect.md#the-passkey-challenge)'s fields, made with a key the engine holds only in memory (a restart invalidates it), over the job's fields in place of a setup fingerprint. It is not single-use, so it can be sent again until `expiresAt`. The admin connection string in the same request is what lets a run happen |
| `POST /api/v1/setup/run` | the check's fields, `answers` (one per question), and, when a passkey is registered, `challenge` unchanged and `passkey` (the [passkey registration response](approvals.md#codes) and an optional `label`) | `200 { "agent", "lines", "warnings", "passkeys", "mcpCommand" }`. `lines` says what the install did, such as `demo ready: leads 30, lead_notes 20`. `passkeys` lists each registered passkey's credential id, label and [check code](connect.md#the-passkey-check-code). `mcpCommand` is the `basalt mcp` line the agent registers, empty after a `REMOVE` |

- **Each call stands alone.** `run` repeats every check of `check` and computes the questions itself. It refuses an answer to a question it did not compute, and a question left without one. The page holds `databaseUrl` in memory and sends it with both calls. The engine keeps nothing from `check`.
- **What `run` does.** Before it connects, it checks the challenge's expiry and the passkey as `RunSetup` does. The challenge's binding (the job, the database the server names and the admin string's host) is checked inside the transaction once the server named the database, before any change. Then, in one transaction: the guard install, the sample data for `demo`, the agent role with its password, the grants, the confirmed agent policies, `attach`, and `register_passkey` for a passkey given (RP ID `localhost`, origin `http://localhost:8787`). A passkey is needed when the database has no active passkey for that origin. Without one, `run` is refused `PASSKEY_REQUIRED`. After the commit, the engine writes the credential and `engine.json` and serves the agent. If that write fails, the answer is `500 SETUP_FAILED` and the agent's password is not kept; `basalt init` then makes a repair link.
- **What `run` does for `UPDATE`.** In one transaction: the `basalt_meta` migrations the build has and the database lacks, nothing else (no password, grant, policy or passkey). `check` and `run` refuse a database with no guard (`GUARD_MISSING`), a guard as new as the binary (`GUARD_CURRENT`, `There is nothing to update.`), a guard newer than the binary (`GUARD_NEWER`, telling the person to update BasaltDB on this computer), another prefix (`PREFIX_MISMATCH`), and a database without the agent's role (`ROLE_MISSING`). The engine reads the guard on every call, so the agent is served again without a restart; `lines` says `guard updated in the database <database> from version <from> to <to>`.
- **What `run` does for `REMOVE`.** In one transaction, the SQL `check` showed, planned again from the catalog: the `DROP POLICY` of each policy named after an agent role or the guard role, `DROP SCHEMA IF EXISTS basalt_meta CASCADE`, and `DROP OWNED` and `DROP ROLE` for each agent role of the prefix, the group and the guard role; then the sample schema's `DROP TABLE` and `DROP SCHEMA` without `CASCADE` when the demo made it (marked by its comment), in a savepoint, so a view or key of the person's on it keeps the schema (a warning says so) and the rest is still removed. A role that still holds privileges in another database fails the whole run (`SETUP_FAILED`, nothing changed). After the commit the engine removes from `engine.json` the agent and every other agent whose credential connects to the same database (and their names from every plugin entry's `agents`), then deletes their credential files; when no agent is left it deletes `engine.json`, so the engine waits for a first install at its next start. The running engine keeps the agents in memory until it stops; their calls fail to log in. If the config write fails, the answer is `500 SETUP_FAILED`, and the same link run again finishes it: on a database Basalt is already gone from, `check` says so and `run` only removes the agents from this engine.
- **The admin connection string.** Only these two routes read `databaseUrl`. Every other route of the listener refuses a body that holds a `databaseUrl` field (`400 INVALID_ARGUMENT`, fixed message). The engine never writes, logs or returns the string or any part of it, and never logs these routes' bodies. Each answer and each refusal message is built from fixed words and from values read from the catalog, never from the string or a driver's message, as [Answers are fixed text](connect.md#setupservice-calls) says for the connect service.
- **Checks.** The routes keep the listener's `websec` Host check (loopback names only), its Origin check (a `POST` must carry `Origin: http://localhost:8787`) and `Content-Type: application/json`, the 16 KiB body limit and `Cache-Control: no-store`. A wrong `Host` is `400` (the listener's check) and a wrong `Origin` `403`, both before the body is read. One setup run, of any job, runs at a time; another is `409 BUSY`. A call stops at 60 seconds and rolls back (`504 TIME_LIMIT`).
- **Errors.** JSON `{ "code", "message" }`. `code` is a reason from [Connect refusals](connect.md#connect-refusals), with the same meaning; `message` is this page's own fixed text, which names no setup code: `CONNECTION_STRING_REFUSED`, `DATABASE_UNREACHABLE`, `CERTIFICATE_NOT_VERIFIED`, `LOGIN_FAILED`, `PREFIX_MISMATCH`, `ROLE_EXISTS`, `NO_TABLES`, `TABLES_CHANGED`, `ANSWERS_INVALID`, `PASSKEY_REQUIRED`, `CHALLENGE_EXPIRED`, `CHALLENGE_INVALID`, `PASSKEY_INVALID`, `SETUP_FAILED`, `TIME_LIMIT`, `BUSY`, `REQUEST_TOO_LARGE`, `TARGET_MISMATCH` and `ROLE_MISSING`. The local codes are `INVALID_ARGUMENT` (`400`: a bad field, an agent already configured or not in `engine.json`, an OS user refused), `JOB_UNAVAILABLE` (`409`: an `INSTALL` on an engine that already has a config, which `INSTALL` never changes; an `UPDATE` or `REMOVE` on an engine with no config; any job on an agent-operated engine), and `GUARD_MISSING`, `GUARD_CURRENT` and `GUARD_NEWER` (`409`, `UPDATE` only, above). A refusal from the database is `409`, unreachable `503`, a refused `Origin` `403`, a wrong `Host` `400`, a wrong content type `415`, a body over the limit `413`.
- **`contract/surface.json`** gains the page `/setup/` with the code that adds `web/setup/`.

### The administrator dialog

Persona 1. On first install `basalt init` installs the engine as a service under its own OS user, and on removal it removes that service. The agent cannot type a password, so `init` asks through the system's own administrator dialog (`osascript` "with administrator privileges" on macOS, `pkexec` on Linux), which only the person can answer.

- **A fixed command.** The dialog runs a script `init` builds from constants only: create the engine's OS user and the system directories, write the service unit that runs `<binary> engine --config <the system config path> --supervise`, and start it (on removal: stop it, remove the unit, the system directories and the OS user). `<binary>` is the running binary's own path with every link resolved. No value from the agent reaches it: not `--agent`, not the environment, not the working directory.
- **The binary root runs.** Before it asks, `init` refuses a binary that anyone but root could change: the file and every directory above it must be root-owned and not writable by group or others. The script reaches every directory it writes in from `/` without following a symlink anyone but root controls, and refuses a directory on the way owned by anyone but root or the engine's user, or writable by group or others. So an agent cannot swap the binary in a folder the person's user can write to and have the person's password run it as root. When neither dialog exists (an SSH session, a headless machine), `init` says so and stops. It never falls back to running the engine as the person's user.

**Limit of persona 1.** An agent running as the person's OS user can serve a lookalike `localhost` page that asks for the admin string, or replace a `basalt` binary in a folder that user can write to. That is not new (a terminal prompt has the same exposure) and is not built around. Signing stays safe: Postgres checks the exact origin, port included.

### Agents and the admin credential

**Target.** The agent runs `basalt init`; it never takes the admin connection string, so nothing in `init` needs to be refused under an agent. The agent-context markers and the refusals below go with the commands they guarded ([Removed](cli.md#removed)). What stays is the goal: the admin connection string never reaches the agent.

Most people tell their agent "connect to database X" rather than run `basalt init` themselves. Setup must work from that sentence, and the admin connection string must never reach the agent: not in the chat, a file, the environment, a log or an MCP result. The agent-led path is `basalt init --remote` on the agent's side, which needs no admin credential, and `basalt init --setup-code` on the person's own computer, the only place the admin connection string is typed. Planned: the [connect page](connect.md#connect) is the second place, on the portal; the string goes from the person's browser to the hosted connect service for one setup, never to the agent's machine. It is the same for an agent on the person's laptop and a bot on its own machine, and for each further database: a new agent name, its own `--database-url` (or none, with a [connect-only code](#connect-only-setup-codes)), the same engine.

- **Agent context.** `basalt` runs under an agent when one of these environment variables is set to a non-blank value: `BASALT_AGENT_CONTEXT` (Basalt's own marker, which a person can set in a bot's environment), `CLAUDECODE`, `CODEX_SANDBOX`, `CODEX_SANDBOX_NETWORK_DISABLED`, `GEMINI_CLI`, `CURSOR_AGENT`, `OPENCODE` (set by coding agents in the shell they run commands in). The first one set, in that order, is the one named in messages.
- **Refused under an agent.** Every command that takes the admin connection string (`basalt init` without `--remote`, `basalt init --setup-code`, `upgrade`, `uninstall`, `classify` and the `passkey` and `engine` subcommands that connect as the admin) refuses under an agent with exit `1` before it reads one: `BASALT_ADMIN_DATABASE_URL` is not read and there is no prompt. `basalt init` and `basalt init --setup-code` refuse before parsing their other flags (a usage error included), unless an argument is `-h` or `--help` (then the flags are parsed and help is printed, or a usage error when `-h` is a flag's value; nothing is read either way); the others refuse where they would ask. The message names the marker and says what to do instead, and never echoes a connection string: `<command> needs the database admin connection string, and it is running under an agent (<marker> is set), so basalt does not read one. An agent never asks for, accepts or types the admin connection string or password.`, then, for `basalt init`, to run `basalt init --remote` and give the person the setup code it prints; for every other command, to give the person the command to run in a terminal of their own, which no agent reads.
- **Refused without a terminal.** `basalt init` without `--remote` also refuses, the same way and before it reads `BASALT_ADMIN_DATABASE_URL` or stdin, when stdin is not a terminal, whether or not a marker is set: an MCP client that sets no marker still runs the agent's commands with no terminal. Steps hand the agent `basalt init --agent <name>` ([Next steps](next-steps.md#next-steps)); until the local setup page exists that run ends with this refusal, never with admin access. At a terminal it never reads `BASALT_ADMIN_DATABASE_URL` ([Environment variables](cli.md#environment-variables)): when the variable is set it refuses, does not use the value, and tells the person to remove it and change that database password; the admin connection string is typed at its prompt only.
- **An admin credential in the agent's environment.** When `BASALT_ADMIN_DATABASE_URL` is set under an agent, the refusal adds `BASALT_ADMIN_DATABASE_URL is set where an agent can read it; basalt did not use it. Remove it from this environment and ask the person to change that database password now.` `basalt init --remote` never uses it either; when it is set, init warns on stderr (`basalt: warning: BASALT_ADMIN_DATABASE_URL is set here; basalt init --remote never uses it. If an agent can read this environment, remove it and ask the person to change that database password now.`) and goes on. A `--database-url` with a password is refused as before ([`basalt init --remote`](#basalt-init---remote-the-engines-machine), step 1).
- **A credential in a tool call.** Every MCP tool, before it does anything else (before the engine checks the guard, reaches Postgres or writes the ledger), looks at its arguments: every string, nested ones and object keys included, and the raw request when it is not valid JSON. One that holds a `postgres://` or `postgresql://` URL (the scheme in any case) with a password, in its user part (`postgres://user:secret@host/db`) or as a `password` parameter, is refused with `INVALID_ARGUMENT` reason `ADMIN_CREDENTIAL`. A connection string without a password is not refused. The call changes nothing and is not recorded: no run, no change record, no refusal row, no log line carries the value or any part of it, and neither does the error, whose message is fixed. The next steps tell the agent to ask the person to change that database password now and to call again without the string; the person's message says the same. This is a mistake guard, like the markers above. The engine-down tools of `basalt mcp` (the engine does not answer) refuse the same way. A password in another spelling (a keyword and value string, a percent-encoded `password` parameter name, or split over several arguments) is not detected, and the boundary stays `basalt init --remote`.
- **What an agent reads.** Text written for agents never tells one to run `basalt init` with `--agent` and without `--remote`: the MCP `initialize` instructions ([What the agent is told](showing-links.md#what-the-agent-is-told)), tool descriptions, next steps and the engine's own messages, `basalt --help` (which ends with `Agents: never ask for or accept the database admin connection string or password.` and `To set up, run basalt init --remote and give the person the setup code it prints.`), `basalt init --help` when an agent reads it (an agent marker is set, or stdin is not a terminal; it then shows only the `--remote` and `--setup-code` forms and the rule above), the error for an agent missing from the config (`agent "<name>" is not in <config>; set it up with basalt init --remote --agent <name> and give the person the setup code it prints`), and the agent setup guide. A test reads these surfaces and fails on such a command. A `RUN_COMMAND` step addressed to the `PERSON` on a person-operated engine is the person's command, run in their own terminal, and is not covered by this rule.
- **The honest limit.** The markers stop mistakes, not a determined agent: an agent that shares the person's OS user and terminal can unset them, or read what is typed there, and `sudo` drops them by default (`env_reset`), so a bot with passwordless `sudo` is not detected under it. The boundary is `basalt init --remote` with the admin connection string typed only on the person's own computer, and the engine and the agent running as OS users who cannot read the person's files.

### Who operates the engine

**Target.** `--remote` on the first setup of an agent marks the engine agent-operated (`"operatedBy": "AGENT"`); afterwards the config says it. Without it the engine is person-operated. `--operated-by`, `--passkey-origin` and `--dev-local-pages` are removed: the operator fixes the page origin (the engine's local pages for `PERSON`, the portal for `AGENT`).

- `basalt init --operated-by=person|agent`, default `person`, is saved in `engine.json` as the top-level `"operatedBy": "PERSON"` or `"AGENT"` (absent means `PERSON`). One engine per machine, one operator. It decides who runs machine steps ([Next steps](next-steps.md#next-steps)) and is independent of how setup runs: the chat-only case is `--operated-by=agent --remote`; a person may also run init with the admin credential on a machine they control and hand that engine to a bot. `basalt init --agent NAME --operated-by=agent` (no `--remote`) does exactly that: it writes `"operatedBy": "AGENT"`, uses the portal's pages (`--passkey-origin` defaults to `https://portal.basaltvault.app`, and any other origin is a usage error unless `--dev-local-pages`, [Page origins](page-links.md#page-origins)), turns the Vault on unless `--vault=off`, saves `--operated-by=agent` in `initArgs`, and, when it installs the service, passes `--operated-by` to `service install --agent`. An explicit `--operated-by=person` writes `"operatedBy": "PERSON"`, so an engine can be switched back; without the flag the config's value stays. `basalt init --help` names `--operated-by` and the other two modes, `--remote` and `--setup-code`, for a person at a terminal; when an agent reads it, it shows only the agent-led setup ([Agents and the admin credential](#agents-and-the-admin-credential)).
- With `AGENT`, `pagesUrl` is the portal `https://portal.basaltvault.app` (CO-6, CO-8): the loopback pages would belong to the bot's machine, so a local `pagesUrl` or `--passkey-origin` is refused, except for development with `--dev-local-pages` ([Page origins](page-links.md#page-origins)).
- **In the ledger (CO-15).** Every `HEARTBEAT` row's detail carries `operatedBy` next to `engineVersion` (and `chainBrokenAt` when the chain is broken), so the ledger shows the periods when enforcement was guard-only. A change shows at the next heartbeat.

### `basalt init --remote` (the engine's machine)

**Target.** `basalt init --remote [--agent NAME]` makes a [connect-only setup code](#connect-only-setup-codes) and prints the connect link, nothing else. The steps below that take `--database-url`, `--write`, `--read`, `--all-tables`, `--os-user`, `--engine-user`, `--prefix`, `--statement-timeout`, `--new-code`, `--forget`, `--trust-root`, `--json` or `--yes` describe flags that are removed ([Removed](cli.md#removed)): tables are picked on the connect page, and the defaults those flags changed are fixed values in the code.

Before its probes (step 2), for a host no profile covers whose certificate verifies against no authority this machine trusts, `init --remote` offers to pin the chain's top for that host ([Pinning on first use](trust.md#pinning-on-first-use); `--trust-root SHA256` answers without a terminal). Under an agent marker it pins nothing, refuses `--trust-root`, and prints the person's `basalt trust pin` command; the setup goes on.

`basalt init --remote --agent NAME [--write schema.table,…] [--read schema.table,…] [--all-tables] [--prefix P] [--statement-timeout D] [--operated-by person|agent] [--database-url URL] [--new-code] [--forget] [--config PATH] [--json]`

`--all-tables` (in place of `--write` and `--read`), `--forget`, and running without `--database-url` are for a [connect-only code](#connect-only-setup-codes).

0. **A release version.** The code carries the build's version, which must be `major.minor.patch` with an optional pre-release (a leading `v` is dropped). A build that reports anything else (a source build without tags reports `dev`) is refused before anything is written, with exit `1` and `this build of basalt has no release version (it reports "dev"), so it cannot make a setup code; install a release build`.
1. **No admin credential.** `--database-url` is the connection string without a password (Supabase shows it with a `[YOUR-PASSWORD]` placeholder), required on the agent's first run and read from the credential file after that. It is not required when init makes a [connect-only code](#connect-only-setup-codes); when it is missing and init cannot make one, the message also names what the connect path needs (an agent-operated engine with the Vault on and the portal's pages, and init run as the engine's OS user). A URL with a password, in the user part or as a `password` parameter, is refused before anything else (exit `1`), and never written, logged or echoed: `This connection string contains a password. basalt init --remote does not need it and it must not be shared with an agent: change your database password now.` The host, port and database come from the URL itself (`postgres://user@host:port/database`): a `host`, `hostaddr`, `port` or `dbname` parameter is refused (exit `2`), so the setup code and the agent's connection name the same database. Login parameters of the URL (`user`, `passfile`, `service`, `sslcert`, `sslkey` and the like) never reach the agent's credential file. `BASALT_ADMIN_DATABASE_URL` is ignored and there is no prompt.
2. **The agent's password stays here.** Init generates it (256 bits, as `basalt init` does), writes the agent's connection string (user `<prefix>_agent_<name>`, or `<prefix>_agent_<name>.<ref>` through Supabase's pooler) to the `0600` credential file, and puts only its SCRAM-SHA-256 verifier in the code. Because the verifier is sensitive ([The setup code](#the-setup-code)), the connection string it writes keeps the strongest protection init can confirm, on by default, in this order: `sslmode=verify-full` with channel binding (`channel_binding=require`, SCRAM-SHA-256-PLUS, bound to the server's TLS certificate); `sslmode=verify-full` alone, for a server whose certificate verifies but that offers no channel binding (PgBouncer, Supabase's pooler); `sslmode=verify-ca` (when the connection string had it) or `sslmode=require`, with channel binding; else the connection string as built. A `verify-ca` or `verify-full` the connection string already had is never weakened. Only a verified certificate stops an active attacker who holds the verifier: with `sslmode=require` they can pose as the server with their own certificate and recover the `ClientKey` from the agent's proof, so channel binding there only stops a plaintext downgrade and a relayed session. Init tries each first with a login bound to fail (the new password is not set yet). With channel binding only a refused password (`28P01`) counts, which proves TLS and channel binding work; `verify-full` alone counts on any refusal of the login (SQLSTATE class `28`, or Supabase's pooler answering `Tenant or user not found` for a role it does not know yet), since the client sends its login only after a TLS handshake whose certificate verified for the host name. On Supabase's pooler (`*.pooler.supabase.com`) that is the pooler's own certificate, the one the agent's connection checks. When none counts (no TLS, a Unix socket, `sslmode=disable`, a certificate that does not verify and no channel binding, or the database is not reachable), it keeps the connection string as built, since a credential that cannot log in is worse; a probe that reaches no address of the server (every address failed to connect or timed out) ends the probing. Init prints one line saying what it applied, for example `basalt: connection protected: database identity verified (channel binding not available through the Supabase pooler)`, or `basalt: connection not protected further: ...` with the reason, the `sslmode` kept and, when no certificate verified, a hint to add `sslrootcert`; a certificate signed by a CA the system does not trust verifies when the connection string names it with `sslrootcert`; Supabase's and Amazon RDS's need none, and a CA the person adds with `basalt trust add` needs none ([Trust profiles](trust.md#trust-profiles)). Each run leaves up to three failed logins in the server's log (some hosts ban an address after many); running init again probes again, as when the server's certificate changes. A new password for an agent whose role already logs in goes to `<credentialFile>.pending` (`0600`) instead: the old one keeps working until the person runs the code, and the engine swaps the files when it sees the setup recorded (below). For a connect-only code there is no address to build a connection string from, so the password goes to `agents/<agent>.secret` instead and nothing is probed ([Connect-only setup codes](#connect-only-setup-codes)).
3. **The kind of code.** A connect-only code is `INSTALL`, or a recovery `AGENT` code ([Connect-only setup codes](#connect-only-setup-codes)). Otherwise `INSTALL` when the agent's role cannot log in with its credential (or there is none yet). Otherwise `AGENT` when `--write`, `--read` or `--statement-timeout` change, or with `--new-code` (then with a new password and verifier); else `UPGRADE` when the installed guard (read with the agent credential, which every guard version allows) is older than this build's; else an `AGENT` code with no change and no verifier (it re-applies the grants, and the person's computer registers a portal passkey when none is active). A code of any kind also applies the migrations the database lacks up to `guard.to`.
4. **One pending code per agent.** While an unexpired code is pending and nothing changed, init prints the same code again (`reused: true`: same `setupId`, same expiry). A code is valid for 10 minutes, so this reuse applies only within those 10 minutes. An expired code is never reprinted: the next `basalt init --remote` makes a fresh one. A change or `--new-code` makes a new one with a new `setupId` and expiry; the old one is then refused by the person's computer once the new one has run (newer setup, below). An expired code is replaced by a new one. A pending connect-only code is not replaced before it expires ([Changes while waiting](#connect-only-setup-codes)). After it expires it is replaced, even inside the 30-minute grace in which a run the person already confirmed may still finish: that run is abandoned (its password is gone with the old `.secret`, and the engine collects only the new code), and the person sets up again from the new link.
5. **Config.** Init writes `engine.json` as `basalt init` does (`initArgs`, [CLI](cli.md#cli)), plus `operatedBy`, `pagesUrl` and, per agent, the pending setup: `"setup": { "setupId", "kind", "guardVersion", "expiresAt", "code", "fingerprint" }` (`guardVersion` is the code's `guard.to`; `code` is the setup code, kept so `status` and a re-run hand out the same one). A connect-only code adds `"awaitingAddress": true` to `setup`, replaced by `"refused": true` when the person says no ([Connect-only setup codes](#connect-only-setup-codes)). Nothing secret goes in `engine.json`. `setupId` is a UUIDv7 of the clock now, and `expiresAt` is its time plus 10 minutes, truncated to the second.
6. **Output.** Exit `0`: the setup is pending, not failed. Text: the code in a block of its own, its [fingerprint](#the-setup-code), and what the person does with it. It also prints the `basalt mcp` command the agent registers in its client: `<binary> mcp --agent NAME`, where `<binary>` is the absolute path of the running `basalt` with links resolved (the agent app may not have it on its `PATH`; a path under the temp directory or a Go build cache is kept, with a warning line to put the binary in a folder that survives), plus `--socket-dir` whenever the socket directory is not the one `basalt mcp` uses when no `--socket-dir` is given (`basalt mcp` never reads the socket directory from the config), and `--config` whenever `basalt mcp` would not find the config by default (the same arguments `basalt init` prints). `--json`: [`remote-init-result.schema.json`](../api/mcp/setup/remote-init-result.schema.json), with `fingerprint`, `personMessage` (install `basalt` from the official release page on their own computer, run the command, check that it shows the same fingerprint, never paste the database password into the chat), `mcpCommand` (that command as an argv array) and `nextSteps`: P `RUN_COMMAND` (`basalt init --setup-code <code>`, on their own computer), P `TELL_AGENT`, A `END_TURN`, A `CALL_TOOL` (`status`). A code longer than 1500 characters is refused (exit `1`), saying to name fewer tables. On an engine whose `operatedBy` is `AGENT`, whose `vault` is `ON` and whose `pagesUrl` is the portal (not with `devLocalPages`), when the whole link fits `linkBudget` ([The connect link](connect.md#the-connect-link)), init also prints the [connect link](connect.md#the-connect-link) `https://portal.basaltvault.app/connect#<code>` next to the code and fingerprint, and `--json` carries it as `connectUrl`, in `personMessage` with `links`, and as a `PERSON` `OPEN_LINK` step before `RUN_COMMAND` ([the connect-link steps](next-steps.md#next-steps-with-the-connect-link)); the message says the link uses Basalt Vault, a hosted service, and the laptop command is the other way (this message leaves out the release page address of the one without the link). When the link does not fit, the text output prints the code and says to paste it at `portal.basaltvault.app/connect`, and the result has none of those fields. There is no network call either way; `operatedBy` and `vault` are those this run writes to `engine.json`. A connect-only code's output is in [Connect-only setup codes](#connect-only-setup-codes): the link and no laptop command.
7. Init does not install or start the engine: on an agent-operated machine the agent does it with the printed `mcpCommand` (an `AGENT` `RUN_COMMAND`).
8. **As root** (`sudo basalt init --remote`). The config's directory may belong to the engine's OS user, so root trusts nothing that user could redirect, and refuses (exit `1`, nothing written) before reading or writing any credential: a config that is not a regular file with one link, is reached through a symlink anyone but root controls (root-owned links on the way, such as macOS's `/etc`, are followed), is owned by anyone but root or its directory's owner, or is writable by group or others (`... is writable by group or others (mode 0666), so another user could change what root trusts in it; remove that access (sudo chmod go-w ...)`); a config whose agent names a `store.credentialFile` other than `agents/<agent>.url` next to the config, the only path `basalt init` and `basalt service install` write (`the config names the credential file X, not Y where basalt init puts it; as root, basalt init --remote uses only that path. Fix the agent's store.credentialFile in the config`). A `store.credentialFile` that differs only in spelling (`agents/sub/../bot.url`) is accepted, and root then uses the path it computed, never the config's string, and writes that path back to the config as an absolute path (also with a relative `--config`). The `agents/` directory is opened once from `/` without following a symlink anyone but root controls, every directory on the way owned by root or the config directory's owner (when the config directory does not exist yet, the owner of the nearest directory above it that does) and not writable by group or others (made `0700` when missing), and the credential file, its `.pending`, its `.lock` and the agent's `.secret` are then read, written and renamed relative to that directory: an `agents/` swapped for a symlink is refused (`... is not a real directory (a symlink is refused)`), on the first run as on later ones. The config directory is opened the same way, once, and `engine.json` is locked (its `.lock`), read (the checks above again) and written relative to it, so a config directory swapped for a symlink between the hardened read and the write (by a user who owns a directory above it) redirects nothing; a symlinked `.lock` there or in `agents/` is refused as a lock file that cannot be used. The `engine.json` root writes there is handed to the config directory's owner when that owner is not root (set on the new file's descriptor before it is renamed into place), as the files in `agents/` are, and a directory root makes on the way (`agents/`, or the config directory itself) is handed to the trusted owner when its parent belongs to that owner. So on a service engine's machine (`basalt service install` made the config directory, owned by the engine's OS user) `engine.json`, a new `agents/` and every file in it are the engine user's, and the service reads them. Root also records the user who ran sudo (`SUDO_UID`, never `0`) as the person, added to the config's `personUids` (an agent changes plugins only while it runs as a recorded person: [`request_plugin`](mcp-tools.md#mcp-tools)); without `SUDO_UID` it records none. With `SUDO_UID` set, a config directory owned by a user other than root and the one who ran sudo is an engine user's, so root writes the config with `"mode": "SERVICE"` and, once `engine.json` is written, says so on stderr (`basalt: <dir> belongs to uid N, not root or you (uid P): this config is a service one (mode SERVICE). ...`); a config directory the user who ran sudo owns stays theirs, in same-user mode. Every file root makes there (the credential file, its `.pending`, its `.lock` and the agent's `.secret`) is handed to the owner of `agents/`, read from the opened directory, when that owner is not root (the engine's user in service mode, as for the [lock files](#on-the-engine)): the owner is set on the new file's descriptor before it is renamed into place, so the engine reads its credential and promotes a `.pending` one. Root reads only credential files owned by root or that owner, and from one that owner wrote it takes only a string starting exactly `postgres://` or `postgresql://`, with a non-empty password, no `#`, `;`, space or control character, and no parameter but `application_name`, `channel_binding`, `connect_timeout`, `default_query_exec_mode`, `max_protocol_version`, `min_protocol_version`, `require_auth`, `sslmode`, `sslnegotiation`, `sslsni` and `target_session_attrs`, checked with the Postgres driver's own parser as well, whose host, port, database and password must match the URL's (exit `1` otherwise, never echoing the string). Every other parameter is refused, among them those that make the driver read a file for root (`passfile`, `service`, `servicefile`, `sslkey`, `sslcert`, `sslpassword`, `sslrootcert`, `sslcrl`), as is a URL without a password, which falls back to root's `~/.pgpass`: that owner could otherwise have root read a root-only file, or send a password from root's `~/.pgpass` to a server of their choosing. Such a credential is still usable by `basalt init --remote` run as that user.

### Connect-only setup codes

The chat path, where the person gives the bot nothing about the database: no address, no table names. The full connection string is typed only on the [connect page](connect.md#the-connect-page), and the admin password never reaches the bot's machine, not even the engine: the bot controls that machine, so anything the engine receives there, the bot can read.

- **When init makes one.** `basalt init --remote` without `--database-url` makes a connect-only code when all of these hold: the agent has no credential file (a `.secret` left by an earlier connect-only code does not count), the engine's `operatedBy` is `AGENT`, its `vault` is `ON`, its `pagesUrl` is the portal (not with `devLocalPages`), and init can load or make the engine's key ([`engine`](#the-setup-code)). The code has no `target` and carries `engine`. Its kind is `INSTALL`, or `AGENT` with a verifier when it is a recovery code (below). Otherwise `--database-url` is required, as in step 1. When the engine's key cannot be loaded or made (`KEY_ERROR`, or init runs as another OS user than the engine's), init refuses with exit `1`, nothing written: `A setup code for the connect page needs the engine's key, and basalt cannot read or make it as this user (<reason>). Run basalt init --remote as the engine's OS user (the owner of the engine's state directory), or give --database-url <the database, without password>.`
- **`--all-tables`.** In place of `--write` and `--read` (giving both is a usage error, exit `2`): the code carries `agent.allTables` `{ "schemas": ["public"] }`, and the agent gets write access to every table in `public` that exists when the setup runs ([The setup code](#the-setup-code)). Allowed on every path; with `--database-url` the code carries `target` as well, and the page or the laptop command still lists the concrete tables before the person approves. It is the chat path's default way to ask: the bot names tables only when the person named them. Tables made after the setup are not covered; the bot makes a new code to add them.
- **The agent's password without an address.** Init generates the password as in step 2 and writes it to `agents/<agent>.secret` (`0600`, next to where the credential file goes, with the same ownership and root rules as the credential file in step 8). The code carries only its verifier, as always. `engine.json` records the pending setup as in step 5 with `"awaitingAddress": true`; nothing secret goes in `engine.json`. Loading the engine config accepts an agent with `awaitingAddress` and no credential file, and the engine serves it as below. `basalt service install --agent --keep-credential` accepts one too: it places the agent with no credential file and keeps its pending setup in the config. The role is `<prefix>_agent_<name>` whatever the address; through Supabase's pooler the agent logs in as `<role>.<ref>`, and the engine learns `<ref>` when it collects the address.
- **Changes while waiting.** While `awaitingAddress` is set and the code has not expired, a run with the same flags prints the same code (`reused: true`), unless `.secret` is gone (then the code's password is lost and the run makes a recovery code, below); a run that changes the tables, or `--new-code`, is refused with exit `1`, nothing changed: `finish the pending setup on the connect page first, or wait until it expires at <time UTC>`. So `.secret` is never overwritten before its code expires. After it expires the next run makes a recovery code and a new `.secret`, even inside the 30-minute grace; a run the person confirmed before expiry and that finishes after this is abandoned, and the person sets up again from the new link (`SUPERSEDED` stops the old code once the new one has run). A run with `--database-url` removes `.secret` and `awaitingAddress` and goes on as a first run with that address.
- **Recovery codes.** When the pending connect-only code expired before the address arrived, the engine cannot tell whether its setup ran. The next run makes a new connect-only code of kind `AGENT` with a verifier (a new password in `.secret`). The connect service runs such a code as a password rotation when the role exists, with the laptop command's warning for that kind (`Run it only if <name> itself gave you this code.`), and as an `INSTALL` when it does not ([Connect](connect.md#setupservice-calls)). The same holds after the person refused the database (`confirm_database` `NO`, which leaves `"refused": true` in the pending `setup`) and after `--forget`: init makes a recovery code when the agent's pending `setup` is connect-only and either expired or `refused`, or its `.secret` is gone. A recovery code is safe either way: if the old code ran, it rotates that role's password; if it runs first, the old code is refused `ROLE_EXISTS` or `SUPERSEDED`.
- **`--forget`.** `basalt init --remote --agent NAME --forget [--config PATH] [--json]` drops the agent's pending connect-only setup: it deletes `.secret` (and the engine drops any address it collected), and then replaces the pending `setup` with a recovery code as above, with its usual output. The engine never logged in with that password, so nothing in a database depends on it. Refused (exit `1`, nothing changed) when the agent has a credential file or no connect-only setup is pending: `there is no pending setup from the connect page to forget for <agent>`. `--forget` is a one-shot flag and is never saved in `initArgs`.
- **Output.** Exit `0`. Text: the [connect link](connect.md#the-connect-link) and the code's fingerprint, and no laptop command. It also prints the `basalt mcp` command, as in step 6. `--json`: [`remote-init-result.schema.json`](../api/mcp/setup/remote-init-result.schema.json) with `connectOnly: true`, `mcpCommand`, `connectUrl`, `links`, and a `personMessage` that says the page asks for the database's connection string, that the bot never needs it, and to check the fingerprint. `nextSteps`: P `OPEN_LINK` (the connect link), A `END_TURN`, A `CALL_TOOL` (`status`). The page waits until the engine has collected the address and says so, so the person does not have to tell the bot. When the link does not fit `linkBudget`, the text says to paste the code at `portal.basaltvault.app/connect` and `connectUrl` and `links` are left out.

### The setup code

`basalt-setup.1.<payload>.<check>`, one line, shown in a code block (so chat apps do not read `_` as emphasis).

- `payload`: base64url without padding of deflate-raw of the JSON in [`setup-code.schema.json`](../api/mcp/setup/setup-code.schema.json): `format` (1), `setupId` (UUIDv7), `kind`, `prefix`, `target` (absent in a connect-only code), `guard` (`from`, `to`), `build`, `agent` (`name`, `write`, `read`, `allTables`, `verifier`, `statementTimeoutMs`, in that order; absent for `UPGRADE`), `expiresAt`, and from M4.1 `engine` (`publicKey`; below). Never the agent's password, never anything of the admin; the one sensitive field is `agent.verifier` (below). Encoders write compact JSON in the schema's key order, deflated at level 9; decoders accept any raw deflate stream and any key order.
- `check`: base64url without padding of the first 4 bytes of sha256 over the bytes before the last `.` (`basalt-setup.1.<payload>`), 6 characters.
- **Decoding**, in order: drop every whitespace character (a wrapped copy still works); not `basalt-setup.` → `NOT_A_SETUP_CODE` (`This is not a Basalt setup code.`); `basalt-setup.1` with nothing after it → `INVALID`; a version other than `1.` → `UNSUPPORTED_FORMAT`; a check that does not match → `DAMAGED` (`This setup code is damaged; copy it again.`); a payload that is not base64url, inflates past 64 KiB, is not JSON, holds a key twice in one object (at any depth; a decoder that kept the first or the last would read different codes) or fails the schema → `INVALID`; `format` other than 1 → `UNSUPPORTED_FORMAT` (`This setup code is newer than basalt on this computer: update it from the release page.`). The golden fixtures [`setup-code.fixtures.json`](../api/mcp/setup/setup-code.fixtures.json) pin each case, and pin the verifier for a password and salt; the contract test checks them.
- **Rules the schema cannot state:** `guard.from` ≤ `guard.to` (`<` for `UPGRADE`); at least one table in `write` or `read`, unless `agent.allTables`; no table in both; a code without `target` carries `engine`, and an `AGENT` code without `target` carries `agent.verifier`; the role `<prefix>_agent_<name>` at most 63 bytes; `expiresAt` no later than the `setupId`'s UUIDv7 time (its first 48 bits, milliseconds since the epoch) plus 10 minutes. Failing one is `INVALID`. These do not depend on the clock; the clock checks are the person's computer's and Postgres's (below).
- **Fingerprint.** `sha256(utf8("basalt-setup-fingerprint.2\n" + payload))`, where `payload` is the decoded payload written back as the compact JSON an encoder writes (the schema's key order, absent keys left out, no HTML escaping), so it covers every field of the code (agent name, tables or `allTables`, verifier, kind, statement timeout, target, guard, build, expiry, engine key) whatever key order or deflate stream the code-maker used; its first 10 bytes (80 bits, too many to grind a matching substitute within the 10 minutes) in lowercase hex as five groups of four (`3f9a 21c0 7d44 e1b2 90ac`). `basalt init --remote` prints it, `status` returns it while the setup is pending, the agent's `personMessage` names it, and `basalt init --setup-code` shows it before asking. It lets the person check that the code they run is the one their own agent made, not one another chat member posted, or reposted with anything changed. It is a matching aid: it proves nothing about who made the code.
- **`verifier`**: `SCRAM-SHA-256$4096:<salt>$<StoredKey>:<ServerKey>` (RFC 5802 and RFC 7677, standard base64): salt 16 random bytes, 4096 iterations, `SaltedPassword` = PBKDF2-HMAC-SHA-256 of the password, `StoredKey` = sha256(HMAC(`SaltedPassword`, `Client Key`)), `ServerKey` = HMAC(`SaltedPassword`, `Server Key`). Postgres stores a verifier given as `PASSWORD` as is, whatever `password_encryption` says. **The verifier is sensitive.** It is not the password, but whoever holds it and sees one SCRAM exchange of the role (a connection without TLS, or TLS the client does not verify) can derive the `ClientKey` and log in as the agent; with the `ServerKey` they can also pose as the server to the agent. So the code goes only from the agent to the person (and, planned, from the person's browser to the [connect service](connect.md#what-the-connect-service-sees) when they use the connect link), and the agent's connection string is hardened ([`basalt init --remote`](#basalt-init---remote-the-engines-machine), step 2).
- **Kinds (CO-14).** `INSTALL`: the guard, a **new** agent role with its password from the verifier, its grants, a portal passkey; a role that already exists is refused (the code-maker would otherwise set the password of a role that is not theirs). `AGENT`: an existing agent's tables (a role that does not exist is refused), replaced by `write` and `read` as given (grants on tables no longer listed are revoked); with `verifier` its password is rotated, without it kept. `UPGRADE`: migrations only; password, grants and policies unchanged. A code without `target` must be `INSTALL`, or `AGENT` with a verifier (a [recovery code](#connect-only-setup-codes)), and carry `engine`; anything else is `INVALID`. `UPGRADE` codes and other `AGENT` codes keep `target`, since their engine already has an address. The format stays 1: a laptop older than this refuses a connect-only code as `INVALID`.
- **`allTables`**: `{ "schemas": ["public"] }` in place of `write` and `read` (a code with both is `INVALID`). The agent gets write access, with the same grants and policies as a `write` table, to every ordinary and partitioned table in those schemas that the admin role owns when the setup runs; `public` is the only schema allowed, so Supabase's `auth` and `storage` are never included. A table without a primary key is given read access only, as a `read` table, since the guard keys an agent's writes by it, and the summary says so (`<table> has no primary key, so <agent> can read it but not change its rows.`). Partitions are not listed (the agent reaches their rows through the partitioned table), and neither is a table whose name is not a plain lowercase identifier, the only names a setup code's tables may have. A table owned by another role is left out, and the page and the laptop command list it as `not included: owned by <role>`. No table at all is refused (`NO_TABLES`, nothing changed). The setup reads the list again inside its transaction; a list that changed since it was shown is refused, nothing changed (today `SETUP_FAILED`; planned: `TABLES_CHANGED`). On the wire the row-level security questions stay one per table, as for named tables; the connect page asks them once for all the tables (all rows or none), with a per-table override, and sends one answer per table, and the laptop command's `--agent-rls` answers all of them. Planned: the connect page asks no row-level security question and answers `ALL_ROWS` for every table it includes, and for an `INSTALL` code the person may untick tables there ([Tables on the connect page](connect.md#tables-on-the-connect-page)). Tables made later are not covered.
- **`target`**: the database the bot's engine connects to (`host`, `port`, `database`, and `supabaseRef` when the connection string names a Supabase project: a pooler user `postgres.<ref>` or a host `db.<ref>.supabase.co`). Absent in a connect-only code, whose database is the one the person pastes on the connect page; that code gives up the mechanical wrong-database check (`TARGET_MISMATCH`), and the person's own checks replace it: the page names the database before they approve, and the engine serves nothing until they confirm it in the chat ([On the engine](#on-the-engine)).
- **Valid for 10 minutes, single use (CO-13).** `expiresAt` is 10 minutes after `basalt init --remote` made the code. There is no flag that makes it last longer. Because the code-maker writes `expiresAt` and `setupId`, neither is trusted as given: the person's computer (its clock) and the connect service refuse an expired code on open and when the person confirms it, a `setupId` whose time is more than the **clock skew of 5 minutes** ahead of now, and an `expiresAt` more than 10 minutes plus 5 minutes ahead of now (`EXPIRY_TOO_FAR`). Expiry itself is checked without skew: a code is expired from `expiresAt` on. Once the person has confirmed a still-live code (on the connect page, "Yes, same code", or once `basalt init --setup-code` has passed its clock checks), the run itself may finish after those 10 minutes, within a **grace of 30 minutes** (the length of the address hold): `record_setup` refuses `EXPIRED` only once the database's clock is more than 30 minutes past `expiresAt`. Past the grace an unused code is refused in Postgres whatever the client checked, so expiry holds even with an old or modified client. Single use is enforced in Postgres (`basalt_meta.setups`): the person's computer records `setupId` in the install's transaction. A code is also refused when the agent's latest recorded setup is newer (UUIDv7 ids are time-ordered), so an older unused code cannot reset the password to an old verifier. Planned: single use is enforced inside the database the code runs in, so a connect-only code, which names no database, can run once in every database it is pointed at. The connect service refuses a second database while it holds the first one's address (`RUN_ELSEWHERE`, [The address hand-off](connect.md#the-address-hand-off)), and the person's confirmation is what stops the engine using a database they did not choose.
- **`engine`** (M4.1, CO-18): `{ "publicKey" }`, the engine's signing key as its SPKI in base64url (122 characters, [Engine keys](vault-channel.md#engine-keys)), optional in a code with `target` (required in a connect-only code, whose engine signs its request for the address with it). `basalt init --remote` adds it whenever the engine's key file loads; when the file is missing it creates it first, as the engine does on its first start (owned by the engine's OS user, mode `0600`), and when the file is refused (`KEY_ERROR`), or this OS user cannot read or create it (init run as another user than the engine's), it leaves `engine` out and says why on stderr, naming the user to run it as. As root (`sudo basalt init --remote`, a service engine's machine) it reads or creates the key file relative to the state directory opened from `/` without following a symlink anyone but root controls. The state directory comes from `engine.json`, which the config directory's owner may write, so it is trusted no further than the config directory: every directory on the way must be owned by root or the config directory's owner and not writable by group or others, the state directory itself must be owned by the config directory's owner, and init never makes it (the service manager makes the default one when the service starts; when it is missing init says to start the service once, or, for a state directory elsewhere (a config given with `--config` keeps its state next to it), to make it for the config directory's owner with `sudo install -d -m 0700 -o <uid> <dir>`). The file must be a regular file with one link owned by that owner, mode `0600` or narrower, and pass the engine's own checks; a new one is written whole for that owner (given to it before it appears under its name), and one the engine made meanwhile is kept. It is in the payload, so the setup fingerprint covers it. A rule the schema cannot state: a `publicKey` that is not a P-256 SPKI with an uncompressed point on the curve is `INVALID`. The format stays 1: a laptop older than this refuses a code with `engine` as `INVALID` (its schema is closed), and the person updates `basalt`.

### The setup checks

Every runner of a setup code (today the connect service, [`RunSetup`](connect.md#setupservice-calls)) runs these steps, in this order. They were the laptop command's, which is removed; a message below that names the laptop command or a laptop flag is rewritten for the connect page with the code.

1. **Decode and validate** as above. A code without `target` is accepted (the connect service decodes with a flag that allows it). Then, by the runner's clock, exit `1` with nothing changed, in this order: `EXPIRED`, now at or past `expiresAt` (`This setup code expired on <time UTC>. Ask <agent> for a new one.`); `SETUP_ID_IN_FUTURE`, the `setupId`'s time more than 5 minutes ahead of now, and `EXPIRY_TOO_FAR`, `expiresAt` more than 10 minutes and 5 minutes ahead of now (both `This setup code claims a time in the future. Check this computer's clock, or ask <agent> for a new code.`); `BINARY_TOO_OLD`, `guard.to` newer than this binary's guard (`Update basalt on this computer to at least <build>.`); `GUARD_TOO_OLD`, `guard.to` older than 1, the first version with `record_setup`, which a valid code never is (`This setup code is for guard version <to>, but setup codes need guard version 1 or later. Ask <agent> for a new code made with an up-to-date basalt.`).
2. **The admin connection string**, typed on the page, never written anywhere.
3. **Target (CO-17).** The admin connection string must name the same database as `target`: with `supabaseRef`, the same project ref (from the pooler user or the direct host) and database name, so the pooler and the direct host of one project match; otherwise the same host, port and database. A mismatch is refused, never asked about (exit `1`, nothing changed): `This setup code is for database <database> of <Supabase project <ref> | <host>:<port>> (the agent connects there). Your admin connection string points at <...>. Either run this command with the admin connection string of <...>, or ask <agent> for a new code for the database you meant (basalt init --remote --new-code --database-url <that database, without password>).`
4. **The database's state**, read with the admin connection string, refused in this order (exit `1`, nothing changed): `PREFIX_MISMATCH`, `basalt_meta` is installed with another prefix (its owner role is not `<prefix>_guard`: `This setup code is for prefix <prefix>, but this database's Basalt uses <installed>.`); `USED` and `SUPERSEDED` (read from `basalt_meta.setups`, and enforced again by `record_setup`: `This setup code was already used on <time UTC>. Ask <agent> for a new one.`, or `A newer setup for <agent> already ran on <time UTC>. Ask <agent> for a new code.`); `ROLE_EXISTS`, an `INSTALL` code whose role already exists (`<role> already exists. This code would replace its password: ask <agent> for a new code, or run basalt init --remote --new-code for that agent if it is yours.`), also enforced in Postgres, since the `INSTALL` SQL creates the role with a plain `CREATE ROLE`, never `IF NOT EXISTS`; `ROLE_MISSING`, an `AGENT` code whose role does not exist. The fixtures' `laptop` cases pin this order. Then an `UPGRADE` code whose `guard.to` is at or below the installed guard's version has nothing to do: exit `0`, nothing changed and nothing recorded (`basalt: the guard is already at version <installed> and this code upgrades it to version <to>: nothing to upgrade; nothing changed`).
5. **Show, then ask.** First the summary, whose lines are fixed so the person reads the same words every time: by kind, `This creates the agent <name> (role <role>). Its password comes from the code: only whoever made this code can log in as <role>.` (`INSTALL`), `This replaces the password of the existing agent <name> (role <role>): only whoever made this code can then log in as <role>. Run it only if <name> itself gave you this code.` (`AGENT` with a verifier), `This changes the tables of the existing agent <name> (role <role>); its password stays.` (`AGENT` without), or `This upgrades Basalt's guard from version <from> to <to>; no agent changes.`; then `Prefix <prefix>, statement timeout <n> ms, at most 8 connections.` (for `AGENT`, with `(now <m> ms)` after the timeout when the role's current `statement_timeout` differs, and `(<m> ms set for this database only, which takes precedence)` when the role has a different `statement_timeout` for the connected database (`ALTER ROLE ... IN DATABASE`), both joined by `; ` when both apply; `UPGRADE`: `Prefix <prefix>.`); then `Setup fingerprint: <fingerprint>. Check that <name> shows the same fingerprint.` (`your agent` for `UPGRADE`). Then in words what the agent gets (`<agent> will be able to read … and change rows in …, up to 10 rows at a time without asking you, 11 to 50 with your passkey, never more. It cannot change your tables' structure.`; with `allTables`, the tables are the ones in those schemas the admin role owns now, listed by name, then each table left out as `not included: owned by <role>`), tables outside `public` flagged (for Supabase, `auth` and `storage` more strongly); then the row-level security question, as `basalt init` asks it (`--agent-rls`: the checklist at a terminal, one line from piped input, or the flag's list form, see [the `basalt init` command](cli.md#cli); with `--yes` or `--dry-run` and `--agent-rls=ask`, every table is answered yes and one line on stderr names them and says how to opt out); the wire stays one answer per table; then the SQL (the role's password shown as the verifier); then `Run this? [y/N]` unless `--yes`. **All or nothing (CO-16):** every requested table or none; to change the list the bot makes a new code. `--dry-run` prints and runs nothing.
6. **One transaction:** the missing migrations, the role (`CREATE ROLE ... PASSWORD '<verifier>'` for `INSTALL`, `ALTER ROLE ... PASSWORD '<verifier>'` for `AGENT` with a verifier), the grants, the confirmed agent policies, `attach`, and `basalt_meta.record_setup`. Any failure leaves the database as it was.

### Removed: the laptop setup command

`basalt init --setup-code`, which ran a setup code on the person's own computer with the admin connection string, is removed (its checks stay, in [The setup checks](#the-setup-checks)), with its flags (`--engine-url` included) and the laptop half of the setup code. Persona 2 has one setup path, the [connect page](connect.md#the-connect-page): `basalt init --remote` makes only [connect-only setup codes](#connect-only-setup-codes), and `--database-url`, which made a code for the laptop command, is removed. The [setup code](#the-setup-code) format stays, for the connect page.

### On the engine

- **Serving while an `INSTALL` setup is pending.** An agent whose `engine.json` has a pending `INSTALL` `setup` is served degraded: `status` works, and every other tool answers `UNAVAILABLE` reason `SETUP_PENDING` (`SETUP_EXPIRED` after `expiresAt`) with the [steps](next-steps.md#next-steps-per-code), the pending `code` filled in. A pending `AGENT` or `UPGRADE` setup does not change serving; `status` reports `SETUP_CHANGE_PENDING` (except a connect-only recovery code, whose agent has no credential yet: it is served degraded as a pending `INSTALL`, [The engine and a connect-only code](#the-engine-and-a-connect-only-code)). An expired `AGENT` or `UPGRADE` setup is dropped from `engine.json`, and the problem that called for it comes back with its steps.
- **Finishing.** On `status`, on every call while degraded, and at each heartbeat, the engine logs in with the agent's credential (not for a connect-only code before the person confirmed its database, [The engine and a connect-only code](#the-engine-and-a-connect-only-code)) (the `.pending` one first, when there is one) and looks for the pending `setupId` in `basalt_meta.agent_setups`. Found: it moves a `.pending` credential over the credential file, clears `setup` from `engine.json`, and serves normally; `setup.state` is `DONE`. Logging in proves the role exists with the bot's password: only the bot knows it, and the verifier came from the bot. Guard version, grants and passkeys are then `status`'s usual checks (`GUARD_OUTDATED`, `PERMISSION_DENIED` on use, `NO_PASSKEY`). Details: the engine moves the `.pending` credential and writes `engine.json` (atomically, only when the agent's pending `setupId` is still the one found, never through a symlink, under `<config>.lock`, the config-wide lock every read-modify-write of `engine.json` by `basalt init` takes too) while it holds `<credentialFile>.lock`, the lock `basalt init --remote` takes; it moves `.pending` only when that path still names the file that logged in (a regular file with one link, owned by the engine's user, mode `0600`), and only when it names the same host, port, database and user as the engine's credential (a code for another database is moved over by the next `basalt init --remote`, and the engine uses it once restarted); the engine's connections then log in with the new password, with no restart. A held lock or a failed move leaves the setup pending in memory and the next call or heartbeat tries again; a config the engine cannot write is logged, and the agent is served all the same, since the database, not the file, says the setup ran.
- **Lock files.** `<config>.lock` and `<credentialFile>.lock` belong to the engine's OS user, mode `0600`, so the engine can always take them. Writers that run as root take them too and never leave one the engine cannot open: `basalt service install --agent` holds `<config>.lock` from reading `engine.json` until the new file is in place, and a lock file that a root process creates, or finds owned by root, is handed to the owner of its directory when that owner is not root (in service mode the engine's user owns the config and credential directories). A lock file the engine cannot open (permissions, owner, not a regular file) is not retried in silence: the engine logs it and `status` reports the problem `LOCK_FILE_UNUSABLE` (`WARNING`, its `personMessage` naming the file) for as long as the next try fails; a `.pending` credential is not promoted meanwhile. Its fix is a root command on the engine's machine, so it is a `PERSON` step on an agent-operated engine too.
- **The shim** reads `operatedBy` and `setup` from the engine config when the engine is down; when it cannot read the file it assumes `PERSON` and no pending setup.
- **Fingerprint in messages.** While a setup is pending, `status` returns `setup.fingerprint`, and every `personMessage` that hands the person the setup code names the fingerprint and asks them to check that `basalt init --setup-code` shows the same.

### The engine and a connect-only code

How the engine of a [connect-only code](#connect-only-setup-codes) gets its database's address, checks it, and starts only after the person confirmed it. The connect service's side is [The address hand-off](connect.md#the-address-hand-off).

- **Serving while waiting.** While the code is pending, the agent is served degraded as for a pending `INSTALL`: `status` works, and every other tool answers `UNAVAILABLE` reason `SETUP_PENDING` (`SETUP_EXPIRED` after the collect window: the code's life plus the 30-minute hold), with the steps of [Next steps for a connect-only code](next-steps.md#next-steps-for-a-connect-only-code). `setup.connectOnly` is `true`. Until the address arrives, `status` reports `SETUP_NOT_RUN` with the message `Waiting for the setup on the connect page. If you already approved it there, open the same link again and approve once more: your bot will connect.` (the engine cannot tell a setup not run yet from an address the service lost). Once the code has expired, that report still waits through the collect window, but it does not reprint the code or the connect link, and the message is `Waiting for a setup already started on the connect page. The setup link has expired, so it cannot be opened again. If you already approved it there, your bot will connect.` After the collect window it becomes `SETUP_EXPIRED`.
- **Collecting.** The engine asks the connect service for the address (`CollectAddress`, signed with its engine key) every 15 seconds while it waits for an address or is `DATABASE_UNREACHABLE_FROM_BOT`, for the code's life plus the connect service's 30-minute hold (40 minutes after the code was made), and at once on `status` ([The reach check](connect.md#the-reach-check)). For an address in phase `PREVIEW` (the person has not approved yet; any phase but `SET_UP` counts as one) it only checks it, probes it and reports whether it reached it (`ReportReach`), shows nothing of it in `status` or the next steps, and keeps collecting: the same address collected again is reported again from its probe, without a new one; an address it reached is not probed again while it stays the same, and one it did not reach is probed again 5 minutes after its probe (such a probe got no SCRAM exchange, so it leaves no failed login on the server). On `RATE_LIMITED` it waits `retryAfterSeconds`; on `HANDOFF_UNKNOWN` it keeps waiting; on `CLOCK_SKEW` `status` reports the problem `CLOCK_SKEW` (the engine's clock is more than 5 minutes off; fix it) and the engine keeps trying. A collected address that the engine has not yet used is kept in memory only; collecting again returns the same address, so an engine that stopped in between collects again. Once a probe of a `SET_UP` address passed (below), the engine stops collecting, so the database it asks the person about cannot change under the question; it collects again only after a restart, which asks again. It drops a collected address as soon as `engine.json` no longer records that pending setup (after `--forget` or a new code; it reads the config on every call and heartbeat). `basalt status` while the engine is down collects once, as the engine would, only in same-user mode and never as root, where the CLI runs as the engine's user and reads its key; it never reads `.secret` and never confirms. It shares the engine's probe cache (`connect-probe.json` in the state directory, `0600`: a hash of the address, never the address, the IP, the time, the result and the `RATE_LIMITED` wait), so a reached `PREVIEW` address is probed once whichever process collects it; it never probes a `SET_UP` address, which waits for the engine (`ENGINE_UNREACHABLE` comes first) unless a passed `PREVIEW` probe of it may be reused, and then shows `CONFIRM_DATABASE` for the engine to ask. In service mode `basalt status`, and the shim in every mode, report the pending setup from `engine.json` without collecting, and `ENGINE_UNREACHABLE` says the engine must be running.
- **An engine started as root.** An engine started as root never collects: root trusts nothing the agent's OS user could redirect, and a YES writes that user's credential. It serves the waiting agent degraded, `status` reporting the problem `ENGINE_AS_ROOT` (restart the engine as the engine's user, the owner of its state directory), touches none of that agent's files, and serves its other agents as usual.
- **Checking the address itself.** The engine trusts the service's address no further than its shape. It accepts only a host name of letters, digits, `.` and `-` (at most 253 characters), a port from 1 to 65535, a database name of `[A-Za-z0-9_.-]` up to 63 characters, and a Supabase ref of 20 lowercase letters and digits, given only with a host that names that project (`db.<ref>.supabase.co`) or Supabase's pooler (`*.pooler.supabase.com`, where the agent logs in as `<role>.<ref>`), since the ref is what the person is asked about; anything else is the problem `ADDRESS_INVALID` and nothing of it is shown, since whoever ran the setup chose it and it would land in the agent's context. It then applies the rules of `--database-url` (step 1) to the connection string it would log in with: the database that string names, read as init reads it, must be the address itself, so a Supabase project's own host (`db.<ref>.supabase.co`) comes with its ref. It resolves the host once, uses only global unicast addresses with the same refused ranges as [Where the runner connects](connect.md#where-the-runner-connects) (a refused address is also `ADDRESS_INVALID`), and connects to that address with the host name kept for TLS. It ignores any TLS mode from the service and requires `sslmode=verify-full`.
- **The probe, with a wrong password.** A server that holds the agent's verifier recovers its `ClientKey` from one real login ([The setup code](#the-setup-code), `verifier`), and the database the engine was handed may be someone else's. So after collecting, the engine only probes, as init does in step 2: logins bound to fail, with a random password, that prove the server is reachable and its certificate verifies for the host name (against the system's authorities, and the roots of the trust profile that matches the host: [Trust profiles](trust.md#trust-profiles)), and whether channel binding works. It never sends the agent's real SCRAM proof before the person confirmed the database. The probe of a `SET_UP` address reuses a passed `PREVIEW` probe only for the same address and the same resolved IP address within 5 minutes, so one flow leaves at most two probes' failed logins in the server's log. When no address of the server answers, `status` reports `DATABASE_UNREACHABLE_FROM_BOT`, naming the database, with the fix in its message: for Supabase, paste the pooler connection string on the page; otherwise allow the bot's machine in the database's firewall. The setup already ran, so the person runs the same link again with a string the bot can reach ([The address hand-off](connect.md#the-address-hand-off), running again), or opens the firewall; the engine keeps collecting, and probes again when the address changes, on every `status` and at the heartbeat.
- **Confirming the database.** After a probe that passed, `setup.state` is `CONFIRM_DATABASE` and `setup.database` names the database. `status` reports the problem `CONFIRM_DATABASE`: the agent asks the person `The setup points me at <Supabase project <ref>, database <db> | <host>:<port>, database <db>>. Is that your database?` and calls [`confirm_database`](mcp-tools.md#mcp-tools) with their answer and the database it named; a `setupId` or database other than the one waiting is refused, so an answer never confirms a database the person was not asked about. Every other tool answers `UNAVAILABLE` reason `DATABASE_NOT_CONFIRMED` until then. `confirm_database` called in any other state answers `INVALID_ARGUMENT`. The steps are A `ASK_PERSON`, A `END_TURN`, then A `CALL_TOOL` of `confirm_database` once the person answered: the engine fills in `setupId` and `database`, never `answer`, which the agent sets from the person's words. The engine never logs in to, or serves, a database the person did not confirm.
  - **Yes.** The engine writes the credential file as init does in step 2 (the role, or `<role>.<ref>` through Supabase's pooler, the address, `sslmode=verify-full`, and `channel_binding=require` when the probe showed it works), under the same locks and ownership rules, removes `.secret`, clears `awaitingAddress`, logs in, and looks for its `setupId` as in [On the engine](#on-the-engine). Found: `DONE`. Not found: the problem `SETUP_NOT_FOUND`, naming the database, and the tools answer `UNAVAILABLE` reason `SETUP_PENDING`. A first login that fails is the usual `status` problem for it (`CREDENTIAL_REJECTED`, `DATABASE_UNREACHABLE`), as for any agent with a credential file.
  - **No.** The engine deletes `.secret` and the collected address, having never logged in there, and replaces `awaitingAddress` with `"refused": true` in the pending `setup` of `engine.json`. While `refused` is set, the engine, and the shim when the engine is down, report `setup.state` `REFUSED` and the problem `DATABASE_REFUSED`, never collect, and never try to log in; the tools answer `UNAVAILABLE` reason `SETUP_PENDING`. The next `basalt init --remote` sees `refused` and makes a [recovery code](#connect-only-setup-codes).

### Controls

What stops a setup code being used against the person (design section 10):

- **Another agent's role.** `INSTALL` never touches an existing role (`ROLE_EXISTS`, and `CREATE ROLE` in Postgres); a code that sets an existing role's password says so in the summary, naming the agent and role.
- **Old or forged-time codes.** Expiry is refused on open and when confirming the code, by the person's clock and by the connect service (no skew: a code is expired from `expiresAt` on). A `setupId` in the future and an `expiresAt` more than 10 minutes plus 5 minutes of clock skew ahead are refused by the person's clock, the connect service and the database; single use and order are enforced by `record_setup`.
- **A substitute code** posted in the chat by someone else, with their own verifier: the fingerprint shown on the person's computer must match the one their agent reports (`status`, `personMessage`).
- **Wrong database**: target mismatch is refused (CO-17). Planned: not for a connect-only code, which has no target; there the page names the pasted database before approval, the connect service refuses a second database while it holds the first (`RUN_ELSEWHERE`), and the engine logs in only after the person confirmed the database it collected ([On the engine](#on-the-engine)). **Wrong prefix**: refused (`PREFIX_MISMATCH`).
- **The admin credential** is used only on the person's computer (CO-9); the SQL comes from the person's own `basalt` binary, never from the code. Planned: with the [connect link](connect.md#connect) the person chooses instead to hand it, for one setup, to the hosted connect service, whose SQL comes from the same public setup package at the engine version it pins, plus the grants of the tables the person left ticked and the column labels they set ([Tables on the connect page](connect.md#tables-on-the-connect-page), [Column labels on the connect page](connect.md#column-labels-on-the-connect-page)); [What the connect service sees](connect.md#what-the-connect-service-sees) says what that trusts. The laptop command is the way that needs no hosted service for every code with `target`; a connect-only code needs the connect service, and the person who wants no hosted service has the bot make a code with `--database-url` instead.
- **Someone else has the link** of a connect-only code (planned): whoever runs it first, with any database they own, sends the bot there. The engine sends no real login there before the person confirms, so they learn nothing that logs in as the agent elsewhere, and the person, who did not paste that database, says no. The confirmation stops a leaked log or a forwarded link, not someone in the same chat: a member of a group chat with the bot sees the link and can also answer yes. In a group chat the setup is only as safe as its members. Planned: before anyone approves, the bot also probes, without logging in, the address of any database pasted on the page, and that server sees the bot's outbound address; someone else with the link can cause that, and can make the person's reach check read "couldn't check" ([The reach check](connect.md#the-reach-check)).
- **An agent running `basalt`** with the admin credential: refused under an agent marker ([Agents and the admin credential](#agents-and-the-admin-credential)), within the limit stated there.
