## The person socket

Service mode only (owner decisions SM-1 to SM-3). With `"mode": "SERVICE"` the engine listens on one more Unix socket, `person.sock` in the socket directory (`/run/basalt/person.sock` on Linux, `/Library/Application Support/Basalt/run/person.sock` on macOS). It serves the person's `basalt log`, `approve`, `revert`, `passkey list`, `passkey check`, `status` and `upgrade`, which cannot read the engine's files in service mode. The engine runs each request with the named agent's own credential and returns rows and prepared text; no response carries the credential, its file name or the config's contents. It serves none of the MCP tools. `person` is reserved: no agent may be named `person`.

- **Access.** The socket file is mode `0666`, like the agent sockets; the socket directory is `0755` and owned by the engine's OS user, so nobody else can replace it. The only access control is the peer uid (`SO_PEERCRED` on Linux, `LOCAL_PEERCRED` on macOS): the engine admits a connection only when the peer's uid is in `personUids`, checked on every connection before a byte is read. Every other uid is refused, an agent's, root's and the engine's own user included; the engine drops `0` and its own uid from the allowlist when it loads it. An empty or missing `personUids` admits nobody. **Agent scope (SM-4).** When the admitted peer's uid is also the `osUser` of one or more agents, every request is scoped to those agents: a request naming any other agent, served or not, is refused with `AGENT_NOT_ALLOWED` before any ledger is read. A peer that is no agent's `osUser` is the person and may name every agent. A connection whose peer credentials cannot be read is closed.
- **Framing.** One request per connection, newline-delimited JSON, UTF-8. After the peer check the engine writes one greeting line: `{"ok":true,"version":1}` when it admits the peer, else `{"ok":false,"version":1,"error":{"code":"UID_NOT_ALLOWED","message":"..."}}` and it closes the connection without reading. The client then writes one request line `{"method","agent","params"}` and reads one response line, `{"result":...}` or `{"error":{"code","message"}}`, and the engine closes the connection. A request over 256 KiB, or one not complete within 10 seconds of the greeting, is refused with `INVALID_ARGUMENT` and the connection closed. Unknown keys in a request or its `params` are refused (`INVALID_ARGUMENT`). The engine serves at most 16 person connections at a time; the next waits in the listen queue.
- **Methods.** `params` and `result` are camelCase JSON as in [Wire format](../CONTRACT.md#wire-format); ids are UUID text, times RFC 3339 UTC, byte strings base64url without padding. Each is the agent-credential call the same-user CLI makes, and nothing more:

The `PLUGIN_*` methods ([Plugin approval in service mode](plugins-approval-service-mode.md#plugin-approval-in-service-mode), which sets out their params, results, limits and errors; schemas in [`person.schema.json`](../api/plugin/approval/person.schema.json)) name no top-level `agent` (a request with one is `INVALID_ARGUMENT`): the agents are in `params`, and when the admitted uid is also agents' `osUser` the methods are scoped to those agents (SM-4), refused with `AGENT_NOT_ALLOWED` otherwise. An agent's own OS user that is not the person's is not in `personUids` and never reaches them. An engine whose state directory cannot hold engine-kept entries (not a directory its OS user owns, writable by no one else) answers them `UNKNOWN_METHOD` and logs why.

`STATUS`, `TARGET` and `AGENTS` (added with `basalt status` and `basalt upgrade`) answer while the guard is missing or outdated: unlike every other method they are not refused by the guard check, since they are how the person finds and fixes that.

`assertion` is `{ "credentialId", "authenticatorData", "clientDataJson", "signature" }`, the passkey assertion of the approval or revert code. `scope` is `CHANGE`, `RUN` or `TASK`. `runs` and `tables` (revert scope) are the scope filters of `basalt revert --runs` and `--tables`, `null` or absent for all; the engine builds the descriptor with `agents` = `[the agent's role]`, as for the MCP tools. `RESCOPE_REVERT` keeps the revert's scope and id and calls `rescope_revert` with no proof or token, so it never widens; `REJECT_REVERT` calls `reject_revert` with no token. A `change` and a `rowChange` carry the fields of [the change record](change-record.md#the-change-record) the CLI prints. `SUBMIT_APPROVAL` and `APPLY_REVERT` are relays: Postgres verifies the passkey signature, as for the same-user CLI, and the socket gives the person no power the agent's credential plus their passkey does not.
- **Errors.** For the `PLUGIN_*` methods only: `PLUGIN_REFUSED`, with a `reason` beside `code` and `message` ([Plugin approval in service mode](plugins-approval-service-mode.md#plugin-approval-in-service-mode)). `error.code` is one of `UID_NOT_ALLOWED` (greeting only), `UNKNOWN_AGENT` (the engine serves no agent of that name), `AGENT_NOT_ALLOWED` (the peer is an agent's OS user and named another agent, or a `PLUGIN_*` request reaches an entry or agent outside its scope; `message` names the fix, a separate `--os-user`), `UNKNOWN_METHOD`, `INVALID_ARGUMENT`, `NOT_FOUND` (`FIND_APPROVAL`, `FIND_REVERT`: not this agent's), `REFUSED` (Postgres refused the call, and `message` is its message and detail, as the same-user CLI prints them; or the engine refused it before reaching the database because the guard is outdated or missing or the database is down, and `message` is the agent's message for that refusal, with the command that fixes it, such as `basalt upgrade` or `basalt init`) and `INTERNAL` (`message` is generic; the engine logs the cause). The CLI prints `message` the way it prints the same error in same-user mode.
