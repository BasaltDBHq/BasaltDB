## CLI

`basalt init`, `basalt log --run`, `basalt approve`, `basalt revert` (first release), plus `basalt version`, from M4.1 `basalt passkey`, from M4 `basalt status`, `basalt upgrade` and `basalt access`, from M5.1 `basalt classify`, `basalt portal verify`, `basalt plugin` ([Plugins](plugins.md#plugins)) and `basalt trust` ([Trust profiles](setup-from-laptop.md#trust-profiles)). Machine output with `--json` uses the wire format above. Paged output prints the next cursor on **stderr**. Exit codes: `0` ok, `1` error, `2` usage. Flag values a person types are lowercase kebab-case with an explicit default (`--agent-rls=ask|all-rows|none`), an input spelling only: anything stored, sent or written to the ledger uses the SCREAMING_SNAKE_CASE enum it maps to.

- `basalt init --agent NAME [--write schema.table,…] [--read schema.table,…]`: prints a short summary of the setup SQL (the full SQL, agent password redacted, is printed with `--show-sql`), asks to confirm unless `--yes`, installs or upgrades `basalt_meta`, creates the agent role (an existing role keeps its password unless `--rotate-password`; the SQL sends Postgres only the password's SCRAM-SHA-256 verifier, computed by init, never the password, so a server log of the statement cannot reveal it; an existing role is taken over only when it is a plain agent, see below), attaches the guard (with the guard's row-level security policy on tables that have RLS enabled), registers the passkey, then sets up the engine. Before that it finds the agent's tables where row-level security hides every row from the agent role and, with `--agent-rls=ask` (the default; the values are `ask`, `all-rows`, `none`, or a list) asks which of those tables the agent may see all rows of; tables without RLS are never asked about. **At a terminal** it shows a checklist grouped by schema with every table checked, its row count beside it, under the header `Row-level security hides every row of these tables from <name>.` / `Checked tables get a policy so <name> can see all rows.` / `Space toggles, a toggles a whole schema, → and ← open and close one, Enter confirms.` / a line naming `--agent-rls`, and the summary line `N of M checked · Enter to confirm`. Arrows move; `→` and `←` open and close a schema; Space toggles the table (on a schema row, the schema); `a` toggles the whole schema under the cursor; Enter confirms; Ctrl-C ends init with nothing changed. The terminal is put back on every way out. A checked table gets the agent policy ([Row-level security policies](basalt-meta.md#row-level-security-policies)) in the SQL. **Without a terminal** (answers piped in) and without `--yes` or `--dry-run`, init prints the same tables grouped by schema on stderr (`<schema> (<n> tables, <m> rows)`, then `<schema.table>  <n> rows` per table) and reads ONE line from stdin: `all`, `none`, or the list syntax below; an empty line or the end of input is `all` (everything checked, as at a terminal); anything else is a usage error (exit `2`) before anything is written, which names the `--agent-rls` form. **The list form** `--agent-rls=us.*,global.user_router` is comma-separated `schema.table` entries and `schema.*` for a whole schema; the listed tables among those RLS hides get the policy, the others none; an entry that is none of the agent's `--write`/`--read` tables is a usage error (exit `2`) naming it (a name of its own table that is no longer hidden, as on a re-run, is accepted), before anything is written. A list applies with `--yes` and `--dry-run` too. `--agent-rls=all-rows` adds the policy for every such table without asking (with `--yes` or `--dry-run`, `ask` answers `all-rows`, and init prints `basalt: <agent> can see all rows of <tables> (row-level security hid them); pass --agent-rls=none to skip this, or --agent-rls=schema.table,... to pick tables` on stderr; the dry run's SQL includes the policies); `--agent-rls=none` skips the question. **Order of piped answers:** the admin connection string (only when `BASALT_ADMIN_DATABASE_URL` is unset), then this line, then the `Run this SQL as <user>? [y/N]` answer; a piped init still stops with the usage error that names `--yes` and `--no-service` when neither is given, before any line is read. Example a script can copy: `printf 'us.*,global.user_router\ny\n' | BASALT_ADMIN_DATABASE_URL=postgres://... basalt init --agent NAME --write us.orders --no-service`. After installing, init warns for each agent table where RLS still hides every row (`basalt: warning: row-level security is on for ... and no policy lets <role> see rows; the agent will read 0 rows. ...`); `basalt log` and the engine log warn the same. At a terminal it asks once `Install the engine as a background service? ... [Y/n]` (`--yes` answers yes, `--no-service` no). Without a terminal and without either flag (answers piped in, for example), init stops before anything is written with a usage error (exit `2`) that names `--yes` and `--no-service`: it never falls back to same-user mode on its own. Yes: one `sudo basalt service install --config ... --user ... --agent NAME --os-user ... --credential-stdin` (the agent's connection string on stdin, never in arguments) creates the engine's OS user, writes the engine config (agent `name`, `osUser` and `store`: its `kind`, `POSTGRES`, and the `credentialFile` inside it) and the `0600` credential file (`<config dir>/agents/NAME.url`) owned by that user in the service's system directories, installs and starts (or restarts) the unit. Before any step it refuses a basalt binary that anyone but root could change (the file and every directory above it must be root-owned and not writable by group or others), and it reaches every directory it writes in from `/` without following a symlink anyone but root controls, refusing a directory on the way owned by anyone but root or the engine's user or writable by group or others, and an existing directory owned by anyone else; init then checks the engine answers MCP `initialize` on the agent's socket, retrying for up to 20 seconds while the service manager starts or restarts it (init has already closed the page server it ran for the passkey registration, so the engine's pages port is free), and when it never answers, names the last error line of the engine's log it can read (`/Library/Logs/Basalt/engine.log` on macOS, the unit's journal on Linux) with the log's location; it then prints the `basalt mcp --agent NAME` line. No, or any of `--config`, `--socket-dir`, `--credential-file` given: init writes the config and credential itself (under the person's config directory when the paths are the system defaults) and prints the one `basalt engine --config ...` command. With the `claude` CLI on `PATH`, at a terminal, it offers `claude mcp add --scope local basalt-NAME -- basalt mcp --agent NAME` and runs it only on yes. Every `basalt mcp` line init prints or offers starts with the absolute, link-resolved path of the running binary in place of `basalt`, and carries `--socket-dir <dir>` when the socket directory is not the default and `--config <absolute path>` when `basalt mcp`, given no `--config`, would not find the config there ([The per-user config](#cli)): a config other than the system default and other than the per-user one init leaves in the user's config directory. `--scope local` is always passed, and init prints `basalt: the server basalt-NAME is registered for this project directory only (--scope local); sessions in other projects do not see it`: one MCP server serves one agent and so one database, and the registration decides which database a session reaches. [MCP clients](../docs/mcp-clients.md) shows the same per-project setup for other clients. The admin connection string comes from `BASALT_ADMIN_DATABASE_URL` or a hidden prompt and is never written anywhere. It must be a `postgres://` or `postgresql://` URL; a keyword/value string (`host=... user=...`), or a URL that does not parse (a Unix socket directory goes in `?host=`, not percent-encoded in the host), is refused before init connects. The agent's connection string is built from it: its scheme, hosts, ports and database, the agent's user (`<prefix>_agent_<name>`, or `<prefix>_agent_<name>.<ref>` through Supabase's pooler) and password, and only these parameters: `host`, `port`, `dbname`, `sslmode`, `sslrootcert`, `sslcrl`, `sslcertmode`, `sslnegotiation`, `sslsni`, `channel_binding`, `require_auth`, `target_session_attrs`, `connect_timeout`, `application_name`, `min_protocol_version`, `max_protocol_version` and `default_query_exec_mode`. Every other parameter is dropped, among them `user`, `password`, `passfile`, `service` and `servicefile`, and the admin's TLS client identity `sslcert`, `sslkey` and `sslpassword` (CO-9). `sslrootcert` and `sslcrl` are file paths: after `service install` the engine's OS user must be able to read them. `--dry-run` prints the SQL and the engine setup (the sudo command and its steps) and runs nothing. Before the admin connection, for a host no profile covers whose certificate verifies against no authority this machine trusts, init reads the chain with the TLS handshake alone and offers to pin its top for that host only (`--trust-root SHA256` answers without a terminal; [Pinning on first use](setup-from-laptop.md#pinning-on-first-use)); on yes the agent's connection string gets `sslmode=verify-full`, the pin is written to the engine's `trust.d` (with one `sudo basalt trust pin ... --trust-root` for a service engine) and recorded with `record_trust_pin`. `--dry-run` offers no pin. M5.1: after installing, init prints `basalt: N columns the agent can read are not classified yet; run basalt classify` when there are any ([PII classification](pii-classification.md#engine-basalt-log-and-basalt-init)).
- **Plain agent roles only.** Whenever init gives a role `<prefix>_agent_<name>` that already exists `LOGIN`, a password or `<prefix>_agents` (keeping its password, `--rotate-password`, or an `AGENT` setup code), the same SQL first refuses, with `BS008` (`LEDGER_INPUT_INVALID`) and nothing changed, a role that is not a plain agent: one that has `SUPERUSER`, `CREATEROLE`, `CREATEDB`, `REPLICATION` or `BYPASSRLS`; that is a member (directly or not, inheriting or not) of any role other than `<prefix>_agents` (an allow-list: predefined roles such as `pg_read_all_data`, `pg_monitor` or `pg_signal_backend`, `<prefix>_guard`, and any other group are all refused); that owns, or is a member of the owner of, the database or any object in it (`pg_shdepend`; the owner of a function, view or default a guarded write runs could replace it and run code as the next writer); or that holds a direct privilege on anything in `basalt_meta`, or `TRUNCATE`, `TRIGGER`, `REFERENCES` or `MAINTAIN` on an agent or guarded table. It then resets the role's own settings (`ALTER ROLE ... RESET ALL`, everywhere and `IN DATABASE` this one) before setting `statement_timeout` and `CONNECTION LIMIT 8`, since a setting such as `session_replication_role = replica` would keep the guard's triggers from firing; a setting the admin may not reset (one only a superuser may set, when the admin is not one) is refused. An `AGENT` setup code also refuses a role outside `<prefix>_agents`.
- `basalt init --demo` (the docs quickstart): `init` for a sample database, in one command. It is the same init (admin connection string, the setup SQL shown and confirmed, guard, passkey, engine), with these differences.
  - **What it creates.** The schema `basalt_demo` with `leads` (30 rows) and `lead_notes` (20 rows, two each on leads 1 to 10, `ON DELETE CASCADE` from `leads`), with row-level security off, from SQL embedded in the binary. It creates the agent `demo_bot` (`--agent` renames it) with `--write basalt_demo.leads,basalt_demo.lead_notes` and nothing else; `--write` and `--read` with `--demo` are a usage error (exit `2`). `USAGE` on `basalt_demo` and the agent's grants are the only access it gets; no other schema gets a table, a change or a grant. Apart from `basalt_demo`, init adds only what it always adds: `basalt_meta`, the roles and the engine setup. The `--agent-rls` check finds nothing to ask about, because row-level security is off on the demo tables.
  - **One confirmation, nothing kept before yes.** A short summary of the sample-data SQL and the setup SQL is printed (the full SQL, passwords redacted, with `--show-sql`), and `Run this SQL as <user>?` is asked once for both. To plan the guard init needs the sample tables to exist, so it creates them in a transaction on the admin connection, plans, and rolls that transaction back before it prints the summary and asks: nothing is committed, and nothing is held open, while the person decides. On yes, it creates the sample data again and applies the install in one fresh transaction that commits once, so a change made meanwhile is caught by the check that every agent-writable table is guarded. `--dry-run` also needs the admin role to be allowed to create in the database, because it plans the same way. `--yes`, `--skip-passkey`, `--no-service` and the other init flags work as for init.
  - **Safe to run again.** When `basalt_demo.leads` and `basalt_demo.lead_notes` both exist, init leaves their rows as they are (it never reseeds over a person's edits), prints `basalt: sample schema basalt_demo already exists; its rows are left as they are`, and installs and guards as usual. When only one exists, init creates the other with its rows, its index and row-level security off, and does not touch the one that exists (no row, index or row-level security change); when the existing `leads` does not have the ids or the columns `lead_notes` needs, the statement fails with the database's error and the transaction rolls back. When a guarded table of the demo is missing from an init run without `--demo` (`--write basalt_demo.leads`), the error suggests `basalt init --demo`. A re-run keeps the agent's password as init does.
  - **The comment.** Init sets the schema comment `BasaltDB demo data` only when it creates the schema in that run, never on a `basalt_demo` that already exists (one from `examples/demo/seed.sql` or made by hand).
  - **Output.** After the usual `basalt: guard installed; agent role <role>` and passkey lines, one line: `basalt: demo ready: leads 30, lead_notes 20` (the counts are read from the tables, so a re-run shows the current ones).
  - **Saved flags.** `--demo` is a one-shot flag and is never saved: `initArgs` in `engine.json` holds `--agent` and `--write` like any init. Running init again later does not reseed, and after `basalt_demo` is gone it fails on the saved `--write` (the table is missing) until `--demo` is given again.
  - **Removal.** `basalt uninstall` removes `basalt_demo` before it drops `basalt_meta` and the roles, in the same transaction, only when the schema carries the comment `BasaltDB demo data`. It runs `DROP TABLE basalt_demo.lead_notes`, `DROP TABLE basalt_demo.leads` and `DROP SCHEMA basalt_demo`, never with `CASCADE`, so it cannot drop a person's view, foreign key or table that depends on or sits in the schema. When one of those statements fails (something outside depends on the tables, or the schema holds other objects), uninstall skips the demo removal, rolling back only those three statements, prints `basalt: demo schema basalt_demo kept: <the database's message and detail>`, and still removes everything else. A `basalt_demo` without the comment is not touched. On success it prints `basalt: demo schema basalt_demo dropped`. The confirmation names the schema: `Drop basalt_meta, the ledger, every <prefix>_* role and the demo schema basalt_demo, if init --demo made it?`; `--yes` skips it.
- **Replication role default.** `basalt init`, `basalt upgrade` and a setup code read the default of `session_replication_role` a new session in the database gets: `ALTER DATABASE ... SET` first, then `ALTER ROLE ALL SET`, then the server's (`postgresql.conf`, `ALTER SYSTEM`, the command line; not read when the admin's own role settings hide it). When it is not `origin` they print, before the SQL runs, `basalt: warning: the database default of session_replication_role is <value>, not origin. ...` on stderr with the statement that fixes it (`ALTER DATABASE <db> RESET session_replication_role;`, `ALTER ROLE ALL RESET session_replication_role;`, or `ALTER SYSTEM RESET session_replication_role; SELECT pg_reload_conf();`), and go on. A warning, not a refusal: the guard's triggers fire in any mode ([Guard triggers fire under any `session_replication_role`](basalt-meta.md#guard-triggers-fire-under-any-session_replication_role)), so only foreign keys and the person's own triggers stop in agent sessions.
- `basalt log [--run ID] [--full] [--sort -id|id]`: the agent's change records, newest first (`--sort` defaults to `-id`; `id` is oldest first; any other value is a usage error), read with the agent credential (`--credential-file`, then `--agent NAME` looked up in the engine config, then `BASALT_DATABASE_URL`; a flag always wins over the environment, and `basalt approve`, `basalt revert` and `basalt passkey` pick the credential the same way). Run as root, these commands, `basalt status` and `basalt upgrade` read a credential file only when it is owned by the owner of its directory (for the config's agent, the config directory's owner; root when root owns it), and from one a user other than root owns, including one root's own `basalt init --remote` wrote and handed to that user, they take only the strings root's `basalt init --remote` takes from the owner of `agents/` (step 8 of [`basalt init --remote`](setup-from-laptop.md#basalt-init---remote-the-engines-machine); exit `1` otherwise, never echoing the string, with `run the command as that user (sudo -u <user>), or fix the file`). Text output is compact (M4.1): one line per change; with `--run`, each row it wrote below it as its key and only the columns that changed, `{"id":4} status NEW -> CONTACTED` (an insert or a delete shows the key only), keeping the `(cascaded)`, `(read at xmin:N)` and `(blind write)` markers and `values hidden` or `values pruned`. Consecutive reads (`SELECT` records) collapse into one line: how many, the rows they returned and their tables (`3 reads, 42 rows: public.leads (2), public.notes (1)`). `--full` prints whole before and after rows and every read on its own line, as before M4.1. `--json` is unchanged. Warnings on stderr: broken ledger chain, unguarded tables, no engine heartbeat for 7 days, the last `DEAD_MAN` row (the engine came back after more than 7 days of silence), and from M4.1 no active passkey, and each passkey not used to sign an approval or revert for 90 days or more (counted from registration when never used), naming its label and id with `basalt passkey remove` as the fix for a lost one. The chain is checked incrementally with `verify_chain_from` from the head this user's `basalt log` last verified (kept under the user cache directory, per database and role, with the guard install it was verified on, and a pin of an earlier install is reported with `record_pin_set_aside` and set aside, never silently, or, when it still verifies there, moved to the new install with a warning on stderr); it prints the [reinstall notice](basalt-meta-installs.md#reinstalls-on-the-record) on stderr for every reinstall the ledger records; `--full-check` runs `verify_chain()` from the anchor instead. M5.1: it also prints the PII line `PII: N columns classified, M unclassified; dictionary of K values, last scan <time>` on stderr, and warns about unclassified columns and columns that need a review ([PII classification](pii-classification.md#engine-basalt-log-and-basalt-init)). After the PII line it prints, on stderr, the `Plugins:` line of [In the ledger](plugins-ledger.md#in-the-ledger) when the agent's ledger has any plugin event.
- `basalt access --agent NAME [--config PATH] [--json]` (M4): read-only. Lists for one agent the tables it can read, the tables it can write, and the tables in user schemas it cannot read, each with the `basalt init` flag that would grant it (`--read schema.table` or `--write schema.table`, the same rebuild init does). Names print as Postgres prints them (`quote_ident`), as `describe` names them; a name that needs quotes is marked `grant by hand`. Each printed command is the saved flags plus one table, so two of them do not stack; under the not-granted list the output says to list several tables in one command or to run `basalt access` again after each grant. User schemas exclude `pg_catalog`, `information_schema`, `pg_toast*`, `pg_temp*`, `basalt_meta` and the schemas of installed extensions; Supabase's own schemas count like any other and are listed under their schema. Without a service it reads with the agent credential, as `basalt log` does; in service mode it uses the person socket method `LIST_ACCESS`. It prints names the `describe` tool only counts, so it is the person's command: the `describe` next steps name it as a `PERSON` step and never as an `AGENT` `RUN_COMMAND`, even on an agent-operated engine.
- `basalt crash list | show <id> | report <id>`: the crash reports basalt saved on this machine, and the GitHub issue link for one ([Crash reports](crash-reports.md#crash-reports)). Nothing is sent. Under an agent, `report` opens and prints no link.
- `basalt portal verify [--portal-url URL] [--manifest PATH] [--json]` (vault channel VC-8, VC-22): read-only, needs no Postgres, no config and no engine. Fetches every file the binary embeds (`web.Files`: the page directories, the portal's home page `index.html` and not-found page `404.html`, `lib/*.js`, `style.css`, the fonts and their license) from the portal origin and compares the bytes (SHA-256); a page `<dir>/index.html` is fetched at `/<dir>/` and `index.html` at `/`. `404.html` is fetched at a path no file or rewrite answers (`/basalt-portal-verify-no-such-page`) and must come back with status 404 and its bytes: a 200 there is `DIFFERS` (the host answers unknown paths with another page), any other status `ERROR`. The list comes from the embed, so a new embedded file is checked without a code change. It also fetches each route people load a page at (`internal/engine/pages` `PageRoutes`: `/approvals/<id>`, `/reverts/<id>`, `/passkeys/register`, `/passkeys/check`, `/passkeys/forget`, with a fixed sample id; and the portal's own `PortalRoutes`: `/engines`, `/engines/add`, `/connect`), which the portal's `_redirects` rewrites to the page files, and compares each with its page file: a rewrite to another page is seen. One line per path, `STATUS  path`, then a summary: `OK`; `DIFFERS` (served bytes differ); `MISSING` (not served); `HEADER` (right bytes, but the response's `Content-Security-Policy` differs from the engine's `internal/websec` policy or is absent, or a `.js` file is not `text/javascript`; the [connect page](connect.md#the-connect-page), at `/connect/` and `/connect`, must carry its own policy instead and `Cache-Control: no-store`; the detail names the header); `ERROR` (could not be checked: network, an HTTP status other than 200 or 404 for an embedded file or a route, a redirect to another origin); `UNEXPECTED` (a path the portal build never publishes answers 200: `embed.go`, `embed_test.go`, `lib/<name>.test.mjs` for each embedded script; a static host has no listing, so only these named paths are probed; for these probes only, 403, 404 and 410 count as not served, and any other status except 200 is `ERROR`). Redirects within the portal's origin (same scheme, host and port) are followed (at most 5), any other redirect is `ERROR` and is not followed. With `--manifest PATH` it also checks the embedded files against that release manifest, a plain `sha256  path` list as in the committed `web/portal.sha256` (sorted by path, written by `make web-sri`, not embedded and not served), and prints `release manifest (PATH)` as `OK` or `DIFFERS` with the paths that differ; without the flag there is no manifest line, since the binary would only be checking itself. `--portal-url` defaults to the compiled-in portal origin `https://portal.basaltvault.app` and takes only an `https://` origin, or an `http://` origin on a loopback host (`localhost`, `127.0.0.1`, `::1`: tests); with a path, query, credentials, any other scheme or any other `http://` host it is a usage error. A `--manifest` file that cannot be read or parsed (bad line, duplicate path) is a usage error. Exit `0` when every path and the manifest are `OK`, `1` when anything else, `2` for usage errors. `--json` prints `{ "portalUrl", "ok", "checked", "files": [{ "path", "status", "detail" }], "manifest": { "source", "status", "mismatches" } }` (`manifest` only with `--manifest`), [`portal-verify-result.schema.json`](../api/mcp/portal/portal-verify-result.schema.json). **Daily check.** The engine runs the same comparison (the embedded files, the routes, the headers; no `--manifest`) against the portal in its config: at start and then every 24 hours, only when `pagesUrl` is `https://portal.basaltvault.app` (with local pages it runs nothing). It reads public pages and sends nothing about the engine. It keeps the last result in memory and in `<stateDir>/portal-check.json` (`0600`; the portal checked, the time, the paths with `DIFFERS`, `MISSING`, `HEADER` or `UNEXPECTED`, at most 100, and the counts). When that result has any such path, `status` (the tool, and `basalt status`, which reads the file when the engine runs as the person) reports the problem `PORTAL_MISMATCH` (`WARNING`, [Next steps](next-steps.md#next-steps)): `message` names the counts and the day of the check, and the one step is a `PERSON` `RUN_COMMAND` `basalt portal verify` to see the files. `ERROR` paths and a check that could not run are only logged and give no problem. The warning does not stop any tool. **Releases.** Each release attaches `portal.sha256`, the `web/portal.sha256` of the tagged commit, for `--manifest`. Limit: it catches a portal that serves different files to everyone, not one that serves the checker something else than a browser (it sends a plain client's request), not a page served to one person only, and not a compromise of this binary's own download.
- `basalt trust list [--config PATH] [--json]`, `basalt trust add --name N --match SUFFIX[,...] --ca FILE [--config PATH]`, `basalt trust pin --host H [--port P] [--trust-root SHA256] [--config PATH]`, `basalt trust remove --name N [--config PATH]`, `basalt trust disable --name N [--config PATH]` ([Trust profiles](setup-from-laptop.md#trust-profiles)): the trust profiles that decide which roots verify a database's certificate. Each reads and writes `trust.d` next to the config (`--config`, relative or absolute; without it the per-user config `basalt init` left when nothing is installed system-wide, else the platform default), with the rules the engine loads it with, and needs no Postgres and no engine. **list** prints every profile, the operator's first: its name, origin (`built-in`, or `operator` for a file in `trust.d`), state (`active`; `replaced` for a built-in an operator profile of the same name replaces; `disabled`), match and each root's subject, SHA-256 fingerprint (of the certificate's DER, uppercase hex pairs with colons) and expiry date (a profile of more than 4 roots, such as the RDS bundle, prints the count and the first expiry; `--json` lists each); then each refused `trust.d` file with why; then, for each agent of the config whose credential this user can read, its database host and what verifies it (a profile, the connection string's `sslrootcert`, the system's authorities alone, or nothing when its `sslmode` is below `verify-full`). The list is bounded: at most 64 operator profiles load. `--json` prints `{ "trustDir", "profiles": [{ "name", "origin": "BUILT_IN"|"OPERATOR", "state": "ACTIVE"|"REPLACED"|"DISABLED", "match", "verify", "roots": [{ "file", "subject", "sha256", "notAfter" }] }], "refused": [{ "file", "reason" }], "agents": [{ "agent", "host", "applies": "PROFILE"|"SSLROOTCERT"|"SYSTEM"|"NOT_VERIFIED", "profile", "unknown" }] }`. **add** copies the PEM file `--ca` into `trust.d` as `<name>.pem` and writes `<name>.json` pinning its SHA-256, then prints the match and each root's subject, fingerprint and expiry. `--match` is comma-separated: a domain (`db.example.com` covers the hosts below it, on a label boundary) or `=host` (that one host, a name or an address). It refuses, writing nothing: a certificate that is not a CA (`basicConstraints CA:true`), a file that is not only PEM certificates or is over 1 MiB, an empty match, a wildcard, a match entry that is a public suffix on its own (a single label such as `com`, a country's second level such as `co.uk`, or a cloud provider's shared zone such as `amazonaws.com`), a name that is not lowercase letters, digits and dashes (up to 63), and a name `trust.d` already holds, or whose `<name>.pem` it holds (remove it first). A built-in's name replaces that built-in. **add** and **remove** are refused under an agent marker, when the engine is `operatedBy: AGENT`, and when the config exists and cannot be read: an agent never adds a root, and removing a profile can bring a built-in's roots back. **remove** deletes `<name>.json`, then the roots files it names that no other profile names (all of them are kept when another profile file cannot be read); for a built-in's name that turns the built-in on again; a built-in itself cannot be removed. **pin** pins the certificate authority host `H` (port `P`, default `5432`) presents, for that host only ([Pinning on first use](setup-from-laptop.md#pinning-on-first-use)): it reads the chain with the TLS handshake alone, shows the top certificate's subject, SHA-256 and expiry, and on yes (default no; without a terminal `--trust-root` must match exactly, else exit `2` naming the flag and the fingerprint seen) writes the `pin-<host>` profile. A host already pinned shows the pinned certificate first, and yes replaces it. A host whose certificate verifies already, or that a profile covers, needs no pin (exit `0`). Refused under an agent marker and when the engine is `operatedBy: AGENT`. **disable** writes `<name>.json` with `"disabled": true` for a built-in only, and refuses when `trust.d` holds that name already. Each write holds the config lock (`<config>.lock`), makes `trust.d` (`0700`) when it is missing, and writes its files (`0644`) atomically, owned by the config directory's owner when root writes them (`sudo`, for a service engine, whose `trust.d` belongs to the engine's user). The running engine reads `trust.d` again for each new connection, so a change applies from its next connection, with no restart. Exit `0` ok, `1` refused, `2` usage.

- `basalt init` (M2) registers the person's passkey: it prints and opens a registration link, reads the pasted `basalt-passkey.1.` code, verifies it, and stores the public key with the admin credential, unless an active passkey is registered already for the origin `--passkey-origin` picks (a passkey signs only on its own origin, so an engine handed over to an agent with `--operated-by=agent` gets a portal passkey even when a local one exists, as `--setup-code` does). `--skip-passkey` defers it, `--add-passkey` registers another, `--passkey-label` names it (default `<database> · <agent> · <date>`, the date local, at most 64 bytes, the database name shortened first, so the picker tells this database's passkey from the person's others on the same site), and `--passkey-origin` picks the pages the passkey belongs to: the engine's local pages `http://localhost:<port>` (default `http://localhost:8787`, RP ID `localhost`) or the portal `https://portal.basaltvault.app` (RP ID `basaltvault.app`); any other origin is a usage error ([Page origins](page-links.md#page-origins)). Init writes it to the engine config as `pagesUrl`. M4.1: for a local origin init serves the built-in pages on that port (127.0.0.1) while it waits for the code, unless the port is taken. When init serves the pages itself, the page hands the passkey back to init and the person types a short pairing code instead of pasting the long one: the registration request carries `handBack`, a secret of 16 random bytes (base64url, [`registration-request.schema.json`](../api/mcp/approval/registration-request.schema.json)) in the link's fragment, and after the passkey is created the page posts the registration response JSON (the JSON the `basalt-passkey.1.` code carries) to `POST /api/v1/passkeys/register` on that server, with the secret in the `basalt-link-secret` header. Init checks, in order: `Origin` equal to the page origin (`403`), the secret, compared as `sha256` in constant time (`404` for a missing or wrong secret), fewer than 4 registrations kept (`429` `RATE_LIMITED`, `basalt init received more passkeys than it takes`; nothing changes, and the count is checked again before a verified one is kept), `Content-Type: application/json` (`415`), at most 16 KiB (`413`), a registration response that verifies against the request (`400`). Init reads and verifies a body without holding up other posts, and its page server bounds a whole request at 20 seconds, so a post that stalls its body blocks neither another post nor the prompt; errors are `{ "code", "message" }` as on the [Local pages](local-pages.md#local-pages). A response that verifies is kept (the same registration posted again is kept once) and init answers `200 { "status": "RECEIVED" }`; it stores nothing yet. **The threat:** the link is visible to other programs on the machine (the terminal, the browser's command line), so one running as any local user, the agent included, could post a key pair of its own first and, if init stored it, approve its own held writes. So only after the `200` the page shows the [pairing code](approvals.md#codes) of the passkey it created (`XXXX-XXXX`, 8 Crockford base32 characters from the request's challenge, the credential id and the public key) with `Type or paste this code into basalt init`, and init asks `basalt: Type or paste the code the page shows:`. Init stores only the kept registration whose pairing code the person enters (typed in any case, with or without the dash or spaces). Each other entry counts as a try: one that is not 8 Crockford characters gets `basalt: that is not the code the page shows (8 letters and digits, like K7Q2-9MX4); check the page`, one that matches no kept registration `basalt: that code doesn't match; check the page`, and one that matches more than one `basalt: that code matches more than one passkey sent to basalt init, so it cannot tell which is yours; check the page`. After 3 tries init fails with `run basalt init again` and stores nothing. A paste that cannot be read (over 64 KiB, a read error) is reported and does not use a try; after 10 such pastes init fails without a passkey. When 4 registrations are kept, init says once `basalt: basalt init received more passkeys than expected; if the page shows no pairing code, paste the long code from it`. A `basalt-passkey.1.` code pasted at the same prompt registers as without a hand-back. A closed stdin ends init without a passkey: the post alone never registers one. When the post fails because init is no longer there (no answer, or `404`), the page says `basalt init is no longer waiting; run it again` and shows no code; on any other refusal it shows the error and the long code to paste. Init adds `handBack` only to links of the pages it serves (never to the portal's, or when the port is taken), and the route exists only on init's server, never on the engine's listener.
- **Pasted codes.** Every prompt that reads a pasted code (`basalt init`'s passkey code or pairing code, `basalt approve` and `basalt revert` without a code argument, including while `--open` waits for the page, `basalt passkey check`) reads it at a terminal with canonical mode and echo off, echoing it and handling backspace itself, and restores the terminal's modes when it returns: a canonical-mode line holds only 1024 bytes on macOS (`MAX_CANON`; 4096 on Linux), and the codes are longer. Enter ends the code, Ctrl-D on an empty line ends the input, Ctrl-C stops the command; surrounding space is trimmed; a code is at most 64 KiB. Without a terminal, or on a platform where basalt does not set the terminal's modes (other than macOS and Linux), the code is one line of stdin. While `basalt approve --open`/`--show` or `basalt revert` also waits for the page, a paste that cannot be read (over 64 KiB, a read error) is reported on stderr and the wait goes on for the page.

Reads the active passkeys with the agent credential (looked up as for `basalt log`; in service mode over the person socket, `LIST_PASSKEYS`), prints the check link (`<base>/passkeys/check#1.<request>`, mode `CHECK`; `--open` opens it as for `basalt approve --open`) for the passkeys registered on the pages base (`--pages-url`, else the engine config's `pagesUrl` (in service mode the engine's, from `PAGES`), else `http://localhost:8787`) and names any registered on another origin with the `--pages-url` that checks them; when the base is local and the engine is not serving it, the CLI serves the pages there while it waits, as `basalt init` does for registration. It reads the pasted `basalt-passkey-check.1.` code, verifies each assertion in it locally against the stored public key and the check challenge, and prints each passkey as `found on this device` or `not found on this device`. For each one not found it asks `Remove <label> (<id>)? [y/N]`; yes runs the `basalt passkey remove` steps (admin connection string asked once). Nothing is written unless a removal is confirmed. A check signature authorizes nothing (see [Passkey management](passkey-management.md#passkey-management)).
- `basalt engine list [--admin] [--json]` (M4.1; [Direct transport](vault-direct-transport.md#direct-transport)): the engines recorded in the database ([Engine records](basalt-meta-installs.md#engine-records)), read through `agent_engines` with the agent credential (looked up as `basalt log` finds it outside service mode: `--agent`, `--credential-file` or `BASALT_DATABASE_URL`; an engine run as a service whose credential this user cannot read uses `--admin`), or with `--admin` through `engines` with the admin connection string (`BASALT_ADMIN_DATABASE_URL` or a hidden prompt), for the person's own computer, which has no agent credential. One line per engine: its fingerprint, address (`no address`), when recorded, and `revoked <time UTC>` when revoked; with the agent credential, the engine's own row is marked `this engine`. `--json` prints `[{ "engineId", "fingerprint", "url", "recordedAt", "revokedAt", "self" }]` (`url` and `revokedAt` null when absent, `self` false with `--admin`). Never more than 100 rows (the newest first); it has no cursor. A guard older than version 33 prints `this database records no engines (guard version <n>; basalt upgrade adds them)` and exits `0`.
- `basalt engine revoke [<engine>] [--yes]` (M4.1): revokes an engine with the admin connection string, as `basalt passkey remove` does a passkey. `<engine>` is the engine id, or a unique prefix of at least 8 characters of it or of its fingerprint (spaces ignored); without it, it lists the engines not revoked and asks which (`Which engine? Type the start of its fingerprint:`). It shows the fingerprint, address and when recorded, and asks `Revoke engine <fingerprint>? Its portal links stop working; approvals go on through long links. [y/N]` unless `--yes`. It calls `revoke_engine` (an `ENGINE_REVOKED` ledger row) and prints what the engine does next ([Direct transport](vault-direct-transport.md#direct-transport), Revocation by the person) and that each device should remove its pin (`https://portal.basaltvault.app/engines`). An unknown, ambiguous or already revoked engine is exit `1`, nothing changed. It never asks for or touches an engine config: it runs on the person's computer.
- `basalt tunnel [--address https://<host>[:<port>]] [--direct-addr <host:port>] [--config PATH]` (M4.1; [Direct transport](vault-direct-transport.md#direct-transport)): helps the person publish the engine's direct listener through their own tunnel. It prints the commands for Cloudflare Tunnel (`cloudflared tunnel create`, `route dns`, `run --url http://<directAddr>`), Tailscale Funnel (`tailscale funnel --bg http://<directAddr>`) and a Caddy reverse proxy (`reverse_proxy <directAddr>`), each forwarding to `directAddr` (`--direct-addr`, else `engine.json`, else `127.0.0.1:8787`, said on stderr when the engine does not have it yet) and each passing the public `Host` on unchanged. Without `--address` the commands use `engine.example.com`. With `--address` (checked by the [engine address grammar](vault-direct-transport.md#direct-transport); a refused one is exit `2`) the commands name that host and the command then fetches `<address>/v1/engine` with no `Origin`, no credentials and no redirect (10 seconds, at most 4 KiB), checks that `engineId` is the hash of `engineKey` and, when this machine's key file is readable, that it is this engine's, and prints the fingerprint with the next steps (`basalt init --setup-code <code> --engine-url <address>` on the person's computer; the pin page on each device). Exit `1`, with the reason, when the address does not answer, answers `400` with the body `host not allowed` (the direct listener does not record that Host: the address is not recorded yet, the tunnel does not pass the public `Host` on unchanged, or the recorded address has another port; the local pages' `host not allowed: <host>` is the wrong listener), a gateway error or Cloudflare's `530` (the tunnel is not connected to the listener), another status or a non-JSON body, an id that is not the key's hash, or another engine's key. It reads no database and no secret and writes nothing.
- `basalt init --direct-addr <host:port|off>` (also `basalt init --remote`): sets `directAddr` in `engine.json` ([Direct transport](vault-direct-transport.md#direct-transport)), with `--remote` or `--operated-by=agent` only (a usage error otherwise, and with a local `--passkey-origin`); a non-loopback address is a usage error (exit `2`). Saved in `initArgs`; a re-run without it keeps the saved value. The engine binds it at its next start.

- `basalt engine [--config PATH] [--user NAME] [--plugin-debug] [--supervise] [--started-by hand|mcp|crash]`: runs the engine in the foreground, and restarts it onto a new `basalt` binary installed at the path it was started from ([Next steps](next-steps.md#next-steps), Restart onto an upgraded binary). **`--supervise`** runs the engine as a child of a small parent that restarts it when it exits with an error: after `1s`, `2s`, `4s`, `8s`, `16s`, then `30s` between restarts (the wait starts again at `1s` after a child that stayed up at least 10 seconds), and it gives up, exit `1`, after 5 exits in a row within 10 seconds each of their start, writing `crashed 5 times within 10s; last: <error>` to its output and `{ "reason", "at", "engineSha256" }` (`at` RFC 3339 UTC; `engineSha256` the lowercase hex SHA-256 of `engine.json` at the give-up) to `last-stop.json` in the state directory, removed again once an engine, supervised or run by hand, has stayed up 10 seconds. One supervisor runs per config (a `supervise.lock` flock in the socket directory): a second one prints `another basalt engine --supervise runs for this config` and exits `0`. A child that stops with status `0` ends the supervisor with `0`; a child that fails because another engine already holds the config's engine lock ends it with `0` too (an engine started by hand beside it is never crash-looped against), and SIGTERM or SIGINT to the parent stops the child and exits `0`. The child stops when its supervisor dies, so a killed supervisor never leaves an engine nobody restarts: on Linux the kernel sends the child SIGTERM (`Pdeathsig`); on macOS the child notices its parent is gone and stops. A crash restart runs the binary at the path the supervisor was started from, resolved again at each restart; when that path is gone, the supervisor writes `the basalt binary <path> is gone` to its output and to `last-stop.json` and exits `1`, instead of looping on a missing file. The upgrade restart is the child's own exec onto the new binary, so the parent never sees it as an exit. `--supervise` runs as the engine's own user: with `--user` it is a usage error (exit `2`, `--supervise runs as the engine's own user; drop --user`). Before it takes the engine lock, a same-user engine makes its state directory, and its socket directory when every configured agent's OS user is its own, with mode `0700`: a missing one is created, one it owns with group or other permission bits (an update of a bot's computer resets folders to `0755`) is set back to `0700`, one another user owns is left as it is, and a symlink there stops it with exit `1`. A service engine's folders are its service manager's and are not changed. A socket file nothing answers on and a lock file left by a killed engine never block a start (the lock is a kernel `flock`, never read for a pid, and nothing decides by a file's age); a credential file whose mode is not `0600` is still refused, never changed. **`--started-by`** says why this engine starts: `hand` (the default), `mcp` (`basalt mcp` found the engine down) or `crash` (the supervisor restarted it); `status` reports it as `engine.startedBy`, `HAND`, `MCP` or `CRASH`; the supervisor passes its own value to its first child and `crash` to every restart; any other value is a usage error. **`--plugin-debug`** shows local plugins' stderr on the engine's own stderr; without it, it is discarded ([Plugins, Failure](plugins-runtime.md#failure)). An engine run as a service starts no local plugin: the service manager runs each one and keeps its stderr ([Service units](plugins-runtime.md#service-units)). **`--user NAME`** (containers without a service manager) makes the engine run as the OS user `NAME` before it opens the config, a credential, a socket or a port, in this order, stopping at the first failure with exit `1` and nothing read: (1) it resolves `NAME` (uid, gid, supplementary groups) and refuses a uid `0`, a gid `0` and membership of group `0`, and refuses unless it runs as root or already as `NAME` (`basalt engine --user NAME starts as root (a container entrypoint) or as NAME itself, not as uid N`); (2) it refuses its own binary when anyone but root could change it or a directory above it (the `basalt service install` check); (3) it sets the umask to `0077`; (4) started as root, it makes or takes over the socket directory and the state directory with the service's modes, owned by `NAME`, reached from `/` without following a symlink (Linux `/run/basalt` `0755` and `/var/lib/basalt` `0700`, the unit's `RuntimeDirectoryMode` and `StateDirectoryMode`; macOS `/Library/Application Support/Basalt/run` `0755` and `.../state` `0750`), then sets the supplementary groups, the gid and the uid, in that order, on every thread; (5) it sets `no_new_privs` on every thread (Linux; macOS has none, and a cgo build, which cannot set it on every thread, is refused); (6) it verifies the drop: on Linux every thread in `/proc/self/task` has all four uids and gids `NAME`'s, exactly its groups, no permitted, effective or ambient capability and `no_new_privs`; on macOS the real and effective ids and the groups; on both, `setuid(0)`, `seteuid(0)`, `setgid(0)` and `setegid(0)` must fail. It then prints `basalt engine: dropped root; running as NAME (uid U, gid G); no_new_privs set` (`already running as` when no drop was needed; no `no_new_privs` note on macOS) on stderr. A `socketDir` or `stateDir` in the config other than these defaults is not made before the drop: the engine, as `NAME`, handles it as it does without `--user`. Without systemd the unit's sandbox and memory limits do not apply: only the OS user split protects the credential. Started as root without `--user`, the engine reads its config as the root person CLI does: reached from `/` without following a symlink anyone but root controls, a regular file with one link owned by root or its directory's owner and not writable by group or others; anything else stops it with exit `1` before it starts. It then reaches each agent's files the way root's `basalt init --remote` does ([`basalt init --remote`](setup-from-laptop.md#basalt-init---remote-the-engines-machine), step 8): the credential file must be `agents/<agent>.url` next to the config (a `store.credentialFile` anywhere else stops that agent: `... as root, basalt engine uses only that path. Fix the agent's store.credentialFile in the config, or start the engine with --user`), and the config directory and `agents/` are opened once at start, from `/` without following a symlink anyone but root controls (every directory on the way owned by root or the config directory's owner, not writable by group or others); the credential file, its `.pending` and its `.lock` are then read, locked and renamed relative to `agents/`, and `engine.json` is locked, read and rewritten (when a setup is cleared) relative to the config directory, so a directory swapped for a symlink after the start redirects nothing. It reads a credential file or `.pending` that is a regular file with one link, mode `0600` or tighter, owned by root or by the owner of `agents/`, and from one the owner of `agents/` wrote it takes only what root's `basalt init --remote` takes from it (step 8: a `postgres://` or `postgresql://` URL with a password and no parameter that makes the driver read a file), else that agent stops (`... as root, basalt engine takes from it only a postgres:// or postgresql:// URL ...; start the engine with --user (as basalt service install does), or fix the file`), never echoing the string; a symlinked `.lock` is refused as a lock file that cannot be used.
- Service mode (owner decisions SM-1 to SM-3). **The person's CLI in service mode.** `basalt log`, `basalt approve`, `basalt revert` and `basalt passkey list` and `check` given `--agent NAME` and the default `--config` find out whether the engine runs as a background service by the installed unit, which the person can read: `/etc/systemd/system/basalt-engine.service` on Linux, `/Library/LaunchDaemons/dev.basaltdb.engine.plist` on macOS. Unit present: they go through the engine's [person socket](person-socket.md#the-person-socket) and never read `engine.json` or the credential file. The engine stopped (socket missing or refusing the connection): `basalt: the engine is not running; start it with <command>, then run this command again` and exit `1`, where `<command>` is `sudo systemctl start basalt-engine.service` on Linux or `sudo launchctl bootstrap system /Library/LaunchDaemons/dev.basaltdb.engine.plist; sudo launchctl kickstart -k system/dev.basaltdb.engine` on macOS. Never `permission denied`, never a fallback to the files. The engine refusing the person's uid: `basalt: the engine does not let OS user <uid> use its person socket; add it with sudo basalt init --agent NAME --person-uid <uid>` and exit `1`. No unit, a `--config` other than the default, `--credential-file` or `BASALT_DATABASE_URL`: same-user mode, the CLI reads the credential as before. `basalt status` and `basalt upgrade` use the same rule.
- **The per-user config.** `basalt status`, `log`, `approve`, `revert`, `access`, `upgrade`, `passkey list` and `passkey check`, `basalt mcp` (for the status it serves while the engine is down) and `basalt engine`, given no `--config`, use the default path; but when the process is not root, nothing exists at the default path (a missing file only, never a file the person cannot read) and `basalt init` left an `engine.json` in the user's own config directory (`basalt/engine.json` in `os.UserConfigDir`), they read that one instead. A `--config` that is given, even if equal to the default, is used as it is, and root keeps the default. `basalt engine --user NAME` looks in the home of NAME, after it has dropped to NAME, not in the HOME it inherited; like `os.UserConfigDir` (and so `basalt init`) it uses an absolute `XDG_CONFIG_HOME` from its environment, off macOS, so the two agree. Commands that print a follow-up command name the config they used with `--config <absolute path>`. `basalt uninstall` and `basalt passkey remove` read no engine config (they use the admin connection string), so they have no fallback. When the engine runs as a service the unit and the system `engine.json` exist, so the default path is used and the person socket is as above.
- Service mode. **Recording the person.** When `basalt init` installs the engine service it records the person's uid(s) in `engine.json` as `personUids` (an array of integers) and sets `"mode": "SERVICE"`; a config init writes for the foreground engine (`--no-service`, or any of `--config`, `--socket-dir`, `--credential-file`) gets `"mode": "SAME_USER"`. A config without `mode` is `SAME_USER`. The person is `--person-uid N` (repeatable, for a second person), else the user who ran init (`SUDO_UID` when init itself runs under `sudo`, else the user running it). Init passes them to `basalt service install` as `--person-uid N`; `basalt service install` run directly takes `--person-uid`, else `SUDO_UID`. Either refuses to install the service when it has no uid, and refuses uid `0` and the engine's own OS user. Re-running init keeps the recorded uids and adds any new `--person-uid`; nothing removes one but editing `engine.json`. `--person-uid` is a one-shot flag: it is not saved in `initArgs`. When a recorded person uid is also an agent's `osUser` (the default `--os-user` is the person), init warns that while they share that OS user the CLI over the socket sees only that agent's ledger and the agent can use the socket too (the engine cannot tell two processes of one OS user apart; approve and revert still need the passkey signature), and recommends a separate `--os-user` for full isolation (owner decision SM-4).
