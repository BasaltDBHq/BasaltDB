### Version 31: the approval reveal reads the approval unlocked

Version 30's `reveal_approval_rows` locked the approval row (`FOR UPDATE`) after the re-run preview had run the held statement, whose `ROW_CHANGE` ledger rows take `chain_head`. `submit_approval` takes the same locks in the other order: the approval row, then `chain_head` in `_append`. A reveal racing the person's signature could hold `chain_head` and wait for the approval row while the signature held the approval row and waited for `chain_head`, and Postgres broke the deadlock (`40P01`). **Breaking** (AE-11), the default. Idempotent.

### Version 36: reinstalls on the record

M4 (owner decision of 14 Nov 2026 on reinstalls). Each engine pins the last chain head it verified (`<stateDir>/<agent>.head.json`), and `basalt log` pins one per database and role. When the guard is uninstalled and installed again, that pin names a ledger that no longer exists. Checking the new ledger against it gives a false tamper alarm. Setting the pin aside quietly would hide a real attack: an admin-level attacker can dump `basalt_meta`, rewrite history with a consistent chain, and drop and restore the schema. So a reinstall sets the old pin aside, never silently. The witness that held the pin records the set-aside in the new ledger, and every engine shows it until an admin acknowledges it (acknowledgement by an admin passkey: Access and audit, later). Each engine is a witness; the Vault keeps heads too (later). **Non-breaking** (AE-11): on an older guard an engine never sets a pin aside and keeps it, reporting the chain broken at it, so a reinstall reports a broken chain. A reinstall always installs the latest version, so this only happens with an engine newer than its `basalt init`. Idempotent.

**The install.** From [schema version 2](#schema-version-2-install-ids), a guard install is identified by a random id the install writes (`installs.install`, a `gen_random_uuid()`), which agent roles read with `install_id()`. A new install (after `basalt uninstall`, or `DROP SCHEMA basalt_meta`) gets a new id; an upgrade and running the install again keep it. A copy of `basalt_meta` (`pg_dump` and `pg_restore`, a template database, a physical backup or replica) keeps it too, so a pin is checked against a copy exactly as against the original. Before this, the install was the oid of the `basalt_meta` schema, which repeats: two clusters made the same way (a Postgres container removed and started again from the same image, then `basalt init`) give the schema the same oid, so the pin of the old ledger was checked against the new one and reported a broken chain. A pin carries the install it was verified on: the pin file adds `installId`. A pin without one (saved before install ids) is taken as a pin of another install, so it is moved or reported (below), never checked as the current install's.

|---|---|
| `installs` | This install's one row (`id boolean` primary key, always true), written by the install transaction itself. Running the install again keeps the row (`ON CONFLICT DO NOTHING`, `install` and `installed_at` unchanged); when the row is missing (deleted, or `basalt_meta` recreated outside the install), the next `basalt init` writes a new one, a new install. Columns: `install uuid` (random, `gen_random_uuid()`), `installed_at` (`clock_timestamp()`), `installed_by` (`session_user`), `vault_user text` (the Vault user the install ran for, from the transaction setting `basalt.vault_user` that the Vault's install path sets; null otherwise, and always null until the Vault installs, Access and audit). **Who sets a pin aside.**

- **The engine** (upkeep, on start and every hour), with a pin of another install:
  1. It first checks the pin against the current chain. This step counts only when `pin_on_chain(seq, hash)` is true (through its anchor branch only when the anchor is the genesis, seq 0: a legitimate pin is at most an hour old and retention deletes rows only after a year, so a pin at a later anchor means the history before it was cut), `verify_chain_from` from the pin is intact, and the full `verify_chain()` is intact (so rows before the pin cannot have been re-chained either). Then this is the same ledger under a new install id: the `installs` row was deleted and `basalt init` wrote a new one, or the pin was saved before install ids. The engine moves the pin to the new install and records nothing in the ledger. It logs a warning naming both installs, the only trace that the install changed (`basalt log` prints it on stderr, and `CHECK_HEALTH` returns `pinMoved`). A pin before the anchor fails `pin_on_chain` and goes to step 2. A restore or copy of `basalt_meta` keeps the install id, so it never comes here: its pins are checked as usual, and a copy whose history was rewritten reports a broken chain.
  2. Otherwise it reports the pin with `record_pin_set_aside` and then sets it aside. The full check covers the new chain, and every new pin carries the new install. A new install over a rewritten copy of the old ledger fails step 1, so it gets the notice.
  3. A call that returns false (this report is already recorded, for example when the pin file write failed after an earlier call) counts as recorded. When the call fails (the database is down, or the guard is older than version 36), the engine keeps the pin and reports the chain broken at it (`chainBrokenAt` at the pinned seq), without checking from it. It never sets aside a pin it did not record.
  4. It also keeps each set-aside it recorded in its own pin file (`setAside`: `pinnedSeq`, `pinnedHash`, `pinnedInstallId`, `installId`, `at`). It shows the notice from that copy as well as from the ledger, so deleting the rows or changing the view in the database does not hide what this witness saw.
- **`basalt log`**: the same steps for its own pin, on the credential it reads with (in service mode through `CHECK_HEALTH`, below), with its copy kept in its pin under the user cache directory.

**The notice.** `basalt status` and `basalt log`, on every engine, read `agent_reinstalls` and their own kept copy. They show one notice per reinstall (one `install` with rows), newest first, at most 3, followed by "and N earlier reinstalls" when there are more:

```
This database's ledger was reinstalled on <installedAt> by <installedBy> (via Vault: <vaultUser>). Previous ledger ended at entry <n> (hash <h>), as reported with the credential of <agent>. If nobody on your team reinstalled Basalt, treat this as tampering.
```

- `(via Vault: <vaultUser>)` appears only when `vault_user` is set. `<installedAt>` is RFC 3339 UTC.
- When no ledger row records the install (the reader's kept copy has a report whose `PIN_SET_ASIDE` rows are gone), the first sentence reads "This database's ledger was recreated or restored outside basalt init (no install record), first reported <at>."
- Each witness keeps its own `<n>` and `<h>`. The notice uses the report of the reader's own credential when there is one, otherwise the earliest report. It is followed by one line per other agent credential that reported this reinstall, at most 5, each with that agent's earliest report and a count of its further ones: "Also reported with the credential of <agent>: entry <n> (hash <h>)[, and N more reports]." Then "and N more agents" when there are more. One agent's many reports therefore take one line and cannot crowd out real witnesses.
- No report replaces another, so an agent role that reports a false pin cannot overwrite a real witness's entry and hash.
- `<n>` is the last entry that witness verified, not necessarily the last the old ledger held.

The notice stays until an admin acknowledges it with an admin passkey, recorded in the ledger (Access and audit, a follow-up). Until then nothing clears it. The `status` tool carries it as the problem `LEDGER_REINSTALLED` ([Configuration and status](vault-channel.md#configuration-and-status)). Its `personMessage` is the notice of the newest reinstall: the first notice line only, then "Run basalt log to see every report." `vaultUser` is cut to 64 characters, so the message stays under 500 characters. `basalt status` prints that problem with the other problems. `basalt log` prints every notice in full on stderr before the change records, with the other warnings.

**Only an admin reinstalls** (Access and audit, AA-2). Both `basalt uninstall` and the install need the admin connection string. Dropping `basalt_meta` needs its owner, and the install creates roles. An agent role owns nothing in `basalt_meta` and can do neither.

**Limits.**

- An agent role can call `record_pin_set_aside` with a pin it never held. That raises a false notice of its own, which names the agent's credential, and it changes no other witness's report. It can also append any number of such rows: a ledger write like any other agent write, with no rate limit.
- `installs` is only as trustworthy as the admin. Someone with the admin connection can write a row that names another user or Vault user, or change the install id. A changed id sends every witness's pin to the steps above (moved when the ledger is unchanged, otherwise reported with the notice); a deleted row stops every check until `basalt init` writes a new one. Neither is silent.
- A restore, or a new install over a copy, that keeps every entry up to the pin and rewrites only later ones passes the check (or moves the pin) with no notice, exactly as a rewrite in place would. Entries after the last pin are unprotected either way.
- An admin can move `chain_anchor` in place on an unchanged install; a pin older than the anchor then verifies from it. That gap predates version 36 and is not covered here (a follow-up).
- The install identity is a random id (`gen_random_uuid()`, 122 random bits), so two installs share one only by copying `basalt_meta`. A copy is the same ledger: a faithful one verifies, a rewritten one reports a broken chain. A pin checked on a copy that lost entries since the pin (a restored backup older than the pin) or went its own way (a copy that took writes while the original kept going) also reports a broken chain: that ledger is not the one the witness saw. Getting such a copy onto the reinstall path takes a new install id, as above.
- That admin can also delete `PIN_SET_ASIDE` rows. Doing so changes the chain after the witness pinned it, so the witness's next check of the same install reports a broken chain, and its own kept copy keeps the notice.
- The witnesses rely on the guard's own code. `verify_chain_from` and `agent_reinstalls` run in the database, and an admin who can replace `basalt_meta` can also redefine them. The engine's kept copy covers a hidden view. Only a witness outside the database that recomputes the hashes itself covers a rewritten verifier (the Vault, later). This is no weaker than before version 36.

### Version 37: held writes keep large lines

M4 (Large values, rule 7). Up to version 36 `hold_action` refused any preview line over 64 KiB with `BS008` `LEDGER_INPUT_INVALID`, so a held `DELETE` of a row with a large value was never held and the agent got `INTERNAL`. **Non-breaking** (AE-11): on an older guard the engine refuses such a write itself with `STATEMENT_REFUSED` `HOLD_TOO_LARGE`. Idempotent.

| Object | Change |
|---|---|
| `_check_held_lines(p_lines text[])` | New, internal (no grants). Refuses lines whose text, in bytes, sums to over 67 108 864 (64 MiB) with `BS007` `NOT_ALLOWED`, detail `HOLD_TOO_LARGE`, hint `the preview lines are <n> bytes; a held write holds at most 67108864` |
| `preview_lines` | Checks the cap before it returns a line, so the engine never reads more than a hold keeps |
| `hold_action` | No per-line cap; checks the cap before it parses a line. Otherwise as version 4 |

Both are replaced with `CREATE OR REPLACE`, `SECURITY DEFINER`, `SET search_path = pg_catalog, pg_temp`; owner and grants are kept. 64 MiB is far below Postgres's 1 GB limits on a value, an array and a protocol message, and above the [Large values](mcp-tools.md#large-values) example (a row with two values of 15 MB, escaped). The engine checks the same cap before it calls `hold_action`.

### Schema version 2: install ids

Breaking (the engine and `basalt log` call `install_id()`). Schema version 1 identified a guard install by the oid of the `basalt_meta` schema, which repeats: two clusters made the same way (a Postgres container removed and started again from the same image, then `basalt init`), or a database created from a template that holds the schema, give `basalt_meta` the same oid. A witness's pin of the old ledger was then taken as a pin of the new install and checked against an unrelated ledger: "ledger chain broken" on every check of an untouched ledger. Version 2 gives each install a random id; the objects are described in [Version 36](#version-36-reinstalls-on-the-record).

| Object | Change |
|---|---|
| `installs` | Replaced: one row (`id boolean` primary key, always true) with `install uuid`. The upgrade keeps the time, user and Vault user of the row for the current schema oid and gives it a random id; with no such row (`basalt_meta` restored outside the install) it writes a new one, as `basalt init` does |
| `install_id()` | New, granted to `<prefix>_agents` |
| `record_pin_set_aside(bigint, bytea, oid)` | Dropped. Replaced by `record_pin_set_aside(bigint, bytea, uuid)`, which also refuses with detail `NO_INSTALL` |
| `agent_reinstalls` | Recreated with `pinned_install` and `install` as `uuid` (the grant is kept). Ledger rows are never rewritten: a report recorded at version 1 keeps its oids in `detail`, and the view shows each such oid as the uuid `00000000-0000-0000-0000-` followed by the oid in 12 hex digits, which no random id is, so the earlier reports of one install still group together |

`basalt init` and `basalt upgrade` write the install row with the statement of the version the guard is at after the migrations, so an install that stops at version 1 still writes version 1's row. After the upgrade, a pin saved at version 1 carries no install id and is settled as [Version 36](#version-36-reinstalls-on-the-record) describes: on an unchanged ledger it moves to the new id with the warning, once.

### Schema version 3: plugin events

Non-breaking (AE-11): on a guard without it the agent is served as before, with `GUARD_UPGRADE_AVAILABLE`, but the engine cannot record a plugin event there, so it serves no plugin to that agent ([In the ledger](plugins-ledger.md#in-the-ledger)). Reading the events needs no new object: `agent_ledger` already shows the agent its own rows. Idempotent.

| Object | Change |
|---|---|
| `record_plugin_event(p_kind text, p_detail jsonb) returns bigint` | New. `SECURITY DEFINER`, `SET search_path = pg_catalog, pg_temp`, owned by `<prefix>_guard`, `EXECUTE` for `<prefix>_agents` only, none for `PUBLIC`. Callers must be agent roles (`BS007` `NOT_ALLOWED` otherwise, a superuser included). Appends one ledger row to the chain with `agent` `session_user` (there is no agent argument), the kind, and `p_detail` as the row's detail, and returns its `seq`. Refuses with `BS008` `LEDGER_INPUT_INVALID`, nothing written: a kind other than `PLUGIN_ENABLED`, `PLUGIN_DISABLED`, `PLUGIN_CHANGED` and `PLUGIN_TRUST_ADDED`; a detail that is not a JSON object or is over 4096 bytes as text; a `PLUGIN_TRUST_ADDED` detail other than `signerKeyId` alone, a key id; any other detail that breaks [`events.schema.json`](../api/plugin/events.schema.json): a key outside the list of [In the ledger](plugins-ledger.md#in-the-ledger), a required key missing, or a value of the wrong type, pattern or enum (nested objects included). It is stricter than the schema in one place: `version` must also be a semantic version, the manifest's own pattern, so it holds no free text. A manifest whose record could break these bounds (a `version` over 64 bytes, or an `egress` list so long that the detail could exceed 4 KiB) is refused when it is verified (`BAD_MANIFEST`), so every plugin a person consents to can be recorded. The error names the rule, never the value given |
| `_check_plugin_detail(p_detail jsonb)` | New, internal (no grants): the detail rules above |

### Schema version 4: plugin trust removed

Non-breaking (AE-11): on a guard without it the agent and its plugins are served as before, with `GUARD_UPGRADE_AVAILABLE`, but the engine cannot write `PLUGIN_TRUST_REMOVED` there, so a key the trust store no longer holds stays recorded as trusted (logged, tried again at each start). Idempotent.

| Object | Change |
|---|---|
| `record_plugin_event(p_kind text, p_detail jsonb) returns bigint` | Replaced (owner and grants kept). Also takes `PLUGIN_TRUST_REMOVED`, whose detail is `signerKeyId` alone, a key id, as for `PLUGIN_TRUST_ADDED`; every other rule is version 3's |

### Schema version 5: plugin approvals

[Plugin approval](plugins-approval.md#plugin-approval), file `015_plugin_approvals.sql`, following the revert pattern. The next free version after 4; if another migration takes 5 first, this one takes the next free number and every "schema version 5" in this file moves with it. **Non-breaking** (AE-11): on a guard without it the agent and its other plugins are served as before, with `GUARD_UPGRADE_AVAILABLE`; an entry that requires approval is withheld from that agent (`PLUGIN_UNAVAILABLE`, [Plugin approvals at engine start](plugins-approval.md#plugin-approvals-at-engine-start)), and `basalt plugin add` and `enable` refuse to open an approval there (`PLUGIN_REFUSED` `GUARD_OUTDATED`) with the upgrade step: `basalt upgrade` for the agent, or on an agent-operated engine an `UPGRADE` [setup code](setup-from-laptop.md#the-setup-code) finished on the person's own computer, as every admin step there. No other admin step is added. New installs get it with the rest. Idempotent.

| Object | Change |
|---|---|
| `plugin_approvals` | New table, no grants to agents: `approval_id uuid` (primary key, UUIDv7), `name`, `instance`, `opened_by` (the opening role), `agents text[]` (sorted), `detail jsonb` (the validated detail), `settings_text text`, `binding_text text`, `binding bytea` (its `sha256`, the challenge), `opened_at`, `expires_at`, `status` (`PENDING`, `APPROVED`, `CANCELLED`), `approved_at`, `credential_id bytea`. No row values: nothing to prune |
| `plugin_approval_ends` | New table, no grants to agents: `(approval_id, agent)` primary key, `ended_at`: a signed approval that a `PLUGIN_DISABLED` ended for that agent role |
| `open_plugin_approval(p_detail jsonb, p_settings jsonb) returns table (approval_id uuid, binding_text text, settings_text text, expires_at timestamptz)` | Agent roles. Validates the detail and the settings ([What a plugin approval binds](plugins-approval.md#what-a-plugin-approval-binds); `BS008` `LEDGER_INPUT_INVALID` otherwise, the error naming the rule, never the value), checks every role in `agents` is a member of `<prefix>_agents` (`BS007` detail `UNKNOWN_AGENT`), marks earlier `PENDING` approvals of the same `(name, instance)` `CANCELLED`, refuses when 8 unexpired `PENDING` approvals remain (`BS007` detail `TOO_MANY_PENDING`), builds `change`, the settings text and the binding text, stores the row, and appends `PLUGIN_APPROVAL_PENDING` to the caller's ledger. `expires_at` is 24 hours after `clock_timestamp()` |
| `submit_plugin_approval(p_approval_id uuid, p_credential_id bytea, p_authenticator_data bytea, p_client_data_json bytea, p_signature bytea) returns timestamptz` | Any agent role, as a relay. Calls `_verify_assertion` with the approval's `binding` (the checks of [Checks in Postgres](approvals.md#checks-in-postgres)), then marks the approval `APPROVED` with the credential id and appends `PLUGIN_APPROVED` to the ledger of every role in `agents`. Refuses, writing nothing: an unknown id or one that is not `PENDING` (`BS005` `APPROVAL_INVALID`, detail `NOT_FOUND`, `CANCELLED` or `ALREADY_APPROVED`), a pending one past `expires_at` (`BS005` `APPROVAL_EXPIRED`), and every `_verify_assertion` failure. It decides nothing about who may sign beyond `_verify_assertion`: any passkey of the database may sign, as for held writes, so signing rules added later go in that one shared place. Returns `approved_at` |
| `agent_plugin_approvals` | View, `SELECT` for `<prefix>_agents`: the plugin approvals that name the calling role or that it opened. `approval_id`, `name`, `instance`, `status` (`PENDING`, `APPROVED`, `CANCELLED`, and `EXPIRED` for a pending one past `expires_at`), `opened_at`, `expires_at`, `approved_at`, `names_caller boolean`, `ended_at` (for the caller, from `plugin_approval_ends`), `detail` (the `PLUGIN_APPROVAL_PENDING` detail, which names no agent), and `binding_text` and `settings_text`, which are `NULL` except for the role that opened it (they list the other agents). The engine's check and `basalt plugin list` read it |
| `record_plugin_event(p_kind text, p_detail jsonb) returns bigint` | Replaced (owner and grants kept). An entry detail may carry `signer` (`KNOWN` or `UNKNOWN`); with `UNKNOWN` it has no `signerKeyId`, otherwise `signerKeyId` is required as before ([`events.schema.json`](../api/plugin/events.schema.json)). It still refuses every kind but the five of version 4, so `PLUGIN_APPROVAL_PENDING` and `PLUGIN_APPROVED` with `BS008`. A `PLUGIN_DISABLED` also records, in `plugin_approval_ends`, the caller as ended for every `APPROVED` approval of that `(name, instance)` that names it |
| `_check_plugin_detail(p_detail jsonb)` | Replaced: the `signer` rule above |

Every function `SECURITY DEFINER`, owned by `<prefix>_guard`, `SET search_path = pg_catalog, pg_temp`, `EXECUTE` for `<prefix>_agents` only (none for `PUBLIC`); callers must be agent roles (`BS007` `NOT_ALLOWED` otherwise). Clock: `clock_timestamp()`. Postgres builds every text; no client re-serialises one.

### Guard errors

Raised by the guard with SQLSTATE class `BS`. The tool code each maps to is in [Error codes](error-codes.md#error-codes), the only mapping table.

| SQLSTATE | Message | When |
|---|---|---|
| `BS001` | `INTENT_REQUIRED` | Agent write without `basalt.intent` |
| `BS002` | `APPROVAL_REQUIRED` | 11 to 50 rows, or any `DELETE`. without a signed approval (`basalt.approval_id`); the engine then previews and holds it |
| `BS003` | `ROW_LIMIT_EXCEEDED` | Over 50 rows in one action, cascades included |
| `BS004` | `STALE_READ` | An agent `UPDATE` or `DELETE` of a row whose `xmin` differs from the version in `reads` for the run in `basalt.run_id`. Detail names the table, key and both versions. Checked before the row policy |
| `BS005` | `APPROVAL_INVALID`, `APPROVAL_EXPIRED`, `REVERT_INVALID`, `REVERT_EXPIRED` | Bad approval, revert authorisation or signature; from schema version 5 also a plugin approval `submit_plugin_approval` refuses |
| `BS006` | `PREVIEW_CANNOT_COMMIT` | A preview transaction tried to commit |
| `BS007` | `NOT_ALLOWED` | `TRUNCATE`, unknown `basalt.mode`, a run of another agent; from version 37 a held write's preview lines over 64 MiB (detail `HOLD_TOO_LARGE`, the hint gives the size); from schema version 5 `open_plugin_approval` with detail `TOO_MANY_PENDING` or `UNKNOWN_AGENT` |
| `BS008` | `LEDGER_INPUT_INVALID` | A ledger function got invalid input; from schema version 3 also a plugin event outside the contract (`record_plugin_event`: an unknown kind or detail key, a wrong shape, or a detail over 4 KiB); from schema version 5 a plugin approval detail or settings outside the contract (`open_plugin_approval`) |
| `BS009` | `NOTHING_TO_REVERT`, `REVERT_CASCADE` | M3. A revert that cannot be prepared; `REVERT_CASCADE` is caught inside the revert and becomes a `CASCADE` conflict. `REVERT_TOO_LARGE` is removed in version 9 |
| `BS010` | `SETUP_REFUSED` | Planned, version 16. `record_setup` refused a setup code; detail `USED`, `SUPERSEDED`, `EXPIRED`, `SETUP_ID_IN_FUTURE` or `EXPIRY_TOO_FAR`. Raised to the admin's `basalt init --setup-code` only, never to an agent |
| `BS011` | `SCOPE_REFUSED` | Version 20. A revert scope descriptor refused by `preview_revert` or `prepare_revert`, and from version 21 `rescope_revert`. Shape details, from the descriptor alone: `SHAPE` (`INVALID_ARGUMENT`), `STORE_RESERVED` (`INVALID_ARGUMENT`), `FILTER_CAP` (`INVALID_ARGUMENT` `SCOPE_FILTER_CAP`). In `preview_revert` and `prepare_revert` (the agent's own proposal): `NOT_OWN_CHANGE`, `NOT_OWN_RUN`, `NOT_OWN_TASK` (the engine maps them to `NOT_FOUND` reason `CHANGE`, `RUN`, `TASK`, unknown and other agents' ids alike) and `FILTER` (`INVALID_ARGUMENT` `SCOPE_FILTER`; the message names each refused entry with the fixed texts of [MCP tools](mcp-tools.md#mcp-tools)). In `rescope_revert` a select that is not provably own work, or any select after a widen, is never answered with `BS011` before the proof or token check: it fails as `BS005` `REVERT_INVALID` detail `WIDEN_REFUSED`, one message for every cause; only a proven or own-work select gets `FILTER` or `DESCRIPTOR` (`INVALID_ARGUMENT`) for an agent, run or table outside the scope ([check order](revert.md#rescope-widen-and-reject)) |
