> Part of **Plugins**. The section starts in [plugins.md](plugins.md).

### Consent

- **`basalt plugin add <dir> --agents a,b [--instance NAME]`** verifies the plugin, installs it and adds its entry disabled. Before anything is written it shows the person the hooks, the entity types, the egress hosts, `LOCAL` or `REMOTE` with the host, the signer and the agents, in plain words: a remote `wire.detect` plugin that declares `NAME_CUE` sees stored values in free text, so with it those values leave the machine; for an `approval.deliver` plugin, the plugin approval page's sentence for it, word for word: "It delivers your approval links. Anyone who can read where it delivers them can see the rows of writes waiting for your approval. Some links carry the whole request, so they can also see what the agent asked to run and why."; a local plugin with a non-empty `egress` runs with network access, not enforced per host. Then it asks to confirm; any answer but yes, or no answer, writes nothing.
- **`enable`** and **`disable <name> [--instance NAME]`** flip `enabled`. `enable` first verifies the installed copy and shows the same screen from it, and asks to confirm.
- **Changing an entry.** `basalt plugin add <dir> --agents a,b [--instance NAME]` for a `(name, instance)` that already exists changes that entry: the manifest in `<dir>` replaces the installed one (a new version, or new hooks, egress or endpoint), and `--agents` is the entry's full new list. It shows the same consent screen, with what changes, before anything is written, keeps `enabled` as it was, and the engine records it at its next start as `PLUGIN_CHANGED` (and `PLUGIN_ENABLED` or `PLUGIN_DISABLED` for the agents added or removed): the `basalt plugin` commands have no database access and write no ledger row. There is no other way to change an entry's manifest or agents.
- **Agent-operated engines.** When an agent marker is set ([Agents and the admin credential](setup.md#agents-and-the-admin-credential)) or the engine is `operatedBy: AGENT`, `basalt plugin add` and `enable` are refused (`PLUGIN_REFUSED` `AGENT_OPERATED`, exit `1`) before anything is written (the plugin directory's manifest is read only to compare its hash with the installed copy's): `engine.json`, the installed copies, the trust store and the ledger are unchanged. The one `add` allowed there changes an existing entry by removing agents from its `agents` and nothing else (same manifest bytes, no agent added). So any new entry, new hook, new egress host, changed endpoint (another host, or local to remote), new manifest version and added agent is refused. On those engines the agent runs the machine steps, so a prompt answered on that machine is no proof that a person consented. `disable` and `remove` stay allowed: they only narrow. This paragraph is service mode's. In same-user mode ([Plugin approval](#plugin-approval)) `add` and `enable` do not refuse there and open a plugin approval instead, which a person signs with a passkey on a page, and in service mode this paragraph is unchanged.
- The other commands: `basalt plugin list` (entries with version, signer, endpoint, isolation and health), `check <name> [--json]` (starts the entry, runs `initialize` and `health` and each declared hook with fixed samples that hold no store data, and prints the timing; the notifier hooks' samples and the `--json` result are in [What `basalt plugin check` sends](plugins-runtime.md#what-basalt-plugin-check-sends)), and `remove`. In service mode every write needs `sudo`, as editing `engine.json` does.
- **Health in `basalt plugin list`.** Only the running engine knows whether a plugin answers. In service mode without `sudo` the list comes from the engine ([Plugin approval in service mode](plugins-approval-service-mode.md#plugin-approval-in-service-mode)), so each entry shows `health`: `READY` (the engine runs it and it answers), `UNAVAILABLE` (the engine runs it, or keeps trying to start it, and it does not answer now) or `NOT_STARTED` (the engine does not run it: turned off, not approved, refused at its check, added since the engine last read its entries, or another entry of the same name and instance runs). Everywhere else the command reads `engine.json` and does not ask the engine: `sudo basalt plugin list`, and every list in same-user mode, show `health UNKNOWN (the engine reports it)`, and the agent's `status` is where a failing plugin shows (`PLUGIN_UNAVAILABLE`). Isolation is shown in every mode: `files` and, from the engine, `network`; a remote entry has none, and a local entry whose installed copy cannot be verified has none to show (the list says so).
- **`basalt plugin` with no command, or an unknown one**, prints one usage line naming every command with the flags it takes. `--config PATH` is taken by every command.

### Plugin approval

In same-user mode only. Service mode is unchanged by it: there `add` and `enable` follow [Consent](#consent), the `AGENT_OPERATED` refusal included, and `--approve-with-passkey` and `basalt plugin approve` are usage errors (exit `2`).

A person approves a plugin install or change once, with a passkey, on the page a link opens, and that one approval installs and enables it. It is a signed kind like a held write or a revert: Postgres builds the binding text, verifies the passkey signature and writes the record ([schema version 5](basalt-meta-schema-versions.md#schema-version-5-plugin-approvals)), so neither the agent, the engine nor the CLI can forge it. Schemas: [`api/plugin/approval/`](../api/plugin/approval/). Shared vectors, which the contract test (`TestPluginApprovalVectors`) checks and the guard, engine and page tests run: [`vectors.json`](../api/plugin/approval/vectors.json), one binding per page level, a change binding, a settings mismatch and a binding of another kind, each text as Postgres returned it.

**What an approval protects.** On an agent-operated engine the agent controls the machine the engine runs on. A passkey approval cannot physically stop a compromised agent from running code there. What it gives:

1. An honest engine never runs a plugin for an agent without a matching approval in that agent's ledger ([Plugin approvals at engine start](#plugin-approvals-at-engine-start)).
2. The ledger shows exactly what a person approved and with which passkey, and nobody but a passkey holder can create that record.
3. An agent tricked by text (prompt injection) cannot install anything through Basalt's own commands: it can only produce a link, and the person sees the truth on the page.

For a person whose agent runs on its own machine, the protection is the approval, the pinned copy and the ledger record. It is not OS isolation, and the page says so ([The plugin approval page](#the-plugin-approval-page)).

**Who needs one.**

- **Agent-operated engine** (`operatedBy: AGENT`): every entry requires approval, whatever `engine.json` says. `add` and `enable` open an approval instead of refusing.
- **Person-operated engine, a command run under an [agent marker](setup.md#agents-and-the-admin-credential):** the same. The person signs on the engine's local pages.
- **Person-operated engine, a person at a terminal:** as in [Consent](#consent): the consent screen, signatures and the trust store as today. `--approve-with-passkey` on `add` or `enable` chooses the approval flow instead, exactly as for an agent.
- **Never:** `disable`, `remove`, and an `add` that only removes agents from an existing entry (the same manifest bytes, the same settings, no agent added). They only narrow.

An entry **requires approval** when the engine is agent-operated or the entry has `"approval": "REQUIRED"` ([Config](plugins.md#config)), which `add` and `enable` write whenever they open an approval. In same-user mode an agent running as the engine's OS user can still edit `engine.json` and drop that key on a person-operated engine; that is the stated limit of [same-user mode](plugins-runtime.md#isolation-and-trust), and the ledger then shows the entry served with no approval (a `PLUGIN_ENABLED` without `signer`). On an agent-operated engine an honest engine has no such gap: there every entry requires approval.

**The flow.** `basalt plugin add <dir> --agents a,b [--instance NAME]`, or `enable <name> [--instance NAME]` for the installed copy:

1. **Check.** Before anything is written, the command stages and checks the copy as [Signing and the trust store](plugins.md#signing-and-the-trust-store) says (manifest rules, file hashes, the path rule) and works out its [signer state](#signer-states). It does not refuse an unknown or missing signature. It refuses, writing nothing, as before for a bad manifest (`BAD_MANIFEST`), a path (`UNSAFE_PATH`), an unknown agent (`UNKNOWN_AGENT`) and a `.sig` that names a built-in key and does not verify (`NOT_TRUSTED`); and also when a listed agent's credential cannot be read or its database does not answer within 15 seconds (`DATABASE_UNREACHABLE`), or a database's guard is older than [schema version 5](basalt-meta-schema-versions.md#schema-version-5-plugin-approvals) (`GUARD_OUTDATED`; the command reads `schema_version` with that agent's credential).
2. **Write.** It moves the copy into place and writes the entry to `engine.json`, enabled, with `"approval": "REQUIRED"`. Nothing runs yet: the engine withholds the entry until a matching approval exists. Writing first means no process has to commit anything after the signature, whichever way the signature comes back.
3. **Open.** One approval per database. The command groups the listed agents by the database their credentials connect to (host, port and database name) and, for each group, calls `open_plugin_approval` with the credential of the group's first agent in `--agents` order, naming every agent of the group (for `enable`, the entry's `agents`). An agent may open an approval that names other agents of its database: it is only a request, and the page shows the list. An open that fails now (for example a database reached its 8 pending approvals meanwhile, `TOO_MANY_PENDING`, or stopped answering, `DATABASE_UNREACHABLE`) leaves the entry written and withheld from that database's agents: the command exits `1`, its result names that database and the reason, and `enable` opens the missing approval later. Reasons after the write: `BS007` detail `TOO_MANY_PENDING` is `TOO_MANY_PENDING`, detail `UNKNOWN_AGENT` is `UNKNOWN_AGENT`, an older guard is `GUARD_OUTDATED`, and anything else (no answer, a refused connection, `BS008` or another guard error) is `DATABASE_UNREACHABLE`, its message carrying Postgres's detail.
4. **Hand over.** The command prints, and returns with `--json`, one link per database to the plugin approval page, with a `personMessage` and next steps ([Plugin approval commands](#plugin-approval-commands)).
5. **Sign.** The person reads the page and signs with a passkey registered on that database. The signature returns by one of the existing paths: the pasted code (`basalt plugin approve <code>`, which the agent runs when the person pastes the code into the chat), or the local pages' relay. A [Vault channel](vault-channel.md#vault-channel) session would carry it too, but a session needs a short link, and no command issues one on the portal for a plugin approval ([Plugin approval commands](#plugin-approval-commands)). `submit_plugin_approval` verifies it and appends `PLUGIN_APPROVED` to the ledger of every agent the approval lists.
6. **Start.** No restart and no command: the running engine sees the signed approval within a few seconds, checks it as at start, records the entry and starts it ([Plugin changes while the engine runs](#plugin-changes-while-the-engine-runs)). An engine that is not running serves it from its next start.

An entry whose agents span databases is served to each agent as soon as that agent's own database holds its approval; it does not wait for the others. Narrowing needs no new approval: the engine checks that the approval names the agent, not that the lists are equal, so the agents that stay still match and an agent removed from the entry is simply no longer served.

#### Signer states

- **`KNOWN`**: the manifest's `.sig` names a publisher key built into the engine, passes its schema and verifies. The key's id is recorded (`signerKeyId`).
- **`UNKNOWN`**: everything else: no `.sig`, a `.sig` that does not pass its schema and names no built-in key, or one that names a key the engine does not have built in. A signature file carries a key id and no public key, so a signature by an unknown key cannot be checked at all, and its key id could be made up. No key id is recorded or shown for it, and it is treated exactly as unsigned.
- **A `.sig` that names a built-in key and does not pass its schema or does not verify is refused**, whatever the approval says: at `add` and `enable` (`PLUGIN_REFUSED` `NOT_TRUSTED`) and at every start (`PLUGIN_NOT_TRUSTED`). That is damage or tampering.
- **The trust store does not make a publisher known** in the approval flow: in same-user mode an agent can write it. It keeps its role for an entry that does not require approval, which a person adds at a terminal.
- **No publisher key is built in yet**, so until one ships every plugin is `UNKNOWN`, and the page's level 1 cannot occur.
- **Verification** of an entry that requires approval, at `add`, `enable` and every start: steps 1, 2, 4 and 5 of [Verification](plugins.md#signing-and-the-trust-store) as for any entry; step 3 becomes "a `.sig` that names a built-in key passes its schema and verifies", and the signer state is worked out as above.
- **The approval takes the place of the trust record.** An entry that does not require approval is served to an agent only when that agent's ledger records the key that signed it ([A record that cannot be written](plugins-ledger.md#in-the-ledger)). For an entry that requires approval, the signed approval takes that place: the engine serves it without a `PLUGIN_TRUST_ADDED` of any key, and a `PLUGIN_TRUST_REMOVED` never withholds it or writes its `PLUGIN_DISABLED`. The key it rests on is built in or there is none, and the approval records the signer state the person saw.

#### How long an approval lasts

- **Pending.** A pending approval expires 24 hours after it is opened (`expiresAt`). The entry then stays in the config, withheld, and `status` says the approval expired and names the two ways out: open a new approval (`enable`, or `add` again) or `remove` the entry.
- **Cancelled.** Opening a new approval for the same `(name, instance)` in a database cancels the earlier pending one there.
- **At most 8 pending** plugin approvals per database, so an agent cannot flood the person or the disk. Opening a ninth is refused (`TOO_MANY_PENDING`); expired and cancelled ones do not count.
- **Signed.** A signed approval does not expire and is not single use. It stays the entry's approval for an agent until a newer approval for the same `(name, instance)` that names that agent is opened in its database, or the entry is turned off or removed for that agent. A newer approval decides from the moment it is opened: until it is signed, the entry is withheld. So turning an entry off and on again with the commands always needs a new signature, even when both happen between two engine starts, because `enable` opens a new approval, and because `add` and `enable` write the ends owed (below) before they write the entry: in same-user mode `basalt plugin disable` and `remove` end the approvals themselves when the database answers (never blocked by it: when it does not, the end stays owed), and `add` and `enable` first write, with each agent's own credential, the `PLUGIN_DISABLED` every agent the entry is turned on or added for owes, as `PLUGIN_OPEN` does in service mode, refusing `PLUGIN_REFUSED` `DATABASE_UNREACHABLE` and writing nothing when one cannot be written. An agent running as the engine's OS user that flips `enabled` in `engine.json` itself between two starts is not seen: the stated limit of same-user mode, as for dropping the `approval` key. "Newest" is by `opened_at`, ties broken by `approval_id`.
- **Turning off ends it.** A `PLUGIN_DISABLED` of `(name, instance)` in an agent's ledger, written after that agent's `PLUGIN_APPROVED`, ends the approval for that agent: `record_plugin_event` marks it ended when it writes the row, so the end outlives the ledger's one-year retention. The engine writes `PLUGIN_DISABLED` when the entry was disabled or removed, when the agent was removed from it, and when it withholds for an approval reason an entry the agent's ledger records as served ([Plugin approvals at engine start](#plugin-approvals-at-engine-start)). Turning it on again, also for the exact same copy, agents and settings, always needs a new signature: anything that turns something on goes through the person. Such records only narrow, so it does not matter that an agent role can write them. An end may follow a signed approval that was never served: disabling or removing an engine-kept entry ends its signed approvals at once ([Plugin approval in service mode](plugins-approval-service-mode.md#plugin-approval-in-service-mode)).

### What a plugin approval binds

The binding text is the `jsonb` text `open_plugin_approval` builds from the detail the caller passes and Postgres validates, as for held writes ([What an approval binds](approvals.md#what-an-approval-binds-decision-m2-1)): keys in `jsonb` order at every depth, and clients parse the text and never rebuild it. **Challenge** = `sha256(utf8(binding text))`, in `clientDataJSON.challenge` as base64url without padding. Every list is sorted by its text `COLLATE "C"`, with no repeats. Schema: [`binding.schema.json`](../api/plugin/approval/binding.schema.json). For example (a level 3 vector):

```json
{"kind": "PLUGIN", "name": "local-ner", "hooks": ["wire.detect"], "roles": ["VALUE"], "agents": ["basalt_agent_product_b"], "egress": [], "signer": "UNKNOWN", "version": "0.3.1", "database": "app", "endpoint": {"kind": "LOCAL"}, "instance": "client_x", "expiresAt": "2026-11-20T10:00:00.500000Z", "isolation": {"files": "NONE", "network": "NOT_ENFORCED"}, "approvalId": "…", "requestedBy": "basalt_agent_product_b", "manifestSha256": "…", "settingsSha256": "…"}
```

| Key | Value | The engine matches it at start |
|---|---|---|
| `kind` | `PLUGIN` | no |
| `approvalId` | the approval's id | no |
| `database` | `current_database()`, for display | no |
| `expiresAt` | RFC 3339 UTC with microseconds, 24 hours after the approval was opened | no |
| `requestedBy` | the agent role that opened it (`session_user`): which agent asked | no |
| `agents` | the agent roles of this database the entry will serve, each a member of `<prefix>_agents`; at least one | the agent's role is in it |
| `name`, `instance`, `version`, `manifestSha256` | of the installed copy | yes |
| `settingsSha256` | lowercase hex `sha256` of the settings text (below) | yes |
| `hooks`, `roles` | the manifest's hooks, and its `wire.detect` roles, present exactly when `hooks` holds `wire.detect` | yes |
| `endpoint` | `{"kind": "LOCAL"}`, or `{"kind": "REMOTE", "host": "<host:port>"}` | yes |
| `egress` | the manifest's `network.egress` | yes |
| `isolation` | `LOCAL` only: `{files, network}` with the values the plugin events use ([In the ledger](plugins-ledger.md#in-the-ledger)); in same-user mode `files: NONE`, `network: NOT_ENFORCED` | yes |
| `signer`, `signerKeyId` | `KNOWN` with the built-in key's id, or `UNKNOWN` with no `signerKeyId` | yes |
| `change` | what differs from the approved entry (below) | no |

- **The detail.** `open_plugin_approval(p_detail jsonb, p_settings jsonb)` takes the keys `agents` to `signerKeyId` of the table, without `settingsSha256`; Postgres adds `kind`, `approvalId`, `database`, `expiresAt`, `requestedBy`, `settingsSha256` and `change`. It validates the detail with the rules of `_check_plugin_detail` ([schema version 3](basalt-meta-schema-versions.md#schema-version-3-plugin-events)) and the binding schema: shapes and patterns, a semantic `version`, `roles` exactly with `wire.detect`, `isolation` exactly with `LOCAL`, `signerKeyId` exactly with `KNOWN`, lists sorted with no repeats. It checks every role in `agents` is a member of `<prefix>_agents` (`BS007` `NOT_ALLOWED` detail `UNKNOWN_AGENT` otherwise). A detail of an honest command always fits: a manifest whose detail could break these bounds is refused at `add` (`BAD_MANIFEST`), as for the plugin events.
- **The caller is not trusted** to tell the truth about the copy. The engine recomputes every field the table marks from the installed copy and its own config at each start, and serves only on an exact match ([Plugin approvals at engine start](#plugin-approvals-at-engine-start)). A caller that lies in the detail gets a signature for something the engine will not run. The fields marked "no" describe the request and are never matched.
- **Agents are roles.** `agents` and `requestedBy` hold role names (`<prefix>_agent_<name>`), as a revert binding does. The command maps each agent in `--agents` to the role its credential connects as; the engine matches an agent by the role its own credential connects as. The page shows the part after `_agent_`, as the approval and revert pages do.
- **The settings text** is the `jsonb` text Postgres returns for the object of the entry's keys other than `name`, `instance`, `manifestSha256`, `enabled`, `agents` and `approval` (today `config`, `auth`, `timeoutMs` and `minConfidence`), each only when the entry sets it: `config` and `auth` as `engine.json` holds them, and the numbers `timeoutMs` and `minConfidence` by value, in their shortest decimal form (`0.60` and `0.6` are the same setting and both are written `0.6`, as the `basalt plugin` commands write `engine.json`). No default is filled in, so writing `"timeoutMs": 300` where it was absent is a change. It is `{}` when the entry sets none ([`binding.schema.json`](../api/plugin/approval/binding.schema.json), `$defs/settings`). A plugin's settings can decide where data goes, so a change to them needs a new approval. Go and JavaScript never build it: `open_plugin_approval` takes the object as `p_settings`, computes `settingsSha256` itself, and stores and returns the text; the engine, at start, sends the object it reads from `engine.json` to the agent's database as `jsonb` and reads its text back (`SELECT $1::jsonb::text`) before it hashes it. So both sides get the same bytes: inside `config`, `0.60` stays `0.60` and `1e3` reads `1000` (a vector holds such a case), and a number written another way there is a change. The settings never hold a secret: [Config](plugins.md#config) refuses one in `config`, and `auth.credentialFile` is a path, never the file's contents.
- **`change`** is built by Postgres from its own records, never from the caller. It is present exactly when the database holds an earlier signed approval for the same `(name, instance)`, and then compares with the newest such one. Each key appears only when that thing differs: `fromVersion`, `fromManifestSha256`, `fromSigner`, `fromEndpoint` and `fromIsolation` hold the earlier value (`fromIsolation` is `null` when the earlier entry was `REMOTE`); `hooksAdded`, `hooksRemoved`, `rolesAdded`, `rolesRemoved`, `egressAdded`, `egressRemoved`, `agentsAdded` and `agentsRemoved` are sorted lists, never empty; `settingsChanged` is `true`. `{}` means nothing differs: the same entry turned on again. A change of built-in key with `signer` staying `KNOWN` has no key of its own yet; it is added with the first built-in key. A first approval of an entry that a person installed at a terminal has no `change`.

**In the ledger.** Neither detail names an agent, so no agent's ledger names another agent; the list is in the binding and the approval table ([`events.schema.json`](../api/plugin/events.schema.json), `approvalPendingDetail` and `approvedDetail`):

| Kind | Written by, to | Detail |
|---|---|---|
| `PLUGIN_APPROVAL_PENDING` | `open_plugin_approval`, to the ledger of the agent that opened it | the binding's keys without `kind`, `database`, `requestedBy`, `agents` and `change` |
| `PLUGIN_APPROVED` | `submit_plugin_approval`, to the ledger of every agent the approval lists | the same without `expiresAt`, plus `credentialId` (the passkey that signed, base64url) and `bindingSha256` (lowercase hex of the challenge) |

`record_plugin_event` refuses both kinds, so no agent role can write a `PLUGIN_APPROVED` row, and the engine's check reads the approval, never an event an agent role could have written.

### The plugin approval page

`<base>/plugins/<approvalId>` ([Page links](page-links.md#page-links)): on the portal for an agent-operated engine, on the engine's local pages otherwise. One page, three levels (owner decision, from a mockup).

- **Input.** The binding text and the settings text, and nothing else: from a long link's format 2 fragment (`texts` are exactly `[binding, settings]`, then optionally `credentialIds`; [Format 2](approvals.md#format-2-the-compact-request)), from a hash link's request file or text blocks ([The request file and pasted blocks](showing-links.md#the-request-file-and-pasted-blocks)), or, for a short link, from `GET /api/v1/plugins/{approvalId}` ([`request.schema.json`](../api/plugin/approval/request.schema.json)). The level and every sentence are derived on the page from the binding text.
- **Checks before anything is shown.** The binding's `approvalId` is the id in the page's path; `kind` is `PLUGIN` (otherwise the page says the link is not a plugin approval and shows no approve button); the binding passes [`binding.schema.json`](../api/plugin/approval/binding.schema.json); and the lowercase hex `sha256` of the settings text is `settingsSha256`. When the settings do not match, the page says the settings in the link do not match what would be approved and to ask the agent for a new link, and shows no approve button.
- **The level**, from `signer`, `endpoint` and `isolation`:
  1. **Known publisher**: `signer` `KNOWN`. Calm.
  2. **Unknown publisher, fenced in**: `signer` `UNKNOWN`, and `endpoint` `REMOTE` or `isolation.files` `OS_USER`. One warning. (`open_plugin_approval` refuses `isolation.files` `OS_USER`: the engine runs every entry that requires approval itself, in either mode, and derives `NONE` for it, so such an approval would never match. A local plugin under its own OS user is a config entry added with `sudo`, which never requires approval. The page still derives the level from `isolation` as it is given.)
  3. **Unknown publisher, local, not fenced in**: `signer` `UNKNOWN`, `endpoint` `LOCAL` and `isolation.files` `NONE`: every local plugin in same-user mode. The strong warning, and the tick.
- **The tick** (level 3 only): a checkbox labelled "I know who made this plugin and I trust them with my data." The approve button works only once it is ticked. Levels 1 and 2 have no tick.
- **The sentences.** The page shows these fixed sentences word for word, filling in only the `<…>` parts from the binding: `<name>` and `<version>` as they are; hosts as `host:port`, joined by ", "; agents by the part of the role after `_agent_`, joined by ", "; the publisher as `Basalt` (`KNOWN`) or `unknown` (`UNKNOWN`); a place as `the computer Basalt runs on` (`LOCAL`) or the host (`REMOTE`). The page cannot tell whose computer runs Basalt (an agent's own machine, or the person's laptop), so the words fit both. In this order:
  1. **What changes**, first, for a binding with `change`. With `change` `{}`: "You approved <name> before, and it was turned off. Turning it on again needs your approval." Otherwise "This changes <name>, which you approved before." and then, for each key present, in this order:
     - `fromVersion`: "Version <fromVersion> becomes <version>."; without it, `fromManifestSha256`: "Its files change, but its version stays <version>."
     - `fromSigner`: "Its publisher was <fromPublisher>; now it is <publisher>."
     - `fromEndpoint`: "It moves from <fromWhere> to <where>."
     - `fromIsolation`: "How it is kept apart from Basalt changes."
     - `hooksAdded`: "It gets new access to: <hookLabels>.", and `hooksRemoved`: "It no longer gets: <hookLabels>.", each hook by its label below, joined by "; ".
     - `rolesAdded`, one line per role: `NAME_CUE` "It now also looks for names in the text.", `VALUE` "It now also looks for private values in the text."; `rolesRemoved`: "It no longer looks for names in the text." and "It no longer looks for private values in the text."
     - `egressAdded`: "It now also connects to <hosts>."; `egressRemoved`: "It no longer connects to <hosts>."
     - `agentsAdded`: "It will now also be used for <agents>."; `agentsRemoved`: "It will no longer be used for <agents>."
     - `settingsChanged`: "Its settings change."
  2. **The level's line.** Level 1: "Published by Basalt." Level 2: "Nobody vouches for this plugin. Add it only if you trust where it came from." Level 3, in red: "Nobody vouches for this plugin. It runs a stranger's program on the computer Basalt runs on, with the same access as Basalt itself, so it could read your database password and the key Basalt uses to hide private values."
  3. **The tick**, at level 3.
  4. **Where it runs.** `REMOTE`: "It runs at <host>. Everything it sees is sent there." and "Basalt cannot check what runs there or where it sends things next." `LOCAL` with `files` `OS_USER`: "It runs on the computer Basalt runs on, as its own user, so it cannot read Basalt's files." `LOCAL` with `files` `NONE` at level 1, the plain line a known publisher still gets: "It runs on the computer Basalt runs on, with the same access as Basalt itself." (At level 3 the warning says it.)
  5. **A declared limit that is not enforced**, for `LOCAL` with `network` other than `ENFORCED`: with an empty `egress`, "It says it needs no network. That is not enforced on the computer Basalt runs on."; otherwise "It says it connects only to <hosts>. That is not enforced on the computer Basalt runs on."
  6. **What it sees**, one line per hook in the binding's order, from the consent texts of [Consent](#consent) and [Hooks](plugins.md#hooks):
     - `wire.detect` (label "the text your agents send to the AI provider"): "It reads the text your agents send to the AI provider, before Basalt hides private values in it." With `NAME_CUE` among its `roles`, then: "It also sees values from your database that appear in that text."
     - `feed.observe` (label "what your agents do in the database"): "It is told what your agents do in the database, such as which tables they change and how many rows, never the values."
     - `approval.deliver` (label "your approval links"): "It delivers your approval links. Anyone who can read where it delivers them can see the rows of writes waiting for your approval. Some links carry the whole request, so they can also see what the agent asked to run and why."
     - `classify.suggest` (label "the names of your tables and columns"): "It reads the names and types of your tables and columns, never their values, and suggests which ones hold private data."
  7. "Used for: <agents>." (the binding's `agents`), then "Asked by <agent>." (`requestedBy`), then "Fingerprint: <fingerprint>", the first 16 hex digits of `manifestSha256` in four groups of four (`a1a1 a1a1 a1a1 a1a1`).

  Beside them the page shows the plugin's name and version, the database, and the settings text. `TestPluginApprovalVectors` builds each vector's sentences from these rules and checks every sentence above is written here word for word.
- **Signing.** The approve button asks for the passkey with the binding's challenge, `allowCredentials` from `credentialIds` when present, and `userVerification: "required"`. The result is the code `basalt-plugin.1.<b64url(json)>` ([`response.schema.json`](../api/plugin/approval/response.schema.json)): `{ "approvalId", "credentialId", "authenticatorData", "clientDataJson", "signature" }`, as an approval response. On a short link the page posts it to the relay and shows "Approved. The plugin starts within a few seconds."; if the relay fails, it shows the error and the code. On a long or hash link, which has no engine, it shows the code, labelled for the person to give to the agent, who runs `basalt plugin approve <code>`.
- **The warning in the chat is a courtesy.** The command's `personMessage` carries the page's level line, so an honest agent relays it. No warning lives only there: the agent's text is not trusted, and a tricked agent would leave it out. The page is what protects the person.

### Plugin approvals at engine start

Same-user mode. At each start, for each enabled entry that requires approval and each agent it lists, after [verification](#signer-states), the engine reads `agent_plugin_approvals` with that agent's credential (within the 15 seconds of [A record that cannot be written](plugins-ledger.md#in-the-ledger)) and takes the newest approval for `(name, instance)` that names the agent's role. Such an entry is served to no agent until this check passes for that agent: an agent whose approvals were never read is not served.

| What the engine finds | Served to that agent | `status` problem for that agent |
|---|---|---|
| The agent's guard is older than [schema version 5](basalt-meta-schema-versions.md#schema-version-5-plugin-approvals) | no | `PLUGIN_UNAVAILABLE`, reason: the guard is older than schema version 5 (run `basalt upgrade` for the agent, on an agent-operated engine an `UPGRADE` setup code; the running engine checks again on its own) |
| The approvals cannot be read (no answer within 15 seconds, or the guard refused) | no | `PLUGIN_UNAVAILABLE`, with the reason |
| No approval names the agent | no | `PLUGIN_AWAITING_APPROVAL`: none was opened |
| The newest is pending | no | `PLUGIN_AWAITING_APPROVAL`, with its expiry |
| The newest was cancelled (a newer approval for the entry does not name this agent) | no | `PLUGIN_AWAITING_APPROVAL` |
| The newest expired unsigned | no | `PLUGIN_APPROVAL_EXPIRED` |
| The newest is signed and a matched field differs, ended or not | no | `PLUGIN_APPROVAL_MISMATCH`, naming the fields that differ, never a value |
| The newest is signed, every matched field is equal, and it has ended for this agent (turned off or removed since, or withheld for a mismatch) | no | `PLUGIN_AWAITING_APPROVAL`: turning it on again needs a new approval |
| The newest is signed and every matched field is equal | yes, if the usual checks pass (a local plugin may run on this engine, the record is written) | none from the approval |

- **Matched fields** are those [What a plugin approval binds](#what-a-plugin-approval-binds) marks: `name`, `instance`, `version`, `manifestSha256`, `settingsSha256` (recomputed through the agent's database), `hooks`, `roles`, `endpoint`, `egress`, `isolation` (as the entry would run on this engine), `signer` and `signerKeyId`, each equal to what the engine derives from the installed copy and `engine.json`; and the agent's role in `agents`.
- **The newest is per agent.** Only an approval that names the agent's role decides for that agent. An approval another agent of the database opens for the same `(name, instance)` that does not name this agent never withholds the entry from it or changes what it is served, pending or signed, and its `PLUGIN_DISABLED` ends nothing for this agent. Opening one does cancel a pending approval of the entry that names this agent: until a new one is signed the entry stays withheld from it, never served.
- **Withheld** is as in [A record that cannot be written](plugins-ledger.md#in-the-ledger): the entry refuses any call naming that agent, and an entry left with no agent is not started. Other agents and every other tool are served as before, and so is the agent itself: a withheld entry blocks none of its calls.
- **Not active is not failing.** An entry withheld with `PLUGIN_AWAITING_APPROVAL` or `PLUGIN_APPROVAL_EXPIRED` (none opened, pending, cancelled, expired unsigned, or turned off since it was signed) is simply not active for that agent: nothing was promised yet, so it never makes a data-path hook fail closed ([Failure](plugins-runtime.md#failure)), and the agent can still carry the approval link to its person. An entry withheld with `PLUGIN_APPROVAL_MISMATCH`, approved and no longer matching, counts as a failing entry of its hook, as [Failure](plugins-runtime.md#failure) says for that hook; for `wire.detect` that is settled with the `detector/1` contract. No data-path hook is called yet, so today no withheld entry blocks anything; a withheld `feed.observe` entry gets no event of that agent.
- **The record.** An entry withheld with `PLUGIN_UNAVAILABLE` keeps its record as it is, as any entry that is not started does, so a passing failure ends nothing. An entry withheld with `PLUGIN_AWAITING_APPROVAL`, `PLUGIN_APPROVAL_EXPIRED` or `PLUGIN_APPROVAL_MISMATCH` keeps it too, except when the agent's ledger records it as served: then the engine writes `PLUGIN_DISABLED` with the detail last recorded, as for a removed signing key, so the ledger never shows it served after it stopped matching. That ends any approval of it for that agent ([How long an approval lasts](#how-long-an-approval-lasts)), so an entry withheld for a mismatch keeps showing `PLUGIN_APPROVAL_MISMATCH` while it differs, and `PLUGIN_AWAITING_APPROVAL` once changed back: changing it back needs a new approval too. An entry served this way is recorded with `signer` in its `PLUGIN_ENABLED` or `PLUGIN_CHANGED` detail ([In the ledger](plugins-ledger.md#in-the-ledger)); its `PLUGIN_ENABLED` is written only after its approval matched.

### Plugin changes while the engine runs

Same-user mode only; in service mode the engine reads `plugins` at start only, as before. The engine applies plugin changes while it runs, so after a person signs nobody restarts it.

- **What it watches.** `engine.json`, read every second (a change made by any writer, a `basalt plugin` command or a hand edit, is seen); and, while an entry that requires approval is configured, each agent's ledger and plugin approvals, read with that agent's own credential over the connections the engine already holds: every 2 seconds while such an entry waits for a signature for one of its agents (`PLUGIN_AWAITING_APPROVAL`), every 15 seconds otherwise. With no entry that requires approval, no database is read until `engine.json` changes.
- **One check, as at start.** Each time, the engine derives what each agent should be served by the checks of [Plugin approvals at engine start](#plugin-approvals-at-engine-start), [Signer states](#signer-states) and [In the ledger](plugins-ledger.md#in-the-ledger), with the same code: verification of a new or changed entry's installed copy, the approval match, the record. It writes `PLUGIN_ENABLED` or `PLUGIN_CHANGED` before an entry starts serving an agent, and `PLUGIN_DISABLED` after it stopped.
- **Starts without a restart.** An entry that requires approval starts once a matching approval is signed for an agent, within a few seconds of the signature, for each agent whose approval matches; an agent added to a served entry is served once its own approval matches.
- **Stops without a restart.** Any entry, whether or not it requires approval, stops for an agent within a few seconds of `engine.json` turning it off (the next read, plus the stop), removing it or removing that agent, before any database is read. An entry that requires approval also stops for an agent when the check finds its approval no longer matches (a newer approval naming the agent, pending or signed and not matching; the approval ended; a matched field changed): `status` shows the same problem as at start. Stopping is as at engine stop: drain, `shutdown`, close, within 5 seconds. One process serves all of an entry's agents, so when the agents it serves change, the engine stops it and starts it again for the agents it now serves.
- **A changed entry.** A change to an entry that requires approval (a new copy, new settings, other agents) stops the running plugin as soon as the engine sees it, before any database is read. It runs again once a matching approval is signed: for a new copy, the approval `add` opened for it. Until then it is withheld as at start.
- **What still needs a restart.** Adding an entry that does not require approval, turning one on, or changing its copy or settings (a person at a terminal, [Consent](#consent)): while the engine runs such an entry only narrows, and the change takes effect at the next start; the command prints the restart command. A trust key added at a terminal, and every key of `engine.json` outside `plugins` (agents, `mode`, `operatedBy`), also take effect at the next start. So does any change to the trust store: while the engine runs, an entry that does not require approval keeps the verification and trust store of the start.
- **A file the engine cannot read.** When `engine.json` changes and does not parse, fails validation or cannot be read, the engine applies nothing: every plugin keeps running or stopped as it was, no database is read for plugins and no record is written (so a newer approval or an ended one is not acted on either until the file can be read), and `status` shows every agent `PLUGIN_CONFIG_INVALID` (`WARNING`), naming no entry, with `basalt plugin list`, which says what is wrong. Once the file can be read again, its state applies. Changes are level-triggered: two writes between two reads end in the state of the last.
- **A database that does not answer.** When an agent's database does not answer (no connection, or no answer within 5 seconds), nothing is decided for that agent and what runs for it stays as it is: a served entry keeps being served (its approval was verified, and no revocation can be written to a database that does not answer), an entry not served stays withheld, and a change to the entry or its config still stops it. Any answer decides as at start: a guard that refuses, is missing or is too old, or an agent served status only, withholds. An agent whose check failed either way is checked again after 2 seconds, doubling up to 60 seconds, until its check passes, also when no entry requires approval (a `PLUGIN_DISABLED` it still owes is written then); the other agents are checked as usual. A `PLUGIN_DISABLED` that could not be written is tried again 2 seconds later.
- **Shutdown.** The watch stops with the engine; the plugins stop within 5 seconds, as at any engine stop.

### Plugin approval commands

Same-user mode.

- **The wait**, in the manner of `write`'s `waitForApproval` ([Approvals](approvals.md#approvals)). By default `add` and `enable` hand the link over at once. **`basalt plugin enable <name> [--instance NAME] --approval-id <id>[,<id>] [--wait SECONDS] [--json]`** opens and writes nothing: it waits, up to `--wait` seconds (0 to 110, default 90), checking about once a second, until every given approval is signed and the running engine serves the entry, `READY`, to each listed agent an approval names, on that approval; or until an approval is no longer open (expired, replaced by a newer approval naming the agent, ended, or unknown to every listed agent's database). It returns at once, `NOT_RUNNING`, when every approval is signed and the engine is not running. A database that does not answer decides nothing: the wait goes on, and every connection and read runs within the wait's bound. The command refuses `--approval-id` for an entry that serves no agent. `add` and `enable` also take `--wait SECONDS` (default 0): after opening, they wait as above before printing, and print the wait's result when the plugin runs before it ends, else the approval result. `--json` prints [`wait.schema.json`](../api/plugin/approval/wait.schema.json): `name`, `instance`, `state` (`RUNNING`; `WAITING`, an approval still pending; `NOT_RUNNING`, all signed and the engine not running or not serving it yet; `ENDED`), `approvals` (`approvalId`, `state`, the `agents` it names), `personMessage` and `nextSteps`: `RUNNING` A `STOP` (tell the person it is done); `WAITING` P `TELL_AGENT`, A `END_TURN` (do not wait again in this turn; run the wait again when the person says they approved, or after `basalt plugin approve` with a pasted code); `NOT_RUNNING` O `RUN_COMMAND` (the engine's start command) when the engine is not running, else A `CALL_TOOL` `status`; `ENDED` O `RUN_COMMAND` (`basalt plugin enable <name> --approve-with-passkey --json`). Exit `0` for `RUNNING` and `WAITING`, `1` for the others. The command knows what the engine serves from `<stateDir>/plugin-serving.json`, which a same-user engine rewrites (whole, mode `0600`) when what it runs changes, and trusts it only while the engine that wrote it holds the engine lock (the engine removes the file as it starts its plugins and as it stops); it is advice to the command, never a reason to serve. Same-user mode, and in service mode without `sudo` for engine-kept entries: there the wait reads the approvals' states and what the engine serves from `PLUGIN_LIST` (`approval` and `serving`), never a file.
- **`basalt plugin add <dir> --agents a,b [--instance NAME] [--approve-with-passkey] [--json]`** and **`enable <name> [--instance NAME] [--approve-with-passkey] [--json]`** follow [The flow](#plugin-approval) whenever the entry requires approval or the flag is given; otherwise they are as in [Consent](#consent). For an entry that requires approval, `enable` opens a new approval for the installed copy and the entry as `engine.json` holds it now, whether or not the entry is enabled, cancelling a pending one. Text output: `personMessage` on stdout, each link on its own line by the [Terminal hyperlinks](showing-links.md#terminal-hyperlinks) rules; no restart command, since the running engine starts the entry once it is signed. `--json` prints [`result.schema.json`](../api/plugin/approval/result.schema.json): `name`, `instance`, `approvals` (one per database: `database` as `{ host, name }`, the `agents` by their names in `engine.json`, and either `approvalId`, `expiresAt`, `url` and, with a hash link, `requestFile`, or `refused` with its reason), `personMessage`, `links` and `nextSteps`. Refusals before the write are the usual `PLUGIN_REFUSED` error body.
- **The links.** `url` is the short link `<base>/plugins/<approvalId>#s=<secret>` when the engine serves the [local pages](local-pages.md#local-pages): the command issues it with `POST /api/v1/plugins/{approvalId}/links`, as `basalt approve --show` does, and the engine keeps its secret in the opener's `<agent>.links.json`. Otherwise it is the long link `<base>/plugins/<approvalId>#2.<request>`, or, when that is longer than the config's `linkBudget`, the hash link `<base>/plugins/<approvalId>#h=<h>` with `requestFile` (file name `basalt-plugin-<approvalId>.txt`; [The request file and pasted blocks](showing-links.md#the-request-file-and-pasted-blocks)). The base is the config's `pagesUrl`, the portal on an agent-operated engine. These are the only links the CLI measures against the link budget: an agent hands them over in a chat. No route issues a short link over the [Vault channel](vault-channel.md#vault-channel) for a plugin approval: in same-user mode the command has no channel to the engine but its local pages, so on an agent-operated engine the person gets the long portal link (or the hash link), and the signature comes back as the pasted code.
- **`personMessage`**: "<agent> asks you to approve the plugin <name> <version>." (with a `change`: "<agent> asks you to approve a change to the plugin <name> <version>."), then the page's level line, then "Approve it with your passkey:" (level 3: "Approve it with your passkey only if you know who made it:"), then each link as a paragraph of its own, then "Expires <YYYY-MM-DD HH:MM> UTC. The plugin starts within seconds of your approval." With more than one database there is one link per database, and each `links` label names its database. The rules of [Links in `personMessage`](showing-links.md#links-in-personmessage) apply: at most 500 characters without the URL lines, which the longest level line leaves room for. With a hash link the wording is a held write's ([The request file and pasted blocks](showing-links.md#the-request-file-and-pasted-blocks)). When a database has no registered passkey, `personMessage` says so first and the steps start with those of `APPROVAL_REQUIRED` `NO_PASSKEY` (on an agent-operated engine, its variant).
- **`nextSteps`**: `SEND_REQUEST` first when a `requestFile` is present; P `OPEN_LINK` for each link; A `RUN_COMMAND` (the wait: `basalt plugin enable <name> [--instance NAME] --approval-id <id>[,<id>] --json`, run in the same turn after showing `personMessage`); P `TELL_AGENT` (once they approved, or the code the page shows); A `END_TURN` (when the wait ended with the plugin not running). No restart step: the running engine starts the entry once its approval is signed. When the person pastes a `basalt-plugin.1.` code into the chat, the agent runs `basalt plugin approve <code>` on an agent-operated engine, and on a person-operated engine shows the person that command (the local pages' relay usually makes it unnecessary there).
- **`basalt plugin approve [code] [--agent NAME] [--json]`** decodes a `basalt-plugin.1.` code. Without a code it asks for one to be pasted, at a terminal only: with no code and no terminal (a script, an agent) it is a usage error (exit `2`) at once, and reads nothing from stdin. It then uses the agent that opened the approval (`requestedBy`: the only agent, `--agent`, or the one whose `agent_plugin_approvals` row carries `binding_text`, which only the opener's does), checks the code locally against the binding text and against the stored passkey, and calls `submit_plugin_approval` with that agent's credential. It prints the approved entry and that a running engine starts it within seconds; `--json` prints `{ "approvalId", "status": "APPROVED", "approvedAt" }`. A refusal exits `1` with Postgres's detail, as `basalt approve` does (`APPROVAL_INVALID`, `APPROVAL_EXPIRED`). An agent may run it: relaying a signature is not consent, and Postgres checks it.
- **`basalt plugin list`** shows, for each entry that requires approval, the state of the newest approval naming each listed agent: `APPROVED`, `PENDING` (with its expiry), `EXPIRED`, `ENDED` (turned off or removed since it was signed), `NONE` (none names the agent, or the newest was cancelled), or `UNAVAILABLE` (the guard is older than schema version 5, or the approvals could not be read); an entry that does not require approval shows `NOT_REQUIRED`. Whether a signed approval matches the installed copy and config is the engine's check at start, which `status` reports. `--json` prints `{ "plugins": [{ "name", "instance", "enabled", "agents", "approval" }] }` (in service mode without `sudo` each item also has `source`, `health` and, for a local entry, `isolation`: [Plugin approval in service mode](plugins-approval-service-mode.md#plugin-approval-in-service-mode)), `approval` being `{ "required", "agents": [{ "agent", "state", "approvalId"?, "expiresAt"? }] }`. Only an entry that requires approval reads a database, each agent's within 15 seconds.
