## Connect

Planned, except [the connect link](#the-connect-link), which `basalt init --remote` prints and the next steps hand over. The [connect page](#the-connect-page) is published on the portal; the connect service does not run yet. This section is the protocol of the **connect service**, the second way to run a [setup code](setup-from-laptop.md#the-setup-code): the person opens a link their bot sent, creates a passkey, pastes the database's admin connection string, and approves. The connect service runs the setup code against that database once, as [`basalt init --setup-code`](setup-from-laptop.md#basalt-init---setup-code-the-persons-own-computer) does on the person's own computer, and forgets the connection string. The laptop command stays, and is the way that needs no hosted service for every code with a `target`. Planned: a [connect-only code](setup-from-laptop.md#connect-only-setup-codes), made when the person gave the bot nothing about the database, has no `target` and runs only here; the service then holds the database's address until the bot's engine collects it ([The address hand-off](#the-address-hand-off)), and lets the engine test that it can reach the database before the person approves ([The reach check](#the-reach-check)).

**A hosted service, used only at setup.** The connect service is run by Basalt Vault at `https://connect.basaltvault.app`. It is closed source; this section and [`connect.proto`](../api/connect/proto/basalt/connect/v1/connect.proto) are the whole protocol it speaks (as the [Vault channel](vault-channel.md#vault-channel) is for the relay, VC-13). It is used only at setup: while a person runs a setup from the connect page, and while the engine of a connect-only code polls for its address, for up to 2.5 hours after the code was made whether or not the link is opened (planned: until the code expires, 24 hours after it was made, [The reach check](#the-reach-check)):

- The engine calls it only to collect the address of a connect-only setup ([The address hand-off](#the-address-hand-off)) and (planned) to report whether it can reach that address ([The reach check](#the-reach-check)), each request signed by its engine key under its own [signing context](vault-channel.md#primitives-and-encodings). Otherwise `basalt init --remote` only prints a link (below), and nothing is registered anywhere before the person opens it: no registration call and no pending setup stored by Vault.
- It has no accounts and no sign-in. It writes nothing anywhere: no database, no queue, no disk. Each setup call stands alone. Planned: it holds a connect-only setup's address (host, port, database, Supabase ref; never the password) in memory for up to 30 minutes: from `CheckSetup`, so the engine can test that it reaches it (a `PREVIEW` hold), and from `RunSetup`, until the engine collects it (a `SET_UP` hold).
- It is not on the data path and has no part in approvals or reverts. After the setup, the engine talks to the person's database as it does after the laptop command.
- When Vault is off, down or over a limit, the person runs the laptop command instead: the engine prints no link with the Vault off, and the page names the laptop command with every refusal. Planned: a connect-only code has no laptop fallback, since the laptop command refuses it (`CONNECT_ONLY`); the person tries again later, or the bot makes a code with `--database-url`.

The setup itself is the same as the laptop command's: the same checks in the same order, the same SQL from the same code (a public setup package in this repository, which the service pins at an engine version), one transaction, and `basalt_meta.record_setup`. The record does not say that Vault ran it. Planned: the connect path adds two things the laptop command does not take, both in the same transaction: the tables the person left ticked ([Tables on the connect page](#tables-on-the-connect-page)) and the column labels they set ([Column labels on the connect page](#column-labels-on-the-connect-page)). With the page's defaults (every table ticked, no label set) the two give the same database: a parity test runs one code with the laptop command and the same code through the service, and compares the roles, grants, policies, `basalt_meta` rows and classes.

### The connect link

`https://portal.basaltvault.app/connect#<code>`, where `<code>` is the setup code as `basalt init --remote` prints it. The code is in the fragment, so it reaches the page and not the portal's server. Like an approval link, the link holds everything the page needs; there is no short form.

- **When it is printed.** `basalt init --remote` prints it when the engine's `operatedBy` is `AGENT`, its `vault` is `ON` ([Configuration and status](vault-channel.md#configuration-and-status)), its `pagesUrl` is the portal (not with `devLocalPages`), and the whole link is at most the engine's [`linkBudget`](showing-links.md#the-link-budget) characters. A setup code is at most 1500 characters, so with the default budget of 1800 the link always fits. When it does not fit, init prints the code and says to paste it at `portal.basaltvault.app/connect`. There is no network call either way.
- **Where it is handed over.** In the text output after the code block, in the `--json` result's `connectUrl` and `personMessage` ([`remote-init-result.schema.json`](../api/mcp/setup/remote-init-result.schema.json)), and in every `personMessage` that hands the person a pending setup code on such an engine ([Next steps with the connect link](next-steps.md#next-steps-with-the-connect-link)). It follows [Links in `personMessage`](showing-links.md#links-in-personmessage): a line of its own, with a `links` entry labelled `Connect your database`. The message says the link uses Basalt Vault, a hosted service, and that the laptop command is the other way (planned: for a connect-only code, which only the link runs, it names no laptop command and says the page asks for the database's connection string, which the bot never needs).
- **The order.** The link first, the laptop command second. Both run the same code, so whichever runs first uses it and the other is refused `USED`.

### `SetupService` calls

ConnectRPC, package `basalt.connect.v1`, service `SetupService`. Each call is a `POST` to `https://connect.basaltvault.app/basalt.connect.v1.SetupService/<Method>`. The connect page sends `Content-Type: application/json` with the request's proto3 JSON form and needs no generated client; other clients may use the protobuf form. Field names in JSON are the camelCase forms of the proto's, byte values are base64url without padding, and enum values are SCREAMING_SNAKE_CASE strings. Proto3 JSON leaves out a field at its default value, so an absent field is `false`, `0`, empty or an empty list. The package is `v1`: a breaking change is a new package, and the page and the service ship it together.

| Call | Input | Output | Database |
|---|---|---|---|
| `DescribeSetup` | `code` | `summary`: the decoded code (kind, agent, role, prefix, target (absent for a connect-only code), tables or `allTablesSchemas`, statement timeout, guard versions, expiry), its setup fingerprint, the engine fingerprint when the code carries an engine key, and the summary `lines` of [step 5](setup-from-laptop.md#basalt-init---setup-code-the-persons-own-computer) that need no database. `challenge`: [the passkey challenge](#the-passkey-challenge) | None |
| `CheckSetup` | `code`, `databaseUrl` | `questions` (the row-level security question per table, as the laptop command asks it: `kind` `ROW_LEVEL_SECURITY`, `table`, `text`, `choices` `ALL_ROWS` or `NONE`), `passkeyNeeded`, `notes` (the lines that need the database: the statement timeout now in force, tables outside `public` flagged, the nothing-to-upgrade line), `nothingToDo`; planned: `database` (the database the pasted string names), with `allTables` `tables` (the tables the agent will get), `readOnly` (those of them without a primary key) and `excluded` (each left out, with the role that owns it), `columns` (each column of the tables the agent will get, with its class now: [Column labels on the connect page](#column-labels-on-the-connect-page)), for a connect-only `INSTALL` code `ticket` (the preview ticket, [The reach check](#the-reach-check)), and for a connect-only code `alreadyRan` | Connects and reads. Changes nothing in the database. Planned: for a connect-only `INSTALL` code, the service keeps a `PREVIEW` hold |
| `RunSetup` | `code`, `databaseUrl`, `answers`, `challenge` and `passkey` when a passkey is registered; planned: `includedTables` ([Tables on the connect page](#tables-on-the-connect-page)), `columnClasses` and `restPublic` ([Column labels on the connect page](#column-labels-on-the-connect-page)) | `warnings`, `passkeys` (each registered passkey's credential id, label and [check code](#the-passkey-check-code)), `nothingToDo`; planned, for a connect-only code: `ticket` (the [hand-off ticket](#the-address-hand-off)) and `reconnected` | Connects and runs the setup in one transaction |
| `CollectAddress` | Planned. The engine: `setupId`, `enginePublicKey`, `time`, `signature` ([The address hand-off](#the-address-hand-off)) | `address` (`host`, `port`, `database`, `supabaseRef`); planned: `phase` (`PREVIEW` or `SET_UP`) | None |
| `ReportReach` | Planned. The engine: `setupId`, `enginePublicKey`, `time`, `address`, `result`, `reason`, `signature` ([The reach check](#the-reach-check)) | Nothing | None |
| `HandoffStatus` | Planned. The page: `ticket` | `state` (`HELD`, `COLLECTED` or `UNKNOWN`), `collectedAt`, a new `ticket`; planned: `phase` and `reach` (`result`, `reason`, `reportedAt`) | None |
| `OfferAddress` | Planned. The page: `ticket` | `state` (`HELD` or `COLLECTED`) | None |

- **Every call stands alone.** `RunSetup` does not rely on `DescribeSetup` or `CheckSetup` having run: it repeats every refusal of both, in the same order, and computes the questions itself. It refuses an answer to a question it did not compute and a question left without an answer (`ANSWERS_INVALID`). The service keeps nothing between the setup calls: the page holds the connection string in memory and sends it with `CheckSetup` and again with `RunSetup`. Planned: the one thing it keeps is a connect-only setup's hold, made by `CheckSetup` (`PREVIEW`) or `RunSetup` (`SET_UP`) ([The address hand-off](#the-address-hand-off), [The reach check](#the-reach-check)), which no setup call relies on except for `RUN_ELSEWHERE`, running again and which hold replaces which.
- **What `RunSetup` runs.** Step 6 of the laptop command, with the confirmed answers in place of the prompts: the missing migrations, the role, the grants, the confirmed agent policies, `attach`, `record_setup`, and, when the code carries an engine key, `record_engine` with no address (the page asks for none, so a recorded address is kept and no other engine is offered for revoking). When a passkey is registered, `register_passkey` runs in the same transaction, after the migrations, so a failure leaves the database as it was. With `allTables`, the grants and policies cover the tables the listing names, read again in the transaction (no table at all is `NO_TABLES`; a listing that changed since it was shown is refused, today `SETUP_FAILED`, planned `TABLES_CHANGED`). Planned: for an `allTables` `INSTALL` code they cover the `includedTables` instead ([Tables on the connect page](#tables-on-the-connect-page)), and the column labels are written last ([Column labels on the connect page](#column-labels-on-the-connect-page)). A connect-only `AGENT` code (a [recovery code](setup-from-laptop.md#connect-only-setup-codes)) rotates the password of a role that exists, with the laptop command's warning for that kind, and runs as an `INSTALL` when the role does not exist; `ROLE_EXISTS` is unchanged for `INSTALL` codes. After a connect-only code ran, the service holds the address and returns a `ticket` ([The address hand-off](#the-address-hand-off)).
- **A passkey is needed** only when the database has no active passkey registered on the portal, whatever the code's kind. An `INSTALL` on a fresh database therefore needs one, and an `INSTALL` on a database that already has one does not. Then `RunSetup` without `passkey` is refused `PASSKEY_REQUIRED`. With one not needed, a `passkey` is registered all the same, as the laptop command's `--add-passkey` does.
- **Nothing to do.** An `UPGRADE` code whose `guard.to` is at or below the installed guard's version: `CheckSetup` and `RunSetup` return `nothingToDo` and the laptop command's line in `notes`, and `RunSetup` changes and records nothing, except as the laptop command does for an engine key not yet recorded.
- **Answers are fixed text.** Every `lines`, `notes`, `text` and `warnings` entry, and every refusal's message, is built from fixed words and values decoded from the code or read from the catalog; none holds the connection string or a database driver's own message.

### Connect refusals

A refusal is a ConnectRPC error whose detail is a `basalt.connect.v1.Refusal`: `reason` (below), `message` (the fixed message, in the laptop command's words where it has one) and `retryAfterSeconds` (set when trying again later can work). In the JSON error body, each entry of `details` has `type` `basalt.connect.v1.Refusal`, `value` (the detail's protobuf bytes, base64), and `debug`, the same detail in proto3 JSON, which the service always sends so a page without a protobuf decoder can read it. The error's own `message` is the refusal's message.

| Reason | ConnectRPC code | When |
|---|---|---|
| `NOT_A_SETUP_CODE`, `INVALID`, `UNSUPPORTED_FORMAT`, `DAMAGED` | `invalid_argument` | Decoding, as in [The setup code](setup-from-laptop.md#the-setup-code) |
| `EXPIRED`, `SETUP_ID_IN_FUTURE`, `EXPIRY_TOO_FAR`, `GUARD_TOO_OLD` | `invalid_argument` | Step 1 of the laptop command, by the service's clock |
| `BINARY_TOO_OLD` | `unavailable` | `guard.to` is newer than the guard of the engine version the service pins. Message: `Basalt Vault is being updated: try again shortly, or use the laptop command.` |
| `CONNECTION_STRING_REFUSED` | `invalid_argument` | The pasted string breaks [The pasted connection string](#the-pasted-connection-string) rules. The message names the rule, never the string |
| `ADDRESS_REFUSED` | `invalid_argument` | The host resolves to an address the service never connects to ([Where the runner connects](#where-the-runner-connects)) |
| `DATABASE_UNREACHABLE` | `unavailable` | No connection: an unreachable host, a closed port and a timeout give the same message |
| `CERTIFICATE_NOT_VERIFIED` | `failed_precondition` | The server's certificate does not verify. The message names the two ways forward: for Supabase, paste the pooler connection string; otherwise use the laptop command |
| `LOGIN_FAILED` | `failed_precondition` | The database refused the login |
| `TARGET_MISMATCH` | `failed_precondition` | Step 3 of the laptop command. Never for a connect-only code, which has no target |
| `RUN_ELSEWHERE` | `failed_precondition` | Planned. A connect-only code whose address the service holds for another database, checked only after the login to the pasted database succeeded ([The address hand-off](#the-address-hand-off)). Message: `This setup code was already used with a different database. If that was not you, someone else has your link: tell your bot to start over.` |
| `PREFIX_MISMATCH`, `USED`, `SUPERSEDED`, `ROLE_EXISTS`, `ROLE_MISSING`, `ENGINE_REVOKED` | `failed_precondition` | Step 4 of the laptop command, in its order. Planned, for a connect-only code: `USED` is not returned when the code may run again ([The address hand-off](#the-address-hand-off)), and a recovery `AGENT` code runs as an `INSTALL` instead of `ROLE_MISSING` |
| `TABLES_MISSING` | `failed_precondition` | After step 4: a table the code names is not in the database. The message names the missing tables and the database |
| `NO_TABLES` | `failed_precondition` | After step 4: a code with `allTables` finds no table in those schemas that the admin role owns; planned: or `RunSetup` with an empty `includedTables` for an `allTables` `INSTALL` code. Planned message: `There is no table to give <agent>. Nothing changed.` |
| `TABLES_CHANGED` | `failed_precondition` | Planned. The tables changed since they were listed: an entry of `includedTables` names a table the admin role does not own now (dropped, renamed or given to another role), or, without `includedTables`, the listing read again in the transaction differs from the one read before it ([Tables on the connect page](#tables-on-the-connect-page)). Nothing changed; the page lists the tables again. Today the second case is `SETUP_FAILED` |
| `CLASSES_CHANGED` | `failed_precondition` | Planned. `RunSetup` only: a column of `columnClasses` whose class stored now is not its `was` ([Column labels on the connect page](#column-labels-on-the-connect-page)). Nothing changed; the page reads the classes again |
| `ANSWERS_INVALID` | `invalid_argument` | `RunSetup` only: an answer to a question it did not compute or a question left without one; planned: also an `includedTables`, `columnClasses` or `restPublic` that breaks the rules of [Tables on the connect page](#tables-on-the-connect-page) and [Column labels on the connect page](#column-labels-on-the-connect-page) |
| `PASSKEY_REQUIRED` | `failed_precondition` | `RunSetup` only. Nothing changed |
| `CHALLENGE_EXPIRED`, `CHALLENGE_INVALID`, `PASSKEY_INVALID` | `invalid_argument` | `RunSetup` only ([The passkey challenge](#the-passkey-challenge)) |
| `SETUP_FAILED` | `failed_precondition` | Reading the database or the transaction failed, the passkey's registration included: nothing changed. The message is fixed per kind of failure (for example, the admin role lacks a privilege) |
| `TIME_LIMIT` | `deadline_exceeded` | The call ran past 60 seconds; the transaction rolled back |
| `RATE_LIMITED`, `BUSY` | `resource_exhausted` | [Connect limits](#connect-limits). Always with `retryAfterSeconds` |
| `REQUEST_TOO_LARGE` | `resource_exhausted` | A body over 16 KiB |
| `HANDOFF_UNKNOWN` | `not_found` | Planned. `CollectAddress` and `ReportReach` with no hold for the `setupId`, another engine key, or a signature that does not verify; `HandoffStatus` and `OfferAddress` with a ticket that does not verify or has expired. One answer for all of them |
| `CLOCK_SKEW` | `invalid_argument` | Planned. `CollectAddress` or `ReportReach` whose `time` is more than 5 minutes from the service's clock. No `retryAfterSeconds` |

The page shows the message and, for every reason but `RATE_LIMITED` and `BUSY`, the laptop command as the other way. Planned: for a connect-only code, which the laptop command refuses, it names instead asking the bot for a code with `--database-url`, and the messages that name the laptop command (`BINARY_TOO_OLD`, `CERTIFICATE_NOT_VERIFIED`) say the same. These reasons are the connect service's; they are not [Error codes](error-codes.md#error-codes) of the MCP tools.

### The passkey challenge

The person creates the approval passkey on the connect page (RP ID `basaltvault.app`, origin `https://portal.basaltvault.app`), with a challenge the service made and does not store:

- `DescribeSetup` returns `challenge` (32 random bytes), `userId` (16 random bytes), `userName` and `displayName` (labels for the passkey picker, as in the [passkey registration request](approvals.md#codes)), `expiresAt` (15 minutes later), and `mac`, a keyed hash over all of them and the code's setup fingerprint, made with a secret only the service holds. `mac` is opaque to the page.
- The page creates the passkey with that challenge and user id, and sends `RunSetup` the challenge unchanged and `passkey`: the browser's answer, with the fields of the [passkey registration response](approvals.md#codes) and an optional `label`.
- `RunSetup` checks, before it connects: `mac` against the challenge's fields and the fingerprint of the code in the same request (`CHALLENGE_INVALID`), `expiresAt` by its clock (`CHALLENGE_EXPIRED`), and the registration with the engine's own check: the challenge, the origin, the RP ID, the ES256 key (`PASSKEY_INVALID`). It stores the key with `userId` as its user handle.

So a registration is refused after 15 minutes, for another setup, or after the code was swapped. The challenge is not what lets a setup run: the admin connection string is. For a code with `target`, someone who has only the link can run nothing. Planned: a connect-only code names no database, so whoever runs it first, with any database they own, sends the bot there; the person's confirmation in the chat is what stops the engine using it ([Controls](setup-from-laptop.md#controls)).

### The passkey check code

The page's guard against a substituted passkey. The connect page computes it in the browser from the public key the browser returned, and shows it with the result; it never shows a code the service sent in its place, and says something is wrong when the service's `checkCode` for that credential differs. After the setup is picked up, the engine names each active passkey of the database with its check code, computed from the key in `basalt_meta.passkeys`. One passkey with the same code is the expected result. A different code, or a passkey the person did not create, means stop and remove it. This detects a substituted key; it does not prevent one.

The code is the first 10 bytes of `sha256("basalt-passkey-check.1\n" ‖ x ‖ y)`, where `x` and `y` are the 32-byte P-256 coordinates of the key, in lowercase hex as five groups of four. For the P-256 base point (`x` = `6b17d1f2…d898c296`, `y` = `4fe342e2…37bf51f5`) it is `dbf5 ff76 2025 209d d866`.

### The pasted connection string

The person types it into the page; the page holds it in a variable only, never in storage, and clears it after `RunSetup`. The service:

1. Keeps it only in the memory of one request. It never writes it to a log, a trace, an error report, a metric label, a disk or another service. In `connect.proto`, `databaseUrl` carries the field option `(basalt.connect.v1.sensitive) = true`. Logs are built from an allow list of fields, request bodies are never logged, and a panic is reported without its arguments.
2. Replaces every error of the setup package with a fixed message before anything reaches the caller or a log. The package's `SETUP_FAILED` can carry the database's own words, so the mapping happens in the service, not in the package; what the service returns holds no connection string and no driver text. The service's own cloud identity has no permissions and no access to other services, so a mistake there reaches nothing else.
3. Accepts only a `postgres://` or `postgresql://` URL with one host, a port, a database, a user and a non-empty password, and no parameter but `application_name`, `channel_binding`, `connect_timeout`, `sslmode`, `sslnegotiation`, `sslsni`, `target_session_attrs`, `min_protocol_version` and `max_protocol_version`. This is deliberately narrower than the list root accepts in a credential file ([`basalt init --remote`](setup-from-laptop.md#basalt-init---remote-the-engines-machine), step 8): `default_query_exec_mode` and `require_auth` are left out. Several hosts, a socket path and every other parameter (`hostaddr`, `passfile`, `service`, `sslrootcert`, `sslcert`, `sslkey` and the like) are refused `CONNECTION_STRING_REFUSED`. It reads nothing from the environment: no `PG*` variable reaches the connection.
4. Requires TLS with a certificate that verifies for the host name against the system's trusted authorities (`verify-full`), whatever the string's `sslmode` says. The admin password is never sent over a connection whose other end is not proven.
5. Requires it to name the same database as the code's `target`, as [step 3](setup-from-laptop.md#basalt-init---setup-code-the-persons-own-computer) does (`TARGET_MISMATCH`). Planned: a connect-only code has no `target`; the database the pasted string names is the setup's target, and the service refuses a second one while it holds the first (`RUN_ELSEWHERE`).

### Where the runner connects

The person types the host, so the service could be pointed anywhere:

- The host name is resolved once, each address is checked, and the connection is made to that exact address, with the host name kept for TLS. When a name has IPv4 and IPv6 addresses, IPv4 is used.
- Only global unicast addresses are used. Refused (`ADDRESS_REFUSED`), for IPv4 and IPv6, among others: loopback, link-local (which holds cloud metadata addresses), private ranges, carrier-grade NAT (`100.64.0.0/10`), `0.0.0.0/8`, `192.0.0.0/24`, benchmarking (`198.18.0.0/15`), reserved (`240.0.0.0/4`) and broadcast, multicast, unspecified addresses, documentation ranges, and IPv6 forms that wrap or route to an IPv4 address (IPv4-mapped, IPv4-compatible, NAT64, 6to4 `2002::/16`, Teredo `2001::/32`). A name with any refused address among those it resolves to is refused as a whole.
- Any port. An unreachable host, a closed port and a timeout return the same message after the same minimum delay, so the service tells a caller little about a host that is not a database they can log in to.
- One setup per request, 60 seconds per call, and a cap on calls running at once.

### Connect limits

No accounts, so the limits are by what the service can see: requests per IP address, different targets per IP address, failed logins per target (so the service cannot be used to guess database passwords), setups run per target, and the body size (16 KiB). A **target** is the database a setup is for (for a connect-only code, the one the pasted string names): the Supabase project ref when the code has one, otherwise host, port and database, so one person's mistakes on a shared pooler host lock out no one else. The client's address is the one the hosting front end adds to `X-Forwarded-For`, never an entry the caller supplied; which entry that is belongs to the service's configuration. At the cap on calls running at once, a call is refused `BUSY`, not queued. The numbers are the service's configuration, not part of the contract, except for `CollectAddress` (planned), which is limited apart from the setup calls: 1 call per 10 seconds per engine key, counted only for calls whose signature verified (so someone who copied the public key cannot starve the real engine), and 20 000 calls per hour per IP address for all calls (hosted bots share outbound addresses; an engine polls about 240 times an hour at most). Over a limit it is refused `RATE_LIMITED` with `retryAfterSeconds`, and the engine waits that long. `HandoffStatus` and `OfferAddress` count as page calls. Planned: `ReportReach` has the same two limits as `CollectAddress`, counted apart from it, and `PREVIEW` holds have caps of their own ([The reach check](#the-reach-check)).

### The connect page

`/connect` on the portal ([Page links](page-links.md#page-links)), a static page with its own script, covered by `basalt portal verify` like the other portal pages. It runs only at `https://portal.basaltvault.app`, the one origin the service allows (CORS, no cookies), so another site's page cannot use the service from a visitor's browser. CORS does not stop a script that calls the API directly: the [limits](#connect-limits) and the [address rules](#where-the-runner-connects) are what protect the service. Its order is fixed:

1. Read the code from the link's fragment, or from a paste box. `DescribeSetup`.
2. Show the summary and the setup fingerprint, and say which host this page must be on. Planned: for a connect-only code the summary says `Database: the one you paste below` where it would name the target.
3. The passkey, before anything is pasted. For an `INSTALL` code the person creates one. For an `AGENT` or `UPGRADE` code the person signs once with the passkey they already have, which only this site can ask for; the page sends nothing of it. This step is a habit that helps a returning person notice a fake site, where their passkey is not offered; it is not counted as a protection.
4. Paste the connection string. `CheckSetup`. Planned: a string that does not start with `postgres://` or `postgresql://` is refused on the page before any call: `Basalt works with Postgres databases; paste a connection string that starts with postgresql://`.
5. Planned, for a connect-only `INSTALL` code with a `ticket`: the reach check ([The reach check](#the-reach-check), the page) before anything else is shown.
6. Show a refusal, or the notes and the questions. When `passkeyNeeded` and no passkey was created yet, create one now. Planned: "Before you approve" leads with the database from `database`, large, as `Supabase project <ref>, database <db>` or `<host>:<port>, database <db>`, with `This is the database your bot will use`, then the tables the agent will get (`tables` and `excluded` with `allTables`, else the code's tables), with ticks for an `allTables` `INSTALL` code and `read only (no row ID)` after each table of `readOnly` ([Tables on the connect page](#tables-on-the-connect-page)); then, on a step the person may skip, the column labels ([Column labels on the connect page](#column-labels-on-the-connect-page)). The page asks no row-level security question: it answers `ALL_ROWS` for every included table the questions name, and says `<bot> can read and change every row of the ticked tables, and can't see the unticked ones.` With `alreadyRan` it shows neither the tables' ticks nor the labels, and says `This setup already ran; your bot is being reconnected to it.`
7. Approve: `RunSetup`. Show the result, the warnings and the passkey's check code. Planned: on `TABLES_CHANGED` the page lists the tables again (step 6), and on `CLASSES_CHANGED` it reads the classes again.
8. Say: tell your bot "done". The engine notices a finished setup only when the bot asks for its status or at its hourly heartbeat. Planned, for a connect-only code instead: show `Waiting for your bot to pick up the address…` and call `HandoffStatus` every 5 seconds with the latest ticket. On `UNKNOWN`, send `OfferAddress` once. On `COLLECTED` (planned: in phase `SET_UP` only): `Your bot picked up the address of <database>. It will ask you in the chat to confirm this database.` After 2 minutes without a pick-up: `Your bot hasn't picked it up yet. Tell it to check its status.` The page never says "connected": only the bot knows it logged in. `reconnected` adds `This setup already ran; your bot is being reconnected to it.`

The page's content security policy is as strict as the approval pages' (no inline script, no third-party script, integrity hashes on its own scripts, no framing, no referrer), and allows connections to `https://connect.basaltvault.app` for this page only: its `<meta>` policy names that one source in `connect-src`, and the portal's edge function serves `/connect` and `/connect/` with the portal's header policy plus `connect-src https://connect.basaltvault.app`, the same for everyone. The page and the service answer with `Cache-Control: no-store`. The page holds the connection string in a variable only and empties the input box as soon as it reads it; after a refusal of `CheckSetup` or `RunSetup` the person pastes it again. It keeps the ticket in a variable only. Planned, for a connect-only code, the disclosure: `Your database password goes to Basalt Vault's connect service for this one setup and is never stored. The database's address (not the password) is kept in the service's memory for up to 30 minutes, until your bot picks it up.` With the reach check it says instead: `Your database password goes to Basalt Vault's connect service for this one setup and is never stored. The database's address (not the password) is kept in the service's memory for up to 30 minutes: while your bot tests that its server can reach it, without signing in, and after you approve, until your bot picks it up. Until then your bot asks the service for it regularly, for up to 24 hours.` On a phone, switching back to the chat may suspend the tab; the engine usually collects within 15 seconds of approval, and if the tab was suspended and the service restarted meanwhile, the person opens the link again ([running again](#the-address-hand-off)).

### What the connect service sees

Everything the setup needs, for the length of one call: the setup code (with the agent's SCRAM verifier, which is [sensitive](setup-from-laptop.md#the-setup-code)), the admin connection string, the person's answers, the new passkey's public key, and the database itself, with admin rights. So while a setup runs, Vault is trusted as the person's own computer is on the laptop path: it could change the database or register a passkey of its own. The check code makes a substituted passkey visible; nothing in this version makes the rest visible. A person who does not want to trust Vault with that runs the laptop command. The service never sees the agent's password, which stays on the bot's machine.

Planned, for a connect-only code: the service also holds the database's address in memory for up to 30 minutes, and Vault is trusted to hand the bot the right address; the person confirms in the chat the database the bot reached, before the engine logs in. Vault also sees which engines are waiting: every engine that made a connect-only code polls `CollectAddress` from its outbound address with its engine key for up to 2.5 hours (planned: until the code expires, 24 hours after it was made), whether or not the link is opened, and (planned) whether each engine reached the address it was handed. Logs carry only the `setupId`, never the address or the ticket.

### The address hand-off

Planned. How the bot's engine gets the address of the database a [connect-only code](setup-from-laptop.md#connect-only-setup-codes) ran in, without the bot or the person telling it. The engine's side is [The engine and a connect-only code](setup-from-laptop.md#the-engine-and-a-connect-only-code).

- **The hold.** After `RunSetup` succeeds for a connect-only code, the service keeps (planned: as a `SET_UP` hold; `CheckSetup` makes `PREVIEW` holds, [The reach check](#the-reach-check)), in memory, a hold keyed by `setupId`: the address (host, port, database, Supabase ref; never the password or anything else of the string), the code's engine key, its setup fingerprint, and the expiry, 30 minutes later. It stays collectable until it expires and is marked collected on the first `CollectAddress`; collecting again returns the same address, so an engine that stopped between collecting and writing its credential collects again. A hold is never written to a log, a disk or another service. A hold made by `RunSetup` is in the instance the engine reaches: the service runs as **at most one instance**.
- **The ticket.** `RunSetup` returns `ticket`, which records the address, the engine key, the `setupId`, the setup fingerprint, the expiry and whether the address was collected (everything a hold needs, so a hold put back from it can be collected), with a keyed hash made with a secret only the service holds and keeps across restarts (configured, never made per process, or no ticket would verify after the restart it exists for), under a domain string of its own, so a ticket is never accepted as a passkey challenge or the other way round. Its format is the service's; the page treats it as opaque, keeps it in a variable only and never shows it. `HandoffStatus` takes the ticket, not a bare `setupId`, so only the page that ran the setup can ask, and returns a new ticket that records `COLLECTED`, with the original expiry, for the page to use from then on. A ticket never replaces a hold that exists with another target: `OfferAddress` then changes nothing, and `HandoffStatus` answers `UNKNOWN` when the hold's target is not the ticket's, so the page never names a database the engine did not collect. `OfferAddress` checks the hash and the expiry and puts the hold back after a service restart, **with the ticket's expiry, never a new one**, and the collected state the ticket records.
- **`CollectAddress`.** The engine sends `setupId`, `enginePublicKey` (its SPKI as in the code's `engine.publicKey`), `time` (RFC 3339 UTC, whole seconds) and `signature`: ECDSA P-256 by the engine's signing key, as 64 bytes `r ‖ s` in base64url ([Primitives and encodings](vault-channel.md#primitives-and-encodings)), over the UTF-8 bytes of `basalt-connect-collect.1\n` + `connect.basaltvault.app` + `\n` + `setupId` + `\n` + the setup fingerprint as printed (five groups of four lowercase hex digits) + `\n` + `time`, with nothing after it. For the setup code `01a1f78c-52b8-7c3a-9f00-0000000000e1` of the fixtures, fingerprint `d48b ee66 a1d9 d005 1f63`, signed at `2026-11-20T06:10:00Z`, the signed bytes are the five lines `basalt-connect-collect.1`, `connect.basaltvault.app`, `01a1f78c-52b8-7c3a-9f00-0000000000e1`, `d48b ee66 a1d9 d005 1f63` and `2026-11-20T06:10:00Z`, joined by `\n`. The audience and the fingerprint are the service's own (the fingerprint is the hold's), never taken from the request. There is no nonce, since the service keeps no state for one: a captured request replays only within the 5-minute window, to the same answer.
- **Who may collect, cheaply.** The service checks `time` first: more than 5 minutes from its clock is `CLOCK_SKEW`, since that says nothing about setups. Then it looks up the hold for the `setupId`, and checks the signature only when a hold exists and its engine key equals `enginePublicKey`, so a flood of made-up keys costs a map lookup. No hold, another key and a bad signature all get the same `HANDOFF_UNKNOWN`. Someone who has the link (it holds the `setupId` and the engine key) may tell from timing whether a hold exists; that tells them only that the setup ran, which the link's owner can see too.
- **One database per code, without an oracle.** While a hold exists for a `setupId` (planned: a `SET_UP` hold; a `PREVIEW` hold never refuses anything), `RunSetup` with the same code and a pasted string for a different target is refused `RUN_ELSEWHERE`. The check runs **after** the login to the pasted database succeeded with a verified certificate, so only someone who can log in to a database learns anything, and its message is fixed and names nothing of the other database. This is best effort: after the hold expired or the service restarted, nothing refuses another database; the person's confirmation in the chat is what stops the engine using it.
- **Running the same code again.** A connect-only code that the pasted database already records as used (the same `setupId`) is not refused `USED` when there is no hold, or the hold's target is this database: `RunSetup` changes nothing, holds the address again (a new 30 minutes, with the address from the string just pasted), and returns a new ticket with `reconnected`. Planned: `CheckSetup` then answers `alreadyRan`, and `RunSetup` ignores `includedTables`, `columnClasses` and `restPublic` (they are not checked either), so the page skips the tables and the labels. A `PREVIEW` hold counts as no hold here. This is the recovery for an address the service lost and for a database the bot's machine could not reach (the person pastes a string it can reach, such as Supabase's pooler string for the same project).
- **Limits.** In [Connect limits](#connect-limits).

### The reach check

Planned. Before the person approves a connect-only `INSTALL` code, the bot's engine tests that it can reach the database they pasted, so an address the bot's server cannot use (Supabase's direct host from a server without IPv6, a firewall) shows up before the setup runs, not after it.

- **The preview hold.** For a connect-only `INSTALL` code, a `CheckSetup` that logged in with a verified certificate and answers (is not refused) makes a hold in phase `PREVIEW`: the address, the code's engine key, its setup fingerprint and an expiry 30 minutes later, as a `SET_UP` hold has, and returns `ticket`, a preview ticket (a hand-off ticket that records the phase). Another `CheckSetup` for the same code, from anyone, replaces a `PREVIEW` hold, never a `SET_UP` one: while a `SET_UP` hold exists, `CheckSetup` makes no hold and returns no ticket. `RunSetup` makes the `SET_UP` hold, replacing a `PREVIEW` one, with the address of **its own** pasted string, never the preview's; the new hold has no reach result and is not collected, and `RunSetup` returns a set-up ticket. `RUN_ELSEWHERE` looks at `SET_UP` holds only. `OfferAddress` with a preview ticket puts a `PREVIEW` hold back when there is none, and never replaces a `SET_UP` hold (nor, as for every ticket, a hold with another target). A set-up ticket ranks as `RunSetup` does: `OfferAddress` with one replaces a `PREVIEW` hold of any target with its `SET_UP` hold, so someone with the link cannot keep a lost hold from coming back by running `CheckSetup`, and `HandoffStatus` with one treats a `PREVIEW` hold as no hold and answers `UNKNOWN`.
- **Caps.** At most 5 `PREVIEW` holds per client IP address (the address of [Connect limits](#connect-limits)) and 1,000 in all. Over a cap, `CheckSetup` answers as it does without the reach check: no hold and no ticket. The page then shows the "couldn't check" answer below at once.
- **The engine on `PREVIEW`.** `CollectAddress` returns the address and the hold's `phase`. On `PREVIEW` the engine runs its own address checks and the probe with a wrong password ([The engine and a connect-only code](setup-from-laptop.md#the-engine-and-a-connect-only-code)) and calls `ReportReach`, and nothing else: it does not clear `awaitingAddress`, write a credential or leave `SETUP_PENDING`, and `status` and the next steps show nothing of the address (`status` reports `SETUP_NOT_RUN` as before the address came). An address that fails the shape rules is not reported, and the engine never reports on a `SET_UP` address. The engine keeps collecting, and when the address changes it checks, probes and reports again. On `SET_UP` it goes on as [The engine and a connect-only code](setup-from-laptop.md#the-engine-and-a-connect-only-code) says: probe, ask the person, log in only after yes.
- **Polling.** The engine polls `CollectAddress` every 15 seconds while it waits for an address or is `DATABASE_UNREACHABLE_FROM_BOT`, for the first 2 hours after the code was made, then every 5 minutes until the code expires (24 hours after it was made), and at once on `status`. So Vault sees a waiting engine's polls until its code expires, whether or not the link is opened; the page's disclosure and [What the connect service sees](#what-the-connect-service-sees) say so. This replaces today's cadence ([Collecting](setup-from-laptop.md#the-engine-and-a-connect-only-code)).
- **`ReportReach`** (the engine): `setupId`, `enginePublicKey`, `time` (RFC 3339 UTC, whole seconds), `address` in its canonical form (the host in lowercase, the port in decimal without leading zeros, the database as given, the Supabase ref in lowercase or empty), `result` (`REACHABLE`, or `UNREACHABLE` with a `reason`) and `signature`. Reasons: `ADDRESS_REFUSED` (the host resolves to an address the engine never connects to), `NO_ROUTE` (no address of the server accepted a connection), `TLS_NOT_VERIFIED` (the server answered without TLS, or with a certificate that does not verify for the host name), `TIMEOUT` (no answer in time). `REACHABLE` means a probe passed: the server answered and its certificate verified. `reason` is empty with `REACHABLE`.
- **Its signature.** ECDSA P-256 by the engine's signing key, as for `CollectAddress`, over the UTF-8 bytes of `basalt-connect-reach.1\n` + `connect.basaltvault.app` + `\n` + `setupId` + `\n` + the setup fingerprint as printed + `\n` + `time` + `\n` + host + `\n` + port + `\n` + database + `\n` + Supabase ref + `\n` + `result` + `\n` + `reason`, with nothing after it: the collect context's lines, then the canonical address and the result. An absent Supabase ref and the reason of a `REACHABLE` report are empty lines, so such bytes end with `REACHABLE\n`. For the setup code `01a1f78c-52b8-7c3a-9f00-0000000000e1` of the fixtures, fingerprint `d48b ee66 a1d9 d005 1f63`, signed at `2026-11-20T06:10:15Z`, for `aws-0-eu-central-1.pooler.supabase.com`, port `5432`, database `postgres`, ref `abcdefghijklmnopqrst`, reachable, the signed bytes are the eleven lines `basalt-connect-reach.1`, `connect.basaltvault.app`, `01a1f78c-52b8-7c3a-9f00-0000000000e1`, `d48b ee66 a1d9 d005 1f63`, `2026-11-20T06:10:15Z`, `aws-0-eu-central-1.pooler.supabase.com`, `5432`, `postgres`, `abcdefghijklmnopqrst`, `REACHABLE` and an empty line, joined by `\n`. The same report for `db.example.com`, port `6543`, database `app`, no ref, unreachable by timeout, ends with the lines `db.example.com`, `6543`, `app`, an empty line, `UNREACHABLE` and `TIMEOUT`. The host, database and ref hold no `\n`: the engine reports only an address that passed its shape rules. The context is in [Primitives and encodings](vault-channel.md#primitives-and-encodings); the engine's test vector comes with the engine's support.
- **How the service checks it**, in the order of `CollectAddress`: `time` (`CLOCK_SKEW`), the hold for the `setupId`, its engine key, the signature, then the limit ([Connect limits](#connect-limits)). The other failures answer `HANDOFF_UNKNOWN`, and so does a `result` or `reason` outside the values above, or a `reason` with `REACHABLE` or without `UNREACHABLE`. It keeps, for the hold's current address, the newest report by `time` (a later arrival wins a tie), and ignores a report for another address or an older one, answering it as accepted. A hold made again by `CheckSetup` or `RunSetup` starts with no report. It is the bot's own report: a bot that lies only misleads about itself.
- **`HandoffStatus`** returns, with `state`, the hold's `phase` and `reach`: the report the service kept, when the ticket's address matches the hold's (compared in the canonical form, on the service). As for every ticket, a hold with another target answers `UNKNOWN`.
- **The page.** After `CheckSetup` returned a preview ticket, the page shows `Checking your database…` with three lines: `Signed in to the database ✓`, `Found <N> tables ✓` and `Can <bot> reach it?`, with `Takes up to a minute. Your bot only tests the connection; it can't sign in yet.` It calls `HandoffStatus` every 5 seconds with the preview ticket (on `UNKNOWN`, `OfferAddress` once), for up to **60 seconds**. `REACHABLE`: `✓ <bot> can reach it`, and the page goes on. `UNREACHABLE`: `<bot> can't reach this database`, with the text of the reason, and **Paste another string**: `NO_ROUTE` and `TIMEOUT` say to use Supabase's Session pooler string; `TLS_NOT_VERIFIED` says the database's certificate could not be verified from the bot's server, and to use the pooler string or a host with a valid certificate; `ADDRESS_REFUSED` says the address is private and the bot's server will not connect to it. No report within 60 seconds, or no ticket: `Couldn't check whether <bot> can reach it. Tell <bot> "check your status" in the chat, then retry.`, with **Retry** and **Go on anyway**.
- **Probes.** The probe on `SET_UP` reuses a passed `PREVIEW` probe only for the same resolved IP address within 5 minutes; otherwise it resolves and probes again. One flow leaves at most two probes' failed logins in the server's log.
- **What it gives away.** The bot learns, and silently probes, the address of a database someone pasted before approving, and that server sees the bot's outbound address. Someone else with the link and a database of their own can cause that too, and can replace the person's `PREVIEW` hold so that their reach check reads "couldn't check". The confirmation in the chat is unchanged, and is what protects the person ([Controls](setup-from-laptop.md#controls)).

### Tables on the connect page

Planned. The person may untick tables, never add one.

- **Only for `allTables` `INSTALL` codes.** The page shows ticks for an `INSTALL` code with `allTables`, connect-only or not, and `RunSetup` then requires `includedTables`: the tables left ticked, schema-qualified (`public.users`), each from `CheckSetup`'s `tables`. An empty list is `NO_TABLES`; proto3 JSON cannot tell an empty list from a missing one. For a code with `write` and `read`, and for an `AGENT` code (a recovery code included), the page lists the tables without ticks and `includedTables` must be empty (`ANSWERS_INVALID` otherwise).
- **The entries.** Each is a plain lowercase `schema.table` in a schema of `allTables`, at most once; anything else is `ANSWERS_INVALID`. `RunSetup` stands alone and cannot know what `CheckSetup` showed, so an entry of that form that the listing in the setup transaction does not have (a table dropped, renamed or owned by another role since, or one that never was) is `TABLES_CHANGED`, and the page lists the tables again. A table made since is not included.
- **What it grants.** Exactly the included tables, as `allTables` grants its tables: write access, or read access for a table without a primary key ([`allTables`](setup-from-laptop.md#the-setup-code)), with `read only (no row ID)` after it on the page. The row-level security questions are computed for the included tables only, and the page answers `ALL_ROWS` to each of them.
- **Without ticks** (the laptop command, and codes the page shows without ticks), the listing read again in the transaction must be the one read before it, or the setup is refused `TABLES_CHANGED` (today `SETUP_FAILED`), nothing changed.

### Column labels on the connect page

Planned. Classes belong to the whole database and every agent ([PII classification](pii-classification.md#pii-classification)). The page lets the person label the columns of the tables the agent will get, on a step they may skip, and never erases a class or lowers one without the person choosing to.

- **Reading.** `CheckSetup` returns `columns`: each ordinary column of the tables the agent will get (the `tables` with `allTables`, else the code's `write` and `read`), read from `pg_attribute` (`attnum > 0`, not dropped), by table and then column order, with its `class`, `entityType` and `phoneRegion` from `basalt_meta.pii_columns`. A column with no row, and every column of a database without `pii_columns` (a fresh database, or a guard older than M5.1), is `UNCLASSIFIED`.
- **The labels.** Blank, **Personal** (`IDENTIFIER` with `EMAIL`, `PHONE` and its country as `phoneRegion`, `PERSON_NAME`, `ADDRESS` or `OTHER`) or **Secret** (`SECRET`). A column with another class (`FREE_TEXT`, `PUBLIC`) shows it as a fixed label with `change`, which offers **Personal** and **Secret** (never Blank, which would erase it). The step says `Labels apply to every bot on this database.` and `Columns without a label aren't masked: <bot> reads them as they are, and they can be sent to its AI provider. They'll be blocked once PII protection ships, until you label them.`
- **`columnClasses`**: only the columns the person changed, at most 500, each with `table`, `column`, `class` (`PUBLIC`, `IDENTIFIER` or `SECRET`: never `UNCLASSIFIED`, which would erase a class, nor `FREE_TEXT`, which the page does not offer), `entityType` (with `IDENTIFIER` only, required), `phoneRegion` (with `PHONE` only, required, `^[A-Z]{2}$`) and `was`: the `class`, `entityType` and `phoneRegion` the column had in `CheckSetup`. `ANSWERS_INVALID`: more than 500 entries, a table outside the included tables (the `includedTables`, else the code's tables), a column the table does not have, a column twice, a class, entity type or region that breaks these rules, any entry or `restPublic` with an `UPGRADE` code, or with a code whose `guard.to` has no `pii_columns`.
- **`restPublic`**: the page's **Mark the rest as not personal**, on purpose: `PUBLIC` for every column of the included tables that has no class in the transaction (no row, or `UNCLASSIFIED`). The page sends it as `PUBLIC` entries of `columnClasses` (with `was` `UNCLASSIFIED`) when all the entries fit in 500, and as `restPublic: true` otherwise. It never changes a column that has a class.
- **Writing.** In the setup transaction, after the grants, as `<prefix>_guard`, as `basalt classify` writes ([PII objects](basalt-meta.md#pii-objects)). For each entry, the class stored now (`UNCLASSIFIED`, with no entity type and no region, when there is no row) must equal `was` in class, entity type and region, or the setup is refused `CLASSES_CHANGED` (someone classified meanwhile), nothing changed. Each entry is then written with `data_type` from the catalog ([Readable columns](pii-classification.md#readable-columns-and-the-fingerprint)), `confirmed_at` now and `confirmed_by` the admin's `session_user`; a row's suggestion, reason and `needs_review` stay as they were. Then `restPublic`, the same way. When anything was written, `pii_catalog` is set to `pii_fingerprint()`, now and the admin's `session_user`, as `basalt classify` does, so a running engine reloads its classes.
- **Unlabeled columns.** Continue writes nothing for a column the person did not label: it stays `UNCLASSIFIED`, warned today and refused from M5.2 until it is labeled. **Skip: decide later** sends no entry and no `restPublic`, and writes nothing.
