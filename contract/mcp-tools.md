## MCP tools

The first release serves exactly these tools (plus the two large-revert tools of owner decision N12-1), and the agent-assisted revert tools `list_runs` (owner decisions N12-R1 and N12-R2) and `request_revert` (N12-R3 to N12-R9), both forms.

| Tool | Milestone | Purpose |
|---|---|---|
| `run_start` | M1 | Start a run with an intent and optional shared `taskId` |
| `query` | M1 | Run one `SELECT`; the engine records the read (M1.5: as a change record, with the rows it saw by version) |
| `write` | M1 | Run one `INSERT`, `UPDATE` or `DELETE` with an intent |
| `run_history` | M1 | The change records of a run |
| `list_pending` | M2 | Held writes waiting for approval, and (LP-1) reverts waiting for the person's signature or for the agent's batches |
| `preview_revert` | M3 | What reverting a change, run or task would restore, and its conflicts |
| `revert_plan` | M3 | Nov 12: the lines of a large revert plan and its progress |
| `apply_revert_batch` | M3 | Nov 12: apply a batch of lines of a large revert plan the person signed |
| `describe` | M4 | The agent's map of the database: overview, search, one table in full |
| `list_runs` | M4.1 | This agent's own runs, newest first, with what each did |
| `request_revert` | M4.1 | Prepare a revert for the person to sign and hand them the link; then wait once for their signature |
| `status` | M4.1 | AE-9. Whether Basalt is ready for this agent, and each problem's next steps; served by the shim when the engine is down |
| `request_plugin` | M4.1 | Simplify for beta (owner sign-off of 21 Nov). Prepare a plugin install or change for the person to approve on the plugin approval page, then wait once for it; or remove a plugin |

`confirm_database` (below): the person's yes or no to the database a connect-only setup reached, before the engine logs in to it.

`status` (AE-9): no arguments. Returns `agent`, `operatedBy` (`PERSON` or `AGENT`), `ready` (no `ERROR` problem), `engine` (`reachable`, `build`, `startedBy`: `HAND`, `MCP` or `CRASH`, why this engine started, from a running engine only; `lastStop`: `{ reason, at }`, from `basalt mcp` when the engine does not answer and its supervisor gave up, with the problem `ENGINE_GAVE_UP` (its message is the reason and, during the 1-minute hold-off after that give-up, when the next try happens)), `guard` (`state`: `OK`, `UPGRADE_AVAILABLE`, `OUTDATED`, `NEWER`, `MISSING`, `UNKNOWN`; `installed`, `build`, `missingBreaking`, `missingNonBreaking`), `pages` (`served`, `url`), `passkeys` (`registered`, `active`, `keys`, `summary`: below), `ledger` (`bytes`, `valuesKeptDays`, `recordsKeptDays`; see [Configuration and status](vault-channel.md#configuration-and-status)), `engineRecord` (`state`, `url`, `recordedAt`, `revokedAt`; same section), `trust` (`host`, `applies`, `profile`, `origin`, `verify`, `rootCount`, `roots`: what verifies the agent's database certificate, from a running engine only; [Trust profiles](trust.md#trust-profiles), with the problems `CERTIFICATE_NOT_VERIFIED`, `TRUST_ROOT_EXPIRING`, `TRUST_PROFILE_REFUSED`, `TRUST_ROOT_CHANGED` and `TRUST_PIN_MISMATCH`) and `crash`, `access`, `plugins` and `problems`, each with `code`, `severity`, `message`, `personMessage` and `nextSteps` ([Next steps](next-steps.md#next-steps)). Served by the engine, and by `basalt mcp` itself when the engine does not answer (then `engine.reachable` is false, `guard.state` `UNKNOWN`, and `operatedBy` comes from the config the shim can read, else `PERSON`; when `basalt mcp` tried to start the engine and could not, it adds the problem `ENGINE_START_FAILED`, whose message is why and the engine log's path, [Next steps](next-steps.md#next-steps)). Also served while the guard is outdated. Read-only; never a secret, and unlike `basalt status` it never names the credential file. Errors: `INVALID_ARGUMENT`, `INTERNAL`; it never answers `UNAVAILABLE`, problems are its result. Three optional fields carry what `basalt crash`, `basalt access` and `basalt plugin check` showed, and are left out when there is nothing to show: `crash` is the newest saved [crash report](crash-reports.md#crash-reports) (`id`, `time`, `version`, `command`, `path` of its file, and `issueUrl`, the pre-filled GitHub new-issue link, its stack cut so the link fits the link budget, and left out when it cannot fit even cut, as with a `linkBudget` under about 1700; nothing is sent); `access` is the tables the agent's role can read and write (`read`, `write`, each at most 200 names, `truncated` when cut), left out when the database cannot be read; `plugins` is each plugin entry served to the agent with its `health` (`READY` or `NOT_READY`, and the `problem` code that says why). None of them is a problem. `passkeys.keys` lists the active passkeys, at most 100, oldest first, each with its `credentialId` and its `checkCode`, computed from the public key in the database ([the passkey check code](connect.md#the-passkey-check-code)); a passkey whose key cannot be read has no `checkCode`. It is left out when no passkey is active, and, with `active`, when the passkeys cannot be read: no code is listed then. `passkeys.summary` is set on every `status` while `setup.state` is `DONE` and at least one passkey is listed, and says in words how many passkeys are registered and the check code of each (and how many codes could not be read), so the person can compare them with the one the setup page showed: a different code, or a passkey they did not create, means stop and remove it. It is left out while a setup is pending, expired or not recorded. With the chat-only operator (design section 9) it also returns `enforcement` and `setup`. `enforcement` is `GUARD_ONLY` when `operatedBy` is `AGENT`, when the engine runs in same-user mode, or when the shim cannot read the config (the agent could use its credential directly; the guard still enforces intent, row limits, holds and signatures), else `ENGINE_AND_GUARD`. `setup` is `{ "state", "setupId", "kind", "expiresAt", "fingerprint" }` (`fingerprint` while pending) with `state` `PENDING` (a [setup code](setup.md#the-setup-code) was made and its setup is not recorded yet), `EXPIRED` (the same, past `expiresAt`), `DONE` (no setup pending; `setupId` and `kind` name the agent's latest recorded setup) or `NONE` (no setup pending and none recorded, or the engine is down and none is pending). A pending `INSTALL` code is the problem `SETUP_NOT_RUN` and an expired one `SETUP_EXPIRED`, both `ERROR`; a pending `AGENT` or `UPGRADE` code is `SETUP_CHANGE_PENDING`, a `WARNING` (the tools keep working; not a connect-only recovery code, which is `SETUP_NOT_RUN`); zero active passkeys stays `NO_PASSKEY`. While an `INSTALL` code is pending or expired and the database refuses the agent's role or has no guard yet, those two problems are left out: they are what the code fixes, and its setup problem is the one to fix. When the database cannot be reached, `status` cannot tell whether the code was used: it reports `DATABASE_UNREACHABLE` and no setup problem (with `setup` still showing the config's code), and the tools answer `DATABASE_UNREACHABLE`, not `SETUP_PENDING`. For a [connect-only code](setup.md#connect-only-setup-codes), `setup` also carries `connectOnly: true`, and `state` is `PENDING` while the engine waits for the address (problem `SETUP_NOT_RUN`), `CONFIRM_DATABASE` once it collected and probed it (`setup.database` names it; problem `CONFIRM_DATABASE`), and `REFUSED` after the person said no (problem `DATABASE_REFUSED`); the problems `DATABASE_UNREACHABLE_FROM_BOT`, `TRUST_ROOT_MISMATCH` ([Pinning from the connect page](trust.md#pinning-from-the-connect-page)), `ADDRESS_INVALID`, `SETUP_NOT_FOUND`, `CLOCK_SKEW` and `ENGINE_AS_ROOT` are in [The engine and a connect-only code](setup.md#the-engine-and-a-connect-only-code).

`confirm_database`: `setupId` and `database` (the pending setup's id and `setup.database`, from `status`) and `answer`, `YES` or `NO`, the person's answer to `The setup points me at <database>. Is that your database?`. Only while `setup.state` is `CONFIRM_DATABASE`, for that `setupId` and that database; anything else is `INVALID_ARGUMENT`, so an answer never confirms a database the person was not asked about. `YES`: the engine writes the agent's credential for that database (first, for a certificate authority the person trusted on the connect page and the engine confirmed, its pin: [Pinning from the connect page](trust.md#pinning-from-the-connect-page)), logs in for the first time and looks for its setup (`state` `CONFIRMED`; then `status` says `DONE` or `SETUP_NOT_FOUND`). `NO`: the engine deletes the address and the agent's password without ever having logged in there (`state` `REFUSED`), and the agent makes a new code. Returns `state`, `database` and `nextSteps`, and on `REFUSED` `personMessage`. The agent never answers for the person. Errors: `INVALID_ARGUMENT`, `UNAVAILABLE`, `INTERNAL`.

`request_plugin` (Simplify for beta, SB-2; [Plugin approval](plugins-approval.md#plugin-approval)): the agent prepares, the person approves on the page, and nothing a plugin gets is decided by the agent. It replaces `basalt plugin`. Served only on an engine that runs as a service ([Plugin approval in service mode](plugins-approval-service-mode.md#plugin-approval-in-service-mode)) and is `operatedBy: PERSON`, to an agent whose OS user is one of the person's (`personUids`); the forms that open an approval also need the engine's [local pages](local-pages.md#local-pages). Anything else is refused, every form, before anything is read or written: `PLUGIN_REFUSED` `AGENT_OPERATED` on an agent-operated engine (plugin changes stay refused there, 18 Nov, until remote installation), `SAME_USER_MODE` on an engine that runs as the person's own OS user (it keeps no plugin entries of its own), `AGENT_NOT_ALLOWED` for an agent of an OS user that is not the person's, and, for install, change and `name` without `remove`, `NO_LOCAL_PAGES` when the engine serves no local pages (the person could sign nowhere: no command takes a pasted plugin code any more). Every entry it writes is an engine-kept entry and requires approval. Four forms, told apart by their arguments; any other mix is `INVALID_ARGUMENT`:

- **Install or change.** `source` (an absolute path on the agent's computer), optional `instance` (default `default`) and `agents`. `basalt mcp` reads the folder as the agent's OS user, exactly as [The upload](plugins-approval-service-mode.md#plugin-approval-in-service-mode) reads a source (the manifest, its `.sig`, every file it lists; no symlink on any path; at most 256 MiB), uploads it over a second connection to the agent's own socket, and forwards the call with the upload in the request's `_meta` (`dev.basaltdb/upload`: `{ uploadId, name, executables }`). The engine takes an upload only when it belongs to the calling agent's own OS user (the peer uid that began it, checked when `PLUGIN_OPEN` takes it): an upload id the client names itself is either its own user's upload, which it could have made anyway, or refused. `basalt mcp` also removes any `dev.basaltdb/upload` the client sent, which keeps the call's meaning plain but is not what the rule rests on. Every refusal of the call drops the upload, so no refused call holds one of the engine's 4 open uploads. The engine never opens the path. It uploads only on a session whose engine said in its hello answer that a person operates it and gave its local page origin; otherwise it forwards the call as it is and the engine refuses it. The engine then runs `PLUGIN_OPEN` for the upload, in process, with the calling agent's OS user as the upload's owner and that user's [scope](plugins-approval-service-mode.md#plugin-approval-in-service-mode) (SM-4). A folder that cannot be read is `INVALID_ARGUMENT`, a manifest that does not parse `PLUGIN_REFUSED` `BAD_MANIFEST`, both answered by `basalt mcp`; an agent the engine refuses the upload to is `PLUGIN_REFUSED` `AGENT_NOT_ALLOWED`, or whichever refusal `request_plugin` itself gives it.
  - **The upload connection.** `basalt mcp` dials the agent's socket again, sends the same hello as its relay connection, then calls two JSON-RPC methods beside MCP's own, one request per line: `dev.basaltdb/pluginUploadBegin` (no params; `PLUGIN_UPLOAD_BEGIN`'s result) and `dev.basaltdb/pluginUploadPart` (`PLUGIN_UPLOAD_PART`'s params and result), then closes it; the whole upload has 2 minutes. The socket admits only the agent's own OS user, as for its tools, and the upload belongs to that user. The engine refuses both methods to an agent `request_plugin` would refuse (`AGENT_OPERATED`, `SAME_USER_MODE`, `AGENT_NOT_ALLOWED`) before anything is written, so an agent the tool refuses cannot hold one of the 4 open uploads. A refusal is a JSON-RPC server error (`-32000`) whose `data` is the tool error (`code`, `reason`, `message`). An engine that keeps no plugins of its own does not serve the methods (`-32601`, method not found): `basalt mcp` then forwards the call without an upload and the engine says why. A call the engine receives with no upload, or with one that is gone (the engine dropped it at a restart), is `INVALID_ARGUMENT`: call again with `source`.
- **A new approval for the installed copy.** `name`, optional `instance` and `agents`: `PLUGIN_OPEN` without an upload (what `basalt plugin enable` did), for a plugin that expired unsigned, was turned off or no longer matches. `NOT_FOUND` when the engine keeps no such entry.
- **Remove.** `name`, `remove: true`, optional `instance`: `PLUGIN_REMOVE` in process: the entry and its copies go, the plugin stops, and every listed agent's approval ends ([How long an approval lasts](plugins-approval.md#how-long-an-approval-lasts)). It returns at once with `state` `REMOVED`. It needs no approval, as removing never widens anything ([Who needs one](plugins-approval.md#plugin-approval)). There is no separate disable: remove, and install again when wanted, which needs a new signature.
- **Wait.** Only `approvalId` and optional `waitForApproval` (0 to 110 seconds, default 90). The engine reads, about once a second, the approval's state as `PLUGIN_LIST` gives it for the entry that holds it, and what the running engine serves, until the engine serves the entry, `READY`, on that approval to every agent it names (`RUNNING`), the approval is no longer open (`ENDED`: expired, replaced by a newer approval, or the entry turned off or removed), or the time is up (`PENDING`, or `APPROVED` when it is signed and the plugin does not run on it yet). It only reads: nothing in it opens, signs or relays anything. An approval no entry holds any more (the plugin was removed, or a newer approval replaced it for every agent) reads `ENDED` when the caller's guard has it (`agent_plugin_approvals`); any other `approvalId` is `NOT_FOUND`. Like the [waiting write](approvals.md#approvals), one wait per turn: a `PENDING` answer after a wait carries the no-repeat steps (A `END_TURN`, then A `CALL_TOOL` with `approvalId` and `waitForApproval: 0` once the person says they approved).

**Agents.** `agents` is the entry's full new list: 1 to 256 of the engine's agents, no repeats. Absent, it is the entry's current agents when the engine keeps it, else the caller alone; it is never every agent. The caller must be in it, and every agent in it must connect to the caller's database (host, port and database name): so there is exactly one approval, opened with the caller's own credential (`requestedBy` is the caller, and the page's "Asked by" is true), and the page lists exactly the agents the plugin will serve. An agent outside that (another database, or the caller left out) is `PLUGIN_REFUSED` `AGENT_NOT_ALLOWED`; one the engine does not have, `UNKNOWN_AGENT`. The entry's `agents` before the change must be within the caller's scope too ([Asking](plugins-approval-service-mode.md#plugin-approval-in-service-mode)). No argument sets `settings`, `config` or `auth`: a change keeps the entry's settings, a new entry has none.

**Results.** One shape for every form ([`request_plugin.json`](../api/mcp/tools/request_plugin.json)): `state`, `name`, `instance`, and as they apply `version`, `agents`, `approvalId`, `expiresAt`, `approvalUrl`, `personMessage`, `links` and `nextSteps`.

- A new approval (install, change or `name`): `state` `PENDING`, `approvalId`, `expiresAt` and `approvalUrl`, the short link `<pagesUrl>/plugins/<approvalId>#s=<secret>` the engine issues for it on its local pages ([Link secrets](local-pages.md#link-secrets)). `personMessage` is the one of [Plugin approval links](plugins-approval.md#plugin-approval-links), and `nextSteps` P `OPEN_LINK`, A `CALL_TOOL` (`request_plugin` with `approvalId`, in the same turn after showing `personMessage`). Only this form carries a link, so only it opens the page by itself on a person-operated engine ([Auto-open](local-pages.md#local-pages)). The link is never handed to an `approval.deliver` plugin.
- A change that only removes agents from an entry that is on ([A narrowing](plugins-approval-service-mode.md#plugin-approval-in-service-mode)): `state` `NARROWED`, the agents it now serves, A `STOP` (tell the person).
- An approval opened and refused after the entry was written (`TOO_MANY_PENDING`, `GUARD_OUTDATED`, `DATABASE_UNREACHABLE`, `UNKNOWN_AGENT`): the `PLUGIN_REFUSED` error with that reason; the entry stays written and withheld, and the `name` form opens the approval later.
- `REMOVED`, `RUNNING`: A `STOP` (tell the person). `APPROVED`: A `CALL_TOOL` `status` (its `plugins` and problems say why the plugin does not run). `ENDED`: A `STOP`, A `ASK_PERSON` (whether to ask again with the `name` form).

Errors: `INVALID_ARGUMENT`, `NOT_FOUND`, `PLUGIN_REFUSED` (reasons in [Next steps per code](next-steps.md#next-steps-per-code)), `UNAVAILABLE`, `INTERNAL`. Like every tool but `status`, it is admitted only while the agent's guard is current.

`preview_revert` (M3): exactly one of `changeId`, `runId`, `taskId`, plus `limit` and `cursor` (no `sort`: lines come in their signed order). The scope is the agent's own: its change, its run, or its own lines in a task it ran in (RS-1); anything else is `NOT_FOUND` before any preview (revert scope, below). Returns `scope`, `scopeId`, the `rows` and `skipped` totals of the whole preview, and one page of lines as objects (see [Revert](revert.md#revert)). It runs the revert on trial and rolls it back; it never reverts. The cursor names the last line of the page by its hash, so a preview whose rows changed between pages is refused with `INVALID_ARGUMENT` (start again). An own scope with nothing to revert is `NOTHING_TO_REVERT` with its AE-8 reason ([Error codes](error-codes.md#error-codes)). A scope of any size can be previewed, within the agent role's statement timeout: a preview that runs out is `QUERY_TIMEOUT` `TIME_LIMIT`, and its next steps give the person `basalt revert ... --dry-run` and `--open`, whose prepare may take 10 minutes.

`revert_plan` (large reverts, N12): `revertId`, optional `pending` (only lines not yet applied), `limit` and `cursor` (keyset on the line number; no `sort`: lines come in execution order). Returns the plan's `status` (`PENDING` until the person signs, `APPLYING`, `APPLIED`, `EXPIRED`), `scope`, `scopeId`, totals `lines`, `restored`, `skipped`, `pending`, `expiresAt` (sign by), `applyBy` (after the signature), `maxBatch` (200), and one page of `items`: `{line, outcome, batch, conflict, sqlState, plan}` with `outcome` `PENDING`, `RESTORED` or `SKIPPED` and `plan` the signed revert line as an object. Only the agent that prepared the revert sees it (`NOT_FOUND` otherwise). A revert of up to 1000 lines is applied in one call and has no plan to page (`INVALID_ARGUMENT`). Revert scope (RS-2, RS-5): `status` also takes `REJECTED` (the person rejected the plan on the signing page; nothing was reverted). For a plan the person widened, the result carries `widened: true` and no `scope`, `scopeId`, `revertUrl` or `links`; its `personMessage` starts "You changed the scope on the signing page; the agent cannot see what you added."; a `PENDING` plan's `OPEN_LINK` step carries no URL (the person signs on the page they widened on, and the call issues no link); and an item's `plan` is absent when its line names a change the agent did not make (`agent_revert_lines.line` is `NULL`). Line numbers, `outcome`, `batch`, `conflict` and `sqlState` stay on every item, so the agent applies a signed widened plan's batches by number.

`apply_revert_batch` (large reverts, N12): `revertId` and `lines`, 1 to 200 unique line numbers from `revert_plan`. Postgres applies those lines only if the person signed the plan, the caller prepared it, it has not expired, and every line is in the plan and still pending; otherwise nothing is written (`REVERT_INVALID`, `REVERT_EXPIRED`). Each line is re-checked with its row locked: a row someone changed after the plan was built is skipped (people win), never overwritten. Returns `revertId`, `batch`, `status`, the plan's totals `restored`, `skipped`, `pending`, and this batch's `items: [{line, outcome, conflict, sqlState}]`. The loop: `revert_plan` with `pending: true` and `limit: 200`, then `apply_revert_batch` with those line numbers, until `pending` is 0. Apply lines in number order: it is the order that worked on trial.

`list_runs` (N12-R1, N12-R2): the calling agent's own runs, read from `agent_runs` and `agent_changes` (no other agent's runs, ever). Arguments `limit`, `cursor` (id-only keyset on `runId`, UUIDv7 so time-ordered), `sort` (`id` or `-id`, default `-id`), and optional `startTime` and `endTime` (RFC 3339) filtering on the run's start: `startTime` inclusive, `endTime` exclusive; `endTime` not after `startTime` is `INVALID_ARGUMENT`. Without them the newest runs come first by `limit` and `cursor`; the agent does not have to ask the person for a period. Each item: `runId`, `taskId`, `intent`, `startedAt`, `lastChangeAt` (absent when the run has no change record), counts `applied` (writes `APPLIED`), `held` (`APPROVAL_PENDING`), `refused`, `reverted` (writes `REVERTED`; a partly reverted write stays `APPLIED`), `reads`, `rowsWritten` (rows of applied and reverted writes, cascades included), and `tables` (the tables it wrote to, at most 10 in name order, `tablesTruncated` when there are more). Counts and tables come from one aggregate per run over `agent_changes`; a revert's own change record (`op` `REVERT`) belongs to no run and is not counted. Paging by `runId` uses the `runs_agent` index. Listing every agent's runs is not part of this tool: it belongs to the hosted Vault, later.

`request_revert` (N12-R3 to N12-R9): the agent hands the person a revert to sign, with no terminal. An agent can never sign a revert; it can only deliver the person's signature. Two forms, told apart by their arguments:

- **Request.** Exactly one of `changeId`, `runId` or `taskId`, plus `intent` (1 to 500 characters: why the person reverts, as the agent heard it; it is in the binding and on the page). The scope must be the agent's own (RS-1, RS-7): a `changeId` or `runId` of another agent is `NOT_FOUND`, and a `taskId` names a task the agent ran in (it has a run with that task id), of which the revert holds only the agent's own lines; a task it never ran in is `NOT_FOUND` reason `TASK` (revert scope, below). An agent that thinks another agent's run is wrong asks that agent, which decides from its own context and requests the revert of its own run. The engine prepares the revert exactly as `basalt revert` does (`basalt_meta.prepare_revert` with the agent credential, with the statement timeout lifted to 100 seconds for that call only, so the MCP call stays in the client's foreground; a prepare that runs out is `QUERY_TIMEOUT` reason `TIME_LIMIT`, and its message gives the person's `basalt revert --agent <name> --<scope> <id> --open` command, whose prepare may take 10 minutes; there is no background prepare), issues the revert's short link ([Link secrets](local-pages.md#link-secrets)), and returns at once with `status` `PENDING`, `revertId`, `scope`, `scopeId`, `intent`, `batched`, the totals `rows` (restored) and `skipped`, `expiresAt`, `revertUrl` and `personMessage`. `waitForSignature`, `reissueLink` and `signature` are refused in this form: the person cannot sign a link before the agent has shown it. `NOTHING_TO_REVERT` when every row would be skipped or the scope wrote none (reasons in [Error codes](error-codes.md#error-codes)). A `changeId` may be a revert's own change of this agent's work: reverting it brings the agent's values back (a redo; [Revert](revert.md#revert), owner decision AE-14), with people still winning and the person still signing.
- **Wait.** Only `revertId` (a revert this agent requested; `NOT_FOUND` otherwise), optional `waitForSignature` (0 to 110 seconds, default 90), `reissueLink` and `signature`. The engine reads the revert's state about once a second until it is no longer `PENDING` or the time is up, and returns the same fields: `APPLIED` with `changeId` (a revert of up to 1000 lines is applied when the person's page relays the signature, M3-2); `APPLYING` for a signed large plan, with `changeId`, `applyBy`, `progress` (`restored`, `skipped`, `pending`, `batches`) and `nextSteps` (the `revert_plan` and `apply_revert_batch` loop of [Large plans](revert.md#large-plans), arguments filled in; [Next steps](next-steps.md#next-steps)); `PENDING` when the wait ran out, with nothing reverted; `EXPIRED`. Without `signature` the wait changes nothing: it only reads `agent_reverts`. Without `reissueLink` it issues no link and `revertUrl` is absent (the link already given keeps working); with `reissueLink` on a `PENDING` revert it issues a new one, the old one stops working, and the call returns at once with the new `revertUrl` and `personMessage` (no wait: the person needs the link before anyone can sign), so `reissueLink: true` with `waitForSignature` is `INVALID_ARGUMENT`. A `PENDING` answer after a wait carries the no-repeat `nextSteps` (end the turn, then call once more when the person says they signed), with `waitForSignature: 0` too. It never hands out the long link while the engine serves the pages: the person signs at the short link the agent gave them earlier, which the agent still has (the engine keeps only its hash); if it is lost or the person asks for a new one, the agent calls `request_revert` with `revertId` and `reissueLink: true` for a fresh short link. Only when the engine serves no pages does the step carry a link: the one the request handed over (the long link within the budget, else the hash link; [The request file and pasted blocks](showing-links.md#the-request-file-and-pasted-blocks)). `revertUrl` and `requestFile` stay absent: the agent sent the file with the request. `EXPIRED` says nothing was reverted (or, for a signed plan not finished in time, what was) and that a new request is needed.
- **Delivering the signature.** `signature` is the `basalt-revert.1.` code the revert page shows the person (a revert response, [Lines, binding and codes](revert.md#lines-binding-and-codes)), for when the page cannot relay it: the engine does not serve the local pages, or the person reaches the agent only through a chat and has no terminal. Like `write`'s `approval`, the engine checks the code is for `revertId`, checks it locally against the registered passkeys, and submits it with `apply_revert` as `basalt revert --apply` does; Postgres verifies the passkey signature. A revert of up to 1000 lines is then applied (`APPLIED`); a large plan's signature is recorded and the agent applies it in batches (`APPLYING`). A code for another revert, a bad signature or rows changed since the preview is `REVERT_INVALID`; an expired revert is `REVERT_EXPIRED`. The code is the person's signature over that revert's binding (its id, `rowsHash` and expiry): an agent holding it can submit that exact revert or not, nothing else. With `signature` the call does not wait (`waitForSignature` or `reissueLink: true` with it is `INVALID_ARGUMENT`). A `signature` that does not decode as a revert code (an approval code, for one) is `INVALID_ARGUMENT`; the engine also refuses with `REVERT_INVALID`, before Postgres, a code signed by a passkey that is not registered or was revoked, one that does not verify against the revert's binding, and one for a revert already signed (a replay); `REVERT_EXPIRED` for an expired revert. Reasons, for the [next steps](next-steps.md#next-steps-per-code): `BAD_SIGNATURE` (another revert's code, or one that does not verify), `PASSKEY_REVOKED` (unknown or revoked passkey), `PLAN_FINISHED` (already signed), `ROWS_CHANGED` (Postgres: rows changed since the preview), `NOT_SIGNED` or `NOT_FINISHED` for `REVERT_EXPIRED`. Postgres checks every code again; nothing is written on any refusal.
- **One wait per turn**, as for the [waiting write](approvals.md#approvals): the agent shows `personMessage`, then in the same turn calls the wait form once. When it returns `PENDING`, its `personMessage` and `nextSteps` tell the agent not to wait again but to end its turn with the link and the expiry; when the person says they signed, a later call with `revertId` returns at once. MCP cannot start a client turn when the person signs, so a finished turn is not woken.
- **Receipt** (VC1-17). An `APPLIED` or `APPLYING` answer of the wait form, after a wait or after delivering `signature`, carries the engine's `receipt` (or `noReceipt`), with the receipt line first in `personMessage` ([Receipts](vault-channel.md#receipts)).
- Nothing in either form signs a revert, and nothing applies one without the person's signature: only their passkey signs, checked inside Postgres; `apply_revert_batch` still runs only lines of a plan the person signed.

**Revert scope on `preview_revert` and `request_revert`** (in part served; owner decisions RS-1 to RS-7, which replace M3-14 and narrow N12-R7; in Postgres, [Revert scope objects](basalt-meta-revert.md#revert-scope-objects)). The agent proposes, the person chooses ([Rescope, widen and reject](revert.md#rescope-widen-and-reject)). Served: every bullet below, including the wait form's `REJECTED` and widened answers and the delivery of a widened revert's signature. Only `select` in the results is planned.

- **Own work only** (served). Both tools take exactly one of `changeId`, `runId` or `taskId` (`request_revert` gains `taskId`, RS-7), and the scope must be the agent's own: its change (`HasChange` on its view), its run (`FindRun`), or a task it ran in (it has a run with that task id in `agent_runs`; any run counts). The engine checks this first, for every scope kind and on both tools, before any guard call; Postgres checks it again ([Revert scope objects](basalt-meta-revert.md#revert-scope-objects)). Another agent's change or run is `NOT_FOUND` reason `CHANGE` or `RUN`; a task the agent never ran in is `NOT_FOUND` reason `TASK`. In a task the proposal holds only the agent's own lines: a row another agent changed later in the task is skipped as `CHANGED_AFTER`. `request_revert`'s refusal of `taskId` and the `NOT_FOUND`-only-when-empty special case of `preview_revert` go.
- **Filters** (served). Both tools gain optional `runs` (only with `taskId`: 1 to 20 of the agent's own runs with that task id) and `tables` (any scope: 1 to 20 `schema.table` names, each a guarded table the agent wrote in the scope). Absent means all. No tool takes `agents`: the engine builds the [scope descriptor](revert.md#the-scope-descriptor) itself, with `agents` = `[the agent's role]`. A filter entry outside the agent's own work (another agent's run, an own run outside the task, `runs` without `taskId`, a table it did not write in the scope) is `INVALID_ARGUMENT` reason `SCOPE_FILTER`; the message names each refused entry with one fixed text per kind, so another agent's run id reads exactly like an unknown run id, and a table that does not exist, is not guarded, or was not written by the agent in the scope reads "`<table>` has no change of yours in this scope". More than 20 runs or tables is `SCOPE_FILTER_CAP`. Filters that leave no line are `NOTHING_TO_REVERT` with the AE-8 reason for what is left.
- **Results.** Planned: both tools' results gain `select`, the normalized descriptor. Served: `preview_revert` of an own task is `PREVIEW_TASK` with the new steps in [Next steps per code](next-steps.md#next-steps-per-code); its `personMessage`, and `request_revert`'s for a task, always add "You can include other agents' changes in this task on the signing page.", the same sentence whether or not anyone else wrote in the task. An own task with nothing to undo is `NOTHING_TO_REVERT` with the AE-8 reason even when other agents' changes could be reverted; its `personMessage` then names `basalt revert --agent <name> --task <id> --open`, which opens the page on an empty proposal for the person to widen (RS-6); the same command is a `PERSON` `RUN_COMMAND` step after the `STOP` ([Next steps per code](next-steps.md#next-steps-per-code), task scope), so with a long `--config` path the message says "the command the agent shows you" in its place.
- **Wait form.** Served: status gains `REJECTED` (with `rejectedAt` and the person's `note` when they wrote one; steps: `STOP`), returned at once once the person rejected it. Served: for a revert the person widened, every answer carries `widened: true` and only `revertId`, `status`, `intent`, `batched`, `rows`, `skipped`, `expiresAt`, `personMessage` (which starts "You changed the scope on the signing page; the agent cannot see what you added.") and, for a large plan, `changeId`, `applyBy` and `progress`: no `scope`, `scopeId`, `select`, lines or link. A widened `PENDING` answer has the `WAIT_ENDED` steps with no URL: the person signs on the page they widened on, and the `reissueLink` step says it resets the revert to the agent's own work. No answer for a widened revert names its scope in `personMessage` (it says "the revert you widened on the signing page"). A step that requests or prepares the revert again (`EXPIRED`, `ROWS_CHANGED`) names the revert's scope kind and id with no filters: a change or run of the agent's, or a task it ran in (the person widens a run at most to its task), so the request covers only the agent's own work and the agent learns nothing it did not have. `APPLYING` keeps the batch loop, by line numbers. `reissueLink: true` on a widened revert resets it to the agent's proposal ([Link secrets](local-pages.md#link-secrets)).
- **Delivering a widened revert's signature** (served). The agent role cannot read a widened revert's binding text, so for `signature` on a widened revert the engine checks only that the code names this `revertId`, the revert is `PENDING` and the credential id is a registered, unrevoked passkey, and leaves the signature check to `apply_revert`, mapping its refusal to the same codes and reasons as today. Those refusals' `OPEN_LINK` steps carry no URL for a widened revert: the agent holds no link to it. When `apply_revert` finds no row to restore in the signed scope (`NOTHING_TO_REVERT`), the engine answers `NOTHING_TO_REVERT` reason `ALL_CHANGED_BY_PEOPLE` when the scope has skipped lines, else `READS_ONLY`, with its own message instead of the guard's detail (which names the scope). What is applied does not change.

**Reverts in `list_pending`** (served; owner decisions LP-1 to LP-3, Nov 13). The person's pending list carries reverts as well as held writes.

- **One list (LP-1).** `list_pending` returns one `items` list. Each item has `kind`: `APPROVAL` (a held write, every field as before) or `REVERT` (below); the schema is a `oneOf` on `kind`, so each kind keeps its own required fields. Items of both kinds are in one order by id (UUIDv7, so by time; `sort` `id` or `-id`, default `-id`) with one cursor. There is no compatibility shim: approval items gain `kind` and nothing else changes for them.
- **Arguments.** `kind` (new, optional): `APPROVAL` or `REVERT`, default both. `status`: `PENDING` (both kinds: waiting for the person), `APPROVED` (held writes only: approved, the agent applies them) or `APPLYING` (reverts only: a signed large plan the agent applies in batches); default all three. `runId` filters held writes by run and lists no revert. `limit`, `cursor`, `sort` and `reissueLink` as before.
- **Which reverts.** The calling agent's own reverts (`agent_reverts`) with status `PENDING` (not expired) or `APPLYING`. An applied, expired or rejected revert is not listed: the wait form of `request_revert` reports it.
- **A revert item.** `kind: "REVERT"`, `revertId`, `status` (`PENDING` or `APPLYING`), `intent`, `rows`, `skipped`, `batched`, `widened`, `createdAt`, `expiresAt`, `headline`, `personMessage`, `nextSteps` (a `PENDING` revert: the person opens the link, then the agent calls `request_revert` with `revertId` and `waitForSignature: 0` once they say they signed; an `APPLYING` one: `revert_plan` with `pending: true`), and when they apply `scope` and `scopeId` (absent when widened), `revertUrl` and `links` (a `PENDING` revert not widened: its long link, or with `reissueLink` a newly issued short link when the engine serves the pages), `applyBy` and `progress` (a signed large plan). `headline` is built from what Postgres returns, never from the agent's text: for a revert not widened "Revert of <scope> <id>[, only <filters>]: N rows to restore, M left as they are (changed after the agent)."; for a widened one only "Revert widened by the person: N rows to restore." with no scope, select, lines or link (RS-5).
- **`reissueLink: true`** issues a new short link for each `PENDING` revert item as for held writes; for a widened revert it first resets it to the agent's proposal (`reset_revert`, as `request_revert` does, [Link secrets](local-pages.md#link-secrets)), so the item then reads as not widened, with the link for the proposal.
- **Notifications (LP-2, parked).** The engine sends the person no notification. The Telegram notifier is parked outside the engine until after M5; notification channels come back later as plugins. The engine still builds a notice when `request_revert` prepares a revert (`REQUESTED`), when it issues a revert link again on the agent's request (`reissueLink: true` on `request_revert` or `list_pending`), and when it holds a write: the agent, the `headline` (as above), the intent, the expiry, the long link and, when the engine serves the pages, the short link; a notice about a widened revert carries only its headline (LP-3). It hands the notice to a notifier that does nothing, the seam a channel plugs into. That internal notice is not what a plugin gets: an `approval.deliver` plugin's notice carries no intent and only the link in the agent's own answer ([Notifier messages](plugins-runtime.md#notifier-messages)).

`write` in M2: two optional arguments, `approvalId` (uuid) and `approval` (an approval response code, below; needs `approvalId`). To apply a held write the agent repeats the same `sql`, `params`, `intent` and `runId` and adds `approvalId`; with `approval` the engine first submits the person's signed approval (the agent relays it; it cannot make one). The `APPLIED` result of a held write carries the engine's `receipt` (or `noReceipt`) and `personMessage`, the receipt line ([Receipts](vault-channel.md#receipts)). A different statement, parameters or run under the approval is `APPROVAL_INVALID`; an approval not yet signed is `APPROVAL_INVALID` with a message saying so. A held write returns `APPROVAL_REQUIRED` with `approval` in the error body; the held change record has status `APPROVAL_PENDING` until it is applied (the record is then replaced by the `APPLIED` one, which carries `approvalId`) or expires (`APPROVAL_EXPIRED`). The ledger keeps the `APPROVAL_PENDING` and `APPROVED` rows either way.

- **Lists** are cursor-paginated (keyset, no offset): arguments `limit` (default 50, max 200, clamped by the handler) and `cursor` (opaque base64url); result `{ "items": [...], "nextCursor": "..." }`, `nextCursor` absent on the last page. Unknown arguments are rejected with `INVALID_ARGUMENT`, never ignored.
- One named params struct per list tool, embedding `pagination.Params`, passed by value through every layer; the same struct backs the CLI flags.
- Agents cannot approve or sign a revert through MCP. Approve and revert need a passkey signature checked inside Postgres. `apply_revert_batch` only runs lines of a plan the person already signed. `request_revert` prepares a revert, waits for the person's signature, and may deliver the person's signed `basalt-revert.1.` code (`signature`), as `write` delivers `approval`; an agent can never sign a revert, only deliver the person's signature.

### Large values

Owner decision of 14 Nov 2026: "make agents' mistakes reversible; if we keep hiding things, it's scary". A value can be far larger than an agent should read in one call: a change whose old and new rows hold 15 MB each, written by the agent itself. The rules split by what the agent does with the value.

- **`query` never shortens.** A row over the result budget is refused with `QUERY_TIMEOUT` `ROW_TOO_LARGE` ([Error codes](error-codes.md#error-codes)), naming the columns and sizes. The agent reads what it asked for, whole, or nothing: it never holds a shortened value it could write back as if it were the real one.
- **The ledger tools mark, they do not fail.** `run_history`, `list_pending` (a held write's `statement` and `params`), `preview_revert` and `revert_plan` read history the agent cannot change, and a large value must not stop the agent from paging it or from applying a signed revert. They replace a large value with a marker and return everything else of the item: ids, cursor, line numbers, op, table, outcome and the other values. A revert never runs from what the agent read: Postgres applies it from the stored rows, so a marker changes nothing about what is restored.
- **Cost.** Both caps below are measured in the budget's own unit, computed in Postgres before anything is read: a value costs the bytes of its JSON text as Postgres prints it (a string with its quotes and escapes, which is what a read of its image carries), plus 6 for every one of those bytes JSON escapes (a control byte, `"`, `\`, `<`, `>`, `&`), plus 128, plus its column's name. An image costs the sum of its values. So the caps bound what the engine is charged, not only the text: 1 000 000 `<` characters cost about 7 MB, not 1 MB.
- **Which values.** In each item, in order (a change record: `statement`, `params`, then each `rowChanges` entry by `seq`, its `key`, `before`, `after`; a revert line: `key`, `now`, `set`):
  1. A single value that costs over **1 MiB** (1 048 576) is left out: its column is absent from its image, never `null`. It is named in `largeValues`.
  2. Then an image (`key`, `before`, `after`, `now`, `set`, the `statement` or the whole `params`) is kept while the item's running cost stays at most **8 MiB** (8 388 608). The running cost counts the image's kept values and the `largeValues` entries of the values left out of it. An image that would take it over is left out whole (absent, never `null`) and named in one `largeValues` entry without `column`, which replaces the entries for its values. The images after it are tested the same way.

  The arithmetic, in the budget's unit:
  - The kept values and their entries cost at most 8 MiB.
  - A whole-image entry costs under 1 KiB. A `run_history` record is an agent change of at most 50 rows, cascades included (a revert's own record belongs to no run, so `run_history` never returns it), so its entries cost under 152 KiB. A revert line has 3 images, so its entries cost under 3 KiB.
  - A revert line's `changeIds` names every change that touched its row, without bound (one counter updated many times). On agent reads a line carries at most its first **100** `changeIds`, with `moreChangeIds` counting the rest; Postgres slices the array before it is read (the read is charged), so the field costs under 6 KiB.
  - The short fields cost under 1 MiB: the record's ids, op, table, outcome, counts and an intent of at most 500 characters, each of at most 50 `rowChanges` entries' own short fields (`table`, `op`, flags, `basedOn`), and a held write's `headline` and `assignedColumns`.
  - Building a link reads the item's request (binding text and lines) once more. Rule 1 below caps that read at **4 MiB** in the budget's unit, and the link fields it produces (`approvalUrl` or `revertUrl`, `links`, a `requestFile` of at most 1 MiB of text) are charged within it. An approval's binding text repeats `statement` and `params`, which is why the cap covers the binding too.

  So an item costs under 14 MiB (8 + 4 + 1 + the entries). Every page fits the 16 MiB budget at `limit` 1, and a `SIZE_LIMIT` ends with a smaller `limit`. The rules depend only on the item, never on the page, so an item reads the same at every `limit`. An image with `largeValues` is not the whole row: never rebuild a row or a write from it.
- **The marker.** `largeValues` ([`large-value.schema.json`](../api/mcp/values/large-value.schema.json)), on a `run_history` record and on each `rowChanges` entry, a `list_pending` held-write item, a `preview_revert` item and a `revert_plan` line's `plan`; absent when nothing was left out. Each entry: `in` (`KEY`, `BEFORE`, `AFTER`, `NOW`, `SET`, `STATEMENT` or `PARAMS`), `column` (the column; for `PARAMS` there is `index`, 0-based, instead; absent when the whole image was left out), `bytes` (the size of the value's text, for the person; the caps use its cost) and `sha256` (lowercase hex of the SHA-256 of that text). A `params` array that has any value costing over 1 MiB is left out whole (one entry per large parameter, with its `index`), so the agent never resends a parameter list with a hole in it. The text of a value: a JSON string's characters in UTF-8 (no quotes or escapes); any other value its `jsonb` text as Postgres prints it; an image, its `jsonb` text; the statement, its text. Postgres computes `bytes` and `sha256` itself (for a string `convert_to(v #>> '{}', 'UTF8')`, else `convert_to(v::text, 'UTF8')`), so the large value never reaches the engine on an agent's call. Shared vectors (a string, an object with numerics such as `1.10` and a large integer, and a value with escapes, each with its `bytes` and `sha256` as Postgres computes them) are in [`api/mcp/values/large-value.json`](../api/mcp/values/large-value.json), with each value's text and its cost in a named column; the engine's tests run them against Postgres, the CLI's cost test and the pages run them too.
- **Requests too large for a link.** A held write's or revert's long link and request file carry its lines whole. The pages decode only what [Format 2](approvals.md#format-2-the-compact-request) allows: the payload, the inflated request and the rebuilt texts each at most 1 MiB. The request file's 4 MiB cap is above that. Every result that hands over or restates such a link (`write`'s hold, `list_pending`, `request_revert`, `revert_plan`) follows these rules:
  1. The engine first measures in Postgres every text the Format 2 request carries: the binding text and the lines, both in the budget's cost unit and as text. When the text is over **1 MiB** or the cost is over **4 MiB**, it reads none of them on the agent's call, and rule 3 applies.
  2. Otherwise it reads them and builds the Format 2 request. It then applies the page's three limits exactly. When any one fails, the request is too large for a long link, a hash link or a request file, and rule 3 applies.
  3. A request too large for a link is handed over only on a short link that can carry it ([The link budget](showing-links.md#the-link-budget), step 1). That means the engine's local pages (no size limit beyond the pages API), or the portal's short link over the Vault when the lines cost at most **15 MiB** in the budget's unit, which counts the 6 bytes a JSON-escaped character takes in the page's response. The page's response over the Vault is at most 16 MiB ([Limits](vault-channel.md#limits)), and the rest of it fits in the remaining 1 MiB. A field that would restate the long link carries the page's address with no fragment (`<base>/approvals/<approvalId>`, `<base>/reverts/<revertId>`), and `personMessage` points to the link already given.
  4. With no such short link, nothing can bring the request to a page: the CLI prints or opens the same long link. The result says so:
     - `write`'s hold is `APPROVAL_REQUIRED` reason `REQUEST_TOO_LARGE`, with the approval's `approvalId` and expiry as for any hold, and no link.
     - `request_revert` is `QUERY_TIMEOUT` reason `REQUEST_TOO_LARGE`. Its message names the prepared `revertId`, which `list_pending` (kind `REVERT`) also lists.
     - A `list_pending` item or `revert_plan` result has a link field with the page's address with no fragment, no `requestFile`, and a `personMessage` and `nextSteps` as for `REQUEST_TOO_LARGE`.
  5. The `REQUEST_TOO_LARGE` `personMessage` depends on the setup:
     - With a local `pagesUrl`: turn on the local pages (`pagesAddr` in `engine.json`, then restart the engine).
     - With the portal: turn on the Vault (`basalt init ... --vault=on`).
     - When the lines cost over 15 MiB, only the local pages carry them. On an engine the person runs, that means a local `pagesUrl` with `pagesAddr`, and a passkey registered for that local origin (a portal passkey does not sign there). An engine that cannot serve them (an agent-operated engine on the portal: local pages need `devLocalPages`) can never get such a hold approved. The message says so plainly: the hold cannot be approved on this setup unless the setup changes, and otherwise it expires.
     - For a revert, in every case, the alternative is a narrower revert (`runs`, `tables`). The agent requests it again with `request_revert`.

     The steps are A `ASK_PERSON`, A `END_TURN`, then A `CALL_TOOL` once the person says they changed the setup. For a revert the call is `request_revert` with `{revertId, reissueLink: true}` (it returns at once; `waitForSignature` is not allowed with it): that item only, so no other revert is reset and no other link replaced. For a hold it is `list_pending` with `{kind: APPROVAL, status: PENDING, runId, reissueLink: true}`; this also gives the run's other pending holds new links, and the agent shows each item's `personMessage` as usual. On the `request_revert` error, a `STOP` comes first: do not retry now. The `ASK_PERSON` text asks the person to tell the agent before opening the revert, since the reissue resets a widened revert. When the person chooses a narrower revert instead, the `ASK_PERSON` step's text tells the agent to request it with `request_revert` and `runs` or `tables`. The setup change is a step for whoever runs the engine (`--vault=on`); there is no `RUN_COMMAND` variant for an agent-operated engine yet, so it stays under `ASK_PERSON`. `request_revert`'s wait form with `reissueLink` on such a revert answers the results case `REQUEST_TOO_LARGE`, not the error. The steps of `list_pending` items, `revert_plan` and `request_revert`'s wait in this case are in the results table ([Next steps per code](next-steps.md#next-steps-per-code), case `REQUEST_TOO_LARGE`).
  6. The held write and the prepared revert stay until they expire. The held write's preview lines count toward the budget only when they are read, so a held `DELETE` of a row with a large value is never refused with `SIZE_LIMIT`.
  7. A hold keeps its preview lines whole, up to **64 MiB** (67 108 864 bytes) of their text in all ([Approval objects](basalt-meta.md#approval-objects)): a held `DELETE` of a row with a large value is held, shown, signed and applied like any other. Over 64 MiB the write is refused with `STATEMENT_REFUSED` reason `HOLD_TOO_LARGE`, and the person is told to make the change themselves or have the agent change fewer rows per write. A guard before version 37 holds a line of at most 64 KiB: the engine refuses a longer one with the same reason, and the message asks the person to update the guard (the setup page's `UPDATE`). No size of a held write's lines is ever `INTERNAL`.
- **The signing pages** (approval and revert). The page holds every value in full and hashes the lines as before. The pages API is not budgeted, and an item this large reaches a page only on a short link: the engine's local pages, or the portal over the Vault up to 15 MiB (above). It takes each value's text out of the line text exactly as given, never parsed and serialized again: the raw slice for a non-string, and for a string the slice with its JSON escapes decoded (its characters, as in the marker), so its hash matches the marker's. A value whose text is over 1 MiB (the page tests the text, not the budget's cost, on purpose: it may show a value an agent saw marked) is shown as "too large to show: <size>, sha256 <hash>" (the size in KiB or MiB with one decimal, the hash in full, as in the marker), with the line "Your signature covers the full value." The person who needs to see it reads it with the CLI (`basalt log`, `basalt revert --dry-run`), which is not budgeted.
- **The CLI** (`basalt log`, `basalt revert`, `basalt approve`) prints values in full: the budget and the markers are for agents only. In the text output, a value that costs over 1 MiB as the marker counts it (so every value an agent sees marked) is followed by `(<size>, sha256 <hash>)`, so the person can match it to a marker; `--json` is unchanged.
- **`describe`** keeps a plain `SIZE_LIMIT` with a smaller `limit`. Its items are catalog data the person wrote, not ledger values; at `limit` 1 only a column or table comment of many megabytes could still be over, which the person wrote; the generic step stands.

### `describe`

M4 (owner decisions D-1 to D-7). The agent's map of the database. It reads only the catalog and statistics counters: never a row, never a sample value (no `pg_stats` most-common values or histograms). It takes no SQL and no filter on data, and it is not `EXPLAIN`. Every result carries `form`: `OVERVIEW`, `SEARCH` or `RESOURCE`. At most one of `query` and `resource` may be given; both is `INVALID_ARGUMENT`, as is a malformed `resource`, a `query` outside 1 to 100 characters, or a cursor that no longer matches.

- **`OVERVIEW`** (`describe()`): `store` (`{ kind: POSTGRES, database, host }`: the name and host of this agent's own database, never a user, port, password or credential, and never another agent's database), `fingerprint` (the catalog fingerprint), `counts` (`schemas` and `tables` the agent can see, tables including views, materialized views and partitioned parents, and `notGranted`, the tables in user schemas it cannot read), `limits` (`readRowLimit`, `statementTimeoutMs` and `writePolicy`: up to 10 rows allowed, 11 to 50 held for approval, over 50 refused, every `DELETE` held, cascaded rows counted). Up to 50 visible tables: `resources`, one line per table (the search item below). Over 50: `schemas`, one line per schema with its table count, and the result case `OVERVIEW_LARGE` (a `CALL_TOOL` step: search). `schemas` lists at most 50 schemas, the ones with the most visible tables first (ties by schema name), so the answer stays small whatever the number of schemas (D-3, one schema per tenant); when more than 50 schemas are visible, `otherSchemas` (`{ schemas, tables }`) counts the schemas left out and the visible tables in them, is absent otherwise, and the `OVERVIEW_LARGE` step's `describe` query (the largest schema) is how the agent reaches them: it searches by name. `counts.schemas` is always the full number. With `notGranted` above 0: the result case `NOT_GRANTED`, a `personMessage` with the count and `basalt access`, and no `ASK_PERSON` step, because platform schemas (Supabase's `auth`, `storage`, `realtime`) are ungranted on every project.
- **`SEARCH`** (`describe(query, limit?, cursor?)`): `query` matches case-insensitively against schema, table and column names and table comments; it is a name filter, never SQL. Ranked: exact table name, table name prefix, table name contains, schema name contains, column name, comment; ties by `schema.table`. `items` are `{ resource, kind, estimatedRows, matched, access, comment }`, `matched` one of `table`, `schema`, `column <name>` or `comment`, `comment` at most 120 characters. `limit` default 50, at most 200; cursor-paged with `nextCursor`, like every list. A hidden column's name never matches.
- **`RESOURCE`** (`describe(resource, ifFingerprint?)`): `resource` is `schema.table`, quoted identifiers allowed. Fields, with the catalog each comes from: `kind` (`pg_class`: `TABLE`, `VIEW`, `MATERIALIZED_VIEW`, `PARTITIONED_TABLE`; partitions are folded under their parent); `comment` (`obj_description`); `fields` in column order, each `name`, `type` (`format_type`), `nullable`, `default` (the expression text), `generated`, `comment` (`col_description`) and `pii` (`class` and `entityType` from `basalt_meta.agent_pii_columns`, `UNCLASSIFIED` until M5.1 classifies it); `primaryKey`; `indexes` (`name`, `definition` from `pg_get_indexdef`, `unique`, `partial`, `sizeBytes`, `scans` from `pg_stat_user_indexes.idx_scan`); `foreignKeys`, outgoing and incoming (`direction`, `columns`, the other `table`, `onDelete`, `onUpdate`, from `pg_constraint`); `stats` (`estimatedRows` from `pg_class.reltuples`, `null` when never analyzed; `tableBytes`, `totalBytes`, `seqScans`, `indexScans`, `lastAnalyzed` from `pg_stat_user_tables`); `rls` (row-level security is on, so rows may be filtered); `actions` (what the agent may do, from its grants); `policy` (the write policy as it applies here, only on a guarded table the agent can write, by `INSERT`, `UPDATE` or `DELETE`; `null` on a read-only table and on a table the agent can write through a grant made outside `basalt init`, which the guard does not police); `fingerprint`.
- **Hidden tables and columns (D-1, D-2).** A table the agent cannot `SELECT` is never named, only counted (`counts.notGranted`). A column the agent cannot `SELECT` (column grants) and a column classed `SECRET` are not listed in `fields`; `hiddenFields` counts them. A foreign key whose other table the agent cannot read is not listed; `hiddenForeignKeys` counts them, and `cascadesIntoHidden` counts the unreadable tables a delete here reaches through cascading keys, transitively. An index, primary key or foreign key that touches a hidden column is left out whole and counted (`hiddenIndexes`, `hiddenKeys`, `hiddenForeignKeys`). "Touches a hidden column" includes a column that appears only in an index expression or a partial-index `WHERE` predicate. A column whose default or generated expression names a hidden column (an expression counts the same way) has `default: null` and `expressionHidden: true`.
- **Not found.** A resource that does not exist and one the agent cannot read get the same answer: `NOT_FOUND`, with the steps in [Next steps per code](next-steps.md#next-steps-per-code). The agent cannot use the difference to probe for names. The person's command, `basalt access`, is always a `PERSON` step: it does not resolve through `OPERATOR` to an `AGENT` `RUN_COMMAND`, because its output is exactly the names the agent should not read.
- **Comments (D-4).** `comment` fields hold text written by database users. They are returned as data about the schema, never as instructions, and the tool description says so. At most 500 characters in the resource form, 120 in search items. When the PII proxy (M5.3) runs, comments pass through it like any other result.
- **Fingerprints.** The resource `fingerprint` is the sha256 of the canonical JSON of the resource answer without `stats` and without index `sizeBytes` and `scans` (row counts and scan counters change constantly and must not invalidate a cache), with the PII catalog fingerprint mixed in. The catalog `fingerprint` is the sha256 of one catalog read over every visible table, sorted (each table with its kind, the agent's `SELECT`, `INSERT`, `UPDATE` and `DELETE` rights and its comment, each column the agent can `SELECT` with its type and nullability, each constraint and index definition), plus `notGranted` and the PII catalog fingerprint: it changes on any structural change, grant or table comment and stays the same as rows change. The lines it hashes are never shown. With `ifFingerprint` equal to the current resource fingerprint the result is only `{ form, resource, fingerprint, unchanged: true }`.
- **Visibility is a context rule, not a boundary (D-7).** Hiding names (hidden tables, hidden columns, cascades) keeps them out of the agent's normal path. They are not secret from it: an agent can still find them through `query` on `pg_catalog`, or by running `basalt` on an agent-operated engine. No SQL-guard rule on catalog reads comes with this tool. The tool description says so. A listed column's `type` name or `default` expression may also name another object, a row type or a sequence for example, as Postgres prints it, whether or not the agent can read that object.
- **Recording.** `describe` reads the catalog and statistics only, so like `status`, `list_runs` and `list_pending` it is not recorded in the ledger.
- **Errors.** `INVALID_ARGUMENT`, `NOT_FOUND`, `QUERY_TIMEOUT` (the search ran past the engine's statement timeout), `UNAVAILABLE`, `INTERNAL`. No new codes.
