## Setup page

Persona 1's setup page, served by the engine on loopback, with its install, its Update check and the administrator dialog `basalt init` uses around them. The flow and the jobs are in [Setup](setup.md#setup).

### The local setup page

Persona 1. The engine serves the setup page on its loopback listener, at the same origin as its approval and revert pages, so the passkey it registers signs there.

- The admin connection string travels from the page to the engine over loopback. The engine, which runs as its own OS user, uses it once for the job's transaction and never writes it to a file, a log or the engine config. It refuses the admin string on every route but the setup page's own.
- The listener keeps the `websec` Host, Origin and header checks of the other local pages.
- **An engine with no config.** On a first install the [administrator dialog](#the-administrator-dialog) starts the service before `engine.json` exists. A service engine (started as its own OS user from the system config path) that finds no `engine.json` does not exit: it serves only `GET /healthz`, the setup page and the two setup routes below on `127.0.0.1:8787` (origin `http://localhost:8787`), and waits. When the first install writes `engine.json`, the engine loads it and serves the agent without a restart. Under `--supervise` this counts as up, so the supervisor never crash-loops on a missing config. When `127.0.0.1:8787` is taken, it exits `1` and names the port and how to find the process, as the [listener](local-pages.md#local-pages) does. Any other config error still stops it with exit `1`.
- **An engine with a config.** A person-operated engine that runs as its own OS user and serves its local pages at `http://localhost:8787` serves the same page and the same two routes there, and `doctor`, for the `UPDATE`, `REMOVE` and fix jobs of the agents in its `engine.json`. It never runs an `INSTALL` (`JOB_UNAVAILABLE`): it loads `engine.json` only when it starts. An agent-operated engine, or one started as root, refuses every setup request `JOB_UNAVAILABLE` without reading it; the jobs themselves refuse root as well.
- **The link.** `basalt init` prints `http://localhost:8787/setup/#1.<b64url(json)>`, with `{ "job", "agent", "osUser", "demo" }`: `job` `INSTALL`, `UPDATE`, `REMOVE` or `CHANGE`, `agent` the `--agent` name (default as `basalt init` picks it), `osUser` the OS user `basalt init` runs as (the agent's), `demo` whether `--demo` was given (always `false` for `UPDATE`, `REMOVE` and `CHANGE`). The fragment never reaches a server or a log. It is not a secret ([Holding the link is not enough](setup.md#setup-jobs)). The page shows the job, the agent and its OS user before anything is asked. The agent writes the link, so the person confirms `osUser` on the page: it is the OS user the agent runs as and the one the agent's socket admits.
- **Jobs.** `INSTALL` for an engine with no config; `UPDATE` (the [guard update](setup.md#setup-jobs)), `REMOVE` (Remove Basalt), and the fixes of [The Update check](#the-update-check), `LABELS`, `TRUST`, `PASSKEY_ADD` and `PASSKEY_REMOVE`, for an agent of an engine with a config. An `INSTALL` with `demo` sets up the sample database; one without `demo` is the [install of a real database](#the-install-of-a-real-database), with its tables, PII classes, passkey and certificate pin, and the engine refuses it with no table `NO_TABLES`. `basalt init` without `--demo` prints that `INSTALL` link.
- **Which link `basalt init` prints.** On an engine with no config, the `INSTALL` link. On an engine with a config (its setup routes answer `JOB_UNAVAILABLE` to an empty request), plain `basalt init [--agent NAME]` prints and opens the `CHANGE` link, with no new flag and no `basalt mcp` line; `--demo` is ignored there. `CHANGE` is a link only: the page opens on [The Update check](#the-update-check), which offers the fixes it found and, under **Update or remove BasaltDB**, Update the guard and Remove BasaltDB; it sends the `job` of the one the person picks. Nothing runs before a pick, and a request with `job` `CHANGE` is refused `INVALID_ARGUMENT`. Before it opens the admin-string field, the page of an `UPDATE` or `REMOVE` link sends `check` for the link's job with an empty `databaseUrl` (a `CHANGE` link sends `doctor` instead, [The Update check](#the-update-check)): the engine checks the agent and its OS user before the admin string, so `CONNECTION_STRING_REFUSED` means the agent is this engine's, and any other refusal is shown instead of the field (an agent `engine.json` lacks says to run `basalt init --agent NAME`). While a check or a run is in flight the choice is locked; a pick changed after a check drops that check's answer and clears the typed database name.
- **The `UPDATE` link in next steps.** An engine that serves these jobs gives each agent's `GUARD_OUTDATED` and `GUARD_UPGRADE_AVAILABLE` steps the agent's own `UPDATE` link (`{ "job": "UPDATE", "agent", "osUser" from engine.json, "demo": false }` at its origin) as a P `OPEN_LINK`, in place of the agent's `basalt init` step ([Next steps](next-steps.md#next-steps)). An engine that does not serve them keeps the `basalt init` step.
- **Removing the engine service.** After opening the `CHANGE` link, `basalt init` polls the engine for 90 seconds: `ENGINE_REMOVED` runs the removal script below, else it exits `0`. A `REMOVE` that deleted `engine.json` (the engine's last agent) answers `engineRemoved` `true`, and the page says `Last step: ask your agent to finish removing BasaltDB. Your computer asks for your password once.` From then on the engine answers every setup request `ENGINE_REMOVED`, and the fix steps of its agents' failing calls and `status` (`CREDENTIAL_REJECTED`, `GUARD_MISSING`, `GUARD_OUTDATED`) are A `RUN_COMMAND` `basalt init`, P `TELL_AGENT`, A `STOP`. `basalt init` on an engine that answers `ENGINE_REMOVED` prints no link and runs the [administrator dialog](#the-administrator-dialog)'s removal script; a closed dialog or no dialog exits `1` and the service stays, and the next `basalt init` asks again. Limit: an engine restarted after the removal (a reboot) has no config and waits for a first install, so `basalt init` then offers an install, and the service stays until the person removes it by hand ([`docs/install.md`](../docs/install.md)).
- **What the engine takes from the request.** `agent` must be a valid agent name and not in `engine.json`. `osUser` must be an existing OS user that is neither root nor the engine's own user, and not in the engine's group. The engine chooses the rest: the prefix `basalt`, the statement timeout `30s`, the agent's password (256 bits, generated in the engine, never in a request or an answer), the credential file `agents/<agent>.url` (mode `0600`, the engine's own user) and the agent's entry in `engine.json` (`operatedBy` `PERSON`, the local pages). For `demo`, it creates the sample schema as [`--demo`](cli.md#basalt-init) says. For `UPDATE`, `REMOVE` and the fix jobs (`LABELS`, `TRUST`, `PASSKEY_ADD`, `PASSKEY_REMOVE`): `agent` must be in `engine.json`, `osUser` must be the OS user `engine.json` gives it, `demo` must be `false`; `UPDATE` and `REMOVE` carry no `answers`, `challenge` or `passkey`, and a fix job carries only the fields [The Update check](#the-update-check) gives it (`ANSWERS_INVALID`). The admin connection string must name the database the agent's credential connects to, compared as [The setup checks](setup.md#the-setup-checks) compare a target (host, port and database, or the Supabase project ref and database), before anything connects with it: another database is `TARGET_MISMATCH`, and a string that names more than one host `CONNECTION_STRING_REFUSED`. A credential the engine cannot read is `SETUP_FAILED`.

| Method and path | Body | Answer |
|---|---|---|
| `GET /setup/` | | The setup page. It reads the job from the fragment |
| `POST /api/v1/setup/doctor` | `agent`, `osUser` | The [Update check](#the-update-check)'s answer. No `databaseUrl`: it reads with the agent's own credential |
| `POST /api/v1/setup/check` | `job`, `agent`, `osUser`, `demo`, `databaseUrl` | `200 { "database", "lines", "sql", "questions", "notes", "passkeyNeeded", "challenge" }`; an `UPDATE` or `REMOVE` answers without `challenge`, with `passkeyNeeded` `false` and no question. It connects with `databaseUrl`, reads and changes nothing. `lines` is the fixed summary, and `sql` the SQL with passwords redacted. `questions` are the row-level security questions (`kind` `ROW_LEVEL_SECURITY`, `table`, `text`, `choices` `ALL_ROWS` or `NONE`). `challenge` has the [passkey challenge](connect.md#the-passkey-challenge)'s fields, made with a key the engine holds only in memory (a restart invalidates it), over the job's fields in place of a setup fingerprint. It is not single-use, so it can be sent again until `expiresAt`. The admin connection string in the same request is what lets a run happen |
| `POST /api/v1/setup/run` | the check's fields, `confirmName` for a `REMOVE`, `answers` (one per question), and, when a passkey is registered, `challenge` unchanged and `passkey` (the [passkey registration response](approvals.md#codes) and an optional `label`) | `200 { "agent", "lines", "warnings", "passkeys", "mcpCommand", "engineRemoved" }`. `lines` says what the install did, such as `demo ready: leads 30, lead_notes 20`. `passkeys` lists each registered passkey's credential id, label and [check code](connect.md#the-passkey-check-code). `mcpCommand` is the `basalt mcp` line the agent registers, empty after a `REMOVE` |

- **Each call stands alone.** `run` repeats every check of `check` and computes the questions itself. It refuses an answer to a question it did not compute, and a question left without one. The page holds `databaseUrl` in memory and sends it with both calls. The engine keeps nothing from `check`.
- **What `run` does.** Before it connects, it checks the challenge's expiry and the passkey as `RunSetup` does. The challenge's binding (the job, the database the server names and the admin string's host) is checked inside the transaction once the server named the database, before any change. Then, in one transaction: the guard install, the sample data for `demo`, the agent role with its password, the grants, the confirmed agent policies, `attach`, and `register_passkey` for a passkey given (RP ID `localhost`, origin `http://localhost:8787`). A passkey is needed when the database has no active passkey for that origin. Without one, `run` is refused `PASSKEY_REQUIRED`. After the commit, the engine writes the credential and `engine.json` and serves the agent. If that write fails, the answer is `500 SETUP_FAILED`: the database part and the agent's credential stay, and running the setup again on the page finishes it. An install that finds the agent's role keeps it only when the engine's own credential for it logs in as that role on that database: the password stays, and the engine writes `engine.json`. Any other role of that name stays `ROLE_EXISTS`: an install never takes over a role.
- **What `run` does for `UPDATE`.** In one transaction: the `basalt_meta` migrations the build has and the database lacks, nothing else (no password, grant, policy or passkey). `check` and `run` refuse a database with no guard (`GUARD_MISSING`), a guard as new as the binary (`GUARD_CURRENT`, `There is nothing to update.`), a guard newer than the binary (`GUARD_NEWER`, telling the person to update BasaltDB on this computer), another prefix (`PREFIX_MISMATCH`), and a database without the agent's role (`ROLE_MISSING`). The engine reads the guard on every call, so the agent is served again without a restart; `lines` says `guard updated in the database <database> from version <from> to <to>`.
- **What `run` does for `REMOVE`.** The person confirms the removal by typing the database's name, as `check` named it in `database`; the page keeps **Remove BasaltDB** disabled until the typed text equals it exactly. The `run` carries the typed text in `confirmName`, and inside the transaction, before anything is planned or dropped, the engine compares it with `current_database()`: a missing, longer than 63 bytes or different name is `ANSWERS_INVALID` (`Type the database's name exactly as the page shows it to remove BasaltDB from it. Nothing changed.`), nothing changed. `confirmName` on a `check`, an `UPDATE` or an `INSTALL` is `ANSWERS_INVALID`. In one transaction (shared with the connect page), the SQL `check` showed, planned again from the catalog: the `DROP POLICY` of each policy named after an agent role or the guard role, `DROP SCHEMA IF EXISTS basalt_meta CASCADE` (which also drops a view or other object of the person's that uses the ledger; `check`'s lines say so), and `DROP OWNED` and `DROP ROLE` for each agent role of the prefix, the group and the guard role; then the sample schema's `DROP TABLE` and `DROP SCHEMA` without `CASCADE` when the demo made it (marked by its comment), in a savepoint, so a view or key of the person's on it keeps the schema (a warning says so) and the rest is still removed. A role that still holds privileges in another database fails the whole run (`SETUP_FAILED`, nothing changed). After the commit the engine removes from `engine.json` the agent, every other agent whose credential connects to the same database, and every agent whose credential it cannot read (and their names from every plugin entry's `agents`), then deletes their credential files; when no agent is left it deletes `engine.json`, so the engine waits for a first install at its next start. The running engine keeps the agents in memory until it stops; their calls fail to log in. If the config write fails, the answer is `500 SETUP_FAILED`, and the same link run again finishes it: on a database Basalt is already gone from, `check` says so and `run` only removes the agents from this engine.
- **The admin connection string.** Only `check` and `run` read `databaseUrl`. Every other route of the listener refuses a body that holds a `databaseUrl` field (`400 INVALID_ARGUMENT`, fixed message). The engine never writes, logs or returns the string or any part of it, and never logs these routes' bodies. Each answer and each refusal message is built from fixed words and from values read from the catalog, never from the string or a driver's message, as [Answers are fixed text](connect.md#setupservice-calls) says for the connect service.
- **Checks.** The routes keep the listener's `websec` Host check (loopback names only), its Origin check (a `POST` must carry `Origin: http://localhost:8787`) and `Content-Type: application/json`, the 16 KiB body limit (256 KiB for the install of a real database, [The body limit](#the-install-of-a-real-database)) and `Cache-Control: no-store`. A wrong `Host` is `400` (the listener's check) and a wrong `Origin` `403`, both before the body is read. One setup run, of any job, runs at a time; another is `409 BUSY`. A call stops at 60 seconds and rolls back (`504 TIME_LIMIT`).
- **Errors.** JSON `{ "code", "message" }`. `code` is a reason from [Connect refusals](connect.md#connect-refusals), with the same meaning; `message` is this page's own fixed text, which names no setup code: `CONNECTION_STRING_REFUSED`, `DATABASE_UNREACHABLE`, `CERTIFICATE_NOT_VERIFIED`, `LOGIN_FAILED`, `PREFIX_MISMATCH`, `ROLE_EXISTS`, `NO_TABLES`, `TABLES_CHANGED`, `ANSWERS_INVALID`, `PASSKEY_REQUIRED`, `CHALLENGE_EXPIRED`, `CHALLENGE_INVALID`, `PASSKEY_INVALID`, `SETUP_FAILED`, `TIME_LIMIT`, `BUSY`, `REQUEST_TOO_LARGE`, `TARGET_MISMATCH` and `ROLE_MISSING`. The local codes are `INVALID_ARGUMENT` (`400`: a bad field, an agent already configured or not in `engine.json`, an OS user refused), `JOB_UNAVAILABLE` (`409`: an `INSTALL` on an engine that already has a config, which `INSTALL` never changes; an `UPDATE` or `REMOVE` on an engine with no config; any job on an agent-operated engine), `ENGINE_REMOVED` (`409`: any request to a configured engine whose `engine.json` a `REMOVE` deleted), and `GUARD_MISSING`, `GUARD_CURRENT` and `GUARD_NEWER` (`409`, `UPDATE` only, above). The fix jobs and `doctor` answer `JOB_UNAVAILABLE` where `UPDATE` does, and add the codes of [The Update check](#the-update-check). A refusal from the database is `409`, unreachable `503`, a refused `Origin` `403`, a wrong `Host` `400`, a wrong content type `415`, a body over the limit `413`.
- **`contract/surface.json`** gains the page `/setup/` with the code that adds `web/setup/`.

### The install of a real database

For the local setup page; the connect page's own version of each part is in [Connect](connect.md#tables-on-the-connect-page). `basalt init` without `--demo` opens it. The page's steps for the tables, the column labels and the certificate reuse the connect page's screens and words. `UPDATE`, `REMOVE` and `CHANGE` are unchanged, and `demo` is unchanged: a `demo` request carries none of the fields below (`ANSWERS_INVALID`).

The job is an `INSTALL` with `demo` `false`, on the same page, the same two routes and the same rules as every setup job: the admin connection string is typed on the page and sent with `check` and `run` only, and the engine never logs or returns it. Everything the engine shows comes from the catalog or fixed words, with the exceptions named below, which are derived from data or supplied by the server: a column's `suggestedClass`, `suggestedEntityType`, `suggestedPhoneRegion` and `reason`, and a certificate's `subject`. One setup run at a time (`409 BUSY`). Each call stands alone.

**What the person decides, in this order on the page.** The database (admin connection string, and the certificate when asked), the tables and the access to each, the column labels (a step the person may skip), the passkey, and one confirmation that shows the SQL.

**New request fields** (`check` and `run`; each is refused `ANSWERS_INVALID` on a `demo`, an `UPDATE`, a `REMOVE` or a `CHANGE`):

| Field | Meaning |
|---|---|
| `schemas` | The schemas whose tables the page lists: 1 to 5 plain lowercase names, each at most once, none of `basalt_meta`, `pg_catalog`, `information_schema` or a name starting `pg_`. Default `["public"]`. |
| `tables` | The tables the agent gets: `[{ "table": "public.users", "access": "WRITE" }]`, `access` `WRITE` or `READ`. Absent on `check` means the listing call (below); absent or empty on `run` is `NO_TABLES`. At most 500 entries. Each `table` is a plain lowercase `schema.table` (`^[a-z_][a-z0-9_]{0,62}\.[a-z_][a-z0-9_]{0,62}$`) in one of `schemas`, each at most once; anything else, or more than 500, is `ANSWERS_INVALID`. An entry the listing in the transaction lacks is `TABLES_CHANGED`. |
| `columnClasses`, `restPublic` | The labels the person set, as [Column labels on the connect page](connect.md#column-labels-on-the-connect-page) defines them (`table`, `column`, `class`, `entityType`, `phoneRegion`, `was`), with the same rules, `ANSWERS_INVALID` and `CLASSES_CHANGED` included. The tables they name must be among `tables`. A `column` is at most 63 bytes with no control character (`ANSWERS_INVALID`). |
| `trustRoot` | The SHA-256 (64 lowercase hex digits) of the certificate authority the person trusted for this database's host, or absent. The page sends the `sha256` of the refusal as received, in lowercase, not the uppercase colon-separated form it displays. |

**The listing call.** `check` with `tables` absent reads the tables of `schemas` and answers `{ "database", "lines", "tables", "excluded", "notes", "passkeyNeeded", "questions": [], "sql": "" }` with no `challenge`: nothing about the install depends on a pick yet. Each entry of `tables` is `{ "table", "canWrite" }`, `canWrite` true when the connected admin role owns the table and it has a primary key ([`allTables`](setup.md#the-setup-code)); a table without one can only be `READ`. `excluded` lists the tables the admin role does not own, with the owner's role name, as `allTables` does, and they cannot be picked. The listing holds at most 500 tables, in schema and name order, and `tablesMore` is true when there are more; the person cannot pick those (a schema with more tables than that is outside this job). A table whose name is not a plain lowercase one (capitals, spaces, quotes) cannot be picked: it is listed under `excluded` with the owner `unsupported name`, never under `tables`. A listing with no pickable table at all is `NO_TABLES`. The page starts each table's access at `WRITE` when `canWrite`, else `READ`. A table the person ticks is picked; an unticked table is never granted.

**The full check.** `check` with `tables` answers as an install does today, with `lines` and `sql` for the picks, the row-level security `questions` for the picked tables (the page answers `ALL_ROWS` to each, as the connect page does, and says so), and the passkey `challenge`; `run` needs one answer per question, as today. It also answers `columns`: each ordinary column of the picked tables (`attnum > 0`, not dropped), by table and column order, at most 500 (`columnsMore` is true when there are more; those get no suggestion and are labeled only through `restPublic`), each `{ "table", "column", "dataType", "class", "entityType", "phoneRegion", "suggestedClass", "suggestedEntityType", "suggestedPhoneRegion", "reason" }`. `class` is what `basalt_meta.pii_columns` stores, `UNCLASSIFIED` for a column with no row and for every column of a database with no guard. The suggestion comes from the engine's classifier ([Suggestions](pii-classification.md#suggestions): name rules, and a sample of up to 1000 non-null values per column read with the admin connection). Each sampled value is cut to its first 256 characters before it is scored, and the whole sampling stops at 30 seconds of the call's 60. A listing of the columns or of their stored classes that fails fails the check (`SETUP_FAILED`), since `restPublic` covers columns the person must see. A column whose sample fails or runs out of time gets no suggestion (the `suggested*` fields and `reason` absent) and `check` still answers; no sampling error reaches the answer. `run` samples nothing and computes no `columns` or suggestions: the labels it writes are the ones the person sent. The sampled values stay in the engine's memory, are dropped when the column is scored, and appear in no answer, log or file. `reason` is the classifier's fixed form (`NAME:email`, `SAMPLE:EMAIL 912/1000`), names and counts only. The page shows a suggestion, and never applies one the person did not accept: a label reaches the database only through `columnClasses` or `restPublic`. **Mark them as not personal** (the choice for the columns the person did not label, as on the connect page) leaves out every unlabeled column the classifier suggests is personal (`IDENTIFIER`) or `SECRET`. The choice is the confirmation: a note under it says how many columns it marks and lists those it leaves out (`Not included, because they look personal:`); when the rest must go as `restPublic` (columns past the 500 listed, or more than 500 labels), which marks those columns too, the note says all unlabeled columns are marked and lists those that look personal, so the person accepts that by choosing it.

**What the challenge binds.** The [passkey challenge](#the-local-setup-page)'s MAC covers, in addition to the job's fields, the database and the admin string's host: the sorted `tables` with their `access`, the sorted `table:choice` row-level security answers the SQL was planned with, and `trustRoot`. `check` takes the answers in `answers` (absent means `ALL_ROWS` for every question, the page's answer) and shows the SQL for them. `check` always issues the challenge, and every `run` of this job carries it unchanged, with or without a passkey: its binding is checked inside the transaction once the database is named, before any change, so a `run` whose picks, answers or `trustRoot` differ from the `check` that made the challenge, or that carries none, is `CHALLENGE_INVALID`. `columnClasses` and `restPublic` are bound too, as one hash of the sorted entries (table, column, class, entity type, region and `was`) and the flag: `check` takes them, so the page calls `check` again with the person's labels to get the challenge it signs, and a `run` with other labels is `CHALLENGE_INVALID`. The transaction still compares each `was` with the database (`CLASSES_CHANGED`). The check's `sql` ends with a comment line saying how many columns the labels write, since a label is data in `basalt_meta.pii_columns`, not a statement.

**What `run` does.** The checks of `check`, then in one transaction, after the database is named and the challenge's binding is checked: read the tables again, refuse `TABLES_CHANGED` (nothing changed) when a picked table is gone, renamed, owned by another role now, or its `canWrite` no longer allows its `access`; install the guard; create the agent role and its grants for exactly the picked tables (`WRITE` tables as write access, `READ` tables as read access); apply the confirmed agent policies for the answered questions; `attach`; write the labels after the grants, as `<prefix>_guard`, as [Writing](connect.md#column-labels-on-the-connect-page) says (`CLASSES_CHANGED` refuses the whole run, nothing changed); register the passkey; and, when `trustRoot` is in force, `basalt_meta.record_trust_pin(host, port, sha256)`. Once the transaction's SQL has succeeded and before `COMMIT`, the engine writes the certificate pin (below), then the credential, then commits, then writes `engine.json`; a pin or credential write that fails rolls the transaction back, so no role is left without its credential. A commit that is known to have failed (fails before it is sent, the server answers with an error, or it turns into a rollback) leaves a pin that was approved and checked, and the engine deletes `agents/<agent>.url` before it answers `SETUP_FAILED`. A commit whose answer was lost has an unknown outcome: the role may exist, and that credential holds its only password, so the engine keeps it and answers `SETUP_FAILED` with `The database did not confirm the setup. Run it again on this page: it finishes if the setup went through, and starts over if it did not.` A run again finds the role and the kept credential (it finishes with them, as for a config write that failed after the commit), or overwrites the file when the role was never made. A rerun never takes a role it cannot log in as (`ROLE_EXISTS`). The passkey, the keep-an-own-role rule, `PASSKEY_REQUIRED`, `500 SETUP_FAILED` and the rest of [What `run` does](#the-local-setup-page) hold as they do for the demo.

**The body limit.** `columnClasses` makes a body larger than 16 KiB. The two setup routes take bodies up to 256 KiB (`413 REQUEST_TOO_LARGE` above it, with the text `The body is over 256 KiB.`); every other route keeps its limit. `columnClasses` has at most 500 entries.

**The database certificate.** The page's version of [Pinning on first use](trust.md#pinning-on-first-use), by the rules of [Pinning from the connect page](trust.md#pinning-from-the-connect-page) with the engine as the one that connects, so there is no second reading to compare.

- **The refusal.** For a host no trust profile covers whose certificate verifies against no authority this machine trusts, the admin connection fails on the certificate before any startup message, so no user name or password was sent. `check` and `run` then read the chain with the handshake alone (`SSLRequest` and a TLS handshake that does not verify the certificate; no startup message, no user name, no password) and refuse `CERTIFICATE_NOT_VERIFIED` with the body `{ "code", "message", "trustRoot": { "subject", "sha256", "expiresAt" } }`, as the connect service does ([Trusting a certificate authority on the page](connect.md#trusting-a-certificate-authority-on-the-page)): the chain's top, `subject` RFC 2253 at most 512 characters (counted in characters, not bytes), with C0 and C1 control characters and bidirectional controls removed (the removal happens before the cut), `sha256` of its DER, `expiresAt` RFC 3339 UTC. A chain from a public authority, a chain that does not verify even against its own top, or a host a profile covers gets the refusal without `trustRoot`. The `subject` is text the database server supplied, so the page shows it as text only, and the engine never logs it. It is the one value in an answer that does not come from the catalog or from fixed words.
- **The page.** It shows the host, the subject, the fingerprint as uppercase hex pairs with colons and the expiry, and asks `Trust it for this host only?`, with the fingerprint stressed over the subject (the person checks the fingerprint against the provider's console); the answer sends `check` again with `trustRoot` set, and `run` carries the same `trustRoot`. Nothing else is sent until the person answers, and **Cancel** drops the admin string.
- **The login.** With `trustRoot` the engine reads the chain again and logs in only when its top has that SHA-256 and the chain verifies against it (`verify-full` against that one certificate, or the chain alone, `verify: ca`, when the server certificate does not name the host), with that certificate as the only root (the system's authorities do not count, nor a root the string or the environment names), so the password reaches only a server that presents it. The login is made with `sslmode=verify-full` and the string's `sslrootcert` removed, whatever mode and roots the string had, and the agent's credential is built the same way: the pin applies with `verify-full` only, so a credential with another mode or root could bypass it. Anything else is `TRUST_ROOT_MISMATCH`, before any login. A `trustRoot` for a host that verifies without it, or that a profile covers, is ignored (it is still bound in the challenge). An admin string that names more than one host has no pin: the refusal carries no `trustRoot`.
- **The pin.** Before the commit, once the SQL succeeded, the engine writes `pin-<host>` in the `trust.d` next to `engine.json` as [Pinning on first use](trust.md#pinning-on-first-use) says, and the agent's credential has `sslmode=verify-full` so the pin applies. A pin that stays after a failed write or commit was approved and checked. A rerun with the same `trustRoot` finds that pin in `trust.d` as its own, records it in the ledger again (the failed run's record was rolled back with it) and goes on; with no `trustRoot`, `check` finds the profile covering the host, which needs none. When a profile other than this same pin covers the host by then, the run writes nothing and is `SETUP_FAILED`.
- **New codes.** `CLASSES_CHANGED` and `TRUST_ROOT_MISMATCH` join the page's list of reasons, with the meaning [Connect refusals](connect.md#connect-refusals) gives them, and `NO_TABLES` now means that no table was listed or picked.

**Passkeys on this job.** Unchanged from the demo install: a passkey is registered in the same request as the admin string and stored in the job's transaction, and the page creates one when `passkeyNeeded`. Adding a passkey to a database that has one, removing one, and labeling an installed agent's new columns are fixes of [The Update check](#the-update-check), not part of this install.

### The Update check

Persona 1. Running `basalt init` again on an engine already set up opens the `CHANGE` link ([Which link `basalt init` prints](#the-local-setup-page)). The page checks first and shows what needs the person, then only the screens that fix it. It replaces `basalt passkey`, `basalt trust` and `basalt classify`. Persona 2's version is [Update on the connect page](connect.md#update-on-the-connect-page).

**The check.** `POST /api/v1/setup/doctor` with `{ "agent", "osUser" }`, checked as `check` checks them (an agent `engine.json` lacks, another OS user: `400 INVALID_ARGUMENT`). It takes no `databaseUrl`: a body with one is refused as on every route but `check` and `run`. The engine reads with the agent's own credential and its own state, so the answer holds only what the agent can read through its own role (its readable columns' names, the passkeys' public data in `basalt_meta.agent_passkeys`) and what the engine knows itself (its pin and the certificate the host presents). It changes nothing and is not a setup run (`BUSY` does not apply). The page sends it when it opens and again after each fix. Limit: the caller is not authenticated (Host and Origin can be forged on loopback), so a program on this computer can ask for any agent of the engine and read that agent's database name, unlabeled column names and passkey labels and dates. None of it is secret and none of it lets the caller change anything; an engine serves one person's agents.

| Field | Meaning |
|---|---|
| `database` | `current_database()` as the agent reads it; absent when the engine could not log in |
| `guard` | `state` `CURRENT`, `OUTDATED` (with `from` and `to`), `NEWER` or `MISSING`, read as `status` reads it |
| `certificate` | `state` `OK`, `CHANGED` or `MISMATCH`. `CHANGED` is `status`'s `TRUST_ROOT_CHANGED`: the host is pinned and presents another chain top, read with the TLS handshake alone; it carries `host`, `port`, `pinned` (the pinned SHA-256) and `presented` (`subject`, `sha256`, `expiresAt`, as the install's [refusal](#the-install-of-a-real-database) gives them). `MISMATCH` is `status`'s `TRUST_PIN_MISMATCH`: the ledger records another pin for the host and port than the engine's |
| `login` | When the agent could not log in for another reason: `status`'s problem code and its fixed message (`DATABASE_UNREACHABLE`, `CREDENTIAL_REJECTED`, …). Absent otherwise |
| `labels` | `state` `OK`, `UNLABELED` or `UNKNOWN`; `count`, the columns `pii_unclassified()` returns for the agent's role with `why` `NEW` or `UNCLASSIFIED`; `columns`, the first 20 of them as `schema.table.column`, in its order |
| `passkeys` | `state` `OK` when an active passkey has this page's origin (`http://localhost:8787`), `NONE` when none has, `UNKNOWN` when not read; `items`, every active passkey of the database, at most 100, oldest first: `credentialId` (base64url), `label`, `rpId`, `createdAt`, and `lastUsedAt` when it was used |

While the certificate is `CHANGED`, or `login` is set, the engine reads nothing from the database: no credential is sent to a server whose certificate it does not trust. `labels` and `passkeys` are then `UNKNOWN`, and the page shows those rows as `Checked once BasaltDB can connect.` After the certificate fix the page sends `doctor` again and shows the rows read.

**The page.** It shows `BasaltDB / Setup · <database>` at the top.

- **Something needs the person:** `<N> things need you` (`1 thing needs you`), `N` counting the rows below that need an action, and `Everything else is working.`, or `The rest is checked once BasaltDB can connect.` while `labels` and `passkeys` are `UNKNOWN`; then one row per finding, each with a mark and an action:
  - `certificate` `CHANGED`: `Your database has a new certificate`, `BasaltDB stopped connecting until you check it.`, **Check**. `MISMATCH`: `Your database's ledger names another certificate`, `Check it is the one you trust.`, **Check**.
  - `guard` `OUTDATED`: `BasaltDB's guard in your database needs an update`, **Update** (the `UPDATE` job, unchanged).
  - `labels` `UNLABELED`: `<count> new columns have no label` (`1 new column has no label`), the names joined by `, ` (with `…` when `count` is over 20), **Label**.
  - `passkeys` `NONE`: `No passkey can approve on this computer`, **Add**.
  - `login`: its message, with no action: the fix is in the agent's `status`.
  - Rows with nothing wrong show `✓`: `Passkeys`, `<n> devices can approve` (`1 device can approve`; `n` counts the passkeys of this page's origin), **Manage**.
  - **Fix these** walks the rows above in that order. **Update or remove BasaltDB** opens the pick of Update the guard and Remove BasaltDB.
- **Nothing wrong:** `All good`, `BasaltDB is running and your agents can connect.`, and `✓` rows `Every column has a label`, `Database certificate checked` and `Passkeys` (`<n> devices can approve`, **Manage**), then **Update or remove BasaltDB**.

**The admin connection string.** Every fix is a setup job on `check` and `run`, with the admin connection string, as every job is ([Holding the link is not enough](setup.md#setup-jobs)). The page asks for it at the first fix the person starts, not to show the check, keeps it in memory for the fixes that follow, and drops it when the page closes, on **Cancel** and after a refusal of the string (the person types it again). Each fix checks what `UPDATE` checks before it changes anything: the agent and its OS user, the admin string names the agent's database (`TARGET_MISMATCH`), a guard of the agent's prefix (`GUARD_MISSING`, `PREFIX_MISMATCH`) and the agent's role (`ROLE_MISSING`). Each `run` stands alone, repeats its `check`, and runs in one transaction.

**`TRUST`: the certificate.** Two cases, from the check's `certificate.state`. A host no pin covers, or one whose pin verifies and whose ledger records the same pin, is `NOTHING_TO_FIX` (`409`, `There is nothing to fix.`).

- **`CHANGED`: a new certificate.** The install's trust screen ([The database certificate](#the-install-of-a-real-database)), with the pinned fingerprint under the new one as `Was: <fingerprint>`.
  - `check` without `trustRoot` reads the chain with the handshake alone and refuses `CERTIFICATE_NOT_VERIFIED` with `trustRoot` (`subject`, `sha256`, `expiresAt`) and `pinned` (the SHA-256 now pinned). The page asks `Trust it for this host only?`; the answer sends `check` again with `trustRoot`, which logs in as the install's [login](#the-install-of-a-real-database) does, with that certificate as the only root (`TRUST_ROOT_MISMATCH` otherwise). It answers `lines` `This replaces the certificate BasaltDB trusts for <host>.` and `sql` `SELECT basalt_meta.record_trust_pin(<host>, <port>, <sha256 of trustRoot>);`.
  - `run`, with the same `trustRoot`: in one transaction `basalt_meta.record_trust_pin(host, port, sha256)`; once that succeeded and before `COMMIT`, the engine replaces its pin as a pin is written ([Pinning on first use](trust.md#pinning-on-first-use)): the new PEM file, then the profile, then the old PEM file removed, under the config lock; then it commits. A pin replaced before a commit that fails stays: the person approved it and the login checked it.
- **`MISMATCH`: the ledger names another certificate.** The engine's pin still verifies, so nothing is pinned: the fix only records the engine's pin in the ledger.
  - `check` takes no `trustRoot` (one given is `ANSWERS_INVALID`), logs in under the engine's pin, and answers `pinned` (the engine's SHA-256), `recorded` (the SHA-256 of the ledger's latest `TRUST_PIN_RECORDED` for the host and port), `lines` `This records the certificate BasaltDB trusts for <host> in the ledger.` and `sql` `SELECT basalt_meta.record_trust_pin(<host>, <port>, <pinned>);`. The page shows both fingerprints, as uppercase hex pairs with colons: `BasaltDB trusts <pinned>` and `Your database's ledger names <recorded>`, with `If you replaced the certificate yourself, record the one BasaltDB trusts.` and **Record it**.
  - `run`, also without `trustRoot`, logs in under the pin again and calls `record_trust_pin` with the engine's pin in one transaction; it writes no file. A pin that changed between `check` and `run` is `TRUST_ROOT_MISMATCH`, nothing recorded.
- In both, the engine reads `trust.d` for each new connection, so the agent is served again with no restart; `TRUST_ROOT_CHANGED` and `TRUST_PIN_MISMATCH` clear at the next `status`.

**`LABELS`: unlabeled columns.** The install's labels screen ([The full check](#the-install-of-a-real-database)), with the same leave and mark choice, showing only the columns without a label.

- `check` answers `lines`, `sql` and `columns`: each column the agent's role may read (`pii_readable_columns()` with the agent role's privileges, as `pii_unclassified()` filters) whose class is `UNCLASSIFIED` (no row, or a row of that class), in its order, at most 500 (`columnsMore` past that), each with the install's fields and suggestion, sampled with the admin connection under the install's limits.
- `run` takes `columnClasses` and `restPublic` as the install does, with its rules, `was` and `CLASSES_CHANGED`; an entry for a column `check` does not list is `ANSWERS_INVALID`. **Mark them as not personal** marks every listed column but those the classifier suggests are personal or secret, as on the install; `restPublic` marks every column the agent's role may read that has no class in the transaction. It writes as the install writes, deletes the rows of columns that no longer exist (a confirmed class survives a revoked grant, owner decision OR-1), and sets `pii_catalog`, so the engine reloads its classes. **Leave them unlabeled for now** with nothing labeled sends no `run`.
- Labels apply to every agent on the database; the screen says so, as on the install.

**`PASSKEY_REMOVE`: a lost device.** The passkey list (**Manage**): `Passkeys`, `These devices can approve your agents' writes and undos. Remove one you lost.`, then each passkey of `doctor`'s `items`: its `label` and `Added <day month> · used <today | N days ago | N weeks ago | never>`, with **Remove**; one of another origin adds `on <rpId>` (it signs on that site's pages, not this computer's). Under them **Add a passkey on this device** and the note `Removing asks for the database's admin connection string, so it works even if the lost device was your only passkey. If you remove the last one, the page asks you to add one before agents can be approved again.`

- `check` with `credentialId` (base64url of an active passkey; any other is `ANSWERS_INVALID`, `This passkey is not active any more. Nothing changed.`) answers `lines` (`This removes the passkey <label>, added <date>. It can no longer approve writes or sign undos.`, and when no other active passkey has this page's origin, `It is the last passkey for this computer: until you add one, your agents' held writes and undos wait.`) and `sql` (`SELECT basalt_meta.revoke_passkey('\x…'::bytea, true);`). The page asks once, **Remove passkey**.
- `run` calls `basalt_meta.revoke_passkey(credential_id, true)`. It always forces: the admin connection string is what allows it, as it allows removing BasaltDB, so the last passkey can go. The function stays admin only and appends `PASSKEY_REVOKED` with `forced`. A revoked passkey is refused by `_verify_assertion` from then on ([Passkey management](passkey-management.md#passkey-management)). It answers `remaining`, the active passkeys of this page's origin.
- After a removal of a passkey whose `rpId` is `localhost`, the page tells the browser it is gone (`PublicKeyCredential.signalUnknownCredential`, feature-detected; a browser without it is a no-op). With `remaining` `0` it goes to the add screen: `Add a passkey so your agents can be approved again.`

**`PASSKEY_ADD`: a passkey on this device.** `check` answers `lines` and the install's `challenge`, bound to the job, the agent, the database and the admin string's host. `run` carries the `challenge` unchanged and `passkey` (the registration response and an optional `label`), checked as the install checks them, and registers it in one transaction (`register_passkey`, RP ID `localhost`, origin `http://localhost:8787`). It answers `passkeys` with each one's [check code](connect.md#the-passkey-check-code), which the page shows as the install's done screen does. A database may hold any number of passkeys up to the list's 100.

**Codes.** `NOTHING_TO_FIX` (`409`) joins the page's local codes ([Errors](#the-local-setup-page)).


### The administrator dialog

Persona 1. On first install `basalt init` installs the engine as a service under its own OS user, and on removal it removes that service. The agent cannot type a password, so `init` asks through the system's own administrator dialog (`osascript` "with administrator privileges" on macOS, `pkexec` on Linux), which only the person can answer.

- **A fixed command.** The dialog runs a script `init` builds from constants only: create the engine's OS user and the system directories, write the service unit that runs `<binary> engine --config <the system config path> --supervise`, and start it. On removal it refuses while `engine.json` exists, then stops and removes the engine and plugin units (by name prefix), the system directories (after the same walk from `/`) and the OS users the install made; an account that can log in is kept ([Service units](plugins-runtime.md#service-units)). Limit: an engine installed with `service install --user` makes the script stop before it removes anything. `<binary>` is the running binary's own path with every link resolved. No value from the agent reaches it: not `--agent`, not the environment, not the working directory.
- **The binary root runs.** Before it asks, `init` refuses a binary that anyone but root could change: the file and every directory above it must be root-owned and not writable by group or others. The script reaches every directory it writes in from `/` without following a symlink anyone but root controls, and refuses a directory on the way owned by anyone but root or the engine's user, or writable by group or others. So an agent cannot swap the binary in a folder the person's user can write to and have the person's password run it as root. When neither dialog exists (an SSH session, a headless machine), `init` says so and stops. It never falls back to running the engine as the person's user.

**Limit of persona 1.** An agent running as the person's OS user can serve a lookalike `localhost` page that asks for the admin string, or replace a `basalt` binary in a folder that user can write to. That is not new (a terminal prompt has the same exposure) and is not built around. Signing stays safe: Postgres checks the exact origin, port included.
