## Connect

**Target ([Setup](setup.md#setup)).** The connect page is persona 2's one setup path. Besides the first install it also runs the guard update and the removal job for an agent-operated engine, with the same flow: the bot runs `basalt init`, the person opens the link, types the admin connection string, reads the SQL and approves once. There is no other way to run a code ([One setup path](setup.md#one-setup-path)): when Vault is off, down or over a limit, the person tries again later. Connect-only codes are the only codes the bot makes. The address hand-off and the reach check stay: they do not depend on the direct transport.

Served. The [connect page](#the-connect-page) is published on the portal, the connect service runs at `https://connect.basaltvault.app`, and `basalt init --remote` prints [the connect link](#the-connect-link), which the next steps hand over. This section is the protocol of the **connect service**, the only way to run a [setup code](setup.md#the-setup-code): the person opens a link their bot sent, creates a passkey, pastes the database's admin connection string, and approves. The connect service runs the setup code against that database once, with [The setup checks](setup.md#the-setup-checks), and forgets the connection string. A [connect-only code](setup.md#connect-only-setup-codes), made when the person gave the bot nothing about the database, has no `target` and runs only here; the service then holds the database's address until the bot's engine collects it ([The address hand-off](#the-address-hand-off)), and lets the engine test that it can reach the database before the person approves ([The reach check](#the-reach-check)).

**A hosted service, used only at setup.** The connect service is run by Basalt Vault at `https://connect.basaltvault.app`. It is closed source; this section and [`connect.proto`](../api/connect/proto/basalt/connect/v1/connect.proto) are the whole protocol it speaks (as the [Vault channel](vault-channel.md#vault-channel) is for the relay, VC-13). It is used only at setup: while a person runs a setup from the connect page, and while the engine of a connect-only code polls for its address, for up to the code's life plus the 30-minute hold (40 minutes after the code was made) whether or not the link is opened ([The reach check](#the-reach-check)):

- The engine calls it only to collect the address of a connect-only setup ([The address hand-off](#the-address-hand-off)) and to report whether it can reach that address ([The reach check](#the-reach-check)), each request signed by its engine key under its own [signing context](vault-channel.md#primitives-and-encodings). Otherwise `basalt init --remote` only prints a link (below), and nothing is registered anywhere before the person opens it: no registration call and no pending setup stored by Vault.
- It has no accounts and no sign-in. It writes nothing anywhere: no database, no queue, no disk. Each setup call stands alone. It holds a connect-only setup's address (host, port, database, Supabase ref; never the password) in memory for up to 30 minutes: from `CheckSetup`, so the engine can test that it reaches it (a `PREVIEW` hold), and from `RunSetup`, until the engine collects it (a `SET_UP` hold).
- It is not on the data path and has no part in approvals or reverts. After the setup, the engine talks to the person's database as after any setup.
- When Vault is off, down or over a limit, the person tries again later. There is no other setup path for an agent-operated engine ([One setup path](setup.md#one-setup-path)).

The setup itself follows [The setup checks](setup.md#the-setup-checks): the same checks in the same order, the same SQL from the same code (the public setup package in this repository), one transaction, and `basalt_meta.record_setup`. The record does not say that Vault ran it. It also applies, in the same transaction, the tables the person left ticked ([Tables on the connect page](#tables-on-the-connect-page)) and the column labels they set ([Column labels on the connect page](#column-labels-on-the-connect-page)). A parity test runs one code through the setup package directly and through the service, with the page's defaults (every table ticked, no label set), and compares the roles, grants, policies, `basalt_meta` rows and classes.

### The connect link

`https://portal.basaltvault.app/connect#<code>`, where `<code>` is the setup code as `basalt init --remote` prints it. The code is in the fragment, so it reaches the page and not the portal's server. Like an approval link, the link holds everything the page needs; there is no short form.

- **When it is printed.** `basalt init --remote` prints it when the engine's `operatedBy` is `AGENT`, its `vault` is `ON` ([Configuration and status](vault-channel.md#configuration-and-status)), its `pagesUrl` is the portal (not with `devLocalPages`), and the whole link is at most the engine's [`linkBudget`](showing-links.md#the-link-budget) characters. A setup code is at most 1500 characters, so with the default budget of 1800 the link always fits. When it does not fit, init prints the code and says to paste it at `portal.basaltvault.app/connect`. There is no network call either way.
- **Where it is handed over.** In the text output after the code block, and in every `personMessage` that hands the person a pending setup code on such an engine ([Next steps with the connect link](next-steps.md#next-steps-with-the-connect-link)). It follows [Links in `personMessage`](showing-links.md#links-in-personmessage): a line of its own, with a `links` entry labelled `Connect your database`. The message says the link uses Basalt Vault, a hosted service, and that the page asks for the database's connection string, which the bot never needs.
- **The order.** The link is the only way to run the code.

### `SetupService` calls

ConnectRPC, package `basalt.connect.v1`, service `SetupService`. Each call is a `POST` to `https://connect.basaltvault.app/basalt.connect.v1.SetupService/<Method>`. The connect page sends `Content-Type: application/json` with the request's proto3 JSON form and needs no generated client; other clients may use the protobuf form. Field names in JSON are the camelCase forms of the proto's, byte values are base64url without padding, and enum values are SCREAMING_SNAKE_CASE strings. Proto3 JSON leaves out a field at its default value, so an absent field is `false`, `0`, empty or an empty list. The package is `v1`: a breaking change is a new package, and the page and the service ship it together.

| Call | Input | Output | Database |
|---|---|---|---|
| `DescribeSetup` | `code` | `summary`: the decoded code (kind, agent, role, prefix, target (absent for a connect-only code), tables or `allTablesSchemas`, statement timeout, guard versions, expiry), its setup fingerprint, the engine fingerprint when the code carries an engine key, and the summary `lines` of [step 5](setup.md#the-setup-checks) that need no database. `challenge`: [the passkey challenge](#the-passkey-challenge) | None |
| `CheckSetup` | `code`, `databaseUrl`, `trustRoot` ([Trusting a certificate authority on the page](#trusting-a-certificate-authority-on-the-page)) | `questions` (the row-level security question per table, as [step 5](setup.md#the-setup-checks) asks it: `kind` `ROW_LEVEL_SECURITY`, `table`, `text`, `choices` `ALL_ROWS` or `NONE`), `passkeyNeeded`, `notes` (the lines that need the database: the statement timeout now in force, tables outside `public` flagged, the nothing-to-upgrade line), `nothingToDo`, `database` (the database the pasted string names), with `allTables` `tables` (the tables the agent will get), `readOnly` (those of them without a primary key) and `excluded` (each left out, with the role that owns it), `columns` (each column of the tables the agent will get, with its class now: [Column labels on the connect page](#column-labels-on-the-connect-page)), for a connect-only `INSTALL` code `ticket` (the preview ticket, [The reach check](#the-reach-check)), and for a connect-only code `alreadyRan`; for a code with a target, `passkeys` (every active passkey: `credentialId`, `label`, `rpId`, `createdAt`, `lastUsedAt`; [Update on the connect page](#update-on-the-connect-page)); for the confirm step ([The connect page](#the-connect-page)), `currentDatabase` (`current_database()`), `sessionUser` (`session_user`) and `certificate` (`kind` `PUBLIC`, `PROVIDER` or `OWN`, and `issuer`), `alreadyRan` included | Connects and reads. Changes nothing in the database. For a connect-only `INSTALL` code, the service keeps a `PREVIEW` hold |
| `RunSetup` | `code`, `databaseUrl`, `answers`, `challenge` and `passkey` when a passkey is registered, `trustRoot` ([Trusting a certificate authority on the page](#trusting-a-certificate-authority-on-the-page)), `includedTables` ([Tables on the connect page](#tables-on-the-connect-page)), `columnClasses` and `restPublic` ([Column labels on the connect page](#column-labels-on-the-connect-page)) | `warnings`, `passkeys` (each registered passkey's credential id, label and [check code](#the-passkey-check-code)), `nothingToDo`; for a connect-only code, `ticket` (the [hand-off ticket](#the-address-hand-off)) and `reconnected` | Connects and runs the setup in one transaction |
| `CheckRemove` | The connect page's Remove BasaltDB tab ([Removal on the connect page](#removal-on-the-connect-page)). `databaseUrl`, `trustRoot` | `database` (`current_database()`), `bots` (the bot names that lose their access, sorted), `lines`, `sql`, `nothingToRemove`, `sampleSchema` (the sample schema `basalt_demo` is dropped too) | Admin, read in a transaction rolled back |
| `RunRemove` | As `CheckRemove`. `databaseUrl`, `trustRoot`, and `code` from a bot's removal link ([The removal hand-off](#the-removal-hand-off)), else empty. The field `confirmName` (3) of earlier pages is reserved: a request that still sends it is read without it | `database`, `bots`, `lines`, `warnings`; with `code`, `ticket` (the `REMOVED` hold's) | Admin, one transaction |
| `ReportRemoved` | The engine: `setupId`, `enginePublicKey`, `time`, `result`, `reason`, `signature` ([The removal hand-off](#the-removal-hand-off)) | Nothing | None |
| `RevokePasskey` | [Update on the connect page](#update-on-the-connect-page). `code` (a code with a target), `databaseUrl`, `trustRoot`, `credentialId` | `remaining` (the active passkeys of the portal's origin left), `lines` | Admin, one transaction |
| `CollectAddress` | The engine: `setupId`, `enginePublicKey`, `time`, `signature` ([The address hand-off](#the-address-hand-off)) | `address` (`host`, `port`, `database`, `supabaseRef`), `phase` (`PREVIEW`, `SET_UP`, or `REMOVED` for [a removal](#the-removal-hand-off)), `trustRoot` (the certificate authority the person trusted on the page, or empty) | None |
| `ReportReach` | The engine: `setupId`, `enginePublicKey`, `time`, `address`, `result`, `reason`, `signature` ([The reach check](#the-reach-check)) | Nothing | None |
| `HandoffStatus` | The page: `ticket` | `state` (`HELD`, `COLLECTED` or `UNKNOWN`), `collectedAt`, a new `ticket`, `phase`, `reach` (`result`, `reason`, `reportedAt`) and, for a `REMOVED` hold, `removed` (`result`, `reason`, `reportedAt`) | None |
| `OfferAddress` | The page: `ticket` | `state` (`HELD` or `COLLECTED`) | None |

- **Every call stands alone.** `RunSetup` does not rely on `DescribeSetup` or `CheckSetup` having run: it repeats every refusal of both, in the same order, and computes the questions itself. It refuses an answer to a question it did not compute and a question left without an answer (`ANSWERS_INVALID`). The service keeps nothing between the setup calls: the page holds the connection string in memory and sends it with `CheckSetup` and again with `RunSetup`. The one thing it keeps is a connect-only setup's hold, made by `CheckSetup` (`PREVIEW`) or `RunSetup` (`SET_UP`) ([The address hand-off](#the-address-hand-off), [The reach check](#the-reach-check)), which no setup call relies on except for `RUN_ELSEWHERE`, running again and which hold replaces which.
- **What `RunSetup` runs.** Step 6 of [The setup checks](setup.md#the-setup-checks), with the confirmed answers in place of the prompts: the missing migrations, the role, the grants, the confirmed agent policies, `attach`, `record_setup`, and, when the code carries an engine key, `record_engine` with no address (the page asks for none, so a recorded address is kept and no other engine is offered for revoking). When a passkey is registered, `register_passkey` runs in the same transaction, after the migrations, so a failure leaves the database as it was. With `allTables`, the grants and policies cover the tables the listing names, read again in the transaction (no table at all is `NO_TABLES`; a listing that changed since it was shown is refused `TABLES_CHANGED`). For an `allTables` `INSTALL` code they cover the `includedTables` instead ([Tables on the connect page](#tables-on-the-connect-page)), and the column labels are written last ([Column labels on the connect page](#column-labels-on-the-connect-page)). A connect-only `AGENT` code (a [recovery code](setup.md#connect-only-setup-codes)) rotates the password of a role that exists, with the summary's warning for that kind (one that names no tables keeps the role's grants), and runs as an `INSTALL` with ticks when the role does not exist; `ROLE_EXISTS` is unchanged for `INSTALL` codes. After a connect-only code ran, the service holds the address and returns a `ticket` ([The address hand-off](#the-address-hand-off)).
- **A passkey is needed** only when the database has no active passkey registered on the portal, whatever the code's kind. An `INSTALL` on a fresh database therefore needs one, and an `INSTALL` on a database that already has one does not. Then `RunSetup` without `passkey` is refused `PASSKEY_REQUIRED`. With one not needed, a `passkey` given is registered all the same.
- **Nothing to do.** An `UPGRADE` code whose `guard.to` is at or below the installed guard's version: `CheckSetup` and `RunSetup` return `nothingToDo` and the nothing-to-do line of [step 4](setup.md#the-setup-checks) in `notes`, and `RunSetup` changes and records nothing, except an engine key not yet recorded, which it records, and except the certificate it logged in against with a `trustRoot`, which `record_trust_pin` records in a transaction of its own (a changed certificate's `UPGRADE` code). Column labels with it are `ANSWERS_INVALID`.
- **Answers are fixed text.** Every `lines`, `notes`, `text` and `warnings` entry, and every refusal's message, is built from fixed words and values decoded from the code or read from the catalog; none holds the connection string or a database driver's own message. The values the database's server chooses are a refusal's `trustRoot.subject` ([Trusting a certificate authority on the page](#trusting-a-certificate-authority-on-the-page)), at most 512 characters, and `CheckSetup`'s `certificate.issuer` (except a provider's name), at most 128, which the page shows as text only.

### Removal on the connect page

Persona 2. The page has two tabs, Connect a bot (the default) and Remove BasaltDB; the link `/connect/#remove` opens the second, and a bot's removal link `/connect#remove=<code>` opens it with that code ([The removal hand-off](#the-removal-hand-off)). The service runs both calls with `pkg/setup` `CheckRemove` and `RunRemove` (`RunRemoveCode` with a code). Remove needs no setup code and no bot: only the admin connection string, which the page sends as for `CheckSetup`, with the same [connection string rules](#the-pasted-connection-string), [where the runner connects](#where-the-runner-connects) and trust prompt, and the same refusals for them.

- **What it drops.** As the local setup page's `REMOVE` ([The local setup page](setup-page.md#the-local-setup-page)), planned from the catalog of the connected database: the `DROP POLICY` of each policy named after a bot role or the guard role, `DROP SCHEMA IF EXISTS basalt_meta CASCADE`, `DROP OWNED` and `DROP ROLE` for each bot role, the agents group and the guard role, then the sample schema `basalt_demo` when it carries its comment (without `CASCADE`; it stays when another object depends on it, with a warning). The role prefix is the installed guard's (the owner of `basalt_meta`, which must be exactly `<prefix>_guard` with a valid prefix; any other owner is refused `PREFIX_MISMATCH`, nothing dropped, so a schema that is not BasaltDB's never picks the roles to drop), or `basalt` when no guard is installed, so a removal that stopped half way finishes on a second run.
- **The bots by name.** `bots` are the members of the agents group named `<prefix>_agent_<name>`, listed by `<name>`, so the person sees which bots lose their access.
- **The tab's steps.** One box and one press. Paste the admin connection string (the page checks it by itself 400 ms after the box changed, so a paste is one change, and **Continue** stays for typing; the trust prompt when the service offers a certificate authority: its host, subject, fingerprint and expiry, `Trust it for this host only?`, **Trust and continue** and **Cancel**; the confirm step of the other tab is for a setup); then what gets removed: the ledger of every action (`basalt_meta`, deleted for good), the guard's triggers and policies, the bots' access by name, the sample schema when `sampleSchema`, and that the person's own tables and rows stay, with the SQL under a disclosure, and one button, **Remove BasaltDB from `<db>` on `<host>`** (the database `CheckRemove` read and the pasted string's host); then done: `BasaltDB is removed from <db>` with the checklist `✓ Removed from the database <db>`, a line for the bot's computer and `Agent connection: your bot drops it the next time you talk to it.`, and the bots that lost their access. Without a removal link the bot's computer line says the page was not opened from the bot's removal link, so BasaltDB stays there, and to ask the bot to remove BasaltDB; with one it follows [The removal hand-off](#the-removal-hand-off). The connection string is held as on the other tab: emptied from the box once read, dropped after `RunRemove` whatever its answer and on every way back; any refusal goes back to the paste step with its message.
- **Confirmed by the admin login.** As on the local page, the admin connection string is the confirmation: there is no typed name. `confirmName` is reserved in the proto, and a request from an earlier page that still sends it is read without it.
- **One transaction.** `RunRemove` plans again in its transaction and runs the drops there; a failed drop rolls everything back (`SETUP_FAILED`: `Removing BasaltDB failed, for example because one of its roles still has privileges in another database; nothing changed.`). `nothingToRemove` (no guard, no bot role, no sample schema) still lets `RunRemove` run; it drops nothing.
- **No passkey and no bot.** As on the local page, the admin connection string is what allows it. Without a removal link the bot's engine is not told: its role is gone, so its next login fails, and its `status` says so. With one, the engine removes itself ([The removal hand-off](#the-removal-hand-off)).

### The removal hand-off

How an agent-operated engine removes itself from the bot's machine after the person removed BasaltDB from its database on the connect page, with no terminal: chat, one page, done. The person asks the bot to remove BasaltDB; the bot runs `basalt init --remove` ([CLI](cli.md#basalt-init)).

- **The removal link.** On an agent-operated engine with the Vault on, `basalt init --remove` (with or without `--remote`) makes, for the agent whose credential file exists, an `AGENT` code with no change (no verifier, no tables, `guard.from` = `guard.to`) that names the credential's database as `target` and carries `engine`, and records it in the agent's entry of `engine.json` as `"removal": { "setupId", "expiresAt", "code", "fingerprint" }`, next to any pending `setup`, which it keeps. It logs in nowhere. It prints `https://portal.basaltvault.app/connect#remove=<code>` with the code's expiry, and a `personMessage` that says to open it, paste the admin connection string there and press Remove; over the `linkBudget` it prints the code and says the page can then remove BasaltDB from the database only (the Remove tab takes no code), since a code is at most 1500 characters and the default budget 1800, that happens only with a smaller configured budget. An unexpired pending removal is printed again (`reused`). With no credential for the agent it refuses: `BasaltDB is not set up for this agent on this computer, so there is nothing to remove`. A person-operated engine, or one with the Vault off, is refused as for a connect-only code ([Connect-only setup codes](setup.md#connect-only-setup-codes)); a person-operated engine's `--remove` is the local page's.
- **On the page.** The page calls `DescribeSetup` with the code when it opens (so a removal confirmed before the code expired may finish within the 30-minute grace) and names the code's database and host in its heading. A refused code (expired, damaged) is shown, and the tab goes on as a removal from the database only. `RunRemove` sends `code`.
- **`RunRemove` with a code.** Before it logs in, the service decodes the code: it must be live, carry a `target` and `engine` (`INVALID` otherwise: `This link is not a removal link of a bot's computer. Ask your bot for a new one.`). In the removal's run, before anything is dropped, the pasted string must name the code's target (`TARGET_MISMATCH`). After the removal commits, the service keeps a `REMOVED` hold for the code's `setupId`: the code's target as `address`, its engine key and fingerprint, no `trustRoot`, and the 30-minute expiry, replacing any hold of the code. No preview, setup, claim or ticket replaces a `REMOVED` hold; a `REMOVED` ticket offered after a restart replaces a `PREVIEW` or `SET_UP` one. `RunRemove` returns the hold's `ticket`. A `CollectAddress` of a `REMOVED` hold never marks an older link `REPLACED`.
- **The engine.** An engine that runs as the agent's OS user (never as root) with its key loaded, for an agent with a pending `removal`, calls `CollectAddress` for the removal's `setupId` and fingerprint every 15 seconds for the code's life plus the 30-minute hold (40 minutes after the code was made), as long as `engine.json` records that removal. It honours `RATE_LIMITED`'s wait, and keeps waiting on `HANDOFF_UNKNOWN` and any other error. It acts only when all of these hold: the hold is for the removal `engine.json` records now (a hold of an older link, or of another code, is never read: the engine collects only for its own pending `setupId`, signed with its key), its `phase` is `REMOVED`, its `address` is the database the agent's credential names (in the canonical form), and a fresh login with the agent's credential, on a connection of its own, is refused by the database (class `28`, or Supabase's pooler not knowing the user). A login that works removes nothing whatever the service says, so a hold the service made up cannot remove an engine whose role exists; a database it cannot reach removes nothing and the engine tries again at the next poll.
- **What it removes.** A service engine reports `KEPT` `SERVICE` and serves on (its removal job removes it), and one that serves other agents reports `KEPT` `OTHER_AGENTS` and serves on. Otherwise the engine stops serving, closes everything it opened, and only then deletes, never through a link: its config folder `<UserConfigDir>/basalt` (`engine.json`, `agents/`, `trust.d`, and the state and socket folders inside it) when the config is that default one, else `engine.json` and its lock only; its state and socket folders outside it when they are folders of its user; and the agent's credential file and the files init keeps next to it (`.pending`, `.lock`, `.secret`) outside the config folder, each only when it is a plain file of the engine's user with one link (another one stays: `KEPT` `CREDENTIAL_FILE_KEPT`). A deletion that fails is `KEPT` `DELETE_FAILED`. The `basalt` binary stays. It then sends `ReportRemoved` (signed with the key in memory, best effort, 20 seconds at most) and exits `0`, so a supervisor stops too and `basalt mcp` answers `status` `REMOVED` ([Removing the engine service](setup-page.md#the-local-setup-page)).
- **`ReportRemoved`** (the engine): `setupId`, `enginePublicKey`, `time` (RFC 3339 UTC, whole seconds), `result` (`REMOVED`, or `KEPT` with a `reason`: `OTHER_AGENTS`, `CREDENTIAL_FILE_KEPT`, `SERVICE` or `DELETE_FAILED`) and `signature`: ECDSA P-256 by the engine's signing key over the UTF-8 bytes of `basalt-connect-removed.1\n` + `connect.basaltvault.app` + `\n` + `setupId` + `\n` + the setup fingerprint as printed + `\n` + `time` + `\n` + `result` + `\n` + `reason`, with nothing after it (the reason of a `REMOVED` report is an empty line, so such bytes end with `REMOVED\n`). The service checks it in `ReportReach`'s order: `time` (`CLOCK_SKEW`), the hold for the `setupId`, a `REMOVED` one, its engine key, the `result` and `reason`, the signature, then the `ReportReach` limits; the other failures answer `HANDOFF_UNKNOWN`. It keeps the newest report by `time` (a later arrival wins a tie), and `HandoffStatus` returns it as `removed`.
- **The page after the press.** With a ticket the done screen reads `Removing BasaltDB…` and `Removing from the bot's computer…`, and calls `HandoffStatus` every 5 seconds (on `UNKNOWN`, `OfferAddress` once) for up to 120 seconds. `removed` `REMOVED`: `✓ Removed from the bot's computer` and the title `BasaltDB is removed`. `KEPT`: a line per reason (`OTHER_AGENTS`: BasaltDB stays there, serving the other bots; `CREDENTIAL_FILE_KEPT`: removed except the bot's connection file outside its folder; `SERVICE` and `DELETE_FAILED`: ask the bot to call status). No report in time: `The bot's computer: no answer yet. Tell your bot "check your status" in the chat: it says what is left.`
- **An older connect service.** A service without `ReportRemoved` or the hold makes no `REMOVED` hold: the engine never collects one and stays as before, and the page shows the database-only checklist. An engine whose `ReportRemoved` is refused or not served still exits after its removal.
- **What it gives away.** Vault sees the polls of an engine with a pending removal for up to 40 minutes, and the result. Vault is trusted to say the removal happened; the engine's own login check is what makes a false `REMOVED` hold harmless while the agent's role exists. Someone with the removal link and the database's admin string can remove BasaltDB from that database and the bot's machine; the admin string alone already removes it from the database.

### Update on the connect page

Persona 2's [Update check](setup-page.md#the-update-check). The bot runs `basalt init --remote` again; for an agent with a credential that makes a code with a target (`AGENT` or `UPGRADE`, [step 3](setup.md#basalt-init---remote-the-engines-machine)), and the person opens its connect link. The page has no engine to ask, so it checks after the paste, with the admin connection string, and shows the same screens and words as the local page.

- **The check.** `CheckSetup` for a code with a target answers, besides its usual fields, `columns` (for an `AGENT` code the code's tables, for an `UPGRADE` code every column of each table that has a readable column, [Column labels on the connect page](#column-labels-on-the-connect-page)) and `passkeys`. A refusal of the certificate with `trustRoot` comes first, as on every visit ([Trusting a certificate authority on the page](#trusting-a-certificate-authority-on-the-page)). The page then shows the local page's check screen: `<N> things need you` with a row for the unlabeled columns (those whose class is `UNCLASSIFIED`) and for no portal passkey (no `passkeys` entry with `rpId` `basaltvault.app`), and the `Passkeys` row with **Manage**; or `All good`. A changed certificate has no row here: it is the confirm step the page already passed. **Fix these** opens the labels screen with only the unlabeled columns, then the approval.
- **The approval.** `RunSetup` runs the code as always (the migrations of an `UPGRADE` code, the grants of an `AGENT` code) and, in the same transaction, writes the labels the person set (`columnClasses`, `restPublic`, as on the install) and registers a passkey when the person adds one (**Add a passkey on this device**, as `RunSetup` registers one when none is needed).
- **Removing a passkey.** The passkey list is the local page's, with the portal's origin in place of this computer's. **Remove** calls `RevokePasskey` with the code, the admin connection string, `trustRoot` and the passkey's `credentialId`. It runs the checks `CheckSetup` runs for the code (the code is live, the string names its target: `TARGET_MISMATCH`, the guard's prefix: `PREFIX_MISMATCH`), then in one transaction `basalt_meta.revoke_passkey(credential_id, true)`: the admin login is what allows it, so the last passkey can go. A `credentialId` that is not an active passkey is `ANSWERS_INVALID` (`This passkey is not active any more. Nothing changed.`). It answers `remaining`, the active passkeys with RP ID `basaltvault.app`, and `lines`. With `remaining` `0` the page asks the person to add one, and the approval registers it. After a removal of a portal passkey the page calls `signalUnknownCredential` as the local page does ([Passkey management](passkey-management.md#passkey-management)).
- **A changed certificate.** The bot's engine reports `TRUST_ROOT_CHANGED`; `basalt init --remote` makes a code with no change marked `certificateChanged` (`UPGRADE` from guard version 0), the person trusts the new certificate on this page, and the engine replaces its pin only after its own reading matches ([A changed certificate on persona 2](trust.md#pinning-from-the-connect-page)).

### Connect refusals

A refusal is a ConnectRPC error whose detail is a `basalt.connect.v1.Refusal`: `reason` (below), `message` (the fixed message, in the words of [The setup checks](setup.md#the-setup-checks) where they give one) and `retryAfterSeconds` (set when trying again later can work). In the JSON error body, each entry of `details` has `type` `basalt.connect.v1.Refusal`, `value` (the detail's protobuf bytes, base64), and `debug`, the same detail in proto3 JSON, which the service always sends so a page without a protobuf decoder can read it. The error's own `message` is the refusal's message.

| Reason | ConnectRPC code | When |
|---|---|---|
| `NOT_A_SETUP_CODE`, `INVALID`, `UNSUPPORTED_FORMAT`, `DAMAGED` | `invalid_argument` | Decoding, as in [The setup code](setup.md#the-setup-code) |
| `EXPIRED`, `SETUP_ID_IN_FUTURE`, `EXPIRY_TOO_FAR`, `GUARD_TOO_OLD` | `invalid_argument` | Step 1 of [The setup checks](setup.md#the-setup-checks), and `DescribeSetup` on open, by the service's clock. `EXPIRY_TOO_FAR` is an `expiresAt` more than 10 minutes and 5 minutes ahead of the service's clock. `EXPIRED` message: `This link expired. Ask <agent> for a new one.`. Opening and confirming need a live code; `CheckSetup` and `RunSetup` after a confirmed live code do not refuse `EXPIRED` within 30 minutes of `expiresAt` (the grace `record_setup` also allows); after that they refuse it. |
| `ALREADY_USED` | `failed_precondition` | `DescribeSetup` (on open) for a connect-only code the service already holds (the setup ran, or a `SET_UP` hold is in memory). Message: `This link was already used. Ask <agent> for a new one.` |
| `REPLACED` | `failed_precondition` | `DescribeSetup` (on open) for a code the service has superseded, best effort: since its last restart the engine has collected a hold for a newer `setupId` with the same engine public key and agent (a `CollectAddress` whose signature verified). A code is unsigned, so opening, checking or running one alone records nothing, and a crafted code cannot replace a real link. Only connect-only codes have holds, so a code with a target is never refused `REPLACED`. The service keeps this in memory, capped in size, and forgets it when it restarts; the engine sends no notice when it makes a code, and `record_setup`'s `SUPERSEDED` is the rule that holds. Message: `This link was replaced by a newer link. Ask <agent> for a new one.` |
| `BINARY_TOO_OLD` | `unavailable` | `guard.to` is newer than the newest guard the service installs. Message: `Basalt Vault is being updated: try again shortly.` |
| `CONNECTION_STRING_REFUSED` | `invalid_argument` | The pasted string breaks [The pasted connection string](#the-pasted-connection-string) rules. The message names the rule, never the string |
| `ADDRESS_REFUSED` | `invalid_argument` | The host resolves to an address the service never connects to ([Where the runner connects](#where-the-runner-connects)) |
| `DATABASE_UNREACHABLE` | `unavailable` | No connection: an unreachable host, a closed port and a timeout give the same message |
| `CERTIFICATE_NOT_VERIFIED` | `failed_precondition` | The server's certificate does not verify. The message: `The database's TLS certificate could not be verified, so the password was not sent. Use a host with a certificate from a public authority.` For a connect-only code and a host no trust profile covers, with a chain that verifies against its own top, the refusal carries `trustRoot` ([Trusting a certificate authority on the page](#trusting-a-certificate-authority-on-the-page)) |
| `TRUST_ROOT_MISMATCH` | `failed_precondition` | A `trustRoot` that is not 64 lowercase hex digits, or that is not the SHA-256 of the top of the chain the server presents now (or a chain that does not verify against it). The password was not sent. The refusal carries the `trustRoot` presented now, when there is one to trust. Message: `The database presents a different certificate authority than the one you trusted, so the password was not sent. Check it against your provider's console again.` |
| `LOGIN_FAILED` | `failed_precondition` | The database refused the login |
| `TARGET_MISMATCH` | `failed_precondition` | Step 3 of [The setup checks](setup.md#the-setup-checks). Never for a connect-only code, which has no target |
| `RUN_ELSEWHERE` | `failed_precondition` | A connect-only code whose address the service holds for another database, or while a run of the same code for another database is in flight, checked only after the login to the pasted database succeeded ([The address hand-off](#the-address-hand-off)). Message: `This setup code was already used with a different database. If that was not you, someone else has your link: tell your bot to start over.` |
| `PREFIX_MISMATCH`, `USED`, `SUPERSEDED`, `ROLE_EXISTS`, `ROLE_MISSING`, `ENGINE_REVOKED` | `failed_precondition` | Step 4 of [The setup checks](setup.md#the-setup-checks), in its order. For a connect-only code: `USED` is not returned when the code may run again ([The address hand-off](#the-address-hand-off)), and an `AGENT` code with a verifier (a recovery code, or a new password) runs as an `INSTALL` instead of `ROLE_MISSING` |
| `GUARD_UNUSABLE` | `failed_precondition` | Step 4 of [The setup checks](setup.md#the-setup-checks): the database has an older BasaltDB install this version cannot use ([An older install](setup-page.md#the-local-setup-page)), and the setup does not replace it (a guard below the update floor is replaced only by an `INSTALL` code whose caller offers it). Nothing changed. The message is the setup package's fixed text, which links to [Remove an older install](../docs/remove-old-install.md) |
| `TABLES_MISSING` | `failed_precondition` | After step 4: a table the code names is not in the database. The message names the missing tables and the database |
| `NO_TABLES` | `failed_precondition` | After step 4: a code with `allTables` finds no table in those schemas that the admin role owns, or `RunSetup` with an empty `includedTables` for a code with ticks (an `allTables` `INSTALL` code, an `AGENT` code that runs as an `INSTALL` with `allTables` or no tables, or one that names no tables for a role that holds none). For an empty `includedTables` the message is `There is no table to give <agent>. Tick at least one table; nothing changed`. |
| `TABLES_CHANGED` | `failed_precondition` | The tables changed since they were listed: an entry of `includedTables` names a table the admin role does not own now (dropped, renamed or given to another role), or, without `includedTables`, the listing read again in the transaction differs from the one read before it ([Tables on the connect page](#tables-on-the-connect-page)). Nothing changed; the page lists the tables again. |
| `CLASSES_CHANGED` | `failed_precondition` | `RunSetup` only: a column of `columnClasses` whose class stored now is not its `was`, or that the table no longer has (dropped or renamed since `CheckSetup`) ([Column labels on the connect page](#column-labels-on-the-connect-page)). Nothing changed; the page reads the classes again |
| `ANSWERS_INVALID` | `invalid_argument` | `RunSetup` only: an answer to a question it did not compute or a question left without one; also an `includedTables`, `columnClasses` or `restPublic` that breaks the rules of [Tables on the connect page](#tables-on-the-connect-page) and [Column labels on the connect page](#column-labels-on-the-connect-page) |
| `PASSKEY_REQUIRED` | `failed_precondition` | `RunSetup` only. Nothing changed |
| `CHALLENGE_EXPIRED`, `CHALLENGE_INVALID`, `PASSKEY_INVALID` | `invalid_argument` | `RunSetup` only ([The passkey challenge](#the-passkey-challenge)) |
| `SETUP_FAILED` | `failed_precondition` | Reading the database or the transaction failed, the passkey's registration included: nothing changed. The message is fixed per kind of failure (for example, the admin role lacks a privilege) |
| `SETUP_UNCONFIRMED` | `failed_precondition` | `RunSetup` only: the setup's `COMMIT` got no answer from the database (the connection dropped), so the setup may or may not have run. Not "nothing changed": checking the setup again tells which (`USED` when it ran). A commit the database answered with an error, or turned into a rollback, is `SETUP_FAILED` |
| `TIME_LIMIT` | `deadline_exceeded` | The call ran past 60 seconds; the transaction rolled back. A deadline that cuts off a `COMMIT` already sent, with no answer, is `SETUP_UNCONFIRMED` instead: the setup may have run |
| `RATE_LIMITED`, `BUSY` | `resource_exhausted` | [Connect limits](#connect-limits). Always with `retryAfterSeconds` |
| `REQUEST_TOO_LARGE` | `resource_exhausted` | A body over 16 KiB |
| `HANDOFF_UNKNOWN` | `not_found` | `CollectAddress`, `ReportReach` and `ReportRemoved` with no hold for the `setupId`, another engine key, or a signature that does not verify (for `ReportRemoved` also a hold that is not `REMOVED`, or a `result` or `reason` outside [The removal hand-off](#the-removal-hand-off)'s); `HandoffStatus` and `OfferAddress` with a ticket that does not verify or has expired. One answer for all of them |
| `CLOCK_SKEW` | `invalid_argument` | `CollectAddress` or `ReportReach` whose `time` is more than 5 minutes from the service's clock. No `retryAfterSeconds` |

The page shows the message. For every reason but `RATE_LIMITED` and `BUSY` it tells the person to try again later or ask the bot for a new link; the messages for `BINARY_TOO_OLD` and `CERTIFICATE_NOT_VERIFIED` say the same. These reasons are the connect service's; they are not [Error codes](error-codes.md#error-codes) of the MCP tools.

### The passkey challenge

The person creates the approval passkey on the connect page (RP ID `basaltvault.app`, origin `https://portal.basaltvault.app`), with a challenge the service made and does not store:

- `DescribeSetup` returns `challenge` (32 random bytes), `userId` (16 random bytes), `userName` and `displayName` (labels for the passkey picker, as in the [passkey registration request](approvals.md#codes)), `expiresAt` (15 minutes later), and `mac`, a keyed hash over all of them and the code's setup fingerprint, made with a secret only the service holds. `mac` is opaque to the page.
- The page creates the passkey with that challenge and user id, and sends `RunSetup` the challenge unchanged and `passkey`: the browser's answer, with the fields of the [passkey registration response](approvals.md#codes) and an optional `label`.
- `RunSetup` checks, before it connects: `mac` against the challenge's fields and the fingerprint of the code in the same request (`CHALLENGE_INVALID`), `expiresAt` by its clock (`CHALLENGE_EXPIRED`), and the registration with the engine's own check: the challenge, the origin, the RP ID, the ES256 key (`PASSKEY_INVALID`). It stores the key with `userId` as its user handle.

So a registration is refused after 15 minutes, for another setup, or after the code was swapped. The challenge is not what lets a setup run: the admin connection string is. For a code with `target`, someone who has only the link can run nothing. A connect-only code names no database, so whoever runs it first, with any database they own, sends the bot there; the person's confirmation in the chat is what stops the engine using it ([Controls](setup.md#controls)).

### The passkey check code

The page's guard against a substituted passkey. The connect page computes it in the browser from the public key the browser returned, and shows it with the result; it never shows a code the service sent in its place, and says something is wrong when the service's `checkCode` for that credential differs. After the setup is picked up, the engine names each active passkey of the database with its check code, computed from the key in `basalt_meta.passkeys`. One passkey with the same code is the expected result. A different code, or a passkey the person did not create, means stop and remove it. This detects a substituted key; it does not prevent one.

The code is the first 10 bytes of `sha256("basalt-passkey-check.1\n" ‖ x ‖ y)`, where `x` and `y` are the 32-byte P-256 coordinates of the key, in lowercase hex as five groups of four. For the P-256 base point (`x` = `6b17d1f2…d898c296`, `y` = `4fe342e2…37bf51f5`) it is `dbf5 ff76 2025 209d d866`.

### The pasted connection string

The person types it into the page; the page holds it in a variable only, never in storage, and clears it after `RunSetup`. The service:

1. Keeps it only in the memory of one request. It never writes it to a log, a trace, an error report, a metric label, a disk or another service. In `connect.proto`, `databaseUrl` carries the field option `(basalt.connect.v1.sensitive) = true`. Logs are built from an allow list of fields, request bodies are never logged, and a panic is reported without its arguments.
2. Replaces every error of the setup package with a fixed message before anything reaches the caller or a log. The package's `SETUP_FAILED` can carry the database's own words, so the mapping happens in the service, not in the package; what the service returns holds no connection string and no driver text. The service's own cloud identity has no permissions and no access to other services, so a mistake there reaches nothing else.
3. Accepts only a `postgres://` or `postgresql://` URL with one host, a port, a database, a user and a non-empty password, and no parameter but `application_name`, `channel_binding`, `connect_timeout`, `sslmode`, `sslnegotiation`, `sslsni`, `target_session_attrs`, `min_protocol_version` and `max_protocol_version`. This is deliberately narrower than the list root accepts in a credential file ([`basalt init --remote`](setup.md#basalt-init---remote-the-engines-machine), step 8): `default_query_exec_mode` and `require_auth` are left out. Several hosts, a socket path and every other parameter (`hostaddr`, `passfile`, `service`, `sslrootcert`, `sslcert`, `sslkey` and the like) are refused `CONNECTION_STRING_REFUSED`. It reads nothing from the environment: no `PG*` variable reaches the connection.
4. Requires TLS with a certificate that verifies for the host name against the system's trusted authorities, plus the provider's own roots for a Supabase or Amazon RDS host (`verify-full`), whatever the string's `sslmode` says. A host is Supabase's when its name ends with `.supabase.co` or `.supabase.com`, and Amazon RDS's (RDS and Aurora) when it ends with `.rds.amazonaws.com` or `.rds.amazonaws.com.cn`, compared in lowercase without a trailing dot; each provider's roots verify only its own hosts, as the engine does ([Trust profiles](trust.md#trust-profiles)). Or, for a connect-only code and a host no profile covers, against the one certificate authority the person trusted on the page (`trustRoot`, [Trusting a certificate authority on the page](#trusting-a-certificate-authority-on-the-page)). The admin password is never sent over a connection whose other end is not proven.
5. Requires it to name the same database as the code's `target`, as [step 3](setup.md#the-setup-checks) does (`TARGET_MISMATCH`). A connect-only code has no `target`; the database the pasted string names is the setup's target, and the service refuses a second one while it holds the first (`RUN_ELSEWHERE`).

### Where the runner connects

The person types the host, so the service could be pointed anywhere:

- The host name is resolved once, each address is checked, and the connection is made to that exact address, with the host name kept for TLS. When a name has IPv4 and IPv6 addresses, IPv4 is used.
- Only global unicast addresses are used. Refused (`ADDRESS_REFUSED`), for IPv4 and IPv6, among others: loopback, link-local (which holds cloud metadata addresses), private ranges, carrier-grade NAT (`100.64.0.0/10`), `0.0.0.0/8`, `192.0.0.0/24`, benchmarking (`198.18.0.0/15`), reserved (`240.0.0.0/4`) and broadcast, multicast, unspecified addresses, documentation ranges, and IPv6 forms that wrap or route to an IPv4 address (IPv4-mapped, IPv4-compatible, NAT64, 6to4 `2002::/16`, Teredo `2001::/32`). A name with any refused address among those it resolves to is refused as a whole.
- Any port. An unreachable host, a closed port and a timeout return the same message after the same minimum delay, so the service tells a caller little about a host that is not a database they can log in to.
- One setup per request, 60 seconds per call, and a cap on calls running at once.

### Connect limits

No accounts, so the limits are by what the service can see: requests per IP address, different targets per IP address, failed logins per target (so the service cannot be used to guess database passwords), setups run per target, and the body size (16 KiB). A **target** is the database a setup is for (for a connect-only code, the one the pasted string names): the Supabase project ref when the code has one, otherwise host, port and database, so one person's mistakes on a shared pooler host lock out no one else. The client's address is the one the service sees the call come from, never an address the caller supplied. At the cap on calls running at once, a call is refused `BUSY`, not queued. The numbers are not part of the contract, except for `CollectAddress`, which is limited apart from the setup calls: 1 call per 10 seconds per engine key, counted only for calls whose signature verified (so someone who copied the public key cannot starve the real engine), and 20 000 calls per hour per IP address for all calls (hosted bots share outbound addresses; an engine polls about 240 times an hour at most). Over a limit it is refused `RATE_LIMITED` with `retryAfterSeconds`, and the engine waits that long. `HandoffStatus` and `OfferAddress` count as page calls. `ReportReach` has the same two limits as `CollectAddress`, counted apart from it, and `PREVIEW` holds have caps of their own ([The reach check](#the-reach-check)).

### The connect page

`/connect` on the portal ([Page links](page-links.md#page-links)), a static page with its own script, covered by the release workflow's [portal check](cli.md#portal-check) like the other portal pages. It runs only at `https://portal.basaltvault.app`, the one origin the service allows (CORS, no cookies), so another site's page cannot use the service from a visitor's browser. CORS does not stop a script that calls the API directly: the [limits](#connect-limits) and the [address rules](#where-the-runner-connects) are what protect the service. Its order is fixed:

1. Read the code from the link's fragment, or from a paste box. `DescribeSetup`. The page shows a countdown from the summary's `expiresAt` (`expires in 7 min`: the time left rounded up to whole minutes, so `expires in 1 min` in the last minute). At zero, and when `DescribeSetup` refuses `EXPIRED`, it shows only `This link expired. Ask <bot> for a new one.` and no setup steps (no summary, no fingerprint, no paste, no continue). A used connect-only code is refused on open as `ALREADY_USED` (the service already holds that setup); a code replaced by a newer one for the same agent and engine is refused on open as `REPLACED`, and the page shows only `This link was replaced by a newer link. Ask <bot> for a new one.` Opening and confirming ("Yes, same code") need a live code; once the person has confirmed it, the run may finish after `expiresAt` and the countdown reaching zero does not take the page off the steps already in progress.
2. Show the summary and the setup fingerprint, and say which host this page must be on. For a connect-only code the summary says `Database: the one you paste below` where it would name the target.
3. The passkey, before anything is pasted. For an `INSTALL` code the person creates one, or signs with the one they already have for this database (`Use it`); when `CheckSetup` then says `passkeyNeeded`, the page creates one at approval, before `RunSetup`. For an `AGENT` or `UPGRADE` code the person signs once with the passkey they already have, which only this site can ask for; the page sends nothing of it. **I don't have it** skips the step, so a person who lost their only device still reaches the passkey list ([Update on the connect page](#update-on-the-connect-page)). This step is a habit that helps a returning person notice a fake site, where their passkey is not offered; it is not counted as a protection.
4. Paste the connection string. `CheckSetup`. Then one confirm step before anything else, **Is this your database?** (below). A `CERTIFICATE_NOT_VERIFIED` refusal with `trustRoot` makes it the step that also trusts the certificate ([Trusting a certificate authority on the page](#trusting-a-certificate-authority-on-the-page)). A string that does not start with `postgres://` or `postgresql://` is refused on the page before any call: `Basalt works with Postgres databases; paste a connection string that starts with postgresql://`.
5. For a connect-only `INSTALL` code with a `ticket`: the reach check ([The reach check](#the-reach-check), the page) before anything else is shown.
6. Show a refusal, or the notes and the questions. When `passkeyNeeded` and no passkey was created yet, create one now. "Before you approve" leads with the database from `database`, large, as `Supabase project <ref>, database <db>` or `<host>:<port>, database <db>`, with `This is the database your bot will use`, then the tables the agent will get (`tables` and `excluded` with `allTables`, else the code's tables), with ticks for a code with ticks ([Tables on the connect page](#tables-on-the-connect-page)) and `read only (no row ID)` after each table of `readOnly` ([Tables on the connect page](#tables-on-the-connect-page)); then, on a step the person may skip, the column labels ([Column labels on the connect page](#column-labels-on-the-connect-page)). The page asks no row-level security question: it answers `ALL_ROWS` for every included table the questions name, and says `<bot> can read and change every row of the ticked tables, and can't see the unticked ones.` With `alreadyRan` it shows neither the tables' ticks nor the labels, and says `This setup already ran; your bot is being reconnected to it.`
7. Approve: `RunSetup`. Show the result, the warnings and the passkey's check code. On `TABLES_CHANGED` the page lists the tables again (step 6), and on `CLASSES_CHANGED` it reads the classes again.
8. Say: tell your bot "done". After a finished setup, and only then, the page shows one optional line, `Want to hear when Basalt Vault launches? Join the list`, a plain link to the waitlist on `https://basaltvault.app/#waitlist` that opens in a new tab (`rel="noopener noreferrer"`). The page sends nothing there itself: no form, no field, no call to another origin. The engine notices a finished setup only when the bot asks for its status or at its hourly heartbeat. For a connect-only code instead: show `Waiting for your bot to pick up the address…` and call `HandoffStatus` every 5 seconds with the latest ticket. On `UNKNOWN`, send `OfferAddress` once. On `COLLECTED` in phase `SET_UP`: `Your bot picked up the address of <database>. It will ask you in the chat to confirm this database.` After 2 minutes without a pick-up: `Your bot hasn't picked it up yet. Tell it to check its status.` The page never says "connected": only the bot knows it logged in. `reconnected` adds `This setup already ran; your bot is being reconnected to it.`

**Is this your database?** One action, on every code, right after `CheckSetup` answers and before the tables, the Update check or the reach check: `Is this your database?`, `Check these, then continue.`, then `Database` (`currentDatabase`, `current_database()` on the login), `Host` (`<host>:<port>`), `Signed in as` (`sessionUser`) and `Certificate`: `✓ Verified by <issuer>` for `PUBLIC` and `PROVIDER` (the provider's name for a built-in [trust profile](trust.md#trust-profiles), `Amazon RDS`, `Supabase`), the issuer alone for `OWN`. **Yes, this is it** goes on; **No, go back** drops the string and goes back to the paste step, sending nothing. The page shows every value as text. The words for a certificate the provider signs itself, the bot's pin and a renewed certificate are in [Trusting a certificate authority on the page](#trusting-a-certificate-authority-on-the-page). An issuer's short name is its common name, else its first organization, else the whole subject, cut to 128 characters; it is text the database's server chose, so it changes the words only.

The page's content security policy is as strict as the approval pages' (no inline script, no third-party script, integrity hashes on its own scripts, no framing, no referrer), and allows connections to `https://connect.basaltvault.app` for this page only: its `<meta>` policy names that one source in `connect-src`, and the portal's edge function serves `/connect` and `/connect/` with the portal's header policy whose `connect-src` is `https://connect.basaltvault.app` alone (in place of the Vault the other portal pages name), the same for everyone. The page and the service answer with `Cache-Control: no-store`. The page holds the connection string in a variable only and empties the input box as soon as it reads it; after a refusal of `CheckSetup` or `RunSetup` the person pastes it again. It keeps the ticket in a variable only. For a connect-only code, the disclosure: `Your database password goes to Basalt Vault's connect service for this one setup and is never stored. The database's address (not the password) is kept in the service's memory for up to 30 minutes, until your bot picks it up.` With the reach check it says instead: `Your database password goes to Basalt Vault's connect service for this one setup and is never stored. The database's address (not the password) is kept in the service's memory for up to 30 minutes: while your bot tests that its server can reach it, without signing in, and after you approve, until your bot picks it up. Until then your bot asks the service for it regularly, for up to 40 minutes.` On a phone, switching back to the chat may suspend the tab; the engine usually collects within 15 seconds of approval, and if the tab was suspended and the service restarted meanwhile, the person opens the link again ([running again](#the-address-hand-off)).

### Trusting a certificate authority on the page

The page's version of [Pinning on first use](trust.md#pinning-on-first-use), for a database whose certificate no public authority signed (Google Cloud SQL, DigitalOcean, Aiven, a self-signed server). The service never adds trust: the person approves a fingerprint, and the bot's engine pins it only after reading the same one itself ([Pinning from the connect page](trust.md#pinning-from-the-connect-page)). A false root would need someone in front of both the service's network and the bot's.

- **What the service reads first.** For a connect-only code, and a code with a target that carries `engine` ([A changed certificate on persona 2](trust.md#pinning-from-the-connect-page)), for a host no trust profile covers whose certificate does not verify, the service connects to the checked address, sends Postgres's `SSLRequest`, completes a TLS handshake that does not verify the certificate, only to read the chain, and closes the connection: no startup message, no user name, no password. When the chain verifies against its own top (for the host name, or without it when the server certificate does not name the host), and neither the top nor the chain is from an authority in the system's trust store ([Pinning on first use](trust.md#pinning-on-first-use), Public authorities), `CERTIFICATE_NOT_VERIFIED` carries `trustRoot`: the top's `subject` (RFC 2253, at most 512 characters counted in characters, with C0 and C1 control characters and bidirectional controls removed), `sha256` (of its DER, 64 lowercase hex digits) and `expiresAt` (RFC 3339 UTC). The top is the root when the server sends it, else the highest certificate it sends. A chain that does not verify even against its own top, or a host a profile covers, gets the refusal without `trustRoot`.
- **The page.** The refusal comes before any login, so the confirm step ([Is this your database?](#the-connect-page)) shows `Database`, `Host` and `Signed in as` as the pasted string names them (read on the page, never the password) and `Certificate` as the subject's short name, with `Check these, then continue. Your provider signs its own security certificate, so confirming also trusts it for this database only.` The fingerprint is under **Details** only, as `SHA-256: <uppercase hex pairs with colons>`, with a link to the provider's documentation for finding it where one exists (Google Cloud SQL: `gcloud sql ssl server-ca-certs list`). Confirming is the person's trust: the page keeps the connection string in its variable while it asks, and nothing else is sent until the person answers. **No, go back** drops the string and goes back to the paste step. **Yes, this is it** sends `CheckSetup` again with `trustRoot` set to that `sha256`, and the page sends the same `trustRoot` with `RunSetup`. When what the service then reached (`currentDatabase`, the host and port, `sessionUser`) differs from what the string named, the page shows the confirm step again with the service's facts and asks once more; otherwise it is not shown again. Only that click sends a `trustRoot`. A detail with a `subject`, `sha256` or `expiresAt` the page cannot read is shown as the plain refusal.
- **The bot's pin.** For a code with `trustPin` (the summary's `trustPin`: the certificate the bot's engine has pinned for this host, [The setup code](setup.md#the-setup-code)), the page compares it with the refusal's `sha256`. The same: the confirm step with `Check these, then continue.` and `✓ Matches what <bot> trusts`; it still waits for **Yes, this is it**. Another: the new-issuer words of the local page's [renewed certificate](setup-page.md#the-update-check), `Is this still your database?`, `The certificate now comes from someone new. Check with your provider first. Your agents stay paused.`, the certificate marked, `Before: SHA-256 <trustPin as uppercase hex pairs with colons>`, the weaker **Trust it anyway** and **Stop here** (as **No, go back**). The code carries the pin's SHA-256, not its issuer, so the page never says `Same issuer as before`. The hint comes from the bot's code, so it only changes the words: the login, the record and the engine's own check are the same either way.
- **The login.** With `trustRoot`, the service reads the chain again, with the handshake alone, and logs in only when its top has that SHA-256 and the chain verifies against it: `verify-full` against that one certificate, or, when the server certificate does not name the host, the chain alone (`verify: ca`, as in [Pinning on first use](trust.md#pinning-on-first-use), Name-only failures). The login is made with that certificate as the only root, so the password reaches only a server that presents it. Otherwise it refuses `TRUST_ROOT_MISMATCH`. A `trustRoot` for a host whose certificate verifies without it, or that a profile covers, is ignored, and the hold carries none. A `trustRoot` with a code that has a target and no `engine` is refused `TRUST_ROOT_MISMATCH`. `RunSetup` records the certificate it logged in against with `basalt_meta.record_trust_pin` in its transaction ([Audit](trust.md#pinning-on-first-use)).
- **The hand-off.** The `PREVIEW` and `SET_UP` holds and their tickets carry the `trustRoot` the login was verified against; `CollectAddress` returns it. It is not secret, but it is part of the hold: a hold put back from a ticket has the same one.

### What the connect service sees

Everything the setup needs, for the length of one call: the setup code (with the agent's SCRAM verifier, which is [sensitive](setup.md#the-setup-code)), the admin connection string, the person's answers, the new passkey's public key, and the database itself, with admin rights. So while a setup runs, Vault is trusted as the engine is on persona 1: it could change the database or register a passkey of its own. The check code makes a substituted passkey visible; nothing in this version makes the rest visible. There is no other setup path for an agent-operated engine, so a person who does not trust Vault with this cannot set one up. The service never sees the agent's password, which stays on the bot's machine.

For a connect-only code, the service also holds the database's address in memory for up to 30 minutes, and Vault is trusted to hand the bot the right address; the person confirms in the chat the database the bot reached, before the engine logs in. Vault also sees which engines are waiting: every engine that made a connect-only code polls `CollectAddress` from its outbound address with its engine key for the code's life plus the 30-minute hold (40 minutes after the code was made), whether or not the link is opened, and whether each engine reached the address it was handed. Likewise an engine with a pending removal link polls for up to 40 minutes, and Vault sees whether it removed itself ([The removal hand-off](#the-removal-hand-off)). Logs carry only the `setupId`, never the address or the ticket.

### The address hand-off

How the bot's engine gets the address of the database a [connect-only code](setup.md#connect-only-setup-codes) ran in, without the bot or the person telling it. The engine's side is [The engine and a connect-only code](setup.md#the-engine-and-a-connect-only-code).

- **The hold.** After `RunSetup` succeeds for a connect-only code, the service keeps (as a `SET_UP` hold; `CheckSetup` makes `PREVIEW` holds, [The reach check](#the-reach-check)), in memory, a hold keyed by `setupId`: the address (host, port, database, Supabase ref; never the password or anything else of the string), the `trustRoot` the login was verified against (empty when there was none), the code's engine key, its setup fingerprint, and the expiry, 30 minutes later. It stays collectable until it expires and is marked collected on the first `CollectAddress`; collecting again returns the same address, so an engine that stopped between collecting and writing its credential collects again. A hold is never written to a log, a disk or another service. A hold made by `RunSetup` is one the engine's `CollectAddress` reaches. A code with a target that `RunSetup` ran against a `trustRoot` gets a `SET_UP` hold of its target too, with that `trustRoot`, so the engine of a `certificateChanged` setup can collect it ([A changed certificate on persona 2](trust.md#pinning-from-the-connect-page)); its `RunSetup` returns no ticket, `RUN_ELSEWHERE` does not apply (the target is fixed), and the page says to tell the bot "done".
- **The ticket.** `RunSetup` returns `ticket`, which records the address, the `trustRoot`, the engine key, the `setupId`, the setup fingerprint, the expiry and whether the address was collected (everything a hold needs, so a hold put back from it can be collected), with a keyed hash made with a secret only the service holds, which outlives a restart, under a domain string of its own, so a ticket is never accepted as a passkey challenge or the other way round. Its format is the service's; the page treats it as opaque, keeps it in a variable only and never shows it. `HandoffStatus` takes the ticket, not a bare `setupId`, so only the page that ran the setup can ask, and returns a new ticket that records `COLLECTED`, with the original expiry, for the page to use from then on. A ticket never replaces a hold that exists with another target: `OfferAddress` then changes nothing, and `HandoffStatus` answers `UNKNOWN` when the hold's target is not the ticket's, so the page never names a database the engine did not collect. `OfferAddress` checks the hash and the expiry and puts the hold back after a service restart, **with the ticket's expiry, never a new one**, and the collected state the ticket records.
- **`CollectAddress`.** The engine sends `setupId`, `enginePublicKey` (its SPKI as in the code's `engine.publicKey`), `time` (RFC 3339 UTC, whole seconds) and `signature`: ECDSA P-256 by the engine's signing key, as 64 bytes `r ‖ s` in base64url ([Primitives and encodings](vault-channel.md#primitives-and-encodings)), over the UTF-8 bytes of `basalt-connect-collect.1\n` + `connect.basaltvault.app` + `\n` + `setupId` + `\n` + the setup fingerprint as printed (five groups of four lowercase hex digits) + `\n` + `time`, with nothing after it. For the setup code `01a1f78c-52b8-7c3a-9f00-0000000000e1` of the fixtures, fingerprint `734b aaea 804e 1065 4148`, signed at `2026-11-20T06:10:00Z`, the signed bytes are the five lines `basalt-connect-collect.1`, `connect.basaltvault.app`, `01a1f78c-52b8-7c3a-9f00-0000000000e1`, `734b aaea 804e 1065 4148` and `2026-11-20T06:10:00Z`, joined by `\n`. The audience and the fingerprint are the service's own (the fingerprint is the hold's), never taken from the request. There is no nonce, since the service keeps no state for one: a captured request replays only within the 5-minute window, to the same answer.
- **Who may collect, cheaply.** The service checks `time` first: more than 5 minutes from its clock is `CLOCK_SKEW`, since that says nothing about setups. Then it looks up the hold for the `setupId`, and checks the signature only when a hold exists and its engine key equals `enginePublicKey`, so a flood of made-up keys costs a map lookup. No hold, another key and a bad signature all get the same `HANDOFF_UNKNOWN`. Someone who has the link (it holds the `setupId` and the engine key) may tell from timing whether a hold exists; that tells them only that the setup ran, which the link's owner can see too.
- **One database per code, without an oracle.** While a `SET_UP` hold exists for a `setupId` (a `PREVIEW` hold never refuses anything), `RunSetup` with the same code and a pasted string for a different target is refused `RUN_ELSEWHERE`. It is also refused `RUN_ELSEWHERE`, after its login, while a run of the same code for another database is in flight: the service claims the `setupId` for the whole `RunSetup` call, runs on the same database share the claim, and a claim is not a hold. The check runs **after** the login to the pasted database succeeded with a verified certificate, so only someone who can log in to a database learns anything, and its message is fixed and names nothing of the other database. This is best effort: after the hold expired or the service restarted, nothing refuses another database; the person's confirmation in the chat is what stops the engine using it.
- **Running the same code again.** A connect-only code that the pasted database already records as used (the same `setupId`) is not refused `USED` when there is no hold, or the hold's target is this database: `RunSetup` changes nothing, holds the address again (a new 30 minutes, with the address from the string just pasted), and returns a new ticket with `reconnected`. `CheckSetup` then answers `alreadyRan`, and `RunSetup` ignores `includedTables`, `columnClasses` and `restPublic` (they are not checked either), so the page skips the tables and the labels. A `PREVIEW` hold counts as no hold here. This is the recovery for an address the service lost and for a database the bot's machine could not reach (the person pastes a string it can reach, such as Supabase's pooler string for the same project).
- **Limits.** In [Connect limits](#connect-limits).

### The reach check

Before the person approves a connect-only `INSTALL` code, the bot's engine tests that it can reach the database they pasted, so an address the bot's server cannot use (Supabase's direct host from a server without IPv6, a firewall) shows up before the setup runs, not after it.

- **The preview hold.** For a connect-only `INSTALL` code, a `CheckSetup` that logged in with a verified certificate and answers (is not refused) makes a hold in phase `PREVIEW`: the address, the code's engine key, its setup fingerprint and an expiry 30 minutes later, as a `SET_UP` hold has, and returns `ticket`, a preview ticket (a hand-off ticket that records the phase). Another `CheckSetup` for the same code, from anyone, replaces a `PREVIEW` hold, never a `SET_UP` one: while a `SET_UP` hold exists, `CheckSetup` makes no hold and returns no ticket. `RunSetup` makes the `SET_UP` hold, replacing a `PREVIEW` one, with the address of **its own** pasted string, never the preview's; the new hold has no reach result and is not collected, and `RunSetup` returns a set-up ticket. `RUN_ELSEWHERE` looks at `SET_UP` holds and at runs in flight, never at a `PREVIEW` hold. `OfferAddress` with a preview ticket puts a `PREVIEW` hold back when there is none, and never replaces a `SET_UP` hold (nor, as for every ticket, a hold with another target). A set-up ticket ranks as `RunSetup` does: `OfferAddress` with one replaces a `PREVIEW` hold of any target with its `SET_UP` hold, so someone with the link cannot keep a lost hold from coming back by running `CheckSetup`, and `HandoffStatus` with one treats a `PREVIEW` hold as no hold and answers `UNKNOWN`.
- **Caps.** At most 5 `PREVIEW` holds per client IP address (the address of [Connect limits](#connect-limits)) and 1,000 in all. Over a cap, `CheckSetup` answers as it does without the reach check: no hold and no ticket. The page then shows the "couldn't check" answer below at once.
- **The engine on `PREVIEW`.** `CollectAddress` returns the address and the hold's `phase`. On `PREVIEW` the engine runs its own address checks and the probe with a wrong password ([The engine and a connect-only code](setup.md#the-engine-and-a-connect-only-code)) and calls `ReportReach`, and nothing else: it does not clear `awaitingAddress`, write a credential or leave `SETUP_PENDING`, and `status` and the next steps show nothing of the address (`status` reports `SETUP_NOT_RUN` as before the address came). An address that fails the shape rules is not reported, and the engine never reports on a `SET_UP` address. The engine keeps collecting, and when the address changes it checks, probes and reports again. On `SET_UP` it goes on as [The engine and a connect-only code](setup.md#the-engine-and-a-connect-only-code) says: probe, ask the person, log in only after yes.
- **Polling.** The engine polls `CollectAddress` every 15 seconds while it waits for an address or is `DATABASE_UNREACHABLE_FROM_BOT`, for the code's life plus the 30-minute hold (40 minutes after the code was made), and at once on `status`. So Vault sees a waiting engine's polls until its code expires, whether or not the link is opened; the page's disclosure and [What the connect service sees](#what-the-connect-service-sees) say so. [Collecting](setup.md#the-engine-and-a-connect-only-code) is the same rule.
- **`ReportReach`** (the engine): `setupId`, `enginePublicKey`, `time` (RFC 3339 UTC, whole seconds), `address` in its canonical form (the host in lowercase, the port in decimal without leading zeros, the database as given, the Supabase ref in lowercase or empty), `result` (`REACHABLE`, or `UNREACHABLE` with a `reason`) and `signature`. Reasons: `ADDRESS_REFUSED` (the host resolves to an address the engine never connects to), `NO_ROUTE` (no address of the server accepted a connection, or the host does not resolve), `TLS_NOT_VERIFIED` (the server answered without TLS, or with a certificate that does not verify for the host name), `TIMEOUT` (no answer in time), and `TRUST_ROOT_MISMATCH` (the hold carries a `trustRoot` and the server presents another chain top to the bot's machine, or one its certificate does not verify against: [Pinning from the connect page](trust.md#pinning-from-the-connect-page)). `REACHABLE` means a probe passed: the server answered and its certificate verified. `reason` is empty with `REACHABLE`.
- **Its signature.** ECDSA P-256 by the engine's signing key, as for `CollectAddress`, over the UTF-8 bytes of `basalt-connect-reach.1\n` + `connect.basaltvault.app` + `\n` + `setupId` + `\n` + the setup fingerprint as printed + `\n` + `time` + `\n` + host + `\n` + port + `\n` + database + `\n` + Supabase ref + `\n` + `result` + `\n` + `reason`, with nothing after it: the collect context's lines, then the canonical address and the result. An absent Supabase ref and the reason of a `REACHABLE` report are empty lines, so such bytes end with `REACHABLE\n`. For the setup code `01a1f78c-52b8-7c3a-9f00-0000000000e1` of the fixtures, fingerprint `734b aaea 804e 1065 4148`, signed at `2026-11-20T06:10:15Z`, for `aws-0-eu-central-1.pooler.supabase.com`, port `5432`, database `postgres`, ref `abcdefghijklmnopqrst`, reachable, the signed bytes are the eleven lines `basalt-connect-reach.1`, `connect.basaltvault.app`, `01a1f78c-52b8-7c3a-9f00-0000000000e1`, `734b aaea 804e 1065 4148`, `2026-11-20T06:10:15Z`, `aws-0-eu-central-1.pooler.supabase.com`, `5432`, `postgres`, `abcdefghijklmnopqrst`, `REACHABLE` and an empty line, joined by `\n`. The same report for `db.example.com`, port `6543`, database `app`, no ref, unreachable by timeout, ends with the lines `db.example.com`, `6543`, `app`, an empty line, `UNREACHABLE` and `TIMEOUT`. The host, database and ref hold no `\n`: the engine reports only an address that passed its shape rules. The context is in [Primitives and encodings](vault-channel.md#primitives-and-encodings); the shared `SIGNATURE` vectors ([`signature.json`](../api/mcp/vault/testdata/signature.json), context `CONNECT_REACH`) sign the first example.
- **How the service checks it**, in the order of `CollectAddress`: `time` (`CLOCK_SKEW`), the hold for the `setupId`, its engine key, the signature, then the limit ([Connect limits](#connect-limits)). The other failures answer `HANDOFF_UNKNOWN`, and so does a `result` or `reason` outside the values above, or a `reason` with `REACHABLE` or without `UNREACHABLE`. It keeps, for the hold's current address, the newest report by `time` (a later arrival wins a tie), and ignores a report for another address or an older one, answering it as accepted. A hold made again by `CheckSetup` or `RunSetup` starts with no report. It is the bot's own report: a bot that lies only misleads about itself.
- **`HandoffStatus`** returns, with `state`, the hold's `phase` and `reach`: the report the service kept, when the ticket's address matches the hold's (compared in the canonical form, on the service). As for every ticket, a hold with another target answers `UNKNOWN`.
- **The page.** After `CheckSetup` returned a preview ticket, the page shows `Checking your database…` with three lines: `Signed in to the database ✓`, `Found <N> tables ✓` and `Can <bot> reach it?`, with `Takes up to a minute. Your bot only tests the connection; it can't sign in yet.` It calls `HandoffStatus` every 5 seconds with the preview ticket (on `UNKNOWN`, `OfferAddress` once), for up to **60 seconds**. `REACHABLE`: `✓ <bot> can reach it`, and the page goes on. `UNREACHABLE`: `<bot> can't reach this database`, with the text of the reason, and **Paste another string**: `NO_ROUTE` and `TIMEOUT` say to use Supabase's Session pooler string; `TLS_NOT_VERIFIED` says the database's certificate could not be verified from the bot's server for this host, and to check that the string is the database's own address or to use a host whose certificate a public authority signed (a Supabase host, direct or pooler, verifies with [Supabase's roots](trust.md#trust-profiles), so the pooler string is not a certificate fix); `ADDRESS_REFUSED` says the address is private and the bot's server will not connect to it; `TRUST_ROOT_MISMATCH` says the bot's server sees a different certificate authority than the one the person trusted, so it trusts neither, to check the certificate against the provider's console, and that something between the bot's server and the database may be in the way if it changes again. No report within 60 seconds, or no ticket: `Couldn't check whether <bot> can reach it. Tell <bot> "check your status" in the chat, then retry.`, with **Retry** and **Go on anyway**.
- **Probes.** The probe on `SET_UP` reuses a passed `PREVIEW` probe only for the same resolved IP address within 5 minutes; otherwise it resolves and probes again. One flow leaves at most two probes' failed logins in the server's log.
- **What it gives away.** The bot learns, and silently probes, the address of a database someone pasted before approving, and that server sees the bot's outbound address. Someone else with the link and a database of their own can cause that too, and can replace the person's `PREVIEW` hold so that their reach check reads "couldn't check". The confirmation in the chat is unchanged, and is what protects the person ([Controls](setup.md#controls)).

### Tables on the connect page

The person may untick tables, never add one.

- **Only for codes that create the role from a listing.** The page shows ticks for an `INSTALL` code with `allTables`, connect-only or not, for an `AGENT` code with a verifier whose role does not exist (it runs as an `INSTALL`) with `allTables` or no tables, and for an `AGENT` code that names no tables whose role exists but holds no table: then the listing is the tables of `public`, and only the ticked ones are granted (nothing is revoked). `RunSetup` then requires `includedTables`: the tables left ticked, schema-qualified (`public.users`), each from `CheckSetup`'s `tables`. An empty list is `NO_TABLES`; proto3 JSON cannot tell an empty list from a missing one. `CheckSetup` returns the setup package's `Checked.Ticked` as `ticked`, and the page shows ticks exactly when it is true, with `tables` as the listing; it never sends `includedTables` otherwise. A response without `ticked` (a service older than the field; proto3 JSON also leaves out `false`) gets the earlier rule: ticks for an `INSTALL` code with `allTables`, which `ticked` always covers. For a code with `write` and `read`, and for an `AGENT` code whose role exists (a recovery code included), the page lists the tables without ticks and `includedTables` must be empty (`ANSWERS_INVALID` otherwise). An `AGENT` code that names no tables and whose role exists lists none (the column labels cover the tables the role holds): the role keeps the grants it holds, and the summary says `<agent> keeps the tables it can use now: this setup grants and revokes none.`
- **The entries.** Each is a plain lowercase `schema.table` in a schema of `allTables`, at most once; anything else is `ANSWERS_INVALID`. `RunSetup` stands alone and cannot know what `CheckSetup` showed, so an entry of that form that the listing in the setup transaction does not have (a table dropped, renamed or owned by another role since, or one that never was) is `TABLES_CHANGED`, and the page lists the tables again. A table made since is not included.
- **What it grants.** Exactly the included tables, as `allTables` grants its tables: write access, or read access for a table without a primary key ([`allTables`](setup.md#the-setup-code)), with `read only (no row ID)` after it on the page. The row-level security questions are computed for the included tables only, and the page answers `ALL_ROWS` to each of them.
- **Without ticks** (codes the page shows without ticks), the listing read again in the transaction must be the one read before it, or the setup is refused `TABLES_CHANGED`, nothing changed. The listing is read again first in the transaction, before the grants name the tables.

### Column labels on the connect page

Classes belong to the whole database and every agent ([PII classification](pii-classification.md#pii-classification)). The page lets the person label the columns of the tables the agent will get, on a step they may skip, and never erases a class or lowers one without the person choosing to.

- **Reading.** `CheckSetup` returns `columns`: each ordinary column of the tables the agent will get (the `tables` with `allTables`, else the code's `write` and `read`), read from `pg_attribute` (`attnum > 0`, not dropped), by table and then column order, with its `class`, `entityType` and `phoneRegion` from `basalt_meta.pii_columns`. A column with no row, and every column of a database without `pii_columns` (a fresh database, or a guard older than M5.1), is `UNCLASSIFIED`.
- **The labels.** Blank, **Personal** (`IDENTIFIER` with `EMAIL`, `PHONE` and its country as `phoneRegion`, `PERSON_NAME`, `ADDRESS` or `OTHER`) or **Secret** (`SECRET`). A column with another class (`FREE_TEXT`, `PUBLIC`) shows it as a fixed label with `change`, which offers **Personal** and **Secret** (never Blank, which would erase it). The step says `Labels apply to every bot on this database.` and `Columns without a label aren't masked: <bot> reads them as they are, and they can be sent to its AI provider. They'll be blocked once PII protection ships, until you label them.`
- **`columnClasses`**: only the columns the person changed, at most 500, each with `table`, `column`, `class` (`PUBLIC`, `IDENTIFIER` or `SECRET`: never `UNCLASSIFIED`, which would erase a class, nor `FREE_TEXT`, which the page does not offer), `entityType` (with `IDENTIFIER` only, required), `phoneRegion` (with `PHONE` only, required, `^[A-Z]{2}$`) and `was`: the `class`, `entityType` and `phoneRegion` the column had in `CheckSetup`. `ANSWERS_INVALID`: more than 500 entries, a table outside the included tables (the `includedTables`, else the code's tables), a column twice, a class, entity type or region that breaks these rules, or any entry or `restPublic` with a code whose `guard.to` has no `pii_columns`. An `UPGRADE` code takes them too ([Update on the connect page](#update-on-the-connect-page)): it names no agent, so its columns are chosen per table: every column of each table that has a readable column (`pii_readable_columns()`, [Readable columns](pii-classification.md#readable-columns-and-the-fingerprint)), for `CheckSetup`'s `columns`, `columnClasses` and `restPublic` alike.
- **`restPublic`**: the page's choice **Mark them as not personal** for the columns the person did not label (the choice is the confirmation: a note under it says how many columns it marks, and Continue goes on): `PUBLIC` for every column of the included tables that has no class in the transaction (no row, or `UNCLASSIFIED`). The page sends it as `PUBLIC` entries of `columnClasses` (with `was` `UNCLASSIFIED`) when all the entries fit in 500, and as `restPublic: true` otherwise. It never changes a column that has a class.
- **Writing.** In the setup transaction, after the grants, as `<prefix>_guard` ([PII objects](basalt-meta.md#pii-objects)). For each entry, the class stored now (`UNCLASSIFIED`, with no entity type and no region, when there is no row) must equal `was` in class, entity type and region, or the setup is refused `CLASSES_CHANGED` (someone classified meanwhile), nothing changed; so is an entry for a column the table no longer has (dropped or renamed since `CheckSetup`), since `RunSetup` cannot tell it from a typo and the page reads the labels again. Each entry is then written with `data_type` from the catalog ([Readable columns](pii-classification.md#readable-columns-and-the-fingerprint)), `confirmed_at` now and `confirmed_by` the admin's `session_user`; a row's suggestion, reason and `needs_review` stay as they were. Then `restPublic`, the same way. When anything was written, `pii_catalog` is set to `pii_fingerprint()`, now and the admin's `session_user`, so a running engine reloads its classes.
- **Unlabeled columns.** Continue writes nothing for a column the person did not label: it stays `UNCLASSIFIED`, warned today and refused from M5.2 until it is labeled. Under **Columns you didn't label:** the page offers **Leave them unlabeled for now** (the default) and **Mark them as not personal**, and hides the choice when every column has a label. Continue always sends the labels the person picked; with the default and nothing picked it sends no entry and no `restPublic`, and writes nothing.
